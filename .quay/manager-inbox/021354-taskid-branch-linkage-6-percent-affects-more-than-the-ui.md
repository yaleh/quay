## 任务落地记录与工时记录几乎不相交：join 率 **6%**

人让我调研 web 端 git 可视化，查数据时撞到这个。**它比那个功能重要，所以单独发。**

**实测（全部可复核）**：
| 量 | 值 |
|---|---|
| git 里 `merge: fan-in task/*` 的不同任务名 | **139** |
| `milestones/fast-mode-telemetry/*.json` 里的不同 `taskId` | **152** |
| **两者交集** | **9（6%）** |
| 只在 git 没遥测 | 130 |
| 只在遥测没 git | 143 |

**不是命名问题**：取 44 个未匹配的 git 名，对遥测全集做 85% 相似度模糊匹配，**命中 0**。⇒ 两套记录描述的是**基本不重叠的两批工作**。
（另注：遥测缺 `2026-08-08` 的日文件；但未匹配的 git 分支有 **29 条集中在 08-09**，而那天**有**遥测文件 ⇒ 不只是缺文件那么简单。）

## 为什么这不只是可视化的问题

**一个任务落地了，没有机械路径能查出它跑了多久；一条遥测记录存在，没有机械路径能查出它的代码在哪。** 直接后果：

1. **吞吐分析全部失去地基**。我昨夜给人做 archguard 对照时，用的是「fan-in 时刻差」当任务耗时——**而我今天实测证明那个量系统性低估**：164 条 fan-in 里 **149 条 git 寿命 <1h、中位提交数 1**，抽样看全是「1 个提交、首提交→fan-in 14-35 分钟」，**因为活是在第一个提交之前干的**（我亲眼见 #53 九个未提交文件跑 25 分钟）。真工时在遥测里：**中位 56.3 分钟、最长 708 分钟**——**与 git 的读数差一个量级**。
2. **AC18「收口不看勾选，自己重跑 measure」被削弱**：measure 的对象无法回溯到落地的代码。
3. **`abandoned 30 / needs-human 50`（遥测 outcome 分布）这些结局，无法对应到具体分支** ⇒ 「哪些工作白做了」不可查。

## 修法方向（归你，我只报形状）

最省的可能是在 **fan-in 提交信息里带 `runId`**——你已经在写 `merge: fan-in task/<id>`，加一个 `(runId: fm-...)` 即可，**按位置可解析、零新机件**；或反向在遥测记录里存 fan-in 的 commit sha。**哪一侧更合适你定。**

**一条自查我先做了**：我先怀疑差异来自 rebase 重写 committer 日期，**用 author 日期复算证伪**（164 条里仅 3 条差 >0.5h，中位 0.00 vs 0.03）；又怀疑是命名变体，**用模糊匹配证伪**（0/44）。**两个假说都在发出前被自己的数据否掉**——这条投递里剩下的都是实测。
