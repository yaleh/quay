人问「archguard 那 7 个任务用时多少、与本项目比如何」，我做了同窗口实测。**同一 3h31m 窗口（16:14:34→19:45:49）**：

| | archguard（ad-arm1） | quay（本机） |
|---|---|---|
| 任务完成（fan-in） | **7** | **9**（10 减去 verify-suite-prod 非任务分支） |
| 平均间隔 | ~30 min/任务 | ~23 min/任务 |
| 产品代码变更 | ~938 行插入 / 17 文件 | 2328 行插入 / 36 文件 |
| **并发** | **串行**（其 tick-log 逐字「在飞，串行」，1 在飞） | **cap=5，多 subagent** |

**最值得看的一行：quay 有 5 倍的并发预算，任务完成数只多约 30%。**

⇒ **这不是 archguard 快，是 quay 的并发没有兑现**。今晚我逐轮记录的正是原因：池荒（`pool` 一度跌到 **1**）、假候选（SUPERSEDED 占位使 `dd` 恒为假，你已修）、派发被 frontmatter 归属卡住（`self-hosted` 的 `depends_on` 边）、closure 停摆 161 分钟。**槽位是空着的，不是被占满的** ⇒ **本窗口的瓶颈在供给侧（没有合格任务可派），不在执行侧。**

**三个口径坑我明说，别拿这张表当结论**：①任务粒度不可比（archguard 是真实产品功能/修复 87~282 行/条，quay 是自己工具链的机制缺陷）；②「插入行数」是代理量不是目标量，衡量不了难度，我用它只因为它可测；③**两边窗口不独立**——quay 那 9 条里有 5 条（coldstart-usability / doc-paths / launch-settings / cross-host-support / no-wait-for-idle）**是在修 archguard 这次运行暴露的缺陷**，是 dogfooding 回流不是独立产出。

**我认为可据此判断的只有一条**：**「供给侧不足」现在有了一个外部对照点**——一个串行、单机、aarch64、第三方项目的 loop 能做到 30 min/任务，而我们五槽并行只到 23 min/任务。若你认同瓶颈在供给侧，则今晚反复出现的那几条（无合格 todo / 任务定义失效 / frontmatter 归属阻塞）就不是零散缺陷，而是**同一个瓶颈的不同切面**，值得当一个整体来治。**是否这样定性、以及怎么治，归你。**
