## 演练记录

本文档是 GOAL-905（goal 分支第二次演练）B 批的第 2 篇，内容刻意无害。

### 这一篇负责验证什么

**落后 develop 的追平。** goal 分支一旦开出来就会变旧：develop 每天有大量提交进来，
而 goal 分支只在「有任务落地」时前进。SPEC 的裁定③把这个漂移的上界定为
「该 goal 两次落地的间隔」，追平动作放在**每次任务 fan-in 的工作树里**做，
而不是单独对 goal 分支做一次 merge——理由是追平后的那棵树必须**恰好**是被全量 suite
验证过、随后被 ff 的那棵树，中间不能存在一棵「没人验证过的树」。

本文档要做的，是在自己的分支上制造一次真实的落后与一次真实的追平，
让「落后 → 合入 develop → 全绿 → ff」这条链在真实数据上跑通。

### 追平链路上每一步的观测点

| 步骤 | 动作 | 期望读数 |
|---|---|---|
| 1 | 在任务工作树里 `git merge goal/GOAL-905` | 快进，无冲突 |
| 2 | 紧接着 `git merge develop` | 产生一个 merge commit（追平） |
| 3 | anti-drift 判定 | 基准是两线合并基的并集，追平进来的文件不计越界 |
| 4 | typecheck + scoped 门 + 全量 suite | 在被追平后的树上全绿 |
| 5 | 持 goal 锁，flip done，ff goal 分支 | goal 分支 tip = 这棵验证过的树 |

### 为什么不能只在 goal 分支上单独追平

单独追平会产生一棵**只有 merge 语义、没有 suite 证据**的树；
等到下一个任务 ff 到它上面时，全量 suite 实际上是在一棵从未被完整验证过的基底上跑的。
把追平挪进任务工作树，代价是多一次 merge commit，收益是「验证过的树 = 被 ff 的树」这个等式成立。

### 不属于本文档的事

- 不规定追平的触发时机（这属于 SPEC 的机制层，不属于一次演练载荷）。
- 不记录本次追平的具体提交号：那是 Evidence 的职责，不是一篇托管文档的职责。
