## 演练记录

本文档是 GOAL-905（goal 分支第二次演练）B 批的第 6 篇，内容刻意无害。

### 这一篇负责验证什么

**方向隔离：一个方向内的工作不出现在 develop 上。** goal 分支存在的全部理由，
是让一组工作在被判定完成之前不进入 `develop`，从而不会堵住 release
（release 只从 `develop` 切）。所以本次演练最关键的一条读数，不是「文档落地了」，
而是**「它落到了哪条线上」**。

判断「落到了哪条线」有一个便宜且可靠的办法：
看这个任务的提交**是否可达于 `develop`**。可达 ⇒ 落到 develop（接线有缺陷）；
不可达而可达于 `goal/GOAL-905` ⇒ 落到了 goal 分支（接线正确）。

### 两张线各自应当看到什么

| 对象 | `develop` | `goal/GOAL-905` |
|---|---|---|
| 本任务的翻 done 提交 | 不可达 | 可达 |
| DOC-920…DOC-927 八个文件 | 不存在 | 存在 |
| 生产实例 `/doc` 页 | 列不出 | 不适用（生产不跑 goal 分支） |
| 预览实例 `/doc` 页 | 不适用 | 列得出 |
| `develop` 的历史 | 不变 | 因追平而可能分叉一次 |

### 这条性质为什么必须用「不可达」而不是「看不到」

「看不到」是一个主观读数：它可能来自分支不同，也可能来自缓存、权限、部署延迟。
「不可达」是一个拓扑事实：它由提交图本身决定，任何缓存与延迟都无法伪造它。
演练要的是后者——一个查一次 `git merge-base --is-ancestor` 就能取到、
且在被违反时会明确翻转的读数。

### 不属于本文档的事

- 不讨论 goal → develop 的最终合入（那是 goal 生命周期的收尾，不是任务落地）。
- 不承诺本批文档在演练结束后一定被删除：清理是人的决定。
