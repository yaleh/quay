## 演练记录

本文档是 GOAL-905（goal 分支第二次演练）B 批的第 7 篇，内容刻意无害。

### 这一篇负责验证什么

**fan-in 的两段合并。** 任务落地到 goal 分支时，机械 fan-in 的合并段从「一次合并」
扩成了两次，两次都发生在任务自己的工作树里，顺序固定：

1. `git merge goal/GOAL-905` —— 先把 goal 分支的当前状态接进来（通常是快进）；
2. `git merge develop` —— 再把 develop 追上（裁定③的追平）。

顺序不能反。先追 develop 再合 goal，会让「本次任务相对于 goal 分支的位置」
变得难以判断，也会让第二段合并更容易落到一个非快进状态上。

### 两段合并各自的失败形态

| 段 | 动作 | 常见失败 | 期望的处置 |
|---|---|---|---|
| 第一段 | merge goal 分支 | goal 分支已被并发的邻批推进 ⇒ 非快进 | 正常合并，产生 merge commit |
| 第二段 | merge develop | develop 与 goal 分支改到同一文件 ⇒ 冲突 | 停在原分支，留痕，不静默丢弃 |
| 合并后 | anti-drift 判定 | 追平进来的变更被判成「越界」 | 基准取两线合并基的并集 |
| 合并后 | 全量 suite | 真正的红 | 修复后重跑，不得跳过 |

### 为什么「冲突」在这里是预期内的

A、B、C 三批并发落地，三者的 Touches 互不相交，但它们都要经过同一个合并段。
第一段落地的任务会把 goal 分支往前推，于是另外两条的第一段合并就不再是快进。
这不是接线缺陷，而是并发落地的正常形态；接线要保证的是**它被正确处理并留下痕迹**，
而不是「它不会发生」。

### 不属于本文档的事

- 不规定重试次数：重试策略是驱动层的事，本篇只描述合并段本身的形状。
- 不替代 Evidence：本次实际发生了几次非快进、几次重试，记在任务的 Evidence 里。
