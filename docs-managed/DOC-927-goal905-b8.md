## 演练记录

本文档是 GOAL-905（goal 分支第二次演练）B 批的第 8 篇，内容刻意无害。
它是 B 批的最后一篇，因此多承担一件事：**收尾读数**。

### 这一篇负责验证什么

**落地之后不再被派发。** 一个任务落地之后，它必须从「可派发」集合里消失。
否则调度会反复把同一个已完成的载荷派出去，看起来像「机器很忙」，
实际是在空转——而空转与正常工作在提交图上长得几乎一样，唯一能区分它们的，
是任务的**状态**与**落地证据**是否对得上。

B 批落地完成后，正确的读数有三个，缺一不可：

1. 三个任务的翻 done 提交都在 `goal/GOAL-905` 上（不在 `develop` 上）；
2. goal 分支已经追平过 develop（追平 merge commit 存在）；
3. `develop` 上不存在这三批文档，因而生产实例的 `/doc` 页列不出它们。

### 收尾时最容易含糊过去的三处

| 容易含糊的地方 | 含糊的说法 | 可核的说法 |
|---|---|---|
| 落地位置 | 「已经落地了」 | 翻 done 提交在 goal 分支上可达、在 develop 上不可达 |
| 追平 | 「顺手追了一下」 | goal 分支上存在一个来自 develop 的 merge commit |
| 清理 | 「脏数据回头再说」 | 明说本批不负责清理，并指明由谁决定 |

### 为什么这一篇仍然要写满 30 行

因为「短文档也能通过」本身就是一次演练要排除的失败形态：如果 30 行的门槛
可以被一篇 12 行的文档绕过，那么这条门槛就是装饰。八篇都写满，
这条门槛才在本次演练里被真正检验过一次。

### 不属于本文档的事

- 不承担 GOAL-905 的完成判据：GOAL 的 AC 由预览实例上的实测读数取得。
- 不代表任何后续批次的模板：后续批次应当重新按自己的验证目标撰写。
