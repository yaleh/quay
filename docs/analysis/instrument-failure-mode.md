# 主导失效模式：仪器的名字与它测量的东西不符

**日期**：2026-08-03
**来源**：2026-08-02 17:43Z 起的无人值守窗口 + 当日全期的实测记录
**用途**：exp6 的能力优先级与裁剪判据

---

## 1. 触发这份分析的数字

无人值守窗口内收尾 **8 个**任务：

| 类别 | 个数 |
|---|---|
| 仪器/观测层修复 | **5** |
| 找回几天前已完成的滞留工作 | 3 |
| **真正的新功能 / 产品工作** | **0** |

全期 15 个收尾任务里，仪器类 7 个。

**执行引擎整晚没出过问题**：三路并发跑起来了、worktree 隔离无冲突、三次合并全部落地、
`orphaned` 归零、没有丢失任何工作。外层介入 21 次，**没有一次是因为调度、并发资格或合并出错**。

消耗掉整晚的是**说谎的仪器**。

## 2. 失效模式的清单

| 仪器 | 名字承诺 | 实际测量 | 后果 |
|---|---|---|---|
| `tasksPerHour` | 每墙钟小时完成的任务数 | `60 / 均耗时`（单任务速度） | 整天的吞吐报告系统性高估；并发使它**反向** |
| `sync-vendor` 的 DRIFT 标签 | `vendor/task-schema.ts` | `dist/quay.js`（前者根本不存在） | M136 被误诊三轮 |
| `test-coverage-check` | `test.sh` 的 canonical glob | 匹配到空数组声明 ⇒ 返回 `[]` | **CI 检查静默失效**，exit 0 |
| `scripts/test.sh <flag>` | 加一个 node 标志 | 静默换掉整个测试集（2296 → 8573） | 一整组对照实验作废 |
| `duration_ms` | （被读作）Σ 每文件耗时 | 该次运行的墙钟本身 | 「lane 未饱和」结论由计算方式而非并发度决定 |
| M136 的「flaky」定性 | 不稳定、偶发 | 连查 3 次每次恰好 1 行 DRIFT，**确定性** | 被判为可忽略，放行了两轮 |

外层自身另有 **7 次** grep 匹配到「提到 X 的文本」而非 X 本身
（提交消息里的 `revert`、`pgrep -f` 匹配自己的命令行、`echo` 字符串里的 `test.sh`、
修复文档里的缺陷名、注释里的 `process.exit(1)`、缺陷自己的文档、`local ` 前缀导致的漏匹配）。
**最后一次差点让外层否掉内层一个正确的发现。**

## 3. 这个模式的两种形态

**形态 A：名字与计算不符。** `tasksPerHour`、`duration_ms`、DRIFT 标签。
读者按名字理解，按错误的量做判断。**危险在于它一直「正常工作」。**

**形态 B：静默降级。** `test-coverage-check` 匹配不到就返回 `[]` 然后 exit 0；
`test.sh` 加个标志就换掉选择集但输出看起来完全正常。
**危险在于「没有发现问题」与「没有在检查」不可区分。**

两种形态的共同点：**输出是合法的、看起来正确的、且不包含任何「我可能没在做我声称的事」的信号。**

## 4. 对能力优先级的含义

**exp6 阶段 1（引擎）**：引擎比原判断更接近够用。缺的不是执行能力，是**仪器的契约**。

**产品化**：双层机制的可观测性今晚**完全是临时搭建的**——`inner-forensics.mjs`、两个 Monitor、
blocked-signal 都是边跑边造。而 blocked-signal 证明了正确形态：检测延迟从最多 20 分钟降到
**< 1 秒**，并产出一个**此前根本不存在的量**（死时间基线 8.2s）。

## 5. 裁剪判据

今晚**赚回自己成本的每一个机制，都是能大声失败且可廉价核对的**；
**消耗时间的每一个，都是报告成功却测错了东西的**。

因此判据不是「它贵不贵」，而是：

> ### 它能不能安静地说谎？

能安静说谎的机制，无论多便宜，**要么加契约要么删掉**；
会大声失败的机制，即使贵也值得留。

这条比 exp6 §0 现有的「元机制应比对象机制简单一个数量级」更可操作——
后者衡量规模，前者衡量**失败时的可见性**，而今晚的代价全部来自后者。

### 按此判据的裁剪结论

**可以裁**

| 对象 | 依据 |
|---|---|
| prepare 管线（ProposalReview / PlanCheck） | 今晚 18 个任务、**零个 `## Plan`、零条 prepare-epoch**，而失败**没有一次是计划失败**。诚实保留：外层确实做了机制审查（36% 的 tick 是 `correct`），所以它是**转移**而非消失——[[gap-dispatch-gate-has-no-checklist-and-no-trace]] 是便宜的替代 |
| `tasksPerHour`（`60/均耗时`） | `meanMinutes` 已在同一输出里，它是确定性变换，不提供新信息 |

**今晚证明不能裁**

| 对象 | 它今晚抓到了什么 |
|---|---|
| 对抗审查（REFUTE 轮） | `=` 拼写歧义、空格形式落进 explicit-file 分支、正则字面量遮蔽 |
| 负控制（tampered fixture） | 唯一能证明「M136 的修复不是掩盖」的东西 |
| `checkTouchesPair` | 每一次并发组批都是实测，一次都没目测 |
| 「连跑 2 次」 | **推翻了 AC1**——第一次 0 失败，第二次 fail 1 |

四者的共同点：**它们都会大声失败**。

## 6. 裁剪任务（人 2026-08-03 指出：分析找出了「能裁什么」，任务却只建了「该加什么」）

**这是一个真实偏差**：本文档第 5 节列出了可裁对象，而首轮只为「加检查」建了任务。
方向应当是**建立可持续高效的开发机制**，而清理是其中必要的一半。

| 任务 | 规模 | 依据 |
|---|---|---|
| [[gap-reclaim-21-merged-worktrees-and-fix-my-bad-criterion]] | **1.1G / 21 个 worktree** | `merge-base --is-ancestor` 实测 21/22 为真、`git cherry` 0 个未合并提交 |
| [[gap-retire-the-prepare-execute-pipeline-cluster]] | **约 14,658 行 + 25 个测试文件** | 最后一条 prepare-epoch 是 22 小时前；窗口内 18 个任务零 `## Plan` 零 epoch；失败无一是计划失败 |

**关于第二个的一次方向修正（人 2026-08-03）**：我一度提出「它的价值依赖于模式，人驱动单会话模式下
仍是对的，所以降为可选而非删除」。**这个推论是错的**——quay 交付的就是双层机制，它存在的目的正是
**改变**人驱动单会话那种工作模式，不是适配它。模式依赖性解释的是**它当初为什么被造出来**，
不是保留它的理由。已改回退役。

### 第一个裁剪任务顺带修正了本文档自己制造的一个「名不符实」实例

昨夜写进 `gap-stranded-worktree-branches-have-no-alarm-channel` AC2b 的判据是
「提交数 0 **但两点 diff 非空** ⇒ `merged-then-reverted`」。**它是错的**：两点 diff 比的是两棵树，
master 前进后任何旧的已合并分支都非空。实测 **21 个分支全部被误报**，而真正的
merged-then-reverted 只有 M243 一个（且已恢复）。

按该判据 `--clean-stale` 会拒绝清理全部 21 个，**1.1G 永久留存**——
**判据的名字说「被 revert 了」，实际测的是「master 有没有前进」**。

这使第 2 节的清单增加一条，且这一条是**本次分析自己产生的**：

| 仪器 | 名字承诺 | 实际测量 |
|---|---|---|
| `merged-then-reverted` 判据 | 分支被合并后又被 revert | master 自合并以来是否前进过 |
