# quay network 的原型：今天已经有什么、缺什么、以及一条最容易做错的事

**日期**：2026-08-03
**来源**：人提出「现在这样的多项目 quay 协调开发已经可以看作一个 quay network 的原型：
项目之间应当可以通信（archguard 发现 quay 的 bug 应当能报给 quay）；
通信也不应限于 tmux，TCP/IP 或其它跨主机机制是必然。」
**性质**：方向讨论 + 今天的实测。**不是实现计划。**

---

## 1. 今天已经有的三层，性质完全不同

| 层 | 载体 | 跨项目？ | 跨主机？ | 有结构？ | 持久？ |
|---|---|---|---|---|---|
| **内容** | git 提交、`tasks/*.md`、`cold-start-gaps.md` | 否（各仓独立） | git 可以 | 是 | 是 |
| **协调** | `heavy-op-token.sh`（`$HOME/.quay-global/`）、`.halt` | **是** | 否（同一文件系统） | 弱 | 是 |
| **唤醒** | `tmux send-keys` | 是 | **否** | **否** | **否** |

**⇒ 需要 TCP/IP 的是唤醒层，不是内容层。**
内容早就在 git 里流动了；今天 archguard 的 `cold-start-gaps.md`（95 行）
从写下那一刻起就对 quay 可见——**只是没有任何东西去读它**。

## 2. 传输面比想象的近

- **两个项目各自已在监听 HTTP**（`:4173`、`:4174`），今天同时跑着
- **已有写入端点**：`POST /task/<id>/action/<actionId>`——不是只读服务
- **MCP 有写能力**（`task_write` 等）**但传输是 Stdio**——工具齐全，只是过不了主机边界

**缺的三件**：
1. **寻址**——archguard 怎么知道 quay 在哪。今天的答案是「管理者知道」
2. **投递语义**——往**另一个项目**提交一条报告的端点（现有 POST 只作用于已存在的任务）
3. **MCP over HTTP**——工具已经在，只差传输

## 3. 今天的实测：我是路由器，而且是单点

archguard → quay 的 4 条、quay → archguard 的 3 条，**全部经我手工搬运**。
`cold-start-gaps.md` 至今**只有我读过**。

**但这不只是瓶颈问题。** 我搬运时做的事，一个自动转发不会做：

| 我准备转发的 | 实际 |
|---|---|
| lint「exit 0」⇒ 一个报 480 error 还判绿的闸 | 退出码是 **1**，我在管道后读了 `sed` 的 |
| 「`ps` 命令被判为套件运行」 | 那条命令**真的跑了套件**，我读的是截断显示 |
| 「quay 板子挂了」 | `curl -m 5` 超时，进程与端口一直正常 |
| 「`OVERDUE` 该报而没报」 | 我把 17 分钟算成了 55 分钟 |

**四条我自己产生的假信息，在转发前被我自己拦下。**

## 4. 因此：跨项目消息应当携带证据，不是结论

这与本仓已在用的规则同源——管理者对外层是**「给证据，不写任务体」**。

**接收方必须能从证据重新推导出结论，而不是相信它。**

具体到设计：

- 一条跨项目报告的**必填字段是复现方式**（命令 + 期望 + 实得），不是「描述」
- 接收方**默认不信任**：一条来自他项目的报告进入队列时应当是**待核实**状态，
  而不是直接成为任务
- **来源必须可追溯**：哪个项目、哪个会话、哪个提交
- **不要做自动转发**——今天四次假信息说明，转发链上没有验证环节就是放大器

## 5. 一个最小可做的第一步（不是计划，是候选）

**让 `cold-start-gaps.md` 这类文件有读者。**

今天它已经是跨项目内容——写在 archguard 的 git 里、对 quay 可见、95 行结构化。
缺的只是「quay 侧有东西定期去读，并把其中可复现的条目转成待核实任务」。

**这一步不需要 TCP/IP、不需要新协议、不需要改 quay 的 schema**，
而它能立刻消掉「管理者是单点路由器」这一条。
**先把同主机、经 git 的那条路走通，再谈跨主机**——
否则会同时引入传输问题和信任问题，而今天的数据表明**信任问题更难**。

## 6. 诚实的限度

- 本文的「网络」只有 **2 个节点**（quay、archguard），meta-cc 未启动
- 全部在**同一主机、同一文件系统、同一个人**之下——
  真实网络的所有难点（分区、时钟、身份、恶意节点）**一个都没遇到**
- 「我拦下了四条假信息」是**单点验证有效**的证据，
  **不是**「去掉单点后仍然有效」的证据。**去掉我，谁来验？** 本文没有答案。

# 7. 计价：让「携带证据」从规则变成经济上的自我执行

**人 2026-08-03 提出**：「提出需求的人要付钱。」

*（管理者先把这句读成了共识机制，答了一通「区块链解决不了『这句话是不是真的』」——
**读错了**。人说的是**计价**，不是信任裁决。这个误读本身值得留着：
「为 X 找到应用场景」这句话里的 X，我按自己熟悉的那一面去解了。）*

## 7.1 今天已经量到的价格信号

第 3 节那四条假信息之外，损失函数（`monitor-loss-function.md`）量到的是**处理成本的分野**：

| 接收一条跨项目消息 | 工具调用 |
|---|---|
| 事件自带成因，一行打发 | **1** |
| 要采样、diff、追根因 | **4** |

**4–5 倍的差价，今天全部由接收方承担。**

archguard 写 95 行 `cold-start-gaps.md` 几乎不花它什么；
管理者读它、逐条核实、转成可行动的东西，花的是管理者的 token。

**⇒ 发送方不承担接收方的验证成本，就没有任何力量促使它把结论写成证据。**

## 7.2 计价把规则变成硬形变

第 4 节写的原则是「跨项目消息应当携带证据，不是结论」——**那是一条规则，也就是散文**。
按 `prediction-prose-drifts-checks-hold.md` 的判断，散文会被侵蚀。

**计价改变的是可达性**：

- 带复现方式（命令 + 期望 + 实得）⇒ 接收方一次调用即可验 ⇒ **便宜**
- 只给结论 ⇒ 接收方要自己去查 ⇒ **贵，且贵在发送方账上**

**发送方会自发把证据写全，不是因为文档要求，是因为省钱。**
这是 `docs/references` §8.3 意义上的**硬形变**——不是更高的墙，是改写了什么划算。

## 7.3 区块链在这里的确切位置

**不是**用来对「谁说了什么」达成共识——git 已经给了有序、防篡改、可追溯、带作者，
加签名提交就补上身份。

**是**用来在**没有共同账户的参与方之间计量与结算**。

今天三个项目共用同一个人的账户 ⇒ 计价退化为**内部记账**：
仍有价值（让成本可见、可归属），**但不需要链**。

**需要链的条件是跨账户、跨主体**——那正是「跨主机协作」真正到来时的样子。
在此之前引入它，是为一个不存在的结算问题付协议成本。

## 7.4 这个方向也约束管理者自己

第 3 节的四条假信息**全部是管理者自己产生的**，不是 archguard 产生的。

按「提出需求的人付钱」，**管理者作为发出错误请求的一方，
应当为让别人去验一条假消息而付费**。

⇒ 这个激励**同样约束单点路由器**，而第 4 节那套「接收方默认不信任」的规则不约束它。
**定价对称，规则不对称。**

## 7.5 未解的

- **谁定价**：一次验证值多少 token？今天只有「1 次调用 vs 4 次调用」这个相对量
- **怎么计量**：token 消耗归属到「哪一条跨项目消息」，今天没有任何机制
- **误报的次生成本**：验一条假消息不只花验证的钱，还可能引出错误动作
  （今天有一例：管理者据一个假前提让 archguard 停 loop，而它的 loop 早就停了）
- **恶意与错误的区别**：计价对二者都收费，但**错误方不该被当成攻击者**——
  今天所有假信息都是诚实的错误
