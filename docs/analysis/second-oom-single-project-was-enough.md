# 第二次全机 OOM：这次只有 quay 一个项目在跑

**时间**：2026-08-04 约 06:39–06:49Z（崩溃前最后活动 06:38:53Z，会话在 06:49–06:52Z 重建）
**与第一次的关键差异**：第一次是三个项目（quay/archguard/meta-cc）六个会话同时跑；
**这次 archguard 与 meta-cc 都没有恢复，只有 quay 一个项目、四个会话**（管理者/外层/内层/至少一个 subagent）。

---

## 1. 排除掉的假设（有证据）

| 假设 | 结论 | 证据 |
|---|---|---|
| archguard/meta-cc 意外复活 | **排除** | 进程枚举无命中；先前的 `meta-cc*` 命中是我自己用的 meta-cc MCP 服务器，不是项目会话 |
| 我那条「恢复并发派发」指令导致的 | **证据不支持，但不能排除风险** | 指令发出于 06:38:24Z；崩溃窗口在其后 <30 分钟内；**遥测显示崩溃窗口内没有新的 `task-start`**——没有证据外层已经真正派发了第二个任务 |
| 我自己的 tmux e2e 诊断命令 | **可能性低** | 命令本身极轻（`mktemp` + 小 tmux socket + 一次 `quay-init.sh --loop` 调用），不含 `node --test`；先后跑了两次(06:38:43/52)，第一次遗留了目录未清理，但那只是几个空目录，不是内存 |
| 仓库/worktree 数据损失 | **无损失** | 三个 worktree 状态干净，`git status` 只有一个 gitignore 内的生成文件 |

## 2. 确认发生的重叠（有证据，但因果强度未知）

**`full-suite-12.log` 创建于 06:38:16Z**——这是内层的 DoD 门（8-lane `node --test`，本仓已知在 4 核机器上是 4.25× 超订）。日志戛然而止，最后一条是一个真实的测试失败（`worktree-root-fs-check.test.mjs` AC4），**没有终结摘要**——不能判定是套件自然结束还是被崩溃打断。

**同一时间窗口，至少 4 个会话在跑**（用 meta-cc 按 session_id 分开确认）：
- 管理者（我）：轻量诊断
- 外层（`dc6a47bd`）：`task_write`、`ToolSearch`、`TaskStop`+`Monitor`（重挂自己的监视器）
- 一个 subagent/fork（`9957a092`）：在独立的 `verify` worktree 里跑真实 tmux e2e 测试（起 tmux server + `quay-init.sh --loop`）
- 内层：在前台阻塞跑 `full-suite-12`（本身即为重活）

## 3. 结论（诚实分级）

**排除**：三项目并发、archguard/meta-cc 复活、数据损失、我的诊断命令是主因。

**观察到但因果未证实**：full-suite-12（8-lane 超订）与至少三个其他会话（含一个正在做真实 tmux/进程操作的 subagent）在同一窗口重叠。

**没有找到**：单一元凶。**没有 `dmesg`/`journalctl` 权限**（与第一次相同），无法直接确认 OOM killer 触发，「OOM」仍是从「多进程同时死亡 + 与第一次同型」推断的，不是内核日志确认的。

**新的、比第一次更重要的结论**：

> **第一次 OOM 的教训是「三个项目跑不下」。这一次表明，即使只有一个项目、一个 DoD 全量套件加日常会话开销，也可能跑不下。**

这把安全边界往下修了一大截——此前的容量讨论（12/16/18 核方案）默认的最坏情形是三项目并发；**这次说明单项目的正常工作（一次 8-lane 套件 + 几个并发会话）已经贴着上限**。

## 4. 对下一步的直接影响

**在没有内存遥测之前，不应该恢复「并发派发多个后台 subagent」那条指令**——它此刻还没被证实是这次的原因，但按上面的新结论，它在单项目场景下也是加重因素而不是安全的。

**恢复顺序建议**（不是本文件的裁定，供人参考）：
1. 先确认这次崩溃时套件并发（8-lane）是否本身已接近或达到内存上限——需要给 `scripts/test.sh` 加一次性的峰值 RSS 记录（比在生产里加令牌 `waited_ms` 更紧急，因为它现在无法回答"是不是套件本身就够呛"）
2. 在有峰值内存数据之前，重启 quay 双层时**不要**同时派发多个后台 subagent，退回严格串行
3. `A6`（worktree 移出 tmpfs）与套件 lane 数的关系需要重新评估——4.25× 超订这个数字是在「假设机器只服务一个套件」下定的，**现在两次 OOM 都发生在「套件之外还有其他活跃工作」的场景**，超订倍数应该按「机器总负载」而不是「单套件」来定
