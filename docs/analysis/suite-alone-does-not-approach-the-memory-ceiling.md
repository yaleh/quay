# 实测：全量套件独立运行，从未接近内存上限——OOM 不是套件本身的问题

**日期**：2026-08-04（管理者，第二次全机 OOM 之后，人要求「先测量再恢复」）
**数据**：`quay-worktrees/mem-sample-1785831266.log`（85 条采样，每 2 秒一条）+
`quay-worktrees/full-suite-measure-1.log`（`scripts/test.sh` 完整输出）

---

## 1. 测量设计

**隔离变量**：不恢复 archguard、meta-cc，也不恢复 quay 的 inner/outer 会话。
只有管理者（本会话，做轻量诊断）+ 全量套件本身在跑。**这样套件的内存占用是唯一被测量的变量。**

- 后台采样器：每 2 秒记录一次 `MemAvailable`、swap 用量、全部 node 进程 RSS 合计、node 进程数、load average
- 安全监视器：可用内存 <2000MB 报警，<800MB 建议立即中止（全程未触发）
- 套件：`timeout 900 bash scripts/test.sh`（本仓完整 canonical glob）

## 2. 结果：内存从未接近危险区

| 量 | 基线 | 峰值/谷值 |
|---|---|---|
| 可用内存 | 11511MB | **最低 10465MB**（降了约 1GB，远高于 16GB 总量的安全线） |
| swap 用量 | 779MB | **765MB（没有增长，甚至略降）** |
| node 进程 RSS 合计 | 1778MB(13 进程，MCP 服务器基线) | **峰值 2856MB(23 进程)** |
| load average | 1.30 | **峰值 19.59**（4 核上的严重排队，但这是 CPU/调度指标，不是内存指标） |

**`si`/`so` 全程为 0（可从 swap 用量不增长间接确认）——没有发生真实换页。**

## 3. 结论

**全量套件独立运行时，峰值内存占用约 1.1GB 增量，可用内存底线 10.4GB。
这与「机器 16GB 会被套件本身耗尽」的假设不符——套件不是元凶。**

**这直接更正了 [[second-oom-single-project-was-enough]] 里的一条推测**：那篇文档把
「全量套件 + 几个会话重叠」列为观察到但因果未证实的相关项，**现在可以排除套件本身的内存占用作为主因**。
真正的候选收窄到：**多个成熟 Claude Code 会话/subagent 的进程开销总和**（每个约 700–900MB，
今晚实测过）+ **tmpfs 占用**（worktree、scratch，已知可达数 GB）——**这两项在本次隔离测量里都不存在**，
所以两次 OOM 与本次「安全」的差别，最可能的解释是「有几个成熟会话同时活着」，而不是「套件在跑」。

## 4. 一个独立的、真实的问题：CPU 超订导致测试挂起/失败

**这次测量本身产出了一次真实的套件失败**，与内存无关：

```
tests 2210 · pass 2185 · fail 0 · cancelled 1 · skipped 24
duration_ms 885411.92（≈885秒，超过本仓已知单次范围 402–700s）
✖ plugin/test/runner-grouping.test.mjs（487402ms ≈ 487秒）
  'Promise resolution is still pending but the event loop has already resolved'
EXIT=124（timeout 900 到点杀掉）
```

**一个测试独占了套件近 55% 的墙钟并最终以内部错误告终**，同一窗口 load 峰值 19.59（4 核 4.9× 超订）。
`si`/`so` 全程为 0，可用内存底线 10.4GB——**排除内存/换页导致的挂起**，
症状指向 **CPU 调度层面的资源枯竭**（8-lane 固定并发在 4 核上排队过久，事件循环得不到调度）。

**这与本仓已知的「lane 仍饱和」结论一致，但给出了一个新证据**：超订不只是让墙钟变慢，
**在极端情况下会让单个测试的内部状态机（Promise 生命周期）出错**，
产出一次这台机器上从未见过的、非确定性的红。

## 5. 对下一步的影响

1. **OOM 的排查方向应从「套件」转向「并发会话数 + tmpfs」**——具体是：
   - 恢复 quay 双层时，先只恢复 inner+outer 两个成熟会话，观察内存基线
   - 令牌等待时长遥测（`waited_ms`，先前已要求但未落地）仍然需要，但现在的问题不是「套件本身多贵」，
     是「重活令牌串行化套件，却不限制同时存活的会话数」
2. **CPU 超订本身是独立于 OOM 的一个正确性问题**——固定 `--test-concurrency=8` 在 4 核机器上
   已经产生过一次真实的挂起。AC5 那个"暂定并发实验"应当把这次挂起记进反例。
3. **诚实限度**：本次测量只跑了一次（未做 σ 纪律要求的多次重复），
   885s 是否是常态还是这次特有的异常需要更多样本；**但内存结论(峰值 2856MB/最低可用 10465MB)不依赖重复次数——
   它是这一次运行的直接观测，且全程没有触及任何危险阈值，方向足够清楚不需要重复来验证「安全」这一半结论。**
