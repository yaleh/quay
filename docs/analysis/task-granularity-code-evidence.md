## 3. 颗粒度建议：三层模型

根据实际代码变更数据，将任务分为三层：

### 3.1 原子任务（单 commit 可直接完成）

| 指标 | 范围 | 典型案例 |
|---|---|---|
| 代码插入 | 50-500 行 | epoch-status 解析回退（+50）、TOCTOU 加固（+589） |
| AC 数 | 3-10 | DIR-124-A3b（6 AC）、DIR-103-A（11 AC） |
| 机制数 | **1** | 一个清晰的单一变更 |
| 文件 | 1-5 | 一个核心文件 + mirror + 测试 |
| 完成时间 | ~10-30 分钟 | 一个 agent 在一个 worktree 中完成 |

**定义：** 一个 agent 可以不中断地阅读、编辑、测试、提交。不需要中间 checkpoint。测试失败时原因明确。审核者可以一次看完全部 diff。

DIR-126 的 5 个子任务（各 1 个机制）是这种粒度的典范——每个都很大（700-1,000 行），但**机制单一**，因此可单独完成。

### 3.2 复合任务（需要 2-3 个原子子任务）

| 指标 | 范围 | 触发拆分的原因 |
|---|---|---|
| 代码插入 | 500-1,500 行 | — |
| AC 数 | 11-20 | DIR-124-A2（15 AC，460 行）——但完成了 |
| 机制数 | **2** | 两个紧密耦合的变更，一起做更高效 |
| 文件 | 3-10 | — |

**定义：** 可以作为一个 milestone 完成，但如果 ProposalReview 发现阻塞性发现超过 3 个，就触发 `split-subsystem-blocking-cluster`。这类任务应该先**消耗可修复绕行**（一轮聚焦修改），只有绕行失败才拆分。

### 3.3 必须拆分的任务

| 指标 | 范围 | 信号 |
|---|---|---|
| 代码插入 | 1,500+ 行 | — |
| AC 数 | 15+ | — |
| 机制数 | **≥3** | `split-multi-mechanism` |
| 文件 | 8+ | `split-touch-set-too-large` |
| 发现聚集 | 同子系统 3+ 阻塞性发现，绕行失败 | `split-subsystem-blocking-cluster`（绕行后） |

**定义：** 无法在单个 milestone 中可靠完成。拆分成 1 机制/任务的原子单元。

## 4. 核心指标：不是行数，是机制数

### 4.1 行数是误导信号

```
DIR-124-A1a: 1 机制, +2,876 行 → 正常（schema 定义就是长）
DIR-099-C:   1 机制, +700 行   → 正常（MCP handler + 合同文档）
DIR-123:     5 机制, +2,074 行 → 应拆分（即使代码量不如 A1a）
```

**规则**：`extractMechanismClaims` 提取的机制数，比代码行数更准确地预测任务是否应拆分。

### 4.2 "1 机制"的两种形态

| 形态 | 代码量 | 例子 |
|---|---|---|
| 纯逻辑 | 50-200 行 | epoch-status 解析回退（+50 行）、prepare-merge schema（+2 行） |
| 模板/基础设施 | 500-3,000 行 | schema 定义（+2,876 行）、新 CLI 子命令 + 测试（+2,297 行） |

机制数相同但代码量差异可达 50 倍。拆分逻辑不应按代码量调整——**1 个机制的模板代码也是 1 个机制**，不应拆分。

### 4.3 中位数的实际意义

64 个快速流程 commit 的中位数是 ~300 行插入。这不是"目标值"——这是自然收敛值。一个 agent 在一次会话中产生的代码量，中位数刚好在 300 行附近。

**结论**：300 行不是规范性目标。但它是一个**校准参考**——如果一个任务预计超过 500 行，就应该检查它是否包含 >2 个独立机制。如果是，拆分。如果不是（如 schema 定义），让它大。

## 5. 对拆分机制的建议

### 5.1 `> 2` 机制阈值保持不变

数据支持当前的 `> 2` 阈值：

- DIR-126 子任务（各 1 机制）全部完成
- DIR-124-B（4 机制）正确拆分为 4 子任务
- DIR-124-F（6 机制）正确拆分为 6 子任务
- DIR-099-A（2 机制）正常完成——没有触发拆分

### 5.2 改进机制提取的校准

DIR-124-A1b 的"14 wiring claims vs 6 AC"说明 `extractMechanismClaims` 将覆盖率条目（"instrument all 8 phase boundaries"）计数为 8 个独立机制。应该修正为：**同一模式的 N 个实例 = 1 个机制，不是 N 个**。

### 5.3 拆分深度指导

| 机制数 | 建议子任务数 | 每个子任务的预计代码量 |
|---|---|---|
| 3 | 3 | 200-500 行 |
| 4-6 | 4-6 | 100-500 行 |
| 7+ | 按子系统群组拆分 | — |

DIR-124-A1（拆成 2 个子任务，但每个仍然 >2 机制）是拆分**太浅**的典型——应该在第一次就拆到足够的深度，避免子任务再次触发 split。

### 5.4 不要拆 schema 定义

DIR-124-A1a（+2,876 行，1 个机制）是正确的——不应拆分。Schema/类型定义天生就长，但这不代表它包含多个独立交付物。`extractMechanismClaims` 对"定义类型"的正确分类（1 个机制）已经覆盖了这一情况。

## 6. 总结

| 问题 | 答案 |
|---|---|
| 合适的任务颗粒度是什么？ | **1 个机制，1 个 milestone。** 代码量 50-3,000 行均可，关键是机制数而非行数。 |
| 什么时候必须拆分？ | 机制数 ≥ 3，或触屏文件 > 8，或同子系统 3+ 阻塞性发现且绕行失败。 |
| 行数有什么用？ | 作为**校准参考**（中位数 300 行），而非决策规则。超过 500 行应检查机制数。 |
| split-recommended 是否过度触发？ | 对 `split-multi-mechanism` 和 `split-touch-set-too-large` 不过度。对 `split-subsystem-blocking-cluster` 应先走绕行（一轮聚焦修改），只有绕行失败才拆分。 |
| 当前 `> 2` 阈值是否正确？ | 正确。数据支持不调整。 |
