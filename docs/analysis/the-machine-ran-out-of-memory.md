# 三套双层跑不下:一次全机 OOM 的取证与结论

**时间**:2026-08-04 约 02:15Z(quay 最后提交 02:14Z、meta-cc 02:06Z、archguard 01:57Z)
**现象**:所有 Claude Code 与 tmux 进程死亡。人恢复 tmux 与管理者会话后取证。

---

## 1. 损失:无

| 检查 | 结果 |
|---|---|
| 三个仓工作树 | 全部干净 |
| git 完整性 | 三个仓均 OK |
| 中途 merge / rebase | 无 |
| 重活令牌 | **无人持有**(没有留下陈旧锁) |
| `.halt` | 无 |
| 未提交工作 | **2 处,在 tmpfs 的 worktree 里**——已抢救 |

**抢救的两条恰好是当时最要紧的两件**:
- `task/gap-the-finding-shape-still-requires-a-plan-section`(`bf9ea942`)——**最后一条门槛项**
- `task/gap-init-guesses-the-tmux-session-and-writes-the-guess-into-the-monitor`(`dc365250`)——**tmux 猜测缺陷的修复**

**第二条是这次事故的解药,而它在事故发生时正在飞、且躺在会被内存回收抹掉的地方。**

## 2. 成因:可算,不是意外

今晚实测的 RSS:管理者 **722MB**、quay 内层 **857MB**、archguard 外层 **602MB**。

| 项 | 峰值 |
|---|---|
| 6 个 Claude 会话 × ~800MB | 4.8GB |
| 三项目的 subagent | +4GB |
| **`/tmp` tmpfs(worktree + scratch)** | **4.4GB** |
| 并发套件的 node worker | 2–5GB |
| **合计** | **13–16GB** |

机器 16GB + 8GB swap(swap 已用 2.3GB)。

**`/tmp` 是 tmpfs 这一条是放大器**:worktree 与 scratch 直接与会话争同一份内存,
而所有人都按磁盘的直觉对待它。事后回收 **1351MB** 只用了删一周前的 go 构建缓存与已死会话的 scratch。

## 3. 结论:一个被实验回答了的问题

人 2026-08-04 裁定启动第三套双层时说:**「等令牌是正常的。我们就是要验证。」**

**验证结果:这台机器扛不住三套双层同时跑重活。**

这不是失败,是那次裁定要的答案。区别在于:
- 事前的推断是「压力是双峰的,间歇尖峰不值得为它停项目」——**那个推断只看 CPU,没看内存**
- 令牌串行化的是**套件**,不是**会话数与 tmpfs 占用**——**它保护的维度不是压垮机器的那个维度**

## 4. 可执行的推论

- **AC9(worktree 不许建在 tmpfs)从「重启风险」升级为「OOM 成因」**——见 [[SPEC-cold-start-one-liner]]。
- **令牌应当把内存纳入判据**,不只是串行化套件。现有的 `resource-gate.sh` 看 cpu_stall,不看可用内存。
- **会话数是一个未被管理的资源**:没有任何机制知道机器上有几个 Claude 会话、各占多少内存。
  今晚的令牌、资源闸、监视器都不看这个量。
- **观测的盲区在这次事故里是完整的**:监视器报的最后几条是 `SESSION-IDLE`,
  而按 §1.6 我不查 IDLE。**一台正在被压垮的机器,在会话面上看起来就是「大家都空闲」。**

## 5. 这次的诚实限度

- **没有 OOM killer 的直接日志**(`dmesg`/`journalctl` 均无权限或无记录),
  所以「OOM」是从现象与内存账推断的,**不是从内核日志确认的**。
- 上面那张峰值表是用**今晚不同时刻**测到的 RSS 拼的,不是同一时刻的快照。
  **它足以支持「三套跑不下」的结论,不足以精确到某个进程是压垮骆驼的那一根。**
