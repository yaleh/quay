# 内核 CPU 负载实测:优化判据选错了维度

**日期**:2026-08-04(管理者,人观察到 `sy` 高于 `us` 后实测)

## 实测

| 量 | 读数 | 排除了什么 |
|---|---|---|
| **fork 速率** | **44 个/秒** ⇒ 10 分钟套件 ≈ **26,000 次进程创建** | — |
| 上下文切换 | 3600/秒(中等) | 不是锁竞争主导 |
| `wa` / `si` / `so` | **全 0** | 不是存储瓶颈、不是换页 |
| 每核 `sys` | 14–19%,**分布均匀** | 不是单核热点/软中断 |
| 空闲 | **带套件仍 27–42%** | **机器没被喂饱** |

**成因**:大量 `fork`/`exec` + 临时目录与小文件操作。

**结构**:全套件 **431 个 CLI spawn 调用点**,其中 **43 个 spawn `.ts` 源 + `--experimental-strip-types`**
⇒ **每次 spawn 都重新解析一遍 TypeScript**。

## 这件事已经被诊断过,任务已经关掉

`gap-tests-spawn-cli-from-ts-source` / `gap-tests-use-cli-where-module-import-suffices`,
**均 `done`,2026-08-02 关闭**。任务体原话:

> 套件墙钟由**最慢的单个文件**决定(`--test-concurrency=8` 并行),**不是由调用点总数决定**。
> 其余 110 个文件 各 <60s — **对墙钟无影响,不动**。

**那个推理在单套件下完全正确。** 一台有空闲核的机器跑一个套件,
spawn 次数散在并行 lane 里,确实不影响墙钟。

## 但判据选错了维度

**spawn 总数不决定单套件墙钟,它决定另外两件:**

1. **内核 CPU 负载**(就是观察到的 `sy`)
2. **机器能同时跑几个套件**

**一个套件时 spawn 是免费的;三个并发时,spawn 正是天花板。**

## 对「令牌放宽到 2 个并发」实验的直接影响

那个实验会把 fork 速率**翻倍到约 88/秒**,而单套件时内核态已占 15–38%。

⇒ **实验之前,优化判据应从「是否降低墙钟」换成「是否降低每套件的 fork 数」。**
机制现成:已关任务的 AC6 写着「67 个 `run()` 调用点全部改用 `QUAY_CLI`」——
**避免 TS 重解析的办法已经有了,只被用在一个文件上**。

## 这类错误的形状(与今晚另外两条同族)

| 实例 | 形状 |
|---|---|
| `vendor/` 撞 Go 保留目录 | **字节相同,后果不同** |
| 本条 | **墙钟不变,成本不同** |
| `inner-state.sh` 保留 | 同一份测量,既能推出「退役」也能推出「它是另一类」 |

**一个优化在一个维度上无收益,不等于它在所有维度上无收益。**
**而判据一旦写进任务体,就会被后来的人当成结论继承——**
那两个任务体里的「对墙钟无影响,不动」正在被继承。


## 追加(2026-08-04):编译步骤存在,只覆盖了产品 CLI

人问「测试前没有统一编译到 `.js` 吗」——**有,而且在跑**:
`scripts/test.sh:335` 的 `build_dist_once` 在任何测试前构建 `dist/quay.js` 与 `dist/quay-native.js`,
`cli-entry.mjs` 把 spawn CLI 的测试路由到预构建包。

**但覆盖面只有 4 个文件**(`cli-entry` / `cli` / `mcp-server` / `serve`,全在 `packages/quay/test/`)。
**剩下 43 个 `.ts` spawn 点全在 `plugin/test/`**,spawn 的是 `plugin/scripts/*.ts` 那批方法论检查器——
**它们不在任何打包流程里。**

### 便宜的办法:`NODE_COMPILE_CACHE`(实测 2.7×)

| | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| 无缓存 | 390ms | 390ms | 343ms |
| `NODE_COMPILE_CACHE` | 347ms(冷) | **124ms** | **161ms** |

缓存目录 **244K**;Node v26.5.0 支持;**`scripts/test.sh` 与所有 plugin 脚本里一处都没设过**。
V8 字节码缓存对**全部 431 个 spawn 点**有效,TS 那批收益最大。

### 验证方法的警告(比上面更重要)

**σ = 297.6 秒。** 43 个点若各执行 2–5 次,节省约 **22–44 秒——远在噪声之下**。
**用墙钟 A/B 验证它必然得出「无改善」,于是一个真实改进会被当成噪声丢掉。**

⇒ **正确验证是直接测每次 spawn 的耗时,或数每套件的 fork/解析次数。**
**这是同一个判据错误在验证环节的版本**:优化判据要用「每套件成本」,验证判据同样如此。

**实现注意**:缓存目录**不要放 tmpfs**——那会重犯今晚的错误。
