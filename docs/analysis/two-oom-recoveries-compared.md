# 两次 OOM 恢复过程的量化对比

**日期**：2026-08-04（管理者）
**用途**：人要求「统计和分析这次重启过程，这些数据对后续的开发和应用都是有价值的」

---

## 1. 时间线对比

| | 第一次恢复 | 第二次恢复 |
|---|---|---|
| OOM 发生 | 约 02:15Z | 约 08:39–08:49Z |
| 会话重建 | 约 02:39Z（+24 分钟） | 约 08:52Z（人手动重开 tmux，用时不可比） |
| 恢复方式 | 管理者代拟简报，136 行，散文摘要 | **先读完两次真实历史，建 AC 文件，简报纯增量（<70 行）** |
| 从重建到第一次真派发 | 未精确记录（估计数小时级，因并发致盲 4.5h 才被发现） | **约 64 分钟**（08:52→09:56:13） |

**第二次恢复的关键设计差异**：先写 AC，再执行，而不是执行完再补记录——
这份分析本身是这个设计的直接产物（如果没有 AC 文件锚定每个判据的证据，
这份对比会退化成印象叙述）。

## 2. 缺陷发现延迟对比（核心数据）

| 缺陷 | 第一次：发生→发现 | 第二次：发生→发现 | 倍数 |
|---|---|---|---|
| 并发派发被简报静默丢弃 | **4.5 小时**（`81a013f4`） | 同类问题以不同根因重现：**约 3 分钟**（09:56:13 派发 → 09:56 内即用 meta-cc 核实并纠正） | **~90×** |
| 遥测括号被简报静默丢弃 | **2.5 小时**（`d9794c3b`） | **0**（这次简报显式点名，未复发） | — |
| 管理者自己的监视器未重挂 | **3 小时 44 分**（人问出来的） | **本轮 tick 内**（挂载时就补了 inner 目标，未被动等人问） | **数十倍** |
| 外层越权替内层实现 | 无此类记录（不同失效形态） | **约 28 分钟**（09:15 起 → 09:43 人观察+我核实并纠正） | 新形态，无法比较 |
| 简报投递失败（送不达） | 未记录 | **约 1 分钟**（发现即验证即纠正） | — |

**读法**：第二次不是「没有缺陷」——**同等数量级的缺陷仍然发生**（本轮清单见下）。
差别在**发现到纠正的延迟压缩了 1–2 个数量级**，因为 AC 文件把「应该验证什么」
在缺陷发生前就写死了，不必等人问或等症状累积到显眼。

## 3. 本轮（第二次）发现的缺陷清单，按发现方式分类

| 缺陷 | 发现方式 | 处置 |
|---|---|---|
| `monitor-mount-check.sh` 仍检查已判定退役的 `inner-state.sh` | 管理者读 tick 文档时顺带发现 | 已记录，未修（留给外层，非阻塞） |
| 我自己的合并挂载最初漏了 `inner` 目标 | 管理者主动核查（不是被动等通知） | 立即自我纠正 |
| 外层越权直接实现（`Agent` 派发绕过内层） | **人观察**（"我观察到 inner 中根本没有活动"） | 管理者核实证据后纠正外层 |
| `send-keys-verified.sh` 投递校验分不清「打字」和「提交」 | 外层自己在重试投递时发现 | **外层自己正确落成任务**，不是口头带过 |
| 内层第一次真派发未带 `run_in_background` | **人追问**（"看上去挺好"之后又问"为什么只跑一个"） | 管理者用 meta-cc 核实原始记录（不信 UI 表象）后纠正 |
| `tmux-detection` 任务代码已落地，`status` 字段仍是 `todo` | 管理者核查分支状态时顺带发现 | 已记录，留给外层订正（任务内容不由管理者改） |

**六条里三条是人观察/追问触发的，不是机制自动发现的**——
这是诚实的限度：AC 文件降低了「该查什么」的遗漏,但不能替代人在恢复现场的持续注意力。
尤其是「外层越权实现」和「只跑一个任务是不是异常」这两条,都需要对当前语境的判断,
不是预先写好的检查项能覆盖的。

## 4. 一个方法论层面的差异：同一类缺陷的根因这次变了

**并发派发**这条两次都发生,但根因不同:

- 第一次:**简报没提**这件事(信息缺失)
- 第二次:**简报提了、指向了正确的文档**,内层拿到信息仍未照做(执行缺失)

**⇒ 「写清楚」解决了第一类问题,解决不了第二类**。这意味着光靠改进简报的完整性
(本轮已经做到「纯增量、不遗漏」)不足以让 AC1 长期稳定——
还需要一层「即使文档写对了,也要核实真的被执行」的机制,而不是假设写对=会照做。

## 5. 数字统计

- 本轮恢复期间提交数(08:44Z–10:01Z,约 77 分钟窗口):**18 个**
- 其中管理者直接提交(AC 文件、简报、分析):**8 个**
- 外层/内层落地的实际开发提交:**10 个**(含 2 个已完成任务:DIR-103-C、one-condition)
- 管理者对外层的纠正消息:**4 次**(AC6 角色越界、投递失败、并发形态、以及本文档前的历次)
- 从「人报告观察」到「管理者给出证据核实结论」的平均延迟:**约 2–5 分钟**
  (三次人工触发的核查,每次都是查真实数据后再回应,没有一次直接采信人的转述或自己的猜测)

## 6. 对后续应用的建议(可执行,不是感想)

1. **恢复流程本身应该产出一份 AC 文件,而不是一份简报**——简报是给失忆会话看的最小上下文,
   AC 文件是给管理者自己验证用的,两者用途不同,不要合并成一份文档。
2. **「文档写对了」和「被照做了」要分别验证**——这次的并发派发问题证明,
   前者达标不能推出后者达标,必须留一步「核实第一次真实执行」的检查,不能在文档纠正后就假定解决。
3. **UI 表象(如「Waiting for background agent」)不能作为并发证据**——
   本轮实测:该提示在 `bg:false` 时同样会出现,唯一可信的判据是原始 `Agent` 调用的
   `input.run_in_background` 字段,或行为证据(内层是否在等待/阻塞)。
4. **单个 session 的恢复应该保留「谁发现的」这个字段**——本轮 6 个缺陷里 3 个是人发现的,
   这个比例本身是个应该被追踪的指标,而不是每次恢复完就丢弃的过程细节。
