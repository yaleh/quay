## Grounded facts this Plan relies on (re-verified live against `d4d46629`, 2026-08-01)

- **No `config` verb exists at base.** `quay.ts` `main()` dispatches by `cmd ===` branches
  (`init` L1048, `serve` L1021, `mcp` L1033, `task` L593+, `adr` L518, `action` L978/997, `gate`
  L1135, `gate-log` L1168, `complete` L1196, `adjudicate` L1212, `promote` L1225, `retreat`
  L1242, `run` L1267, `migrate` L1306) with the CB-021 `--format-json` command allowlist/validator
  at L507–509 (`resolveJsonFlag(flags)` at L85 returns `null` for any non-`json` `--format`
  value; the L510 guard errors out with exit 1 only when `jsonFlag === null && jsonCommands` —
  so a (cmd, sub) pair NOT in the `jsonCommands` allowlist is never `--format`-validated, and its
  `--format yaml` silently falls through to human-readable output, the exact bug CB-021 closed)
  and `printHelp(sub)` at L299. The allowlist IS what declares a (cmd, sub) pair JSON-capable and
  rejects a bad `--format` for it — so adding `config` (validate/check) to it is REQUIRED, not
  optional (Stage 3's spec below makes that explicit). A new `if (cmd === "config")` branch +
  `config` entries in `printHelp()` and the L507–509 `jsonCommands` allowlist are additive;
  nothing existing is rewritten.
- **CLI conventions:** `--json` is the documented machine-readable flag (`printJson` helper at
  L37; CB-021: `--format json` is a recognized alias everywhere `--json` is). Exit codes are set
  via `process.exitCode = 1` on guarded failures (the `withGuardedErrors` helper, L65–76,
  recognizes `unknown gate:`/`no such task:`/`illegal transition:` and prints a clean one-line
  message — the shape the new `config validate` branch mirrors for its own fail verdicts).
- **YAML parsing:** `config.ts` imports `YAML from "yaml"` (dependency `yaml: ^2.5.1`, verified in
  `packages/quay/package.json`) and uses `YAML.parse` (L30). For LINE-LEVEL diagnostics (AC2) the
  new module must parse with `YAML.parseDocument` (also from `yaml`) and read
  `doc.errors[]` line/col ranges — the module does NOT call `loadConfig()` first (which throws on
  the FIRST malformed construct, losing the all-issues report), it parses independently and then
  reuses the loaded providers/gates/loop views for the field checks.
- **Gate type schemas (`packages/quay/src/gate/config/types.ts`), the single source for check #3:**
  `It0Entry` = `{name, script, argsKey}`; `FixedEntry` = `{name, script}`;
  `TestPassEntry` = `{name, command}`; `CoverageFloorEntry` = `{name, command, floor}`;
  `RedGreenEntry` = `{name, red, green}`; `adr[]` = non-empty strings naming an ADR id (e.g.
  `ADR-001`). `readGatesConfig(workspaceRoot)` (`gate/config/loader.ts` L78–115) returns
  `{ it0, adr, fixed, testPass, coverageFloor, redGreen }` read from `.quay/config.yml`'s own
  `gates:` section (branch-A unified workspace, DIR-050/DIR-120) OR the legacy `.quay/gates.yml`
  (branch-B workspace with no `config.yml`) — the same two-source resolution AC8 pins, and the
  "wrong nesting level" check (#5, AC3) is a structural probe of the RAW parsed tree: a `gates:`
  key whose direct value is a MAP of name→map (e.g. `gates: vitest: command: ...`) instead of a
  MAP of type→ARRAY (e.g. `gates: testPass: [ { name: vitest, ... } ]`) is a placement error to
  report with the corrected shape.
- **Loop contract (`packages/quay/src/loop-params.ts`):** `readLoopParams(workspaceRoot)` is
  already FAIL-CLOSED — throws `Error("FAIL-CLOSED: ...")` for malformed YAML, missing `loop:`
  section, missing/empty `board`, missing `gates`, invalid `stop` (`VALID_STOP_RE`), invalid
  `execution` (`VALID_EXECUTION = {dispatched, inline}`), and (L40+) invalid `audit`/
  `concurrency`/routines. Check #6/#7/#8 (AC5/AC13/AC14) REUSE this single source for the same
  verdicts — the module catches each thrown `FAIL-CLOSED` message and converts it to an
  `Issue{severity:"error", field, message}` rather than re-deriving the field rules (single
  source of truth). `stop` valid values (documented L22): `"once" | "until(.halt)" |
  "until(empty)" | until(K·ΔV<ε) prefix`.
- **Provider env contract (`packages/quay/src/provider-env.ts`):** `resolveProviderEnv(cfg,
  provider)` builds the env from `provider.tasks_dir`/`provider.env`; `QUAY_NATIVE_TASKS_DIR`
  derives from the native provider's `tasks_dir`/env, and the github provider's
  `QUAY_GITHUB_REPO` similarly. Check #9 (AC15) verifies the native provider carries
  `tasks_dir` (or `QUAY_NATIVE_TASKS_DIR` in env) and the github provider carries
  `QUAY_GITHUB_REPO` — reusing the same field sources `resolveProviderEnv` reads.
- **MCP surface (`packages/quay/src/mcp-handlers.ts`):** `registerAllHandlers` (L609) calls
  `registerTaskHandlers`/`registerGateHandlers`/`registerLifecycleHandlers`/`registerAdrHandlers`/
  `registerActionHandlers`. A new `registerConfigHandlers(server, getClient, cfg)` registering the
  `config_validate` tool follows the `gate_run` convention (L280–300): `server.registerTool(...)`
  with `inputSchema` via `zod`, returning `{ok, issues[]}` in `structuredContent`, where a
  validation FAIL is a NORMAL successful call with `ok:false` (NOT `isError:true` — matching the
  gate/lifecycle parity note at L271–285). The tool's issues array is produced by the SAME
  `validateConfig()` function the CLI calls (AC16 parity is by construction, then pinned by a
  test that runs both surfaces against the AC2/AC4 fixtures).
- **Test runner convention:** `gate.test.mjs` (header L1–20) uses `import { test } from
  "node:test"` + `assert` from `node:assert/strict` and drives the real CLI via
  `execFileSync` against a disposable `makeWorkspace()` (`mkdtemp` + `.quay/config.yml`) — the
  exact pattern `config-validate.test.mjs` follows. RED→GREEN pairs per ADR-001 are encoded as
  `test("ACn ...", ...)` cases that FAIL while `src/config-validate.ts` is absent (Stage 1) and
  flip GREEN as it lands (Stage 2).
- **meta-cc vitest-gate-error fixture (DoD5):** the 2026-07-25 failure shape —
  `gates: vitest: command: npx vitest run` written directly under `gates:` instead of
  `gates: testPass:` — is embedded INLINE as a fixture constant in the test file and MUST be
  flagged by check #5 (wrong nesting) with a suggestion of the correct `testPass` shape. This is
  the concrete artifact DoD5's "correctly flags" clause is verified against; the real meta-cc
  config is a foreign workspace (not fetched at Build time — the reproduction fixture is the
  ground truth for the assertion).

## Plan-check stopping rule

The PlanAuthor/PlanCheck loop follows the standardized rule: at most **3** Plan-check rounds;
success only when `F_i = 0` (zero findings) on a round. After round 3 with `F_i > 0`, the Plan is
returned for revision rather than dispatched — never a silent proceed.
