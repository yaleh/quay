## Grounded facts this Plan relies on (re-verified live against `d4d46629`, 2026-08-01)

- **`readGatesConfig(workspaceRoot)`** (`packages/quay/src/gate/config/loader.ts` L77–116) is
  branch-A terminal: if `<ws>/.quay/config.yml` exists and carries a `gates:` key it resolves from
  it alone and NEVER falls through to a legacy `.quay/gates.yml` (DIR-050/DIR-120; the
  silent-data-loss behavior pinned by `gate-config-loader.test.mjs`); only with no `config.yml`
  does branch B read the legacy `.quay/gates.yml`. It extracts the six arrays
  (`it0, adr, fixed, testPass, coverageFloor, redGreen`) with `Array.isArray` guards — a malformed
  `gates: vitest: command: npx vitest run` (map-of-name under `gates:`, the exact meta-cc 2026-07-25
  shape) yields an empty `testPass` and the unknown `vitest` key is currently SILENTLY DROPPED (the
  DIR-100 finding).
- **`loadWorkspaceGates(workspaceRoot)`** (loader.ts L131–177) skips the factory call on missing
  required fields via bare `continue` — no diagnostic (the fail-silent path). Consumers:
  `listGates(ws)` returns `[...Object.keys(gateRegistry), ...Object.keys(loadWorkspaceGates(ws))]`
  (`registry.ts` L127), printed by `quay gate --list` via `console.log(listGates(ws).join("\n"))`
  (`quay.ts` L1114–1131 — stdout ONLY), and `loadWorkspaceGates(ws)[name]` (`registry.ts` L119) is
  the `gate_run` unknown-gate path.
- **Entry schemas (`packages/quay/src/gate/config/types.ts`):** `It0Entry` = `{name, script,
  argsKey}`; `TestPassEntry` = `{name, command}`; `FixedEntry` = `{name, script}`;
  `CoverageFloorEntry` = `{name, command, floor, pattern?}`; `RedGreenEntry` = `{name, red,
  green}`; `adr[]` = strings naming an ADR id. The common per-entry runner keys `cwd`/`timeoutMs`
  are read by the `gateConfigOf` helper (loader.ts L138) and are therefore ALLOWED on every
  entry.
- **CLI invocation:** tests spawn the real CLI as `node packages/quay/bin/quay.ts ...` (the
  `quayBin` const in `gate.test.mjs` L29 + `execFileSync("node", [quayBin, ...args], {encoding,
  cwd})` L80). The new test file uses the same path.
- **`gate --list` has NO `--json` mode (Plan-check finding note, verified 2026-08-01):** the CLI
  implements `--json` only for `gate-log` (quay.ts help L382). The `gate --list` handler (quay.ts
  L1114–1131) matches `sub === "--list"` (arg destructure L468; `parseFlags` runs earlier but the
  handler returns before ever reading `flags`) and emits plain-text `console.log(listGates(ws).join(
  "\n"))`, so a trailing `--json` is silently ignored and plain-text output is still emitted. Task
  AC6's `quay gate --list --json` phrasing is therefore vestigial — the load-bearing claim is
  "diagnostics never touch stdout", which holds whether or not `--json` is passed. Stage assertions
  correctly use plain `gate --list` (`out.stdout === quietOut.stdout`).
- **Test runner convention:** `node:test` + `node:assert/strict`, with the `tmpWs()` mkdtemp +
  `.quay/config.yml` fixture pattern of `gate-config-loader.test.mjs` (L21–25) — the exact pattern
  `gate-diagnostics.test.mjs` follows.
- **Env-var convention:** the env is read at call time from `process.env` via a default sink; the
  sink factory accepts an explicit env record so the quiet/file/stderr modes are asserted
  hermetically without mutating `process.env`.
- **meta-cc vitest-gate-error fixture (DoD4):** the 2026-07-25 failure shape —
  `gates: vitest: command: npx vitest run` written directly under `gates:` instead of
  `gates: testPass:` — is embedded INLINE as a fixture constant in the test file and MUST be
  flagged by the unrecognized-key scan (AC1) and, when a sibling `.quay/gates.yml` also declares a
  `vitest` gate, by the AC3 shadow hint.
- **Repo's real config is clean (AC7 real-landing):** the checked-in `.quay/config.yml` `gates:`
  section contains only FOUR of the six known section types — `it0` ×6 (all with name/script/
  argsKey), `adr` ×2 (strings), `fixed` ×5 (name/script), `testPass` ×4 (name/command);
  `coverageFloor` and `redGreen` are absent (verified by parsing the real config, 2026-08-01). All
  present entries are complete, so the load-bearing assertions hold — no unrecognized key, no
  missing-field entry, and a real `gate --list` produces zero diagnostics. Existing
  `gate-config-loader.test.mjs` fixtures likewise use only known sections or an empty `gates: {}`
  → the new scan adds zero false positives to the existing suite (AC7).

    "redGreen"] as const`.

    `export type GateDiagnosticsSink = (d: GateDiagnostic) => void`.
  - `export function resolveGateDiagnosticsSink(env: Record<string, string | undefined> =
    process.env): GateDiagnosticsSink` — reads `QUAY_GATE_DIAGNOSTICS` (AC4/AC5): `undefined` /
    `"stderr"` → writes `[gate-loader] <severity>: <message>\n` to `process.stderr` (AC6);
    `"quiet"` → no-op (AC4); any other value → `fs.appendFileSync(path, line)` (create + append,
    recursive mkdir; a write failure falls back to stderr, never throws) (AC5). Resolved lazily
    (optional arg) so existing one-arg callers get the env-driven default and tests inject a
    collector.

    backward-compatible signature (existing `gate-config-loader.test.mjs` one-arg calls unchanged).
    After extracting the six arrays, scan `Object.keys(parsed)`; every key not in
    `KNOWN_GATE_SECTIONS` → emit `{severity:"error", message:"unrecognized gate section '<k>' —
    expected one of: it0, adr, fixed, testPass, coverageFloor, redGreen"}` (AC1). AC3 hint: for
    each unrecognized key `<k>`, peek (HINT-ONLY — never resolution, so branch-A-terminal gate data
    and `gate-config-loader.test.mjs`'s silent-data-loss regression are untouched) at
    `<ws>/.quay/gates.yml`; if its parsed six arrays contain an entry named `<k>` (adr: lowercase
    string equal) append "gate '<k>' is declared in .quay/gates.yml but is shadowed by
    .quay/config.yml's gates: section — move it to config.yml or remove the config.yml gates:
    section to restore legacy behavior." (both files named, AC3). The peek is defensive — an
    absent/unparsable sibling file yields no hint, never a throw.
  - `loadWorkspaceGates(workspaceRoot, sink: GateDiagnosticsSink = resolveGateDiagnosticsSink())` —
    forwards `sink` into its `readGatesConfig` call. Per-entry validation before each factory call,
    required-field sets from `types.ts`:
    - missing required fields → `{severity:"error", message:"<type> gate '<name>' missing required

      and `continue` (NOT registered — preserves the current skip semantics, now loud)
      (AC2/AC9/AC10/AC11/AC12).
    - extra-field check for entries that PASS required validation: allowed keys = the type's
      required fields + `cwd`/`timeoutMs` (the `gateConfigOf` keys) + type-optional keys

      (AC13).
    - `adr` entries remain plain strings (unchanged); a non-string `adr` entry is skipped with an
      `error` diagnostic (defensive; not an AC, left out of the mapping).

## Rollback

- **Mid-stage:** a failed Stage-1/2 command is fixed in-place within the same worktree before
  proceeding (no partial Land); the RED evidence for Stage 1 is preserved before Stage 2 flips it.
- **Post-Land regression:** the full-suite GREEN is a Land precondition; a regression surfacing
  only on `master` after Land triggers `quay retreat DIR-100 --reason <specific>`, a fix commit,
  and a fresh acceptance-gate run — the `tasks/DIR-100.md` status ticks written at Land are
  un-ticked (DIR-020 discipline) until the re-run passes.
- **False-positive escape hatch:** if a real workspace config ever trips a new diagnostic that is
  NOT a genuine config error, that is a diagnostic-precision bug (warn-level over-reach), fixed by
  tightening the required/extra-field sets — the quiet sink is a temporary mitigation, never the
  fix.

## Plan-check stopping rule

The PlanAuthor/PlanCheck loop follows the standardized rule: at most **3** Plan-check rounds;
success only when `F_i = 0` (zero findings) on a round. After round 3 with `F_i > 0`, the Plan is
returned for revision rather than dispatched — never a silent proceed.
