- Type: code
- Line budget: ~10 lines changed (1 import line + ~9-line `run()` body replacement)
- Dependencies: Stage 1

Detail: Two edits, both in `packages/quay/test/cli.test.mjs`:

1. **Import (line 99):** Change `import { execFileSync } from "node:child_process";` to
   `import { execFile, execFileSync } from "node:child_process";`. Both are needed — `execFile`
   for the async `run()`; `execFileSync` stays for the 23 direct seeding calls.

2. **run() body (lines 143-157):** Replace the synchronous `execFileSync`-based body with a
   Promise-based `execFile` wrapper:
   ```js
   function run(args, opts = {}) {
     return new Promise((resolve) => {
       const child = execFile("node", [coreBin, ...args], { encoding: "utf8", ...opts });
       let stdout = "";
       let stderr = "";
       child.stdout.on("data", (c) => (stdout += c));
       child.stderr.on("data", (c) => (stderr += c));
       child.on("close", (code, signal) => {
         resolve({ status: signal ? (code ?? 1) : (code ?? 0), stdout, stderr });
       });
       child.on("error", (err) => {
         resolve({ status: err.status ?? 1, stdout: "", stderr: String(err) });
       });
     });
   }
   ```
   Contract preserved:
   - Return shape: `{status, stdout, stderr}` — unchanged.
   - Error path: `err.status ?? 1` (byte-identical to existing line 152 symbol). The `error`
     event on `ChildProcess` fires on spawn failures (e.g. ENOENT for a missing binary) —
     its `err` object carries `.status` (not `.code`), preserving the exact existing contract.
   - Close handler: maps signal-death (`signal` non-null → `code` may be null) to
     `status: 1`, matching the existing behavior where `execFileSync` would throw with
     `err.status === null` under signal death, hitting the `?? 1` fallback.
   - Never throws: always resolves with `{status, stdout, stderr}`.
   - All 66 call sites already use `await run(...)` and destructure
     `const r = await run(...)` → `r.status`/`r.stdout`/`r.stderr` — zero call-site changes.
