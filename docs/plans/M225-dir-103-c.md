## Guardrails

- **Per-provider resolution lives ONLY where the enabled-provider id is known** — the CLI
  `pinAcceptanceEnv`/`resolveAcceptanceEnvFile` and the MCP `gate_run`/`resolveAcceptanceEnvFile`.
  The gate registry stays provider-agnostic: `registry.ts` reads only the pinned
  `QUAY_ACCEPTANCE_ENV` env var and never the config (the acceptance gate fn receives only `task`,
  by design — the Proposal's "Finding" cites this as the reason resolution must happen at the
  CLI/MCP layer; do not re-derive the provider inside the registry).
- **NO new tracked module cycle (F2):** the per-surface `resolveAcceptanceEnvFile` helpers live in
  `bin/quay.ts` (CLI) and `mcp-handlers.ts` (MCP) — NEVER exported from `mcp-server.ts`, because
  `mcp-server.ts:51` already imports `registerAllHandlers` from `mcp-handlers.ts` (used at `:155`),
  so importing a `mcp-server.ts`-exported helper into `mcp-handlers.ts` would create the tracked
  cycle `mcp-server → mcp-handlers → mcp-server` (archguard L_D / ADR-007). `mcp-handlers.ts` must
  import nothing from `mcp-server.ts`; a per-surface duplicated helper is the repo's own documented
  convention (`mcp-handlers.ts:32-36`). Stage 7 re-checks this (item v).
- **Explicit-override-wins, exactly like `QUAY_ACCEPTANCE_CWD`:** pre-set `QUAY_ACCEPTANCE_ENV`
  env var > provider `acceptance_env` config key > unset. Never clobber a pre-set env var (the
  session-8b74052c bug class that `pinAcceptanceEnv`'s `:215-217` comment documents).
- **MCP env-var hygiene:** `QUAY_ACCEPTANCE_ENV` is pinned per `gate_run` invocation and restored
  in the existing `finally` block (`mcp-handlers.ts:328-335`) — one call's env file must never
  leak into later calls, same discipline as `QUAY_ACCEPTANCE_CWD`/`QUAY_ACCEPTANCE_TIMEOUT_MS`.
- **Fail-closed is PRE-execution:** the missing-file check happens inside `runAcceptance` before
  `spawnSync`; the acceptance command must not run at all (Stage 1's T2 proves it via a marker
  file that stays absent).
- **The config key is `acceptance_env`; `QUAY_ACCEPTANCE_ENV` is an override only.** Do not
  introduce an env-file config key under a different name, and do not treat the env var as the
  authoritative source (the task's Proposal is explicit: "the config key `acceptance_env` is
  authoritative"). AC #7 is resolved by implementing the env-var override — the name is kept, the
  precedence is explicit, and Stage 4 documents it.
- **Docs accuracy is load-bearing (AC #6):** the clean-shell contract must state PATH is inherited
  from the invoking process — NEVER claim a fixed system default (`/usr/bin:/bin`). The
  correction of that imprecise claim is an explicit AC deliverable, not cosmetic. The `gate --help`
  lines MUST contain the literal phrase "inherited from the invoking process" because Stage 4's
  verification grep keys on it (F3 — grepping `QUAY_ACCEPTANCE_ENV` in `bin/quay.ts` would be
  vacuous: Stage 3 already puts that string in `pinAcceptanceEnv`).
- **RED/GREEN discipline is per full-file run (F1):** the full `acceptance.test.mjs` run is RED at
  Stage 1 (all four new tests fail), STILL RED (partial) at Stage 2 (T1/T2 green, T3/T4 red), and
  first turns GREEN at Stage 3 (all four pass). Do NOT annotate a stage "GREEN (exit 0)" while any

  `expected exit ≠ 0`, with the RED scoped to T3/T4 (proven by the `--test-name-pattern="A2:"`

- **Touch-set discipline:** every stage's `- Files:` line names only paths inside the task's own
