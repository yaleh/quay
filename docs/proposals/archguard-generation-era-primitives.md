# archguard 能力提案：生成近乎免费时代的架构度量原语

> **状态**：proposal（未实现，未接线）
> **测量日期**：2026-09-03
> **被测对象**：`quay` 仓库自身（首次提交 2026-07-15，测量时 50 天龄，12 673 次提交，约 253 提交/天）
> **文档用途**：作为 archguard 的能力输入。第 2 节是可复用的回归语料，第 3 节是五个原语的定义与**可证否的验收判据**。

---

## 0. 这份文档在主张什么

一句话：**archguard 现在测的是「这些东西之间是什么关系」，而生成近乎免费的开发模式下，真正要问的是「这些东西还活着吗，删掉一个要付多少代价」。**

这不是猜测。本仓库是一个由自主循环以 253 提交/天的速度写出来的真实系统，archguard 对它的产品层判定是 **0 个依赖环、0 个字面量弥散异味**——按经典标准干净。而同一个仓库里：

- 退役一个 shell 脚本要动 **150 个文件 / 17 个目录**，已失败 3 次；
- 该脚本的**真调用只有 21 个文件**——按经典耦合度量这是低耦合；
- 产品层 `packages/quay/src/observation.ts:2729` 硬编码了它的相对路径并解析它的输出 schema，**而这条依赖不走 import，import 图上不存在**；
- 同一个「识别这个脚本」的判定被**独立重写了 ≥4 次**；
- `plugin/scripts/` 与 `experiments/*/scripts/` 之间有 **45 对字节完全相同的文件、24 069 行**。

**前提翻转**：人力时代写代码贵 ⇒ 人会复用 ⇒ 病理是**缠结**（环、上帝类、耦合）。生成近乎免费时 ⇒ 复制比抽象便宜 ⇒ 病理是**增生与身份复制**。什么都不缠结，因为什么都不复用。经典指标对后者结构性失明。

### 2.6 自举差距：产品层在自己的开发循环里被用到的比例

本仓库的既定目标是「本项目自己的开发循环跑在自己的产品层上」。这一维的读数比结构指标更直接。

| 量 | 读数 |
|---|---|
| 机制层中触及任务数据的文件 | **70** |
| 其中**经由产品层**（`quay` CLI / MCP `task_*`）访问的 | **1**（且是 shell 脚本；`plugin/scripts/*.ts` 中的代码位置 = **0**） |
| 直接读盘 `tasks/*.md` | 33（80 处代码行） |
| 自行解析 frontmatter / 任务体 | 31（其中 **16 个不用任何共享解析器**） |
| 经由**机制层**共享解析器（`task-schema.ts` / `touches-parser.ts`） | 39 |
| 绕过 ABI 直接 import provider 内部 `createStore` | 7 |

⇒ **98.6% 的任务数据访问绕过产品层。** 机制层拥有一套**平行的任务数据栈**（`task-schema.ts` 31 个导出 + `touches-parser.ts` 7 个 + 39 个消费者），**功能上比产品 ABI 丰富**——它事实上是第二个 provider 实现。

**依赖方向是反的（结构核心）**：

```
packages/quay-native/src/store.ts:18
  import { parseFrontmatterCompletely } from "../../../plugin/scripts/task-schema.ts";
```

「任务 frontmatter 的权威解析」这份正本住在机制层，产品层是它的消费者。**产品层不是循环可以站上去的层——它自己站在循环上。** 这是 `packages/**` → 机制层唯一的 src 级硬 import（另 33 处在测试夹具、4 处在模板字符串内）。

**ABI 缺口——迁移没有增量路径的原因**。ABI 把任务体建模为不透明字符串（`abi.ts`：`{id,title,status,role,labels,parent,children,body,extra}`，`body: string`）。机制层需要的是任务体的**结构**。缺失能力按通用/特有切分：

| 应上收到产品层（**通用**，任何用 quay 的项目都要） | 应留在机制层（**本项目特有**） |
|---|---|
| ① `## <heading>` section 切片（`extractSection` 被 23 个文件 import） | ⑤ 按 git revision 读任务状态（`git show develop:tasks/<id>.md`） |
| ② AC/DoD 复选框计数（`countAcCheckboxes`） | ⑥ 状态翻转 + 原子提交 + develop 同步 |
| ③ shape-aware 四件套完备性判定 | ⑦ `## Contract` 六键解析（fast-mode 契约） |
| ④ 批量状态写 | ⑧ 任务↔代码落地关联 |
| ⑤ workspace-root / worktree 参数化（MCP 绑定固定 root，`it0-task-bulk-write.ts` 因此绕过） | ⑨ 在飞 worktree 枚举 / 槽位计算 |
| ⑥ `depends_on` 一等公民（`task_write` 无此参数） | |

`## Touches` 是混合：**求互斥可派发子集是通用的，Touches 语法是本项目特有的** ⇒ 产品层应提供结构化字段读写，语法留机制层。

**这 6 项通用能力是自举的真实前置，不是那 1 条 import。** 即使翻转 `store.ts:18`，机制层依然迁不过去——**没有哪个脚本能单独迁移，因为 ABI 表达不了它们中任何一个需要的东西。** 1/70 是阈值现象，不是执行不力。

### 2.8 图论方法应用：十条具名风险，与「82% 纯度」的方法学修正

对 P1（删除闭包）/P2（身份复制）的机械化，实测了四个可复用方法。

| 方法 | 边的定义 | 成本 |
|---|---|---|
| (d) 共改减依赖 | git 共同提交次数（双向置信度 ≥0.25–0.30）减去内容互相提及（**同名对须比对完整相对路径，不能只比 basename**） | 纯 git，零解析 |
| (a) 身份图最小顶点割 | 文件×实体二部图；边＝按位置剔除注释后的字面量/import/spawn 引用；求分离实体与其余图所需的最小顶点数 | node-split 最大流 |
| (c) 社区发现 vs 声明结构 | 同一张图上跑 Louvain（8 个随机种子验证稳定性），与声明的目录标签比对 | — |
| (e) 效果指纹 | 稀有事实合取（同时读同一 `/proc` 路径 ∧ 同一 basename 等），**不是**整文件相似度 | 单位选错会完全聚不出已知靶子 |

**四个方法里三个的首次实现都给出了自信的错误答案，全靠「零计数/低命中对已知真样本干跑」这条纪律拦下**——不是靠更谨慎的实现，是靠这一条纪律：

- (d) 首版把同名镜像对判成"有引用"——A 文件头注释里写着自己的文件名，被误判成"提到了 B"；改为按完整路径比对后，现存文件间的隐藏耦合对数从 0 变成 **46**。
- (a) 边界正则的环视断言漏掉了 `/`，导致 `import "./x.ts"` 与 `source "$(dirname $0)/x.sh"` 全部不匹配；`gate-script-lib.sh` 因此读出 **0 个消费者**（真值 grep 命中 164，去重后 63）。
- (e) 整文件 Jaccard 对已知的 4 处 `/proc/cmdline` 判定重写全部聚不出来（两两最高相似度仅 **0.296**）——单位错了：一个判断是文件的一个片段，被文件其余部分稀释。改用「稀有事实合取」后命中 **9 处**（比已知的 4 处更多）。

⇒ **这四个方法本身也需要被检验，不能因为它们是"图论/机械方法"就默认可信。**

#### 方法学修正：社区纯度不能回答「有没有有效的抽象/封装/继承/复用」

⚠️ **本节修正一个已在讨论中出现、但从未写入正文的误读**：方法 (c) 曾报出「82% 的文件落在层纯的社区里」，这个数字若被读作"分层设计良好"，是对指标的误用。

**指标本身的漏洞（已用已知案例证实）**：标准纯度按**社区**聚合打分——一个社区若 90% 成员同层，整个记为「纯」，**不检查那 10% 少数派自己是不是被误分类的**。已有数据里正是两个反例：

- 前表 R2（`fan-in/ff-merge.ts`）：所在社区 117/124=94.4% 机制层，判定为「纯」；但这个「纯」恰恰是靠把那 1 个产品文件算作机制层多数派实现的——**它自己按声明是产品、按耦合是机制，是被误分类的那个，却因社区整体同质倒扣进了纯度的分子。**
- 前表 R4（`loop-complete-task.ts`）：反方向同形，嵌在一个产品占绝对多数（31 产品:5 机制）的社区里。

⇒ **纯度指标会把真正的层违规（R2、R4）算作"合格"，不能当分层质量的证据。**

**更根本的问题**：六个跨层社区各自的粘合边加总约 **42 条**，占全图 2947 条边的约 **1.4%**。这个比例低，可能来自两种相反的原因——精心设计的封装，或者两层根本没什么可说的话。§2.6 的自举差距测量已经独立回答了是哪一种：机制层 70 个碰任务数据的文件里 **98.6% 绕过产品层**。「跨层边少」与「自举率 1/70」是同一个事实的两面：**不是设计得好，是压根没建立起该有的联系。**

**真正回答「抽象/封装/继承/复用」的四个直接指标**（均为独立测量，非从纯度推导）：

| 维度 | 读数 | 判读 |
|---|---|---|
| 继承 | 产品层 367 个实体，**继承关系 = 3**（archguard `relationCountByType`，本节复核） | 基本没有 |
| 封装（门面） | 见 R1：2.2% | 基本没有 |
| 封装（共享基座） | `gate-script-base.ts` 占守卫代码 **0.4%**，被用到的部分是 `helpExit`(60 次)/`isDirectEntry`(44 次)——真正的行为契约 `parseArgs` 用 2 次、`emitPass`/`emitFail` 用 **0** 次 | 共享的是帮助文本，不是行为契约 |
| 抽象 | 全系统站得住的抽象只有 2 个（Provider ABI、gate registry/factories），均靠单一正源 + tsc 强制 | 孤例，非常态 |
| 复用 | 184 个 basename 存在于多个脚本根，117 个字节相同，**67 个已经漂移** | 主要形态是复制粘贴，不是引用共享 |

一个反例值得记：`packages/quay-native/src/store.ts` 1515 行仅导出 9 个符号——证明这个仓库知道怎么做封装，只是孤例，不是常态。

**结论**：82% 纯度与上表四个指标不矛盾——它们在说同一件事的两面：**这个系统里大部分东西彼此没有关系，少数有关系的地方，关系处理得不好。纯度高恰恰是缺乏抽象的另一种读数，不是它的反证。**

## 3. 五个原语

每个原语给出：定义 → 现有工具为何测不到 → 本仓库实测 → 计算方法 → **验收判据（可证否）** → **反向判据（防止它报假阳性）**。

### P1 · 删除闭包 Deletion Closure

**定义**　对构件 X，`DC(X)` = 为使 X 不再存在、且不留下悬空引用或永久变红的检查，**必须修改的文件集合**。
**核心指标**　剖面比 `R(X) = |DC(X)| / |CallGraph(X)|`。封装良好 ⇒ `R ≈ 1`。

**须计入的边**（前四类是现有工具缺的）：
1. import / require（现有工具已有）
2. `bash` / `exec` / `source` / spawn 携带 X 的路径 —— **跨语言，import 图看不见**
3. X 的路径或 basename 以**字符串字面量**出现在代码中（注册表、laydown 清单、常量导出）
4. **解析 X 输出 schema** 的代码（知道 X 的输出格式 ⇒ 依赖 X）
5. 断言 X 存在的测试夹具
6. 任务体 `## Touches` 段的声明（本仓库特有，可选）

**本仓库实测**　`session-liveness.sh`：CallGraph = 21 文件，DC = 150 文件 / 17 目录，**R ≈ 7.1**。

**计算方法**　先用 P2 建立实体别名索引，再对每个别名做按位置的引用抽取（区分代码 / 注释 / 文档），闭包取并集。输出应同时给出分类计数，而非一个总数。

**验收判据（可证否）**　用本仓库 **8 个已落地的退役任务**做回归集：工具**事前**给出的 `DC` 与真值的对称差 **≤ 20%**。

> ⚠️ **参照系更正（2026-09-03，由地面真值实测暴露）**：真值 **不是**「删除提交实际改动的文件集」，而是 **「实际改动集 ∪ 事后仍能命中的残留引用集」**。
> 实测 `message-bus.ts`：方法预测 33 文件、删除提交触及 30，对称差 31（Jaccard 34%）——看似判不通过；但复核发现 **17 个「误报」里有 16 个至今仍在 develop 上带着该引用**，全仓仍有 **52 个文件**提到这个已废除的机制。**不是方法错了，是删除没删干净。**
> `.halt` 同形：按脚本名预测 31（实际 30），放宽到路径字面量则预测 98——因为 `stop: "until(.halt)"` 至今是 `config-validate.ts` / `init.ts` / `loop-params.ts` 里的**活语法，从未退役**。
> ⇒ **DC 的分歧应先当残留发现处理，再当方法误差。** 用未更正的参照系会把一个正确的检测器判为不合格。

**反向判据**　对一个真正封装良好的构件（如 `gate-script-lib.sh` 中被 87 处 `source` 的共享库函数）若报出 `R > 2`，说明它把叙述性引用当成了结构边——必须能在同一语料上同时给出低 R 的正例。

### P2 · 身份复制 Identity Replication

**定义**　同一个运行时实体在代码中被**独立命名或独立判定**的次数。两个子度量：
- **(a) 字面量复制度**：含 X 路径 / basename / 环境变量名 / CLI flag 的**代码**文件数，且未经由单一访问器。
- **(b) 判定重写数**：独立实现「识别 X」或「X 是否处于某状态」的代码点数。

**现有工具为何测不到**　克隆检测键在**代码形状**上——那 4 份 `/proc/cmdline` 判定代码各不相同，抓不到；依赖分析键在 **import** 上——字符串字面量不是 import。**两者的交集正好是这个盲区。**

**本仓库实测**　`session-liveness.sh`：字面量复制度 97 个代码文件（对 21 个真调用），判定重写 ≥ 4 处，并已烧进产品层常量与 Web UI（`serve-system.ts:27/30` 直接渲染 `resource-gate.sh --json`）。另有 45 对字节相同文件 / 24 069 行、15 组守卫 stem 的相同副本。

**计算方法**
- (a) 建立实体别名索引（路径、basename、env 名、flag 名、输出 schema 字段集），标记别名出现在 > N 个文件且未经单一访问器者。
- (b) **按「读取的外部事实集合」聚类代码块**，而非按 token —— 例如「读 `/proc/<pid>/cmdline` ∧ 比较 basename」构成一个判定指纹。同指纹多实现 ⇒ 判定重写。

**验收判据（可证否）**　在本仓库上跑，**必须**报出：① `observation.ts:2729` 的路径常量；② 4 处 cmdline 判定；③ 45 对字节相同文件。**且不得**把 97 个提及全部报为复制——须按位置剔除注释与文档（真值应在 40 量级，即代码中的字面量数）。

**反向判据**　若对 `gate-script-base.ts`（被 70 处正当 import 的真共享模块）报出高复制度，说明它没有区分「经由单一访问器」与「各自硬编码」——这两者必须给出不同读数。

### P3 · 机件活性双轴 Artifact Liveness (Reference × Execution)

**定义**　每个可执行构件两个**独立**读数：
- `R` = 是否被任何执行路径引用（静态）
- `E` = 窗口内实际执行次数 + 最近一次执行时刻（运行时）

四象限：**活**（R∧E）/ **冻结**（R∧¬E）/ **孤儿**（¬R∧¬E）/ 不可能（¬R∧E）。

**现有工具为何测不到**　经典死码分析**只有引用轴**。本仓库上它会报 0 死码——而这是对的，孤儿确实是 0；但它同时会漏掉 70 个 24 天未执行的守卫与 68 个冻结超 30 天的 `.sh`。**冻结与孤立在这个仓库里是完全分开的两批。**

**本仓库实测**　孤儿 = 0；冻结 = 70 个守卫（24 天记账窗口内零执行）+ 68 个 `.sh`（31%，> 30 天未变更）。

**计算方法**　执行轴需要运行时记账。本仓库恰好有 `checker-cost.jsonl`，**多数项目没有** ⇒ archguard 应当**定义记录格式并提供接入垫片**（可参照 `checker-cost-lib.sh` 的 `run_checker_parallel_wait`），而不是假定它存在。记录最少需 `{name, at, verdict}`——注意本仓库现有格式 `{name, ms, n, load, at}` **没有 verdict**，这直接导致 P4 无法计算。

**验收判据（可证否）**　在本仓库上，必须把 70 个未执行守卫归入**冻结**而非孤儿，且孤儿数报 **0**。二者混为一谈即判不通过。

**反向判据**　若把 `experiments/` 下的 selfcheck 报成孤儿，说明它只看了 suite 接线一条路径（36%），漏了被其它脚本调用的 56%。

### P4 · 守卫谱系 Guard Lineage

**定义**　每个检测器机器可读地声明四元组
`⟨guards: 对象或不变式, wired-into: 执行路径, last-run, last-fired⟩`
工具核验前两项、记录后两项。

**新增的关键轴是 `last-fired`。** 一个**从未变红**的守卫，与一个**坏掉的**守卫，在记录上是同一个形状。

**现有工具为何测不到**　这不是代码结构问题，现有架构分析完全不涉及。本仓库已有全部原料却缺这一条关系：`checker-cost.jsonl` 记 name/ms/load **不记裁决**；`checker-mutation-check.sh` 验证守卫**能**变红，但不记录它**是否曾经**变红。

**本仓库实测**　**165 个守卫中声明了守卫对象的：0 个（0%）**。这直接导致「守卫对象还存在吗」在本仓库结构上无法回答——我只能查路径字面量，而多数守卫守的是一条约定（如 anti-drift 守「改动不得越出声明范围」），没有可指对象。

**计算方法**　需要两项约定：① 守卫头部的声明块（可复用现有 `capability-catalog.sh` 的登记位）；② 结果流记录裁决而非仅成本。有了这两项，工具即可对每个守卫回答：对象是否仍存在 / 上次运行 / 上次变红 / 从未变红。

**验收判据（可证否）**　对本仓库 165 个守卫，工具须能报出「已声明守卫对象的比例」（**今天应为 0%**）与「窗口内曾变红的比例」。引入声明后，须能逐个回答「该守卫的对象是否仍存在」。

**反向判据**　若把 `checker-mutation-check` 这类**预防性**守卫因「从未变红」报为可疑，说明它没有区分预防性与失效——判定必须同时采信 `last-fired` 与 `mutation-verified` 两项证据。

### P5 · 仪器腐烂 Instrument Decay

**定义**　一个写入载体的写入速率归零，**而它的产生路径仍在运行**。

**现有工具为何测不到**　这是遥测层的属性，不在代码结构里。且它的失败形态与「一切正常」同形：没有新记录，看起来就像没有新问题。

**本仓库实测**　`fan-in-step-trace.jsonl` 的 `suite` 步骤自 **2026-08-30T01:47Z** 停写（全历史 40 条），而同一条 fan-in 路径的 `ff`（158）、`merge-develop`（390）、`scoped-gate`（345）仍在写。后果：一次执行 **74% 的时长无记录**，两轮失败在步骤链上无痕。**没有任何机制发现它。**

**计算方法**　对每个载体把写入速率建成时间序列，当速率 → 0 **而伴生载体（同一代码路径产生）仍在写** 时告警。关键是用**伴生对照**而不是绝对速率——否则低频载体会被误报。

**验收判据（可证否）**　在本仓库上必须报出：① `suite` 步骤自 2026-08-30T01:47Z 停写；② `outcome` 字段自同期起缺失（仅 40 条带有）。

**反向判据**　不得把真正低频但仍在写的载体（如 `message-receipts.jsonl`，176 字节）报为腐烂。用绝对速率阈值的实现必然踩这个，是判不通过的充分条件。

## 4. 实施顺序与依赖

```
P2 身份复制  ──►  P1 删除闭包        （P2 产出的身份边就是 P1 的闭包边）
   纯静态                需 P2
   今天即可跑             回归集现成（8 个退役任务）

P3 活性双轴  ──►  P5 仪器腐烂  ──►  P4 守卫谱系
   需记录格式            复用 P3 记录        需声明约定 + verdict 字段
```

**建议起点是 P2**：纯静态、不需要任何新数据、在本仓库上立刻能验（三条验收判据全部现成），而且它的产出直接喂给 P1——P1 才是回答「删掉一个要付多少代价」的那个量。

**P3 与 P4 共用一个记录格式**，应一起设计：`{name, at, verdict, guards}`。本仓库现有的 `{name, ms, n, load, at}` 缺 `verdict` 与 `guards` 两个键，这正是 P4 今天算不出来的直接原因。

## 5. 结论：迁移 = 创建 + 删除，而只有创建被度量

前四节的所有读数收敛到一条可操作的结论。

**本仓库历史上「机制→产品」的迁移只真正完成过 1 例**（`promotion-driver-launch.sh` → `packages/quay/src/cli/driver.ts`，2026-08-23，原件已删）。

**同时「在 `packages/` 新增」且「在 `plugin/` 删除」的提交 = 0 次。** 迁移从来不是原子移动，一律是「重新实现，原件另行退役（或不退役）」。

**活标本 `fan-in/ff-merge.ts`（582 行，2026-08-31）**：
- 产品副本**确实是活路径**——按位置核实，`worker-driver.ts` 中 11 处对旧 `.sh` 的引用**全部是注释**；
- **但旧 `plugin/scripts/fan-in-ff-merge.sh` 仍在树上 581 行**，仍在 `capability-catalog.sh` 注册为**在册能力**，仍被 `suite-slot-ssot-check.ts` 的 I1 不变量当**活体代码**读取；
- 文件头自述 "the TS-ification of the **retired** bash" / "No shell-out remains"——**后半句真，前半句假**；
- 其 SPEC 的成功判据（旧 `.sh` 删除、删双副本 `fan-in-execute.js` 1010 行 ×2）**双双未达成，且无任何检查器守护**。

⇒ **迁移做到了「产品副本活了」，没做到「原件死了」。而卡住的那一半，正是 P1 测量的删除闭包。**

**这解释了为什么结晶停在一个面**：创建的成本可见且可估（写一个新模块），删除的成本不可见且无人度量（原件的 DC）。在一个对新增有充分机制（165 个守卫、catalog 登记、四件套判据）而对移除**一个机制都没有**的系统里，每一次迁移都会在删除那一半停下——**并且停下时的状态与完成态在记录上难以区分**（头注释写着 retired，调用确实没了，只有对象还在）。

**由此得到一条可立即执行的过程判据**：

> **裁定任何迁移/退役之前，先算 `R(X)` 并把删除那一半的成本写进决策。**
> 今天的做法是先裁定、再实现产品副本、最后发现原件退不掉。

**判据存在 ≠ 判据生效**：`orchestration/SPEC-execution-loop-productization-2026-08-28.md` §6 已给出唯一可复用的分界线——**确定性业务过程 → 产品层；语义判断 + 方法论观测器 → 机制层**。§8 并自带预警：「若此裁定不成立，P2–P4 会产品化到一半又退回 plugin」。**P2 现正停在该状态**，而判据成文后的 6 天里机制层仍以 10 文件/天沉积。**没有任何检查器守着这份 SPEC 的成功判据。**

**交付边界尚未裁定**：`packages/quay/package.json` 的 `files` 含 `"plugin"` ⇒ **发布的 npm 包携带整个机制层（334 个文件）**。在「循环是产品的一部分，还是建立在产品之上的另一个东西」被回答之前，「清晰的产品层」没有可收敛的定义。

## 6. 已知局限与反向判据

**必须先说的**：以下每一条都可能推翻本文的主张，列出它们是为了让它们可被检验。

1. **n = 1**。全部读数来自一个仓库。文中所有阈值（`R > 2`、`< 0.1%`、`> 30 天`）都是**假说，不是标定过的常量**。任何实现都不应把它们写死。
2. **50 天龄的天花板**。所有「寿命」类读数受年龄约束——被删文件最长寿命 37 天，只因仓库没有更老的文件。我用了两个归一化对照替代（死于可能寿命的前 18%；幸存者 44% 已超过任何被删文件的最长寿命），**但这个替换本身是一个判断，可以被质疑**。
3. **「生成近乎免费导致复制替代抽象」是一个机制假说，本文只在一个仓库上观察到它的相关物**。真正的对照是：同等规模、由人力写出的仓库是否呈现相反的比例（高缠结 / 低复制）。**该对照不可得**，因此这条机制陈述应当被读作假说而非结论。
4. **P4 的动机测量是欠功率的**。我判「守卫对象是否还在」只能查路径字面量，161 个守卫中报 8 个悬空、复核后真值 1 个。**这个测量弱到不足以支持任何结论**——它只支持一件事：今天答不出这个问题。
5. **archguard 的扫描范围**。文中「0 依赖环」仅覆盖 `packages/quay/src` 的 79 个文件，**未扫 `plugin/scripts` 的 314 个**。机制层是否有环**未测**——这是一个应当补做的读数，且它可能改变第 2.2 节的判断。
6. **重复计数的口径差**。`plugin/scripts` ↔ `experiments/*/scripts` 的逐字重复，我的直接测量是 **45 对 / 24 069 行 / 5 对漂移**（限 `.ts`+`.mjs` 同名比对，单一 experiments 目录）；更宽的扫描给出 47 对 / 24 290 行 / 14 对漂移。**取窄口径为准，宽口径记录在此备查。**
