# SaaS：让内网里的循环能被办公室外看见

- **Status:** Proposal（管理者，人给出方向）—— **明确未启动，启动条件见 §6**
- **Date:** 2026-08-06
- **性质**：架构与**时机**判断。核心主张：**它不是第二个产品，是第三种传输。**
- **Relates:** [`orchestration/SPEC-integration-architecture-2026-08-05.md`](../../orchestration/SPEC-integration-architecture-2026-08-05.md)（两个窄接口），
  [`orchestration/SPEC-state-crystallization-2026-08-05.md`](../../orchestration/SPEC-state-crystallization-2026-08-05.md)（每实体一个写入者），

---

## 0. 触发

人：**「可以考虑另开一个项目，做上述 quay web 服务的 SaaS 版：多用户、多项目；
让在内网用 quay 开发软件的用户在办公室外就可以访问自己的项目。」**

---

## 1. 真正难的不是多租户

**难的是数据在内网，SaaS 够不着。**

quay 的数据模型是**本地磁盘上 git 仓库里的 markdown 文件**（`tasks/*.md` 就是数据本身）。
SaaS 不可能反向伸手进用户的内网去读它们。

⇒ 架构上**只有一种形态成立**：

```
内网（驻场 agent）                     公网（SaaS）
  ├─ 拥有真值：tasks/ + git + 会话       ├─ 只读镜像（状态投影）
  ├─ 主动 push 状态出去  ────────────>  │
  └─ 主动 pull 回程消息  <────────────  └─ 回程消息队列（人的指令）
```

**这正好又是 `deliver()` / `observe()` 那一对**，只是传输层从 tmux/文件换成了 HTTPS。

---

## 2. 关键判断：它是传输层替换，不是重写

> **如果消息总线从一开始按「传输层无关」设计，SaaS 就是加一个 transport 实现。
> 如果按「web server 直接读本地文件」实现，SaaS 就得把业务逻辑重写一遍。**

| | 总线设计对了 | 总线设计错了 |
|---|---|---|
| SaaS 要做的 | **一个 transport 适配 + 多租户路由 + 认证** | 上述 **+ 把 web 层的所有读写逻辑重新实现一遍** |
| 真值源 | 仍在内网，SaaS 是投影 | 容易滑成「SaaS 也能改」⇒ 双写入者 |

**这个分叉在写第一行代码之前就定死了，事后补救的成本远高于当初想清楚。**
⇒ **本文的第一价值不是 SaaS 本身，是它对总线设计提出的约束**（见前置文档）。

---

## 3. 三条必须诚实说明的约束

### 3.1 密钥绝不出内网

驻场 agent 持有：模型 API key、仓库写权限、本机 tmux/进程控制权。
**SaaS 中继必须在设计上永远不需要这些**——它只转发消息，不代表用户执行任何东西。

**判据**：如果 SaaS 侧任何一条代码路径需要读用户的 API key 或仓库凭证，**架构是错的**。

### 3.2 SaaS 不能是真值源

按 `SPEC-state-crystallization` §3 的硬约束——**每个实体恰好一个写入者**。
今晚「六个源、四个答案」的教训（问「有几个任务在飞」得到 4 个不同答案）
**直接来自多写入者、无权威**。

⇒ SaaS 侧：**只读镜像 + 一个回程队列**。任务状态的唯一写入者永远在内网。
人在 SaaS 上「操作」的语义只能是**发一条指令**，不是**改一个状态**——
这与 [`quay-web-human-is-not-an-operator.md`](./quay-web-human-is-not-an-operator.md) 是同一条原则的两次应用。

### 3.3 新仓库会原样重演今晚所有的遗传问题

`dist` 不随 clone → `package.json` ENOENT → `mcp_entry` 路径形态错 → 构建产物不随 `git pull` 同步
→ `.quay/config.yml` 被跟踪导致每次 pull 结构性冲突……
**这一整条链子在一个新仓库上会重来一遍。**

**但这恰恰有价值**，见 §4。

---

## 4. 生态位视角：这会是 quay 的第一个非开发工具项目

按 `quay-as-a-living-system.md` §2 的实测结论：

> **亲代的环境掩盖了亲代的缺陷。子代进入不同生态位，才暴露出来。**
> （archguard 发现了 `full-suite-runner` 的裸 `✖` 判红——quay 自己跑 `node:test`，**永远发现不了**。）

**quay 至今的全部项目（quay / archguard / meta-cc）都是开发工具，都在开发者自己的机器上跑。**
SaaS 是第一个：

| 维度 | 现有三个项目 | SaaS |
|---|---|---|
| 用户 | 开发者自己 | **真实终端用户** |
| 运行环境 | 本机 | **公网 + 多租户** |
| 失败后果 | 自己重启 | **别人看不到自己的项目** |
| 数据边界 | 无 | **必须隔离** |

⇒ **它会撞到的问题，正是现在这三个都撞不到的。**
按生态位分化那条，这是一次**刻意制造的差异**，不只是「多做一个产品」。

---

## 5. 与「另开一个项目」的关系

人说的是「另开一个项目」。按现有网络形态，这意味着：

- 第四个 outer/inner 对，第四个 tmux session；
- **两机协作/任务认领的问题会立刻放大**（当前 A/B 两机已经在同一份任务板上无认领机制地取活，
  已实测出现文件级冲突）；
- 也是 `gap-fast-mode-cross-project-portability-strategic-question` 的又一次真实检验。

⇒ **在两机认领机制落地之前开第四个项目，会把一个已知的、尚未解决的问题乘以二。**
这不是反对，是次序上的提醒。

---

## 6. 启动条件：应当由外部信号触发，不是内部判断

**这条是本文最重要的一句。**

今晚刚在 os-anchor watchdog 上确认过一次同型错误：
用**实验室自伤**（4 次全灭，全部是本实验特有的危险操作，且根因都已在修）
去论证一个常设机制的必要性，**是循环论证**——
用一个正在被消除的风险，论证一个要长期存在的东西。

**SaaS 同理，不该由「我们觉得会有用」启动。**

建议的启动条件（外部、可证伪）：

> **有真实用户提出「我在办公室外看不到我的项目」。**

在那之前：
- **总线按传输层无关设计**（这条现在就要做对，成本几乎为零）；
- **SaaS 本身不动工**。

**理由**：前者是**保留选项**（成本近零，事后无法补救）；后者是**行使选项**（成本高，随时可行使）。
在没有需求信号时，正确的动作是保留而不是行使。

## 7. 未验证的部分（AC11）

本文**全部**是设计判断，**没有一条被跑过**：

- 没有真实用户提出过这个需求（**包括人自己也只是说「可以考虑」**）；
- 「传输层替换」的可行性依赖总线先做出来，而总线**也还不存在**；
- 多租户隔离、认证、计费——**一个字都还没想**，本文刻意不展开，因为在启动条件满足前想这些是浪费。
