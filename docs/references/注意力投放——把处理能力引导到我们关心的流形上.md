# 注意力投放——把处理能力引导到我们关心的流形上

> 状态：持续修订的工作文档（living reference）。初稿 2026-10-24，来自 CloudCLI 驾驶舱设计会话与 quay-fleet 协作会话的讨论。
> 与本目录其他文档的关系：以《维度边界与结晶》《两阶段周期版》《geometry-as-llm-architecture-interface》《harness-semantic-compression-and-meta-driver-builder》为理论底座；本文只处理一个问题——**人、LLM、机械这三种处理器的能力，如何被持续、精确地投放到我们真正关心的那部分高维语义空间上**。
> 约定：〔实测〕= 有数据出处；〔判断〕= 推论，待检验；每条判断尽量附可证伪的预测，见 §6。

## 0. 一句话

我们在建设的不是若干工具，而是一套**注意力投放机制**：在高维语义空间里勾勒出我们关心的流形（新的软件开发实践这一族系统的可行区域与演化轨迹），并把三种处理器的能力按各自的成本与视野，持续投放到流形上最需要的位置。meta-cc → archguard → quay → CloudCLI → quay-fleet 是这条路径上依次补上的「看」与「投放」能力。

## 1. 三种处理器

人、LLM、机械检查都是处理信息的形式。它们的差别不在「有没有智能」，而在四个量：

| | 单位成本 | 延迟 | 可靠性 | 能看见的维度 |
|---|---|---|---|---|
| 机械（测试、闸、扫描、契约） | 近零 | 毫秒到分钟 | 在已固化的轴上近乎完美 | 只看得见已结晶的轴 |
| LLM | 低 | 秒到分钟 | 概率性，会自信地出错 | 已点亮的轴及沿轴插值 |
| 人 | 极高、极稀缺 | 小时级（注意力排队） | 疲劳、偏好 | **唯一能开新轴（OOD 形变）** |

投放原则〔判断〕：**每个判断交给「看得见相关维度」的最便宜处理器。**看不见就上移，看得见就下移。

## 3. 现状：人的处理能力被投放在哪里〔实测〕

数据：2026-10-11 至 10-24 的 Claude Code 会话记录（剔除 worker 与自动会话后 2159 条人类输入），以及 `~/.quay-fleet/` 的 attention / outbox / resolution-cases。脚本见 claudecodeui 任务 `observation-p0-view-instrumentation-and-weekly-report`（`scripts/workload-report/`）。

- 每天并发 3–5 个项目；14 天 675 次跨项目切换，切换间隔中位 2.2 分钟；相邻两条输入一半落在不同会话。
- 人工抽样 60 条的构成：新意图 / 设计 ~22%，会话间转述 ~20%，轮询进度 ~18%，语音测试 ~13%，运维排障 ~12%，「同意 / 继续」~8%，纠偏与验证 ~5%。31% 的输入 ≤ 20 字。
- fleet 推给人的消息 80% 是摘要与 goal-achieved，411 条无人处理过期；人标记的反馈 noise 68 : useful 3；真正需要人处理的约每天 1–2 条。
- **盲区**：以上只统计打字。「点开会话读输出、切去 Quay / 架构 tab 看状态」这类只看不打字的切换完全没被记录——而用户确认这正是最大负载（§5.2）。

解读〔判断〕：人约一半的处理能力花在本该由下层处理器完成的粘合工作上（轮询应是机械的，转述应是 LLM 的）；真正属于人的 A 类形变只占约两成。目标是把这个比例倒过来。

## 4. 人不可替代的部分

引自《维度边界与结晶》§3 与《两阶段周期版》§8.3，并经本轮讨论确认：

1. 开新轴、换范式（A 类形变）；
2. 触发时机——B 类检查至今都由人从环外发起；
3. 裁定范围、守住正确方案防止过度推广；
4. 收缩与退役——实测机制发起的收缩为 0 次；
5. 样本外审计、goal 立项审批、呼吸节律。

人**不该**做：调和矛盾的状态源、读全部代码、充当唯一的异常探测器、在会话之间搬运上下文。

## 5. 判断

### 5.1 结晶阶梯是双向的，目前只建了向下的半边

- **向下（结晶）**：人反复做的判断 → LLM 可代理的策略（授权章程）；LLM 反复做的判断 → 机械检查。每下一级，单位成本降一个量级。
- **向上（降级 / 上报）**：机械检查变瞎（静默、恒绿、读数恒定）→ 退回给 LLM 或人；LLM 遇到授权外的问题 → 上报给人。

向上半边几乎不存在：收缩 0 次、18 个闸 0 事件无人察觉。harness 应当显式记录**阶梯迁移**（本周哪些判断下移、哪些检查上移），作为健康度的核心读数。第一个向上的机制：claudecodeui 任务 `contraction-candidates-signal-inventory-and-design`。

### 5.2 每个投影都有盲区，盲区必须声明

§3 的负载分析把「只看不打字」投影成了 0，是用户指出来的——与《维度边界与结晶》§2.2「仪器把相异的那一维压成 0，系统自信地收敛到错误盆地」同构。驾驶舱里的每个摘要、指标、磁贴都是投影。

规则：**每个投影除了声明它显示什么，还要声明它看不见什么（blindSpots），并给出回到原始材料的入口。**这把「压扁」从隐性失败变成显式的已知限制，比追求更完整的摘要更重要。

### 5.3 沉默有歧义：不会大声失败的信号必须配活性读数

闸、观察层的生产者、联络会话、fleet 的注意力流反复出现同一模式。应上升为 harness 的通用不变量，而非每个任务各自想起才补。已落实：CloudCLI 观察层的生产者心跳（`observation-object-model-seen-cursor-and-delta` AC6），fleet `liveness` 读口（`fleet-liveness-read-port`）。

### 5.4 处理器之间靠认识层级协作，不靠互相信任

每个读数、每个决定都带认识层级（fact / inference / experience / llm）与验证状态，按层级决定能授权什么。两个 agent 一致只是更高置信的 inference，不是 fact（quay-fleet 的倡议决策日志据此设计）。驾驶舱上每个读数应显示层级，裁定队列抽查 inference 层。

### 5.5 对「理解」的检验是预测

《两阶段周期版》附录的诚实条款：几何模型在三个项目里先于结果的预测为 0 次。我们对流形的理解是否为真，唯一检验是**先登记预测、再对账**（confirmed / refuted / no-prediction）。倡议章程因此带 `predictions[]`，见 §6。

### 5.6 最该被优化的是「开新轴」的成本

执行正在被 LLM 和机械接管。人的不可替代处是引入与退役轴（呼吸）。前沿指标：

- **轴引入延迟**：从人说出一个新方向，到它成为可观察、可检查的轴所需的时间。例：2026-10-24「观察才是最大负载」→ T0 埋点 + 观察墙任务立项，约 1 小时。
- **轴退役延迟**：一个不再有用的仪器多久被发现并移除。

### 5.7 建 harness 本身也在流形上

harness 是元层；元机制要比被治理对象小一个量级（ADR-021），而 harness 有 3.7 倍倒挂的前科（harness §12）。harness 的建设本身也要做注意力核算：一周里多少处理花在建 harness、多少花在被治理的产品上，超预算即收缩。

### 5.8 投放的层级：人向上、向外退出

| 层 | 对象 | 主要执行者 | 人的角色 |
|---|---|---|---|
| L0 执行 | task | worker | 不在场 |
| L1 项目 | goal / AC / 项目 loop | quay driver + 项目会话 | A 类形变、抽样审计 |
| L2 倡议 | 跨仓库的一件事 | 联络会话 + fleet | 批准章程、裁定上报 |
| L3 组合 | 倡议集合、优先级、退役 | fleet manager 辅助 | 主要停留层 |

撤出某一层的前提：授权（章程 grantScope）、硬边界（跨仓库契约测试，长在写入路径上）、活性、独立审计（决定性的门 + 对 inference 层的人工抽查）、经验传递（`~/.claude/shared-lessons/`）。
拓扑是星形（fleet 为中心），协调开销 O(倡议 × 项目) 而非 O(项目²)；活跃倡议数有上限。

### 5.9 「该看什么」与「看了什么」是两条轴

（与 quay-fleet 对齐）对象身份收敛为同一套坐标（`quay://`、`cloudcli://` 等 URI）；但 fleet 的 attention（push / 紧迫度）与 CloudCLI 的 SeenCursor（pull / 已看到）不塌成一个模型。写者由 URI 前缀机械推出：`quay://*` 的已看到写回 fleet 的 acked（fleet 单写），其余由 CloudCLI 持有。驾驶舱要呈现的是两个场的差：**紧迫而尚未被看到的地方**。

## 7. 开放问题

1. 「已看到」写回 fleet 的接口形状——等观察墙有真实使用数据再定。
2. 阶梯迁移如何机械计数（什么算一次「下移」「上移」）。
3. 盲区声明的粒度：按对象类型声明，还是按每个读数声明。
4. 轴引入延迟如何自动测量（从哪一刻算「人说出」，到哪一刻算「可检查」）。
5. 联络会话「互相同意」的偏误，抽查比例（暂定 1/5）是否足够，如何用对账结果调整。
6. 组合层（L3）是否需要独立的 manager agent，还是由 fleet observe 的投影足够。
