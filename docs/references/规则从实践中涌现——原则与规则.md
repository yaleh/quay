# 规则从实践中涌现——原则与规则的分界

> 本文记录一次以 quay 自身规则语料为实证的讨论（2026-08-30）：CLAUDE.md 的硬规则在
> 一个月内从 0 条长到 18 条、且每条都带事故日期与发生率——由此讨论「在这些规则之上
> 找到更通用的原则」这句话的边界：原则（可事前设计）与规则（不可提前设计）不是「从
> 一般到特殊」的推导关系，而是 `L(X)=L(G)+L(R|G)` 的分解关系 + 扩张/收敛的呼吸操作
> 关系。框架文本是《基于几何信息论的未来软件开发与信息系统建设(两阶段周期版)》，
> 及其严苛审计《几何框架作为 LLM 软件架构接口的可用性讨论》。结论分层给出。

## 0. 实证：规则是「长」出来的，不是「设计」出来的

- CLAUDE.md 编号硬规则：**2026-07-19 有 0 条 → 2026-08-01 有 4 条 → 2026-08-30 有 18 条**
  （1、2、3、3b、4、4b、4c、5、5b、6、7、8、9、10、11、11b、12、12b）。全文「实证」
  标注 18 处。
- **每条规则几乎都带事故日期与发生率**：3b「同日三次、两层、三个互不相关的载体」、
  4c「一天内同形三次，全部是我自己写的判据」、5b「同日三次」、12「人指出后实测
  44/12/3」。没有一条是「先有规则，再等事故」——全部是「先有事故，当场立规则」。
- 近 14 天规则类提交几乎每天一条，每条钉一个具体失败：FORCE_COLOR ANSI 破 suite 摘要
  解析 →「5b 同族」（补第四表面）；needs-human 写盘不提交 git →「5b 未 port 到
  needs-human 兄弟」；分支同步撞 fan-in 持锁窗口 →「直落 develop 边界」。会话历史
  （meta-cc 可查）里也是同一形态：branch-principle 会话、`gap-main-manager-doc-doc-only-ff-only-tracking`、
  各种「检查最近 24 小时会话历史分析 XX 违规」——规则从具体事故当场立起，不是先立规
  则再找事故。
- 机件密度同步增长：capability-catalog 声明 **300 个脚本、295 个在产出**。

**读法**：这是一条只进不出的曲线，说明项目处于规则层的**扩张期**（见 §4）。单看某一条
规则，「它为什么是这句话」只能由它锚定的那次事故解释——这正是 `R|G` 的条件性。

## 1. 核心映射：原则 = G，规则 = R|G

GIT 基本公理 `L(X) = L(G) + L(R|G)`（`G` 为生成规则/抽象，`R|G` 为在其上的残差实现）
套到规则语料上：

- **原则 = G**：薄、可事前设计、跨项目迁移。例如「优先观测直接量，不叠加未经验证的
  过滤/派生」（4b 的抽象形态）。
- **规则 = R|G**：厚、条件于本项目、只能在实践上长出来。例如 4b 的具体实例——本机
  comm=`MainThread` 使 `pgrep -xc node-MainThread` 恒零、而 `pgrep -cf 'bin/node'`=25；
  `outer.ticklog` 行形谓词对 `- 04:09Z` 形真样本命中 0。这些内容离开本项目的具体载体
  就无意义。
- **两者的关系不是「从一般到特殊」的推导，而是「呼吸」的操作关系**：扩张（让实践
  失败，注入熵）→ 收敛（把事故压缩成规则，支柱化 + 断言加固）。这正是两阶段模型对
  DreamCoder wake-sleep 的对应：wake = 在当前库 `G` 下解新任务；sleep = 从已解任务
  中提取新抽象更新 `G`。

**「规则无法提前设计」的正确形式化**：`R|G` 不可从 `G` 推出——它条件于实际系统 `X`
（本项目的可行流形 `M_T`），不是条件于原则本身。原则不生成规则，原则只提供三样东西：
**(a) 轴（目标闭包）**、**(b) 准入判据**、**(c) 执行面**。规则由事故在流形上生成。

## 2. 为什么「无法提前设计」——三点论证（均有本项目实证）

**① 约束集 T 与漂移分布是项目特异的，事前不可知。** 规则是断言（`A` = 边界约束）。
值得锁哪条断言，取决于系统实际往哪漂——这是 `M_T` 的性质，不是目标的性质。提前设计
的规则 = 没有对应实测失败的断言 = 沿未测轴的 `L_T=0` = 审计文档里的**伪收敛**。本项目
自己的实例：`gap-phase-boundary-differential-accounting`，status=done、AC 5/5 全勾，
而生产载体 `verification-round.jsonl` **167 轮中含 `cpu_usec` 的记录 = 0**——5 条 AC 全
由 `QUAY_TEST_CGROUP_SCRIPT` 注入的假 cgroup 数据满足（硬规则 4 推论三）。提前写好的
规则就是那个 fixture：证明「能产出」，不证明「已产出」。

**② 规则集本身是被优化的系统，其最优解依赖数据。** MDL 的完整形式是 `L(H)+L(D|H)`：
最优规则集 = 对本项目事故历史**描述长度最短**的集合。没有那份历史，就无从最小化。项目
已把它制度化成了硬规则 12：「要求一个新前置/新机制之前，先给出它【已经发生过几次】」，
给不出发生率就降为观察项、不作阻塞——这是把「不能提前设计」做成了机械闸门；12b 又补
了取证方向：默认查历史（`since` 全量），不是等下一轮（窄窗计数冒充全量读数的实例：
同 session id 不加 `since` 的查询，全历史真值 = 90，而窄窗读数 = 1）。

**③ 自然梯度：正确的下降方向由当前点的局部几何决定。** 模型里 `X_{t+1} = X_t − η·I(X_t)⁻¹∇L(X_t)`，
`I(X_t)`（局部 Fisher 度量）只能站在 `X_t` 上量，不能从目标推出。规则空间同理：哪些
规则被违反会真的改变行为、哪些是空转，只能在操作点上测量。审计文档里 manda 的第三次
架构反转（`∇L` 按「最低 `L(R|G)` 局部步」指错方向、把 dispatch 塞进 core，需自然梯度
校正）与本项目的硬规则 4b（「代理量会与实际偏离——优先观测直接量」）是同一句话的两个
实例。

## 3. 可设计的是接口，不是内容——「原则不可设计」是假命题的一半

如果你说「原则也无法提前设计」，那与实证矛盾。项目**事前设计了**不少结构，而且它们是
规则能累积的前提：

- **目标闭包（哪几根轴存在）——可设计**。GIT 的五项损失 `L_T/L_C/L_D/L_G/L_S` 断言「完整
  目标就这几根轴」；本项目规则语料同样聚成几个家族（判定方法 / 观测方法 / 修复后核验 /
  机制准入 / 记录产物）。闭包的价值不是预言规则内容，是**让暗轴可检测**——规则没长满的
  格子是显式的空白（审计文档层次一：传统 SE 是并列惯用语堆、无「是否测全」的闭包 claim；
  正常 review 只 instrument 了 `L_T` 与半个 `L_C`，`L_G`/`L_D`/`L_S` 基本是暗的）。
- **准入判据——可设计**。发生率要求（硬规则 12）+ 可区分性要求（3b 的「未评估」独立取值、
  9 的「守与不守在记录上可区分」）。
- **执行面——可设计，且是唯一真正复利的地方**。审计文档的结论：几何唯一付过钱的，是
  把「连续意图 → 可执行检查」的投影算子 `Π_{S→E}` 机制化——**硬形变**（截断状态空间，
  先验侵蚀不了），区别于软形变（prompt、更醒目的措辞，会被流长程重新侵蚀）。

**本项目对「硬形变才存活」的实证最充分**：**带产物的规则活下来，标「靠自觉」的反复再犯**。
硬规则 2 在立条当天就同形四次，直到补上「引用一个计数之前，先打印它匹配到的前 3 条实际
内容」的动作才刹住；3b 的三个实例（`task-status-drift-check.ts:126` 的零未勾判完成、
`slot-refill.ts:373` 第一行判 landed、`outer-tick-log-check.sh:107/112/205/262` 的 ACTION
解析不出全分支跳过）共同症状就是**没有「未评估」这一态**，修法是给「无法评估」一个独立
取值；9 的正文自己写着「该给它造产物，不是把它写得更醒目」。审计文档的警告在本项目里
同样成立：原则写得越自洽流畅，对 LLM 越有欺骗性——硬规则 4 推论四「能解释现象的说法
不是被检验的结论」，三次都被一条命令的对照推翻（查动作记录 / 让两假设给出相反预测 /
改一个参数看结论翻不翻）。

**精确表述**：原则给格子、给判据、给投影算子；规则的内容（具体直量、具体 seam、具体
谓词）必须在流形上读出。可事前设计的是「接口」，不是「内容」。

## 4. 规则语料自己也在呼吸——收敛的信号已经出现

套用模型的呼吸节律看规则语料本身：

- **扩张期（现状）**：一个月 0 → 18 条，每条带事故日期。这是受控熵注入——`d` 暂时上升。
- **收敛的标志其实已启动：规则正在被支柱化**。看结构就知道：4 长出 4b（观测侧镜像）、
  4c（撰写侧镜像）、推论一/二/三/四；5 长出 5b；11 长出 11b；12 长出 12b。父规则是 G，
  子规则是 R|G，正在归并——这是 `L_D` 在规则语料上起作用。
- **CLAUDE.md 头注释本身就是 MDL 预算**：「本文件是唯一每会话自动注入的文档——它的行数
  是本仓库最稀缺的资源」「任何清单、命令块、参数表都属于它们各自的正本，在这里复制
  一份就是制造漂移」。这是对 G 的体积设约束（`L_D`），同时是 `L_G`（别重复造抽象）。
- **何时做一轮显式收敛 pass**：当新规则的边际吸收率下降（新事故不再被旧原则吸收、而是
  开新格子）、`∂L_D/∂t → 0` 时。当前 18 条里有几条是窄机制性规则（6、7、8、10、11），
  若被后续原则吸收应降级为「实例」，正交的新规则才升级为「候选原则」。
- **监测信号用模型自己的本征维度 d**：如果规则语料停止归并、每条正交、无 subsumption，
  `d` 涨——这是 GIT 给的架构腐化早期预警，用在方法层自己身上。同一条杠杆，反过来指自己。

## 5. 操作纪律（对规则语料的管理者）

1. **别试图提前设计完整规则集。** 保持 G 薄（闭包 + 准入判据 + 呼吸节律），让规则按流形
   累积。硬规则 12 已是闸门；剩下的工作是让发生率读全（12b：默认查历史，不是等下一轮）。
2. **新规则入册需要两张通行证，缺一不收**：它拦截了哪次失败（发生率），以及**守与不守
   在记录上是否可区分**（产物 / 硬形变）。只有软表述、没有执行面的规则，标为观察项。
3. **对规则语料做定期收敛 pass**：把被原则吸收的降级、把正交的提升、把已证伪的退役。
   这一步本身就是一次 `Π_{S→E}` 的实例——把「这套规则还成不成立」这个连续判断，投影
   成几个可执行的计数。

## 6. 结论与证据分级

**结论**：「规则无法提前设计」是对的，但它的对不是「设计无用」，而是「设计只能覆盖 G
的薄层——闭包、判据、投影算子；`R|G` 必须由事故在具体流形上生成，再靠支柱化反哺 G」。
审计文档给了这条结论的精度上限：能复利的不是更抽象的连续理论，而是那个
`region → executable check` 的离散化算子。本项目这一个月的规则演化，就是把该算子跑在了
自己身上——`实证` 标注是它的梯度信号，`产物` 标注是它的硬形变，`发生率` 要求是它的
准入门槛。

按审计文档的三级标准分级：

- **证据充分**：规则由实践涌现、原则不生成规则只提供闭包/判据/执行面——本项目的规则
  演化曲线 + 事故-规则一一对应可核（§0、§2）。
- **机制成立待验**：支柱化 = `L_D` 在规则语料上的作用、收敛 pass 会降低语料总描述长度——
  方向正确，尚未做过一轮显式收敛 pass 去实测（§4）。
- **观察项**：本征维度 d 用作方法层腐化预警——从模型类比借来的量，本项目没测过，不应
  作为阻塞判据（遵硬规则 12：先给发生率）。
