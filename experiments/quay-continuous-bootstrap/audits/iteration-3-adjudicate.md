### 3. `addParam()` helper correctness

```js
function addParam(urlPath, key, value) {
  const u = new URL(urlPath, "http://x");
  u.searchParams.set(key, value);

}
```

### 4. Open-redirect guard in back link (QX-011)

**Code read directly (line 136)**:

```js
const backHref = fromParam && fromParam.startsWith("/") ? fromParam : "/";
```

Test in `serve.test.mjs` (lines 509–514):
```js
const externalFrom = encodeURIComponent("https://evil.com");
const detailExternal = await get(ux3Port, `/task/UX3-1?from=${externalFrom}`);
assert(
  detailExternal.body.includes('href="/"') && !detailExternal.body.includes("evil.com"),
  "... open-redirect guard rejects external URL, defaults to / (QX-011)"
);
```

This test passes. `https://evil.com` is correctly rejected (does not start with `/`).

**Finding (NOTE — not a blocker):** The guard `startsWith("/")` allows protocol-relative URLs such as `//evil.com`. A `?from=//evil.com` value starts with `/` and would be used directly as `backHref`, yielding `<a href="//evil.com">` in the rendered HTML — which is a browser-resolved protocol-relative reference to `evil.com`. Independently verified:

```
node -e "console.log('//evil.com'.startsWith('/'));"  // → true
```

The test suite does not exercise this case. In practice, the `?from=` value is only ever generated by the server itself (encoding `currentListHref`, which is always a safe relative path), so the attack surface is limited to a manually crafted URL. However, the guard as written does not fully close the open-redirect surface and the missing test case leaves it undetected.

**Additionally**: the action POST handler uses the same `startsWith("/")` guard for `baseRedirect` before passing it to `addParam`. However, `addParam` itself parses its input through `new URL(urlPath, "http://x")` and returns `u.pathname + "?" + ...`, which normalizes `//evil.com` to `/` (URL parsing treats it as a host, not a path). So the action-handler redirect is safe even for `//evil.com`; the vulnerability is isolated to the GET detail page back link rendered directly in HTML.

Recommendation: tighten the guard to `startsWith("/") && !fromParam.startsWith("//")` or use a URL-parse normalization approach consistent with `addParam`. Also add a `//evil.com` test case.
