Verdict: FAIL
--------------
The Web UI's "Advance" action_button does NOT perform the task's status
round-trip. It gate-checks correctly (Step 1's RED path is fully correct
and matches CLI `task check`), but on success it only *delivers a trigger*
(here: prints instructions to the server process's own stdout, since no
manda dispatcher is configured) — it does not itself drive the task to its
next status. The page's own success banner text ("Done: Task ... advanced")
actively overstates what happened: nothing about the task was "done" or
"advanced"; only a trigger message was printed server-side. An operator
watching only the browser UI, with no independent CLI/task_get check, would
be misled into believing the task transitioned.

This matches the source-level reading of packages/quay/src/serve.js's POST
/task/<id>/action/<actionId> handler and packages/quay/src/action.js's
deliverTrigger(): by design, action buttons dispatch async work for
something else (a human, a manda-managed subagent, or Claude-Code-inline
sync spawn) to complete; they are not a synchronous status-mutation
primitive. In THIS scratch environment (no manda, no Claude-Code-inline
wiring configured), the round trip cannot complete via the UI alone.

Gap logged (per M28 "log, don't fix" discipline):
G-S4-01 (UX honesty): the POST action route's success banner says
"Done: Task <id> advanced" even in plain-CLI-print degraded-delivery mode,
where nothing about the task has changed yet. Recommend the success message
be conditioned on delivery mode, e.g. "Trigger sent (print mode) — run the
printed command to complete the transition" vs. an unqualified "advanced".
Disposition: DEFERRED — future-candidate backlog note (UI copy-only fix,
no functional gate-logic change implied); not fixed here per charter's
"log, don't fix" discipline. Filed for the DIR-001 backlog, not blocking
this milestone.

G-S4-02 (capability gap, not a bug): action_buttons' "advance" semantics
depend entirely on which deliverTrigger mode is configured/available
(manda / Claude-Code-inline / print / mock-log). In the print-degraded
mode used by this scratch harness (representative of a bare `quay serve`
deployment with no agent dispatcher wired up), the Web UI cannot complete
an end-to-end round trip unassisted. This is an environment/config
limitation, not a code defect — but it means Scenario 4 as specified
("Web UI task-board round-trip", "independent task_get/task view
confirmation of persisted state") genuinely does not pass out of the box.
Disposition: DEFERRED — future-candidate backlog note recommending either
(a) documenting this limitation prominently in the Web UI's own copy, or
(b) wiring a default in-process delivery mode for `quay serve` so the
button is functionally complete without external dispatcher setup.
