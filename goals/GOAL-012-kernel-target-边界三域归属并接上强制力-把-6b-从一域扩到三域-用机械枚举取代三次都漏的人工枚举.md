## 背景

2026-09-09/10 一夜之间，GOAL-009 的 AC-207（第三方项目端到端自证）在真实远程主机上连续撞出 **8 个独立缺陷**，逐个解锁后又撞下一个：`resource-gate.sh` 锚点 → shipped `profiles.yml` 缺 worker roles → `promotion-driver`/`worker-driver` 三处锚点 → `worker-driver` 另 3 处 + `cap-from-gate` 1 处 → `DOC_BRANCH` 硬编码 → fan-in 三步硬编码 `scripts/test.sh` → `full-suite-runner` 家族 5 处 naive `__dirname`。

**它们不是 8 个孤立 bug，是同一个结构性缺口的 8 次显形**：**shipped kernel 代码在驱动目标项目时，伸手去拿只存在于「本仓库自己」的东西。**

**为什么本仓库结构上测不出这一类**：本仓库同时满足三种身份——它既是 kernel，又是 target，还拥有全部 dev-tree-only 能力。**不存在任何一种本仓库的配置能让这些缺陷显形**。⇒ 无论单测写多细都覆盖不到；只有一个「不像本仓库」的目标才能暴露。这就是它必然靠试错逐个发现的根本原因。

**既有契约已存在但两处不足**：`SPEC-plugin-lifecycle-single-bundle-2026-09-02.md §6b` 已写下「解析器契约」三条约束、并指定唯一解析器 `packages/quay/src/plugin-root.ts`。缺的是：
① **只覆盖三域中的一域**（脚本路径）——分支身份与能力身份从未纳入；
② **没有强制力**——落实靠人工枚举调用点，而人工枚举已做过 **3 次**（`gap-plugin-root-resolution-non-skill-entrypoints` / `-remaining-callsites` / `-round2`），**3 次都有遗漏**，第 4 簇今晚才撞出来。硬规则 5b 所述形态，发生率已达 3。

## 范围与非目标

**范围**：

① **三域归属写进 SPEC**（扩 §6b，⛔ 不另起炉灶）——每一处运行时「伸手」（脚本路径 / 分支名 / 命令）必须归属且仅归属一域，由该域唯一解析器产出：
   - **KERNEL 域**：随 quay 出厂、住在运行中内核旁的东西（`resource-gate.sh`/`ready-pool-check`/`process-budget.sh`/`full-suite-runner` 等）⇒ `resolveKernelSibling`/`resolveKernelPluginRoot`；⛔ 不得锚在 target root/worktree/naive `__dirname`。
   - **TARGET 域**：属于被驱动项目、逐项目不同的东西（分支名/`test_command`/`tasks_dir`）⇒ 读目标 `.quay/config.yml` 或其实时 git 状态；⛔ 不得是 kernel 代码里的字面量。
   - **DEV-TREE-ONLY 域**：只有当 target 就是本仓库时才存在的能力（bucket 化 suite / doc 静态检查 / `scripts/test.sh` / capability-catalog）⇒ **条件能力**：在则用，不在则**以可区分取值降级**；⛔ 不得「试着调用然后 exit 127」。

② **A/B 两域的静态检查器**——把「人工枚举调用点」换成机械枚举，接入常规套件。

③ **一致性目标（conformance target）夹具**——沿三域轴线尽可能不像本仓库（无 `plugin/`、分支非 `author`、无 `scripts/test.sh`、只有 `test_command`），接入常规 `scripts/test.sh`。
   **必须由真实 `quay-init` 现场生成**——⛔ 不是提交进仓库的快照、⛔ 不是手写 `.quay/config.yml` 的 `makeWorkspace()` 形态。理由：手写夹具匹配的是「测试作者以为的布局」而非「quay-init 实际产出的布局」，而今晚的 `profiles.yml 缺 worker roles` 恰恰是二者之间的漂移——**任何手写夹具都会照 driver 的期望去写，从而把这一类结构性地藏起来**。
   初期两个配置：**P-real**（三轴全不像本仓库，做闸）与 **P-self**（本仓库形态，做负控制——断言降级不回流）。

④ **已知站点按检查器枚举迁移完毕**——完整性由机械枚举证明，⛔ 不是「改了被报出来的那几处」。

**非目标（明确排除）**：

- **不把 `full-suite-runner` 的 bucket 语义移植到第三方**——第三方拿到的是 `test_command`，这是**降级**不是移植（人 2026-09-10 裁定①：第三方项目验证强度降级可接受）。
- **不追求三域统一检测器**——C 域「这是不是 dev-tree 专属能力」需要语义，静态检测不到；**C 域的强制力来自夹具，不来自检查器**（⛔ 不做一个做不出来的承诺）。
- **周期性真实远程复证不写成本 goal 的 AC**——`achieved` 不可逆，活性/周期性判据写成 goal AC 是 2026-09-09 退役 AC-180/184/186 的同款类别错误。人 2026-09-10 裁定②的「真实远程」那一半归**例行/监控**，一次性证明归 GOAL-009 的 AC-207。
- **夹具暂不跑真 `npm install` 安装物**（人 2026-09-10 裁定：暂缓，机制跑起来后再检查）——理由：dist 布局特有的 naive `__dirname` 一类**已由 A 域静态检查器覆盖**（AC-224/225 静态、穷举、便宜），夹具再装一次包每轮多花十几秒却不增加覆盖面。**残余盲区见风险 6。**
- **单轴探针先不建**（只缺 `plugin/` / 只改分支名 / 只缺 `scripts/test.sh` 各一个）——它们的价值是「红了能快速定位是哪个域」，那是诊断便利、不是覆盖率；等真出现一次难归因的红再加，代价只是生成器多传一个参数（硬规则 12 的精神：别为还没发生的问题先加机制）。
- 不改本仓库自身运行行为（回归：逐字不变）。
- GitHub provider 对第三方驱动的映射（沿用 GOAL-009 非目标）。

## 退出条件

散文版：

1. 每一处运行时「伸手」都归属三域之一、由该域唯一解析器产出——**无裸字面量、无 naive `__dirname`**，且这一点由**机械枚举**证明而非人工清单。
2. 「能力不存在」有**独立取值**，与「能力存在但失败」在载体里可区分——不再以 `exit 127` 的形态出现。
3. 存在一个沿三域轴线尽可能不像本仓库、**由真实 `quay-init` 生成**的一致性目标，**跑在常规套件里**；本类缺陷在它上面**先红**，而不是等真实第三方项目撞出来。
4. **本仓库自身行为逐字不变**——降级只对第三方生效，不得回流污染本仓库的验证强度。
5. 检查器**能取假**——每个新检查器都有突变用例证明它会红（⛔ 恒绿的检查器是假保证，比没有检查更贵）。

机器判据在本 GOAL 名下的 AC 记录里，**不在本节**。

## 风险

1. **降级让第三方的验证强度低于本仓库**——人 2026-09-10 裁定①已接受。但**必须在载体里可见**（退出条件 2 的独立取值就是这个可见性），⛔ 不得静默降级；否则「第三方跑绿」会与「第三方根本没跑」同形。
2. **检查器过宽会误伤合法的 dev-tree-only 代码**——本仓库有大量只对自己有意义的自检工具（`precommit-guard`/`runner-static-gate`/`identity-replication-check` 等，今晚扫描已确认它们锚在 root 是**正确的**）。⇒ 检查器必须能表达「本条属 DEV-TREE-ONLY 域」，且该豁免要带理由、可复核，⛔ 不是一个无理由的 allowlist。
3. **夹具本身也只跑在本仓库里**——这是有意为之：夹具的价值恰恰在于它在本仓库内部制造一个「不像本仓库」的目标。但**夹具与真实第三方的差异本身是残余风险**（夹具是合成的，真实项目的形态更野），⇒ 裁定②的真实远程周期性复证是这条风险的对冲，不可省。
4. **三次人工枚举都漏了**——本 goal 的核心赌注是「机械枚举能做到人工做不到的完整性」。若检查器本身写得不完整（比如只认 `path.join` 不认模板字符串），会重复同一个失败。⇒ 检查器的突变用例必须覆盖**多种拼接形态**，不止一种。
6. **夹具不装真安装物 ⇒ dist 布局的行为面有残余盲区**：静态检查器看得住「源码里锚错了」，看不住「打包后运行时布局与预期不符」这类只在真安装物上才显形的问题。⇒ 该盲区由裁定②的**真实远程周期性复证**兜底；人 2026-09-10 明确此项**暂缓、待机制跑起来后再检查**，⛔ 不是认为它不存在。
7. **夹具生成器自身的卫生**：mkdtemp 生成、**不提交**（嵌套 `.git` 无法提交；提交即开始漂移）、⛔ 不得落在仓库树内被 `ready-pool-check` 当成真项目发现而污染派发计算、必须自带 teardown（本机已有 3389 个测试遗留目录 / 1.1G 的前科）。
5. **判据的类别纪律**：本 GOAL 的判据只引用不会自行回退的量——代码状态与套件绿红，⛔ 不含进程存活/远程主机可达性/当前真实第三方项目的跑通状态（后者归 GOAL-009 AC-207 与例行监控）。

## 与其他 goal 的关系

`GOAL-009`（交付面端到端自证）是**验证型**——证明端到端能跑通一次；本 GOAL 是**机制型**——让这一类结构上不可能再发生。二者是 `GOAL-001`→`GOAL-010` 的同款关系（把机制用起来之后才暴露的结构缺口）。

**AC-207 留在 GOAL-009 不动**——它是真实世界的最终证明；但这意味着 **GOAL-009 在本 GOAL 落地前关不掉**（AC-207 此刻正卡在本 GOAL 要修的第三簇缺陷上：`full-suite-runner` 家族 5 处 naive `__dirname`）。本 GOAL 是 AC-207 的前置。

`GOAL-011`（store-commit 传播策略）与本 GOAL 同时 active，二者不共享 AC，受 I1′ 硬上限约束（cap=3，立本条后恰好占满）。
