## 背景

2026-09-10 对「用 quay 驱动第三方项目」的五维预期行为做系统核查，发现两处**不在 GOAL-009 退出条件内**、且**无任何 AC 覆盖**的缺口。两者共同点：**交付出去的东西，下游拿到手后是不是真的能用**——而这一问从未被机械问过。

**⚠️ 缺口 A 已被证否——原立条前提是本人误判，如实更正（2026-09-10 同日）**：立条时称「下游 CLI 与 web 不可用（Node 底线致 shipped CLI 拒跑）」。**该结论错误，根因是调错入口**：所调的 `lib/node_modules/quay/bin/quay.js` 是包内**源码路径的版本探针**，而 `package.json` 的 `bin` 逐字为 `{"quay": "./dist/quay.js"}`——真正的安装入口是 dist bundle。用正确入口 `<prefix>/bin/quay` 实测：`--help` 正常、`task list` 正确读出第三方项目任务。**且它在该宿主还是 Node 18.19.1 时就已可用**（本人当日更早即用它成功停过 driver，返回 `stopped`，当时未意识到那正是反例）。

**同日对第五维（web 可观测）做了内容级实测，结论是通的**（⛔ 不以 HTTP 200 为据）：

| 面 | 读数 |
|---|---|
| `/dashboard` | 200，52015 字节，任务 id `e2e-verify-207` 出现 **4** 次、`needs-human` **10** 次 |
| `/goal` | 200，33717 字节，空状态正确渲染（该项目确无 goal，非面板故障） |
| `/tests` | 200，33187 字节 |
| `/git` | 200，336156 字节，含真实提交 |
| 过程记录 | 项目内 `.quay/*round*.jsonl` 共 **961** 行（promotion 482 + worker 479） |

（另记一处同类自误：首测 `/goals` 得 404，真实路由是 `/goal` 单数——同一晚第二次「入口/路径调错导致假结论」。）

**缺口 A 的残余（真实但轻微，与缺口 B 同族）**：交付包的 `files` 仍装入 `bin/quay.js` + `bin/quay.ts`，而这两个文件**在安装位置下结构上不可运行**——Node 拒绝为 `node_modules/` 下的文件做类型剥离（`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`），与 Node 版本无关。它们既非 `package.json` 声明的 bin，又长得像入口 ⇒ **交付了永远用不上、且会把人引向假结论的东西**（本人即是第一个受害者）。⇒ 与缺口 B 同一条原则：**交付面不得含无人消费/无法使用的东西**。

**缺口 B — 交付的配置键无人消费**：`quay-init` 写进目标项目 `.quay/config.yml` 的 `merge_target: integration`，全仓（`plugin/scripts/*.ts` + `packages/quay/src/*.ts`，排除测试）**零读者**；下游 fan-in 记录里 `mergeTarget: None`，实际合到 develop。对照组：同一段里的 `fork_baseline` **有**真实消费者（`fork-baseline.ts`）。⇒ 交付给下游一个**看起来在配置分支模型、实际不接任何机制**的键；且该键指向的 `integration` 分支 quay-init 从不创建（全仓零 branch 创建点）。

**为何单独立目标而非并入 GOAL-009**：GOAL-009 的退出条件逐字限定在「产物在非本机非本仓库安装 → 由该项目自己的 drivers 驱动 → 留下可核提交 → task 翻 done」，**通篇不含「人能否看见该项目状态」，也不含配置面完整性**。把它们塞进 GOAL-009 会扩它的声明范围（本轮已有 GOAL-010 从 6 条 AC 涨到 12 条的前车之鉴）。⇒ 另立。

## 范围与非目标

**范围**：

① **下游可观测面真的可用**——在满足交付所声明底线的宿主上，shipped CLI 的核心动词与 `quay serve` 能起来；⛔ 不接受「driver 能跑而 CLI 拒跑」这种同宿主内的不一致。

② **web 指向第三方项目时显示其真实载体与过程记录**——task/goal 双载体 + `.quay/*-round.jsonl` 等过程记录，⛔ 不是只渲染出一个空壳页面。

③ **交付的每个配置键都有消费者**——零消费者的键要么接线、要么删除；由**机械枚举**证明，⛔ 不是人工清点。

**非目标（明确排除）**：

- **不改 driver 行为**——driver 侧归 GOAL-009 与已 achieved 的 GOAL-012。
- **不承诺零配置**（沿用人 2026-09-10 裁定①的诚实边界：第三方项目需按自己的模型栈配置，这是配置不是缺陷）。
- **不做 GitHub provider 对第三方的映射**（沿用 GOAL-009 非目标）。
- **不重新裁定 Node 底线的取值**——本 GOAL 只要求底线**自洽且下游可验**（同一宿主上 driver 与 CLI 的可用性判断不得互相矛盾），⛔ 不讨论该定多少。

## 退出条件

散文版：

1. **交付包不含「长得像入口、却在安装位置下无法运行」的文件**——每个随包装入且形如入口的文件，要么是 `package.json` 声明的 bin 且能从安装位置跑起来，要么不随包装入。⛔ 不接受「它只是给开发用的」这种口头豁免：随包装入就会被人调用（本 GOAL 立条时的缺口 A 正是这样产生的假结论）。

2. `quay serve` 指向一个第三方项目时，能显示该项目的 **task 与 goal 双载体**以及 `.quay/*-round.jsonl` 过程记录——以在真实第三方项目上取得的读数为准。
3. 交付给下游的配置键**全部有代码消费者**，零消费者的键已接线或已删除，且该结论由**机械枚举**给出（⛔ 不是人工清点一次）。
4. **本仓库自身行为逐字不变**——本 GOAL 的改动不得改变本仓库既有的 CLI/web/配置行为。

机器判据在本 GOAL 名下的 AC 记录里，**不在本节**。

## 风险

1. **Node 底线的取值是产品决策，不是本 GOAL 的裁量**——本 GOAL 只管「自洽 + 下游可验」。若为求自洽而擅自下调底线，就越过了非目标；正确形态是让**不一致本身被报出来**，由人裁定取值。
2. **「web 能显示」容易退化成「页面能打开」**——退出条件 2 必须落到**具体载体内容**（task/goal 记录、round jsonl），⛔ 不接受 HTTP 200 当证据（硬规则 4：结构上不可能取假的量不是测量）。
3. **配置键枚举可能误伤**——有的键是给人读的文档性配置、或为未来接线预留。⇒ 枚举结果需可区分三态（有消费者 / 无消费者待接线 / 有理由的文档键），豁免要带理由可复核（同 GOAL-012 风险 2）。
4. **本 GOAL 自身曾建立在一个错误前提上（已更正，留作教训）**：缺口 A 原判「下游 CLI/web 不可用」，根因是调错入口而非产品缺陷；同日同类自误发生两次（CLI 入口、`/goal` 路径）。⇒ **对「下游不可用」这类结论，取证前必须先核对所调的是不是交付面声明的入口**（`package.json` 的 `bin`、路由表），⛔ 不以「我调了一个看起来是入口的文件」为据。本条写在这里，是因为它正是本 GOAL 要治的那类问题在**观测侧**的镜像。

5. **判据的类别纪律**：本 GOAL 判据只引用不会自行回退的量——代码状态、append-only 载体里的历史事实、机械枚举计数；⛔ 不含进程存活/远程主机当前可达性（那些归监控）。

## 与其他 goal 的关系

`GOAL-009`（交付面端到端自证）证明的是**驱动链路能跑通**；本 GOAL 证明的是**跑通之后人能看见、且交付的配置面不含死键**。二者不共享 AC：GOAL-009 的退出条件通篇不含可观测面与配置完整性（已逐字核对）。

`GOAL-012`（kernel↔target 边界三域归属，achieved）修的是 driver 侧的锚点与身份；本 GOAL 的缺口 B（死配置键）是**同一族的另一面**——不是「锚错了」而是「交付了却没人读」。

`GOAL-013`（判据保真性）与本 GOAL 正交：那条管判据能否取假，本条管交付物下游可用性。
