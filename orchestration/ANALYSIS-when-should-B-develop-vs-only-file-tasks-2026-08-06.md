# B 该不该自行开发？—— 冲突成本模型与边界（2026-08-06，管理者，参数全部实测）

人的提问：**已知 A/B 各自开发速率、冲突概率、单位冲突 merge 耗时，如何表达它们的关系？是否存在一个边界，
在边界内/外 B 不应自行开发，只应给 A 提任务？**

结论先说：**存在边界，但边界不在 B 的速率上——B 的速率会被约掉。边界落在
「A 每次同步之间碰了多少文件」和「一次错误合并要多久才被发现」这两个量上。**

---

## 1. 符号与实测参数

| 符号 | 含义 | 实测值 | 来源 |
|---|---|---|---|
| $F_A$ | 一个同步周期内 A 改动的文件数 | **238** | 今日 A/B 分叉窗口（共同祖先 d85ae594） |
| $F_B$ | 同周期 B 改动的文件数 | **117** | 同上 |
| $N$ | 「热文件宇宙」——近期真正在被改的文件总数 | **381** | `git log --since="24 hours ago" --name-only origin/develop \| sort -u \| wc -l`（全仓 tracked 3619，热集只占 10.5%） |
| $C$ | 实际冲突文件数 | **56** | 双方改动文件交集 |
| $c$ | 单个冲突文件的机械解决耗时 | **0.006 h**（≈21 秒） | B 第二次 cutover merge：45 冲突，12:48:13→13:02:03 = 13m50s，加两条即时修正提交（13:03/13:04） |
| $p$ | 一个冲突被**解错**的概率 | **0.14** | 第一次 cutover merge：35 冲突 → 已确认 5 个回归（arity / title / session-liveness-test / loop-driver / cap-from-gate） |
| $d$ | 一个错误合并从落地到**被发现并修好**的耗时 | **自由变量（见 §4）** | 今日实测区间极宽：ad-arm1 冷启动闸几十分钟内抓到 4+3 个；无该闸时到人来看为止 ≈6h |

---

## 2. 冲突量的表达式

若双方在热集内近似独立取文件，则

$$C \;=\; \frac{F_A \cdot F_B}{N}$$

**拟合检验（这是本模型唯一的经验支撑，必须写出来）**：$238 \times 117 / 381 = \mathbf{73}$，实测 **56**。
模型**高估 30%**——即偏保守，可用作一阶估计。（偏低说明 A/B 今日的工作面比随机取样**更分离**一些，
不是更集中。）

把 $F = (\text{文件触及速率}) \times T$ 代入：

$$C \;\propto\; \frac{r_A \, r_B \, T^2}{N}$$

**这是全部问题的核心：产出随同步间隔 $T$ 线性增长，冲突成本随 $T$ 平方增长。**
两次大分叉（上午 105 提交、下午 432/102）都不是判据发现的，是人亲眼看到才问出来的——
$T$ 一旦失控，$T^2$ 就把当天的产出吃掉。

---

## 3. B 自行开发的净价值，及 $r_B$ 的消去

B 独立开发的净价值率 = 毛产出 − 机械解冲突 − 解错代价：

$$V_B \;=\; w F_B \;-\; c\,\frac{F_A F_B}{N} \;-\; p\,d\,\frac{F_A F_B}{N}
\;=\; F_B\left[\,w - \frac{F_A\,(c + p d)}{N}\,\right]$$

$F_B$（等价地 $r_B$）**整体提出到括号外**，因此令 $V_B > 0$ 时它被约掉：

$$\boxed{\;\text{B 应自行开发} \iff F_A \;<\; F_A^{*} \;=\; \frac{w\,N}{c + p\,d}\;}$$

**结构性结论（反直觉但重要）：**

1. **边界与 B 的开发速率无关。** 因为 B 的产出和 B 带来的合并负担**同比例**缩放。
   所以「B 慢，所以不该让它自己开发」是**错误推理**；「B 快，所以更该拦住它」同样错误。
2. **边界只由 A 的每次同步文件量 $F_A$、热集大小 $N$、以及 $(c + pd)$ 决定。**
3. $c = 0.006$ 而 $p d$ 在任何合理的 $d$ 下都 $\ge 0.07$ ——
   **机械解冲突的耗时可以忽略；成本几乎全部在「解错了、且没被及时发现」这一项。**
   今晚的直觉「45 个冲突好可怕」是错的：45 个冲突只花了 14 分钟；真正吃掉一晚上的是那 5 个回归。

---

## 4. 边界的数值位置——决定性变量是 $d$（发现延迟）

$F_A^{*} = 76.2 / (0.006 + 0.143\,d)$：

| 错误合并的发现+修复延迟 $d$ | 边界 $F_A^{*}$（文件/同步周期） | 今日 $F_A = 238$ 落在哪边 |
|---|---|---|
| 0.5 h（有快速冷启动闸，如 ad-arm1） | **983** | 远在界内 ⇒ **B 自行开发净正**，且余量很大 |
| 2.2 h | **238** | **正好在边界上** |
| 4 h | **132** | 界外 ⇒ **B 自行开发净负** |
| 8 h（无人看，直到人来问） | **66** | 远在界外 ⇒ **强净负** |

$$\boxed{\;d^{*} \approx 2.2\ \text{小时}\;}$$

**这就是答案的可执行形态：在今天的运行点上，一次错误合并必须在约 2.2 小时内被发现并修好，
B 的独立开发才是净正的。超过这个延迟，B 越努力，全局越亏。**

今晚正好骑在这条线上——而把我们拉到「净正」一侧的，**不是任何设计好的机制，是 ad-arm1 这台
第三方机器碰巧在跑冷启动闸**（它抓到了 A 自己套件从 07:07 起没抓到的 4+3 个缺陷）。
**这是运气，不是机制。**

---

## 5. 第二条边界：范围，不是速率

§3 的模型假设双方在热集内**独立取样**。这个假设在一类文件上会失效：**双方都在改同一个机制**
（今晚的 session-liveness.sh / quay-init.sh / 两个 tick 文档 / slot-refill / ready-pool）。
在这类文件上 $C/F_B \to 1$，$F_A^{*}$ 不管取什么值都被突破。

把文件宇宙拆成两段：$N = N_{\text{shared}} + N_{\text{local}}$

- **$N_{\text{local}}$（项目自有、下游不共享）**：§4 的边界适用 ⇒ **B 自行开发**。
- **$N_{\text{shared}}$（plugin/ 下的机制、共享 tick 文档）**：边界恒被突破 ⇒ **B 只提任务，不自行改**。

**这正是人已经裁定的 producer/acceptor 轴**（A 产，B/archguard 验），
本模型给它一个定量理由，而不只是分工习惯。

---

## 6. 由模型直接推出的三条动作（按杠杆大小排序）

1. **压 $d$（发现延迟）——杠杆最大。** $d$ 从 8h 降到 0.5h，边界从 66 抬到 983，**扩大 15 倍**。
   今晚靠 ad-arm1 的运气拿到了这个效果 ⇒ **把它做成机制**：合并后立即在一台**不参与该合并**的
   机器上跑冷启动/冒烟闸。这比任何「更小心地解冲突」都值钱一个量级。
2. **压 $T$（同步间隔）——因为成本是 $T^2$。** 即 `gap-cross-machine-sync-has-no-mechanism`（f38514c4）
   那条任务。它同时压 $F_A$ 和 $F_B$，对 $C$ 是平方级收益。
3. **压 $p$（解错概率）——杠杆最小但最直觉。** 「更仔细地解冲突」只是线性地降 $p$，
   而 $c$ 本来就可忽略。**不要把力气主要花在这里。**

---

## 7. 参数可靠性（不掩盖弱项）

- $N$、$F_A$、$F_B$、$C$、$c$：**实测**，可复算，命令已写在表里。
- $p = 0.14$：来自**单次**合并（35 冲突 / 5 回归），样本 1，可能偏差大。
- $w = 0.2$：**估计值**，由 ready-pool 的 cost 字段与「一条任务约值 1.5h」推得——**最弱的一项**。
  $F_A^{*}$ 与 $w$ 成正比，$w$ 差 2 倍则边界差 2 倍。
- $d$：**故意留作自由变量**，因为它正是控制量；不该被估成一个数然后当事实用。

⇒ 表 §4 的**绝对数字**（983 / 238 / 132 / 66）应当读作**量级**，
而 §3 的**结构性结论**（$r_B$ 被约掉、成本集中在 $pd$ 而非 $c$、$T$ 的平方律）
只依赖实测量，**比数值更可靠**。

## 后验：$d$ 的第一个真实测量（2026-08-06 20:46Z 补记）

本文写作时 $d$ 是**假设值**。当晚它被真实事件量到了，**结论与模型一致，且余量很大**。

| 项 | 实测 |
|---|---|
| 引入损坏的合并 | `8e2e49b9`，**08-06 13:02:03**，自述「B-machine's master onto origin/develop，432 A 侧 + 99 B 侧提交，**45 conflicts resolved** … **all syntax verified**」 |
| 实际损坏 | `plugin/scripts/trend-check.ts` **被复制 2 份**（copy1+copy2 塞在文件中段）；**8 个任务 frontmatter 不可解析**（dup title/status） |
| 被发现并修复 | **20:43:05**（`fix: trend-check.ts — repair 8e2e49b9 merge corruption`） |
| **$d$（发现延迟）** | **7 小时 41 分** |
| 其间提交数 | **154** |
| 发现途径 | **全量套件偶然撞见**（不是任何针对性机制） |

$$d = 7.68\ \text{h} \;\approx\; 3.5 \times d^{*}(2.2\ \text{h})$$

**⇒ 在实际运行点上，$d$ 超出破局点 3.5 倍。** 按本文的判据，这意味着当时的 B 侧自行开发
**不划算**——人 2026-08-06 取消「跨机同项目协作开发」的裁定，**事后被测量支持**，
而不只是偏好。

**三条附带结论**：

1. **$d$ 之所以这么大，正是因为没有机制**：发现靠的是七个多小时后一次为别的目的跑的全量套件。
   这正是 `gap-no-post-merge-cross-machine-verification-detection-latency-is-luck` 的标题所断言的
   ——**"detection latency is luck"，现在有了 7.68 小时的实例**。
2. **合并提交自称「all syntax verified」而实际带着两类损坏**——又一条"带已验证字样但未验证"的断言，
   与 `manager-phase-goal.md` AC11 同族，**这次出现在合并提交消息里**，是该族的一个新载体。
3. **模型里 $w=0.2$ 仍是最弱项**（见 §7），本次测量**只加固了 $d$，没有加固 $w$**——
   不得因这一条实测就宣称整个模型已被验证。
