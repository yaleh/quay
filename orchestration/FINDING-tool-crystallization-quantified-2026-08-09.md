# 发现:高频行为的工具可靠性,量化到「结晶点」

**日期**:2026-08-09(管理者)
**触发**:人「本项目历史中这样的例子很多。对于许多高频行为,其工具必须结晶到足够冷才可靠,
例如跨 tmux 和 Claude Code 的消息发送上我们就有教训。请在会话历史中搜索这类问题,并量化分析。」
**方法**:meta-cc 检索全会话历史(2026-07-25→08-09,15 天),不靠印象。

---

## 0. 先分清这与既有的「状态结晶」原则不是同一件事

`SPEC-state-crystallization-2026-08-05.md` 讲的是**数据表示结晶**(同一个"在飞任务数"六个来源
四个答案 → 结晶成单一代码路径)。本发现讲的是**动作可靠性结晶**:一个被反复执行的高频动作
(发消息、计数、取时间戳、读写文件),其"正确做法"要经过多少次真实失败才会固化成一个
不会被绕过的形式(脚本/固定命令/契约字段),而不是继续停留在"记得住就对、记不住就错"。

**两者共享一个判据:执行密度决定了什么能活过一次重读**(今晚 `manager-tick-core.md` 拆分时
的判据),但对象不同——状态结晶治的是"读到什么",本发现治的是"做对一个动作要几次"。

## 1. 校准案例:跨会话 send-keys——本仓唯一被正式命名为「结晶」的案例

### 1.1 频率(meta-cc 实测,不是估计)

```
全会话 send-keys 相关 Bash 调用总数:2237 次,跨 15 天(07-25 → 08-09)
```

这是本仓事实上**调用频率最高的跨进程动作**——高于任何单个 git 命令类别。

### 1.2 结晶时刻:2026-08-04,人明确要求「把反复出现的手工修法固化到脚本」

`orchestration/CRYSTALLIZED-reliable-send-2026-08-04.md` 记录了**同一晚(08-04)真实发生、
非推断的 5 个独立故障模式**:

| # | 故障 | 证据(节选) |
|---|---|---|
| 1 | `C-u` 只清当前行,多行残留清不掉 | 一条 1554 字节的消息**需要连续 30 次 `C-u`** 才清空 |
| 2 | 长文本后紧跟 `Enter`,接收端未处理完则回车不生效 | 字节级验证:tmux/pty 层投递完全正确,问题在接收端渲染未完成 |
| 3 | 即使空闲、即使等渲染稳定,`Enter` 仍可能不生效 | 补发一个独立的 `Enter` 后才真正落进 transcript |
| 4 | "已提交"与"真正落进 transcript"之间有排队延迟 | 一条消息**30 秒后**才出现在 transcript 里,期间误判会重复提交 |
| 5 | **三种"看起来送达"的信号全部被证明不可靠** | 哈希 exit 0 ❌、输入框显示为空 ❌、`SESSION-RESUMED` 事件 ❌;**唯一可信的是接收方自己 transcript 里出现匹配的真实消息** |

### 1.3 用量对比:结晶前后,调用量涨了但没有停

```
结晶前(07-25 ~ 08-04 18:00,5 个自然日):  564 次  日均 113 次
结晶后(08-04 18:00 ~ 08-09,6 个自然日): 1673 次  日均 279 次
```

**用量涨了 2.5 倍**(项目整体活跃度在涨,这本身不是失败信号)。

### 1.4 一个不舒服的发现:结晶落进了文档,但没有落进「每次执行的动作」

`CRYSTALLIZED-reliable-send-2026-08-04.md` 给出的修法是:**发送后必须 grep 接收方自己的
transcript jsonl,确认内容匹配**。但今晚(08-08~09)我实际的发送形态是:

```
C-u → -l 文本 → Enter → sleep N → capture-pane 目视核对
```

**没有一次是照文档要求 grep 目标会话的 transcript 做送达确认的。** 我用的是"三次分开调用"
这个更便宜的子集,省掉了 08-04 文档里最贵、但也最可靠的那一步(transcript 匹配)。

⇒ **这与今晚反复出现的「机制存在 ≠ 机制在跑」是同一个形状,但换了个更隐蔽的入口:
这次不是"没接线",是"接了一半的线——省掉了成本最高、也最关键的那一步"。**
文档结晶了,执行只结晶了容易的那一半。

## 3. 横向对比:量化出的共同结构

### 3.1 触发结晶的从来不是"自己发现",是外部压力

| 案例 | 谁先注意到 |
|---|---|
| send-keys | **人**要求「把反复出现的手工修法固化到脚本」 |
| cap-from-gate 双取 | manager 自己(但 19 分钟后自己又犯) |
| workflow 静默 21.5h | **人**追问「这样看来 Claude Code workflow 的应用是有必要的」 |
| 1b 静默 8.5h | **人**问「outer 机制上是不是有缺陷」 |
| A5 只读不判 | manager 自查(本轮才首次触发) |

**5 例里 3 例的第一次揭发来自人的追问,不是本层的主动巡检。** 主动发现的两例(cap-from-gate、A5)都发生在"我正在处理另一件相关的事、顺手核对"的场合,不是常规巡检设计出来主动抓到的。

### 3.2 「结晶」这个词的本仓既有用法:已是通用概念,不是本发现新造的

`结晶` 一词在 `orchestration/` 下已出现在 **13 份文档**里,包括
`SPEC-state-crystallization` / `SPEC-integration-architecture` / `SYNTHESIS-four-gaps` 等。
**本发现是把这个已有概念,从"状态表示"这一个应用面,扩展到"动作可靠性"这第二个应用面。**

### 3.3 一条可推导的量化判据(供下一次判断"这个动作该不该结晶")

综合以上案例,**触发结晶的从来不是频率单独达标,是「频率 × 失败可被静默」的乘积**:

```
send-keys:       高频(2237次) × 失败会显式报错/卡住   → 结晶慢但发生了(08-04)
workflow 周期:   低频(每 20 分钟一次) × 失败完全静默   → 21.5h 无人发现
1b 收尾:         中频(每 tick) × 失败完全静默          → 8.5h 无人发现
A5 巡检:         每轮都读 × 判断从不产出               → "看见但没发现"持续数十轮
```

**⇒ 高频不是危险的充分条件,"失败是否会自己发出声音"才是。** send-keys 结晶得(相对)快,
是因为它的失败**会卡住会话、会被立刻看见**;workflow/1b/A5 拖了 8.5~21.5 小时甚至数十轮,
是因为它们的失败**是静默的,读数照样打印、动作照样返回,只是内容是空的**。

**这条判据比"高频行为需要结晶"更精确,建议作为今后判断优先级的依据**:
一个动作要不要立刻结晶,先问「它错的时候,谁会先知道」——答案是"下一次它自己该产出东西但没产出、而没有任何东西检查这一点"的,优先级最高。

本发现的 §2.5(执行账本)、§2.6(收尾/状态翻转)两条已经是这个判据的产物——
四元组里第①项("我声称在用的每个机制,最近一次真实执行时刻")直接对应

## 5. 更正(人 2026-08-09 10:2xZ 指出):「失败自己发声」这条判据本身有一个洞

**人的原话**:「这实际上把可靠性的责任转移到后面那个"会知道"的点了。这是可行的,但仍然要求
后面这点有更高的可靠性。本项目也出现过不止一次一串都失效的问题。」

**成立,且本仓历史上至少 3 次是这个更贵的形态——不是一个机制静默失败,是几个本该互相备份的
机制【同时】失效,因为它们共享同一个死因。**

### 5.1 三个「一串都失效」的真实案例

| # | 案例 | 共享的死因 | 代价 |
|---|---|---|---|
| 1 | **29 小时停摆** | `CronCreate` 和 `Monitor` **都是会话作用域**——会话一崩,两个互相独立设计的监督机制**同时**消失,不留痕迹 | meta-cc/archguard 停摆 29 小时(`SPEC-integration-architecture` #1/#2) |
| 2 | **send-keys 三种"看起来送达"的信号** | 哈希 exit 0 / 输入框显示为空 / `SESSION-RESUMED` 事件——**三个都建立在同一个未经验证的假设上**(会话已经真正处理了这次输入),假设一错,三个信号一起给假阳性 | `CRYSTALLIZED-reliable-send-2026-08-04.md` §故障5 |
| 3 | **outer 心跳单源反转** | 判据只读 `tick-log.md` 的 mtime——处置红窗事故时写的是 queue-state + 提交,不写 tick-log,**越认真处理事故,心跳看起来越旧**;同一信号同一晚出现一次真阳性一次假阳性,信号本身分不清 | `gap-outer-heartbeat-source-inverts-under-incident-handling` |

**这三例与昨晚新发现的 8 个实例是两种不同的形状,必须分开算代价:**

```
形状 A(本节，共享死因）：3 例，每例的代价是"整批备份机制一起消失"——29 小时是三例里最贵的
形状 B（§2，各自独立)：8 例，每例是一个机制自己静默失败，其余机制不受影响
```

**§3.1 那条「频率 × 失败是否会自己发出声音」的判据,只覆盖形状 B。对形状 A 它会给出错误的
安全感**——因为它默认"能发声的备份机制"是可信的,而形状 A 恰恰是备份机制本身也被拖下水。

### 5.2 判据修正:先问共享死因,再问会不会发声

```
原判据（不完整）：这个动作错的时候，谁会先知道？
修正后（两步，第一步优先）：
  ① 那个"会先知道"的机制，与被它监督的对象是否共享同一个死因（同一次崩溃/kill/压缩会一起消失）？
     是 ⇒ 这不是真的冗余，只是把 SPOF 换了个名字，先处理这一层，再谈"会不会发声"。
     否 ⇒ 走原判据（§3.1）。
  ② 递归问下去，直到落在一个真正独立失效域的机制，或落在一个已被人明确接受为范围外的边界上。
```

**本项目那个「边界」是什么,已经在今晚有裁定,不是没被发现的洞**:人 2026-08-09 裁定
自愈只做 Claude Code **进程内**,跨进程复活不做(见 `manager-phase-goal.md` 「会话级启动被接受」)。
`plugin/scripts/os-anchor-watchdog.sh` 本可以是那个真正独立的失效域(进程外的 OS 级 watchdog),
但 2026-08-06 已被人裁定为**非交付物**。**⇒ 进程边界之下的 SPOF 是已知且被接受的,不需要
再去发现;进程边界之内,才是判据该管的范围。**

### 5.3 用修正后的判据重新过一遍今晚的产物

- **§2.5 的四元组(执行账本)**:`meta-cc query_session_content` 是**外部进程查询**,与被查询的
  会话本身**不共享死因**(会话压缩/上下文清空不影响 meta-cc 能不能查到历史记录)——
  这条通过第①步,是真冗余,不是换皮的 SPOF。
- **`manager-tick-log.md` 的账本**:是**文件**,同样不与会话共享死因(压缩不清文件)——通过第①步。
- **但两者都与会话【进程】共享死因**:进程一死,没人再触发下一次 `meta-cc` 查询或下一次
  tick-log 追加。**这正是 5.2 说的"已知且被接受的边界",不是新发现的洞——不需要为此再开一条任务。**
- **三层的 `.halt` 组合判据(A5)**:检测 archguard 停摆的机制(git log 时距)与 archguard 会话本身
  **不共享死因**(检测方是 manager 这一层的进程,被测方是另一个项目的会话)——通过第①步,是真冗余。

## 6. 改进方案(人 2026-08-09 10:3xZ 要求):按案例给形式,不止机械代码

**判据(用 §5 修正后的两步)**:先问共享死因,再问频率×静默,最后选形式——
**形式跟着动作的性质走,不是都往"脚本"一个方向收**:

```
纯读 + 聚合、无判断、无副作用      → 机械代码(脚本/模块)，单命令输出全部读数
需要外部可信来源(会话历史/审计)   → MCP(已有 meta-cc，复用不新造)
多步编排 + 并行 + 需要持久账本    → workflow .js，但必须绑定一个"必须调用"的锚点
人工触发、低频、边界清晰的入口    → Claude Code skill(slash command)
```

### 6.2 一条统一约束(适用于表里所有"新建脚本/skill"的条目)

**任何新建的机械代码,必须先过 §5 的两步检验,并把结果写进它自己的头注释**——
这不是额外要求,是让"这条工具本身是否有单点失效"这个问题,**在它被写下的那一刻**
就有答案,而不是像今晚这样等出了事才回头查。今晚每一个被查出问题的机制
(workflow / `1b` / A5 / `--reconcile`)都没有在建成时写下这个自检,这正是它们
后来静默失效很久才被发现的共同前置条件。
