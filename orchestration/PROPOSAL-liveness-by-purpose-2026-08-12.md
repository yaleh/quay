**来源**：人指派分析「这一存活信号的实际用途，是否可用 SendMessage 代替」（manager，2026-08-12 14:0xZ）。

---

## 一、诊断：1512 行复杂度来自**一个选择**

**它试图从「观测」推断「事件」。**

「下层完成了一件事」是**正事件，只有下层自己知道**。当前设计让上层去看 pane 形状「忙→闲」来**推断**它。
这一个选择往下必然长出：形状分类 → 状态机 → 边沿检测 → 两轮确认防抖 → 真 tmux 测试 → 私有 socket → 孤儿进程泄漏。

**108 个分支、23 个测试文件、一死一盲的观察者注册表，都是这一个选择的下游产物。**

### 两条实测支撑（非论证）

1. **`SESSION-*` 事件在两个执行核里命中 0**（`orchestrator-tick-core.md` / `manager-tick-core.md`）。
   消费方全是 `SPEC-`/`FINDING-`/`CRYSTALLIZED-` 类文档，**没有一处「收到 X 就做 Y」的执行路径**。
   ⇒ 与 `__CEILING__`、文件收件箱同族：**仪器在报，无人声明判据。**
2. **自然实验**：观察者 13:13Z 因 inner 重启换 session id 而失明，13:47Z 才被发现。
   **34 分钟内三层照常产出**（inner 提交 / outer 立任务并 dispatch / manager 加判准 ⑦），**无一处因它失明而坏掉**。
   ⇒ **真正承载协作的是 SendMessage，观测那条线早已冗余。**
   ⇒ 并且：**故障的是探针，不是被监视对象。**

## 二、上层需要被回答的是三个**性质不同**的问题

| | 问题 | 性质 | 谁能回答 | 能否用 SendMessage |
|---|---|---|---|---|
| **A** | 下层**做完了**，我该看结果/派活 | 正事件，边沿 | **下层自己** | **能，且更准** |
| **B** | 下层**还活着吗** | **缺席**——「事件没发生」 | **只有外部观察者** | **原理上不能** |
| **C** | 下层**现在能否收指令** | 状态 | 两者皆可 | 大部分能 |

**结构性不对称（B 不可替代的理由）**：
**能发「我完成了」的前提是它还活着，而 B 问的就是这个前提本身。**
卡死 / OOM / 被 kill / 静默降级的 agent，**恰恰失去了发消息的能力**。
**这是逻辑问题，不是实现问题——再好的消息机制也补不上。**

---

## 三、设计：三个机制，各管一件事，互不重叠

### ① 完成 / 状态 → **SendMessage（已有，无需建设）**
下层做完就发，带语义：任务 id、结果位置、下一步建议。
**比推断强在哪**：`忙→闲` 分不清「做完了」与「卡住了」；`"我完成了 X，结果在 Y"` 无此歧义。
身份由平台标注（`from-name`/`from-mode`），不需要自建认证。

### ② 存活 → **一个极简探针，每层一个**
```
判据：进程存在？ + transcript mtime < 阈值？
输出：只有一种事件 DOWN（附证据）
没有：状态机 / IDLE·RESUMED 边沿 / pane 解析 / tmux / 私有 socket
配置：目标用【tmux 窗口名】（稳定）；transcript【动态解析】（= outer 2026-08-12 正在修的方向）
测试：纯函数（pid 存在性 + mtime → DOWN|OK），零真 tmux
```
**设计原则：探针必须比它监视的对象更笨。**
否则探针本身成为更可能的故障源——**2026-08-12 实证：故障的是探针，不是 inner。**

### ③ 探针的探针 → **各层 tick 的一行读数**
每层每轮问一次「我下层的探针还活着吗」（`observer-registry-check.sh` 已是此物，outer 已接进其读数）。
**顶层由 cron + tick-log 兜底**——人可直接看 tick-log 是否在长。

## 四、取舍（损失写在前面）

**砍掉 IDLE/RESUMED 会失去**：「下层忘了发完成消息时，上层不会自动知道」。
**缓解**：探针的 `DOWN` 阈值本就会在长时间无产出时触发 ⇒ **只是慢一些，不会漏。**

**pane 观测保留多少**：**只保留控制面那一处。**
理由是实测出来的——**SendMessage 目标忙时直投即达、由接收端排队**（2026-08-12 双向实证），
⇒ **发消息前根本不需要知道对方忙不忙，can-receive 那一整类检查失去存在理由。**
**唯一还需要看屏幕的是 `/clear` 这类必须走 tmux 输入的控制命令**（正是人裁定保留旧机件的那个用途）。

## 六、与 2026-08-12 三个缺陷的关系

| 缺陷 | 在本设计下 |
|---|---|
| 观察者失明（绑旧 session id） | 配置面只剩窗口名 + 动态解析 ⇒ **消失** |
| tmux 孤儿泄漏 | 探针测试是纯函数，不起真 tmux ⇒ **源头消失** |
| 仪器在报无人读 | 只剩一种事件 `DOWN`，判据唯一 ⇒ **不存在「该怎么解读」的空间** |
