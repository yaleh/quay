# 提案：task status 语义收紧为「静态条件」+ 取消 pool 过滤层

**来源**：人 2026-08-12 三条裁定 —— ①`todo` = 当前有外部条件阻碍该任务执行；`ready` = 该任务执行的条件已全部满足
②新语义**限定为静态条件**（我提，人「同意」）③「任务体没写全」按**宽松解释算作阻碍 → todo**，
且 **`ready` 应在例行检查与 todo→ready 提升过程中修复此类错误** ④**可取消现有 pool，让 inner 直接从 ready 取任务
（保持必须的防冲突机制）**。

**状态**：人已裁定，本文件是落地方案与风险清单。**执行归 outer。**

---

## 一、为什么取消 pool 的推导成立 —— 它是 ready 的影子副本

**实测（2026-08-12 15:0xZ）**：
```
status=ready  15 条
  → excluded  8 条（not-yet-flipped 6、fixture 2）  ← 新语义下这些根本不该是 ready
  → pool      7 条
```
**新语义下这 8 条会在提升闸被拦住 ⇒ `pool` 与 `ready` 恒等 ⇒ 过滤层无事可做。**

**更强的理由：当天的三个缺陷全部长在这一层**
- `not-yet-flipped` 静默吞掉 5 条任务（含耗时优化最大的一块，286 execve）
- A9 的 `≥floor/2` 阈值挡住了对它的感知
- stale-ready：状态与现实脱节

**共同形状是「影子与本体漂移」。取消影子 ⇒ 这一整类缺陷消失。**
与 `CLAUDE.md` 的 single-source-of-truth 原则一致：**同一内容活在两个地方就是漂移，修源头不修产物。**

## 二、静态/动态的分界，正好落在两个现有工具之间

| 工具 | 判什么 | 新语义下的定位 |
|---|---|---|
| `ready-pool-check` | 静态（产物、fixture、not-yet-flipped…） | **过滤职能取消；提升职能保留并扩容** |
| `slot-refill` | 动态（touches 冲突、槽位、套件红绿） | **完整保留** —— 这就是人说的「必须的防冲突机制」 |

**⇒ 不是删掉 `ready-pool-check`，是把它从「过滤器」改成「提升闸」。**

**为什么动态条件不能进状态字段**：`touches` 冲突取决于此刻谁在飞、槽位取决于此刻并发数。
**若写进状态，则每当有任务开始/结束，其它任务的状态都要跟着变** ⇒ 状态沦为需要持续同步的缓存，
**而当天已证明这类缓存必然漂移**。

## 三、承重墙移到提升闸，它必须扩容

```
今天：todo --[artifactsComplete]--> ready --[pool 过滤]--> pool --[slot-refill]--> 派发
新的：todo --[静态条件全查 + 能修则修]--> ready --[slot-refill 动态]--> 派发
```

**提升闸要新增的静态判据**（原 pool 层的全部）：非 fixture／非 parked／非 ac-record／非 compound／
self-touch 齐全／依赖已 done／`Touches` 指向的文件存在／**产物齐全（不齐 ⇒ 留 todo）**。

**人特别指定的一点：「能修则修」而非「简单拒绝」** —— 产物不全就补全、`Touches` 写错就改对。
提升闸的产出应是「修好后晋级」或「明确的阻碍原因」，不是静默留在 todo。

## 四、已经具备的部分（好消息）

**降级路径已在状态机里**：
```
lifecycle.ts:  ready: { forward: "done", back: "todo" }
```
`ready → todo` 已是合法转换 ⇒ 「条件后来被破坏的 ready 退回 todo」**不需要新机制，只需要有人执行它**
——那正是人说的「例行检查」。

**原子认领机件已存在**：`claim-task.sh —— Is a task/branch claimed by a specific machine (claim protocol, atomic CAS push)?`
**但它是为【跨机器】认领设计的（CAS push 到远端），同机多 subagent 是否适用【未验证】** —— 落地前必须确认（见 §5③）。

## 五、四个必须一起定的问题

### ① 例行检查是承重墙，不是补充
静态条件会**变质**：写任务时依赖未完成（todo），后来完成了 —— **谁把它挪到 ready？**
取消 pool 后没有别的地方兜底。**需明确周期与触发**（每 tick？依赖 done 时事件驱动？）。

### ② `deficit` 语义要重定义，否则会重演已发生过的误判
今天是「pool 不够就补晋」。新语义下 `ready` 少有两种原因：**能晋而未晋**（要补）／**真的都被阻塞**（补不出来）。
**两者必须可区分** —— manager 2026-08-12 上午就是没区分，误判成「晋级引擎吞吐瓶颈」，被 outer 用证据纠正。

### ③ inner 直接取 ready ⇒ 需要原子认领
今天 outer 派发是串行的，天然互斥。**inner 自取后，两个 subagent 可能同时看到同一条 ready。**
**并且**：当前 `slot-refill` 的 `measurement_source = telemetry-slot-status`，**「在飞」是从遥测读的，不是从「谁认领了」读的**
⇒ **取消 pool、inner 自取之后，「在飞」的真值来源应改为认领记录，否则又是一个副本。**

### ④ ⚠️ 完成判定必须覆盖 DoD，不能只看 AC —— **这是当天的活证据**
`reason-gate-fix`（`7acbc1b1`）给 `not-yet-flipped` 加了 **AC-合取**，被吞 5 条中 **2 条回池、3 条仍被吞**。
**逐条查后发现原因**：
```
gap-cli-import-refactor-run-shell-architecture 的 4 个未勾项，全部在 ## Definition of Done，AC 段是全勾的
```
⇒ **合取只看 AC，而不完整性藏在 DoD 里** ⇒ 修复按自己的规则「正确地」没救它。
**⇒ 判据应是「任务体中【任何】未勾选框存在 ⇒ 不算 landed」，而非「AC 段无未勾项」。**
**这条同时也是新语义下提升闸的判据**：产物/完成标记不齐 ⇒ 留 todo。

## 六、落地顺序（先立不破，避免中间态无网）

1. **先扩容提升闸**（静态判据全部接过来 + 能修则修）
2. **再建例行检查**（todo↔ready 双向重评，含 §5① 的周期/触发）
3. **确认认领机制**适用于同机多 subagent（§5③），并把「在飞」真值改为认领记录
4. **最后才取消 pool 过滤** —— 此时它已无事可做，**取消是收尾，不是手术**

**理由**：今天的承重墙是 pool 层（最后一道网）。**先取消再补提升闸 ⇒ 中间态无网，不合格任务会直接进 ready 并被派。**
