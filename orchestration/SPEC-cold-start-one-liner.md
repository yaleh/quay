# 规格：把冷启动压成「一两行命令 + 两个 skill + 内层零操作」

**提出**：人 2026-08-03 ——「安装应当使用一两行命令行（还没发布到 GitHub，本地稍复杂点可接受）；
在 outer 初始化和冷启动应当各只需要一行非常简单的 `/` skill 或 mcp 命令；inner 不需要操作最好。」
**定义者**：管理者。**实现者**：quay 外层 + 内层（走项目正常流程）。

---

从 archguard 冷启动的 git 历史还原：

|---|---|---|

## AC

- [ ] **AC1（可数判据）**：从零到「双层循环在目标项目里跑起来并派出第一个任务」，
      **人/agent 需要输入的命令 ≤ 4 条**（1–2 行安装 + 1 行 init + 1 行冷启动）。
      判据：在一个全新项目上实跑并**记录每一条输入**，条数可数。

- [ ] **AC2**：**参数可推导者不得要求输入**。
      当前 `quay-init --loop` 要求 `--test-command`（失败关闭，这是对的），
      但**它可以被检测**：`package.json` 的 `test` 脚本、`go.mod` ⇒ `go test`、
      `Cargo.toml` ⇒ `cargo test`、有 `scripts/test.sh` ⇒ 用它。
      判据：检测出来后**显示给人确认**，而不是要求人先知道。
      **检测不出来时仍须失败关闭**——不许猜一个默认值。

- [ ] **AC3**：**残留清理并入安装**，不作为独立的一步要人记得。
      判据：安装命令自己检测热拷贝残留（内容与产物不同的同名文件）并处置；
      **处置方式必须可见**（报告清了哪些、备份在哪），不是静默覆盖。

- [ ] **AC4**：**监视器挂载并入冷启动 skill**。
      判据：冷启动后 `inner-state.sh` 与 `session-liveness.sh` 两个进程都在，
      **不需要人分别挂**。且两者不合并的理由随文档走（已有）。

- [ ] **AC5**：**inner 零操作**。
      判据：整个流程中**不需要向内层会话输入任何东西**——
      它要么由冷启动 skill 驱动，要么读安装好的文件自行开始。

- [ ] **AC6（负控制）**：**在一个没有 quay 开发树的环境里实跑一次**。
      判据：把 `/home/yale/work/quay` 改名后，那 ≤4 条命令仍能走通。
      **这条不过，前面五条都不算数**——因为整个目标是「别人能用」。

- [ ] **AC7**：**README 里那段命令序列与实跑的一致**。
      判据：逐字对照，不是"大意相同"。

## 明确不做

- **不追求「一键」**——人说的是一两行命令加两个 skill，不是一个按钮。
  把四条压成一条会把可诊断性也压掉：四条里哪条失败，现在是可分辨的。
- **不为此改 `.quay/config.yml` 的 schema**（产品配置面，要走产品评审）。
- **不猜测试命令**——检测不出就失败关闭，这条比少一个参数重要。

## 一条今天的教训要写进实现

这次冷启动**每一步的外部知识都在我脑子里**（产物在哪个分支、残留是哪三个文件、
要挂哪两个监视器、cron 多少）。**它跑通了，但不可复现**——
下一个项目还要我再口述一遍。

**"我口述一遍它就能跑"与"它自己能跑"，在结果上同形，在可交付性上是天壤之别。**
这正是本仓当天数了 7 次的那一族（存在≠生效）的又一个变体：**可用≠可交付**。

## AC8（追加，2026-08-03，人：「这是 skill 应该做的事」）

**人的原话**：「一行极简的固定的 `/` 开头的 skill 命令，启动确定的行为，
**最小化对 prompt 文本篇幅和质量的依赖**。」

### 触发它的实测失败

| 层 | 引导形式 | 结果 |
|---|---|---|
| 外层 | 管理者发的一段长散文 | **成功**——但依赖「我写得全 + 它读得懂」 |
| **内层** | **没有人发** | **静默地从没跑过 fast mode** |

archguard 装到了 440 行的内层 tick 文档，**它的 pane 里一次都没提到过那个文件**；
`.workflow-events/` 不存在；今天 0 个 subagent（quay 同期 48 个）。
⇒ **并行派发、对抗 REFUTE 轮、遥测——三层全缺，而从外部看不出来。**

### 为什么散文引导不够（今天三次换模型的证据）

pro → flash → qwen，**同一段引导我重写了三次**，还得特意加
「凡是靠推理补上的隐含前提都要写成明文」。
**散文引导的效果取决于读者的推理能力，而读者会换。**

按 `prediction-prose-drifts-checks-hold.md` 的判断：散文会漂。
**技能加载的是固定指令，不依赖当时写了多少、也不依赖读者能推理多少。**

### AC

- [ ] **AC8a**：**内层的引导是一个 `/` 技能，不是一段散文**。
      判据：在一个新装好的项目里，对内层只发一行技能命令，
      **`.workflow-events/` 随后出现真实记录**（不是「它说它读了」）。

- [ ] **AC8b**：**外层的引导同样是一个技能**。
      现在能成是因为管理者在场手写；**交付物不能依赖管理者在场**。

- [ ] **AC8c**：**技能内容不随模型变**。
      判据：同一个技能命令在三个不同模型上（当前实际在用的 opus / flash / qwen）
      都产生同一组可观测后果——监视器挂上、循环起来、遥测有记录。
      **有差异就是技能还在依赖读者的推理，要继续收紧。**

- [ ] **AC8d（负控制）**：**不执行技能时，缺失必须可见**。
      今天的失败是静默的——外部看不出内层没跑 fast mode。
      判据：造一个「装了但没引导」的项目，某个检查必须报出来，
      而不是等人去数 subagent transcript。

### 与 AC1 的关系

AC1 说「安装 1–2 行命令 + outer init 1 行 + 冷启动 1 行」。
**AC8 揭示那个清单漏了一项：内层的启动。**
⇒ **AC1 的命令数应当改为「≤4 条，其中必须包含内层启动」**，
不是把内层启动算作外层引导的副作用——今天证明了那个副作用不会发生。

## AC9:worktree 不许建在 tmpfs(2026-08-03,meta-cc 实测后追加)

**实测**:meta-cc 有 4 个 git worktree 注册在 `/tmp`(DIR-045/053/056/066),
而这台机器的 `/tmp` 是 **tmpfs——重启即消失**。
损失的**不是提交**(对象在磁盘 `.git` 里,已验证四个分支全部可解析),
而是**未提交的工作**:其中一个 worktree 里躺着一份 07-29 写的 `status: accepted` 的 ADR,
五天没进任何仓库,再一次重启就没了(已救出,见 [[a-mechanism-discarded-as-noise]])。

- **AC9a**:冷启动脚本在建 worktree 前**检查目标路径的文件系统类型**;
  是 `tmpfs` 则拒绝并说明原因,**不静默继续**。
- **AC9b**:负控制——在一个真磁盘路径上必须正常建成,
  否则这条检查就把正常路径也挡了。
- **AC9c**:已存在的 tmpfs worktree 要能被**发现**(`git worktree list | grep ^/tmp`),
  这是冷启动前置检查的一项。

**一般形态**:`/tmp` 在不同机器上是磁盘还是内存**不确定**,
而 worktree 的语义假定它在磁盘上。**把一个持久性假设建在一个不确定的路径上,是静默的。**

**已落地(2026-08-04,`gap-the-shipped-tick-doc-teaches-every-project-to-put-worktrees-in-tmpfs`)**:
`quay-init --loop` 现在解析 `loop.worktree_root`(缺省 `<repo>/../<basename>-worktrees`,
磁盘),并在落盘前校验其文件系统类型——`tmpfs` 则 fail-closed 退出非 0、说明「这是内存」并给出
该改成什么(AC9a);真磁盘路径正常建成、exit 0(AC9b,负控制);存量由
`git worktree list | awk '$1...'`+`stat` 一行报出(AC9c)。**理由从「重启即消失」升级为「OOM 成因」**:
2026-08-04 整机 OOM 的分解直接把在飞 worktree 所在的 `/tmp`(tmpfs,占 4.4GB)指向内存——
同一判据,严重性从「你会丢工作」变成「你会打死整台机器」。
