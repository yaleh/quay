# 规格:砍掉任务里的等待(实测 64%)

**依据**:用 meta-cc 查 quay 内层 session `9957a092`(02:43–04:27,共 **104.4 分钟**)的相邻命令间隔。

## 实测

| | |
|---|---|
| 间隔 >2 分钟的段落合计 | **4020 秒 = 67.0 分钟 = 64%** |
| 那些段落前后的命令 | `grep -cE '^(✔\|✖)' full-suite-N.log`、`pgrep -fc 'node --test'`、`sleep 120` —— **全是轮询套件** |
| 剩余 36%(37 分钟) | 约 90 条命令,每条 5–60 秒 —— **真工作** |
| **那段时间跑的全量套件** | **6 次**(03:04 / 03:20 / 03:38 / 03:54 / 04:09 / 04:41),6 × ~500s = **3000 秒** |

**⇒ 先前按 DoD 推算「套件占 32%」是低估**,因为没算重跑、rebase 后再跑、失败后再跑。

## 砍法一:迭代用范围化跑法,只有最后两次用全量

`scripts/test.sh --for-task <id>` **已存在**(`scripts/test.sh:518`),按 `## Touches` 选测试、跳资源闸。

```
现在:6 次全量 × 500s          = 3000s
改后:2 次全量 + 4 次范围化     = 1000s + ~200s = 1200s   省 1800s = 30 分钟
```

## 砍法二:套件放后台,靠通知唤醒,不要轮询

**tick 文档已经这么写了**(`plugin/loop/fast-mode-loop-tick.md:81`):

> 后台 agent 完成时会自动触发 `<task-notification>` 重新唤起会话——**那是主要的推进信号**

**而内层实际在轮询。** 又一次「存在≠生效」:机制写在文档里、harness 原生支持,实践却是 `sleep 120; pgrep`。
轮询不只浪费墙钟——**每次轮询是一个 LLM 回合**,占 token、占延迟,且期间不能干别的。

## AC

- **AC1**:tick 文档的等待形态**只有一种**——后台派发 + `<task-notification>`。
  文档与实践里不再出现 `sleep N; pgrep`、`for i in 1..N do grep 日志` 这类轮询。
- **AC2**:开发迭代用 `--for-task`;**全量只用于 DoD 要求的最后两次**。
- **AC3(可判收口)**:**每任务的全量套件次数从 6 降到 ≤3**。
  判据是数 `full-suite-*.log` 的个数,或遥测里的全量运行记录。
- **AC4(负控制,必须显式)**:**DoD 的「最后连跑 2 次全量全绿」不许放宽**。
  砍的是**中间的迭代跑**,不是闸。**把 AC2 读成「少跑全量就行」就是把方向 C 做成了方向 A**,人已明确排除方向 A。
  > **Cross-annotation (2026-08-07, `gap-suite-green-gate-duplicated-in-task-dod-and-batch-merge`)**:本 AC4 的「不许放宽」
  > **继续有效**。闸是**批量合边界的全量套件绿**（`fast-mode-loop-tick.md` 红窗规则:red 阻 `$MERGE_TARGET`→
  > `$FORK_BASELINE`），那条闸**原封不动**。移除的是**任务级 DoD 的重复**（「完整套件连跑 2 次全绿」），
  > **不是放宽**——AC4 的负控制继续指向批量合边界那道闸。
- **AC5(效果验证,用 meta-cc 不要用墙钟)**:改后再查一次会话间隔分布,
  **等待占比应从 64% 降到 ~35%**。**不要用套件墙钟验证**——σ=297.6s 会把它吃掉。

## 追加(2026-08-04):等待的另一半——前台派发

**实测**:今天 **9 次 `Agent` 派发,`run_in_background` 全部为 `false`**,零例外。
而 `plugin/loop/fast-mode-loop-tick.md:303` 写的是「派发形态:**后台 `Agent(run_in_background)`**」。

**并发本身是真的**:遥测区间重叠 **5 对**,**同时在飞峰值 3**
(`both-gates` ∥ `blocked-channel` 重叠 20 分钟;`install-rewrites` ∥ `drift-check` 重叠 18 分钟)。
**但那个并发来自「一条消息里发多个 `Agent` 调用」(harness 并发执行),不是后台派发。**

**差别很实际**:前台派发下内层**阻塞到整批返回**——
不能交错、拿不到先完成者的早期反馈、期间什么也做不了,
而 tick 文档设计的 `<task-notification>` 唤醒流**从未被触发**。

**这是本规格原先漏掉的一半**:我只看到轮询循环,
**而前台阻塞那部分连命令都不产生,在会话日志里是纯空白**——
按间隔统计时它被算进了等待,却找不到成因。

### AC1 扩充

**派发形态必须是 `run_in_background`。**
**判据**:meta-cc 查 `Agent` 调用的 `run_in_background` 字段**全为 `true`**——
可直接查,不需要新仪器。
