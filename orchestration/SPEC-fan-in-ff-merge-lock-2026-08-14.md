# SPEC：fan-in 改为「无锁段自测 + 锁内 ff-merge」——让 merge 可以安全地在任务 subagent 内完成

**作者**：manager（设计由人 2026-08-14 02:2xZ–02:4xZ 主导，manager 补实测基线与两处修正）
**状态**：已获人裁定，**排期即本阶段**（AC62–AC64）
**要解决的问题**：inner 的 A6 fan-in 目前**整段在主会话串行执行**（`fast-mode-tick-core.md:25` 明文规定「串行」），
rebase + scoped 门 + merge 全部占着主会话；而其中**只有最后一步真正需要串行**。

## 0. 人的裁定（逐字，本 SPEC 的来源）

> 「每个 subagent 应在 merge 前把 develop 最新变更 merge 回自己的 worktree 并执行 suite 测试；
> 最后合并回 develop 的操作必须为 ff merge；为 merge 过程单独加锁（和 suite test 不是同一个锁，
> 且覆盖范围不得交叉），ff merge 结束（无论成功或失败）即解锁，失败则退回修复。」

> **更正（人，同日）**：「**拿 merge 锁了以后不得再跑 suite，此时唯一可以做的事情就是 ff merge。**」
> —— 这条推翻了 manager 提的「(a) 锁内跑最后一轮」方案，**该方案已删除，不作为选项保留**。

## 1. 协议

```
无锁段（全部在自己的 worktree 内，不碰共享检出）
  1. git merge develop            ← 冲突【只可能在这里】出现，可以慢慢解，不占任何人
  2. 跑全量 suite                 ← 绿才继续
  3. 跑 doc 检查                  ← 补 ff 不触发任何钩子的缺口（见 §4）
持锁段
  4. git merge --ff-only          ← 唯一允许的动作
解锁（成功或失败都立即释放）
  失败 ⇒ 回第 1 步，并写一条重试记录（见 §5）
```

## 2. 为什么「锁内跑 suite」不合法（不只是更慢）

```
锁内跑 suite ⇒ 锁的持有时长 = 6.5–14.5 min（p90），max 75.1 min（实测，见 §6）
⇒ 锁语义变成「我占有 develop 一段任意长的时间」
⇒ 需要超时调参 / 陈旧锁回收 / 崩溃泄漏处理——全是本仓库反复付过代价的那类脆弱机制
```

**而 ff-only 已经保证了安全 ⇒ 锁内跑 suite 不增加任何安全性，只是把「重试」换成「等待」。**

**⇒ 锁只包 `git merge --ff-only`，持有时长毫秒级** ——
碰撞概率趋近于零，**陈旧锁回收变成一个几乎不会走到的分支**。
**一个短到不需要精心设计回收逻辑的锁，才是好锁。**

## 3. 安全性来自 ff-only，不来自锁

```
A 从 develop@X 建树 → merge develop@X 进来 → 跑绿
   期间 B 先 ff 上去，develop 变 Y
A 去 ff ⇒ 【失败】，因为 A 的 tip 不含 Y ⇒ 不是 fast-forward
⇒ A 绝不可能把一个「未与 Y 一起测过」的状态推上去
```

**这是结构性保证，不依赖锁的正确性**——即使锁写错了、超时了、被绕过了，**ff 仍然会拒绝**。
**锁只是减少无谓的失败，不是安全的来源。**（这一点重要：本仓库反复见到「靠正确实现」的保证如何失守。）

**ff 可行性的一个易错细节，已验**：第 1 步之后分支 tip 是一个以 `develop@Y` 为父的 merge commit
⇒ **`develop@Y` 是它的祖先 ⇒ ff 成立**。协议自洽。

## 4. 本设计最有价值的性质：冲突与竞争被彻底分开

```
冲突   只可能在第 1 步（无锁段）出现——内容合并在那里发生
竞争   只可能在第 4 步（持锁段）出现——ff 只是快进指针，【不可能有冲突】
```

**⇒ ff 失败的原因唯一（develop 前进了），处置也唯一（回第 1 步重跑）。**
**没有「ff 冲突」这种情况** ⇒ 不需要人判断、不需要 needs-human 路径
——**这比现有 A6 的 rebase 冲突处理简单一个量级。**

## 5. 钩子缺口（本设计唯一的真风险，必须显式补）

`plugin/scripts/precommit-guard.ts` 的实现注释逐字：

> **"Fast-forward merges create no merge commit, so pre-merge-commit does not fire for them"**

⇒ **改成 ff-only 之后，doc 检查在 fan-in 路径上一个钩子都不触发**
（`pre-commit` 只由 `git commit` 触发，`pre-merge-commit` 只由 `--no-ff` 触发）。

**⇒ 第 3 步是必需的，不是冗余**：subagent 必须在 ff 之前显式跑
`bash scripts/test.sh --static-checks-doc`，**且它属于无锁段**（内容检查，与竞争无关）。

**doc 检查会跑两次，【刻意不去重】（人 2026-08-14 确认）**：
```
第一次  subagent 自己 git commit 时，pre-commit 钩子触发 ⇒ 只覆盖【自己的改动】
第二次  第 3 步显式跑                                    ⇒ 覆盖【与 develop 合并之后的内容】
```
**两次检查的对象不同 ⇒ 去重会漏掉合并引入的文档冲突。**

## 6. precommit-guard 的两个职责，去向不同（manager 修正了「重建参照系」这个说法）

`precommit-guard.ts:2-3` 逐字，它做两件**不相干**的事：

| | 职责 | 去向 |
|---|---|---|
| ① | 文档类检查（AC51 断言面拆分，7 个 doc checker） | **保留**，且必须在 §1 第 3 步被显式调用 |
| ② | 拒绝「轮 running 且触及断言面」的写入 | **退役** |

**② 退役的理由不是「参照系失效」，是【它保护的危险已经不存在】**：
```
② 原本保护   suite 正在跑时别改它正在读的文件——因为当年 suite 读【共享检出】
AC42 之后    per-task suite 跑在各自 worktree，读的是 worktree 的文件副本
⇒ 改共享检出的 develop 完全不影响正在跑的 worktree suite
⇒ ② 保护的那个危险随 AC42 结构性消失（属「输入不存在」那一族）
```
**而 merge 锁保护的是【另一个、新出现的】危险**：两个 ff 同时改 develop ref。
**两者不是同一个东西** ⇒ **不是「② 换个参照系」，是「② 退役 + 新增一个不同的保护」。**

**② 的立条理由仍然值得留档**（`precommit-guard.ts:19-25` 逐字，三条支撑）：
「round 期间零提交」的约定守不住——①约定无产物（round 60 约定后 26s 即破）
②事后都难区分 ③**参与方名单不可维护**（inner 从不在约定里，round 63 窗口内 30–40s 一次提交 4 笔）。
**⇒ 那三条教训在新协议下仍成立**：所以 merge 锁必须是**共享的机制**（钩子/文件锁），
**不能是「各层记得调的约定」**——这正是 ② 当初选择 pre-commit 钩子而非 commit 包装的理由。

## 7. 活锁：降级为观察项，不预先造机制

ff-only 把风险从「错误」换成「重试」。**最坏情况是活锁**：
大任务（p90 14.5 min）在高并发下可能反复追不上 develop。

**但按实测，现在不需要为它造机制**（硬规则 12：先给发生率，给不出就降观察项）：
```
merge 频率   近 6 小时 4 次；最密集相邻间隔 11.6 / 12.6 min
suite 时长   6.5 min（三棵在飞 worktree 现读）；历史 164 轮 中位 7.4 / p90 14.5 / max 75.1
⇒ 碰撞窗口内被抢先的概率不高；p90 以上的大任务才是风险
```
**⇒ 产物先行**：**每次 ff 失败必须写一条重试记录**（任务 id + 第几次 + 当时 develop 头 + 时刻）。
**触发条件写死：若出现同一任务 ff 失败 ≥3 次，那时才谈防活锁**
——**届时会有真实的重试分布，而不是现在拍一个 N。**

这是 (a) 除持锁时长外的第二个致命问题，一并留档。）**
