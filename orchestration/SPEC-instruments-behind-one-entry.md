# 规格:仪器收进单一入口(先收缩,再暴露,最后才新增)

**人 2026-08-04**:「把更多仪器集成到一个入口并把这个入口更好地暴露给 Claude Code——
这符合几何信息论的结晶方向。**写更多散落的仪器不是,它们很难重用**。」

## 现状

| | |
|---|---|
| quay MCP 暴露的工具 | **17 个**(`task_*` / `gate_*` / `adr_*` / `action_*` / `lifecycle_*` / `config_validate`)——**全是任务板** |
| `plugin/scripts` 的仪器 | **81 个**,只能靠记住路径 `node --experimental-strip-types plugin/scripts/<name>.ts` |
| 普查器结论(2026-08-03) | live **36** · library 72 · ci-only 1 · dormant 7 · never-runs-test 8 · **unaccounted 81** |
| 脚本总数 | **205 → 207**,尽管退役物理删了约 51 个 —— **种群再生和修剪一样快** |

**一个佐证**:管理者在自己产品的源码里**连查两次都没数出那 17 个工具**,第三次读文件才对。
**可发现性不是抽象问题。**

## 三步,顺序不可换:先收缩,再暴露,最后新增

### 第一步(收缩):重跑已有普查器,不要新写

`plugin/scripts/runtime-usage-inventory.ts` **已存在**。拿到当前数字,给 **81 个 `unaccounted`** 每个一个处置:
保留(并说明理由)/ 退役 / 归入 library。

- **AC1**:普查重跑,`unaccounted` 每一项有处置,**「以防万一」不是理由**。
- **AC2(可判收口)**:**脚本总数下降**。205→207 是失败信号——**这一步不让数字下降就是没做**。

### 第二步(暴露):`live` 的仪器进 MCP,声明是筛选器

- **AC3(2026-08-04 人纠正后重写)**:**入口是一个工具,不是 36 个。**

  **人的原话**:「MCP 也不应暴露过多 tools 给 Claude Code,那会占用 Claude Code 的上下文。
  应该区分需要作为产品交付的能力和仅 quay 自己开发使用的。」

  **我原先写的「36 个 live 进 MCP」是错的**:现有 quay MCP 17 + meta-cc 约 17 = 34,
  再加 36 就是 **70 个,而每个会话都要付这份上下文**。

  **实测两个维度**:

  | 维度一:是否交付 | 数 |
  |---|---|
  | 随产品交付(在插件产物里) | **80** |
  | quay 自用(`experiments/` 下,不进产物) | **116** |
  | 本仓 `scripts/` | 7 |

  **产物里至少 9 个是 quay 方法论遗产**(`it0-*` 5 / `codex-stage1*` 2 / `audit-independence*` 2)
  ——**它们不该出现在别人的项目里**。

  | 维度二:谁调用 | 数 |
  |---|---|
  | tick 文档以**固定命令**调用 | 17 |
  | 被其它**脚本**调用 | 22 |
  | 被 **skill 文档**提及 | 8 |

  **⇒ 绝大多数是固定命令调用的,不是智能体临时挑选的。**
  **写在 tick 文档里的固定命令不需要成为 MCP 工具——文档本身就携带调用方式。**

  **正确形状**:

  ```
  instrument(action: "list" | "run", name?, args?)
  ```

  - **上下文成本:1 个 schema,不是 36 个**
  - **可发现性**:`action:"list"` 返回目录,每项带它声明的「我回答什么问题」
  - **交付/自用变成目录里的一个字段**,而**产物里只装 product 那些**

  **MCP 工具的判据不是「有用」,是「智能体必须在会话中途发现并选择它」。**
  按这条,仪器里够格的**接近于零**——目录解决可发现性,不必加载 schema。
- **AC4(筛选器,不是形式)**:**说不出自己回答什么问题的脚本,进不了目录**。
  ⇒ 「进目录」这件事本身强制收缩,而**不是把 81 个原样搬进去**。
- **AC4b(交付面筛选)**:**产物里只装 product 类**。
  `it0-*`、`codex-stage1*`、`audit-independence*` 这类 quay 自用的**从产物中移除**——
  **收口判据:插件产物的脚本数从 80 下降**。
- **AC5**:进入口后,调用方式从「记住路径 + `--experimental-strip-types`」变成 Claude Code 自动发现的工具。

### 第三步(新增):基于 meta-cc 的封装

管理者用 **4 次工具调用 + 手工算间隔**才得出「任务耗时 64% 在等套件」。**它应该是一次调用**:

```
task_time_breakdown(taskId) → { waitingPct, workingPct, fullSuiteRuns, gaps[] }
```

底下查 meta-cc,上面是一个 quay 工具。

- **AC6**:该工具**必须在第一、二步之后**才做。
  **先收缩再膨胀,否则入口一开始就装了不该装的东西。**

## 为什么这是结晶而不是又一个脚本

- **81 条要记的路径 → 1 个自动发现的入口**
- **声明要求是硬筛选**:回答不出「我解决什么问题」的东西被挡在外面
- **两个已有 MCP(quay + meta-cc)之间那层手工分析被固化成可复用的工具**,而不是每次重做


## 追加(2026-08-04,人问「会减少仪器和测试数量吗、会帮到套件时间吗」)

**会,而且主要收益来自下面这层——它原先不在本规格里。**

### 实测

| | |
|---|---|
| 全套件测试文件 | **143** |
| 其中 `plugin/test`(测仪器的) | **47(33%)** |
| **47 个里 spawn 子进程的** | **41** |
| 直接 `import` 被测模块的 | **3** |
| 81 个仪器脚本里有同名测试的 | **31** |

### 三层收益

1. **仪器数量**:第一步(收缩)的 AC2 已经要求总数下降;
   **81 个里 31 个有同名测试 ⇒ 退役一个脚本带走一个测试文件**。
2. **测试数量**:随之减少,但这只是零头。
3. **套件时间**:**主要收益在这里**——

### AC7(新增):进入口的仪器,其测试从 spawn 改为 import

**当一个仪器变成 in-process 的 MCP 工具,它的测试就可以 `import` 而不是 `spawn`。**

**这不是新规则,是 `CLAUDE.md` 已有的 AC7 分层判据**:

> **分支密集的纯函数 → 直接 `import` 单元测试**——
> 一个失败的 CLI 断言只说明「输出里没有 X」,**说不出是哪个分支错了**

**而 `plugin/test` 里 41/47 在 spawn,3 个在 import ⇒ 政策存在,未生效。**

**诚实的边界(必须写明,否则这条会被做过头)**:
- **检查 CLI 契约的测试必须继续 spawn**(argv 解析、退出码、stdout 格式)——
  那正是 AC7 第一层「用户可见契约 → 端到端」
- **能转的是检查逻辑的那部分**,估计约一半

**判据**:`plugin/test` 里 spawn 的文件数下降,且**每一个仍然 spawn 的都能说出它在验哪条 CLI 契约**。
说不出的,就是该转 import 的。

**与 `SPEC-cut-the-waiting.md` 的关系**:那份砍的是**等待**,这条砍的是**每套件的成本**(fork 数、内核态占比)。
**两者的验证方法不同**:前者用 meta-cc 查间隔分布,后者数 fork 与 spawn 调用点——
**都不要用套件墙钟,σ=297.6s 会把两者都吃掉。**


## AC8(2026-08-04 人补):自用仪器也要集成,只是入口形态不同

**人的原话**:「对于这些本项目用的仪器,即使不进 mcp,也还是应当适当集成。」

**116 个 `experiments/**/scripts` 不进产物、不进 MCP,但不能继续散着。**
形态是**一个派发入口**(如 `quay-dev <instrument> [args]`),不是 36 个 MCP 工具:

- 目录集中在一处,每项同样声明「我回答什么问题」
- 共享的启动开销(路径解析、`NODE_COMPILE_CACHE`)只配置一次
- **最关键的一条见下**

## AC9:集成是「import 取代 spawn」的前提,不是它的附带好处

**散落的 CLI 脚本强制测试用 `spawn`;模块化到一个入口之后,测试才能 `import`。**
⇒ **AC7(测试从 spawn 改 import)依赖 AC8 与第二步,不是独立项。**

### 内存实测(人问「import 是否也减小内存压力」——是,机制具体)

| | |
|---|---|
| **`spawn` 一个仪器** | **79MB RSS**(≈42MB node 基线 + ≈38MB 模块) |
| **`import` 同一模块** | 基线 42MB → 80MB,**增量 38MB** |

**每次 `spawn` 重付一次 ~42MB 的 node 基线,`import` 不付**——基线已由测试进程付过。

**8 条 lane 各 spawn 一个 ⇒ 约 336MB 纯重复基线,而这是峰值。**
**峰值正是 2026-08-04 全机 OOM 的那个量**(见 [[the-machine-ran-out-of-memory]])。

**诚实限度**:336MB 是**用单进程实测值外推的**——
「同时起 8 个测总量」那次测法失败(进程太短命,只捕到 1 个),**不是直接测到的**。

⇒ **这条改动同时买到三样**:套件时间(每 spawn 省 ~220ms)、
内核 CPU(fork 数下降)、**峰值内存(每并发 spawn 省 ~42MB)**。
**三者里只有第一样会被 σ=297.6s 吃掉,后两样都可直接测。**
