# 裁定:方法论层能力是交付物的一等公民——但先让已有的 36 个可被发现,不是再写更多

**人 2026-08-04**:「这显然是一个软件工程方法层的改进。这是对的,
而且 quay 应当交付更多工程方法层的能力,以支持应用 quay 的项目更好地开发。」

## 实测:能力不缺,可见性缺

产物 `~/.local/share/quay-plugin/scripts/` **80 个脚本**,粗分类:

| 类 | 数 |
|---|---|
| **判据/检查** | **36** |
| 资源/闸 | 10 |
| 度量 | 4 |
| 观测 | 3 |
| **其它(按文件名归不进任何类)** | **27** |

**最后一行是真问题**:粗分就有 27 个归不进去,**因为产物从来没有声明过自己的分类**。
README 里 methodology 出现 3 次,全是顺带提及。
⇒ **一个装了 quay 的项目拿到了 36 个检查,却没有任何东西告诉它这些检查各自回答什么问题。**

## 组织原则:一个能力 = 让一个原本不可机械提问的问题变得可提问

今晚四个仪器提案的共同形状:

| 能力 | 它让什么问题可被提问 |
|---|---|
| 事件落盘 + 零触发报告 | 「这个机制响过吗」 |
| 名实一致检查 | 「我们是不是又造了一遍已有的抽象」(`L_G`) |
| 守卫移除测试 | 「这个守卫真的在生效吗」(`Π_{S→E}` 第二步) |
| 规则的跨介质清单 | 「这条规则还适用在哪里」 |

**这既是组织原则,也是筛选判据:一个不对应任何问题的 checker,不是能力,是本仓的 lint。**

## AC

- **AC1(先目录,后新增)**:每个随产物交付的检查**声明它让什么问题可被提问**——
  一行、机器可读的字段(不是 README 小节,那会漂)。
  `quay methods list` 之类的命令能列出「你装到了什么、各自回答什么」。
- **AC2(筛选)**:对 80 个脚本跑一次与 `runtime-usage-inventory` 同款的分类,
  判据是「**这个能力是否只有本仓的历史才motivate它**」。
  `codex-stage1-selfcheck`、`it0-enforcement-with-design-check`、`audit-independence-check`
  这类 exp5 遗产**不该随产物进入每个目标项目**。
  **收口数字**:交付的能力数从 80 降到「每个都能回答 AC1 那个问题」的子集。
- **AC3(第一个新增)**:事件落盘 + 零触发报告。
  它同时是**收缩相的机制**(见 [[crystallization-the-contraction-phase-has-no-mechanism]])——
  唯一一个会主动产出「删掉它」的能力。
- **AC4(纯读契约的收窄)**:把「不许写任何文件」改为「**不许写被观测者的状态**」。
  写事件日志不改变被观测对象的状态空间(不碰工作树、不碰 git),
  与「`--report` 不许写文件」不是同一件事。**现行契约让「从没响过」无法被查询。**
- **AC5(负控制)**:目录建好后,**随机抽 5 个交付的检查,问「它回答什么问题」**。
  答不出来的就是 AC2 该筛掉的。

## 明确不做

**不要先写更多 checker。** 36 个已经在那里,而没人知道它们回答什么。
**在可见性建立之前新增能力,只会让 27 这个数字变大。**
