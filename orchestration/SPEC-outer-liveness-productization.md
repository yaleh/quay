# 规格：`outer-liveness.sh` 产品化

> **RETIRED (2026-08-06)**：本规格的 **AC20（单飞挂载 + 共享 events 文件）与 AC21（共享文件记全量、
> 阈值只作用于持有者 stdout）已被推翻**——人裁定彻底去掉共享事件文件 + 互斥锁（观测是树、只读天然
> 不排他；`heavy-op-token.sh` 整体删除）。实现随 `plugin/scripts/session-liveness.sh` 更新：
> 每观察者自己的 stdout 事件流（谁挂的谁拥有）、无锁、无共享文件。本文件保留为**历史记录**——
> 其中的 AC10-19（信号源/阈值/心跳源/忙闲判据）仍有效，AC20-22（单飞/共享/订阅）已退役。

**提出**：人 2026-08-03 ——「这个 monitor 脚本应当进一步产品化、通用化和参数化。使用 quay 的项目都需要使用它。」
**定义者**：管理者（`quay-0:manager`）。**实现者**：`quay-0:tools`。
**这份文件只定义「要什么」和「怎么算达成」，不规定实现细节**——实现选择由 tools 判断。

## 核心判断（这条决定了设计方向）

**一个采用 quay 的项目只有一个自己的外层。** 三项目扇出是**管理者的特殊用法**，不是通用形态。

⇒ **默认必须是「看本项目自己的外层」，零额外配置**；多目标是可选能力，不是前提。
⇒ 目标与路径应当**在 quay-init 安装时被替换进去**（和两份 tick 文档同一机制），
   **不要在运行时解析 YAML**——bash 解析 YAML 会引入一个不值得的依赖与一类新的失败。

# 追加规格（2026-08-03，人问「你和 quay outer 都在用它吗、还需要改进吗」）

## 实测：不是同一个工具，是两个互补的工具

| | 管理者挂的 | quay 外层挂的 |
|---|---|---|
| 工具 | `outer-liveness.sh` | `inner-state.sh` |
| 事件 | `GONE`/`BACK`/`IDLE`/`RESUMED`/`STALL`/`LOOP-OVERDUE`/`STATUS` | `INIT`/`START`/`BATCH-END`/`BLOCKED`/`UNBLOCKED`/`REVERT`/`MASSDELETE` |
| 判据 | 进程存活 + pane 哈希 + tick 日志 mtime | 遥测 JSON + `git log`/`show` + 阻塞信号文件 |
| 看的是 | **会话状态**（活/闲/停滞） | **工作状态**（批次起止/阻塞/危险变更） |

## 缺口：没有任何东西看内层【会话本身】是否还活着

`inner-state.sh` 看的是工作产出。**内层进程死了，它只会看到「没有新遥测」——
而那和「内层在思考一个难题」完全同形。** 这是本仓今天已经栽过两次的那一族失效
（外层空闲被当成健康、监视器盯错层），只是换了个位置。

## 判断：`outer-liveness.sh` 的名字取窄了

进程存活、pane 忙闲、心跳逾期——**这套逻辑对任何 Claude Code 会话都成立，与「外层」无关**。
内层同样需要它，而且更需要：内层跑的是重活，死掉的代价更大。

## AC（追加，编号续前）

- [ ] **AC10**：改名并泛化为**会话存活监视**（名字由你定，`session-liveness` 之类），
      `outer-*` 的字样只应出现在**默认值**里，不应出现在**概念**里。
      判据：事件名与文档不再假设被监视者是「外层」。

- [ ] **AC11**：**心跳文件可参数化**。外层的心跳是 tick 日志，内层的心跳不是——
      内层的心跳应当是它自己的工作产出（遥测 / `.workflow-events/` 之类，**由你判断哪个最可靠**）。
      判据：同一个脚本用不同参数分别监视外层与内层，两边的逾期判据都能正控制触发。

- [ ] **AC12**：**quay 外层能同时挂两个**——`inner-state.sh` 看工作状态、
      泛化后的存活监视看会话状态。两者**不合并**：一个报「它在做什么」，
      一个报「它还在不在」，合并会让一种失效掩盖另一种。
      判据：外层的 tick 文档写明它该挂哪两个、各自答什么问题。

- [ ] **AC13**：**随包走**——泛化后的版本仍由 `quay-init --loop` 铺下，
      且随包的两份 tick 文档（内层那份也要）写明各自该挂什么。

## 不做

- **不把两个工具合并成一个**（理由见 AC12）
- **不在这一轮改 `inner-state.sh` 的事件集**——它的事件是对的，缺的是它旁边少了一个存活监视

# 追加规格二（2026-08-03，人问「session-liveness.sh 到底在观察什么」）

## 审计：四类事件里有两类根本不在看会话

| 事件 | 信号源 | 在看会话吗 |
|---|---|---|
| `SESSION-GONE` / `SESSION-BACK` | 进程存活 | ✓ |
| `SESSION-IDLE` / `SESSION-RESUMED` | tmux pane 哈希 | ✓ |
| `SESSION-STALL` | **≥`STALL_MIN` 分钟无新提交** | ✗ **看的是仓库** |
| `SESSION-OVERDUE` | 心跳文件 mtime（tick 日志 / `.workflow-events`） | ✗ **看的是工作产出** |

**心跳设计之所以垮掉，根因在这里**：`.workflow-events/` 是**工作产物**不是会话信号，
外层实测证明它在任务进行中冻结（每任务 jsonl 只有 1–2 行，19 分钟的在飞任务仍是 1 行）。

**我们一直在用「它产出了什么」去推「它还活着吗」——那两件事只在正常情况下相关。**
而监视器存在的全部意义，恰恰是覆盖不正常的情况。

## 人给的判据

> 「它应当观察 Claude Code 会话，看 tmux 屏幕或看 `~/.claude` 下的 transcripts 都可以。」

**⇒ 会话信号只有两个合法来源：tmux 屏幕、`~/.claude/projects/<项目>/<会话>.jsonl`。
不是仓库、不是提交、不是工作产出。**

## 实测：transcript 是可用的会话心跳

2026-08-03 同时用两种方法测同一批会话，**结论一致**：

| 会话 | transcript 写入距今 | pane 哈希法 | 一致 |
|---|---|---|---|
| 管理者 `b8dc91a6` | **0s** | 在忙 | ✓ |
| quay 外层 `a725919c` | 267s | 空闲 | ✓ |
| quay 内层 `3bbd3095` | 332s | 空闲 | ✓ |

**transcript 优于 pane 哈希的三点（每点都有今天的实例）**：

1. **不受 TUI 重绘影响**——管理者那个停泊会话的 `RESUMED`/`IDLE` 假阳性就是重绘造成的
2. **不依赖 tmux**——不在 tmux 里的会话也有 transcript
3. **`stat` 比 `capture-pane` 便宜**，且没有「读 TUI」的观感问题

**未解的问题（实测过，不是推测）**：`pid → transcript` 的映射。
`/proc/<pid>/fd` 里**找不到** jsonl（Claude Code 追加后关闭）。
同一项目目录下有多个会话（inner/manager/outer/tools），需要区分谁是谁。

## AC18（追加，2026-08-03，人：「TUI 也是可以考虑的…考虑一个人是如何观察屏幕的」）

**人的判据**：不追求假阳性完全为零；可以过滤掉屏幕上更容易变化的区域。

**⇒ 屏幕信号不是「整屏哈希」，是「人真正看的那几个标志」+「屏蔽易变区」。**

### 实测（2026-08-03）

| 屏幕元素 | 人看不看 | 实测行为 | 作为信号 |
|---|---|---|---|
| `esc to interrupt` / 输入框可用性 | **看** | 2 秒内 `1→1`、`0→0`，**不抖** | **主信号** |
| 转圈耗时 `✽ …（41s · ↓1.2k tokens）` | 不看 | **每秒跳** | **必须屏蔽** |
| `✻ Baked for 8m54s` 残留 | 不看 | **五个会话全部存在，含空闲的** | **不能当忙**——是上一次动作留在屏上的字 |
| `/clear to save 151.2k tokens` | 不看 | 缓慢变化 | 必须屏蔽——**管理者那个停泊会话的假阳性就是它** |

**真正空闲的会话整屏无变化**（probe 2 秒 diff 为空）——所以整屏哈希不是完全不能用，
**是它把「人不看的部分」也算进了信号**，于是把 chrome 的抖动读成了会话的活动。

### 判据

- [ ] **AC18**：屏幕信号改为**语义标志 + 屏蔽易变区**，不是整屏哈希。
      - 主信号：`esc to interrupt`（或等价的输入框可用性标志）
      - 屏蔽：转圈耗时行、token 计数行、提示语行
      - **`✻ …` 残留不得作为忙的判据**
      - 正控制：造一个确定在忙与确定空闲的会话，两个方向都要报对
      - **允许有假阳性**——人明确说了不追求为零；但**假阳性必须可解释**
        （能指出是屏上哪一部分造成的），不可解释的假阳性仍算缺陷

### 与 AC16（transcript）的关系

**两者都要，因为盲区不同**（AC17 已要求写下取舍）：

- 屏幕：语义清晰、即时；但依赖 tmux，且 TUI 布局变化会让标志失效
- transcript：不依赖 tmux、不受重绘影响；但 pid→文件映射未解，且**只在会话写入时更新**

**一个提示**：屏幕标志失效的形态是**静默**（找不到 `esc to interrupt` 就永远判空闲），
这与「会话真的空闲」同形——**需要一个正控制定期确认标志本身还在**，
否则 Claude Code 改一次 TUI 文案，这个监视器就无声地失效了。

## AC19（2026-08-03 新增，由一次自造假阳性触发）

监视器刚报 `SESSION-RESUMED quay`，成因字段诚实地写「上次收到输入：**取不到**」。
**真实成因是我自己一分钟前 `send-keys` 唤醒了它。**

这不是误报率问题——按损失函数它属于**可一次调用打发**的那类，代价已经付得起。
问题是**缺的那个字段恰好是唯一能消解歧义的字段**：
「自己醒的」和「被我叫醒的」在屏幕上完全同形，而两者的处置完全相反
（前者是它在干活，后者是我在干活）。

**tmux 取不到「上次收到输入」，但发送方知道。**
监视器解不了的问题，驱动方一行就能解：

- **AC19a**：凡通过 `send-keys` 唤醒会话的一方（管理者、外层），
  把 `<ts> <target> <发送方>` 追加进一个共享的只追加日志
- **AC19b**：监视器在报 `SESSION-RESUMED` 前查该日志最近 N 秒；
  命中则**降级为 `SESSION-RESUMED(driven)` 或直接不报**
- **AC19c**：负控制——一次**没有**对应发送记录的恢复必须仍然照报，
  否则这条改动就把真信号一起吃掉了

**这是「观察者解不了、参与者随手可解」的一般形态**：
不要为了让观察者更聪明而加推断，去问那个本来就知道答案的人。

### AC19 的匹配对照组（同一分钟内白捡，非构造）

写完 AC19 一分钟内，监视器报了第二条 `SESSION-RESUMED`，这次是 **archguard**——
**我没有对它发过任何东西**。

| | quay 那条 | archguard 那条 |
|---|---|---|
| 成因 | **我 `send-keys` 唤醒**（20:56:35Z） | **自发**（无任何发送记录） |
| 屏幕证据 | `esc to interrupt` + 内容区变化 | **完全相同** |
| 「上次收到输入」 | 取不到 | 取不到 |
| AC19 下的正确处置 | 降级/不报 | **必须照报** |

**两条事件相隔约一分钟、屏幕上逐字段同形、正确处置相反。**
这对控制组不是构造出来的，是自己撞上来的——
它同时给了 AC19b（该压的）和 AC19c（该留的）各一个真实样本，
所以这条 AC 不需要再单独造 fixture 去验证。

## AC20：挂载必须单飞（2026-08-03，实测半小时内从 1 个涨到 5 个）

**实测**：21:2xZ 我杀掉 5 个旧版实例并通知两个外层「需要就自己重挂」。**30 分钟后有 5 个挂载、12 个进程**：

| ppid | 属主 | 挂载时刻 |
|---|---|---|
| 120373 | 管理者（我） | 19:21Z **和** 21:50Z —— **我自己就有两个** |
| 966759 | quay 外层 | 21:23Z（收到我的通知后重挂） |
| 2388387 | archguard 外层 | 21:24Z（同上） |
| **270244** | **quay 内层** | 21:49Z —— **它也挂了一个，没人知道** |

**「需要就自己重挂」这句话本身就是缺陷**：它把一个本该单飞的资源交给每个参与者各自判断，
而每个参与者的判断单看都对——**我需要监视器，我没有，所以我挂一个**。
五个人都这么想，就有五个挂载，同一次状态切换被报五遍。

### 判据

- **AC20a**：挂载前取单飞锁。**复用 `heavy-op-token.sh` 已验证的那套**——
  `wx` 原子创建 + mtime 陈旧 **且** pid 不存活才回收，绝不裸覆盖、绝不永久锁死。
  **不要新写一套锁**：那套锁今天已经在真实的死持有者上回收了 17 次。
- **AC20b**：第二个挂载**不是失败，是空操作**——检测到活着的持有者就打印属主与 pid 后退出 0。
  报错会让人去 kill，而 kill 正是这一整摊事的来源。
- **AC20c**：事件**写进共享文件**（如 `$QUAY_GLOBAL_DIR/session-liveness/events.jsonl`），
  任何一方都能读。**订阅与挂载分离**——需要看事件的人不必自己挂一个。
- **AC20d**：负控制——持有者进程被 `kill -9` 后，下一次挂载必须能**接管**（陈旧回收），
  否则单飞就变成了单点故障。

**一般形态**：**「谁需要谁自己起一个」对单飞资源是错的默认。**
正确的默认是「谁需要谁去订阅」，而挂载是一个有主的、可接管的角色。
这与令牌是同一条原理，区别只在于令牌天然是排他的、监视器看起来不是——**看起来不是，所以没人给它加锁。**

### 落地（2026-08-03/04，gap-liveness-mounting-is-a-single-flight-role-with-no-owner）

- **挂载入口**：`plugin/scripts/session-liveness-mount.sh`（`exec` 进 `session-liveness.sh`，同一 pid）。
  `session-liveness.sh` 自身也在长跑模式取单飞锁——**任何入口都单飞**，`--once` 等诊断接缝不取锁。
- **AC20a**：取锁 = 直接调用 `heavy-op-token.sh --acquire <owner> --root $QUAY_GLOBAL_DIR/session-liveness`
  （**不新写锁**；wx 原子创建 + mtime 陈旧 AND pid 不存活才回收，那套已在真实死持有者上回收 17 次）。
  锁状态在 `$QUAY_GLOBAL_DIR/session-liveness/heavy-op/token`。
- **AC20b**：`_sl_acquire_or_noop` 先 `--timeout 0` 快查；有活持有者 ⇒ 打印属主与 pid、退出 0。
  两个实现陷阱（均已修并测试钉住）：① 取锁不能用命令替换 `$(...)`——它会引入瞬态子 shell 当
  heavy-op-token 的父进程，锁记下子 shell 的 pid（随即退出），下一个挂载会误回收活持有者；
  ② 单飞门必须直接调用、不能 `case "$( _sl_acquire_or_noop )" in`——命令替换的子 shell 会在函数
  返回时触发 EXIT trap 立刻释放锁。
- **AC20d**：持有者 kill -9 后，下一次挂载 `--timeout N` 有界等待回收并取得，输出
  `takeover_ms=<毫秒>`（`SESSION_LIVENESS_MOUNT_STALE_S` 默认 3 只影响接管速度，活持有者永不回收）。
- **AC20c / AC7**：事件与心跳写 `$QUAY_GLOBAL_DIR/session-liveness/events.jsonl`
  （每行 `{"ts":…,"event":…,"name":…,"msg":…}`）；持有者每轮追加一条 `HEARTBEAT`。
  订阅方读最后一条 ts / 文件 mtime 判「看门的不在了」，**不需要任何人去试挂**。
- **AC9（本任务的判据）**：`monitor-mount-check.sh` 的 `ownedByThisSession` 已废除，
  判据改为 `delivered`（共享事件文件有新事件）——别的会话挂的、投递正常 ⇒ PASS；无人挂载 ⇒ FAIL。

## AC21(2026-08-04):共享日志记全量,过滤属于订阅方 —— AC20c 的修正

**这是我自己那份 AC20 的设计缺陷,不是实现问题。**

### 实测

人 06:3xZ 指出「quay outer 在等待输入,monitor 应该通知你」——**而我没收到**。
查:共享 `events.jsonl` 里 **`SESSION-IDLE` 出现 0 次**,`SESSION-RESUMED` 20 次。

代码是对的(`session-liveness.sh:645` 走 `sl_emit`,`sl_emit` 确实双写),
**是发出之前就被抑制了**:

```
:639   elif [ "$hmin" = "?" ] || [ "$hmin" -ge "$LOOP_MIN" ]
持有者(外层的挂载 pid 456415)环境无 LOOP_MIN ⇒ 默认 20

```

**「空闲但心跳新鲜」在 `LOOP_MIN=20` 下被静默** —— 而抑制理由的注释是我自己标定的
(「健康循环每 20 分钟一对事件、三项目满载 18 次/小时,全是噪声」)。

### 缺陷

**单飞挂载 + 共享文件,而过滤发生在【发出端】⇒ 持有者的阈值被强加给所有订阅方。**

| 订阅方 | 需要什么 |
|---|---|
| 外层(持有者) | **不想**听自己空闲——噪声 |
| 管理者 | **想**知道外层空闲等输入——「该派活了」 |

**两者恰好相反,而现在只有持有者的阈值生效,被滤掉的事件根本没进文件,订阅方无法补救。**

### 判据

- **AC21a**:**共享 `events.jsonl` 记录全量事件,不施加任何阈值抑制**
  (`LOOP_MIN`/`STALL_MIN`/`OVERDUE_MIN` 只作用于持有者自己的 stdout)。
- **AC21b**:每条事件带上判定所需的原始量(如 `hmin` 心跳分钟数),
  **让订阅方能自己决定报不报**,而不是只给一个已经判完的结论。
- **AC21c(负控制)**:持有者以 `LOOP_MIN=20` 运行时,
  共享文件里**仍应出现 `hmin < 20` 的 IDLE 记录**——出现即通过,不出现即未修。

### 一般形态

**已经被一个消费者的阈值筛过的日志,服务不了第二个消费者。**
**记录与判断必须分开**:记录记全量,判断留给读的人。
这与本仓「carry evidence not conclusions」是同一条,
**而我在自己设计的机制里违反了它。**
