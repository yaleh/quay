## §1 它要解决的问题（实测，不是推理）

**根问题**：三层的每轮机械检查是**散文驱动**的，义务会随上下文推移**逐条静默脱落**，且脱落与执行在记录上同形。

**§1.1 实测基线（2026-08-14 13:10Z → 2026-08-15 01:43Z，会话动作记录，第三方可读，非自述）**

| 义务 | 层 | 形态 | 每轮覆盖率 |
|---|---|---|---:|
| B1 调 workflow | manager | 0 跳（prompt 到达即触发的第一个动作） | 33/33 = **100%** |
| A1 `manager-anchor-check.py` | manager | 1 跳，绑真钟/哨兵 | 33/33 = **100%** |
| 收尾0 `manager-arm-loop.sh --verify` | manager | 1 跳，绑哨兵核实 | 32/33 = **97%** |
| 步骤 0b 判准主题词 | manager | 1 跳，**物理并进**每轮必跑的同一条命令 | 4/4 = **100%** |
| A13 `inner-wakeup-heartbeat-check.ts` | outer | 1 跳，绑每轮读数 | 38/38 = **100%** |
| A23 `outer-anchor-check.ts` | outer | 1 跳，**独立一条** | 8/13 = **61.5%**，末 5 轮连续 0 |
| A9 判 B1 是否执行 | manager | 1 跳，**独立一条且无载体** | ≤5/33 = **15.2%** |

**⇒ 结论（`manager-phase-goal.md` 🔭 观察项节，n=7 方向一致无反例）**：
**义务的可靠性由【到外部触发点的跳数 / 是否绑在必然发生的动作上】决定，不由载体是散文还是 workflow 决定。**
workflow 把 N 条义务压成 1 跳，**压不掉它返回清单里的每一条**（B1 100% 与 A9 15.2% 同在 workflow 保护下，差 6 倍）。

**§1.2 为什么现有的两种「上下文之外」都不够**

| | 在所有层的上下文之外？ | 能检查吗？ |
|---|---|---|
| cron 每轮重投的 prompt | ✅ 结构上不可漂移 | ❌ **只能命令，不能检测** |
| 另一层（outer/inner/manager 互查） | ✅ | ⚠️ 能，但**没有义务来源** —— outer 2026-08-15 02:5xZ 拒绝时的理由成立：「查 manager 没有对应判据/义务来源，加它是我自行扩大观测面」；人同日亦否决接环 |
| **MCP server** | **✅** | **✅ 且是构造性的——「谁本轮调没调」是服务端事实，不需要任何一层去查，也不给任何一层新义务** |

**⇒ 这是本 SPEC 的唯一结构性理由**：今天存在一个**不可由任何单层关闭**的残留——
`B1 没被调 ⇒ 由 B1 返回的 A9 也不在场 ⇒ 无人发现`（2026-08-14「停调 workflow 19 小时、事后清点出 8 条违规」即此形态）。
**把「有没有调」的记录搬到会漏调的主体之外，该残留自动消失。**

## §2 接口（15:3xZ 设计 + 2026-08-15 实测加固）

```
quay_next(who, cursor, facts[], evidence[]) → { instructions, refused, notEvaluated, missingFacts, rulesVersion }
```

**§2.1 五条硬约束（前两条是人的原话）**

1. **须支持 manager / outer / inner + 未来新角色**（人 15:3xZ）
   ⇒ `who` 是**自由串不是枚举**；角色与业务都是**规则数据里的条目**，不是 schema 里的分支。
   （枚举会逼实现方每加一个角色就碰 `tools/list_changed`。）
2. **MCP 内不得调 LLM，须机械**（人 15:3xZ）⇒ 全部判据是纯谓词；语义选择留在 agent 侧（见 §2.3）。
3. **`refused` / `notEvaluated` 必需**——沉默的不作为 ≠ 判断为不该做。
   **实证（本 SPEC 最干净的一条）**：A9 覆盖率 15.2% 而**从未被发现**，因为它的检查对象恒 100% ⇒ 它从来没有东西要报
   ⇒ **「没运行的检查」与「运行了且输出 OK 的检查」在记录上完全同形**（硬规则 3b 的镜像）。
4. **每个 fact 必带 `measuredAt` 与 `source`。**
   `measuredAt` ⇒ 机械判过期。**实证**：outer 的 tick-log 行只有 `HH:MMZ`、无日期且顺序非单调
   ⇒ 2026-08-15 两次算其覆盖率得 18.4% / 81.6%，**两个都不可信** ⇒ 无 `measuredAt` 的量，任何比率都不可信。
   `source` ⇒ 规则可声明「该量只接受来自机件 X 的值」，**在结构上消灭【读法散落】整类**
   （实证：`mon_procs` 10 vs 1、lane 三推导两条绕开旋钮②）。
5. **比较类判据必须声明归一化函数，且「无法归一化」是第三个取值**（2026-08-15 新增，原设计没有）。
   **实证**：`outer-cron-registry.ts` 曾用 `expr === rec.cronExpr` 严格字符串比较，把 `*/20` 与 `0,20,40` 这对
   **语义等价**判成漂移 ⇒ 每轮 `code=1` ⇒ 开始训练「已知、跳过」的习惯。
   **参考实现 = 修复后的 `cronExprsEquivalent`**（负控制实跑 5/5）：
   ```
   语义等价 → true ｜ 三类真漂移 → false ｜ 无法归一化 → 保守 false（⛔ 不静默通过）
   ```
   **⇒ 恒红与恒绿一样是零信息，而恒红更贵——它训练出忽视。**

**§2.2 `evidence` 是产物不是自述**

校验规则本身也是数据（纯机械谓词，如 `jsonl_lines_increased`）。
**谓词形态的参考实现 = `outer-tick-log-check.sh:113-115`**：判 A23 输出行不是「本段含 `A23`」，
而是**含 `A23` 且带状态词**（`code=N` / `VIOLATED` / `OK` / `NOT-EVALUATED` / `CRITICAL`），
注释明写为了区分「真跑了留下输出」与「散文里讨论 A23 而无产物」。
**⇒ evidence 谓词一律【按产物形态命中】，⛔ 不按关键词命中**（硬规则②）。

**§2.3 指令要能表达【约束】而非只【命令】**

`dispatch` 类指令返回 `candidates + mustSatisfy + choose`，agent 选并回报 `chosenBecause`。
**理由**：纯机械排序已退化（value 三轴 21 条只 1 条取 Y ⇒ 有效排序 = 1/cost），
且人 2026-08-13 裁定「先派谁」归 inner。
**⇒ 与 `SPEC-dispatch-ordering-semantic-2026-08-13` 的分工保持一致：机制答「能不能派」，agent 答「先派谁」。**
**⛔ 本 MCP 不得返回「派哪几个」** —— 那会把语义选择收回机制手里，与该 SPEC 相反。

## §3 与现有 quay MCP server 的集成（人 03:0xZ：「显然它应当和现有的 quay MCP server 集成」）

**§3.1 落点**：`packages/quay/src/mcp-server.ts` + `mcp-handlers.ts` 的既有工具面
（现有：`task_*` / `gate_*` / `lifecycle_*` / `adr_*` / `action_*` / `instrument` / `config_validate`）。

**§3.2 现成可复用的两件（用机件，不手搓——用在设计上）**

**① `packages/quay/src/observation.ts` 已实现本 SPEC 最难的那条契约。** 其头注释逐字：
> 每个数据源**独立** try/catch；ABSENT ⇒ `status:"empty"`；PRESENT 但读不懂 ⇒ `status:"error"` + `reason`；
> **「无数据」与「读失败」永远可区分**；本模块**从不抛出**；读路径**从不写文件**。

**⇒ §2.1-3 的 `notEvaluated` 不是要新发明的东西，是把一个已在产品里跑着的降级契约推广到检查面。**
**⚠️ 但注意边界**：`observation.ts` 头注释同时声明它是「Core 里唯一知道工作区特定观测细节的模块」，
是**被隔离的**、不属 Provider ABI。**本 MCP 若引入工作区特定路径，必须沿用同一隔离策略，⛔ 不得渗进 Core 的其余部分。**

**② `cronExprsEquivalent`（`plugin/scripts/outer-cron-registry.ts`）** 是 §2.1-5 比较类判据的参考实现。

**§3.3 provider 无关性**：`facts` 是开放键值集合、`who` 是自由串、规则是数据
⇒ **本工具面不引入任何 provider 特定分支**，符合 Core「只对任务视图模型编程」的既有约束。

## §5 最大风险与它的两条机械检查

**风险：规则数据会长成第二个散文。**

**必须自带两条机械检查（缺一不可）**：
```
① 同一 fact 名只能有一处 source 声明
② 同一判据不得有两条规则给出相反结论
```
**反例一（15:3xZ 记）**：manager 核里 A10 与 A0-⑤ 两条并存、一对一错，
而 `tick-core-static-check` 报 55/55 PASS ——**它查覆盖率，不查一致性。**
**反例二（2026-08-15 新增）**：outer `71b91799` 修「一条散文条款被静默跳过」，
用的是**同一份文件里的另一条散文条款**
⇒ **规则数据一旦允许自由文本，这个动作会以同样的形式重演，只是换了个载体。**

### §8.1 问题的重新表述（比「跳数」更准）

人 2026-08-15 08:1xZ 逐字：「**我们担心的不是偶尔的抖动，而是长期的漂移**」
「**subagent call limit 不重要，其比发生漂移需要的次数高一个量级，而且可以用工程手段处理**」。

**⊢ 量化核实（我此前的反对因此撤回）**：
```
预算：CLAUDE_CODE_MAX_SUBAGENTS_PER_SESSION 默认 200（会话累计）
     tasks/gap-inner-subagent-budget-invisible.md:49 逐字「/clear 立刻解封（重置预算至 200）」
     env var 可设 2000（同文件 :45）
漂移：A23 衰减到零 = 13 轮 ≈ 4.3 小时；A9 覆盖率 15.2% = 33 轮窗口
⇒ 漂移在 ~10 轮显形；200 预算按每 tick 3 subagent = 66 轮、5 个 = 40 轮，仍是漂移时标 4 倍以上
⇒ **不是悬崖，是可调参数**；我 04:1xZ「拿已知漂移换未知悬崖」的说法【尺度算错，撤回】。
```

**⊢ §1.1 七个覆盖率点指向的真正规律**：
> **凡每轮从上下文【外部】重新物化的，都是 100%；凡需要在上下文【内部】跨轮存活的，都衰减。**
> B1（cron 每轮重投）33/33 · A1/arm-loop（绑必做动作）33/33、32/33 ｜ A23、A9（靠记得）61.5%→0、15.2%

**⇒ 设计目标不是「少犯错」，是【让需要跨轮存活在主上下文里的东西趋近于零】。**

### §8.2 两类错需要两种解法（⛔ 不可混谈）

**这是 2026-08-15 一夜实证才分清的**：
```
判断类错 ⇒ 新鲜上下文（subagent/workflow）—— 它们本来就只需要「facts + 一条判准」，不需要任何历史
   实例（全部当夜、全部长上下文内）：AC62 在错误环境验绿就勾 · 手搓资格谓词漏 PARKED_MARKER_RE/isCompound
                                    · 18 vs 5 混违规类型 · 30 vs 1 把全史审计数当 enforcement 差集
路由类错 ⇒ 自门控命令形态 —— 换多新鲜的上下文都不会好
   实例：改完不提交（阻断 inner fan-in 1.5h）· 读到非终态仍提交（两次）
   已落产物：manager-tick-closing.md「提交必须用自门控的那一条命令」+「改被机械断言的豁免面文件时并进断言测试」
```

### §8.3 三阶段

**阶段 1（本次执行）——【读数】搬进 subagent。**
现状：`manager-tick-core.js` 把 `READ_CMD` 作为**命令块交还主线程执行** ⇒ 命令输出全部沉积在主上下文。
改为：**workflow 内一个 readings agent 跑固定命令集，只回结构化 facts**；主循环再也看不到原始输出。
**落点全在 manager 豁免面**：`.claude/workflows/manager-tick-core.js` + `orchestration/manager-tick-prompt.txt`。

**阶段 2 —— 【判断】搬进 workflow。** 每条判准 + 它需要的 facts，交给一个新鲜 agent 单独评。
直接对着 §8.2 的判断类错——它们不需要当夜积累的任何上下文，**却被那些上下文污染了**。

**阶段 3 —— 路由器的残余。** 留在主循环的只有投递/裁定/提交（要权限与连续性），由自门控命令形态兜住。

### §8.4 四条工程细节（不做会前功尽弃）

1. **`/clear` 安全性是硬前提，且已有人的裁定**（08-14 08:4xZ「保障 `/clear` 后的行为稳定性；subagent/workflow
   的独立上下文是优势」）⇒ `/clear` 之后还需要的一切必须在盘上：prompt 正本 + workflow 脚本 + 账本。
   **这同时是「预算可随时 `/clear` 重置」的前提——两件事是同一个设计。**
2. **args 是漂移的回流口**：今天 B1 传的 `prior:<本轮读数差异>` 是主上下文的总结文字
   ⇒ **执行搬走了、输入还在漂**。args 必须机器可算（runId/路径/任务 id/facts JSON），⛔ 不是总结。
3. **subagent 返回必须带 schema**，否则散文从返回值那一侧灌回来，白搬。
4. **每多一层隔离，就多一个「输入没跟着过去」的机会** —— 实证即本日 carriers bug
   （gitignored 载体在一次性 worktree 里不存在 ⇒ 检查器恒 NOT-EVALUATED）
   ⇒ **输入必须显式传，不能靠「它在那儿」。**

### §8.5 验收：不造新指标，重测同一组基线

**仪器与基线 2026-08-15 已建**（`manager-phase-goal.md` 🔭 观察项）：用会话动作记录（第三方可读的直接量）
逐轮对齐 cron 触发时刻算每轮覆盖率。**改后重测同样七个点。**
**⊢ 能取假的预测**：A23/A9 这类「独立一条」的义务覆盖率应从 15–61% 升至接近 B1 的 100%；
**若不升，结论是「搬家没解决问题」，⛔ 不是「还需要再搬一点」。**
