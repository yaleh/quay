# 综合：用单个 Claude Code 会话推进一个 goal 落地的方法

**日期**：2026-09-06
**证据来源（两半，各自独立取证）**：
① **一手**：本会话推进 `GOAL-001`（goal 机制启用与改造）的 36 轮 cron tick，11.5 小时，立案 11 条、判据 0/10 → 7/10。
② **跨会话**：`meta-cc` 检索 2026-08-30 → 09-06 全窗口 1638 个会话，筛出 6 个"单会话持续推进一批任务"形态
（`e721dbaa`/`f2536f55` 常驻 fan-in 监控 · `e04ad102` 其分叉 · `73939f36` 自驱闭环 · `d21c7f86` manager · `fc0adcc2`+`e8df4b6a` outer）。

**⚠️ 本文是【观察综合】不是规格**：标注为「假说」的条目样本不足，不得当作已确立结论引用。

---

## 0. 定位：会话不是产能，是保通与保真

窗口内 `tasks: 翻 <id> done` 提交共 **161 条**（按日 2/28/28/24/10/29/17/23）。
**常驻会话在 09-04 19:59 全部停摆后，09-05 仍落 17 条、09-06 落 23 条。**
⇒ 落地由**机械 driver + 一次性 worker 会话**产生，常驻 Claude 会话不在关键路径上。

本会话独立印证：推动的 5 期全部由 worker 落地，**驱动会话自身一行产品代码未改**；
它实际做的是**立案 · 诊断 · 解阻**三件事。

**⇒ 第一条方法是定位**：单会话的职责是「让机械路径不被挡住、且不撒谎」，不是「自己把活干完」。
把它当产能用，就会得到 `73939f36` 08-31 09:25 那次结果——宣布「同步机制完整落地 ✅」，
理由是"机制代码已上线"，而外核复核发现 `syncDevelopToDoc` **零非测试调用者**，任务被 retreat 加 AC4。
（相关性证据，非因果：09-03 只落 10 条却正是常驻会话在跑，故不能反推"常驻会话拖慢落地"。）

## 1. 骨架：每轮四件事 + prompt 自包含

跨 `e721dbaa`/`f2536f55` 390 轮与 `d21c7f86` 213 轮的共同做法：
**判据脚本、真值源、归因表全部写在每轮 prompt 正文里，并明令「不依赖上下文记忆」。**

理由是硬的：会话会被压缩、会分叉、会重启。**写进 prompt 的活得下来，记在上下文里的活不下来。**

本会话的 cron prompt 同构：读判据 → 读任务状态 → 按分期推进 → 一句话汇报。

## 2. 判据纪律：把判据挪到能取假的生产载体上

两边各被证明一次，且**两次都不是靠想清楚，是靠去读一个能取假的量**：

- `73939f36`：09:25 以"代码在 develop"宣布完成 ✗ → 12:45 真实接线 → 12:46 载体
  `.quay/doc-develop-sync.jsonl` 出现 `doc-develop-sync-ff-synced` ✓（终局判据是三条同时成立，含两分支双向 0）
- 本会话：每条 AC 的 DoD 写成「生产载体里有**实现落地之后**写入的记录」，
  并把**反例判据**写死进任务体——「把 fixture / 注入 seam 关掉后仍能通过，它才是测量」

配套三条：
- **真值源显式钉死并写明"为什么不能读另一个"**。`e721dbaa` 每轮写：
  `status 读源 = develop（git show develop:tasks/<id>.md），不读主检出 disk——主检出落后会把「已 done 但未同步」误算成 ready`。
- **判据词表要有"未评估"第三态**并报计数（`d21c7f86` 每轮 `criteria judged ①-⑥′ with 0 notEvaluated`）。
- **peer 的诊断是假说不是结论**：投递前先取自己的读数（`d21c7f86` 08-30 08:09 证伪 outer 的"2 tasks blocked"；09:08 更正其 merge 归因）。

## 3. 仪器会坏，且频率不低——但多数能自捕

窗口内 4 次 + 本会话 3 次 = **7 次**，其中 **6 次由会话自己在一两轮内捕获**：

| 实例 | 形态 |
|---|---|
| `d21c7f86` 08-30 08:27 | `grep` 命中的是**自己前面几条 grep 命令本身**（自匹配假阳性） |
| `e721dbaa` 09-02 22:32 | 把**滞后快照**当新失败（monitor 报 3 个 suite 红，实为数小时前的旧记录） |
| `f2536f55` 09-03 11:37 | 不信检查器的 `reason` 字段，去读原始日志——发现 reason 取的是**检查器标题行**，由此还原三条互不相同的真实失败 |
| 本会话 tick 14 | 判据抽取用 awk 只匹配 `criterion: \|`，而记录已变 `criterion: >` ⇒ 抽空 ⇒ `bash -c ""` 退出 0 ⇒ **抽不出判据被记成通过** |
| 本会话 tick 27 | `pgrep -af` 匹配到自己的命令行，污染在飞清单 |
| 本会话 tick 31 | 把"单相轮 PSI 为 null 的**设计行为**"误判为"仪器静默停摆" |
| `73939f36` 08-31 09:25 | **唯一没自捕的一次**（伪实现，3 小时后被外核推翻） |

**⇒ 唯一没自捕的那次，恰是判据落在"代码存在"而非"载体出现"上的那次**——与 §2 同源。

**两个可操作动作**：
- 引用一个计数之前，**先打印它命中的前 3 条实际内容**
- **计数为零时**，把谓词对着一个**已知为真的样本**干跑一次
  （本会话修 `AC-179` 时正是用它确认 `goal-card` 不命中是真阴性、而非管线坏了）

## 4. 立案纪律：任务要能通过机制自己的闸

本会话一手教训，**3 次各赔掉一个周期**：

| 卡点 | 表现 | 修法 |
|---|---|---|
| Touches 用 glob（`goals/AC-1[4-6][0-9]-*.md`） | `touchesNarrow: false` ⇒ `eligible: false`，卡在 todo 不晋升 | 待创建文件标 `(new)`（该标注跳过窄度检查）；多文件逐条精确路径 |
| 漏了新增文档的注册面 | 新增 `orchestration/SPEC-*.md` 须在 2 处声明 `reference-doc`，否则 `spec-declaration-point-check` **全库红** | 立案前 grep 该文件类型的注册面 |
| 漏测试文件 / self-touch | 门直接拒 | 立案模板固定包含 |

**⇒ 立案不是写清楚就行，是要让它通过晋升门。**
`task_write` 之后**立刻**跑一次 `ready-pool-check --json`，看自己那条的
`touchesNarrow / eligible / depsReady / fourArtifacts`。本会话从第 3 次才养成这个习惯，前两次都赔了周期。

## 5. 阻塞处置决策树

**先分类再处置——混了就空转。**

| 类型 | 处置 | 证据 |
|---|---|---|
| **判据写错** | 改判据 | 本会话改 `AC-179` 的 `head -1` 不稳定实例选择（本机同时 5 个 serve 实例，取到哪个随进程列表顺序漂移） |
| **与本任务无关的 flaky** | **立案 + `depends_on` 显式门控，⛔ 不要重试** | G6 在门控前已空转 **6 次全量 suite（约 2 小时）**，而空转本身在加剧饱和；门控后实测 `depsReady=False, eligible=False` |
| **全仓级红** | 立 `delivery-critical` 标签 | 那是唯一真正的优先级轴（`slot-refill.ts:1030`，排序键 `blocking_suite → delivery_critical → id`）。**只对未派发任务有效**——给在飞任务补标签只会进 `delivery_critical_in_flight`，那是专门检出"事后补标签冒充优先级生效"的负控制 |
| **干完了但没落地** | 语义兜底 fan-in | **死角**：AC 全勾 ⇒ pool 按 `not-yet-flipped` 把它排除出派发，而翻 done 又是错的（代码不在 develop）⇒ **两条路同时断** |
| **"等另一层去做"** | **下一轮必须用直接量核对该层是否活着并动过**，否则收回自办 | `e721dbaa` 09-02 20:11→22:11 连续 **7 轮字节完全相同（422 字节）的报告**，处置写着"归 outer/driver reconcile"，而 manager 已停摆、outer 无人投递 ⇒ 无人接；解法出现在会话自己动手的那一轮 |

## 6. 改共享配置解阻，先算代价对比

本会话按人授权把 `drivers.yml` 的 `worker.cap` 5→2 缓解 flaky，
结果引入**确定性全仓红**：`cap-from-gate` 的 `effective_cap` 读 yml，
而 `FIXED_EFFECTIVE_CAP = defaultDriverConfig().worker.cap` 与其测试读**代码默认值**——
同一个量两个来源，yml 与默认值相同时恒等、缺陷不可见，一改立刻分叉。

**⇒ 用确定性阻塞换概率性阻塞是净亏。**
改任何共享旋钮前先问：它会不会把一个"有时挡"变成"总是挡"；**改完立刻跑相关测试，别等 fan-in 替你发现**。

## 7. 节奏与终止条件

**固定周期对"落地事件"过密**：`e721dbaa`+`f2536f55` 的 183 份四行摘要中
**161 份（88%）报 LANDED 0**；本会话 36 轮里约 29 轮"无变化"。两边收敛到同一数量级。
（该计数是"当前监控队列内的累计落地数"，队列换血时归零，故它意味"本轮无新增落地"而非"全局零落地"。）

**更要紧的是终止条件**：
- `73939f36` 收到的目标句带「**直至这一同步机制有效运转起来**」——终止条件是**可观测的机制状态**而非任务状态；
  它闭环后主动清掉自建的 Monitor 与冗余定时（08-31 15:22「我不再逐条响应例行 churn」→ 15:32「监控与冗余定时都已清理」）。
- `e721dbaa`/`f2536f55` 的 prompt 只有"报告 + 主动推进"、**无终止条件** ⇒ 全收敛后仍每 20 分钟产同一份报告（§5 的 7 轮空转）。

**⇒ 常驻 prompt 必须带一个可观测的终止/降频条件。**

**〔假说，样本不足〕** 事件驱动（`Monitor` 持久订阅 + 长兜底 `ScheduleWakeup`）优于固定周期——
仅 `73939f36` 一个样本、无对照。

## 8. 单会话推 goal 的真实风险形状

本会话产出分布：

| 批次 | 时段 | 条数 | 落地 |
|---|---|---|---|
| 计划内分期 G1–G5 | 05:18–09:05 | 5 | **5/5 done** |
| 发现型阻塞（flaky×2 · 分相记账 · 棘轮 · 双来源 cap） | 12:27–16:43 | 5 | **0/5** |

**计划内的全落，发现型的一条没落**，且它们互相串联成一条链
（负载敏感 flaky → 闭包棘轮全仓红 → 驱动会话自己引入的 cap 红）。

**⇒ 真实风险不是"推不动计划"，是【沿途发现的债形成新的串行链，把 goal 的剩余部分堵在后面】。**
本会话判据停在 7/10 达 6 小时，全部卡在这条链上。

## 9. 未被守护的薄弱面（观察，非本文范围）

**会话身份没有任何机制守护**：
- `e721dbaa` 与其分叉 `e04ad102` 被**同一个 cron 同时投递 15.6 小时**（48 轮 × 2，时间戳逐条相同），两个 agent 并行对同一 pool 做同一份 triage
- 两个 `agentName: quay-outer`（`fc0adcc2` / `e8df4b6a`）并存约 34 小时，各自收消息

两处都**没有任何检查报红**——它们与"一切正常"同形。
manager 的锚哨兵只验 `CronList 恰 1 条`，**验的是 cron 条数，不是接收方会话数**，
因此对"一条 cron 投给两个会话"结构上不可能报警。
