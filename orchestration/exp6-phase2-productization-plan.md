## 1. 交付物的定义——人 2026-08-03 09:4xZ 给出的三条硬判据

**这三条推翻了本文件原来的定义。** 原定义是「把内核和 tick 文档装进目标项目」，
而那等于**从 quay 的开发目录复制文件**——我已经这么干了一次（archguard，提交 `c8f612f`），
**它不满足第 3 条**。

| # | 判据 | 现状 |
|---|---|---|
| 1 | 用**尽可能常见的方式**从安装包或通用包管理工具装到 **user scope** | 包名 `quay`，`bin: {quay: ./dist/quay.js}`——**可全局装** |
| 2 | 在一个**从未用过 quay（或用过旧版）**的项目上，用**几条 README 里列得出的命令**配好、跑起来，**真正开始**和本仓过去十几小时一样的持续开发 | **不满足**——README 没有这条路径 |
| 3 | **运行时不得依赖本项目开发环境目录下的文件** | **部分满足**（见下） |

### 第 3 条的实测：配置面已经是冷的，方法论面完全不在包里

archguard 的 `.quay/config.yml` **完全自足**——路径全相对，
`mcp_entry: ["quay-native","mcp"]` 走 PATH，不引用 `/home/yale/work/quay` 的任何东西。
它甚至已经有 `loop:` 段（`board`/`gates`/`stop: until(.halt)`/`concurrency: 4`）。**这一面是冷的。**

**不冷的是方法论面。** `packages/quay/package.json` 的 `files`：

```
["README.md","CHANGELOG.md","LICENSE.md","bin","src","dist"]
```

⇒ **两份 tick 文档、`scripts/heavy-op-token.sh`、`scripts/resource-gate.sh`、
`scripts/test.sh` 的判绿约定——一个都不在包里。**

一个照 README 走的人拿不到它们。我给 archguard 装上它们，用的是 `cp`。
**那不是冷启动，是热拷贝**，而热拷贝证明不了任何可交付性。

### 因此真正的交付物是三件，不是「更多文档」

1. **把机制打进包**——tick 文档 + 那几个脚本进 `files`，
   并有一条命令能把它们**释放到目标项目**（`quay loop init` 之类）
2. **README 的冷启动小节**——从 `npm i -g quay` 到「循环跑起来了」的**完整命令序列**，
   条数少到能列在 README 里
3. **一次真实的冷启动验证**——在一个**没有 quay 开发树可复制**的环境里照 README 走通。
   **这条是唯一能证明前两条成立的**；archguard 那次不算，因为我用了 `cp`

### 已知的诚实限度

archguard 那次冷启动**仍然有价值**——它验证的是**机制能不能在第二个项目上产出真活**
（那里 CI 连红一个月、`npm test` 300s 超时、lint 480 errors，都是真的）。
它**不验证**可交付性。两件事不要混。

## 2. 硬约束：这台机器跑不下第二套循环

**必须先说这条，它决定计划能不能按序执行。**

实测：本仓一套循环在 4 核上已使 CPU 压力常在 85–95、单套件 16 进程（4.25× 超订）。
**再起一套双层循环（1 内层 + N subagent + 套件）会让两边都饿死**——今晚两个套件并发就把压力推到 96.62。

三个选项，**需要人裁定**：

| | 做法 | 代价 |
|---|---|---|
| **A** | 冷启动试验期间 `.halt` 暂停本仓循环 | 本仓停 4 小时 |
| **B** | 等硬件迁移（12 核 / 48 GB）后再做阶段 3–4 | 阶段 2 推迟 |
| **C** | 只做阶段 0–2（定义与打包），阶段 3–4 的真实验证延后 | 交付物未经真实验证 |

**建议 A**：本仓此刻队列近空（只剩 sigma + tmpdirs），是暂停的好窗口；而**未经真实冷启动验证的交付物没有价值**——今晚全部教训都指向这一点。

## 3. 分阶段计划（约 12 小时）

### 阶段 0：对齐阶段 1 记分卡（约 1 小时）

- 逐条核对 exp6 阶段 1 的 21 个 AC，**用实测证据勾或明确写「未满足及原因」**
- 特别处理 AC7（连续 12 小时无人值守）——今晚人多次介入（裁定、纠偏），**严格说未满足**，
  应如实记为「未满足：人介入 N 次，每次原因见 tick-log」，而不是含糊带过
- **产出**：一份可信的阶段 1 记分卡

**验收**：21 个 AC 每个都有 `[x]` 或 `[ ] + 未满足原因`，零个含糊

### 阶段 1：测出冷启动内核（约 2 小时）

- **重跑 `runtime-usage-inventory.ts`**——退役删了 51 个文件，旧的 live 集合已过时
- 对每个 `live` 脚本再分一次类：**普适机制** vs **本仓专属**
  - 判据不是印象：普适 = 不引用 `experiments/`、不引用本仓任务 id、不依赖 exp5 遗留
- **产出**：`docs/delivery/cold-start-manifest.md`——文件清单 + 每个文件「为什么它在内核里」

**验收**：清单里每个文件都有一句理由；「以防万一」不是理由（今晚退役任务的 DoD 同款要求）

### 阶段 2：切分 tick 文档（约 3 小时）

两份 tick 文档共 573 行，而散文审计实测：**内层那份 36 条决策性语句里大部分是本仓事故史**。

- 用 `normative-prose-audit.md` 的分类切成两半：
  - `mechanism`（普适，随交付走）
  - `incidents`（本仓事故日志，留下）
- **`<!-- unmechanized: -->` / `<!-- unmechanizable: -->` 标记随机制半一起走**——
  新项目需要知道哪些规则是有意不机械化的
- **产出**：`plugin/loop/tick-inner.md`、`plugin/loop/tick-outer.md`（普适半）

**验收**：把普适半交给一个没读过本仓历史的读者，他能据此启动循环——
**用一次真实的冷启动检验，不是自评**

### 阶段 3：真实冷启动 archguard（约 4 小时）

**这是唯一能证明交付物成立的一步。**

1. `.halt` 暂停本仓循环（选项 A）
2. 把内核 + 普适 tick 文档装进 archguard
3. 在 `archguard-2` 用实测配方启动内层
4. 外层可以是本会话（我）或另起——**建议本会话，因为外层的 tick 文档也在被验证**
5. **跑满 2 小时**，记录：完成任务数、停摆次数与原因、需要人工补的东西

**验收（硬）**：
- **至少 1 个任务由移植后的循环端到端完成**（建任务 → 派发 → 测试 → 合并 → 收尾）
- 每一次「需要人工补」都记进差异报告——**那就是交付物缺的东西**

### 阶段 4：差异报告与回填（约 2 小时）

- 阶段 3 里每一处人工补的动作 → 回填进内核或 tick 文档
- **明确记录哪些是 archguard 特有、哪些是交付物缺失**——两者处置不同
- **产出**：`docs/delivery/cold-start-gaps.md`

**验收**：差异清单里每条都标注「已回填 / 属目标项目特有 / 明确不做及理由」

## 5. 时间分配与风险

| 阶段 | 时长 | 最大风险 |
|---|---|---|
| 0 记分卡对齐 | 1 h | 低 |
| 1 测内核 | 2 h | 低（工具现成） |
| 2 切分文档 | 3 h | **中**——「普适 vs 本仓」的判定容易主观 |
| 3 真实冷启动 | 4 h | **高**——可能发现内核缺件，需回到阶段 1 |
| 4 差异回填 | 2 h | 中 |
| **合计** | **12 h** | |

**最大的单点风险是阶段 3**：如果冷启动失败，阶段 1–2 的产出需要返工。
**这是设计如此**——真实验证放在前面，比放在最后交付时才发现要便宜得多。
