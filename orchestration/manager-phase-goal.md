**为什么这不是同一件事**：产品化的判据是「装得上、跑得起来」（静态、一次性）；

而人开的维度**不需要疼**。⇒ 没有人时不会停止发现，会**渐近**——
把硌人的地方修完，然后在从未打开过的每根轴上报绿。
（完整测量与生成器见 `SYNTHESIS-axis-generation-2026-08-05.md`，已转外层。）

#### ⚠️ 2026-08-08 08:4xZ：我给出的判别式是错的，已更正（必要条件当成了充要条件）

**我 08:2xZ 发给 outer 的机械测试**：

```

  merge-base vs integration = 5036647e
  但：是 integration 的祖先 = YES  ⇒ 它是【已被 fan-in 进 integration】，不是【从 integration 切】
      分叉点 5d7c96f4 是 develop 的祖先 = YES，是 integration 的祖先 = YES
```

**根因**：`merge-base` 不等 是「从 integration 切」的**必要条件**，但同样被
「已合入 integration」满足 ⇒ **我把一个必要条件当成充要条件写成了判据。**

**更正后的判别式（看【分叉点】，不看 merge-base）**：

```bash
b=<task 分支>
fp=$(git rev-list --first-parent "$b" ^develop | tail -1)   # 分支第一个独立提交
p=$(git log -1 --format=%P "$fp" | awk '{print $1}')        # 它的父 = 分叉点
git merge-base --is-ancestor "$p" integration   # 必须 YES
git merge-base --is-ancestor "$p" develop       # 必须 NO   ← 关键就在这一条
```
**「分叉点在 integration 上但不在 develop 上」才是「从 integration 切」。**
两条都要，只查前一条同样有假阳性（公共线上的点对两者都是祖先）。

而它恰恰是最常发生的那种情况。**代理量与目标量之间是蕴含关系还是等价关系，是要单独验的。**

### AC25（机制·上游追查）：槽未满即追上游，且当轮处置，不等未来机制（人 2026-08-08 12:0xZ）

**人的原话**：「outer 的 tick 应该检查 inner 的状态：**如果 inner 的槽不满，就要检查上游有没有问题**
——应该**积极处理 inner 提到的任务的问题**，而不要等未来的机制。」

**判据（对 outer 每 tick 可机械核对）**：

```
触发：in-flight < cap（槽未满）
动作：
  1. 取 slot-refill 的 recommended 与 no_refill_reason
  2. 对每个被 inner 退回/判为不可做的候选，【当轮给出处置】：
     翻状态 / 退回 todo / 作废 / 修前提 —— 四者之一
     **不得只立案后把它留在 ready**
  3. recommended 为空或全部不可做 ⇒ 逐层追上游：
     供给（AC 全勾未翻转？）→ 采样（cap 是否落在回退默认值？）→ 晋级（pool<floor 是否被积压顶住？）
判读：**槽未满 且 本轮无任何处置动作 ⇒ 违规。**
```

**为什么「不得只立案」是这条的要害**：2026-08-08 11:50 实测的正面例子与反面例子在同一件事上——
outer **看见了并且诊断接得完整**（`aac97a8f` 的提交信息自己重数过「17/21 ready are AC-complete」、
修法也记准了），**但它立的是一条 `todo` 任务，那 19 个积压一个都没翻。**
⇒ **修机制 ≠ 清积压**：机制修好后新增的不再堆，**已经堆着的不会自己走**；
积压不清 ⇒ inner 下一轮拿到同一批 ⇒ 再核一遍、再退回。**今晚已这样转过至少三轮。**

**而且它会形成自我指涉的死结**（实测）：
```
修积压的任务 status=todo ⇒ 要靠晋级 ⇒ 晋级判据 pool < floor ⇒ 24 > 20 ⇒ 不晋级
而 pool=24 之所以这么大，正因为里面 19 个是已完成未翻转的
⇒ 积压把 pool 顶在 floor 之上，从而阻止了修积压的那条任务被晋级
```
**⇒ 修盘子的任务被盘子堵在门外。** 所以顺序是死的：**先清积压 → pool 掉到 floor 以下 →
晋级自然触发 → 修机制的任务进场。反过来不行。**

**manager 侧的核对**（我每 tick 做，属 AC23 的层间检查）：
采样 `in-flight`、`cap`（**用 `cap-from-gate.sh` 的 `effective_cap`，不用回退值**，见 ②i-F）、
`slot-refill` 的 `recommended`；若槽未满，查 outer 本轮 tick 有没有出现上述四类处置之一。

**⚠️ 不覆盖什么**：本条不要求「槽必须满」——可能确实无可做之事；
只要求**槽未满时上游被追查过、且被退回的候选当轮离开可派发集**。

### AC22（机制·衔接）：「收尾」与「下一次派发评估」之间有机械衔接

**判据（2026-08-08 12:0xZ 泛化——原来是枚举，枚举会漏）**：
**任何使派发【由不可能变为可能】的状态变化**之后，**在无上层介入的情况下**，
下一次派发评估在 ≤5 min 内发生。
**为什么从枚举改成一般形式**：原文枚举「fan-in / 翻状态 / 子代理返回」，
而今晚第二个实例是**上游积压被清通**（4 个 `ready→done` + 一次 `todo→ready` 晋级）——
它恰好落在「翻状态」里，**但下一次未必**：套件转绿、依赖落地、资源档位回升、
锁释放，都同样「使派发由不可能变为可能」，而枚举一条都没写。
⇒ **判据锚在【状态变化的效果】上，不锚在【事件的名字】上。**
**取证**：收尾时刻（git/遥测）与下一次派发评估时刻之差；且该次评估**不得**由
上层 send-keys 触发（同 AC21(b) 的分辨要求）。
**今晚两个实例，都不满足**：
- ① reporter `10:49:27` 收尾 → 至 `11:23` 无任何驱动。
- ② outer `12:00:43` 清积压 4 个 + `12:03:28` 晋级 `closure-detection`（**上游清通**）
  → `12:06:36` 实测：outer idle、inner idle、in-flight 0/cap 5、`recommended=5`、无套件
  ⇒ **5 个空槽 + 5 个可派候选全闲着，而 inner 下次自驱约 12:24（还有 18 分钟）**。
  **靠 manager 看见了才提醒** —— 而「靠人看见」正是 AC20 要消除的东西。
**⇒ ② 比 ① 更清楚地指出缺口位置**：outer 上游动作全对，**差的是最后一步「叫 inner」**。
**⚠️ 不覆盖**：不要求那次评估**必须派发**（可能确实无可派发）；只要求**评估发生过**。

### AC24（机制·池质量）：派发不会反复落在不可做的任务上

**判据两条**：

### 三条纪律（对我自己，防今晚的错误在新目标上重演）

1. **量自驱信号，不量活动信号**（AC21(b)）——今晚同一错误连犯两轮。
2. **每条 AC 明写「不覆盖什么」**——今晚多次遇到「标题点两个缺陷、AC 覆盖一个、
   另一个没有主人」，包括这条被我引为反例的 done 任务。
3. **取证脚本不得预写结论行**——今晚我在自己现写的取证脚本里**三次**把判定写成常量
   （`⇒ 全 0 = 零立案`、AC19 (ii) 空值判定、`reanchor_cycles=0 ≥ 1 通过`），
   三次都与实际数值相反。**判定必须由数值计算得出，不得是 echo 常量。**
