## AC

**判据一律可执行、可复核。** 「感觉进展顺利」不是 AC——这是本仓自己的标准（ADR-004）。

- [x] **AC1（已达成 2026-08-03）**：推送授权的决定**被人裁定并记录**。
      **裁定**：push 与 release **仍须人显式触发**（「未来我可能会授权自动 push & release」）。
      记录在 `orchestration/escalations.md`，附实测的触发面（推 master 只跑 CI，不产生 release；
      只有 `v*` 标签才 release；`publish-plugin-dist.yml` 的 `workflow_dispatch` 只重建 `dist-plugin`、不 release）。

- [ ] **AC2（2026-08-03 重新解冻）**：**存在一个可安装物含有本阶段的机制**。
      **人裁定：基于本地 build 执行安装即可，不必直接复制源文件——那已经足够「冷」。**
      ⇒ 这条**不再依赖推送**，回到我与外层可达成的范围。
      判据：`bash plugin/scripts/publish-dist-branch.sh --branch <local>`（**不加 `--push`**）产出真实 bundle
      （脚本自身在产物为空时拒绝发布），再从该产物安装，安装出来的 plugin root 中
      `scripts/quay-init.sh` / `scripts/inner-state.sh` / `loop/orchestrator-loop-tick.md` 三者齐全。
      **关键区分**：被测物必须是 **build 出来的产物**，不是 `cp` 过去的源文件——
      archguard 第一次冷启动用的就是 `cp`，那不构成可交付性证据。
      *（推送与 release 仍须人显式触发，那条裁定未变；它现在只影响「别人能不能装到」，不影响本 AC。）*
      判据（不看工作树，看可安装物）：`git cat-file -e <marketplace 指向的 ref>:plugin/scripts/quay-init.sh` 成功。
      现状：远端 `dist-plugin` 落后 master **2424 个提交**，`quay-init.sh` / `inner-state.sh` /
      `loop/orchestrator-loop-tick.md` **一个都不在**。
      附带已知事实：npm 上 `quay` 这个名字**是别人的包**（mattstyles，"Turns keypresses into event streams"），
      所以 npm 路径不能成为「通用包管理工具装到 user scope」，plugin 路径是唯一成立的形式。

- [x] **AC2b（已达成 2026-08-03）**：**那一次人工动作是最小且已验证的**——
      命令序列写在 `escalations.md` 里、每条的触发面经实测（不是读文档推断）、
      且不含任何会意外产生 release 的步骤。落地于 `escalations.md`。
      *（此 AC 关乎「让别人装得到」，与 AC2 的本地验证是两件事，都要。）*

- [ ] **AC3（随 AC2 解冻）**：archguard **用 build 出来并安装的那份**重做冷启动（`quay-init --loop`，**不是 `cp`**），
      并产出一份区分「交付物缺失 / archguard 特有 / 已回填」的差异报告。
      判据：archguard 仓中存在该报告，且其 git 历史显示机制文件**来自 plugin 安装**而非从 quay 开发树复制。

- [ ] **AC4**：**没有项目饿死另一个**。
      判据：本阶段内不出现两个项目同时跑重活而未经 `heavy-op-token.sh` 串行化的情形；
      每个管理者 tick 记录当时的 `cpu some avg10`，全程无连续两次 tick 超过 80。

- [ ] **AC5**：**角色纪律**——管理者不做外层的活。
      判据：本阶段管理者名下的提交中，**写任务体/AC/DoD 的次数为 0**，
      跑项目验证的次数为 0（跨项目共享机件除外，那是明写的唯一例外）。
      现状：**已有一次越界风险**——`plugin/scripts/outer-liveness.sh` 是我写的，
      但它是跨项目机件，落在例外内；本阶段起按此判据自查。

- [ ] **AC6**：**每个外层都有自己写下的目标与 AC**，在各自仓中可读。
      判据：`quay` 与 `archguard` 各自仓中存在 outer 自己写的目标/AC 文件，
      且**不是我替它们写的**（git 作者与内容出自该 outer 的会话）。

- [ ] **AC7**：**阻塞主目标的升级项在一个 tick 内上报，不进「攒着」队列**。
      判据：`manager-tick-log.md` 中，凡标记为阻塞主目标的升级项，其上报 tick 与发现 tick 相同。
      **这条是今晚的教训**：推送授权昨夜被我当成常规项攒着，而它已经是主目标的唯一阻塞。

- [ ] **AC8**：**管理者自己的仪器是对的**。
      **第二次修正（2026-08-03，人指出）**：外层跑完一次操作后空闲等输入，我的监视器**没看见，
      而且按设计看不见**——进程活着、刚提交过，三个事件全部静默。
      根因是**心跳信号选错了**：我用「有没有新提交」判推进，而循环的心跳是「tick 有没有按期跑」，
      且 fan-in 带来的提交还会把基于提交的计时器重置。
      已补事件 4 `OUTER-LOOP-OVERDUE`（tick 日志 mtime 超 45 分钟未更新且项目未暂停）。
      **第三次修正（同日，人追问「按设计你什么时候才能观测到」）**：事件 4 仍是**滞后**指标，
      而人的要求是「可以接受让 outer 等待，**但应当是我及时知道并决定**让它等待」。
      已补事件 5 `OUTER-IDLE` / `OUTER-RESUMED`——相邻两轮 pane 哈希相同即空闲，
      **在转换发生后一个轮询周期（60 秒）内报出**。
      **判据用真正控制验过**：造一个由测试控制忙闲的探针 pane，确认事件真的触发；
      过程中连着踩了三个装置错误（探针不含 `claude` 故被判为不存在、`sed` 缓冲吞掉输出、
      `/proc` CPU 增量分离度太弱），**每一个都是「干跑没有输出」原本会掩盖掉的**。
      判据：监视器的目标经过实测核对（不是「挂上了」而是「挂的是对的东西」）。
      **这条也是今晚的教训**：我挂了 18 小时的监视器盯的是内层而不是外层，
      是人问起才发现——一个盯错东西的 monitor 和一个正确的 monitor 从外面看一模一样。
