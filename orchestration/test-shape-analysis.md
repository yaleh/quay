# 测试形态分布分析（2026-08-02，外层）

**问题**：现有测试中多少是对整个 cli/server/mcp-server 的测试，多少是对单个模块的测试？分布是否合适？

**方法**：对 `scripts/test.sh --list-files` 的 160 个文件（已按 realpath 去重）静态分类。
判据是**测试如何触达被测代码**：跨进程/协议边界（`execFileSync`/`spawn`/`connectStdio`/`startServer`）
算「进程」，直接 `import` 实现模块算「模块」，两者都有算「混合」。

分析过程中修正了分类器的两个缺陷，记录以免复用时重犯：
（a）第一版正则要求 import 路径与 `import` 关键字同行，**漏掉全部多行 import**，把大量 mixed
误判成 process（`proposal-convergence.test.mjs` 是最明显的一个）；
（b）`-E` 模式下写了 `\|`，那是字面竖线不是选择，导致一组入口统计全为 0。

## 结果

160 个文件 · 50,915 行 · 7,349 处断言

| 访问方式 | 文件 | 断言 | 行数 |
|---|---|---|---|
| 只走模块 | 70 (44%) | 1,797 (24%) | 11,780 (23%) |
| 只走进程 | 32 (20%) | 1,279 (17%) | 10,891 (21%) |
| 混合 | 58 (36%) | 4,273 (58%) | 28,244 (55%) |

按访问点计数：**进程边界 396 次 vs 直接 import 189 次 = 2.1 : 1**。

| 组 | 文件 | 进程边界 | 直接 import | 比值 |
|---|---|---|---|---|
| product | 87 | 266 | 100 | **2.66** |
| engine | 60 | 126 | 70 | **1.80** |
| governance | 13 | 4 | 19 | 0.21 |

入口被提及的次数（一个调用点可能同时匹配多个模式，**不是划分，只作比例参考**）：
native CLI 309、core CLI 191、方法论脚本当 CLI 90、MCP 握手 58、web server 56、github CLI 48。

## 分布是否合适

**product 的 2.66:1 是站得住的。** quay 交付的就是 CLI + MCP server + web UI，用户依赖的契约正是
这三个表面。ADR-019 的 `dist-verify-node-floor` 与 B5-1 把测试改走 `dist/quay.js` 都强化了同一条
理由：**测用户真正运行的产物比测只存在于本仓库的源码更接近真实契约**。这不只是提速，是更正确。

**engine 的 1.80:1 是可疑质量所在**，但没有想象中严重。这些方法论脚本确实**也被 workflow 当 CLI
调用**（`node --experimental-strip-types plugin/scripts/foo.ts --json`），所以其 argv 解析与 JSON
输出形状本身就是契约，值得端到端测。

**真正的缺陷不是比值，是没有政策。** 没有任何文档写明「每个入口保留 N 次真实端到端检查，其余走
import」。唯一存在的规则写在 `gap-tests-use-cli-where-module-import-suffices` 的任务体里
（「保留 ≥1 次真实端到端调用」），那是为**一个任务**写的，不是仓库规则。当前分布是累积出来的，
不是选出来的。

## 对当前提速工作的直接含义

396 次进程边界 × ~1.4s（换 bundle 后的单次成本）≈ **550s 的 CPU**。套件 489s 墙钟 × 并发 8
≈ 3,900s 总 CPU（**这是估算，待 `gap-suite-cost-model-is-wrong-optimizations-buy-nothing` 的 AC2
实测**）。若成立，**进程边界只占约 14%**。

这与实测吻合：118s 的单文件节省只换来 2s 墙钟。**结论：进程 vs 模块这个问题不是套件提速的杠杆。**
继续削减端到端测试买不到多少时间，成本在别处。

## 一个顺带发现：24% 的测试代码在 `node:test` 之外

**34 个文件（21%）、12,204 行（24% 的测试代码）完全没用 `node:test`**，而是手写的
`makeAssert()` + `failures` 计数器 + `process.exitCode = failures === 0 ? 0 : 1`。

失败**会**传播（退出码正确），所以这不是静默洞。但它有三个后果：

1. 这 **1,235 处断言不在「2135 tests」这个数字里**——我们报告的测试数系统性偏低
2. `--test-concurrency=8` **无法在文件内并行**它们，每个文件是一个不可分割的整块
3. **每文件耗时归因到此为止**——成本模型任务想按文件拆解成本时，这些只能是一个个黑盒

而且它们恰好是最大的几个文件：`serve.test.mjs` 1,800 行、`cli.test.mjs` 1,744、
`mcp-server.test.mjs` 1,652、`prepare-milestone-convergence.test.mjs` 2,287。
**成本模型任务在这四个文件上拿不到细粒度数据**，这是它必须知道的前提。

## 是否该统一测试框架、重构测试（2026-08-02 外层判断）

**要拆成三个问题，它们的成本效益差一个数量级，不该打包决定。**

### 1. 找出耗时的测试 —— 必要，而且便宜到不需要动框架

四个黑盒里有三个把**每一处断言都汇聚到同一个函数**：`cli.test.mjs` 的 `makeAssert()`、
`serve.test.mjs:61` 和 `mcp-server.test.mjs:121` 的 `assert(cond, msg)`。在那**一个**函数里记
距上次断言的耗时，整个文件的逐断言归因就有了——**每文件约 5 行，零断言改动**。间隔长的地方就是
进程 spawn。`cli.test.mjs` 另有 19 个 `block` 函数，块级归因白送。

已写进 `gap-suite-cost-model-is-wrong-optimizations-buy-nothing` 的 AC1b。

### 2. 统一框架 —— 现在没有依据，且现有证据倾向于「不值得」

转换的**速度**理由只有一个：`--test-concurrency` 能在文件内并行。但那只在套件**延迟受限**
（少数长文件主导）时才有回报。而实测 **118 s 的单文件节省只换来 2 s 墙钟**，这正是延迟受限的
**反证**。若是吞吐受限，把整块拆成子测试只是重新分配 CPU，不减少 CPU。

**判定规则**：等成本模型数据，**只转换它证明确实压在关键路径上的那个文件**。一个，不是 34 个。

### 3. 重构 —— 只有一件现在就该做，理由不是速度而是治理

报告的测试数漏掉 1,235 处断言。于是
`gap-test-suite-has-no-layer-grouping` 的 AC11「测试数不减」**可以在删掉手写断言的同时被满足**
——这是一条我们正在依赖的 AC 上的治理漏洞。便宜的补法：让每个手写 harness 结束时打印
`# assertions: N`，`scripts/test.sh` 汇总。**一处断言都不用碰。**

### 明确不做：34 文件、12,204 行的整体迁移

三条理由：

1. **没有实测的速度收益**——见第 2 点，证据反向
2. **转换过程弱化断言的风险是真实的**。本仓库已有先例（RED test 被静默、golden replay 被当作
   已接受基线）。12,204 行的机械改写正是那类风险最高的作业
3. **它会吃掉本该用于建立持续无人运行的 12 小时窗口**。ADR-021 原则 1 正是针对这个——
   元机制不该比它服务的对象更重

### 一个核实后收回的说法

我一度准备论证「手写 harness 丢失失败隔离」。**它没有**：`makeAssert` 只计数不抛出，所以断言失败
之后剩余断言照常跑，185 处一个不少。只有**真正的异常**才会经 `main().catch` 跳过剩余块。
这个差别比我初判的窄得多，**不构成转换的有力理由**。
