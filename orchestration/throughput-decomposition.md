# 内层吞吐率的真实成本分解（2026-08-02，外层实测）

**问题**：内层吞吐率不高，直觉归因是「等待测试执行」。

**方法**：解析内层会话的完整 transcript（`82ecfb6a-…jsonl`，10.3 小时），把 `tool_use` 与
`tool_result` 按 id 配对得到工具执行时长；把「内层最后一次活动 → 下一条外层指令」的间隔计为空转。

分析过程中修正了两个自身错误，记录以免复用时重犯：
（a）第一版把 `system`/`user` 条目**之后**的间隔当成「用户时间」——那其实是模型在工作的时间，
归因方向反了；
（b）第一次选错了会话文件（`8e4b1f78`），它对 `B5-1` 零命中。**在得出「测试只占 6%」这个结论前
先做了这个校验，否则整份分析都是对另一个会话做的。**

## 结果

| 去向 | 时长 | 占比 |
|---|---|---|
| **空转——停下等外层裁定** | **5.1 小时** | **49%** |
| 全量套件（35 次） | 82.3 分钟 | 13% |
| 其它 Bash（563 次） | 68.8 分钟 | 11% |
| 范围化测试（47 次） | 13.4 分钟 | 2% |
| 实际模型生成（余量） | ≈2.5 小时 | ≈24% |

**37 次停摆。最长几次：26、22、21、21、19、17 分钟——全部贴着 20 分钟，即外层 tick 间隔。**
平均每次等 8.3 分钟。

**测试合计 15%，不是瓶颈。** 直觉归因错了。

## 排序后的杠杆

### 1. 外层延迟 —— 5.1 小时（49%），最大的一个

三条路，效果依次递增：

- **已做**：`orchestration/watch/inner-state.sh` 挂成 persistent Monitor，检测延迟从 ≤20 分钟降到
  ~1 分钟。**但它的 `IDLE` 是代理信号**（遥测 `inProgress` 为空），37 次停摆里只覆盖一部分
- **待做**：[[gap-no-explicit-blocked-signal-from-inner-layer]] —— 内层主动写
  `.quay/inner-blocked.json`，存在性信号，覆盖全部停摆，且**顺带把空转时长变成可计量的数**
- **更根本：减少停摆次数，而不只是缩短每次等待。** 10.3 小时停 37 次 = 平均每 17 分钟停一次。
  其中相当一部分问的是「下一步派发哪个」「A 还是 B」这类**在给定政策下内层本可自决**的事

### 2. 预授权 —— 把「问」变成「按政策自决 + 事后报告」

当前内层的默认是**凡有分歧就停**。这在建立信任期是对的，但它是 49% 空转的直接来源。

可以立刻预授权的一类：**后果可逆且已设时间盒的选择**。例如「A 修复 / B 回退」——B 是可逆的，
时间盒已定，内层完全可以自己选 A、超时自动落到 B、事后报告，不必停下问。

**不可预授权的**：范围变更、合并决定、与既有决定冲突的取舍。这些继续停。

### 3. 测试 —— 95.7 分钟（15%），真实但次要

- `scripts/test.sh --for-task <id>` 实测 **68s vs 全量 489s（7.2 倍）**，机制已存在，
  内层 tick 第 91 行已要求用它，实际用了 47 次 vs 全量 35 次——**还有一半没换过来**
- 它会 fail-closed：Touches 解析不出测试文件时拒绝运行（实测某任务 0/6 解析 → 拒绝）。
  这是对的，但意味着 Touches 写得不好的任务只能回退全量
- **全量套件应移出关键路径**：合并前跑一次即可，且可以后台跑、同时开始下一个任务

### 4. 并发 —— 当前未使用

工具调用统计里 `Bash×693 / Edit×178 / Read×157`，**没有 `Task`/`Agent` 进前六**。曾经有过
3 个 subagent 并发的一批（每个约 40 分钟，并行完成），之后退回串行。其中一部分是外层的裁定
（B5-1/B5-2 因 `checkTouchesPair` 重叠必须串行），但串行之后没有重新组织并发批次。

## 量级估计

若外层延迟从平均 8.3 分钟降到 ~1 分钟，10.3 小时里可回收约 **4.5 小时**——**吞吐率大致翻倍**。
测试的全部优化空间加起来不到 1.6 小时，且其中大部分是必要的验证。

**先修延迟，再修测试。** 顺序反了会把力气花在 15% 上。
