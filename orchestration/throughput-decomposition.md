**问题**：内层吞吐率不高，直觉归因是「等待测试执行」。

**方法**：解析内层会话的完整 transcript（`82ecfb6a-…jsonl`，10.3 小时），把 `tool_use` 与
`tool_result` 按 id 配对得到工具执行时长；把「内层最后一次活动 → 下一条外层指令」的间隔计为空转。

分析过程中修正了两个自身错误，记录以免复用时重犯：
（a）第一版把 `system`/`user` 条目**之后**的间隔当成「用户时间」——那其实是模型在工作的时间，
归因方向反了；
（b）第一次选错了会话文件（`8e4b1f78`），它对 `B5-1` 零命中。**在得出「测试只占 6%」这个结论前
先做了这个校验，否则整份分析都是对另一个会话做的。**

**测试合计 15%，不是瓶颈。** 直觉归因错了。

## 排序后的杠杆

### 1. 外层延迟 —— 5.1 小时（49%），最大的一个

三条路，效果依次递增：

- **已做**：`orchestration/watch/inner-state.sh` 挂成 persistent Monitor，检测延迟从 ≤20 分钟降到
  ~1 分钟。**但它的 `IDLE` 是代理信号**（遥测 `inProgress` 为空），37 次停摆里只覆盖一部分
- **待做**：[[gap-no-explicit-blocked-signal-from-inner-layer]] —— 内层主动写
  `.quay/inner-blocked.json`，存在性信号，覆盖全部停摆，且**顺带把空转时长变成可计量的数**
- **更根本：减少停摆次数，而不只是缩短每次等待。** 10.3 小时停 37 次 = 平均每 17 分钟停一次。
  其中相当一部分问的是「下一步派发哪个」「A 还是 B」这类**在给定政策下内层本可自决**的事

### 2. 预授权 —— 把「问」变成「按政策自决 + 事后报告」

当前内层的默认是**凡有分歧就停**。这在建立信任期是对的，但它是 49% 空转的直接来源。

可以立刻预授权的一类：**后果可逆且已设时间盒的选择**。例如「A 修复 / B 回退」——B 是可逆的，
时间盒已定，内层完全可以自己选 A、超时自动落到 B、事后报告，不必停下问。

**不可预授权的**：范围变更、合并决定、与既有决定冲突的取舍。这些继续停。

### 3. 测试 —— 95.7 分钟（15%），真实但次要

- `scripts/test.sh --for-task <id>` 实测 **68s vs 全量 489s（7.2 倍）**，机制已存在，
  内层 tick 第 91 行已要求用它，实际用了 47 次 vs 全量 35 次——**还有一半没换过来**
- 它会 fail-closed：Touches 解析不出测试文件时拒绝运行（实测某任务 0/6 解析 → 拒绝）。
  这是对的，但意味着 Touches 写得不好的任务只能回退全量
- **全量套件应移出关键路径**：合并前跑一次即可，且可以后台跑、同时开始下一个任务

### 4. 并发 —— 当前未使用

工具调用统计里 `Bash×693 / Edit×178 / Read×157`，**没有 `Task`/`Agent` 进前六**。曾经有过
3 个 subagent 并发的一批（每个约 40 分钟，并行完成），之后退回串行。其中一部分是外层的裁定
（B5-1/B5-2 因 `checkTouchesPair` 重叠必须串行），但串行之后没有重新组织并发批次。

## 量级估计

若外层延迟从平均 8.3 分钟降到 ~1 分钟，10.3 小时里可回收约 **4.5 小时**——**吞吐率大致翻倍**。
测试的全部优化空间加起来不到 1.6 小时，且其中大部分是必要的验证。

**先修延迟，再修测试。** 顺序反了会把力气花在 15% 上。


## 修正后的杠杆排序（以正确窗口为准）

### 1. 全量套件 29.2% —— 现在是可立刻回收的最大一块

8 次 × 均 7.1 分钟 = 57 分钟，在 3.2 小时里。三条，成本递增：

- **迭代阶段一律 `--for-task`**（68s vs 489s，7.2 倍）。机制已存在、tick 文件第 91 行已要求，
  但正确窗口里全量 8 次 vs 范围化 11 次——**仍有四成走了全量**
- **全量移出关键路径**：合并前跑一次即可，且应 `run_in_background`，同时开始下一个任务
- **外层自己也要改**：「先绿再测」这类指令直接制造全量运行。外层要求验证时应指明范围，
  不要默认全量

### 2. 空转 53.8% —— 但「更快的外层」已被证明不是解法

外层 loop 启动前后，空转比例与停摆频率几乎不变。**缩短单次等待不是杠杆，减少停摆次数才是。**

12 次停摆里，多数问的是「下一步派发哪个」「A 还是 B」。**预授权「后果可逆且已设时间盒的选择」
由内层自决、事后报告**，是唯一可能真正降低这一项的动作。已提请人裁定，未获批准前不实施。

### 3. 并发 —— 正确窗口里 `Task`/`Agent` 仍未进前六

137 次 Bash / 3.2 小时，全部串行。下一批任务应先用 `checkTouchesPair` 组可并发批次。


## 成本模型任务的实测结论（B6-1，2026-08-02 落地，commit 4282632c）

**判据**：`Σ duration_ms / 墙钟` —— run3 = 3266 s / 460.9 s = **7.09**；run4 = 3434 s / 477.7 s =
**7.19**；均值 **7.14**，并发度 8。

**结论**：**不是「最慢单文件」决定**（`cli.test.mjs` 201.5 s ≪ 墙钟 460.9 s），套件把 8 条 lane
打满了。

**内层自己撤回的一个过度声称（值得记）**：比值≈8 本来支持「吞吐受限（by CPU）」，但对抗评审时
发现本机 `nproc=4`（外层已独立核实：4 物理核、每核 1 线程，而 `--test-concurrency=8`）——
**8 个并发进程是 2 倍过订**，lane 无论 CPU 还是 IO 都会保持占用，所以比值≈8 只是「调度占位」，
**不能区分 CPU 吞吐受限与延迟受限**。标签改为「lane 饱和、非单文件延迟受限」。

可确证的量：墙钟 = Σ/8 + ~53 s 未归因差；Σ 是各文件**套件内 wall 时长之和**（受争用抬高，非纯 CPU）。

**对外层估算的校验**：`orchestration/test-shape-analysis.md` 估 Σ≈3900 s，实测 3266–3434 s——
**高估 15–19%**；估进程边界占 ~14%，实测 **16–17%**，同量级。方向对，量级对，绝对值偏高。

### 由此产生的下一个实验（尚未派发）

`nproc=4` 而并发度写死 8，这是**测量出来的、此前没人注意的事实**。并发度对墙钟的影响现在是一个
可直接测量的问题：同一 commit 分别用 `--test-concurrency=4` 与 `=8` 各跑若干次，与已测出的噪声
带宽（20–63 s）对照。过订对 IO 密集的测试可能有利、对 CPU 密集的不利，而本套件两者都有——
**必须实测，不要按直觉设**。这属于测量而非优化，与成本模型任务的「不做优化」约束不冲突。
