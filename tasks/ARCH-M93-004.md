## Finding

**WHAT:** `packages/quay-native/src/mcp-server.ts` imports `createAdrStore` from `quay/src/adr-store.ts` — a concrete Core implementation function, not an ABI type. This couples the native provider's MCP server to Core's internal implementation module, violating the stated architectural invariant that Core is provider-agnostic and providers talk to Core only through the Provider ABI.

**WHERE:**
- `packages/quay-native/src/mcp-server.ts` line 13: `import { createAdrStore } from "quay/src/adr-store.ts";`
- `packages/quay-native/src/mcp-server.ts` line 25: `const adrStore = createAdrStore(resolvedAdrDir);`

For comparison, the type-only imports (`Task`, `Manifest` from `../../quay/src/abi.ts`) are the intended ABI surface; those are correctly scoped to the abi.ts module. The `createAdrStore` import goes beyond the ABI into Core implementation code.

**METRIC:**
- Cross-package implementation import count: 1 concrete function crossing ABI (`createAdrStore` from `quay/src/adr-store.ts`)
- Type-only ABI imports (intended): 3 (`Task` from `abi.ts` in store.ts, `Manifest` from `abi.ts` in manifest.ts — both native and github packages)
- `adr-store.ts` has fanIn=1 (archguard_get_package_metrics) — that sole inbound dependency is this cross-boundary import from quay-native

**WHY:** The design principle stated in CLAUDE.md is "Core is written against the task view-model only, never a specific backend." The inverse should also hold: providers should depend on Core only through the Provider ABI, not through Core's internal implementation modules. When `quay-native` imports `createAdrStore` from Core, it creates a hard structural coupling: any refactor of `adr-store.ts` (rename, signature change, module split) silently breaks `quay-native`. It also means quay-native cannot be used as a standalone binary without pulling in Core's adr-store implementation, blurring the package boundary. The fanIn=1 of adr-store.ts confirms this is the only consumer of that cross-boundary import.
