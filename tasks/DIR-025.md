## Finding

Verified live 2026-07-19 via Playwright against `quay serve` on
`/task/DIR-021`: the rendered Details section contained ONLY three things —
`` Source: `experiments/.../DIR-021-...md` ``, a single ~3-line paragraph
(the Finding's first paragraph), and `Status mirror: pending`. It did NOT
show the DIR's runnable **Acceptance Criteria**, its **Definition of Done**,
its **full proposal** (the complete `## Finding` + `## Requested action`),
or any **plan reference** — all of which exist in the canonical DIR file
(`experiments/quay-perpetual-stream/directives/pending/DIR-021-*.md`) but are
never projected into the task body.

Root cause: the `/quay-directive` skill's projection step (step 6b, the
`body` construction) deliberately writes a *thin* body — "exactly three
parts": a `Source:` link, "the Finding section's **first paragraph**
(summary), copied verbatim — not the whole Finding section", and a
`Status mirror:` line. Because the quay web UI renders the *task* body
(not the file), the web can NEVER show a directive's AC/DoD/proposal/plan —
they are structurally absent from what it renders.

This is the same "task is not the single canonical record" gap that
[[DIR-014]] item 6 addresses for MILESTONE tasks (proposal embedded + plan
referenced + AC/DoD as checklists), reproduced one class over on DIRECTIVE
tasks. The directive task is a projection shell, not a viewable record.

Enabling fact (lowers the cost): `packages/quay/src/serve.js` ALREADY has an
inline markdown-to-HTML renderer for task bodies (it renders `##` headings,
`- ` / `- [ ]` lists, and code spans — see its `.body h2/h3/ul/ol/li` CSS and
the "inline markdown-to-HTML renderer replacing the bare `<pre>` body dump"
comment). So a fuller markdown body containing `## Acceptance Criteria`,
`## Definition of Done`, etc. will render correctly with NO serve.js change
required for the common case — the only missing piece is that the projection
never PUTS those sections into the body.

## Requested action

Make the directive-task projection carry the FULL, regenerated content of the
DIR file, so the directive task is the single canonical viewable record —
consistent with [[DIR-014]] item 6's "task = single canonical lifecycle
record" principle, now applied to directive tasks. Concretely:

1. **Change the `/quay-directive` projection body contract (skill step 6b).**
   The task `body` MUST be a fully-regenerated projection of the DIR file that
   includes, in order:
   - the `Source:` link line (unchanged);
   - the COMPLETE `## Finding` + `## Requested action` sections (the full
     proposal, verbatim from the file — not only the first paragraph);
   - the COMPLETE `## Acceptance Criteria` checklist (verbatim, `- [ ]` items
     preserved);
   - the COMPLETE `## Definition of Done` section (verbatim);
   - any **plan reference** the DIR carries (e.g. a `docs/plans/*.md` path or a
     `## Plan` section), verbatim;
   - the `Status mirror: <value>` line (unchanged — the anti-drift join field).
   It remains a GENERATED projection (DIR-002/M-DIR-PROJECTION): fully
   regenerated from the file, never hand-edited, never incrementally patched.
   Update the skill's own step-6b text (and the `## File format` expectations it
   cites) so future DIRs project full bodies by default.

2. **Provide a re-projection sweep for the EXISTING directive tasks.** The
   already-projected DIRs (DIR-001..024) currently carry thin bodies; regenerate
   each one's task body from its file under the new full-body contract (a small
   script or a documented `task_write` loop that reads each `DIR-NNN.md` file and
   rewrites the matching `tasks/DIR-NNN.md` body). At minimum DIR-021 must be
   re-projected as the proof object for this DIR's own Definition of Done.

3. **Keep the anti-drift check green.** `scripts/it0-dir-projection-check.sh`
   joins file↔task on `DIR-NNN` and compares the `status:` mirror only — a
   fuller body does not change the join key or the mirror, so the check must
   still pass. If the skill/README documents the body's "first-paragraph-only"
   contract anywhere the check or a test relies on, update it consistently so
   nothing asserts the OLD thin shape.

4. **Confirm the web renders the full body (no or minimal serve.js change).**
   Because `serve.js` already renders markdown headings/lists, the full body
   should display AC/DoD/proposal/plan as structured sections. Only if a specific
   construct (e.g. a `- [ ]` checkbox glyph) renders poorly should a minimal
   serve.js tweak be made; do NOT rebuild the renderer.

Non-goals: do NOT make the task body a second AUTHORITATIVE copy — the DIR file
stays canonical and the body is always regenerated from it (DIR-002); do NOT
hand-edit any task body to patch a mismatch (regenerate instead); do NOT change
the milestone-task lifecycle record (that is DIR-014 item 6's scope — this DIR
is the directive-task analogue, not a re-scope of it).

## Definition of Done — REAL LANDING is the bar, not artifacts

This DIR is **NOT done** when the skill text is edited, a script is written, or
one task body is hand-updated. Artifacts are necessary but NOT sufficient. It is
done **ONLY** when a **REAL directive's task projection, regenerated by the
updated mechanism, actually renders its Acceptance Criteria + Definition of Done +
full proposal + plan reference in the quay web UI** — verifiable by:
(a) loading `http://localhost:<port>/task/DIR-021` (a real directive, not a demo
    task) in a browser / via the served HTML and SEEING all four sections
    rendered (the same Playwright check that found them ABSENT in this Finding
    must now find them PRESENT); AND
(b) `tasks/DIR-021.md`'s body containing the full `## Acceptance Criteria` /
    `## Definition of Done` / `## Requested action` sections, produced by the
    regeneration mechanism (not a one-off hand edit); AND
(c) the anti-drift check still green (the fuller body did not break the
    file↔task status join).
A green grep on the file alone, an edited SKILL.md alone, or a single
hand-written body alone is necessary but NOT sufficient. Escrow discipline: until
a real directive's web page shows all four sections via the regeneration
mechanism, this DIR stays `pending`.
