## Proposal
Build the quay-side capability to MIGRATE tasks from archguard's two current backends — its GitHub issues + its local Backlog.md board — INTO a single quay-native store. This is the "read → consolidate" step [[DIR-037]]'s scope note deferred, and the prerequisite for archguard adopting quay as its task manager. Pure in-repo quay capability development → **LOOP-EXECUTABLE** (`milestone-candidate`, NOT `human-steered`), unlike the off-repo [[DIR-036]] deployment. Two capabilities, ABI-pure and single-sourced:

**(A) Generic provider-to-provider migration via the ABI.** A `quay migrate --from <providerA> --to <providerB>` (verb/flags at the milestone's discretion) that reads EVERY task from the source provider through the Provider ABI (the task view-model: id/title/status/role/labels/parent-children/body) and writes it to the target provider through the ABI — provider-agnostic, works for any pair, NOT github-specific. archguard's case is `--from github --to native`. This is the ABI proving itself again (Core reads A, writes B, knows neither concretely).

**(B) A Backlog.md source adapter.** Backlog.md (archguard's `backlog/tasks/*.md`) is NOT a quay provider. Its files carry frontmatter `id: TASK-N` / `title` / `status` (Done/To Do/…) / `labels` / `dependencies` / `ordinal` + a sectioned body — maps cleanly onto the view-model. Add a read adapter so the board becomes importable. **STRONGLY PREFERRED design** (confirm at proposal-to-plan): a read-only `quay-backlog` PROVIDER — a 3rd heterogeneous provider, mirroring how quay-github proved the ABI transfers — so (A)'s generic migrate handles it for free. If a full provider is too big for one milestone, a Backlog.md→native importer that emits the SAME view-model is acceptable, but it MUST reuse (A)'s write path (single-source, ADR-004), never a parallel task-writer.

**Out of scope (a later HUMAN decision, not this DIR):** whether archguard ACTUALLY cuts over to quay-native as its sole backend / retires its Backlog.md Monitor loop. This DIR BUILDS + PROVES the importers on real data into a scratch/target quay-native store; the operational cutover inside the archguard repo is a separate human step.

Value type: **capability-growth** (a genuinely new product surface — migration/import) — and it directly feeds [[DIR-038]]-C's unbounded outward-VT term (a real external migration is exactly the outward value the saturated cov-ruler cannot score). Read path unblocked by [[DIR-037]] (github ENOBUFS fix, done M55) + [[DIR-036-A]] (deployment landed, quay reads yaleh/archguard via the ABI).
