## Proposal
Implement cross-milestone concurrent execution using **NATIVE Claude Code background subagents** (NOT manda — the DIR-020 hard-mandate against manda for real dispatch stands; manda-nesting is not relied on). This realizes the deferred §5.3 design in `docs/proposals/exp5-concurrent-background-agents-for-milestone-iteration.md`. Today the OUTER-LOOP runs ONE milestone at a time (SELECT→build→ABSORB, fully serial, ≈37 min/milestone M44→M57); for DEPENDENCY-ORTHOGONAL execution-type milestones this leaves throughput on the table (this conversation's analysis: exp5's product batch [[DIR-039]]∥[[DIR-042]] is orthogonal; archguard's 12-task corpus decomposes into 4–5 independent streams, ~3× available).

**Two-level scheduler (native, Level-0 orchestrated — no nesting, §5.0):**
- **Outer (across-milestone):** at SELECT, assemble a BATCH — the top-ranked candidate, then greedily add candidates whose `touches` set is disjoint from all already-selected AND which are execution-type. Run the orthogonal batch in parallel: one native `Agent(run_in_background=true)` per milestone, each in its OWN worktree, each building ONLY its milestone's code + charter + iteration report and writing **NO shared-state files** (`dashboard.md`/`backlog.md`/`milestone_counter`/`gate-events`). Then a SINGLE serial **fan-in ABSORB** merges each completed build one-at-a-time (branch merge → counter++ → dashboard/backlog append → independent audit). **Learning-type milestones ALWAYS run alone, serial** (their output changes the value function/machinery the next SELECT depends on — §5.2).
- **Inner (within-milestone):** unchanged from the already-safe fan-out (scouting/verification/map-chunks at Level 0); out of scope except that the outer scheduler must not double-count the concurrency budget.

**The enabler that makes "orthogonal" a CHECK, not a guess:** a **machine-checkable `touches` declaration** in each charter (surfaces + code paths + value-function/cov terms + machinery). The scheduler's own blind spot (a mis-declared `touches` → silent conflict or lost learning-dependency, §5.3) is covered by (i) a **conservative default** — when `touches` is absent/ambiguous, serialize; and (ii) an **after-the-fact anti-drift check** (same enforcement pattern as DIR-002/005): after a parallel batch, verify no two concurrent milestones actually wrote overlapping files and no learning-dependency was skipped; HARD-fail the batch if violated.

**Why native + this shape works WITHOUT the full state-sharding refactor:** because build DEFERS all shared-state writes to the serial fan-in ABSORB, the only concurrent writes are each milestone's OWN worktree files — zero collision. The append-all collision that forced serialization (witnessed at merge `afcdbff`) is avoided by construction, not by sharding the files. (Note: in a PRODUCT loop over quay-native — e.g. archguard — the per-task-file store shards naturally, so this discipline is even lighter there; but exp5's monolithic `dashboard.md` makes the defer-writes rule mandatory here.)

**Driver change** (restructures the SELECT←ABSORB serialization core) → `human-steered` (DIR-030 / DIR-027 fence; proposal §4 explicitly requires this be "a deliberate, separately-justified change, not a default").

- Real blockers are (a) shared append-all state files and (b) the SELECT←ABSORB learning dep — BOTH avoided for touches-disjoint execution-type batches with build-defers-shared-writes + serial fan-in ABSORB (proposal §5.1–5.2).
