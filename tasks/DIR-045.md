## Proposal
[[DIR-042-B]] ships a slim loop-driver skill. This follow-on makes it GENERAL and FORMAL, per the 2026-07-20 analysis of how exp5 actually launches vs the ad-hoc archguard prompt.

**The finding that motivates it:** exp5 launches via a THIN invocation — `/loop @experiments/quay-perpetual-stream/OUTER-LOOP.md 持续迭代。除非遇到中止条件，不得停下。` — where ALL discipline lives in a fat driver DOC. The ad-hoc archguard launch prompt instead inlined a fat PROSE driver with hardcoded params (task ids, worktree paths, gate names, pause-hooks, one-shot) — the wrong abstraction level. **Both are the SAME universal driver with different PARAMS.** Refactor the DIR-042-B skill so the driver is expressed ONCE, formally, and projects differ only in a params file.

**(1) The driver becomes ONE formalized `iterate` contract** (baime prompt-doc style — `name :: In → Out -- ⊨ invariant`, same house style as `/quay-directive`):
```
iterate :: Board × Kit × Gates → Milestone        -- once ; or iterate* until Stop
  select  :: Board ⇀ Task        -- ready·top-ranked ; ⊨ exclude label:human-steered
  isolate :: Task → Worktree     -- git worktree off HEAD ; ⊨ ¬on-master (DIR-027) ; ⊨ deps-ready (node_modules/venv present — symlink or install)
  build   :: Task × Worktree → Diff  -- TDD ; ⊨ behavior-preserving
  gate    :: Task → {PASS, FAIL}     -- runner-agnostic ; ⊨ fail-closed ; ⊨ runner ∉ driver ; ⊨ cwd = worktree (gate the BUILT tree, not workspaceRoot — see DIR-046)
  record  :: Diff × Gate → Evidence  -- ⊨ real-object (DIR-026) ≠ fixture
  land    :: Diff → Commit ⊕ needs-human  -- ⊨ done ∨ needs-human (SPLIT-OR-COMMIT)
invariants (∀ iteration): worktree ⊥ master · gate fail-closed · coexist: pause(peer-loop)
  · evidence real ≠ fixture · runner ∈ workspace .quay/gates.yml ONLY (never the driver)
```
**(2) Per-workspace params in `.quay/loop.yml`:** `board` (provider) · `gates` (refs into `.quay/gates.yml`) · `stop` (once | until(∅ ready) | until(.halt) | until(K·ΔV<ε)) · `coexist` (pause-hook) · `policy` (select-ranking).
**(3) A THIN launcher** (`/quay-loop`, or the skill invocation) reads `.quay/loop.yml` and runs the contract; the fat driver lives ONCE in the skill.

**(4) `isolate` produces a DEPENDENCY-READY worktree + hands its path to `gate` as the cwd.** Surfaced by the real archguard iteration (meta-cc `8b74052c`): a fresh `git worktree` has NO `node_modules`, so the test runner failed until the user manually `ln -s`'d it; and the `gate` step must run the suite IN the worktree (the gate-cwd fix itself is [[DIR-046]] — this driver's job is to PASS the worktree path as the acceptance cwd, not to gate `workspaceRoot`). So `isolate` MUST leave the worktree runnable (symlink/install deps) and the driver MUST thread the worktree path into `gate`.

**Real-landing = universality proof:** the SAME skill drives a REAL archguard dev iteration from archguard's `.quay/loop.yml` (external dogfood: real diff + a `quay gate` PASS), AND an exp5 `.quay/loop.yml` exists capturing exp5's own settings — proving one contract + two params files, NOT a per-project fork.
- exp5 params: `{board:native, gates:it0-set, stop:until(.halt), policy:value-typed-ledger, coexist:∅}`
- archguard params: `{board:native, gates:vitest(testPass), stop:once, policy:ready-first, coexist:pause(backlog/.loop-stop)}`

**Out of scope (a SEPARATE `human-steered` driver-rewrite):** re-expressing exp5's OWN `OUTER-LOOP.md` AS the universal contract — that rewrites the live loop's control structure (DIR-030/DIR-027 fence). This DIR only PROVES exp5 maps to params + drives archguard; migrating exp5's actual driver is a later human-authorized step.

**LOOP-EXECUTABLE** (in-repo product-skill formalization + external dogfood) → `milestone-candidate`. Depends on [[DIR-042-B]] (the driver skill it refactors); builds on [[DIR-042-A]] (runner-agnostic gates, done M59) + [[DIR-040]] (portable skills, done M58).

## Finding
- meta-cc: exp5 launches via a thin `/loop @OUTER-LOOP.md`; all discipline in the fat driver doc.
- The 2026-07-20 archguard launch prompt inlined a fat PROSE driver with hardcoded params — non-reusable, prose, project-coupled (wrong abstraction level).
- Both are one universal driver + different params (exp5 vs archguard params enumerated above).
- [[DIR-042-B]] (M60) ships the slim driver skill — this follow-on gives it the formalized contract + params split so it does not become yet another prose driver.
- The real archguard iteration (meta-cc `8b74052c`) also exposed that `isolate` under-specifies environment readiness: a fresh `git worktree` has no `node_modules` (manual `ln -s` needed), and the `gate` step ran in the main repo, not the worktree — the driver must (a) leave the worktree runnable and (b) thread the worktree path as the gate cwd (the gate-cwd knob itself is [[DIR-046]]).

## Requested action
1. Refactor the [[DIR-042-B]] loop-driver skill to the formalized `iterate` contract (baime prompt-doc style) with invariants inline.
2. Add a `.quay/loop.yml` params schema (board/gates/stop/coexist/policy); the skill reads it; a thin launcher.
2b. `isolate` leaves a DEPENDENCY-READY worktree (symlink/install deps) and threads the worktree path into `gate` as its cwd (uses [[DIR-046]]'s gate-cwd knob) — so the gate validates the built tree, and the runner actually runs (no manual `ln -s node_modules`).
3. Prove universality: drive a REAL archguard iteration from archguard's `.quay/loop.yml`, AND ship an exp5 `.quay/loop.yml` capturing exp5's settings — one contract, two params files.
4. Do NOT rewrite exp5's own `OUTER-LOOP.md` (separate human-steered driver-rewrite).
