## Proposal
Fix the `quay gate` ergonomics gaps surfaced by the FIRST real archguard development iteration (meta-cc session `8b74052c`, 2026-07-20 14:39–15:05 — the loop-driven refactor of `arch-metrics.ts` in an isolated worktree). Three real frictions, all clustered on gating a foreign worktree with a real test suite:

**(A) The gate runs in the WRONG tree.** `packages/quay/bin/quay.js`'s gate branch UNCONDITIONALLY sets `process.env.QUAY_ACCEPTANCE_CWD = cfg.workspaceRoot` (`:965/1013/1040/1082`); `registry.js` factories then run the command in that cwd (`:117/140/193`). So a `quay gate` invoked from the main repo runs the tests in `workspaceRoot` (the MAIN repo), NOT the worktree where the milestone's changes live. In the archguard session the user reverse-engineered `QUAY_ACCEPTANCE_CWD` from the source and set it explicitly — **but the CLI's unconditional pin OVERWROTE it**, so the gate validated the UNCHANGED main repo, not the worktree refactor. The DIR-027 worktree-before-merge flow (the methodology's own hygiene) is unsupported by the gate. (exp5 never hit this because it gates post-merge on `master` == workspaceRoot; the worktree-before-merge pattern is new to the off-repo product use.)

**Fix A:** an explicit CWD override wins — a `quay gate --cwd <dir>` flag AND a pre-set `QUAY_ACCEPTANCE_CWD` are honored (the workspaceRoot pin is the DEFAULT, applied only when neither is given); optionally a per-gate `cwd` in `.quay/gates.yml`. So a worktree-based iteration can gate the worktree, before merge.

**(B) The gate timeout (60s) is too short for a real suite.** `registry.js` defaults `Number(process.env.QUAY_ACCEPTANCE_TIMEOUT_MS) || 60000`; archguard's vitest suite exceeds it, so the user had to set `QUAY_ACCEPTANCE_TIMEOUT_MS=300000`. Env-only, not `gates.yml`-configurable. **Fix B:** a per-gate `timeoutMs` field in `.quay/gates.yml` (`testPass`/`coverageFloor`/`redGreen`) + a saner default; the workspace declares its own suite's budget as DATA (like the command — DIR-042-A/ADR-013 pattern).

**(C) The knobs are undiscoverable.** `QUAY_ACCEPTANCE_CWD`/`QUAY_ACCEPTANCE_TIMEOUT_MS` are env-only, absent from `quay gate --help`, and not in any failure text — the user spent ~15 min (14:50–15:05) grepping the installed quay source in `node_modules` to find them. **Fix C:** surface `--cwd`/`--timeout` (or the gates.yml fields) in `quay gate --help`; make a TIMEOUT failure's `reason` text name the `timeoutMs` knob ("raise gates.yml timeoutMs / --timeout"). No user should need to read source to gate a real project.

Same class as [[DIR-037]] (ENOBUFS): a product gap invisible on quay's own repo, surfaced ONLY by real external usage — exactly the [[DIR-043]] external-dogfooding value, manifesting by hand. **LOOP-EXECUTABLE** (in-repo quay gate work) → `milestone-candidate`. Related: worktree dependency-readiness (no `node_modules` in a fresh worktree — the user had to `ln -s` manually) is folded into [[DIR-045]]'s `isolate` contract, NOT here.

## Finding
From meta-cc session `8b74052c` (the real archguard iteration):
1. Gate ran vitest in the MAIN archguard repo, not the worktree (`bin/quay.js` pins `QUAY_ACCEPTANCE_CWD = cfg.workspaceRoot` unconditionally → user's explicit override clobbered).
2. Default timeout 60s < archguard suite → user set `QUAY_ACCEPTANCE_TIMEOUT_MS=300000`.
3. Both knobs env-only + undocumented + absent from `quay gate --help` → ~15 min grepping installed source to find them.
4. Root pattern: quay gate has no first-class notion of "gate this milestone's worktree" (worktree-before-merge); exp5 dodged it by gating post-merge on master.

## Requested action
1. **A:** honor an explicit acceptance CWD (`quay gate --cwd <dir>` and/or a pre-set `QUAY_ACCEPTANCE_CWD` and/or a gates.yml per-gate `cwd`) — the workspaceRoot pin becomes the DEFAULT applied only when none is given; explicit override wins.
2. **B:** add a per-gate `timeoutMs` to `.quay/gates.yml` (testPass/coverageFloor/redGreen) + a saner default; workspace-declared budget as data.
3. **C:** surface `--cwd`/`--timeout` (+ the gates.yml fields) in `quay gate --help`; a TIMEOUT failure reason names the `timeoutMs` knob.
