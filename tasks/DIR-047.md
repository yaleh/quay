## Proposal
Add a **per-provider `default_task_status` key to `.quay/config.yml`** that replaces the hardcoded `flags.status ?? "todo"` fallback in the task-creation path (`packages/quay-native/bin/quay-native.js` `task create`, and the equivalent `task_write`/MCP default). When a caller creates a task WITHOUT an explicit status, the provider stamps `config.default_task_status` (falling back to `"todo"` when the key is absent, preserving today's behavior exactly). Pure in-repo quay capability → **LOOP-EXECUTABLE** (`milestone-candidate`, NOT `human-steered`).

**Why this is the right mechanism (writer-side, not reader-side).** The archguard loop-driver dogfood exposed the friction: a seeded quay-native task lands at `todo` and is INVISIBLE to `quay task list --status ready`, so the loop finds nothing until a human manually `task edit --status ready`. Two dual mechanisms can fix "created-tasks-are-directly-executable":
- **(A) reader-side** — make the loop's SELECT predicate configurable (pick up `todo`);
- **(B) writer-side, THIS DIR** — make the CREATION default status configurable, keep the SELECT predicate a **fixed universal `ready`**.

(B) is preferred because it **protects the invariant "`ready` = runnable" across every workspace** — the consumer (loop-driver / any board reader) never has to branch on per-workspace config, and the lifecycle `todo→ready→done` keeps a single stable meaning. The "auto-drive vs human-release" decision lives entirely on the write side, as one declarative config key.

**The knob (global, per-provider):**
```yaml
providers:
  native:
    enabled: true
    default_task_status: ready   # newly-created tasks land ready → immediately selectable
    # (omit, or set `todo`, for human-release: tasks wait until manually promoted)
```
- `default_task_status: ready` → auto-drive: `quay task create TASK-N` (no `--status`) yields a `ready` task the loop picks up with zero manual promotion.
- absent / `todo` → today's behavior EXACTLY (human-release): tasks sit at `todo` until `task edit --status ready` (or the lifecycle `promote`).
- **Global**: applies to ALL creation paths for that provider — CLI `task create`, MCP `task_write` (status omitted), and the DIR-039 migrate/import writers — so the mode is consistent, not per-callsite.
- An explicit `--status <x>` on any call ALWAYS wins over the default (the key sets the *fallback*, never overrides an explicit request).
- **Fail-closed on a bad value**: a `default_task_status` that is not one of the 4 legal lifecycle states `{todo, ready, done, needs-human}` is a hard config error at load, not a silent coerce-to-todo.

**Out of scope (explicitly NOT this DIR):**
- The reader-side mechanism (A) — a configurable SELECT predicate in `.quay/loop.yml`. This DIR deliberately keeps the SELECT predicate FIXED at `ready`; (A) is a separate, possibly-never-needed follow-on.
- exp5's OWN OUTER-LOOP selection (`label:milestone-candidate --status todo`). exp5 is a human-steered driver that intentionally keeps new candidates at `todo` for its charter/split step — it does NOT consume via the generic `ready` predicate and MUST NOT be forced onto `default_task_status: ready` (that would skip charter). This DIR does not touch exp5's driver (DIR-027/DIR-030 fence); exp5's workspace simply omits the key (→ `todo`), preserving its behavior.

Value type: **capability-growth** (a new product config surface that makes quay usable as a directly-drivable board in external workspaces — the archguard adoption path), building on [[DIR-039]] (migrate/import — the writers that also honor the default) + [[DIR-042-B]]/[[DIR-045]] (the loop-driver whose fixed `ready` predicate this keeps clean).

## Finding
- Task creation hardcodes the default: `packages/quay-native/bin/quay-native.js:303` → `status: flags.status ?? "todo"`. There is no config-driven override.
- The archguard loop-driver dogfood (2026-07-21): seeded `quay-native` tasks (TASK-24/25, DIR-001/002) landed at `todo`; `quay task list --status ready` returned empty; `/quay:loop-driver` correctly reported Idle every wakeup because nothing was `ready` — the human had to manually `task edit --status ready` to feed the loop.
- exp5's own convention is "created DIRs/tasks are directly executable" — but it achieves that via `label:milestone-candidate + status:todo` selection in its OUTER-LOOP, NOT via `ready`. exp5's `ready` is a reserved "charter done, about to gate" state. So exp5 is NOT a case for `default: ready`.
- The clean split: keep the consumer predicate a fixed universal `ready`; put the auto-vs-manual decision on the writer via one config key. "ready = runnable" stays true everywhere.
