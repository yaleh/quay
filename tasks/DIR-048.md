## Proposal
Add two **optional** keys to the `.quay/loop.yml` schema that let a workspace lift the loop-driver's `build` and `record` steps from **inline** (done in the driver's own context) to **dispatched** (a fresh background subagent builds; an independent fresh-context subagent adversarially audits before land):

```yaml
# existing schema (DIR-045): board, gates, stop, policy, coexist
execution: inline        # inline (default) | dispatched — where the build step runs
audit:     none          # none  (default) | adversarial — fresh-context verify before land
```

- `execution: inline` (**default, unchanged**) — the driver session implements the task itself (today's behavior, keeps the portable skill light for small single-refactor tasks).
- `execution: dispatched` — the driver SPAWNS a background subagent (harness-tracked, `run_in_background`) to run the `build` step in the worktree, then polls for completion (completion notification is the primary wake; a fallback poll re-arms) — the driver stays a lean **orchestrator** that never accumulates build churn in its own context.
- `audit: none` (**default, unchanged**) — `record` captures the gate output only (today's behavior).
- `audit: adversarial` — after gate PASS, before `land`, the driver dispatches a **fresh-context** subagent (`Explore`/`general-purpose`, `run_in_background`) prompted to REFUTE the milestone's claims; a refutation blocks `land` (routes to `needs-human`). The auditor never saw the build → real verification asymmetry.

Pure in-repo quay/skill capability, backward-compatible by default → **LOOP-EXECUTABLE** (`milestone-candidate`, NOT `human-steered`).

**Why this is needed (the gap the archguard dogfood exposed).** The portable `quay-loop-driver` skill (DIR-042-B / DIR-045) runs the ENTIRE iterate — select+build+gate+land — inline in one driver context. exp5's `OUTER-LOOP.md` instead runs a **two-layer** loop: the outer session is a pure orchestrator that DISPATCHES each milestone build to a background `iteration-executor` subagent and then dispatches a SEPARATE fresh-context adversarial-audit subagent (OUTER-LOOP.md steps "DISPATCH INNER" + "Adversarial-audit role"). The archguard dogfood (2026-07-21, session `bdf78e54`) ran DIR-001+DIR-002+TASK-25 with **124 Bash + 26 Edit + 17 Write all inline** in the driver context, and its only "verification" was a same-session test run — no independent audit. Two real capabilities are therefore missing from the portable skill:
1. **Context isolation of the build** — inline execution makes per-iteration driver context grow monotonically; a long driver cannot run many milestones without exhausting its window (archguard works around this by having `/loop` re-spawn a fresh driver session every ~4 min — a symptom, not a fix).
2. **Verification asymmetry** — a fresh-context auditor that did NOT produce the diff is the GIT-lens hard check (ADR-004/006 hard-over-soft; the "can't-read-your-own-work" refutation role). Same-session self-gating lacks it.

**Why keep it OPTIONAL and default-inline.** DIR-045 deliberately made the skill a flat, minimal, portable `iterate` contract — one skill, different params, any workspace. Small tasks (a single refactor) do NOT need two-layer machinery; forcing it on every workspace would betray that portability. So the two-layer capability becomes **two declarative opt-in keys**, not a rewrite: the便携 skill stays a one-context contract by default, and heavy workspaces (archguard, and eventually exp5 itself folding its bespoke OUTER-LOOP machinery back into the shared skill) turn it on in `loop.yml`. This aligns the portable skill with ADR-009 (background workflows at milestone granularity) WITHOUT baking exp5-specific complexity into every consumer.

**Out of scope (explicitly NOT this DIR):**
- Migrating exp5's OWN `OUTER-LOOP.md` onto the shared skill. exp5's bespoke driver (charter/proposal-adjudication/dual-iteration/dashboard) is richer than `dispatched`+`adversarial` and stays as-is (DIR-027/DIR-030 fence). This DIR only gives the PORTABLE skill the two primitives; whether exp5 later consolidates onto it is a separate decision.
- Parallel cross-milestone subagents (DIR-044). This DIR dispatches ONE build subagent per iterate (still serial iterations); concurrency is a different, deferred directive.
- Changing `stop`/`policy`/`board`/`gates` semantics — those DIR-045 keys are untouched; `execution`/`audit` are additive and orthogonal.

Value type: **capability-growth** (the portable loop-driver gains context-isolated execution + independent audit — the robustness exp5 already enjoys), building on [[DIR-042-B]]/[[DIR-045]] (the portable skill + `loop.yml` schema this extends) and the ADR-009 background-workflow / adversarial-audit discipline exp5 runs.

## Finding
- The portable skill `plugin/skills/loop-driver/SKILL.md` (DIR-045) declares `allowed-tools: Bash, Read` and its step 4 "Build" says "Implement the task in the worktree" — i.e. the driver implements INLINE; there is no dispatch step and no audit step. `record` (step 6) only "captures the gate output".
- exp5 `experiments/quay-perpetual-stream/OUTER-LOOP.md`: "DISPATCH INNER" runs the milestone as a background subagent (`baime:iteration-executor`, `run_in_background=true`) with poll-don't-conclude waking; a later step dispatches a fresh-context adversarial-audit subagent that "MUST originate from the TOP-LEVEL loop session" (only the top-level context can spawn a genuinely independent fresh-context subagent).
- archguard dogfood evidence (session `bdf78e54`, 2026-07-21): the loop autonomously completed TASK-24/DIR-001/DIR-002/TASK-25/TASK-29, but the main iterate ran inline (124 Bash + 26 Edit + 17 Write in the driver context); the only subagents spawned were TASK-29's task-intrinsic A/B/C experiment groups, NOT a structural build/audit dispatch. Verification was a same-session test run — no independent auditor.
- The clean split: keep the default one-context contract (portable, light); add two opt-in `loop.yml` keys that unlock context-isolated dispatch + fresh-context audit for heavy workspaces.

## Requested action
1. Extend the `.quay/loop.yml` schema in `src/loop-params.js` (`readLoopParams`): add optional `execution` (`inline`|`dispatched`, default `inline`) and `audit` (`none`|`adversarial`, default `none`); fail-closed on any other value.
2. In the loop-driver skill, branch the `build` step: `inline` → today's in-context implementation; `dispatched` → spawn a background subagent to build in the worktree, then poll to completion (completion notification primary; fallback poll re-arms). The dispatched build prompt MUST carry the full task body + worktree path (no bare hash reference).
3. Branch the `record`/pre-`land` step: `audit: adversarial` → after gate PASS, dispatch a fresh-context (`Explore`/`general-purpose`, `run_in_background`) subagent prompted to REFUTE the milestone's AC/DoD claims from the diff; a refutation blocks `land` → `needs-human`. The dispatch MUST originate from the top-level driver session.
4. Keep defaults EXACTLY backward-compatible: absent keys, or `inline`/`none`, reproduce today's behavior byte-for-byte. Do NOT migrate exp5's OUTER-LOOP onto the skill; do NOT add cross-milestone concurrency (DIR-044).
5. Prove it real on archguard: set `execution: dispatched` (and `audit: adversarial`) in archguard's `.quay/loop.yml`, run one iterate, confirm the build ran in a subagent (a subagent session file exists for the build, driver context stayed lean) and the audit subagent ran fresh-context before land.

## Acceptance Criteria
- [ ] `src/loop-params.js` accepts optional `execution` and `audit` keys; `readLoopParams` returns them with defaults `inline`/`none` when absent, and REJECTS any illegal value fail-closed — a RED+GREEN test pins valid values parsing and an illegal value throwing.
- [ ] With `execution: dispatched`, the skill's `build` step spawns a background subagent for the worktree build and polls to completion (does NOT implement inline); demonstrated by a real iterate whose build work lives in a subagent session file, with the driver context NOT containing the build's Edit/Write churn. Captured in the milestone record.
- [ ] With `audit: adversarial`, after gate PASS and before land, a fresh-context subagent is dispatched to refute the AC/DoD; a refutation routes the task to `needs-human` instead of `done` (a test/real-run pins both a clean-pass land and a refutation-blocked land).
- [ ] Backward compatibility EXACT: absent keys OR `execution: inline` + `audit: none` reproduce today's inline, no-audit behavior — existing workspaces (incl. exp5's own `loop.yml` if present, and archguard before opt-in) are unaffected (a test asserts the inline path is unchanged).
- [ ] Out-of-scope fences held: exp5's `OUTER-LOOP.md` driver was NOT migrated onto the skill; NO cross-milestone concurrency was added; `board`/`gates`/`stop`/`policy`/`coexist` semantics are untouched.
- [ ] No regression: quay Core + quay-native + quay-github suites still pass (excluding the known live-github suites); `readLoopParams` existing tests still green.

## Definition of Done
References the standard inherited-core DoD clauses; the bar is REAL LANDING, not artifacts. A passing synthetic test alone is necessary-not-sufficient. Done ONLY when:
- [ ] A REAL dispatched iterate ran on a real workspace (DIR-026 real object): with `execution: dispatched` set, a real task's build executed in a background subagent (subagent session file exists), the driver session did NOT accumulate the build's Edit/Write churn, and the task landed `done` (or `needs-human`) — pasted in the milestone record, not a synthetic fixture.
- [ ] A REAL adversarial audit ran fresh-context: with `audit: adversarial`, a real gate-PASS task was verified by an independent subagent that did not produce the diff, and the refute-blocks-land path is demonstrated (a deliberately-broken task routed to `needs-human`).
- [ ] Backward compatibility proven: the inline/none default reproduces today's behavior exactly (a test asserts it), so exp5 and pre-opt-in archguard are unaffected; the it0 DoD meta-enforcer passes.
- [ ] The schema keys are fail-closed on illegal values (RED→GREEN test) and single-sourced through `readLoopParams` (ADR-004); TDD per ADR-001.
- [ ] Per DIR-026 SPLIT-OR-COMMIT: if `execution:dispatched` and `audit:adversarial` land as separate milestones, each is done-or-`needs-human`; this DIR is done only when BOTH knobs are honored by the portable skill AND proven real on a workspace.

5. Was exp5's OUTER-LOOP left untouched, and was NO cross-milestone concurrency (DIR-044) pulled in?
