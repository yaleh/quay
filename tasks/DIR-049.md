## Proposal
Give the PORTABLE loop-driver skill autonomous cross-milestone concurrency by wiring DIR-044's
already-built, adversarially-audited scheduler into DIR-048's dispatched-execution skill. Today the
skill (DIR-048) dispatches ONE audited build per iterate — serial. DIR-044's scheduler (orthogonality
→ batch → serial fan-in → anti-drift) exists as scripts and is proven end-to-end, but ONLY by
human orchestration ([[DIR-044-LIVE]] on exp5, Path A). This DIR makes the skill ITSELF batch-aware so
`/loop /quay:loop-driver` runs a real ≥2-wide concurrent batch with no human in the loop — the
production capability behind DIR-044.

```yaml
# .quay/loop.yml — NEW key (additive; DIR-045 board/gates/stop/policy/coexist + DIR-048 execution/audit unchanged)
concurrency: 1     # 1 (DEFAULT) = serial (one dispatched build per iterate) | N = max touches-disjoint batch width
```

**The deliberate asymmetry — concurrency defaults OFF (opt-in), unlike DIR-048's dispatch/audit
which default ON.** This is principled, not inconsistent:
- DIR-048 `execution: dispatched` + `audit: adversarial` default ON because they are **correctness**
  (verification asymmetry / context isolation are GIT-lens hard requirements — every consumer should
  have them).
- DIR-049 `concurrency` defaults to **1 (serial)** because concurrency is a **throughput** trade with
  real risk (a mis-declared `touches` → conflict / lost learning-dependency). It is safe ONLY where
  tasks are genuinely disjoint AND carry no SELECT←ABSORB learning dependency. So a workspace must
  OPT IN explicitly (archguard's independent refactor tasks qualify; exp5's methodology milestones do
  not). The weak-but-safe default; the powerful mode is a visible, deliberate config choice.

**Control flow (skill orchestrates; DIR-044 scripts compute — single-source, no re-implementation):**
1. **SELECT → batch** (step 2): if `concurrency > 1`, run `concurrent-batch-scheduler.mjs` over the
   ready candidates that carry a `## Touches` declaration; assemble a maximal touches-disjoint,
   execution-type batch up to width `concurrency`. Candidates without `## Touches`, overbroad, or
   learning-type → conservative-serialize (fall to width 1). Graceful degrade: `concurrency: N` on a
   board with only 1 disjoint-ready task simply runs 1-wide.
2. **Dispatch N** (step 4–6b, per batched task, CONCURRENTLY): each task → dispatched build (DIR-048,
   own worktree, defers shared-state) + fresh-context adversarial audit (DIR-048). N builds + N audits
   in flight; the driver stays a lean orchestrator and polls all.
3. **Fan-in** (step 7): builds that PASS gate AND audit → `anti-drift-touches-check.mjs` on the REAL
   diffs (NON-WAIVABLE HARD backstop — mis-declared overlap HARD-fails the batch, blocking the merge)
   → `serial-fanin-absorb.mjs` computes the deterministic merge plan → merge each one-at-a-time, mark
   each task done. A build that FAILS gate or is REFUTED by audit → `needs-human`, EXCLUDED from
   fan-in (partial-batch success: the disjoint survivors still land).
4. **Guardrails (NON-WAIVABLE, all from DIR-044, already 3-round-audited):** conservative-default
   serialize; learning-type never batched; anti-drift HARD check pre-merge; native-only (no manda).

`stop`/`until` semantics extend cleanly: one iterate = one BATCH; `until(empty)` keeps assembling
batches until the ready queue is empty.

Pure in-repo quay/skill capability, additive and opt-in → **LOOP-EXECUTABLE** (`milestone-candidate`,
NOT `human-steered` — it edits the PORTABLE skill, not exp5's own OUTER-LOOP).

**Prerequisite (2 DIR-048 frictions become BLOCKERS under concurrency):**
The DIR-048 archguard proof logged two env/config frictions that a single-task driver worked around by
hand but that BREAK an autonomous N-wide run (N builds, no human to rescue each):
- **B1 — `gate_run` ignores `gates.yml` `timeoutMs`:** the quay `gate` MCP timed out at a 60s default
  despite `.quay/gates.yml` `timeoutMs: 300000`; archguard's suite needs ~137s. In the DIR-048 single
  run the driver fell back to a manual `npx vitest run`. Under concurrency, ALL N builds hit this and
  there is no per-build manual rescue → every build fails its gate. `gate_run` MUST read the workspace
  gate `timeoutMs` first (a DIR-046 gate-ergonomics fix).
- **B2 — isolate does not sync untracked-but-needed files:** the build worktree lacked an untracked
  fixture (`.agents/skills/.../archguard-project-semantics.json`); the driver copied it in by hand.
  N worktrees each need it → the isolate step must sync untracked-but-required files (or the skill's
  `deps-ready` invariant must cover them).
These are folded in as **DIR-049 prerequisites** (fix first, small, independently valuable).
