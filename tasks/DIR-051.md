## Proposal
The portable loop-driver today does ONE thing: SELECT a ready task and drive it (task-driven). But the
highest-value discovery in this experiment came NOT from the ready queue — every product DIR
(DIR-037/039/040/041/042) came from a human manually dogfooding/auditing, and every recent milestone
(DIR-044/048/049/038) surfaced real defects only via ad-hoc fresh-context adversarial audits. Formalize
that into a **standing, configurable ROUTINE track** parallel to the SELECT track.

Add an OPTIONAL `routines:` key to `.quay/loop.yml` (additive; absent = today's behavior exactly):

```yaml
routines:
  - name: self-validation           # a label
    trigger: every(5)               # every(N) | on(checkpoint) | on(idle) | on(<condition>)
    dispatch: adversarial-explore   # the kind of background agent to fire (a fresh-context probe)
    files: tasks                    # findings become evidence-backed tasks on the board
    gate: quality-dedup-rate        # a filed finding must pass a quality/dedup/rate gate (no spam)
```

**Control flow (skill orchestrates; opt-in):** each iterate, AFTER SELECT (or when the queue is idle),
the driver evaluates each routine's `trigger` against the loop state (iteration/milestone counter,
checkpoint boundary, idle). A due routine DISPATCHES a background agent (`execution: dispatched` infra,
DIR-048) to perform its `dispatch` action; the agent's findings are filed as `## Finding`-bearing tasks
onto the board, each passing a `gate` (quality: is it real + actionable; dedup: not already filed;
rate: ≤ K new per window) before landing — so a routine industrialises discovery without spamming the
queue. Routines NEVER auto-execute their own findings (they only FILE tasks; the SELECT track drives
them under the normal gates/audit), preserving the human/SELECT approval boundary.

`readLoopParams` parses `routines` (optional, default `[]`), validating each entry (name + a well-formed
trigger + dispatch action), fail-closed on a malformed routine. Pure in-repo skill capability, additive
and opt-in → **LOOP-EXECUTABLE** (`milestone-candidate`; edits the PORTABLE skill, not exp5's OUTER-LOOP).

**Why a mechanism (DIR-051), not just two routines.** [[DIR-052]] (self-validation) and [[DIR-053]]
(architecture-analysis) are the first two riders; making the trigger/dispatch/file-gate loop generic
means any future standing concern (external dogfooding — cf. [[DIR-043]] — competitive bench, coverage
sweep) is a config entry, not another skill rewrite. Single mechanism, many routines.

**Out of scope:** the specific routines (DIR-052/053 author those); auto-executing routine findings
(they FILE tasks only); exp5's OUTER-LOOP (its own bespoke dogfood cadence stays; this is the portable
skill's mechanism, which exp5 may later adopt).

  non-task-driven track.

- DIR-052/053 both want "periodically dispatch a background probe + file findings" — the same shape → a
  single generic routine mechanism serves both (and DIR-043).
