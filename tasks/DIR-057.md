## Proposal
exp5's OUTER-LOOP runs strictly SERIAL (the `concurrency: 2` in its `.quay/loop.yml` is INERT — OUTER-LOOP
is bespoke and does not read that key; the portable skill's DIR-049 concurrency is a different code path).
Serial is the correct DEFAULT because BAIME's two-layer model runs on a **SELECT←ABSORB learning loop**:
each milestone's ABSORB updates the method (inherited-core / ρ / calibration / value-ledger) and the next
milestone's SELECT reads it. Running two methodology milestones concurrently = the second SELECTs stale
method state — an exp4 pathology, the exact thing the experiment guards against.

**But a real safe subset exists, with real cost.** The recent TS-P3 run is the proof: M80/M81/M84/M85
(native / github / gate / serve+mcp ports) were **touches-disjoint and carried no learning dependency**
(porting different files; nothing learned between them), yet ran serially 24–80 min each — ~3h wall-clock
that concurrency 2–4 could have compressed to ~1h. With **substantial feature development still ahead**,
migration/refactor/sweep-heavy stretches will keep producing such independent mechanical clusters. A
narrow, hard-gated concurrency lane is worth it.

**The design — build-concurrent / fan-in-ABSORB-serial (reuse DIR-044, do not re-implement):**
Concurrency lives ONLY in the BUILD+AUDIT phase; the fan-in ABSORB stays SERIAL, so every milestone still
gets its own clean ABSORB bookkeeping (VT append, Δv calibration, ρ, checkpoint, DoD meta-enforcer,
dashboard summary row) and ledger integrity is preserved. OUTER-LOOP calls the existing DIR-044 scripts
(`concurrent-batch-scheduler` → dispatch N → `anti-drift-touches-check` HARD → `serial-fanin-absorb`) —
single-source, no re-implementation.

**The exp5-specific hard gate — an EXECUTABLE batch-eligibility predicate (ADR-004, not a prose rule or a
hand-label).** A milestone may enter a concurrent batch IFF, mechanically:
1. its value-type is **capability-growth** (NOT governance-integrity / instrument-correction); AND
2. it declares a `## Touches` set; AND
3. its `## Touches` is DISJOINT from the method-surface allowlist
   `{inherited-core.md, OUTER-LOOP.md, .quay/gates.yml, scripts/it0-*, dashboard mechanics, value-ledger}`
   — i.e. it does not modify the method itself.
Methodology milestones fail (1) or (3) → never batched → always serial. This is layered ON TOP of DIR-044's
touches-orthogonality (which already enforces mutual disjointness on real diffs).

**The safety is itself golden-testable.** If a batch is truly learning-independent, running it CONCURRENTLY
must yield the SAME per-milestone ABSORB results as running it SERIALLY. So the golden-replay proof (serial
== concurrent, same ABSORBs) IS the correctness proof of the eligibility predicate: any divergence means a
hidden dependency slipped the gate → the predicate is wrong, fail closed.

**Human-steered + golden-replay.** This edits OUTER-LOOP.md — the load-bearing driver-self-rewrite file
(DIR-027/030 fence). It MUST be authored human-steered, off-loop, behavior-preserving under golden-replay;
never a mid-loop autonomous self-rewrite. A false "safe" verdict = an exp4-class regression, so blast radius
is high and the gate must be bulletproof.

**Out of scope:** general OUTER-LOOP concurrency (only the eligible subset batches); the portable skill
(DIR-049 already does N-wide there); methodology/golden-diff-sensitive milestones (P4 method-infra ports,
crystallization, ledger/gate changes — permanently serial); changing any ABSORB bookkeeping (fan-in stays
serial and identical to today).
