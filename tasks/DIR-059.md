## Proposal

Split the repo-wide `tsc --noEmit` type-check into per-package invocations (each against its own
tsconfig, scoped to just that package's files) instead of the current single root-level
`npx tsc --noEmit` run — to bound peak memory per invocation and stop it from being the thing that
OOM-kills the host.

Context (established this conversation, 2026-07-22): the currently-wired `ts-typecheck` gate in
`.quay/gates.yml`/`.quay/config.yml` (`command: "npx tsc --noEmit"`, no `-p`, so it resolves the root
`tsconfig.json` which covers all 4 packages' `src/**` + `bin/**` in one compiler invocation) is the
proximate cause of **three confirmed OOM kills on this host today** (`orangevps`), each of which took
down an entire Claude Code session process running the autonomous loop:

```
Jul 22 12:07:48  Out of memory: Killed process 3684395 (tsc) anon-rss:3887208kB (~3.9GB)
Jul 22 15:18:09  Out of memory: Killed process 3886934 (tsc) anon-rss:4164032kB (~4.2GB)  -> killed session 4d2e9f2d-...
Jul 22 15:41:47  Out of memory: Killed process 3894831 (tsc) anon-rss:4520296kB (~4.5GB)  -> killed session f8266dcf-...
```

(confirmed via `sudo dmesg -T` / `sudo journalctl -k`; host is `orangevps`, 7.8GB total RAM). A single
root `tsc --noEmit` invocation now routinely peaks at 4-4.5GB anon-rss and is climbing as more `.ts`
files accumulate (P3/P4/P5 phases keep adding files to the same one compiler invocation). A 4GB
persistent swapfile was added this conversation as an immediate mitigation (`/swapfile`, in
`/etc/fstab`), confirmed via `sudo swapoff /swapfile && sudo swapon -a` — this makes a peak survive
(slower, not killed) but does not address the root cause: one compiler process re-parsing and
type-checking the union of all 4 packages' code (plus the MCP SDK's type definitions 4 times over,
once per package that imports it) every single invocation, when most callers (a single milestone's
gate check, a human's ad-hoc verification) only need ONE package re-checked.

Splitting into per-package tsconfigs directly reduces peak memory (each invocation only loads that
package's own dependency graph + its own copy of `@modelcontextprotocol/sdk` types, not all 4 at
once) and, as a side effect, also allows partial/parallel checking and clearer per-package error
attribution (already visible in this conversation's `tsc --noEmit -p .` output: `quay-github` and
`quay-backlog` are the ones with new TS2339 errors, but the current single invocation can't tell you
"only 2 of 4 packages have errors" — you get the whole flat list of everything, unattributed).

## Finding

1. Root `tsconfig.json`'s own header comment (`"//": "..."`) explicitly documents it was authored as
   ONE root config on purpose: *"Covers the npm workspaces (packages/*, per root package.json's own
   `workspaces` field) ... from one root invocation — no per-package tsconfig needed at this phase."*
   — a P0-era (pre-migration) decision, made before any files existed to check, that has not been
   revisited despite the codebase growing to 40+ `.ts` files across 4 packages.
2. The `ts-typecheck` gate is wired in exactly 2 places (both must change together — this is NOT a
   projection/dual-source risk since both files declare the same gate list independently per
   ADR-013's data-driven-gates discipline, not a copy of each other):
   - `.quay/gates.yml:100-101` — `name: ts-typecheck / command: "npx tsc --noEmit"`
   - `.quay/config.yml:57-58` — same `name`/`command` pair
3. No per-package `tsconfig.json` files exist yet anywhere under `packages/*/` (verified:
   `find . -maxdepth 3 -iname "tsconfig*.json" -not -path "*/node_modules/*"` returns only the root
   file).
4. Confirmed via `sudo dmesg -T` / `sudo journalctl -k` (kernel-level, not inference): 3 separate OOM
   kills of a `tsc` process today, 2 of which took an entire autonomous-loop Claude Code session down
   with it (see the exact log lines quoted in Proposal above).

## Requested action

1. Create one `tsconfig.json` per package (`packages/quay/tsconfig.json`,
   `packages/quay-native/tsconfig.json`, `packages/quay-github/tsconfig.json`,
   `packages/quay-backlog/tsconfig.json`), each `"extends"`-ing the root config's `compilerOptions`
   (do not duplicate the options — single source stays the root file) and narrowing `include` to just
   that package's own `src/**` and `bin/**`.
2. Update the `ts-typecheck` gate's `command` in BOTH `.quay/gates.yml` and `.quay/config.yml` to loop
   over the 4 per-package tsconfigs (e.g. `for d in packages/*/; do npx tsc --noEmit -p "$d" || exit 1;
   done`) instead of one bare `npx tsc --noEmit` — PASS iff all 4 exit 0, matching the existing
   `makeTestPassGate` "PASS iff exit 0" contract unchanged.
3. Keep the root `tsconfig.json` itself as a convenience/CI-parity aggregate (some callers may still
   want a single "does the whole repo typecheck" answer) but it is NO LONGER the gate's own command —
   the gate calls the per-package configs.
4. Verify: golden-diff on the gate — same PASS/FAIL verdict on the current tree before/after this
   change (i.e., this change must not silently mask or newly surface errors relative to the root
   invocation's verdict on the SAME code state); AND measure peak RSS per per-package invocation
   (`/usr/bin/time -v npx tsc --noEmit -p packages/<pkg>` or equivalent) to confirm each is materially
   lower than the ~4-4.5GB root baseline recorded in Finding.

## Human verification when the experiment marks this done

1. `cat packages/quay/tsconfig.json` (and the other 3) — confirm each `extends` the root config and
   scopes `include` to only its own package.
2. `grep -n "command:" .quay/gates.yml .quay/config.yml` near `ts-typecheck` — confirm it's a
   per-package loop, not the old bare `npx tsc --noEmit`.
3. Re-run the gate on the real repo and compare its RSS peak (`/usr/bin/time -v` or watch `ps` during
   the run) against the ~4-4.5GB baseline this directive recorded — a number close to or above the old
   baseline is a red flag that the split didn't actually reduce per-invocation memory (e.g. if the loop
   still somehow re-parses everything, or `skipLibCheck`/project-reference caching wasn't configured
   correctly).

   from demo/fixture evidence (a synthetic test asserting the command string changed, without an actual
   run's memory numbers).
