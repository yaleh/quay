## Proposal

Context (established this conversation, 2026-07-23, while attempting the first post-TS-migration
release): the M116 `bin/*.js` → `bin/*.ts` migration (commit `3667b02`) turned every package's CLI
entrypoint into a `.ts` file executed via its shebang. Native `.ts` execution (Node's
strip-types) requires Node **>= 23** (22.6+ behind a flag), but this project declares a **Node >= 20**
floor (README "Install" section; each package's `package.json` `engines`) and the CI/release workflows
pin **Node 20**. The result is a live distribution regression: the shipped/publishable artifacts no
longer run on the floor they claim to support.

Approach: pick ONE coherent Node-execution story for distributed artifacts and make README, every
`package.json` `engines`, `.github/workflows/{ci,release}.yml`, the plugin's `.mcp.json`, and (where
relevant) the SEA build all agree on it — enforced by a check that actually runs an artifact on the
declared floor. Two viable directions (the resolving milestone picks and justifies one):
(a) **Transpile-on-publish** — keep authoring in `.ts` but ship `.js` (esbuild, already used by the
SEA build) in the npm-pack tarball and the plugin's vendored Core, so distributed bins run on Node >=20
unchanged; OR (b) **Raise the floor to >= 23** consistently everywhere and bump CI/release runners,
accepting that downstream consumers (e.g. archguard, whose own `engines` is `>= 18`) must be on >= 23.
Direction (a) is the lower-blast-radius default; (b) is simpler but pushes the constraint onto every
consumer.

## Plan

N/A — directive resolved via a milestone; no staged plan. The shape is well-defined (one execution
story, propagated to ~5 declaration sites + one runnable floor-check); the resolving milestone chooses
direction (a) or (b) with justification.

## Finding

Evidence gathered this conversation (all verified, not inferred):

1. **CI + release are red on this exact cause.** The `v0.3.5` release attempt (tag pushed then deleted
   this session) failed: `release.yml`'s "Run tests" step and the separate `CI` workflow both threw
   `TypeError [ERR_UNKNOWN_FILE_EXTENSION]: Unknown file extension ".ts"` on Node 20
   (`packages/quay-native/bin/quay-native.ts`, `.../src/store.ts`). The SEA `sea-verify-node-free` job
   ALSO failed, but on the separate `exp5-DEFECT-QUAY-CORE-SEA-BUILD-CRASH` cause (`import.meta.url`
   undefined in the CJS SEA bundle) — that defect is related but distinct; see cross-link below.
2. **The plugin will break on next publish.** The installed plugin cache
   (`~/.claude/plugins/cache/quay/quay/0.3.20/`) still ships `vendor/quay/bin/quay.js` and an
   `.mcp.json` pointing at `quay.js` — so it works TODAY only because it predates the rename. The
   current source `plugin/.mcp.json` already points at `quay.ts`, and `plugin/scripts/sync-vendor.sh`
   only `cp`s bin/src verbatim (no transpile) — so the NEXT plugin publish carries `quay.ts` and
   breaks for every consumer on Node < 23.
3. **The floor is declared >= 20 in multiple places.** README "Install" ("Requires Node.js >= 20"),
   each `packages/*/package.json` `engines`, and both workflows pin/assume Node 20. None was updated
   when the `.ts` entrypoints landed.
4. **Local dev masks it.** This dev host runs Node v25.2.0, so `.ts` shebang bins run fine here and the
   autonomous loop (which only runs LOCAL test suites, never the GitHub Actions workflows) never
   surfaced the regression — it was invisible until an actual release was attempted.

Cross-link: `exp5-DEFECT-QUAY-CORE-SEA-BUILD-CRASH` (the SEA binary's own `import.meta.url` startup
crash) is a SEPARATE distribution defect in the same neighborhood; this directive does NOT close it,
but a resolving milestone should sequence the two so a release can be cut once BOTH are fixed.

## Requested action

1. Choose ONE Node-execution story for distributed artifacts (transpile-on-publish to `.js`, OR raise
   the floor to >= 23) and apply it consistently to: README install/engines prose, all 4
   `packages/*/package.json` `engines`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`,
   `plugin/.mcp.json` (+ whatever `sync-vendor.sh` produces), and the SEA build inputs where relevant.
2. Add a **runnable floor-check**: build the npm-pack artifact (and, if direction (a), the plugin's
   vendored Core) and execute `quay --help` (and one `task list`) under the DECLARED floor Node
   version in CI — PASS iff exit 0. This is the mechanical guard that would have caught the regression.
3. Re-run the release workflow green end-to-end on a throwaway/pre-release tag (or a `workflow_dispatch`)
   BEFORE cutting a real version tag, so "release is green" is demonstrated, not assumed.
