## Proposal

Context (established this conversation, 2026-07-23, from a delivery-scope audit + a read-only
inspection of the real downstream consumer `/home/yale/work/archguard`): the intended productized
delivery is **all 4 packages (`quay`, `quay-native`, `quay-github`, `quay-backlog`) + the Claude Code
plugin**, but the current release pipeline delivers only a fragment of that, ships it with pervasive
version drift, and provides no coherent way for a foreign workspace to actually install the pieces it
needs. This directive scopes the delivery to that full set and pins it with fail-closed executable
invariants (the repo's own single-source + executable-invariant discipline, applied to the release
surface itself).

Approach: (1) decide and DOCUMENT the delivery manifest — exactly which artifacts constitute a
release (npm tarballs for which packages? SEA for which? the plugin as a marketplace-installable
unit?) — as machine-readable data, not prose; (2) make `release.yml` build/test/publish every artifact
on that manifest; (3) unify versioning so a single source drives all package + plugin + manifest
version numbers, with a check that FAILs on drift; (4) close the foreign-workspace install gap so a
project like archguard can install "the plugin + the providers it spawns" as one coherent step; (5)
prove it end-to-end against archguard (install → `loop-driver` can SELECT + write task status through
the real Provider ABI). This is a design-carrying milestone — it likely warrants quay-task-to-plan and
SPLIT into board children per DIR-026.

## Finding

Evidence gathered this conversation (verified against the real repo + a read-only inspection of
`/home/yale/work/archguard`; the archguard tmux Claude Code session was NOT driven — filesystem/git
only):

1. **Only a fragment is packaged.** `.github/workflows/release.yml` runs `npm pack` for `quay` (Core)
   ONLY; SEA builds cover `quay` + `quay-native` only; `quay-github`'s tests are explicitly EXCLUDED
   from the release test gate; `quay-github` and `quay-backlog` have no `package.sh` and are never
   published. The delivery is Core-plus-native at best, not "4 packages".
2. **The plugin ships Core but not the Providers it must spawn.** The installed plugin cache
   (`~/.claude/plugins/cache/quay/quay/0.3.20/`) vendors ONLY `vendor/quay` (Core) and launches it via
   `.mcp.json` → `node .../vendor/quay/bin/quay.js mcp`. But Core's entire job is to spawn the active
   Provider's `mcp_entry` as a child. archguard's `.quay/config.yml` sets
   `mcp_entry: ["quay-native", "mcp"]` → Core must find a bare `quay-native` on PATH. The plugin does
   not provide it.
3. **The Provider bins are not actually installed anywhere resolvable.** In archguard I verified
   (`which quay-native/quay-github` empty; not in npm global prefix `~/.nvm/.../v25.2.0/bin`; not in
   archguard's `node_modules`; whole-home `find` found nothing) — the config's documented "installed to
   user scope via npm link" is NOT currently satisfied. The one gate that produces GateEvents there is
   `npx vitest run` (workspace data, does not touch quay), so the Provider-MCP path (SELECT / task
   status write) has no shipped install mechanism and its live resolution is unverified.
4. **Pervasive version drift — five different numbers for the same plugin.** installed cache =
   `0.3.20`; `plugin/.claude-plugin/plugin.json` = `0.3.22`; `plugin/.claude-plugin/marketplace.json`
   plugin entry = `0.3.16`; root `.claude-plugin/marketplace.json` = `0.3.5`;
   `plugin/vendor/quay/package.json` = `0.3.5`. The 4 packages are independently `0.3.5 / 0.3.4 /
   0.1.0 / 0.1.0`. `plugin/test/plugin-packaging.test.mjs` pins 5 packaging invariants but NONE checks
   version consistency, so the drift went undetected.
5. **What a foreign workspace actually needs (the delivery target), from archguard:** (a) the plugin
   = 4 skills (author/execute/loop-driver/quay-directive) + the vendored Core MCP; (b) the Provider
   entrypoints Core will spawn, on PATH (native at minimum; github for `--provider github`); (c) the
   workspace's own `.quay/config.yml` (provider map + gates + loop — authored per-project, not shipped);
   (d) a native task store dir. quay currently ships (a)-minus-providers and nothing for (b).

Cross-cutting dependency: DIR-060 (the `.ts` × Node-floor regression) blocks any actual release, so
this directive's end-to-end proof cannot land until DIR-060 is resolved. Sequence DIR-060 first.

## Requested action

1. Author a machine-readable **delivery manifest** (e.g. a checked-in JSON/YAML listing every artifact
   a release must produce: which packages get npm tarballs, which get SEA binaries, the plugin as a
   marketplace unit) — the single source the release workflow and the completeness check both read.
2. Extend `.github/workflows/release.yml` to build, test, and publish EVERY artifact on that manifest
   (all 4 package tarballs as decided; the plugin bundle), replacing the current Core-only path.
3. Unify versioning: one source of truth drives all 4 package versions + the plugin's 3 manifest
   version fields + the vendored-Core version, with a **fail-closed check** (extend
   `plugin/test/plugin-packaging.test.mjs` or add a sibling) asserting they are equal on every commit.
4. Close the foreign-workspace Provider-install gap: EITHER have the plugin vendor/bundle the Provider
   entrypoints too, OR ship a documented, runnable install step that puts `quay-native`/`quay-github`
   on PATH — decided and implemented, not left to a per-project `npm link` the config only mentions in
   a comment.
5. Prove it end-to-end against archguard (or an equivalent clean foreign workspace): after install, the
   plugin's `loop-driver` can SELECT a task and write its status back through the real Provider ABI —
   i.e. a real `task_write`/status transition observed, not a dry `--help`.
