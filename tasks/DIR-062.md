## Proposal

Context (this conversation, 2026-07-23): a review of the `human-steered` label found it was applied
by judgment with three distinct implicit meanings, and one of them (DIR-035) was a pure misapplication.
The human then TIGHTENED the semantics. This directive crystallizes the tightened definition into an
executable, single-source form so SELECT can decide "may the loop take this autonomously?"
mechanically, instead of by per-task human judgment.

**Tightened `human-steered` definition (authoritative).** A task is `human-steered` iff at least one:
1. **Driver-self-rewrite** — it edits the loop's own driver files (`OUTER-LOOP.md`, `inherited-core.md`,
   inner-iteration prompts). Bootstrap hazard; requires halt + golden-replay. UNCONDITIONAL (independent
   of any registry or environment).
2. **Mission redirection** — it changes the loop's PRIMARY value source / objective away from developing
   quay itself (e.g. adopting a foreign repo as the successor value source). This is not "do under human
   steering" — it is simply OUT OF SCOPE / rejected (see DIR-036).
3. **Un-authorized cross-workspace drive** — it remote-drives a workspace's Claude Code / tmux session
   that is NOT covered by the drivable-workspaces registry. Once a workspace is registered (a durable,
   loop-readable human authorization), driving it is NO LONGER human-steered.

**Newly autonomous (was previously fenced):** using REGISTERED foreign workspaces (all of
`/home/yale/work/*`, per the human's 2026-07-23 declaration) as validation / experimentation instruments
for quay's own product + methodology development — including remote-driving their sessions, filing
findings, running e2e proofs. The distinguishing test is INSTRUMENT vs MISSION: a bounded validation
using a foreign workspace is fine (clause 3, registry-gated); making a foreign repo the loop's ongoing
objective is not (clause 2).

Approach: (1) record the tightened definition in the canonical methodology docs; (2) the registry
`experiments/quay-perpetual-stream/drivable-workspaces.yml` is the single source of clause-3
authorization (created this conversation as the durable record of the human declaration); (3) build a
fail-closed gate that refuses any task driving a workspace not covered by the registry; (4) wire SELECT
so `human-steered` is computed as `driver-edit OR mission-redirection OR drives-unregistered-workspace`.

## Finding

Established this conversation (2026-07-23):

1. **The old label conflated two things** — "foreign product" (archguard IS a different codebase) vs
   "not under quay's control" (FALSE — the whole host `/home/yale/work` is the same operator's quay
   experimental substrate). The real hazards were never "it's a different codebase"; they were
   **driver-contention** (a human/another driver typing in the same session) and **mission-drift**
   (the loop adopting a foreign repo as its objective). The tightened definition separates these.
2. **The authorization must be loop-readable, not chat-only.** The autonomous loop runs in independent
   sessions and cannot read this conversation. "I declare archguard drivable" only becomes operative if
   recorded in a durable, single-source, gate-checkable place — hence the registry file + a fail-closed
   gate (the repo's own "single source of truth + executable invariant over prose" discipline).
3. **The human declaration (2026-07-23):** the current server is entirely quay's experimental substrate;
   ALL projects under `/home/yale/work` are authorized drivable validation targets — recorded in
   `drivable-workspaces.yml` (`authorized_root: /home/yale/work`, `scope: validation`).
4. **Immediate dispositions that follow (done this conversation):** DIR-035 was a clause-mismatch and
   was closed; DIR-036 (parent, "foreign repo as SUCCESSOR VALUE SOURCE") is exactly clause-2 mission
   redirection → rejected; DIR-036-B (bounded V_meta transfer-test validation) → superseded by DIR-061,
   and becomes autonomous-eligible under this registry once the gate lands.

   GREEN case: a task targeting `/home/yale/work/archguard`).

   `edits-driver-files OR is-mission-redirection OR drives-a-workspace-the-registry-does-not-cover`,
   replacing per-task hand-labeling — with the existing `label:human-steered` retained only as a manual
