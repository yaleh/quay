## Finding

`quay serve` currently hardcodes binding to `0.0.0.0` (all interfaces) with no way to restrict it to a specific interface.

1. **`packages/quay/src/serve.ts:90`**: `server.listen(port, "0.0.0.0", ...)` — host is hardcoded.
2. **`StartServerOptions` interface**: only `port`, no `host`.
3. **CLI usage**: `quay serve [--port <port>]` — no `--host`.

## Requested action

Add a `--host` option to `quay serve` that passes through to `StartServerOptions` and `server.listen()`. Default remains `0.0.0.0` (backward-compatible).

## Proposal

Source: adjudicated, 2026-07-24, minimal-surface-area + pattern-consistency (converged)

Problem framing: `quay serve` hardcodes binding to `0.0.0.0` with no CLI option to restrict to a specific interface, limiting security-hardening (localhost-only), Tailscale/VPN binding, and multi-instance deployment.

Approach: Add `host?: string` to `StartServerOptions` in `packages/quay/src/serve.ts`, thread through to `server.listen(port, host, callback)` defaulting to `"0.0.0.0"`, add `--host <host>` CLI flag in `packages/quay/bin/quay.ts`, update help text (line 314) and log line (line 91). ~30 lines total, fully backward-compatible.

Key design decisions:
- `host` is optional (`string | undefined`), defaulting to `"0.0.0.0"` at the `server.listen()` call site — minimal diff, no change to existing callers.
- CLI flag `--host <host>` parsed via existing `parseFlags()` and passed through to `startServer({ port, host })`.
- Log line changes from `http://0.0.0.0:${port} (all interfaces)` to `http://<host>:${port}` — reflects the actual bound address.

Alternatives considered and rejected:
- Environment variable `QUAY_SERVE_HOST` — rejected: CLI flag is more discoverable, consistent with `--port`, and avoids env-var sprawl.
- Combined `--bind host:port` flag — rejected: over-engineered for the scope; inconsistent with existing `--port` pattern.
- Make `host` required — rejected: would force every internal/test caller to specify it explicitly.
