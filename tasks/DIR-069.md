## Finding

The routine track (step 5a, DIR-051/056) currently has three probes — self-validation (code-only), architecture-analysis (archguard, structural), history-mining (meta-cc, session history). None exercise quay's Web UI surface (`quay serve`) with a real browser. Gap analysis:

1. **ADR-010** (`adr/ADR-010-scheduled-milestone-e2e-incl-browser-tests.md`, status: `proposed`) explicitly calls for "a hard, scheduled mechanism running e2e tests — including browser tests (via Playwright / chrome-devtools) — at milestone frequency" to keep L_T on the real product axis. Its enforcement is explicitly **deferred/unwired** ("enforcement (E3, deferred)"). This directive provides the mechanism ADR-010 needs.

2. **`inherited-core.md`'s Web UI verification rule (lines 519-568)** mandates `mcp__playwright__*` / `mcp__chrome-devtools__*` tool-call traces for any milestone Done-when clause claiming Web UI rendering/interaction verification — but this only fires when a milestone explicitly scopes browser work. There is no standing, milestone-independent browser probe that continuously discovers defects in the current deliverable regardless of what the milestone claims.

3. **`serve-browser-render.test.mjs` (QN-046)** proved the value of real browser exploration: it found a genuine production bug (charset encoding causing "Quay â€"" display) that all curl/unit tests missed. But it cannot run standalone (`node --test`) — it requires MCP tooling — and is not wired as a routine probe.

4. **None of the three existing probe specs** mention chrome-devtools or playwright. The `self-validation` probe reads code but never launches `quay serve` or navigates a browser to it.

Net: the Web UI surface is dark to the routine track. A defect in rendering, interaction, or visual coherence can persist across many milestones with zero automated detection — exactly the DIR-006 pattern (narrative claims of "real browser" backed by curl-only evidence), but at the routine level rather than the milestone level.

## Requested action

Create a fourth routine probe — `browser-explorer` — that uses chrome-devtools or playwright MCP tools to explore the live `quay serve` Web UI and file evidence-backed findings for defects, interaction issues, and visual regressions.

Scope (as a probe spec + wiring, NOT a full product feature):

1. **Author `plugin/probes/browser-explorer.md`** — a probe spec following the existing pattern (instrument, fallback, output_routing frontmatter + objective prompt). Instrument: `chrome-devtools` (primary) with `playwright` fallback. The objective: launch `quay serve`, navigate the Web UI (list → detail → filter → search → action flows), take screenshots at dual viewports (desktop 1280×800 + mobile 390×844 per inherited-core.md), find rendering defects, interaction bugs, and visual regressions. File each finding as a task with concrete evidence (screenshot paths, DOM snapshots, tool-call traces).

2. **Wire into the routine track** — add `trigger: every(10)` (same cadence as architecture-analysis/history-mining) with `probe: browser-explorer` in `.quay/config.yml`'s `loop.routines:`.

3. **Instrument availability check** — the `/run-routines` workflow's Dispatch phase already checks MCP server availability and skips with `filed: false` if unavailable (line 60-63 of `run-routines.js`). The probe must declare `instrument: chrome-devtools` and `fallback: playwright` — the dispatch agent tries chrome-devtools first, falls back to playwright, skips if neither is available.

4. **FILE-ONLY invariant** — the probe explores the CURRENT build (launches `quay serve` on a temp port, navigates, takes screenshots, kills the server). It writes findings as task files only — never modifies product code, method docs, or config. The existing Verify phase of `/run-routines` enforces this via `git status --porcelain`.

5. **Output routing** — `defect: milestone-candidate`, `regression: milestone-candidate`, `default: milestone-candidate`. Routine-file-gate handles quality/dedup/rate gating.

## Acceptance Criteria

- [ ] `.quay/config.yml` `loop.routines:` includes `browser-explorer` with `trigger: every(10)` and `probe: browser-explorer`.
- [ ] `routine-scheduler.ts` parses the new routine entry without error (valid trigger + probe).
- [ ] Manual smoke: invoking `/run-routines` with chrome-devtools MCP available dispatches the browser-explorer probe, which launches `quay serve`, navigates, takes screenshots, and files findings as task files — or returns `filed: 0` if no defects found.

- [ ] FILE-ONLY invariant holds: no product/method code modified by the probe run.
