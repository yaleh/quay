## Finding

Session `b643aa4d` (2026-07-24) ran `execute-milestone` 6 times: 5 at Verify phase, 1 resume that passed Verify → Build → Audit but failed at Gate. The Verify phase failure rate is 83% (5/6). Each failure costs 5–9 minutes (5 parallel agents), and each failure triggers a near-identical manual debug loop:

```
读 workflow journal → 找到失败的检查 → 理解失败原因 →
修复 charter 或 task → 删除 .halt → 重新调度 workflow
```

This loop takes 5–10 turns (another 3–5 minutes) and is entirely manual. The specific failures observed:

| Run | Failing Check | Root Cause |
|-----|--------------|------------|
| wf_1caf91bd-719 | ceiling-check | Charter cited directive IDs with stale `dirStatus` |
| wf_7782a177-2a6 | gate-hash-check | ITERATION-PROMPTS.md HARD GATES block hash mismatch |
| wf_d6a5bda0-fdd | ceiling-check | Same class — charter→task alignment not yet corrected |
| wf_1fc8d8f8-4ef | gate-hash-check | Same class — hash still mismatched after partial fix |
| wf_75338146-5cf | ceiling-check | M136 charter: directive IDs cited but not yet drained |

The pattern is mechanical: read journal → identify which of 5 checks failed → diagnose from the agent's detail output → apply fix to charter/task → retry. An encapsulated diagnostic workflow can:

- Automatically read the workflow journal and identify failed checks
- Produce a structured diagnostic report (which check failed, why, what to fix)
- For simple fixable cases (stale `dirStatus`, hash mismatch), attempt the fix automatically
- For complex cases, produce a clear human-actionable report instead of requiring the loop to dig through journal JSONL

## Requested action

### 1. `/diagnose-verify-failure` workflow

Saved workflow at `.claude/workflows/diagnose-verify-failure.js`. Phases:

- **Read journal:** Read the most recent `execute-milestone` workflow journal from the session's workflow directory. Extract per-agent results (ceiling-check, gate-hash, domain-misfit, line-budget, dogfood-evidence).
- **Classify failure:** For each agent that returned `ok: false`, classify the failure type:
  - `stale-directive` — charter cites directive IDs with non-`applied` `dirStatus` → auto-fixable: `task_write dirStatus: applied` on cited directives
  - `hash-mismatch` — gate-hash-check failed → auto-fixable: re-compute hash from ITERATION-PROMPTS.md and update charter
  - `line-budget-exceeded` — charter exceeds ~2000-line ceiling → needs charter split/trim (complex, human action recommended)
  - `domain-misfit` — §3.2 ceiling trigger → needs scope redesign (complex)
  - `dogfood-evidence-gap` — missing pasted evidence → inner iteration issue, send back
- **Auto-fix (simple cases):** For `stale-directive`: run `task_write dirStatus: applied` on each cited stale directive. For `hash-mismatch`: compute current HARD GATES hash and update charter. Return `{fixed: true, actions: [...]}`.
- **Diagnose (complex cases):** For `line-budget-exceeded` and `domain-misfit`: produce structured diagnostic with the specific scope issue and suggested resolution. Return `{fixed: false, diagnosis: {...}}`.
- **Verify fix:** Re-run only the failed check(s) against the updated charter/task. Return `{diagnosis: {...}, autoFixed: [...], retryReady: true|false}`.

### 2. Integration with `/execute-milestone`

When `/execute-milestone` returns `{outcome: "needs-human", phase: "Verify"}`, the outer loop invokes `/diagnose-verify-failure` before manual investigation. If `retryReady: true`, immediately re-invoke `/execute-milestone`. Only escalate to human attention when `retryReady: false`.

### 3. OUTER-LOOP.md update

The step 4 retry block gains a one-line invoke of `/diagnose-verify-failure` instead of the current ~10-turn manual debug prose.
