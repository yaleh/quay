## Proposal

Historical proposal: move the then-assumed asynchronous Build coordination protocol out of the
Build-agent prompt. The resolution below records why that premise was superseded by the installed
synchronous Build path; this section restores the schema heading without reviving the mechanism.

## Finding

The `execute-milestone` workflow's Build phase agent prompt contains ~30 lines of operational guidance that the agent CANNOT execute:

```
WAITING ON A LONG INNER ITERATION (background) — poll, don't conclude:
- The completion notification is the PRIMARY wake — dispatch as a harness-tracked
  background task so the loop is auto-re-invoked when the iteration finishes.
- Any ScheduleWakeup fallback (~1200–1800s) is a HANG-DETECTION HEARTBEAT, NOT a deadline.
- On a fallback wake: POLL the background task. Still running → re-arm the fallback and
  keep waiting; do NOT absorb, do NOT advance to the next phase.
- If the iteration waits on EXTERNAL STATE the harness can't track (e.g. a GitHub Actions
  run), poll that system's status explicitly and match the fallback to its cadence.
```

This is NOT executable by a Build-phase agent — it's the **caller's** operational protocol. The agent returns its dispatch result and exits. The real coordination (poll, fallback heartbeat, absorb gate) happens in the **outer loop**, not in the agent.

**Crystallization analysis (2026-07-24):** this requires NO LLM agent and NO new workflow. It is a **pure code refactoring** of `.claude/workflows/execute-milestone.js`:
1. Remove ~30 lines of coordination protocol from the Build agent's prompt string
2. Add JavaScript control flow after the `agent()` call that checks `buildResult.outcome` and returns `{outcome: "building", buildTaskId}` when appropriate
3. The OUTER-LOOP.md coordination logic (wait/poll/heartbeat/resume) is already prose-editable

The coordination logic IS the workflow script's control flow — `if (buildResult?.outcome === 'dispatched') return { outcome: 'building', buildTaskId }` is JavaScript, not something an agent executes. No new workflow file, no new script file. Just editing the existing `execute-milestone.js`.

## Requested action

### Direct edit to `.claude/workflows/execute-milestone.js`

Three changes:

**1. Shrink Build agent prompt (lines 48–93 → ~15 lines)**

Remove the `WAITING ON A LONG INNER ITERATION...` block (the ~30 lines of coordination protocol). Replace the Build prompt with:

```
CLASS-ROUTE per inherited-core.md's two-class diversity policy:
- DEVELOPMENT-class (capability-growth typed): run proposal→plan pipeline FIRST
  (invoke quay-task-to-plan skill), then implement with TDD ≥80% hard gate.
- METHODOLOGY/DESIGN-class (discovery/governance-integrity typed): whole-milestone
  independent dual-iteration (iteration-0 builds, iteration-1 re-derives from fresh worktree).

Per iteration: use baime:iteration-executor fed the charter (Tier-A) only. For
development-class, also feed the checked plan.

Dispatch the inner iteration as a harness-tracked background agent in an isolated git
worktree off master HEAD. Return the dispatch result — do NOT wait for completion.

TERMINATE on first of (§3.2): Done-when complete | ΔV<0.02 K=2 consecutive |
ceiling→redesign | past budget≈10 & nothing climbing | external HALT.

Return {taskId, outcome, iterationCount, mergeCommit, worktreePath, harnessTaskId}.
```

**2. Add post-Build coordination logic in script body**

After the Build `agent()` call (current line ~93), add:

```js
// If Build dispatched a background task (not yet complete), return building status.
// The caller (outer loop) handles poll/heartbeat/resume — NOT the Build agent.
if (buildResult?.outcome === 'dispatched' || buildResult?.harnessTaskId) {
  log(`Build phase dispatched background task: ${buildResult.harnessTaskId}`)
  return { outcome: 'building', buildTaskId: buildResult.harnessTaskId, phase: 'Build' }
}
```

**3. Update return schema and meta**

Add `buildTaskId` to the Build agent's return schema. Update the workflow `meta.description` to note the `building` outcome.

### OUTER-LOOP.md coordination (step 4 prose update)

The coordination protocol that was in the agent prompt moves to OUTER-LOOP.md step 4:
- When `/execute-milestone` returns `{outcome: "building", buildTaskId}`: the outer loop waits for harness-tracked background task completion (PRIMARY wake), sets ScheduleWakeup fallback (~1200–1800s) as hang-detection heartbeat, polls on fallback wake, resumes `/execute-milestone` from Audit phase on completion.

This is a prose edit, not a new mechanism.

## Resolution

2026-07-25: **Reverted then set `needs-human`.** DIR-074's core premise — "workflow agent
dispatches background task → returns `{outcome: building}` → outer loop polls/resumes" —
is fundamentally unsupported by the Workflow JS runtime. Agents inside workflows cannot
use `run_in_background: true` to dispatch subagents.

Commit `6b0765e` (2026-07-24) implemented the full pattern (reduced Build prompt ~45→20
lines, added `harnessTaskId` to schema, added post-Build `building` coordination logic).
Commit `549a3c3` (2026-07-25, ~14h later) discovered the runtime limitation and replaced
the dispatch model with synchronous execution ("DO THE ACTUAL WORK — you are the build
executor, not a dispatcher"), removing all of DIR-074's deliverables.

`needs-human` because the task is not just incomplete — the approach is proven non-viable
under current runtime constraints. Human must decide: (A) redesign — e.g. make OUTER-LOOP
(the main session) dispatch N concurrent workflows directly, each with synchronous Build;
or (B) abandon the goal and accept serial Build. A re-selected agent without this
guidance would retry the same broken dispatch pattern.

## Resolution, closed (2026-07-27)

Option **(B) confirmed as the permanent, working reality — not a still-open choice.**
Direct verification this session: `grep -n "ScheduleWakeup\|harnessTaskId\|building"
.claude/workflows/execute-milestone.js` finds no active code path (only a stale mention of
`"building"` in `meta.description`, left over from the reverted `6b0765e` attempt — the
Build phase itself has been fully synchronous since `549a3c3`); `grep -n "ScheduleWakeup\|
building" experiments/quay-perpetual-stream/OUTER-LOOP.md` returns zero matches — the
poll/heartbeat coordination text was never added there either, consistent with (B) having
been the outcome by default rather than a deliberate choice at the time.

Independent, extensive real-world evidence for (B) working: this session alone dispatched
20+ real `Workflow({scriptPath: ".../execute-milestone.js", ...})` calls from the top-level
orchestrating session — each one synchronous end-to-end (Verify→Build→Audit→Gate→Land in a
single call), with the harness's own `task-notification` as the sole completion signal, no
polling, no `ScheduleWakeup` heartbeat anywhere in the loop. This **is** option (A)'s spirit
(the main/orchestrating session is the one doing the dispatching and waiting), just applied
one milestone at a time rather than N-concurrent — dispatching several at once is a scheduling
choice for the caller, not something that requires DIR-074's abandoned in-workflow background-
dispatch mechanism.

**Disposition: DIR-074 is closed as resolved-by-default.** No further implementation is
requested — (B) already is what runs, verified working across dozens of real dispatches. If
genuine N-wide concurrent dispatch from the orchestrating session is ever wanted, that is a
new, separate concern (how the CALLER chooses to invoke `Workflow()` multiple times), not a
gap in `execute-milestone.js` itself. AC/DoD checkboxes above remain unticked (DIR-020 — they
describe the abandoned (A)-style mechanism, which was never built and is not being pursued);
this closure documents disposition, not retroactive completion. See also [[DIR-078]], whose
own premise depended entirely on this mechanism and is closed alongside it for the same reason.
