## Finding

The `execute-milestone` workflow's Build phase agent prompt contains ~30 lines of operational guidance that the agent CANNOT execute:

```
WAITING ON A LONG INNER ITERATION (background) — poll, don't conclude:
- The completion notification is the PRIMARY wake — dispatch as a harness-tracked
  background task so the loop is auto-re-invoked when the iteration finishes.
- Any ScheduleWakeup fallback (~1200–1800s) is a HANG-DETECTION HEARTBEAT, NOT a deadline.
- On a fallback wake: POLL the background task. Still running → re-arm the fallback and
  keep waiting; do NOT absorb, do NOT advance to the next phase.
- If the iteration waits on EXTERNAL STATE the harness can't track (e.g. a GitHub Actions
  run), poll that system's status explicitly and match the fallback to its cadence.
```

This is NOT executable by a Build-phase agent — it's the **caller's** operational protocol for managing the inner iteration lifecycle. The Build agent receives this text, processes it, and then… can't act on it. It returns its dispatch result and exits. The real coordination (poll, fallback heartbeat, absorb gate) happens in the **outer loop**, not in the agent.

This is a structural defect:
- Agent prompt balloons with non-executable instructions (~30 lines, ~15% of the total Build prompt)
- The actual coordination logic lives in prose that the outer loop agent must interpret anew each cycle
- Future edits to the coordination logic require editing the workflow script (which embeds agent prompts), not a separate coordination concern

The fix: move the coordination protocol from the Build agent's prompt into the workflow script's post-Build logic in `execute-milestone.js`. The agent prompt shrinks to what the agent actually does (class-route + dispatch); the coordination logic lives in the workflow script (the caller side), where it can be deterministically executed.

## Requested action

### 1. Extract coordination protocol into `execute-milestone.js`

In `.claude/workflows/execute-milestone.js`, after the Build phase `agent()` call returns:

- **Check Build outcome:** If `buildResult.outcome` indicates the inner iteration dispatched as a background task (not yet complete), record the harness task ID.
- **Coordination logic (in script, not agent prompt):** The workflow returns `{outcome: "building", buildTaskId: <harness-task-id>}` to the caller. The caller (outer loop) receives this and:
  1. Waits for the harness-tracked background task completion notification (PRIMARY wake)
  2. Sets a ScheduleWakeup fallback (~1200–1800s) as hang-detection heartbeat
  3. On wake: polls the background task. Still running → re-arm fallback. Complete → resume `/execute-milestone` from Audit phase.
- **Resume path:** The workflow script's Audit/Gate/Land phases already handle resume correctly (cached agent results). Add a `buildTaskId` field to the return value so the caller can correlate.

### 2. Shrink Build agent prompt

Remove the ~30 lines of coordination protocol from the Build agent prompt. Replace with a single line:

```
CLASS-ROUTE per inherited-core.md's two-class diversity policy. Dispatch the inner iteration
as a harness-tracked background agent. Return the dispatch result — do NOT wait for completion.
```

The agent now does ONE thing: class-route + dispatch. It returns immediately with the dispatch result. The workflow script handles everything after dispatch.

### 3. Outer loop coordination

OUTER-LOOP.md's step 5 gains explicit coordination logic:
- When `/execute-milestone` returns `{outcome: "building", buildTaskId: <id>}`: schedule heartbeat, poll on wake
- When background task completes: resume `/execute-milestone` with `resumeFromRunId`

This replaces the current prose-heavy "wait for inner iteration" section with a mechanical protocol.
