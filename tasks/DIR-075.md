## Finding

DIR-044 (2026-07-18) built a complete concurrent multi-milestone scheduler for the quay platform:
`concurrent-batch-scheduler.ts` (greedy touches-disjoint batch assembly),
`serial-fanin-absorb.ts` (deterministic fan-in merge plan + counter advance),
`touches-orthogonality-check.ts` (conservative fail-closed disjointness verdict),
and `anti-drift-touches-check.ts` (post-build NON-WAIVABLE guardrail on real diffs).
DIR-049 wired this into the portable `quay-loop-driver` skill as an opt-in `concurrency: N`
knob, and the mechanism was proven live once (M75 ∥ M76, DIR-044-LIVE). But **exp5's own
OUTER-LOOP.md has never been wired to use it.**

An audit of the 2026-07-22–24 session history (M114–M136, 57 agent calls, 10 sessions) confirms:
**zero cross-milestone concurrent subagents have ever run in exp5.** Every milestone executed
serially (SELECT one → execute → absorb → counter++ → next). The infrastructure for concurrency
exists on disk but is gated by five missing pieces:

1. **0 of ~136 charters** carry `## Touches` or `type:` fields. Without these,
   `concurrent-batch-scheduler.ts` fail-closed defers every candidate to serial.
2. **No `.quay/loop.yml`** exists; `concurrency` defaults to 1.
3. **OUTER-LOOP.md step 1 (SELECT)** picks exactly one winner, never assembles a batch.
4. **OUTER-LOOP.md step 4 (execute)** calls `/execute-milestone` once, never fans out.
5. **`execute-milestone.js` Land phase** does inline `milestone_counter++` + dashboard
   write-back — incompatible with concurrent builds (shared-state collision).

This is a throughput ceiling. Many exp5 milestones ARE product/deliverable tasks touching
disjoint `packages/` files (e.g. M136 touches `packages/quay/src/serve.ts`; a concurrent
milestone touching `packages/quay-native/` would be fully disjoint). The mechanism to run
them concurrently exists; it just needs wiring into the exp5 driver.

## Requested action

Wire the DIR-044 concurrent-scheduler + DIR-049 fan-in absorb into exp5's OUTER-LOOP.md
and supporting files. This is a **driver-rewrite** (touches `OUTER-LOOP.md` →
`label:human-steered` by the 3-clause classifier). Execute under `.halt` off-loop.

### 1. Charter template: add `type:` and `## Touches`

Add to the charter authoring step (OUTER-LOOP.md step 1) the requirement that every
milestone charter MUST declare:

```markdown
type: execution
```
(or `type: learning`, `type: methodology`, etc. — per `inherited-core.md`'s value-type
ledger categories). The `concurrent-batch-scheduler.ts` `isLearning()` guard matches any
type containing `/learning/i` → always serial.

```markdown
## Touches
- packages/quay/src/serve.ts
- packages/quay/bin/quay.ts
- packages/quay/test/serve.test.mjs
```

Globs must satisfy `touches-orthogonality-check.ts`'s `isOverbroadDeclaration`: ≥2
concrete (no-wildcard) leading path segments before any wildcard, OR an exact path at any
depth. `packages/**` is overbroad → fail-closed to serialize. Absent/empty `## Touches`
→ fail-closed to serialize (conservative).

`task-schema-check.sh`: add an **INFO** line when `type: execution` is present but
`## Touches` is absent/missing (the milestone can still run serial, but cannot be batched).
A HARD FAIL only if `type: execution` + `## Touches` is present but ill-formed (overbroad
glob, empty expansion). Non-execution types skip the check.

### 2. Create `.quay/loop.yml`

```yaml
board: native
gates: [vitest]
stop: until(.halt)
policy: value-typed-ledger
execution: dispatched
audit: adversarial
concurrency: 4
```

`concurrency: 4` = max batch width. The scheduler may produce a 1-wide batch (fully serial)
when candidates are all learning-type or touch-overlapping — this is a valid outcome, not
an error.

### 3. Modify OUTER-LOOP.md step 1 (SELECT → batch)

After the existing ranked-shortlist + deliverable-governor + value-ranking produces the
ordered candidate set, insert a **batch assembly** sub-step:

a. For each candidate in the shortlist, ensure its charter has been authored (existing
   step 3 charter-authoring) AND carries `type:` + `## Touches`.
b. Call `node experiments/quay-perpetual-stream/scripts/concurrent-batch-scheduler.ts
   --root . <charter1.md> <charter2.md> ...` over the ranked shortlist's charter files.
c. The script outputs `BATCH (N-wide, concurrent): <ids>` + `deferred: <id> — <reason>`
   lines. Parse them.
d. The BATCH set → step 4 concurrent dispatch. Deferred candidates → remain in the
   candidate pool for the next cycle (their `## Not selected` note records the deferral
   reason). A 1-wide batch = fall back to serial (existing behavior).
e. **Learning-type milestones are always serial** (scheduler defers them). When a
   learning-type milestone is SELECTed as the sole candidate or the batch is 1-wide
   learning, the loop runs exactly one serial milestone — this is the SELECT←ABSORB
   feedback path, preserved unchanged.

### 4. Modify OUTER-LOOP.md step 4 (execute batch)

Current: "invoke `/execute-milestone` with `{taskId, charterFile, absorbEntryFile}`."

New: for each candidate in the batch:

a. Create absorb-entry file `/tmp/m<NN>-absorb-entry.md` with ABSORB narrative header.
b. Dispatch `Workflow({ name: "execute-milestone", args: {taskId, charterFile,
   absorbEntryFile, mode: "concurrent"} })` with `run_in_background: true`.
c. All N workflows run concurrently. The driver polls all N for completion (harness
   notifications are the primary wake; ScheduleWakeup fallback is hang-detection).
d. When all N complete:
   - Collect survivors: those returning `{outcome: "done"}` (gate PASS + audit NO-REFUTATION).
   - Gate-fail / REFUTED candidates → `needs-human` (existing path, unchanged).
   - Run `node experiments/quay-perpetual-stream/scripts/anti-drift-touches-check.ts
     <ran-batch-manifest.json>` on the REAL `git diff --numstat` output from each build.
     HARD FAIL → abort the ENTIRE batch (NON-WAIVABLE — a mis-declared overlap means the
     pre-flight orthogonality check has a bug or a charter was dishonest; do not merge).
   - Run `node experiments/quay-perpetual-stream/scripts/serial-fanin-absorb.ts
     --counter <current milestone_counter> <survivors-manifest.json>` for the deterministic
     merge plan (stable-sort by milestone id → reproducible).
   - Merge each survivor's worktree into master, one at a time, in the plan order.
   - Append N dashboard entries via `renderDashboardAppend(plan)`.
   - `milestone_counter += survivors.length`.
   - Regenerate `backlog.md`/`dashboard.md` views via `it0-backlog-regen.ts`.
   - Run `tree-hygiene-check.sh` + `worktree-branch-hygiene-check.sh` final close-out.

### 5. Modify `execute-milestone.js` Land phase for concurrent mode

When `args.mode === "concurrent"`:

- Land phase does NOT update `milestone_counter` or append to `dashboard.md`.
- Land phase DOES: merge worktree → master, capture+prune worktree, write execution
  record to task file, set `status: done`.
- Return `{outcome: "done", mergeCommit, touchedFiles: [...], dashboardEntry: "..."}`.
  `touchedFiles` is from `git diff --numstat <base>..<build-branch>` — the input to
  `anti-drift-touches-check.ts`. `dashboardEntry` is the markdown block for
  `serial-fanin-absorb.ts`'s `renderDashboardAppend`.

When `args.mode` is absent/`"serial"` (backward-compatible default): existing behavior
unchanged (inline counter++ and dashboard append).

### 6. Gate the batch scheduler into the gate registry

Register `concurrent-batch-scheduler.ts` as a `quay gate --gate batch-safety` check.
Run it at SELECT time (pre-dispatch) AND at fan-in time (anti-drift). The gate wraps
the existing script — never re-implements its logic (ADR-004 single-source).
