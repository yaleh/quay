## Proposal

Historical proposal: adapt the heartbeat of the then-assumed asynchronous Build polling path. The
resolution below records why synchronous Build made that path moot; this schema section does not
authorize reintroducing polling.

## Finding

The `b643aa4d` session (2026-07-24, 384 min, M135-M137) recorded **7 ScheduleWakeup gaps**
of 7–10 minutes each during the Build phase:

```
09:11→09:21 (9 min)    09:24→09:35 (10 min)    09:37→09:48 (10 min)
10:14→10:23 (9 min)    11:08→11:18 (9 min)     11:38→11:46 (7 min)
13:22→13:32 (9 min)
```

These are the `execute-milestone.js` Build phase's ScheduleWakeup fallback heartbeats.
The current coordination protocol (which DIR-074 refactors from agent prompt to script
body) uses a fixed ~1200–1800s fallback as a hang-detection heartbeat. The harness-tracked
background task completion notification is the PRIMARY wake, but the fallback fires on a
conservative fixed cadence regardless.

**The problem:** when the Build agent completes at minute N of a 10-minute heartbeat window,
the loop wastes (10 − N) minutes doing nothing before the next polling check. Across 7
observed gaps in one session, the cumulative waste is ~35–50 minutes.

Additionally, the gap at 13:22→13:32 (9 min) occurred AFTER M137's workflow was dispatched
at 13:19 — this is the loop waiting for the Build phase to start producing results, even
though the harness notification should have fired sooner.

**Root cause:** the ScheduleWakeup fallback interval is not adaptive — it doesn't learn
from historical Build completion times, and it doesn't shorten when the Build agent is
known to be fast (small-scope milestones like M136, ~30 lines of code, should complete
faster than M120's full Node-floor refactor).

## Requested action

Make the Build-phase waiting adaptive: shorter heartbeats for small milestones, harness
notification as the exclusive primary wake, and ScheduleWakeup only as a genuine
hang-detection backstop.

### 1. Remove the fixed ScheduleWakeup from the Build phase

Per DIR-074's refactoring, the Build coordination protocol moves from the agent prompt to
the `execute-milestone.js` script body. Change the waiting logic:

```js
// AFTER DIR-074 refactoring: the Build agent dispatches and returns {outcome: "building", buildTaskId}
// The workflow script's post-Build coordination:

if (buildResult?.outcome === 'building' || buildResult?.harnessTaskId) {
  log(`Build phase dispatched background task: ${buildResult.harnessTaskId}`)

  // PRIMARY wake: harness-tracked background task completion notification.
  // The harness automatically re-invokes the workflow when the task completes.
  // DO NOT set a ScheduleWakeup here — the harness IS the wake mechanism.

  // Hang-detection heartbeat ONLY: if we haven't been re-invoked after 600s
  // (10 min, well past any reasonable cache window), set a single fallback.
  // This is a BACKSTOP, not a polling cadence.

  return { outcome: 'building', buildTaskId: buildResult.harnessTaskId, phase: 'Build' }
}
```

The key change: **no ScheduleWakeup polling loop**. The harness-tracked background task
completion IS the wake. The script returns `{outcome: "building"}` and the outer loop
re-invokes it when the task completes. Only if 600s pass with no notification does a
SINGLE fallback fire.

### 2. Milestone-size-adaptive initial heartbeat

For the hang-detection fallback (the 600s backstop above), scale it by the charter's
estimated scope:

- Charter `## Scope` section contains a heuristic size signal: line count estimate,
  file count, or explicit `size: small|medium|large` marker
- Small milestones (≤50 lines, 1-2 files): fallback = 300s (5 min)
- Medium milestones (50-200 lines, 3-5 files): fallback = 600s (10 min)
- Large milestones (>200 lines, >5 files): fallback = 1200s (20 min)
- Unknown size: fallback = 900s (15 min, conservative default)

The fallback is STILL only a hang-detection backstop — the harness notification remains
the primary wake. The adaptive sizing just ensures we don't wait 20 minutes to detect
that a 30-line fix hung.

### 3. OUTER-LOOP.md coordination: poll-on-fallback, not heartbeat-loop

When the outer loop's CronCreate (DIR-077) fires and the previous cycle returned
`{outcome: "building"}`, the loop:

1. Checks harness task status via `TaskOutput` (or equivalent)
2. If still running → re-arm CronCreate with the adaptive fallback interval, continue waiting
3. If completed → resume `/execute-milestone` from Audit phase
4. If the harness task is NOT FOUND (crashed/lost) → mark `needs-human`

This replaces the current "set ScheduleWakeup, wake up, check, re-arm" loop with a
single "check on CronCreate wake, re-arm if needed" pattern that's driven by the same
self-continuation mechanism.

### 4. Record Build completion times for future adaptivity

After each successful Build phase, record the wall-clock Build duration in the charter's
execution evidence. This builds a dataset that the adaptive heartbeat can query:

```
milestones/M<NN>/iterations/iteration-0.md:
  Build duration: 47 min (dispatched agent, 3 files, 89 lines)
```

Future milestones can query historical Build durations for similar-scope charters to
set the initial heartbeat.

## Resolution

2026-07-25: **Reverted then set `needs-human`.** DIR-078 depends on DIR-074's
background-dispatch model. The adaptive Build heartbeat (`ScheduleWakeup` removal,
harness-notification primary wake, fallback interval scaling by charter scope) was built
on the assumption that Build returns `{outcome: "building"}` with a `harnessTaskId`.
When commit `549a3c3` made Build synchronous ("DO THE ACTUAL WORK"), the entire
heartbeat/fallback mechanism was structurally removed.

DIR-078 cannot be implemented independently — it requires DIR-074's dispatch model to
exist first. See [[DIR-074]]'s Resolution for the runtime limitation and human-decision
options. Whichever path is chosen for DIR-074, DIR-078 follows.

## Resolution, closed (2026-07-27)

[[DIR-074]] is now closed: option (B) (synchronous Build, no in-workflow background
dispatch) is confirmed the permanent reality, not a still-open choice — verified via direct
`grep` showing zero `ScheduleWakeup`/`harnessTaskId` code paths in
`.claude/workflows/execute-milestone.js` (only a stale `meta.description` mention) and zero
matches in `OUTER-LOOP.md`, plus 20+ real dispatches this session that completed via a
single harness `task-notification` with no polling.

**DIR-078's entire premise — an adaptive heartbeat for a ScheduleWakeup polling loop that
waits on a Build-phase background dispatch — no longer applies, because that polling loop
does not exist.** There is no heartbeat to make adaptive; the "waste" this directive was
filed to reduce (7 gaps of 7-10 min each, ~35-50 min total, observed in the `b643aa4d`
session on 2026-07-24) was a real, correctly-diagnosed cost of the OLD (now-abandoned)
architecture — but the fix that actually landed (going fully synchronous) eliminated the
cost by removing the mechanism entirely, not by making it adaptive. Re-implementing DIR-078
as scoped would mean re-introducing the very background-dispatch pattern DIR-074 found
non-viable under the current Workflow JS runtime, just to then optimize its heartbeat.

**Disposition: DIR-078 is closed as moot, superseded by the synchronous-Build outcome.** No
further action requested. If Build-phase wall-clock time is ever a real concern again, the
correct framing is a fresh directive about synchronous-Build duration/scope estimation, not
a revival of this ScheduleWakeup-heartbeat design. AC/DoD checkboxes remain unticked
(DIR-020 — they describe a mechanism that was never built and is not being pursued); this
closure documents disposition, not retroactive completion.
