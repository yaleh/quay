## Finding

The `b643aa4d` session recorded M135 requiring **6 workflow invocations**, with the Verify
phase running all 5 it0 checks (5-agent parallel) on EACH attempt. Of the 5 failures:

- Attempt 1: gate-hash FAIL (charter hash missing) → re-ran all 5 checks on retry
- Attempt 2: ceiling-check FAIL (gap-list ID) → re-ran all 5 checks on retry
- Attempt 3: dogfood-evidence FAIL (M01-dist format) → re-ran all 5 checks on retry
- Attempt 4: dogfood-evidence FAIL (format still wrong) → re-ran all 5 checks on retry
- Attempt 5: all 5 PASS → proceeded to Build

Each retry re-ran checks that had ALREADY PASSED on the previous attempt, wasting agent
execution time and tokens. For example, gate-hash passed on attempt 2 but was re-run on
attempts 3, 4, and 5 — its input (the charter file's HARD GATES block hash) had not changed
since attempt 1's fix.

The `execute-milestone` Workflow already supports **resume** (DIR-067): when re-invoked
with the same `args`, completed phases return cached results. But the resume mechanism
operates at the PHASE level — if ANY it0 check fails, the entire Verify phase is marked
incomplete, and the next invocation re-runs ALL 5 checks. There is no per-check granularity.

**What's needed:** per-check incremental caching within the Verify phase. If a check's
inputs haven't changed since the last run, reuse its cached result. Only re-run checks
whose inputs differ.



## Proposal

Add per-it0-check incremental caching to execute-milestone.js Verify phase. Compute input fingerprints for each check, cache results keyed by {phase, label, fingerprint}, and skip re-running checks whose inputs haven't changed since the last run. Reduces wasted agent execution when a single check fails and forces a full Verify re-run (observed in session b643aa4d: 5 retries, each re-running 4 already-passing checks).
## Requested action

Add per-it0-check incremental caching to the `execute-milestone.js` Verify phase.

### 1. Compute per-check input fingerprints

Each it0 check has well-defined inputs. Before running the Verify phase, compute a
fingerprint for each check:

| Check | Inputs | Fingerprint |
|---|---|---|
| `ceiling-check` | charter file path + gap-list.md hash | `sha256(charter + gap-list)` |
| `gate-hash` | charter file HARD GATES block hash | `sha256(charter_gates_block)` |
| `domain-misfit` | charter Done-when list | `sha256(charter_done_when)` |
| `line-budget` | charter file full text | `sha256(charter_full)` |
| `dogfood-evidence` | milestone iteration report files | `sha256(all_iteration_md)` |

### 2. Store per-check results in the workflow cache

The Workflow resume mechanism stores phase-level results. Extend it to store per-agent
results keyed by `{phase, label, inputFingerprint}`:

```js
// In execute-milestone.js Verify phase:
const VERIFY_CHECKS = [
  { label: 'ceiling-check',    fingerprint: sha256(charter + gapList) },
  { label: 'gate-hash',        fingerprint: sha256(gatesBlock) },
  { label: 'domain-misfit',    fingerprint: sha256(doneWhen) },
  { label: 'line-budget',      fingerprint: sha256(charterFull) },
  { label: 'dogfood-evidence', fingerprint: sha256(iterationReports) },
]

// For each check, before dispatching the agent:
// 1. Look up {phase: 'Verify', label, fingerprint} in the workflow's prior results
// 2. If found AND the prior result was {ok: true} → SKIP, reuse cached result
// 3. If found AND the prior result was {ok: false} AND fingerprint unchanged → SKIP,
//    the check is still failing on the same input (the fix didn't address this check)
// 4. If NOT found OR fingerprint changed → dispatch agent, store result
```

### 3. Scope: Verify phase only

The Build, Audit, Gate, and Land phases have different caching semantics:
- Build: always re-run if the phase was marked incomplete (the fix may have changed the
  approach, not just the inputs)
- Audit: always re-run with fresh context (adversarial, by design)
- Gate: mechanical checks, similar to Verify — could benefit from the same caching
  (future work, out of scope for this directive)
- Land: always re-run (idempotent but fast)

Only the Verify phase gets incremental caching in this directive. The Gate phase's 7
parallel checks are fast enough (~2-5 min total) that caching provides marginal benefit.

### 4. Fallback: when fingerprint computation fails

If any fingerprint input is unavailable (charter file missing, iteration reports not yet
generated), fall back to full re-run of all 5 checks. Conservative-fail: a caching gap
is not a correctness gap — it just means the check runs again.

### 5. Integration with DIR-076 (scoped checks)

When DIR-076's `--milestone` scoping is active, the fingerprint inputs shrink to match
the scoped scan radius (current milestone + dependencies, not global history). This makes
fingerprints more stable across retries — a fix to M01-dist's report no longer changes
M135's fingerprint.

## Resolution

2026-07-25: **Reverted to `todo` but with a known workaround.** The initial implementation
(per-check input fingerprints computed before Verify agent dispatch, cache-hit skip, cache
write-back agent) was fully built then fully removed by commit `13ab23b` because the
Workflow JS runtime lacks `readFile` and `sha256` — the caching mechanism cannot read
charter files or persist cache state to disk.

However, unlike DIR-074, there IS a viable alternative: **pass cache state via workflow
`args`** instead of file I/O:
- Input: `args.cacheFingerprints` (passed by caller, computed from charter text available
  to the main session)
- Output: `args.cacheUpdates` (returned to caller, persisted by the outer loop)
No filesystem access needed. `status: todo` (not `needs-human`) because the approach is
not fundamentally blocked — the implementation just needs to use a different data channel.
