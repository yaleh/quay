## Finding

**WHAT**: The MCP API surface has no `gate_list` tool — agents connected via MCP cannot discover available gates. The CLI has `quay gate --list` which calls `listGates()` from `packages/quay/src/gate/registry.ts`, but this capability is not exposed over MCP.

**WHERE**:
- `packages/quay/src/mcp-handlers.ts`: `registerGateHandlers` registers `gate_run` and `gate_log` but not `gate_list`
- `packages/quay/src/gate/registry.ts` lines 126-128: `listGates()` exists and is the single-source for gate enumeration
- `packages/quay/bin/quay.ts`: the CLI `quay gate --list` branch calls `listGates()` and prints the result

**WHY IT MATTERS**:
- Agents connected exclusively via MCP (which is the intended integration path — Core's MCP server is the provider-agnostic entry point) cannot discover which gates are registered in a workspace
- This forces agents to either hardcode gate names or inspect `.quay/gates.yml` directly, breaking the abstraction layer
- A `gate_list` tool would be a trivial read-only passthrough — zero new logic, just exposing existing `listGates()` output

**Design note**: The `listGates()` function (registry.ts:126-128) already returns both built-in gates (dod, acceptance, doc-*) AND workspace gates (from gates.yml). A `gate_list` MCP tool would simply call `listGates(cfg.workspaceRoot)` and return the array.

## Plan

1. Add `gate_list` MCP tool registration in `registerGateHandlers` (`packages/quay/src/mcp-handlers.ts`).
2. Tool schema: optional `provider` parameter (consistent with all other tools). No other parameters needed.
3. Returns `{ gates: string[] }` in structuredContent (list of gate name strings).
4. Add MCP server test asserting the tool returns at least `"dod"` and `"acceptance"`.
