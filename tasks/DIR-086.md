## Finding

**WHAT**: The lifecycle library functions (`runComplete`, `runPromote`, `runRetreat`) in `packages/quay/src/gate/lifecycle.ts` directly set `process.exitCode = 1` on error paths. This couples a pure library to the process execution context and forces every caller to manually reset `process.exitCode` afterward. In MCP server contexts, this stale exit code persists between calls.

**WHERE**:
- `packages/quay/src/gate/lifecycle.ts` line 122: `process.exitCode = 1;` (in `runComplete` — precondition not-ready)
- `packages/quay/src/gate/lifecycle.ts` line 129: `process.exitCode = 1;` (in `runComplete` — acceptance gate fail)
- `packages/quay/src/gate/lifecycle.ts` line 186: `process.exitCode = 1;` (in `runPromote` — gate fail)
- `packages/quay/src/gate/lifecycle.ts` line 207: `process.exitCode = 1;` (in `runRetreat` — missing reason)

**WHY IT MATTERS — evidence from callers working around it**:
1. `packages/quay/bin/quay.ts` lines 1178-1193 explicitly documents the workaround:
   > "CRITICAL (proposal review note 3): runComplete sets process.exitCode=1 on a meter fail...
   > Reset AFTER runOnce returns."
   Then manually resets: `process.exitCode = 0;`

2. `packages/quay/bin/quay.ts` line 1192 does the same for `runLoop`:
   > "runComplete unconditionally sets process.exitCode=1 on a per-task meter fail...
   > there is no equivalent reset for the non-`--once` branch"
   Then manually resets: `process.exitCode = r.stopped === "cap" ? 1 : 0;`

3. `packages/quay/src/gate/driver.ts` `runLoop` does NOT reset `process.exitCode` between iterations — a failed gate sets exitCode=1, and subsequent passes don't clear it. The driver's caller (CLI) must reset after `runLoop` returns.

4. In MCP handler context, the lifecycle handlers (`lifecycle_complete`, `lifecycle_promote`, `lifecycle_retreat`) NEVER reset `process.exitCode` after calling these functions. In a long-running MCP server, a failed lifecycle operation leaves `process.exitCode = 1` for subsequent unrelated operations.

**Test evidence**: `packages/quay/test/lifecycle.test.mjs` has a `resetExit()` helper (line 69-71) that sets `process.exitCode = 0` before EACH test — confirming this is a known pattern that tests must work around.

## Plan

### Option A (clean, breaks callers): Change return type
Make `runComplete`/`runPromote`/`runRetreat` return an `exitCode` field alongside `ok`/`reason`, and let callers decide whether to set `process.exitCode`. Remove all direct `process.exitCode` assignments from lifecycle.ts.

### Option B (backward-compatible, minimal): Add exitCode to return type AND keep the set
Add `exitCode: number` to the return types, but keep the existing `process.exitCode` sets for backward compat. Add a comment marking them deprecated.

### Option C (immediate fix): Have MCP handlers reset process.exitCode
Add `process.exitCode = 0` after lifecycle handler calls in `mcp-handlers.ts`.

Recommendation: Option A is cleanest but highest blast radius (CLI code, driver code, all tests). Option C is the minimal immediate fix for the MCP path. Option B is the pragmatic middle ground.
