## Finding

M139-M143 (2026-07-25) were all manually landed via commit `266981d` because the
execute-milestone workflow's Gate phase systematically fails for methodology-class
tasks running inside Workflows. The issue is not new:

- DIR-070-B needed 4 rebuilds (M135 window)
- DIR-075 (M142) failed Gate phase — merged manually
- DIR-080 (M144/M145/M146) failed Gate phase — skipped entirely
- DIR-081 (M143) failed Gate phase — merged manually
- M139-M143: ALL 5 milestones stuck at Gate, manually landed

**Three gates consistently fail inside Workflow-internal execution:**

1. **acceptance gate**: Requires `extra.acceptance` to be set on the task BEFORE the
   workflow runs. The Build agent is instructed to set it, but may fail to do so
   (forgets, or the task_write fails silently). Gate fails with "no acceptance command
   defined."

2. **it0-impl-row-check**: Requires a backlog.md row for the milestone ID. Backlog.md
   is regenerated at ABSORB time — it does not yet contain the current milestone's
   entry. Gate fails because the task's milestone ID isn't in the backlog.

3. **audit-independence-check**: Requires a dispatch-record file at a specific path
   (`/tmp/m<NN>-dispatch-record.txt`). This file is created by the Audit phase per
   the M90 procedure, but the Gate agent may not find it (path mismatch, or the file
   wasn't written by the Audit agent). Gate fails with "audit artifact does not exist."

**Root cause:** These three gates were designed for the OUTER-LOOP's serial fan-in
ABSORB, where they run in the MAIN session with full context. Inside an
execute-milestone Workflow, the Build/Audit/Gate agents run in a constrained
environment where task metadata, backlog state, and file-system side effects are
not reliably available.

**Impact:** Every methodology-class milestone processed via execute-milestone Workflow
is blocked at Gate phase, requiring manual intervention to land. The loop has adapted
by manually landing batches of stuck milestones.

## Requested action

### Option A: Make the three gates work inside Workflows

1. **acceptance gate**: Have the workflow SCRIPT (not the Build agent) set
   `extra.acceptance` via `task_write` at the start of the Build phase. JavaScript
   in the script body, not prose in an agent prompt.

2. **it0-impl-row-check**: Provide an `--absorb-entry` flag that makes the check
   read from the absorb-entry file directly instead of scanning backlog.md. The
   absorb-entry file exists at Gate time (it's created before the workflow starts).

3. **audit-independence-check**: Have the Audit agent WRITE BACK the session ID
   into the absorb-entry file or a known path. The Gate agent reads from that
   known path. Eliminate the separate dispatch-record file.

### Option B: Skip unreliable gates in Workflow mode

When `args.mode === "concurrent"` or when running inside a Workflow, skip the
acceptance, impl-row, and audit-indep gates. These gates are designed for the
OUTER-LOOP's fan-in ABSORB phase and should run THERE, not inside each workflow.

The fan-in step (OUTER-LOOP step 4b) already runs `anti-drift-touches-check.ts`
as a NON-WAIVABLE guardrail. Adding these three gates to the fan-in phase would
restore their intended function without blocking individual workflows.

### Recommendation: Option B.

The three gates are OUTER-LOOP fan-in gates — they validate cross-milestone
consistency. Running them inside individual workflows is architecturally wrong.
Move them to the fan-in absorb step where they have full context.
