## Finding

There is no `quay init` (or equivalent) command to scaffold a new workspace.
Users must manually create `.quay/config.yml` — the only reference is the
minimal example at `packages/quay-native/examples/sample-workspace/.quay/config.yml`,
which shows only the `providers:` section. The full config schema supports three
top-level sections (`providers:`, `gates:`, `loop:`) with many sub-options, none
of which are discoverable without reading source code across 5+ files.

Concrete gaps in the manual-init path:

1. **No single schema reference.** Config fields are spread across:
   - `packages/quay/src/config.ts` (providers, activeProvider)
   - `packages/quay-native/src/store.ts` (default_task_status)
   - `packages/quay-native/bin/quay-native.ts` (QUAY_NATIVE_* env vars)
   - `packages/quay/src/gate/config/types.ts` + `loader.ts` (gates schema: it0/adr/fixed/testPass/coverageFloor/redGreen)
   - `packages/quay/src/loop-params.ts` (loop schema: board/gates/stop/policy/execution/audit/concurrency/routines)

2. **No guided initialization.** A new user running `quay task list` gets
   "no .quay/config.yml found" — no hint about what to create or where.

3. **Sample workspace is minimal.** `examples/sample-workspace/` shows only the
   provider section; gates and loop sections are invisible.

4. **No validation before first use.** The config is only validated when a
   command reads it — no dry-run or validate subcommand.

## Proposal

Add a `quay init` subcommand that scaffolds a complete, documented `.quay/config.yml`
at the user's project root. The command should:

1. **Detect or prompt for project root.** Default to CWD; `--root <path>` override.
2. **Detect existing config.** Refuse to overwrite unless `--force`.
3. **Auto-detect provider.** If `quay-native` is on PATH → default to native provider.
   If run from within a quay repo → offer native + github. `--provider <id>` override.
4. **Detect project type for sensible gate defaults:**
   - Node.js (`package.json` exists) → suggest `node --test` testPass gate
   - Go (`go.mod` exists) → suggest `go test ./...` testPass gate
   - Other → no gates scaffolded
5. **Write a fully-commented `.quay/config.yml`** with every supported field documented
   inline — providers, gates (all 6 types), loop (all 8 fields) — commented-out optional
   fields acting as reference documentation.
6. **Create the tasks directory** (`QUAY_NATIVE_TASKS_DIR`) if it doesn't exist.
7. **Print next-step instructions** (how to create a task, start the MCP server, etc.).
8. **Dry-run mode:** `quay init --dry-run` prints the config to stdout without writing.

Non-goals for v1:
- Interactive prompts (keep it flag-driven; add `--interactive` later)
- Multi-provider auto-detection beyond native + github
- Gate script bootstrapping (just reference the gate types in comments)

## Acceptance Criteria

- [ ] AC1: `quay init` at a Node.js project root creates `.quay/config.yml` with all 3 sections (providers, gates, loop), creates `./tasks/` dir, and exits 0
- [ ] AC2: `quay init` at a Go project root creates `.quay/config.yml` with Go-appropriate gate suggestions
- [ ] AC3: `quay init` refuses to overwrite existing `.quay/config.yml` (exit 1 with message) unless `--force`
- [ ] AC4: `quay init --dry-run` prints the config to stdout, does NOT touch disk
- [ ] AC5: `quay init --root /some/path` scaffolds at that path instead of CWD
- [ ] AC6: Generated `.quay/config.yml` is valid YAML and passes `quay task list` immediately after creation (no manual edits needed)
- [ ] AC7: Generated `.quay/config.yml` contains inline comments documenting every supported field across all 3 sections, including commented-out optional fields
- [ ] AC8: `quay init --help` prints usage including all flags
- [ ] AC9: Tests: `quay test/init.test.mjs` — covers AC1-AC6 with RED→GREEN test pairs per ADR-001
- [ ] AC10: `quay-native` (not just `quay` Core) also gets the `init` subcommand — `quay-native init` works identically when native is the sole installed package
