## Finding

There is no way to validate `.quay/config.yml` before runtime. Configuration errors
— malformed YAML, missing required fields, gate references to non-existent gates,
incorrect gate entry shapes — are only discovered when a command fails at runtime.

Concrete failure modes observed in the meta-cc project (2026-07-25/26):

1. **Gate format error silently ignored.** `gates: vitest: command: npx vitest run` was
   written directly under `gates:` instead of `gates: testPass:`. The malformed entry
   was silently skipped by the YAML parser — no error, no warning. The `vitest` gate
   simply didn't exist at runtime, causing `unknown gate: vitest` failures.

2. **Gate reference to non-existent gate.** `loop: gates: [vitest]` referenced a gate
   that wasn't registered. Discovered only when `gate_run` failed at the GATE phase
   of the loop — after BUILD had already completed.

3. **Dual source of truth.** `.quay/gates.yml` correctly declared vitest as a
   `testPass` entry, but `.quay/config.yml`'s malformed `gates:` section silently
   took precedence (DIR-050 unified format priority), hiding the correctly-declared gate.

4. **No pre-flight for loop config.** `loop:` section errors (missing `board`,
   invalid `stop` values, invalid `concurrency`, malformed `routines`) are only caught
   by `readLoopParams()` when the loop driver starts — no command to check them ahead
   of time.

## Proposal

Add a `quay config validate` (or `quay config check`) subcommand that performs a
comprehensive, fail-closed validation of `.quay/config.yml` and prints a clear,
actionable report. Exit 0 = all checks pass; exit 1 = issues found (with line-level
diagnostics).

### Validation checks (v1)

1. **YAML syntax** — parse without error; report line number on failure
2. **Required provider fields** — `enabled` providers must have `mcp_entry`
3. **Gate shape validation** — each entry in `gates:` must match exactly one known
   gate type schema (it0 requires name+script+argsKey; testPass requires
   name+command; fixed requires name+script; coverageFloor requires
   name+command+floor; redGreen requires name+red+green)
4. **Gate reference resolution** — every gate name in `loop.gates` must resolve to
   a registered gate (built-in OR declared in config.yml's `gates:` section).
   Report unresolvable names with a hint ("did you mean: testPass.vitest?")
5. **Gate entry placement** — detect gate entries written at the wrong YAML nesting
   level (e.g. `gates: vitest:` instead of `gates: testPass: - name: vitest`) and
   suggest the correct shape
6. **Loop required fields** — `board` is present and non-empty; `gates` is present
7. **Loop field validation** — `execution` ∈ {dispatched, inline}; `audit` ∈
   {adversarial, none}; `concurrency` is integer ≥ 1; `stop` matches valid pattern
8. **Routine shape validation** — each routine has `name` + `trigger` +
   at least one of `probe`/`dispatch`
9. **Provider env validation** — native provider has `QUAY_NATIVE_TASKS_DIR` or
   a `tasks_dir` field; github provider has `QUAY_GITHUB_REPO`
10. **File existence checks (optional, `--check-files`)** — gate scripts exist on
    disk; tasks_dir exists and is a directory

### CLI surface

```
quay config validate [--check-files] [--json]
quay config check           # alias
```

- `--check-files`: also verify that referenced scripts/files exist on disk
- `--json`: output machine-readable JSON instead of human-readable report
- Default: human-readable report with file:line references, exit 0 on clean, exit 1 on issues

Non-goals for v1:
- Schema migration (e.g. auto-converting gates.yml → config.yml)
- Auto-fix / `--fix` mode
- Remote provider connectivity check (network-dependent, belongs in a separate `quay doctor` command)

## Acceptance Criteria

- [ ] AC1: `quay config validate` on a valid config.yml exits 0 with a "Config valid" message
- [ ] AC2: `quay config validate` on a config with malformed YAML exits 1 with line number
- [ ] AC3: `quay config validate` on a config with a gate entry at wrong nesting level (e.g., `gates: vitest:` instead of `gates: testPass:`) exits 1 with a diagnostic suggesting the correct shape
- [ ] AC4: `quay config validate` on a config where `loop.gates` references a non-existent gate exits 1 with "unresolved gate: <name>" and a hint
- [ ] AC5: `quay config validate` on a config missing `loop.board` exits 1 with a specific message
- [ ] AC6: `quay config validate --check-files` on a config referencing a missing gate script exits 1 with file path
- [ ] AC7: `quay config validate --json` outputs a JSON array of issues (empty on valid) with {severity, field, message, suggestion?}
- [ ] AC8: `quay config validate` works on both unified config.yml (DIR-050) AND legacy separate-file workspaces (gates.yml + loop.yml)
- [ ] AC9: Tests: `packages/quay/test/config-validate.test.mjs` — covers AC1-AC6 with RED→GREEN test pairs per ADR-001, >=80% coverage
- [ ] AC10: `quay config --help` lists `validate` / `check` as a subcommand
