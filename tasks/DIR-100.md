## Finding

When a gate is declared in `.quay/config.yml` (or `.quay/gates.yml`) with a
format error — wrong YAML nesting level, missing required fields, or entry under
the wrong section — the gate loader silently skips it. No error, no warning, no
diagnostic. The gate simply doesn't appear in the registered gate list.

Concrete case from meta-cc (2026-07-25):

```yaml
# .quay/config.yml — WRONG: vitest written as a direct key under gates:
gates:
  vitest:
    command: npx vitest run
    cwd: /home/yale/work/meta-cc
```

This should have been:

```yaml
gates:
  testPass:
    - name: vitest
      command: "npx vitest run"
      timeoutMs: 120000
```

The loader (`loader.ts:83`) sees the `gates:` key exists in config.yml, tries to read
`parsed.it0`, `parsed.adr`, `parsed.fixed`, `parsed.testPass`, etc. as arrays. The
malformed `vitest:` key is a YAML map, not an array — so `Array.isArray()` returns
false, and the gate is silently dropped. The correct vitest declaration in
`.quay/gates.yml` is also invisible because config.yml's `gates:` section takes
precedence (DIR-050 unified format).

The user experience: `gate_run` fails with "unknown gate: vitest", `gate_list`
doesn't show it, and there's zero indication that a configuration error caused the
problem. 3 separate Bash reads + 1 Edit were required to diagnose and fix.

## Proposal

Make gate configuration errors **fail-loud** rather than fail-silent. When the gate
loader encounters entries it cannot parse into any known gate type, it should report
them as diagnostics.

### Changes

1. **`readGatesConfig()` in `loader.ts`**: after extracting the six known arrays
   (it0, adr, fixed, testPass, coverageFloor, redGreen), scan the parsed YAML for
   **unrecognized top-level keys** under `gates:` that don't match any known type.
   For each unrecognized key, emit a diagnostic.

2. **Per-entry validation in `loadWorkspaceGates()`**: for each entry in each array,
   validate required fields before calling the factory. On mismatch:
   - `it0` entry missing `name`/`script`/`argsKey` → warn which field is missing
   - `testPass` entry missing `name`/`command` → warn
   - `fixed` entry missing `name`/`script` → warn
   - `coverageFloor` entry missing `name`/`command`/`floor` → warn
   - `redGreen` entry missing `name`/`red`/`green` → warn

3. **Diagnostic severity levels**:
   - `error`: gate will not be registered (missing required fields)
   - `warn`: gate registered but entry has unexpected extra fields

4. **Output channel**: diagnostics written to stderr (not stdout — so they don't
   interfere with `gate --list --json`). Controlled by a new `QUAY_GATE_DIAGNOSTICS`
   env var: `stderr` (default), `quiet` (suppress), or a file path.

5. **Hint system**: when an unrecognized key name matches a gate declared in the
   legacy `gates.yml` file (but shadowed by config.yml), include a cross-reference
   hint: "gate 'vitest' is declared in .quay/gates.yml as a testPass entry but is
   shadowed by .quay/config.yml's gates: section — move it to config.yml or remove
   the config.yml gates: section to restore legacy behavior."

Non-goals for v1:
- Auto-fix / migration of malformed entries
- Interactive resolution
- Changing the precedence rules (config.yml wins over gates.yml — that's DIR-050 by design)

## Acceptance Criteria

- [ ] AC1: When `gates:` in config.yml contains an unrecognized top-level key (e.g., `vitest:`), the loader emits a stderr diagnostic: "unrecognized gate section 'vitest' — expected one of: it0, adr, fixed, testPass, coverageFloor, redGreen"
- [ ] AC2: When an `it0` entry is missing `script`, the loader emits: "it0 gate '<name>' missing required field 'script' — gate will not be registered"
- [ ] AC3: When a gate is declared in `.quay/gates.yml` but shadowed by config.yml's `gates:` section, and the shadowed gate name appears nowhere in config.yml's gates, emit a hint mentioning both files
- [ ] AC4: `QUAY_GATE_DIAGNOSTICS=quiet` suppresses all diagnostics
- [ ] AC5: `QUAY_GATE_DIAGNOSTICS=/path/to/log` writes diagnostics to that file instead of stderr
- [ ] AC6: Diagnostics go to stderr, not stdout — `quay gate --list --json` output is unaffected
- [ ] AC7: A correctly-configured workspace produces zero diagnostics (no false positives)
- [ ] AC8: Tests: `packages/quay/test/gate-diagnostics.test.mjs` — covers AC1-AC3 with >=80% coverage
