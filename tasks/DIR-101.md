## Finding

Every `task_write` call in the meta-cc project (25 calls observed across 3 sessions,
2026-07-25/26) explicitly passes `extra.schema: "v1"`:

```json
{"extra": {"schema": "v1", "acceptance": "..."}}
```

This is boilerplate. The `schema` field is structural metadata — it describes the
task body format, not task-specific data. It should have a creation default, just
like `status` has `default_task_status` (DIR-047).

In the quay-perpetual-stream experiment, `schema: v1` is further enforced by
`scripts/task-schema-check.sh` at SELECT time (OUTER-LOOP.md line 28) — tasks
without it are rejected. This means every task creator must remember to set it,
and forgetting produces a silent deferral at SELECT (the task simply doesn't get
picked up, with no immediate error).

The `default_task_status` precedent (DIR-047, `packages/quay-native/src/store.ts:125`)
shows the exact pattern: a per-provider config key that sets the creation default,
with the store applying it when `write()` creates a new task and no explicit value
is given.

## Proposal

Add a `default_task_schema` configuration key, mirroring `default_task_status`
(DIR-047), with the same resolution chain:

1. **Provider config**: `default_task_schema: "v1"` in `.quay/config.yml` under the
   provider entry
2. **Store default**: `createStore(tasksDir, { defaultStatus, defaultSchema })` —
   when creating a new task with no explicit `extra.schema`, apply the configured
   default
3. **Fallback**: if `default_task_schema` is absent, `extra.schema` is unset
   (backward compatible — existing tasks without schema are unaffected)

### Changes

1. **`packages/quay-native/src/store.ts`**:
   - `createStore()` accepts `defaultSchema?: string`
   - `write()`: when creating a new task, if `frontmatter.extra.schema` is unset
     and `storeDefaultSchema` is set, apply it to `frontmatter.extra`
   - `resolveDefaultSchema(value)`: validate the value is a non-empty string
     matching `/^v\d+$/` (schema versions are "v1", "v2", etc.)

2. **`packages/quay-native/bin/quay-native.ts`**:
   - `loadDefaultSchema()`: reads `default_task_schema` from the enabled provider's
     config block in `.quay/config.yml`
   - **Invokes `resolveDefaultSchema()` on the configured value before returning** —
     mirroring `loadDefaultStatus()` (bin/quay-native.ts:100-101), the validator
     throws a clear error on illegal values, so the CLI and MCP server fail closed
     (exit non-zero, no task created) rather than silently creating tasks with an
     invalid schema value
   - Passes the validated value to `createStore()` alongside `defaultStatus`

3. **`packages/quay-native/src/mcp-server.ts`**:
   - `startMcpServer()` accepts and passes through `defaultSchema` (already
     validated by the caller — see bin/quay-native.ts `loadDefaultSchema()`)

4. **`.quay/config.yml` schema**: new optional per-provider field:
   ```yaml
   providers:
     native:
       default_task_schema: "v1"   # applied to new tasks when extra.schema is unset
   ```

### Behavior

- Task created via `task_write` with no `extra.schema` + `default_task_schema: "v1"` in config → task gets `extra.schema: "v1"`
- Task created with explicit `extra.schema: "v2"` → explicit value wins (same as `default_task_status`)
- `default_task_schema` absent from config → `extra.schema` is unset (backward compatible)
- Patching an existing task (not creating) → `default_task_schema` is NOT applied (same as `default_task_status` — only creation)
- `default_task_schema` set to an illegal value in config → CLI/MCP server fail closed (exit non-zero, no task created), with a clear error naming the key

Non-goals for v1:
- Schema migration/upgrade (v1→v2)
- Schema-aware rendering (body section parsing based on schema version)
- Enforcing schema at `task_check` time
