## Finding

The acceptance runner (`acceptance-runner.ts`) executes `task.extra.acceptance` as a
shell command in a clean environment. It does NOT inherit the user's shell profile
(PATH, env vars, aliases). This is correct behavior for isolation, but it creates a
recurring failure pattern where acceptance commands fail because essential tools are
not on the default PATH.

Observed in meta-cc (2026-07-25/26): DIR-005 needed **3 retries** to get the
acceptance command right:

```
Attempt 1: cd /tmp/.../DIR-005 && make commit
  → FAIL: "go: command not found" (go not on default PATH)

Attempt 2: export PATH=/usr/local/go/bin:$PATH && cd /tmp/.../DIR-005 && make commit
  → FAIL: "No module named pre_commit" (Python pre_commit not installed)

Attempt 3: export PATH=/usr/local/go/bin:$PATH && cd ... && go test ./... && go build ./...
  → PASS
```

The root causes are:
1. **No visibility into what the acceptance runner's environment looks like.** The
   user/loop driver guesses at PATH and discovers missing tools only by failure.
2. **No convention for where environment setup lives.** Each acceptance command
   reinvents `export PATH=...` inline.
3. **No way to dry-run the acceptance command** in the same environment the runner
   will use without actually running the gate.

## Proposal

Three orthogonal improvements, each independently useful:

### A. `quay run --dry-run` — execute acceptance command in the runner's environment without recording a GateEvent

```
quay run --dry-run DIR-NNN
```

Runs `task.extra.acceptance` in the EXACT same cwd + timeout + clean-env that
`gate_run` / `complete` would use, prints stdout/stderr + exit code, but does NOT
append a GateEvent. This lets the loop driver (or a human) test the acceptance
command before committing to a gate run.

### B. Document the runner's environment contract

Add a section to README.md (and the `quay run --help` output) documenting:
- The acceptance command runs in a clean shell (no `.bashrc`/`.profile`)
- Default PATH is the system default (typically `/usr/bin:/bin`)
- Use `export PATH=...` inline, or point `--cwd` at a directory with a `.env`-style
  setup script
- Default timeout is 60s; raise with `--timeout` for builds
- The working directory defaults to workspace root; override with `--cwd`

### C. `QUAY_ACCEPTANCE_ENV` — optional env file for acceptance commands

Allow `.quay/config.yml` to declare a per-provider env file that is sourced before
every acceptance command:

```yaml
providers:
  native:
    acceptance_env: "./.quay/acceptance.env"   # optional; sourced before acceptance commands
```

`.quay/acceptance.env` would contain:
```sh
export PATH=/usr/local/go/bin:/home/user/bin:$PATH
export GOPATH=/home/user/go
```

The runner sources this file (if configured) before executing the acceptance
command. This is a workspace-level setting — all tasks share the same baseline
environment.

Non-goals for v1:
- Per-task env overrides (use inline `export` in the acceptance command)
- Automatic PATH detection ("sniff the user's shell and replicate it")
- Environment diffing between runner and user shell
