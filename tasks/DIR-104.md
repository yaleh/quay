## Finding

`quay gate --list` returns a flat list of registered gate names:

```
$ quay gate --list
dod
acceptance
doc-quay-directive-skill
```

This tells you WHAT gates exist, but not WHERE they came from or WHY a gate you
expect to see is missing. In the meta-cc vitest incident (2026-07-25), `gate --list`
showed only 3 built-in gates — the vitest gate declared in `.quay/gates.yml` was
invisible because config.yml's malformed `gates:` section silently shadowed it.
There was no way to diagnose this from the CLI; it took 3 separate Bash reads of
config files to understand the problem.

A verbose mode should show each gate's provenance (source file + line or "built-in"),
its type (it0/testPass/fixed/etc.), and any diagnostic warnings. This turns
`gate --list` from a name-dump into a diagnostic tool.

**Grounded facts for Plan authors (2026-08-01, from real PlanCheck rounds):**

1. **Flag order is meaningless — `parseFlags` collects flags into an order-independent
   object** (quay.ts L116-143). `--verbose --json` and `--json --verbose` are byte-identical
   inputs and MUST render identically. The both-flags case is JSON precedence (the AC7
   shape wins over the table) — never branch on flag order.
2. **`loadWorkspaceGateMetadata`/`listGatesVerbose` need an explicit null/undefined
   `workspaceRoot` guard.** The registration loop it mirrors executes
   `const adrDir = path.join(workspaceRoot, "adr")` UNCONDITIONALLY (loader.ts L152),
   before the adr loop — `path.join(undefined, "adr")` throws
   `ERR_INVALID_ARG_TYPE`. Today's flagless `gate --list` handles the documented
   no-config case; the verbose path must too.
3. **The branch-A shadow probe cannot fit a bare `parseGatesConfig(text)` signature** —
   a `text` string cannot convey which branch was taken (config.yml vs legacy gates.yml)
   nor locate/read the legacy `.quay/gates.yml`. The implementer will need a
   `workspaceRoot`/gates.yml-path param or hoist the probe into
   `loadWorkspaceGateMetadata`. Pre-declare this deviation rather than discovering it
   mid-Build.
4. **The five silent-`continue` sites in `loadWorkspaceGates` are the AC5 diagnostic
   emission points** (it0 L146, fixed L158, testPass L165, coverageFloor L169, redGreen
   L173) — each skip site emits a diagnostic instead of continuing silently.

## Proposal

Add `--verbose` (short: `-v`) to `quay gate --list`:

```
$ quay gate --list --verbose
dod                    built-in     (acceptance)
acceptance             built-in     (acceptance)  
doc-quay-directive-skill  built-in  (doc)
vitest                 .quay/gates.yml:10  testPass  command: npx vitest run
tree-hygiene           .quay/config.yml:94  fixed  script: ./scripts/gates/tree-hygiene-check.sh
```

### Verbose output columns

1. **NAME** — gate name (as registered)
2. **SOURCE** — where the gate was defined:
   - `built-in` for `dod`, `acceptance`, `doc-*`
   - `<file>:<line>` for workspace gates (e.g., `.quay/config.yml:64`)
3. **TYPE** — gate factory type: `it0`, `adr`, `fixed`, `testPass`, `coverageFloor`, `redGreen`, `doc`, `acceptance`
4. **DETAIL** — type-specific summary:
   - `it0`: `script: <path> argsKey: <key>`
   - `testPass`: `command: <cmd>`
   - `fixed`: `script: <path>`
   - `coverageFloor`: `command: <cmd> floor: <N>%`
   - `redGreen`: `red: <cmd> green: <cmd>`
   - `adr`: `adr: <id>`
   - `doc`: `skill: <name>`
   - `acceptance`: `(runs task.extra.acceptance)`

### Diagnostic section

When gates are declared but NOT registered (shadowed, malformed, missing required
fields), append a `## Diagnostics` section below the gate list:

```
## Diagnostics (2 warnings)

WARNING: gate 'vitest' declared in .quay/gates.yml:10 as testPass but NOT registered
  — .quay/config.yml has a `gates:` section that takes precedence (DIR-050).
  — The config.yml gates section does not include a testPass entry for 'vitest'.
  — Fix: add vitest to config.yml's gates.testPass section (removing the config.yml
    gates: section does NOT restore legacy gates.yml behavior — DIR-120 made branch A
    terminal, so the legacy file is never re-read when config.yml exists).

WARNING: it0 entry 'impl-row' at .quay/config.yml:65 missing required field 'script'
  — gate will not be registered. Required fields: name, script, argsKey.
```

### CLI

```
quay gate --list                  # flat name list (current behavior, unchanged)
quay gate --list --verbose        # table + diagnostics
quay gate --list -v               # short flag
quay gate --list --json           # NEW: JSON output — `gate --list` has no JSON mode today, so this is created from scratch
quay gate --list --json --verbose # NEW: JSON with source/type/detail/diagnostics fields
```

Today `gate --list` ignores all flags — the handler matches only
`sub === "--list"` (quay.ts) and prints the flat name list, and help documents
`--json` only for `gate-log`. This change adds real `--verbose` / `-v` / `--json`
flag handling (plus matching help text) for `gate --list`. There is no pre-existing
`gate --list --json` format, so the JSON output (AC7) is a NEW format created from
scratch — not an extension of an existing one; the byte-identical no-regression
guarantee covers only the flagless `gate --list` path (AC6).

### Mechanism (provenance + diagnostics ownership)

Provenance and diagnostics are produced by the SAME production loader pass that
registers/skips workspace gates: `readGatesConfig` / `loadWorkspaceGates` in
`packages/quay/src/gate/config/loader.ts`. The CLI `--verbose` path only formats
what that loader pass emitted — it does NOT re-parse `.quay/config.yml` or
`.quay/gates.yml` on its own (no second source of truth). The config.yml-vs-gates.yml
precedence (DIR-050/DIR-120 branch-A) and the per-entry skip decisions stay in the
loader; the skip sites that today `continue` silently past entries missing
`name`/`script`/`argsKey` (loader.ts) are exactly where AC5's diagnostics are
collected.

Because the current loader parses with `YAML.parse` (plain objects carrying no node
location data), per-entry `<file>:<line>` provenance (AC3) requires switching
`readGatesConfig` to `yaml`'s `parseDocument`/CST mode with `keepSourceTokens` and
threading the resulting source location through `GatesConfig` (`types.ts`) and the
six section readers in `loader.ts`. The `<file>:<line>` shown for a workspace gate is
then the loader-recorded location.

**Decided-invariant deviation (AC4 shadow probe vs DIR-120 terminal branch A):** DIR-120
made branch A (`.quay/config.yml` present) TERMINAL — `readGatesConfig` resolves
exclusively from config.yml's `gates:` section and NEVER reads a legacy `.quay/gates.yml`,
even one with real content (loader.ts L84-97; `gate-config-loader.test.mjs`'s silent-data-loss
case asserts that empty-shape return 'by design'; this workspace's own root `.quay/gates.yml`
is physically deleted). AC4's shadow diagnostics therefore CANNOT be computed "in the same
loader branch that resolves precedence" — that branch never touches the legacy file, so a
probe living inside it would be dead code that could never fire. The reversal is pre-declared
here (and in `docs/plans/M220-dir-104.md`): the AC4 shadow probe is a read-only, loader-side
pass that resolves the legacy `.quay/gates.yml` path DIRECTLY (a `workspaceRoot`/gates.yml-path
parameter, per grounded fact #3) purely to emit shadow diagnostics. It is a diagnostic probe
ONLY — it never registers a gate from the legacy file and does not weaken branch A's terminal
guarantee (no gate ever resolves from `.quay/gates.yml` when config.yml exists). In THIS
workspace the root gates.yml is absent, so the probe emits zero shadowed-gate diagnostics
here; AC4/DoD5 fire only in a workspace where a legacy `.quay/gates.yml` still exists
alongside a `.quay/config.yml`.

Non-goals for v1:
- Color-coded output (plain text columns, defer to a future `--color` flag)
- Interactive drill-down into a specific gate
