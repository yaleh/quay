## Finding

`plugin/vendor/quay/dist/quay.js` is a committed BUILD ARTIFACT — a 1.2MB esbuild bundle of
`packages/quay/bin/quay.ts`. It is the only build artifact in the repo tracked by git; the
`.gitignore` `dist/` rule excludes every other one (including its own source
`packages/quay/dist/quay.js`). It exists in git ONLY because of a distribution constraint,
not by design principle.

### Why it is committed today (the binding constraint)

`.claude-plugin/marketplace.json` declares `"source": "./plugin"`. `/plugin install quay`
clones the git repo and copies the `plugin/` subtree directly — there is NO build step in the
install path. So whatever is committed in `plugin/vendor/quay/dist/` is exactly what external
consumers receive. The bundle serves two purposes simultaneously:
1. **Node-20 compatibility** — esbuild compiles TS → JS runnable on the declared Node-20 floor
   (source `.ts` needs Node ≥23).
2. **Dependency self-containment** — esbuild inlines `@modelcontextprotocol/sdk` + `yaml`, so
   consumers need no `npm install`.

### Why this is a problem

- Committing a build artifact violates the repo's own single-source discipline (ADR-004) and
  the "executable invariants over prose" principle. The source of truth is
  `packages/quay/bin/quay.ts`; the committed bundle is a derived duplicate.
- The drift check `sync-vendor.sh --check` exists but is wired into NOTHING (no it0 selfcheck,
  no CI, no pre-commit hook). Result: since M136 (last regeneration), 10 commits touched
  `packages/quay/src|bin` WITHOUT regenerating the bundle — it silently went stale. It was
  ultimately deleted entirely, and no mechanism caught it until the MCP server failed to
  connect (this session, 2026-07-26).
- Every source change SHOULD produce a 1.2MB binary diff — pure noise in git history.

### Why "just gitignore it" is insufficient

Because marketplace installs from git `./plugin` with no build step, a bare `git rm --cached`
would immediately break external installs (missing MCP server binary). Getting the artifact
out of git REQUIRES changing the distribution path so a build happens between source and
install. Shipping source `.ts` instead (run via `node --experimental-strip-types`) is NOT
viable: it raises the Node floor 20→23 AND reintroduces `npm install` at the consumer (the
bundle's inlined deps would be lost) — exactly the tradeoff DIR-060/M120 rejected.

## Requested action

Driver/infra-rewrite (touches marketplace topology, CI, `.gitignore`, `quay:init`) →
`label:human-steered`. Execute under `.halt` off-loop.

### Distribution side (external consumers): B1a — built orphan branch

1. Add a CI job (GitHub Actions) that, on release (version tag or a dedicated trigger):
   - runs `bash plugin/scripts/sync-vendor.sh` (builds the fresh bundle + mirrors all vendor
     assets),
   - commits the fully-built `plugin/` subtree to an ORPHAN branch (e.g. `dist-plugin`),
     force-updated each release (the gh-pages pattern),
   - the orphan branch carries the built `plugin/vendor/quay/dist/quay.js`; the main branch
     never does.
2. Repoint `.claude-plugin/marketplace.json` `source` from `./plugin` to the built orphan
   branch (or a subdir ref the marketplace schema supports). External `/plugin install quay`
   then always pulls a freshly-built, self-contained, Node-20-runnable plugin.
3. Verify a real external install from the orphan branch produces a working MCP server.

### Local side (this repo IS its own MCP runtime): Consumer-2 fallback via quay:init/postinstall

The in-tree `.mcp.json` resolves `${CLAUDE_PLUGIN_ROOT}` to `plugin/`, so the dev workspace
runs `plugin/vendor/quay/dist/quay.js` from the working tree. Once gitignored, that file is
absent after a fresh clone. Regenerate it locally via a build step, NOT via committing:

4. Wire `sync-vendor.sh` into `quay:init` (the skill already exists) AND/OR an npm
   `postinstall` script at the repo root, so `npm install` or `/quay:init` regenerates the
   gitignored bundle in place. A developer who clones + installs gets a working local MCP with
   no manual step.

### Ordering (SAFETY-CRITICAL — do NOT reorder)

The artifact must NOT leave git until the replacement distribution path is proven, or
marketplace installs break in the interim:
1. Build the CI publish job → orphan branch exists and is fresh.
2. Repoint marketplace source → verify external install works from the orphan branch.
3. Wire local fallback (quay:init/postinstall) → verify a fresh clone yields a working local MCP.
4. ONLY THEN: `git rm --cached plugin/vendor/quay/dist/quay.js`, add it to `.gitignore`,
   remove the now-obsolete `!plugin/vendor/quay/dist/**` negation.

### Non-goal

- Do NOT ship source `.ts` as the plugin entry (rejected: Node-floor + npm-install regression).
- Do NOT change `packages/quay/bin/quay.ts` (the canonical source) or the esbuild build itself.
- Do NOT remove `sync-vendor.sh` — it becomes the CI build step and the local fallback step.
- Do NOT `git rm --cached` before the orphan-branch distribution is proven working.

## Proposal

The vendored bundle exists in git only because marketplace installs from `./plugin` with no
build step. Insert the build into the distribution pipeline instead: CI builds the plugin and
publishes it to an orphan `dist-plugin` branch (the gh-pages pattern), marketplace installs
from there, and the main branch carries only source. The "this repo is its own MCP runtime"
need is solved separately by a local build fallback (`quay:init`/postinstall runs
`sync-vendor.sh`), never by committing the artifact. Drift disappears because there is no
committed artifact to drift — CI regenerates on every release.
