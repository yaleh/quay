## Finding

Full-suite profiling (2026-07-26) found `packages/quay/test/cli.test.mjs` is the single largest
contributor to local/CI test wall-clock: 236.06s inside the full 80-file run at
`--test-concurrency=8`, but only 108.9s run in isolation — the ~127s gap is CPU/disk contention
with other concurrently-scheduled files, not this file's own necessary cost. The file predates
`node:test`'s `test()` API (zero registrations — the whole file is one implicit test to the
runner) and makes 68 sequential `execFileSync` calls into fresh `node bin/quay.ts` subprocesses
(avg ~1.45s/call), summing to 98.4s of strictly serial work.

Structural analysis found the file is internally organized into 10 filesystem-isolated scenario
blocks, each constructing its own `mkdtempSync` tasksDir + workspaceRoot pair, with no shared
`process.env` mutation or `process.chdir()` calls found anywhere in the file (confirmed via
`grep -n "process\.env\.\|process\.chdir"` — zero hits) and no port conflicts (the one block that
starts a real HTTP server derives its port from `process.pid`, unique per test-runner process).
Call-count-per-block: main/shared-state block 20, qx45 15, prefix 11, search+bodysearch 7,
action-github-log 4, sort/multilabel/hdng/qx37 2 each. These blocks are correctness-independent of
each other but forced to run serially by the file's construction, not by any real coupling.

## Requested action

1. Convert the `run()` helper from `execFileSync` (sync, blocking) to an `execFile`-based async
   version (promisified), preserving its existing return shape (`{status, stdout, stderr}`).
2. Wrap each of the 10 independent scenario blocks into its own `async function`. WITHIN each
   block, calls stay strictly sequential (`await run(...)`) to preserve each block's existing
   create→edit→check ordering and correctness.
3. At the top level, `await Promise.all([...])` the 10 block functions so they execute
   concurrently instead of serially.
4. Prefix each block's console PASS/FAIL/assert output (e.g. `[qx45] PASS: ...`) so interleaved
   concurrent output stays attributable to its origin block when diagnosing a failure.
5. Preserve every existing assertion verbatim — this is a control-flow/scheduling refactor only,
   never a change to what is asserted or the fixtures used.

## Proposal

A scheduling refactor of one file, correcting the prior "10 isolated blocks, 68 subprocess calls"
premise, which does not match the file: it actually makes **89** total subprocess spawns — **66**
via the `run()` helper plus **23** direct `execFileSync("node", ...)` seeding calls — and only
**~7** blocks are genuinely filesystem-isolated (13/17/18/19/20/21/22, each building its own
`mkdtempSync` tasksDir + workspaceRoot pair; block 9 uses its own serveWorkspaceRoot but reads
the shared `envTasksDir` task store; block 23 needs no workspace). The remaining blocks share the
top-level `tasksDir`/`workspaceRoot` task store (1-7, 14, 15, 16, 24, 25; 25 of the 66 `run()`
calls occur in this pre-856 shared region), and blocks 8/10/11/12 additionally write-and-restore
the SAME `workspaceRoot/.quay/config.yml` (write/restore pairs at lines 419/449, 585/645,
701/781, 807/841) while blocks 4b/5b mutate CLI-1/CLI-2 status mid-stream (lines 337-350,
295-301) — so a faithful `Promise.all` over all these "independent" blocks would race that shared
filesystem state and is not safe as specified.

Corrected mechanism: parallelize ONLY the isolated own-workspace blocks (13/17/18/19/20/21/22)
via `Promise.all`; the shared-resource blocks (1-7, 8, 9, 10, 11, 12, 14, 15, 16, 23, 24, 25)
remain strictly serial (async-uniform, `await`ed in their existing order), keeping the config.yml
write/restore pairs, the 4b/5b status sequencing, block 9's shared-store HTTP server, and block
25's `allTasks.length === 2` sanity intact by construction. The concurrency-safety contract is a
falsifiable invariant rather than an assertion: the concurrent set contains only blocks that
construct their own `mkdtempSync` workspaceRoot, so a reviewable diff can prove no shared-config
or shared-store block was admitted to the parallel set, and no shared resource is touched while
any concurrent block is in flight. Within each block, calls stay sequential (`await run(...)`) to
preserve each block's create→edit→check ordering; assertions and fixtures are unchanged
(control-flow/scheduling only, never a change to what is asserted). Shared-state concurrency is
designed out, not accepted as risk: no block touching the shared task store or the shared
`workspaceRoot/.quay/config.yml` — the write/restore pairs at 419/449, 585/645, 701/781, 807/841,
the 4b/5b status mutations, block 9's shared-store HTTP server, block 25's `allTasks.length === 2`
sanity — is admitted to the parallel set, so no config-write race or shared-store race can arise
and no accepted-risk decision is required. That seriality is itself the falsifiable acceptance
criterion (the added seriality AC): the evidence is a reviewable diff of the concurrency grouping
showing only blocks 13/17/18/19/20/21/22 in the `Promise.all` set and every shared-resource block
serially `await`ed — repeated green runs are not evidence, because a nondeterministic interleaving
race cannot be falsified by N successes.
