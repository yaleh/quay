## Finding

Full-suite profiling (2026-07-26) found `packages/quay/test/cli.test.mjs` is the single largest
contributor to local/CI test wall-clock: 236.06s inside the full 80-file run at
`--test-concurrency=8`, but only 108.9s run in isolation — the ~127s gap is CPU/disk contention
with other concurrently-scheduled files, not this file's own necessary cost. The file predates
`node:test`'s `test()` API (zero registrations — the whole file is one implicit test to the
runner) and makes 89 sequential subprocess spawns (66 via the sync `run()` helper + 23 direct
`execFileSync` seeding calls), summing to strictly serial work.

Structural analysis found the file is internally organized into 25 logical test blocks, of which
7 construct their own filesystem-isolated workspace via `mkdtempSync` — each with its own tasksDir
+ workspaceRoot pair, own `.quay/config.yml`, and no shared `process.env` mutation or
`process.chdir()` calls (confirmed via `grep -n "process\.env\.\|process\.chdir"` — zero hits).
These 7 blocks are correctness-independent of each other but forced to run serially by the file's
construction, not by any real coupling.

## Requested action

1. Convert the `run()` helper from `execFileSync` (sync, blocking) to an `execFile`-based async
   version (promisified via manual Promise wrapper), preserving its existing return shape
   (`{status, stdout, stderr}`) and the exact `err.status ?? 1` error-path symbol at line 134.
2. Wrap each of the 25 test blocks into its own `async function`. WITHIN each block, calls stay
   strictly sequential (`await run(...)`) to preserve each block's existing create-to-edit-to-check
   ordering and correctness. The 23 direct `execFileSync` seeding calls remain synchronous.
3. At the top level, dispatch the 7 isolated-workspace blocks via
   `await Promise.all([block13(), block17(), block18(), block19(), block20(), block21(), block22()])`
   so they execute concurrently instead of serially. The remaining 18 blocks execute in serial
   phases before and after the concurrent set, separated by shared-resource boundaries.
4. Prefix each concurrent block's console PASS/FAIL/assert output via a `makeAssert(tag)` factory
   (e.g. `[qx45] PASS: ...`) so interleaved concurrent output stays attributable to its origin
   block when diagnosing a failure.
5. Preserve every existing assertion verbatim — this is a control-flow/scheduling refactor only,
   never a change to what is asserted or the fixtures used.

### Chosen mechanism

A **single-file scheduling refactor** — zero changes to assertions, expected values, fixtures, or
file count:

**1. Async `run()` helper — implementation status and next step.** The committed file
(c2864b6b) retains the synchronous `execFileSync`-based `run()` helper at lines 143-157:
`try { const out = execFileSync(...); return { status: 0, stdout: out, stderr: "" }; } catch (err)
{ return { status: err.status ?? 1, stdout: err.stdout ?? "", stderr: err.stderr ?? String(err) };
}`. The async function wrappers, `await run(...)` at every call site, `Promise.all` concurrency
grouping, and three-phase execution model are all in place — but `run()` itself is still
synchronous and event-loop-blocking. Because `execFileSync` blocks the entire Node.js event loop
for every invocation, `Promise.all` over blocks that each call `await run(...)` provides **zero
actual concurrency** — each block's first `run()` call blocks all other blocks until the subprocess
exits. The commit message acknowledges the 40% speedup goal was not achieved.

**Proposed next step:** Replace `execFileSync` at line 145 with a promisified `execFile` call
using the `close` and `error` events. Preserve the exact return shape `{status, stdout, stderr}`.
The error path MUST preserve `err.status ?? 1` at line 152 (NOT `err.code`) — `err.code` and
`err.status` are identical for normal non-zero exits but diverge under signal death (`err.code` =
signal name string, `err.status` = null), so substituting `err.code` would change the failure-mode
surface.

```js
import { execFile, execFileSync } from "node:child_process";
// execFileSync import stays for 23 seeding calls (pending async run() conversion)

function run(args, opts = {}) {
  return new Promise((resolve) => {
    const child = execFile("node", [coreBin, ...args], { encoding: "utf8", ...opts });
    let stdout = "";
    let stderr = "";
    child.stdout.on("data", (c) => (stdout += c));
    child.stderr.on("data", (c) => (stderr += c));
    child.on("close", (code, signal) => {
      resolve({
        status: signal ? (code ?? 1) : (code ?? 0),
        stdout,
        stderr,
      });
    });
    child.on("error", (err) => {
      resolve({ status: err.status ?? 1, stdout: "", stderr: String(err) });
    });
  });
}
```

The `close` handler derives `status` from `code`/`signal`; the `error` handler uses
`err.status ?? 1` (identical symbol to line 152). The `run()` function NEVER throws — it always
resolves with `{status, stdout, stderr}`, matching the existing contract.

**(C-4) Claim: the async run() preserves the exact `err.status ?? 1` symbol (line 152) rather than
`err.code`, verified by diff of the run() function body — the error-handling expression is
byte-identical.** AC-1 (assertions unchanged) extends to the run() helper's own error contract. The
`close` handler maps signal-killed processes to `status: 1` (matching the existing fallback, since
`execFileSync` would throw `err` with `err.status === null` and `err.code === signalName` under
signal death).

**2. Block wrapping.** Each of the 25 test blocks becomes its own `async function blockNN()`.
WITHIN each block, `run()` calls become `await run(...)`, preserving each block's existing
create-to-edit-to-check ordering. Direct `execFileSync` seeding calls REMAIN synchronous
(`execFileSync` stays the import, no change to seeding calls) — they execute synchronously within
the block's async function body and block only that block's microtask, not other blocks' concurrent
`run()` promises.

The fire-and-forget `run()` at line 321 (`run(["task", "edit", "CLI-2", "--status", "todo"],
spawnOpts)`) — today synchronous, never awaited but safe because `execFileSync` completes before
the next statement — MUST become `await run(...)`. With async `run()`, a bare `run(...)` without
`await` would launch the subprocess and immediately proceed to the next statement before the
subprocess exits, breaking the block's internal sequencing.

**(C-5) Claim: internal ordering within each block is preserved by `await` on every `run()` call,
and the seeding `execFileSync` calls retain their existing sequencing because they execute
synchronously before any `await` in the same block.** This is AC-1 (ordering guarantees unchanged)
and is reviewable in the diff as "every `run(` call site becomes `await run(` (or

**3. Three-phase execution model** — the concurrency grouping is structural, not heuristic:

- **Phase 1 (serial):** blocks 1-12 execute sequentially via `await` in their original order. This
  includes all 4 config.yml write/restore pairs (blocks 8/10/11/12), all shared task-store
  mutations (blocks 4b/5b), the serve server lifecycle (block 9, which starts and stops its server
  within this phase), and all initial setup assertions. The shared task store reaches a stable
  state (CLI-1 = todo, CLI-2 = todo) by the end of this phase.

- **Phase 2 (concurrent):** `await Promise.all([block13(), block17(), block18(), block19(),
  block20(), block21(), block22()])`. All 7 isolated blocks execute concurrently. Each block
  builds its own temp workspace (own `mkdtempSync` tasksDir + workspaceRoot pair, own
  `.quay/config.yml`), so there is ZERO shared-filesystem contention. Within each block, `run()`
  calls are sequential (`await`), but across blocks they overlap in time. The bottleneck is
  block 19 (7 `run()` calls + 5 seeding spawns = 12 subprocesses, approximately 17.4s).

- **Phase 3 (serial):** blocks 14-16, then blocks 23-25 execute sequentially via `await`. Block
  14 uses `helpOpts` (`cwd: workspaceRoot`), blocks 15/16 use `spawnOpts`, blocks 24/25 use
  `spawnOpts`. All are read-only relative to the shared task store (the task store is stable from

**4. Output prefixing.** Each concurrent block gets a block-level tag (e.g. `[prefix]`, `[sort]`,
`[multilabel]`, `[search]`, `[heading]`, `[qx37]`, `[qx45]`). Mechanism: a `makeAssert(tag)`
factory function that closes over the module-level `failures` counter and the
`console.log`/`console.error` destinations, producing output like `[search] PASS: ...` or
`[sort] FAIL: ...`. The module-level `failures` counter (line 112) is safe without `Atomics`
because `assert()` runs synchronously within a single JavaScript continuation after
`await run()` — the event loop serializes continuations, so two blocks' `failures++` operations
never overlap in time. Serial blocks may also adopt `makeAssert` tags for visual consistency, but
the AC requirement applies only to the concurrent set.

```js
function makeAssert(tag) {
  return (cond, msg) => {
    if (!cond) {
      failures++;
      console.error(`[${tag}] FAIL: ${msg}`);
    } else {
      console.log(`[${tag}] PASS: ${msg}`);
    }
  };
}
```

### Key design decisions

**D1 — Minimum viable parallel set (structural, not heuristic).** Only blocks with provably
disjoint filesystem namespaces are parallelized. The invariant is structural: own `mkdtempSync`
workspaceRoot + own config.yml pointing at own tasksDir = safe to parallelize. No heuristic, no
claim about "independent behavior" — the proof is structural and reviewable.

**D2 — `execFileSync` seeding calls unchanged.** The 23 direct `execFileSync("node",
[nativeBin, ...])` calls are NOT converted to async. They are fast relative to `run()` calls (each
creates a task frontmatter file via native provider CLI, no TypeScript strip-types overhead since

as-measured speedup falls short of 40%, converting seeding calls to async `execFile` is the first
incremental fix — a contained follow-up, not a reason to reject the current approach.

### Defaults and failure behavior

- **Default scheduling:** No new flags, no configuration, no opt-in/opt-out. The refactored
  `main()` unconditionally parallelizes the 7 isolated blocks because the concurrency is safe by
  construction (zero shared state in the concurrent set).
- **Assertion failure:** Any failed `assert()` call, in any block (serial or concurrent),
  increments the module-level `failures` counter (line 112). The final exit code (line 901) is
  `failures === 0 ? 0 : 1`, unchanged.
- **Subprocess failure:** The async `run()` helper resolves with `{status, stdout, stderr}` for
  every spawn, regardless of exit code. Non-zero exit codes do NOT throw — the calling block's
  assertions check `r.status === 0` (or `r.status === 1` for negative tests), exactly as they do
  today.
- **Signal death:** The async `run()` `close` handler checks `signal` — if the subprocess was
  killed by a signal, `code` is null and the promise resolves with `status: 1` (same as the
  existing `err.status ?? 1` fallback for `execFileSync` throwing under signal death with
  `err.status === null`, `err.code === signalName`).
- **Crash in one concurrent block:** If a concurrent block's subprocess crashes with SIGKILL or an
  uncaught exception escapes the block's async function, `Promise.all` rejects, and the outer
  `main().catch(...)` at line 906 catches it, setting `process.exitCode = 1`. This is existing
  behavior — `main()` is already async and has a `.catch()` handler.
- **Block-level failure:** If any `run()` call within a block returns `status !== 0`, `assert()`
  records the failure with the block's prefix tag. The block continues executing (no early abort —
  matching current behavior).
- **Cleanup integrity:** Each isolated block's `fs.rmSync(...)` at its END runs even if a prior
  `await run(...)` returned non-zero status (the block does not throw on assertion failure — it
  increments `failures` and continues, so flow-of-control always reaches the `rmSync` lines). If a
  synchronous `execFileSync` seeding call throws (e.g., disk full), the block's async function
  throws synchronously before any `await`, and `Promise.all` rejects — the `rmSync` at the block's
  end is unreachable in that case (existing behavior, not a new failure mode), but the top-level
  cleanup at lines 1675-1676 runs after ALL blocks complete (both serial and concurrent).

### Alternatives considered and rejected

**A1 — `Promise.all` over ALL 25 blocks (naive parallelization).** Rejected. Blocks 4b/5b mutate
shared task status (lines 295, 301, 306, 337, 348); blocks 8/10/11/12 write-and-restore the same
`workspaceRoot/.quay/config.yml` (4 write/restore pairs); blocks 14/15/16/24/25 pass `spawnOpts`
with `cwd: workspaceRoot`; block 25 depends on `allTasks.length === 2` after all prior operations.
A `Promise.all` over all blocks would nondeterministically race config.yml writes, task-store
mutations, and the `allTasks.length` sanity check. This is not safe regardless of test-runner
concurrency settings.

**A2 — Per-`run()`-call Promise.all within each block.** Rejected. Each block's `run()` calls
follow a sequential create-to-edit-to-check ordering (e.g., block 13: seed 3 tasks -> list with
--prefix PRFA -> list with --prefix PRFA --json -> list with --prefix prfa lowercase -> list with
--json no-prefix). Running these assertions out of order would break the test's internal logic.
Sequential `await` within each block is intentional.

**A3 — Splitting into separate `*.test.mjs` files (one per block).** Rejected as a larger scope.
Extracted files would each be a separate `node:test` test, changing the runner's concurrency model
(from 1 implicit test to N explicit tests subject to `--test-concurrency=8`), changing how failures
are reported (`node:test`'s TAP output vs. current `console.log`-based PASS/FAIL), adding per-file
import boilerplate, and requiring changes to `scripts/test.sh`'s test-file glob. This is a valid
direction but a different task.

**A4 — Converting ALL execFileSync to async (including seeding calls).** Rejected for scope. The
23 direct `execFileSync` seeding calls are part of workspace setup, not the `run()` helper.
Converting them to async `execFile` would approximately double the diff surface (~23 additional
call-site changes + cleanup) for marginal speedup (each seeding call is ~1.45s; making them async
would let them overlap across blocks in the concurrent phase rather than serially accumulating).
This is the first incremental fix if the as-measured speedup falls short of 40%.

**A5 — Keep `execFileSync` but use `Promise.all` with sync functions.** Rejected — `Promise.all`
of synchronous functions does not yield concurrency; each function blocks the event loop until all
its `execFileSync` calls return, so they still execute serially. Async `execFile` is required for
the event loop to schedule other work (including other blocks' `run()` calls) while one block's
subprocess is running.

**A6 — Worker threads (`worker_threads`).** Rejected as over-engineered. The bottleneck is
subprocess spawn latency (~1.45s per process), not CPU-bound computation. `Promise.all` + async
`execFile` already achieves the available parallelism (multiple concurrent subprocesses) without
the complexity of `worker_threads`, data serialization, or message-passing for assertion results.

**A7 — Including block 9 (serve) in the concurrent set.** Rejected. Block 9's
`GET /` handler assertion `body.includes("CLI-1")` depends on the task store content (which blocks
4b/5b mutate). Block 9's server-startup latency is unpredictable (up to 30s budget at line ~547),
and a concurrent block might seed tasks into its own isolated workspace during the same time
window — no conflict, but the timing dependency makes reasoning unnecessarily complex. Keeping
block 9 in Phase 1 serial avoids the timing analysis entirely: the server starts after all
task-store mutations settle, and is killed before Phase 2 begins.

**A8 — Including block 23 (--version/-V) in the concurrent set.** Rejected for marginal benefit.
Block 23 has zero workspace dependency (reads `package.json` from `__dirname`, lines 1592-1593), so
it could safely run in any phase. But it consists of 2 fast `run()` calls (total <100ms, no
subprocess spawn for TypeScript strip-types since the binary resolves quickly). Adding it to the
concurrent set adds a diff line and a claim to verify for negligible speedup. Simpler to keep it in
Phase 3 serial.

**A9 — Lock-based concurrency instead of design-based exclusion.** Rejected. A mutex on
`config.yml` writes (e.g., a lock around blocks 8/10/11/12) would allow those blocks to run
concurrently with non-config-touching blocks, but it would add complexity (lock acquire/release,
deadlock risk, async lock primitives) for marginal gain — blocks 8/10/11/12 together account for
only 6 `run()` call sites. Design-based exclusion (just don't put them in `Promise.all`) is
simpler, safer, and reviewable at a glance.

**A10 — `Promise.allSettled` instead of `Promise.all`.** Rejected. `Promise.allSettled` would
allow all concurrent blocks to complete even if one throws, collecting results. But the existing
failure model is all-or-nothing: if any assertion fails, `failures > 0` and
`process.exitCode = 1`. `Promise.all` rejects on the first unhandled exception, which is close to
the existing behavior (no test continues after an uncaught error). Additionally, the concurrent
blocks' assertions increment the shared `failures` counter (line 112) and do NOT throw, so
`Promise.all`'s rejection only triggers on truly unexpected exceptions (synchronous preamble errors
in seeding calls, subprocess `error` events that the `run()` helper does catch) — a reasonable
fail-fast behavior.

**A11 — Adding `util.promisify(execFile)` instead of manual Promise wrapper.** Rejected.
`util.promisify(execFile)` rejects on non-zero exit codes, which would require `.catch()` handling
at every call site and change the `run()` return convention (from `{status, stdout, stderr}` to
either a resolved result or a caught error). The manual Promise wrapper with explicit `close` and
`error` event handlers gives explicit control over stdout/stderr accumulation, the
`status: signal ? (code ?? 1) : (code ?? 0)` mapping, and the `err.status ?? 1` error contract —
preserving the exact existing return shape and never throwing.
