## Proposal

给全部 5 个 checked-in 的 dynamic workflow 脚本（`.claude/workflows/*.js`）顶部加一个统一的 args
归一化防御，修复一个通过 meta-cc 检查另一个 exp5 loop-driver 会话（session
`80ae3423-65e2-42d1-bbd3-5894a6f0ad3b`）真实发现、且已被那个会话自己诊断确认、临时修复过、但没有
落到仓库里的 bug：Workflow 工具运行时交付给脚本体的全局 `args`，有时候是 JSON 编码的**字符串**而
不是解析好的对象，跟工具自己文档承诺的"verbatim"矛盾；对字符串做 `args.field` 访问得到
`undefined`，链式调用（如 `.match()`）直接崩溃。

## Plan

N/A — directive resolved via a milestone; no staged design doc needed。修复形状已经在会话
80ae3423 里被验证过一次（`execute-milestone` 私有副本打了这个补丁后真的跑通了）：
```js
const $a = (typeof args === 'string') ? JSON.parse(args) : args
```
需要做的是把它变成 5 个 checked-in 文件的**永久**内容，而不是每次靠某个会话现场手动补丁。

## Finding

（全部用 meta-cc 直接核对过 session `80ae3423-65e2-42d1-bbd3-5894a6f0ad3b` 的真实 JSONL 记录 +
`.claude/workflows/wf_*.json` 运行元数据，不是推测）

1. **真实故障链**：`Workflow(execute-milestone)` 用完全正确的 `args`
   （`{workspaceRoot, taskId, charterFile, absorbEntryFile}` 齐全，`wf_5ad0677e-3a0.json`/
   `wf_f7485ff9-b5e.json` 的 `args` 字段记录完整无误）派发了两次，**两次都在脚本第 29 行
   `args.charterFile.match(...)` 处炸掉**：`Error: undefined is not an object (evaluating
   'args.charterFile.match')`。

2. **该会话自己写了两个诊断 workflow 定位根因**：`args-probe`（`log(JSON.stringify(args))`）和
   `args-probe2`（`typeof args`）。`wf_d11b9344-c22.json` 的记录实锤：传入
   `args={"foo":"bar","charterFile":"some/path.md"}` 时，脚本体里拿到的全局 `args` 的 `typeof`
   是 `"string"`——一个 JSON 编码的字符串，不是解析好的对象。这跟 Workflow 工具自己的文档承诺
   （"args: any — the value passed as Workflow's args input, verbatim"）矛盾。

3. **表现不稳定，不是"总是字符串"这么简单**：同一会话里，`drain-directives.js`（跟仓库里
   checked-in 版本字节完全相同，`diff` 确认零差异）被调用两次——第一次因为调用方完全没传 `args`
   （`wf_25dd9c40-fe8`，`args.workspaceRoot` undefined，纯调用方失误）而失败，**第二次传了同样
   内容的 `args` 后却成功**（`wf_6772fd6c-b12`，`status: completed`）。同一份未改动脚本，一次
   失败一次成功——args 到底以什么形态（对象 vs JSON 字符串）交付给脚本体，本身就不稳定/不确定，
   不能假设"调用方传对了就一定没事"。

4. **该会话事后做的修复只打在会话私有临时副本上，没有落到仓库**：在
   `~/.claude/projects/-home-yale-work-quay/80ae3423-.../workflows/scripts/execute-milestone-wf_5ad0677e-3a0.js`
   顶部加了上面 Proposal 里那行归一化代码，把脚本里全部 ~25 处 `args.xxx` 替换成 `$a.xxx`，重新用
   `scriptPath` 派发后台任务 `w7o4k8i27` 成功启动。但这只是 Workflow 工具运行时给这次调用**临时
   物化**出来的私有副本，**不是** `.claude/workflows/execute-milestone.js` 这个 checked-in 的规范
   定义。下一次任何全新的 `Workflow({name:"execute-milestone",...})` 调用（同一会话重新 `/loop`，
   或任何别的会话）大概率会从没打补丁的规范脚本重新物化一份新副本，同样的崩溃可以复现。

5. **实测核对：全部 5 个 checked-in workflow 脚本都直接读 `args.field`，零防御**

1. 在全部 5 个 checked-in workflow 脚本顶部加统一的归一化防御（跟已经在
   execute-milestone 私有副本里验证过生效的写法一致）：

   select-preflight.js 1 处）。

   boilerplate，还是等 Workflow 工具本身提供内置归一化选项；不管哪种，5 个文件不能各自手抄一份、
   以后新脚本容易漏抄同一个坑。
3. 用会话 80ae3423 里已经验证过的诊断手法（`args-probe`/`args-probe2` 的思路），对补丁后的 5 个
   脚本各跑一次真实 `Workflow()` 调用，验证归一化确实生效（无论 args 以对象还是字符串形态到达，

   因为这个原因崩溃。
