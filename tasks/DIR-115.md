## Proposal

给 `.claude/workflows/execute-milestone.js` 里 domain-misfit 这个 Verify-phase check 的 dispatch
prompt 补上 `${args.charterFile}`（可以再加 `${args.taskId}`），跟同一个 `_dispatchList` 里其它 4
个 mechanical check（`ceiling-check`/`gate-hash`/`line-budget`/`dogfood-evidence`）已经在做的事完全
一样。目前 domain-misfit 是这 5 个 check 里唯一一个 prompt 里不带任何里程碑上下文的，代价是它每次
调用都要自己从零"侦查"当前到底在验证哪个里程碑，而不是真正花时间在它该做的判定逻辑上。

## Plan

N/A — directive resolved via a milestone; no staged design doc needed。改动范围是
`execute-milestone.js` 第 72-74 行那一段 dispatch prompt 字符串，加一处插值，不改判定逻辑本身，
不改 schema，不改缓存机制（`_cached('domain-misfit')` 沿用现有的 DIR-079 per-check 缓存路径不变）。

## Finding

的真实时间戳 + 真实 tool-call 轨迹分析，共 33 个真实 domain-misfit 调用样本，跨 2026-07-25 15:33 至
2026-07-26 12:44，约 48 个里程碑）

1. **`execute-milestone.js` 第 72-74 行现状**：
   ```js
   `Apply the domain-misfit audit-channel decision procedure (inherited-core.md) to the milestone's Done-when list. Return {ok: true, step3conclusion} — ok indicates the check completed (always true when the procedure was applied); step3conclusion records whether a misfit was found. This check is INFORMATIONAL, never blocking.`
   ```
   全字符串没有一处 `${args.charterFile}`/`${args.taskId}`/`${_milestone}` 插值——同一 dispatch
   list 里其余 4 个 check 全部都有（例如 gate-hash 的 prompt 显式带
   `--by-reference ${args.charterFile}`）。

2. **统计（33 个真实样本）**：均值 **92s**，中位数 **90s**，标准差 **39s**，范围 45s–234s。作为
   对照，同一批运行里其它 4 个 mechanical check 通常 5-30s（因为路径是直接给的，agent 拿到就能跑）。

3. **两个真实案例的 tool-call 轨迹对比，证实"整段时间花在侦查上"**：
   - **M167/DIR-107（72s，"正常"案例）**：14 次工具调用——读 `inherited-core.md`、读
     `dashboard.md`，试 `node packages/quay/bin/quay.js task get --id DIR-166`（顺带暴露了
     bin/quay.js 那个已知问题），翻 `milestone-candidate` 标签，读 M166 的 charter/audit/task
     文件，**最后一步**才跑一段 `node -e` 内联脚本算出真正的判定结果并返回
     `StructuredOutput`。
   - **M173/DIR-109（234s，你观察到的这次）**：33 次工具调用，94 条消息（远高于其它样本的
     25-67 条）——因为当时 M172/M173/M174 三个里程碑并存、`/tmp` 下有残留的 absorb-entry
     文件、又赶上刚发生的一次 args 传参 bug 重试，环境比平时更乱：grep 了 3 遍
     `inherited-core.md` 找 misfit 定义、翻遍 `milestones/` 目录、试了两种 quay CLI 入口、读了
     charter/`OUTER-LOOP.md`/`git branch`，最后才在 `/tmp/m173-absorb-entry.md` 里确认目标是
     M173/DIR-109，读 `tasks/DIR-109.md` 后才真正开始判定。
   两个案例里，真正应用 domain-misfit 判定逻辑本身都只占最后一两次调用；**其余全部时间是在猜自己
   该测哪个里程碑**。

4. **放到全局比例里看**：从 M167/DIR-107 完整运行拉出 5 阶段真实耗时——Verify(72s，被
   domain-misfit 拖住)/Build(285s)/Audit(252s)/Gate(27s)/Land(286s)，合计 ≈922s（跟该 workflow
   自己记录的 958s 基本吻合）。domain-misfit 单独只占全流程 ~7.5%，修好它每次能省下几十秒到大几
   分钟（取决于当时环境乱不乱），但不是决定总耗时的大头——Build/Audit/Land 合计占了近 90%，是
   inherently 必要的 LLM 工作量（读代码/写代码/对抗审计/合并），不是这次改动的范围。

## Requested action

1. 把 `execute-milestone.js` 第 72-74 行 domain-misfit 的 dispatch prompt 改成显式携带
   `${args.charterFile}`（建议同时带 `${args.taskId}`），例如：
   ```js
   `Apply the domain-misfit audit-channel decision procedure (inherited-core.md) to milestone task ${args.taskId}'s Done-when list (charter: ${args.charterFile}). Return {ok: true, step3conclusion} — ...`
   ```
2. 不改判定逻辑、schema、缓存路径（`_cached('domain-misfit')`/`verifyCacheUpdates`）——纯粹是给
   prompt 补上下文，缩小改动面。
3. 用真实的下一次 `/loop` 冷启动跑一次 execute-milestone，对比新旧 baseline：domain-misfit 的
   tool-call 数 + 耗时应该显著下降（对照组：72-234s / 14-33 次工具调用）。
