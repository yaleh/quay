**type:** execution

## Proposal

Introduce a dedicated, resumable `prepare-milestone` workflow between SELECT/charter authoring and
`execute-milestone`. The existing `quay-task-to-plan` skill remains the single policy/template
source for proposal generation, adjudication, plan authoring, and grounded plan-check; the new
workflow makes that skill's pipeline an actual lifecycle stage instead of an instruction that a
dispatcher may omit.

The prepared state has two authoritative content artifacts:

1. the task's portable `## Proposal`, replaced with an independently re-derived and adjudicated
   proposal; and
2. a milestone-level `docs/plans/M<NN>-<slug>.md`, referenced from the task's `## Plan`.

A generated `milestones/M<NN>/preparation.json` is only a verification receipt, never a second
content source. It records hashes of the Proposal section, charter, Plan, and the source files the
grounded plan-check actually inspected, plus the proposal-review and plan-check verdicts. A
mechanical `milestone-preparation-check` recomputes those hashes immediately before Build. Missing,
failed, or stale preparation returns `revision-needed` and cannot enter Build.

### Lifecycle and ownership

1. `quay-directive` or ordinary task authoring continues to create an initial, substantive
   Proposal. A directive may initially carry `Plan: N/A — directive resolved via a milestone`.
2. After SELECT assigns a task to a milestone and a charter exists, `OUTER-LOOP` invokes
   `prepare-milestone` before final dispatch.
3. For `development` work, preparation runs two independent proposal authors by default (three only
   when SELECT explicitly records high risk), an independent adjudicator, a separate grounded
   proposal reviewer, a Plan author, and an independent grounded Plan checker.
4. For `methodology`/`learning` work, preparation may use the lighter single-author + independent
   review route, but it still produces a real checked Proposal and executable checked Plan. The
   later dual-iteration policy remains unchanged; it is not a substitute for pre-Build planning.
5. The task's `## Plan` is replaced with the checked `docs/plans/*.md` reference. Once SELECTed for
   execution, `N/A` is no longer an acceptable Plan state.
6. `execute-milestone` consumes the checked artifacts. It does not author or repair them in its
   Build phase.

### Proposal contract

The reconciled Proposal must make the implementation approach reviewable without re-designing it:
problem framing grounded in current code, chosen mechanism, concrete control/data flow, key design
decisions, defaults and failure behavior, compatibility, risks, non-goals, AC coverage, and
explicit alternatives considered and rejected. The final proposal reviewer reads the actual
repository and returns a finding count; preparation can pass only with zero unresolved findings.

### Plan contract

The Plan must name the milestone/task/charter and base revision, declare the complete touch set,
map every AC to ordered phases/stages, name real files and symbols, specify RED/implementation/GREEN
or equivalent mechanical checks with expected exit behavior, classify each stage as code or prose,
record line budgets and dependencies, and state guardrails/rollback/real-landing verification.
The Plan checker verifies signatures, call sites, dependency order, commands, budgets, stage
classification, AC coverage, and touch-set completeness against the current repository.

Use one stopping rule everywhere: at most three Plan-check rounds; success requires `F_i = 0`.
Standardize proposal diversity at N=2 by default, N=3 only for an explicit SELECT-time high-risk
flag. This removes the current drift where `SKILL.md` says N=3, its prompt/design says N=2, and
different records use incompatible convergence rules.

### Freshness and batching

Do not invalidate preparation merely because unrelated HEAD content changed. The receipt hashes
the task Proposal, charter, Plan, and each source file named/inspected by the checked Plan:

- Proposal or charter change → rerun the full Proposal→Plan preparation;
- Plan change → rerun grounded Plan check;
- checked source-file change → rerun grounded Proposal/Plan review;
- unrelated-file change → preparation remains valid;
- checked Plan touch set exceeds the task/charter `## Touches` declaration → update the declaration
  and rerun final batch assembly before dispatch.

For concurrent execution, prepare the candidate set first, then run the final
`concurrent-batch-scheduler` using the checked Plan touch sets. A prepared candidate deferred for
overlap keeps its preparation and may reuse it next cycle if all fingerprints still match.

### Alternatives considered and rejected

- **Add Proposal generation to `select-preflight`: rejected.** That workflow deliberately performs
  shortlist preflight with one judgment call; multi-agent generation and revision would make
  selection slow, stateful, and hard to resume.
- **Let the Build agent write Proposal/Plan before coding: rejected.** Design and implementation
  would share one context, the Plan would become an execution-time narration, and direct
  `execute-milestone` invocation could still bypass independent review.
- **Trust `extra.proposalStatus`/`planStatus`: rejected.** Status strings do not prove which task,
  charter, Plan, or source revision was checked and become stale silently.
- **Require exact repository HEAD equality: rejected.** Unrelated commits would invalidate valid
  Plans. File-level fingerprints are the narrow fail-closed boundary.
- **Keep `N/A` for small SELECTed milestones: rejected.** A short executable Plan is acceptable; no
  Plan is not. The goal is a uniform pre-Build invariant, not a size-dependent convention.

## Plan

N/A — directive resolved via a human-steered milestone. That resolving milestone must itself be
prepared manually under `.halt` before changing the preparation pipeline, then implement in this
dependency order: (A) normalize `quay-task-to-plan` defaults/contracts; (B) add the preparation
workflow and receipt/checker with negative fixtures; (C) wire OUTER-LOOP after charter authoring and
before final batch assembly/dispatch; (D) add the independent Prepared gate to
`execute-milestone`; (E) prove the route on one real milestone. Its task `## Plan` must point to a
checked `docs/plans/*.md` before implementation begins—this directive may not self-exempt from the
rule it introduces.

## Finding

The policy and most authoring machinery already exist, but they are not connected to the current
runtime path:

1. `inherited-core.md` defines development dispatch as
   `proposalPlanPipeline(t)`—`quay-task-to-plan` before Build—and marks it mandatory.
2. `.claude/skills/quay-task-to-plan/SKILL.md` already defines independent proposal generation,
   adjudication/write-back, milestone Plan authoring, and grounded convergent Plan checking.
3. `OUTER-LOOP.md` says SELECT performs `author_proposal_plan(c)`, but the actual
   `select-preflight.js` workflow only runs candidate preflight, deliverable classification, and
   shortlist composition. It never invokes `quay-task-to-plan`.
4. `execute-milestone.js` enters Build after its it0 Verify checks and tells one Build agent to read
   the task/charter and implement. It neither invokes nor verifies the proposal→plan pipeline.
5. Therefore the runtime has no non-bypassable boundary between a structurally-valid 40-character
   Proposal/`N/A` Plan and actual implementation. `DIR-109` is a concrete recent example: schema
   PASS, but its Proposal is a one-sentence direction and its Plan contains only a dependency note.
6. Existing real milestones such as M42 show the intended route can work when the charter manually
   instructs the executor to run it first, but a charter note is discipline, not enforcement.

## Requested action

1. Add a `prepare-milestone` workflow, distributed through the existing plugin/runtime workflow
   mechanism, that consumes `{taskId, milestoneId, charterFile, planFile, class}` and orchestrates
   the existing `quay-task-to-plan` prompts: proposal authors → adjudication/write-back → grounded
   proposal review → Plan author → grounded Plan-check/revision.
2. Standardize the skill and prompts on N=2 default/N=3 explicit-high-risk and a maximum of three
   Plan-check rounds with success only at `F_i=0`.
3. Add `milestone-preparation-check.ts` and fixtures. Generate and verify
   `milestones/M<NN>/preparation.json` with Proposal/charter/Plan/checked-source hashes, zero-finding
   review verdicts, Plan-check rounds, and the checked touch set.
4. Change OUTER-LOOP ordering to: SELECT → charter → prepare candidates → final touch/batch assembly
   → execute. Prepared-but-overlap-deferred candidates may reuse a still-fresh receipt.
5. Add an independent `Prepared` phase/gate to `execute-milestone` immediately before Build.
   Direct invocation must fail closed on missing/failed/stale receipt, `N/A` Plan, missing plan
   reference, nonzero findings, or touch-set expansion.
6. Preserve task/body and `docs/plans/*.md` as the content sources of truth. The receipt is derived
   verification metadata only; do not copy Proposal or Plan content into it.
7. Preserve class-specific implementation diversity after preparation: development remains single
   implementation + downstream independent audit; methodology remains dual iteration.
8. Prove real landing with one subsequent real milestone whose durable record shows checked
   Proposal, checked Plan, passing receipt gate, and Build executing that Plan. A synthetic fixture
   alone is necessary but insufficient.
