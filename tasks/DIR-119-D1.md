## Proposal

Add the real, production manifest phase/shard synthesis step that converts a SELECT-produced flat
`MilestoneCandidate` into a `CompositeManifest{phases[], auditShards[]}` — the missing input every
other DIR-119-D child (Build/Audit/Reconcile/Land wiring) depends on. This is child 1 of DIR-119-D's
split (per the `split-multi-mechanism` finding from a real `prepare-milestone.js` ProposalReview run
against the pre-split DIR-119-D: 5 independently landable mechanisms in one candidate, above the
task's own 2-mechanism split threshold). Depends on nothing else in this split; DIR-119-D2 through D5
depend on this child's real, checked-in manifest shape.

### Problem framing (re-verified against current tree, 2026-07-29)

No manifest phase/shard synthesis exists in production. `composite-manifest-synthesis.ts` does not
exist (`find` returns nothing). The only function anywhere producing a `CompositePhase[]` is
`composite-contracts.ts`'s `makeValidCompositeFixture`/`makeSharedPhaseCompositeFixture`, explicitly
test fixtures.

SELECT's real pipeline (`select-preflight.ts`'s already-wired candidate synthesis, chained through
`coupling-graph.ts` → `candidate-synthesis.ts` → `portfolio-choice.ts`) is confirmed by reading its
return type to produce only a flat candidate record (id/taskIds/score) — never a phase/shard
structure. (Existing-state description, not a proposed mechanism.)

Two things ARE genuinely, already wired today, and this proposal builds on them rather than redoing
them. First, the existing composite-preflight check already validates a supplied manifest file
against the composite contract checker when the composite flag is set — for a legacy/no-manifest
call it is a documented vacuous pass, and the gap is specifically that nothing on the production
side ever supplies a real manifest for that check to validate. Second, the existing composite-args
normalizer already accepts the wide-dispatch shape (`{milestoneCandidate:{taskIds,...},
compositeManifestFile,...}`) and its own header comment states the hard invariant of never rejecting
on task-array length — the wide-dispatch entrypoint shape is already load-bearing; what's missing is
a real producer for the manifest-file argument and real consumers of manifest width once Verify has
validated it (DIR-119-D2 through D5's own scope).

**Confirmed there is exactly ONE `select-preflight.js` file in this repo** —
`.claude/workflows/select-preflight.js` — with no `plugin/workflows/` mirror (`find -iname
'select-preflight*'`; `plugin/scripts/config-wiring-check.ts` line 139 hardcodes this same single
path as the repo's intended one-file bespoke-driver design). This is a correction to earlier DIR-119-D
drafts, which wrongly asserted "both wrappers" in some places while correctly stating "one file" in
others — a real, previously-flagged self-contradiction this child's AC wording avoids repeating.

The workflow DSL itself is a hard constraint, not a design choice. It exposes only five globals
(phase/agent/parallel/log/args) — no module-import, filesystem, or shell primitive. Every "wire
module X" claim in this proposal bottoms out in the same one pattern: a labeled agent call invokes a
deterministic, non-selftest JSON CLI wrapping module X's real exported function, and the caller only
branches on the structured JSON result.

### Chosen mechanism

New module `composite-manifest-synthesis.ts` (+ `plugin/scripts/` mirror + a matching test file,
canonical-first then byte-copied, same discipline `sync-vendor.sh --check`/`cmp`/packaging tests
already enforce for every other `composite-*.ts` module).

A pure function `synthesizeManifest(candidate, taskFacts, couplingGraph, capacity) -> {manifest,
context}` takes the exact real SELECT `MilestoneCandidate`, authoritative current task facts
(Touches, AC counts), and the coupling graph, and returns a `{manifest, context}` pair.

It reuses — never reimplements — `touches-orthogonality-check.ts`'s exported
`parseTouches`/`expandGlobs`/`filesDisjoint`, and `coupling-graph.ts`'s exported
`buildCouplingGraph`/`deriveInternalOrderEdges`/`hasProhibitingEdge` (the real exported symbol,
confirmed by reading `coupling-graph.ts` line 164 — not `isProhibiting`, an earlier draft's error).

It builds an undirected overlap graph over declared `## Touches`, union-finds any pair not proven
disjoint into one shared phase with one owner and a deterministic `integrationInvariant` string
naming the members and overlap reason, and translates cross-component internal-order edges into
`requires` (intra-component order becomes ordered instructions, never silently dropped).
Unknown/missing/empty/overbroad/zero-match Touches are treated as overlapping everything — fail
toward fusion, never toward optimistic parallelism.

It emits one `task-ac` audit shard per task plus one `semantic-integration` shard per multi-task
phase, sorts every collection (task ids, phase ids, shard ids, touches/resources unions) so output
is deterministic and byte-identically re-runnable from the same inputs, and derives stable IDs only
from sorted membership and fixed prefixes — never a timestamp, random value, filesystem enumeration
order, or current commit hash.

The CLI accepts candidate/charter/workspace/task-store paths and an output path, validates source
hashes and charter membership, calls `checkCompositeContract()` (existing, unmodified
`composite-contracts.ts` export) on its own output BEFORE writing, and writes via
temp-file-plus-rename so any failure leaves no partial artifact.

Defaults `maxPhases:32`, `maxAuditShards:64`, `maxParallelAgents:4`, `landPolicy:"atomic"` are
explicit exported constants, serialized into `context`, overridable only through validated
`CapacityLimits`; SELECT resource/line budgets are preserved when supplied and capacity violations
are reported with their own reason code.

**Caller-side wiring:** the single real `.claude/workflows/select-preflight.js` file is updated to
pass through the real `portfolio`/selected candidate (not a hand-shaped stub) so the synthesis CLI
receives genuine SELECT output. `OUTER-LOOP.md`'s `execute()` step, when `taskIds.length > 1`,
invokes the synthesis CLI between the real SELECT candidate and the `execute-milestone.js` dispatch
and threads the result as `compositeManifestFile`. No hand-authored manifest satisfies the real
proof required by this child's AC.

**Verify-phase fail-closed reason codes** (consumed by `composite-preflight.ts`, which
DIR-119-D2/D3/D4/D5 exercise but do not modify): a composite-shape dispatch missing
`compositeManifestFile` fails closed with `revision-needed/composite-manifest-missing`; a composite
dispatch combined with `mode:"concurrent"` fails closed with
`revision-needed/composite-concurrent-unsupported`; both checked, by the EXISTING unmodified
`composite-preflight.ts`, before any `{manifest,context}` is accepted into Build. This child's own
scope is emitting a manifest that satisfies that existing check, not modifying the check itself.

### Compatibility

Legacy `{taskId,...}` calls and effective-width-one candidates are unaffected: synthesis is invoked
only when `taskIds.length > 1`. Existing valid hand-authored manifests remain accepted by the
unmodified `composite-preflight.ts` check (no regression to any prior fixture-driven exercise), but
a genuinely wide real dispatch now requires a manifest produced by this real synthesis step — the
task's own AC requires exercising synthesis on a REAL SELECT-produced candidate, not a hand-authored
one. No product-package (`packages/quay*`) or Provider ABI changes.

### Risks and mitigations

- **Vague/missing Touches causing false parallel-safety** — mitigated by reusing the existing
  `parseTouches`/`filesDisjoint`/`hasProhibitingEdge` helpers rather than reimplementing them, and
  biasing unknown input toward fusion, never toward optimistic parallelism; the real proof run must
  use a SELECT candidate whose actual declared Touches are precise enough to produce more than one
  phase (needed by DIR-119-D2's own multi-phase journal proof).

- **Mirror drift** between the canonical script and its vendored `plugin/` counterpart — mitigated
  by the existing sync-check tooling and packaging tests as part of this child's own evidence.

### Non-goals

No candidate-scoring/cadence/portfolio redesign (SELECT-side scoring logic untouched beyond
passthrough). No worktree-per-phase as an isolation mechanism (a DIR-119-D2 concern, not this
child's). No product-package or Provider ABI changes. No modification to `composite-preflight.ts`'s
existing check logic — this child produces valid input for it, never edits it.
