**type:** execution

## Proposal

Add the real, production manifest phase/shard synthesis step that converts a SELECT-produced flat
`MilestoneCandidate` into a `CompositeManifest{phases[], auditShards[]}` — the missing input every
other DIR-119-D child (Build/Audit/Reconcile/Land wiring) depends on. This is child 1 of DIR-119-D's
split — a real bounded-review run against the pre-split parent task found 5 independently landable
mechanisms in one candidate, above the parent's own 2-mechanism split threshold, and recommended
exactly this split. Depends on nothing else in this split; DIR-119-D2 through D5 depend on this
child's real, checked-in manifest shape.

### Chosen mechanism

New module `experiments/quay-perpetual-stream/scripts/composite-manifest-synthesis.ts`,
byte-identically mirrored to `plugin/scripts/composite-manifest-synthesis.ts` (the same
canonical-first + `sync-vendor.sh --check`/`cmp` discipline every other `composite-*.ts` module
already uses — verified byte-identical today for `composite-contracts.ts`), plus a matching test
file in both locations.

**Core pure function:**
```
synthesizeManifest(candidate: MilestoneCandidate, taskFacts: TaskCandidate[],
  couplingGraph: CouplingGraph, capacity?: Partial<CapacityLimits>)
  -> { manifest: CompositeManifest, context: CompositeContext }
```

**[WIRING CLAIM 1 — reuse, not reimplementation]** It imports and calls the real exported
`parseTouches`/`expandGlobs`/`filesDisjoint` from `touches-orthogonality-check.ts` (confirmed present
at lines 63/152/162) and `buildCouplingGraph`/`deriveInternalOrderEdges`/`hasProhibitingEdge` from
`coupling-graph.ts` (confirmed real exported names via `grep -n "^export"` — `hasProhibitingEdge` at
line 164, not `isProhibiting`, which is `candidate-contracts.ts`'s own distinct export that
`coupling-graph.ts` merely imports internally and does not re-export). This is AC bullet 3 on the
task as currently written; this proposal keeps that item exactly, does not weaken it.

**Fusion algorithm:** build an undirected overlap graph over each task's declared `## Touches` (via
`parseTouches`/`expandGlobs`/`filesDisjoint`); union-find any pair of tasks NOT proven disjoint into
one shared `CompositePhase` with exactly one owner and a deterministic `integrationInvariant` string
naming the fused members and the overlap reason (shared file path(s), expanded globs, or
"undecidable — treated as overlapping"). `hasProhibitingEdge` pairs are excluded from fusion (a
prohibiting edge between two tasks must never be masked by putting them in one phase) — checked
*before* any union-find step, not after, so the CLI can fail with a distinct reason before manifest
assembly even begins.

**Correction (2026-07-29, ProposalReview finding, evidenced further at AC17):** the pre-existing
`candidate-synthesis.ts` module already prunes any prohibiting-pair task union before a candidate
is ever constructed, at both of its call sites (grep-confirmed). A real SELECT-produced candidate
therefore never structurally contains a prohibiting-edge pair, and this fusion-exclusion check can
never be exercised end to end via the real production dispatch path. The behavior is still a
required, falsifiable part of this Proposal's own scope, but as a defense-in-depth guarantee of the
pure synthesis function's own contract, exercised at the unit level directly (not via a real
SELECT-produced candidate) — see AC17 for the exact evidence commitment. This Proposal commits the
test file (`composite-manifest-synthesis.test.mjs`) to a required fifth RED/GREEN scenario — calling
`synthesizeManifest()` DIRECTLY (unit-level, not via the CLI's SELECT-fed real-candidate path) with
two candidate member tasks joined by a `hasProhibitingEdge` coupling edge — asserting (a) the
prohibiting-edge check runs before any union-find step, (b) the CLI exits with a distinct reason code
naming the conflicting pair, and (c) no manifest file is written (RED fixture), followed by GREEN
confirmation once the check is implemented. This guards a future caller that does NOT pre-prune
(e.g. a hand-authored manifest input, or a future SELECT variant) — it is honest belt-and-suspenders
coverage of this module's own contract, not a claim that today's real dispatch path can trigger it.
AC bullet 10 on `tasks/DIR-119-D1.md` today enumerates
four scenarios by name (overlapping-Touches fusion, fail-toward-fusion-on-ambiguous-input,
deterministic sorted output, temp-file-plus-rename fail-closed write) without naming this fifth one;
this Proposal treats that enumerated list as the historical minimum, not a ceiling, and adds the
prohibiting-edge scenario as a binding Proposal-level requirement on top of it — Build does not get
to treat AC bullet 10, or this Proposal's own Fusion-algorithm claim, as satisfied without this exact
RED/GREEN evidence existing in the test file. This closes the coverage gap at the Proposal level
without depending on the AC section's literal enumerated text being separately edited first; it
remains open to adjudication/Plan-authoring to also update AC bullet 10's own wording to name this
scenario explicitly, but this Proposal's own required work no longer waits on that edit.**
`deriveInternalOrderEdges` converts same-component internal-order edges into a
phase's `requires` list (never silently dropped); intra-component ordering between tasks already
fused into one phase is preserved as ordered `auditShardIds`/instructions rather than dropped.
Missing/empty/unparseable/overbroad Touches bias toward fusion (safety), never toward optimistic
parallelism.

**Shard emission:** one `task-ac` shard per member task, one `semantic-integration` shard per
multi-task phase (`taskIds.length > 1`). All collections (task ids within a phase, phase ids, shard
ids, touches/resource unions) are `.sort()`ed before emission; IDs are derived only from sorted
membership + fixed string prefixes (e.g. `phase-${sortedTaskIds.join("+")}`, never a
timestamp/`Math.random`/`Date.now()`/directory-walk order/commit hash) so two runs against identical
inputs produce byte-identical JSON.

**[WIRING CLAIM 2 — self-validation before write, detailed above under Chosen mechanism]**
The CLI wrapper accepts candidate/charter/workspace-root/task-store-dir/output-path flags (matching
the sibling preflight checker's own CLI convention so the whole composite-CLI family stays
uniform), validates the candidate's task ids against the charter's declared scope and current
source hashes, then self-validates its own freshly-built output before writing anything. On a
contract violation the CLI exits non-zero and writes nothing — the AC item above requires a RED
fixture proving this rejected-pre-write behavior. On success it writes via a temp-file-plus-rename
discipline (`fs.writeFileSync(tmp)` then `fs.renameSync(tmp, out)`) so a crash mid-write never
leaves a partial/corrupt manifest for the downstream contract checker to later read as valid-looking
JSON — **verified by direct repo-wide search (`grep -rln "renameSync"`, zero matches outside this
new module) that no such discipline is reused from an existing writer elsewhere in this codebase
today, including the preparation-receipt writer (`milestone-preparation-check.ts`, which writes
directly via `fs.writeFileSync` with no temp-file/rename step); this proposal introduces the
temp-file-plus-rename pattern to this module on its own merits, not as reuse of an existing
precedent, correcting an earlier draft's inaccurate claim of such a precedent.**

Defaults are real exported constants (see the capacity-defaults AC item above for the exact list
and where each field structurally lives), serialized into the returned context, overridable only
through a validated options object — no ad hoc partial overrides at each callsite.

**[WIRING CLAIM 3 — SELECT-side caller passes the real portfolio through, detailed above under
the AC item of the same name]** The sole real SELECT-side driver file is edited so the field the
candidate-portfolio logic already computes and attaches to its result is threaded through into the
structured JSON that workflow returns to its caller, rather than being read internally and
discarded.

**[WIRING CLAIM 4 — OUTER-LOOP's dispatch step invokes the synthesis CLI and threads its output,
detailed above under the AC item of the same name]** The dispatch-driver document's own step gains
new text: when the chosen candidate/batch is genuinely multi-task, a new step runs the synthesis
CLI BEFORE the milestone-execution dispatch and threads the resulting manifest path into that
dispatch's args, alongside the pre-existing argument names. This is a doc-text change only — the
workflow DSL's five globals expose no import/filesystem/shell primitive — analogous in kind to how
the sibling preflight checker is already invoked as a labeled shell-out inside the dispatch
workflow's own Verify phase today.

### Concrete control/data flow

1. SELECT cycle runs today's already-wired candidate-portfolio pipeline inside the sole real
   dispatch driver, producing a portfolio result [WIRING CLAIM 3 changes what the driver
   additionally exposes from this step — see the AC item of that name above].
2. For a single-task chosen candidate, the dispatch driver's execution step uses the unchanged
   legacy dispatch shape — no synthesis CLI call, zero behavior change (compatibility invariant,
   see AC18, the legacy golden-replay item, added 2026-07-29 to close a dangling reference this
   Proposal's own earlier draft left unbacked by any real AC bullet).
3. For a genuinely multi-task candidate, the execution step first shells out to this child's new
   synthesis CLI with the real selected candidate, current task facts read fresh from the task
   store (not cached/stale), and a freshly built coupling graph, producing the manifest/context
   pair [WIRING CLAIM 1 — see the AC item of that name above].
4. The CLI self-validates before writing [WIRING CLAIM 2 — see the AC item of that name above]; on
   violation it exits non-zero and the dispatch driver treats this as a hard stop before Build is
   ever reached — fail-closed, a bad manifest never reaches the milestone-execution phase at all.
5. On success, the manifest file path is threaded into the milestone-execution dispatch's args
   [WIRING CLAIM 4 — see the AC item of that name above].
6. The milestone-execution workflow's pre-existing, unmodified Verify phase re-validates the
   manifest a second time, independently, reading from the file on disk — defense in depth against
   a manifest mutated or corrupted between synthesis and dispatch, not a single trust-on-write
   assumption.
7. Build/Audit/Gate/Land proceed exactly as the milestone-execution workflow already implements
   today for the composite path — unchanged by this child (later sibling children's own scope).

### Key design decisions

- **The manifest-missing/concurrent-unsupported reason-code AC item is treated as a pre-existing,
  separately-tracked defect in the inherited task body, not silently absorbed into D1 and not
  silently dropped.** Because grep confirms these two reason codes exist nowhere in the codebase,
  and this child's own Non-goals explicitly forbid modifying the existing manifest-validation
  checker's logic, D1 cannot honestly claim to satisfy that AC item as originally written without
  either editing the checker (contradicting the stated Non-goal and the declared touch-set, which
  does not include that file) or fabricating test evidence for behavior the shipped code does not
  exhibit. This proposal's resolution: document the actual current behavior honestly as a RED
  fixture demonstrating the current gap, and recommend real enforcement be scoped to whichever
  later sibling child legitimately touches that checker file. Silently asserting a passing item
  that doesn't match shipped behavior would repeat exactly the kind of prose-over-proof failure
  this repo's own prior directives already found once — better to surface it now than have it
  re-discovered by a later independent audit.
- **The Build-phase concurrency cap is NOT part of the shared manifest-contract type's own
  capacity-limits interface** (confirmed by reading that interface directly: it declares only two
  required fields plus two optional line-estimate fields — no concurrency-cap field). That field
  instead belongs to a separate, Build-phase-only options type — a DIR-119-D2 concern, not this
  child's. This proposal satisfies the underlying AC requirement (a real exported default constant,
  serialized into context, not an inline literal) by exporting one combined defaults constant from
  this child's own new module, populating the manifest-contract's own capacity field with only the
  subset the contract checker actually validates, while the concurrency-cap value rides along in
  the synthesis module's own output as advisory metadata for the later Build-phase child to read —
  never smuggled into the shared contract type, which is outside this child's declared touch set.
- **Reuse over reimplementation** for both Touches parsing and coupling-graph construction — the
  charter and task both name this as a requirement, and it is independently the right call: these
  modules already carry their own test coverage and are the single source of truth for
  disjointness/overlap semantics elsewhere in the composite pipeline (another dispatch-scheduling
  module already depends on the same Touches-parsing module today).
- **Fail-toward-fusion, never fail-toward-parallelism** for ambiguous Touches — matches the task's own
  stated risk mitigation and is the safer default: the cost of a false negative (fusing two tasks
  that could have run in separate phases) is wasted parallelism, while the cost of a false positive
  (declaring two conflicting tasks independently phased) is a Build-time collision in the shared
  working tree — the exact concrete failure mode this repo's own operating guidance already
  documents.
- **Self-validation before write, not after** — the contract check runs on the in-memory output
  before any file touches disk, so a failed synthesis run never produces a manifest file a later,
  unrelated process could accidentally pick up and treat as valid.
- **CLI-wrapped pure function, not inline workflow-DSL logic** — forced by the workflow DSL's
  documented five-global constraint, the same constraint the sibling preflight checker's own header
  comment names as the reason it exists as a separate CLI rather than inline code.
- **Determinism via sorted collections + membership-derived IDs**, not incidental ordering — required
  both by the byte-identical-rerun AC clause and because the contract checker's own cycle-detection
  logic is order-sensitive if phase IDs collide or reorder nondeterministically; a non-deterministic
  manifest would also make the RED/GREEN fixture tests themselves flaky.
- **Capacity defaults as named exported constants, not inline literals** — makes the values
  independently greppable/auditable (an AC item above requires this) and gives later sibling
  children one place to read the same numbers from if their own scope needs them.
- **Temp-file-plus-rename introduced fresh, not reused from an existing precedent** — a repo-wide
  `renameSync` search confirms no other writer in this codebase (including the preparation-receipt
  writer) currently uses this discipline; this module adopts it on the strength of the general
  crash-safety argument (an interrupted write must never leave a partial file a downstream reader
  could mistake for valid), not because it is following an established local pattern. An earlier
  draft of this Proposal incorrectly claimed such a precedent existed; that claim is corrected here.
- **WIRING CLAIM 3 and 4 stay part of this one child, not a further split, despite each having its
  own named claim** — a ProposalReview round (2026-07-29) flagged 4 named WIRING CLAIMs as
  potentially 4 independently-landable mechanisms (above the repo's 2-mechanism split threshold).
  This is corrected here: WIRING CLAIM 1+2 (the new module + CLI) are the actual deliverable and
  are naturally cohesive — a CLI with no self-validating output is not a landable thing. WIRING
  CLAIM 3 (a single-field passthrough edit to one existing prompt file) and WIRING CLAIM 4 (a
  doc-text edit naming one new invocation step) are each too small to independently land or be
  independently useful — a synthesis CLI nothing calls (no WIRING CLAIM 4) has no consumer, and a
  SELECT-side portfolio field nothing downstream reads (no WIRING CLAIM 1/2 to consume it) is dead
  data. They are named as separate WIRING CLAIMs only because DIR-117's mechanism-claim wiring
  coverage convention requires every distinct call/dispatch/ownership relationship to be named and
  separately evidenced — that naming discipline is not the same thing as independent landability.
  Unlike DIR-119-D's original 5-way split (5 substantial, genuinely separately-buildable modules —
  Build/Audit/Reconcile/Land/this synthesis child), splitting D1 further would produce 1-2 line
  diffs as their own milestones, disproportionate process overhead for wiring completions that only
  make sense alongside the module they connect.

### Defaults and failure behavior

- No override supplied → the default capacity constant named in the AC item above applies;
  SELECT-side resource/line budgets are passed through and preserved when supplied (never silently
  dropped), overridable only through a validated options object (no ad hoc partial overrides).

- Unknown/missing/empty/overbroad/zero-match Touches on any member task → fused into the broadest
  phase that touches it (fail toward fusion) — never silently excluded from the manifest, never
  optimistically parallel.

- A prohibiting coupling edge (`hasProhibitingEdge`) between two candidate member tasks → CLI fails
  before manifest assembly even begins, with a distinct reason code naming the conflicting pair, no
  partial output. **This is a required, falsifiable Proposal commitment, not mere prose — see Chosen
  mechanism / Fusion algorithm above: this Proposal expands the test file's own AC-bullet-10 scope to
  include a dedicated RED/GREEN scenario proving this exact ordering/reason-code/no-partial-output
  behavior, exercised as a direct unit-level call to `synthesizeManifest()` since a real
  SELECT-produced candidate can never structurally contain such a pair (see the Fusion-algorithm
  correction above).**

- A contract violation on the synthesis module's own output → CLI exits non-zero, prints
  violations, **writes nothing** — verified via a RED fixture: hand-corrupt a synthesized manifest
  in-memory before the write step (e.g. a shared phase missing its integration-invariant field), in
  the test file, and assert no file lands on disk; the dispatch driver treats this as a hard stop
  before Build is ever reached rather than falling back to a vacuous single-phase manifest.

- Any crash mid-write → temp-file-plus-rename means the target path either has the last-good content
  or doesn't exist; it is never truncated/partial.

- `taskIds.length === 1` → synthesis is never invoked; the legacy path is byte-for-byte unaffected
  (compatibility invariant, see below).

- A composite dispatch that reaches `execute-milestone.js`'s Verify phase WITHOUT a
  `compositeManifestFile` (e.g. if `execute()`'s new invocation step is itself skipped or fails
  silently upstream) still hits the EXISTING, unmodified `composite-preflight.ts` **vacuous-pass**
  path, not a fail-closed rejection — this is the corrected (not aspirational) description of current
  behavior; per the Problem-framing/Key-design-decisions correction above, this proposal does not
  claim or implement a fail-closed rejection at that boundary, only supplies real input to it.
  Implementing one would require editing `composite-preflight.ts`, out of this child's Non-goals.

### Compatibility

Legacy single-task calls and effective-width-one candidates are entirely, byte-for-byte
unaffected — synthesis is invoked from the dispatch driver only for a genuinely multi-task
candidate, confirmed by direct read of the wide-dispatch normalizer's branch structure (its two
shape-detection branches are fully disjoint code paths, not a shared path with a conditional).
Existing valid hand-authored manifests remain accepted by the unmodified contract checker —
nothing in this module changes contract-check semantics, it only produces a new kind of valid
input; a genuinely wide real dispatch now requires a manifest produced by this real synthesis
step, and the task's own AC requires exercising synthesis on a REAL SELECT-produced candidate, not
a hand-authored one. No product-package code or Provider ABI change — confirmed this proposal's
Touches list is entirely within the experiment scripts, workflow drivers, and their vendored
mirror trees.

### Risks

- **AC-wording/behavior mismatch on AC bullet 4** — the highest-priority risk for this proposal
  specifically, because it is a defect in the task's own acceptance text discovered by grounding
  against current source, not a risk in the mechanism itself. Mitigated by the RED fixture proving
  the checker's real current vacuous-pass behavior and by flagging the wording correction explicitly
  for adjudication/review rather than quietly reinterpreting the AC unilaterally during Build.
- **Prohibiting-edge fusion-exclusion required a dedicated falsifiable AC-level commitment, AND is
  structurally unreachable via the real SELECT-to-dispatch path** — the Chosen-mechanism prose
  describes a specific ordering (checked before union-find), reason code, and no-partial-output
  guarantee for `hasProhibitingEdge` pairs; AC bullet 10 (the test-file coverage item) as currently
  worded on `tasks/DIR-119-D1.md` names only four scenarios and not this one. Resolved at the
  Proposal level (see Chosen mechanism / Fusion algorithm above): this Proposal makes the
  prohibiting-edge RED/GREEN scenario a required fifth item within the test file's own scope,
  independent of whether AC bullet 10's literal enumerated text is separately amended to name it —
  the behavior is no longer asserted as prose only, it is a required, falsifiable test commitment of
  this Proposal's own Requested-action test-file work item. **Corrected 2026-07-29 (ProposalReview
  finding):** because `candidate-synthesis.ts` already prunes prohibiting-pair unions before
  `MilestoneCandidate` construction, this scenario is exercised as a direct unit-level call to
  `synthesizeManifest()`, not via a real SELECT-produced candidate — this Proposal states that
  honestly rather than implying end-to-end reachability that does not exist. Residual risk is
  limited to whether a later adjudication also updates AC bullet 10's literal wording for full
  textual parity; that edit, if made, is additive and does not change what this Proposal already
  requires be built and tested.
- **Vague/missing Touches causing false parallel-safety** — mitigated by reusing the existing
  disjointness helpers and biasing unknown input toward fusion (see Defaults above); the real proof
  run must be against a SELECT candidate whose actual declared Touches are precise enough to produce
  more than one phase (needed by DIR-119-D2's own multi-phase journal proof — an external dependency
  this child does not control the timing of, only the shape it hands off).
- **SELECT-side driver prompt-text edit risk** — it is an LLM-driven agent prompt, not code; a
  wording change that fails to actually thread the portfolio field through would be a silent no-op.
  Mitigated by requiring a real, non-selftest run showing the returned JSON actually contains a
  non-empty portfolio field for a real multi-candidate SELECT cycle, not just a source-text grep of
  the prompt.
- **Mirror drift** between canonical and vendored copies — mitigated by the existing sync-check
  tooling (verified byte-identical today for a sibling composite module), exercised as this child's
  own evidence.
- **Coupling-graph API drift** — the coupling module is maintained by sibling DIR-119 work; a
  future rename of its exported edge-check function would silently break this module's import.
  Mitigated by import-grep evidence being part of this child's own AC (already required) and by the
  type checker's own compile-time verification (a renamed export fails immediately, not silently).
- **Coupling-graph recomputation cost at synthesis time** — the coupling-graph builder recomputes
  from task facts on every synthesis call rather than reusing any cache from the earlier
  SELECT-cycle computation; acceptable at current milestone-candidate widths but worth naming as a
  non-blocking scaling risk for a future child if candidate widths grow substantially.

dispatch path from the phase-fused composite manifest this child produces).

### Alternatives considered and rejected

1. **Extend `composite-contracts.ts` itself with a `synthesizeManifest` export**, instead of a new
   module. Rejected: `composite-contracts.ts`'s own header states it is "Pure, fixture-driven, NO I/O"
   and "the ONE place this shape gets validated" — conflating the validator with the producer would
   blur that single-responsibility boundary the existing module explicitly claims, and would make the
   RED "contract-violating output rejected" test circular (checker validating output from a function
   living in the same file as the checker).
2. **Have the SELECT-side driver itself run the full synthesis inline**, skipping a separate
   dispatch-time invocation step. Rejected: selection and dispatch are different points in the
   outer driver's own pipeline with different lifetimes (a candidate can be selected without
   necessarily being dispatched this cycle); synthesizing eagerly at SELECT time would compute (and
   risk going stale on) a manifest that might never be consumed, and would require the SELECT-side
   driver to also own manifest-file lifecycle/cleanup, expanding that file's responsibility beyond
   candidate selection.
3. **Inline the fusion/shard logic directly into workflow-DSL prompt text**, having an LLM agent

   violates the repo-wide pattern (every other `composite-*` concern is a real TS module behind a
   thin CLI, never inline prompt reasoning) — directly contradicts the DoD's "prompt text...
   insufficient" standard.
