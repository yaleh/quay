## Proposal

Make `execute-milestone.js`'s Build phase literally dispatch one agent per manifest phase
instead of the pre-existing single monolithic agent call regardless of manifest width. That per-phase
path dispatches exactly one labeled `build-phase-<id>` agent per manifest phase and respects
`requires` edges, so the DAG order is observable off the real dispatch, not asserted in prompt
prose. Second child of DIR-119-D's split (`split-multi-mechanism` finding). Depends on
DIR-119-D1's real, checked-in `composite-manifest-synthesis.ts` output shape for its real proof run.
Both halves of that mechanism claim carry hard, non-prose evidence contracts: per-phase dispatch
counts AND `requires`-edge observance are read off the real dispatch's workflow RESULT record
(`workflows/wf_*.json`'s `workflowProgress[]`, which carries one `{type:"workflow_agent", label,
phaseIndex}` entry per labeled dispatch — NOT `journal.jsonl`, whose entries carry only
`{type, key:"v2:<hash>", agentId[, result]}` and no label, batch index, or phase id), parsed off disk
per the M195/M197/M203 audit precedents, plus production import-graph wiring — not AC-citation prose.

## Chosen mechanism

Add non-selftest JSON CLI modes to `composite-build.ts`: `--plan-json` (a PURE wrap of the
existing, already-exported `planPhaseExecution` — it changes NO planner semantics, so the existing
`parallel-agentcount-capped-below-task-count` selftest (5 phases, cap 2 → `agentCount <= 2`) still
passes unchanged) and `--map-evidence-json` (a pure wrap of the existing, already-exported
`mapEvidenceToTasks`, inheriting its skip-missing / dedupe-duplicate behavior as-is).

Planning chunks dependency-ready levels into batches capped at `maxParallelAgents` simultaneous
dispatches. Two naming layers must not be conflated: the PLANNER's `owners` map (untouched by the
pure wrap) assigns concurrency owners `build-agent-${cursor % maxAgents}`, so its distinct-owner
count is `min(phaseCount, maxParallelAgents)` — this is what the cap bounds and what the existing
selftest asserts; the WORKFLOW's dispatch LABEL `build-phase-<phaseId>` is applied by
`execute-milestone.js` itself, one per manifest phase, regardless of which planner owner the phase
maps to — so `build-phase-*` label/dispatch count always equals the phase count regardless of the
cap. Per-phase labeling is a workflow-level guarantee, not a planner change; `--plan-json`'s pure
wrap leaves the selftest untouched.

A labeled `build-plan` helper agent invokes the plan CLI; batches then run serially — each dispatch
is recorded in the workflow RESULT record (`workflows/wf_*.json`), whose `workflowProgress[]` carries
one `{type:"workflow_agent", label, phaseIndex}` entry per labeled dispatch (label and phase id, with
batch ordering read off that same record — NOT off `journal.jsonl`, whose entries carry no label,
batch index, or phase id), and that record MUST show batch i's phases dispatched and completed before
batch i+1's phases dispatch (the `requires` observance contract, `PhaseExecutionPlan.batches`'
"batch i+1 only starts once batch i's phases finish" — a dispatcher that ignores `requires` edges and
fans all phases out in one parallel batch violates this ordering, which is readable off disk per the
M195/M197/M203 per-dispatch audit precedents). Within each proven dependency-ready, proven-disjoint
batch the workflow calls
`parallel()` with exactly one labeled `build-phase-<id>` agent per phase in that batch, each prompt
scoped ONLY to that phase's task IDs, predecessors, invariant, allowed Touches, and evidence schema
— a scoping guarantee with its own falsification surface: the raw per-dispatch agent records under
`~/.claude/projects/.../subagents/workflows/wf_*/agent-*.jsonl` (which M197's audit parses
directly) must show no `build-phase-<id>` prompt referencing another phase's task IDs or Touches
outside its allowed set. Phase workers never stage or commit.

A final serial `build-integrate` helper integrates in deterministic topological order, runs
integration tests, creates the ONE candidate-generation commit, and invokes `--map-evidence-json`.
In-scope-changed-file validation, unexpected-commits-mid-Build detection, and generation-mismatch
fail-closed are NOT claimed by this child — they are deferred to DIR-119-D3/D4's Audit/Reconcile
scope (and any future hardening child); this child's commit-safety guarantee is only the one stated
in the next paragraph.

Because this repo runs milestones directly in a shared working tree with no per-phase worktree
isolation on the default path (CLAUDE.md's own corrected note on `execute-milestone.js`'s Build
phase), phase batches that could theoretically run independent git-writing agents must instead
serialize at the one integration-commit step — a cap on `maxParallelAgents` bounds simultaneous
*inspection/build* work, never simultaneous *commits*. The honest fail-closed boundary, stated
against the code that actually exists: CYCLES fail closed before mutation via the UPSTREAM
`composite-contracts.ts` validator (which Build runs against the manifest before any dispatch) —
the wrapped planner itself does NOT fail closed on cycles, it appends remnants in declaration order
and still emits a plan, so the pre-dispatch validator call is what carries this guarantee;
DANGLING/unknown `requires` are NOT fail-closed (both existing validators silently skip them —
preserved behavior, not a gate); evidence mapping (`mapEvidenceToTasks`, which skips nonexistent
evidence and dedupes duplicates) runs at integrate time, AFTER phase workers have mutated the tree,
and is by construction not a pre-mutation gate. Mid-batch phase-worker failure IS specified: if a
`build-phase-<id>` worker returns non-`done` mid-batch, Build fails closed immediately — no further
batches dispatch, `build-integrate` does not run, and no candidate-generation commit is created
(the commit-safety half is structurally entailed by `build-integrate` being the sole
commit-creator); the uncommitted partial changes phase workers left in the shared tree (phase
workers never commit) are left in place for Audit/Reconcile (DIR-119-D3/D4's scope) — this child's
guarantee is that the ONE commit is never created on top of a failed batch, NOT that the working
tree is rolled back. That failure branch has a precise off-disk falsification surface — the exact
shape a violation would take — even though, per the accepted-risk decision recorded below and in
Key design decisions, THIS child does not gate on a dedicated failure-injection AC/DoD item: a real
or deliberately-injected failing `build-phase-<id>` worker (one returning non-`done`) would leave
three checks readable off disk — the real workflow RESULT record (`workflows/wf_*.json`'s
`workflowProgress[]`) shows that batch's `build-phase-<id>` entry non-`done`, NO later-batch
`build-phase-<id>` entry present, and the `build-integrate` label entirely ABSENT (this
skip-`build-integrate`-on-failure branch is the one no success-path item
exercises); `git log`/reflog shows zero candidate-generation commits created after the failing
batch; and Build returns `needs-human` immediately. Any run whose `workflows/wf_*.json`
`workflowProgress[]` shows a `build-integrate` entry, or any candidate-generation commit, after a
non-`done` `build-phase-<id>` entry would violate that surface. **Accepted-risk decision (this round),
stated explicitly rather
than left silent:** the skip-`build-integrate`-on-failure control-flow branch is documented and
ACCEPTED as a reasoned, bounded residual risk of THIS child rather than gated by a dedicated
failure-injection AC/DoD item. Two stated reasons make this a defensible accepted risk, not an
untested one slipped through: (a) the commit-safety half — no candidate-generation commit on top of
a failed batch — is structurally entailed by `build-integrate` being the sole commit-creator, an
invariant AC8 already evidences (if `build-integrate` never runs, no commit can exist), so the most
dangerous half of the failure branch is NOT ungated; and (b) the residual ungated half — the
needs-human-return / no-further-batch control flow and the deliberately-left-in-place partial
working-tree changes — is small, reviewable control flow in `execute-milestone.js`, and its
tree-rollback half is explicitly OUT of this child's scope (deferred to DIR-119-D3/D4's
Audit/Reconcile). This is recorded here and as a Key design decision so the ready->done gate and any
human verifier encounter it as a named, bounded residual, never as a silent untested gap
masquerading as an evidenced guarantee.

Legacy width-1 never touches this new dispatcher. The dispatch predicate is exact: the new
per-phase path fires IFF `_isComposite && _taskIds.length > 1` — it branches on width, not on
`_isComposite` alone, precisely because `_normalizeExecuteArgsInline` returns `isComposite: true`
for the agreed composite-shaped singleton (the `hasLegacy && hasNew && agrees` case falls through
to the `hasNew` branch), which already fires the composite text block (now at L456) TODAY. Under
this predicate that singleton — like the legacy `{taskId,...}` shape — stays on the existing
single-agent path with that composite text block unchanged; the existing single-agent Build path
is completely untouched, additive not rewritten.

### Key design decisions

- **Overlap fuses into one phase owner; uncertainty fuses, never parallelizes.** Consumed from
  DIR-119-D1's synthesis output — a valid candidate with precise disjoint Touches must produce more
  than one phase for THIS child's real proof run, or the multi-phase AC item is unproven.

- **No concurrent commits in the shared working tree.** `maxParallelAgents` only bounds simultaneous
  inspection/build work, never simultaneous commits — `build-integrate` is the sole, serial
  commit-creating step.

- **Legacy path is a hard boundary, not a fallthrough.** Width 1 stays completely untouched, the
  compatibility oracle for DIR-119-D5's golden-replay test.

- **The skip-`build-integrate`-on-failure branch is an explicit accepted-risk decision, not an
  evidenced guarantee.** This child's hard, falsifiable evidence covers the success path and the
  sole-commit-creator invariant (AC8); the failure-injection path (a non-`done` `build-phase-<id>`
  worker) is accepted as a documented, bounded residual risk rather than gated by a dedicated AC/DoD
  item. Its commit-safety half is structurally entailed by that sole-commit-creator invariant (no
  `build-integrate` run => no candidate-generation commit), and its working-tree-rollback half is
  deliberately out of scope for this child (DIR-119-D3/D4's Audit/Reconcile). Named here so it is a
  bounded, visible residual, never a silent untested gap.

### Risks and mitigations

- **Control-plane regression on the one script every future milestone runs through** — mitigated by
  keeping the repo-root halt sentinel present for the duration of Build, never running this child
  concurrently with any other dispatch, keeping the width-1 golden replay as a hard regression gate,
  and running the full canonical test suite as part of this child's own Gate/DoD evidence.

- **False confidence from prompt text** — the exact failure mode this task exists to fix. Mitigation:
  require literal non-selftest CLI invocations and raw import-graph plus journal-count evidence, not
  AC-citation prose.

### Non-goals

No Audit/Reconcile/Land wiring (DIR-119-D3/D4/D5's own scope). No worktree-per-phase as the primary
isolation mechanism — this repo does not currently isolate `execute-milestone.js`'s Build phase in a
worktree, and introducing that here would be a much larger, orthogonal runtime change. No
product-package or Provider ABI changes.
