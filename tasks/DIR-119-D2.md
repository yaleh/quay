## Proposal

Make `execute-milestone.js`'s Build phase literally dispatch one agent per manifest phase,
respecting `requires` edges, instead of the current single monolithic agent call regardless of
manifest width. Second child of DIR-119-D's split (`split-multi-mechanism` finding). Depends on
DIR-119-D1's real, checked-in `composite-manifest-synthesis.ts` output shape for its real proof run.

### Problem framing (re-verified against current tree, 2026-07-29)

`.claude/workflows/execute-milestone.js` and its `plugin/workflows/` mirror are 508 lines and
byte-identical (`cmp` confirms). At any composite width, Build dispatches exactly one `agent()`
call — the only composite-aware content is an inline text block appended to that single prompt
(line ~246) instructing the one agent to itself treat shared phases as one owner, an honest
admission that the real per-phase dispatcher does not exist. `composite-build.ts` has zero
non-test importers anywhere in the tree (`grep`/import-graph check, run fresh this session) — its
`planPhaseExecution`/`mapEvidenceToTasks` exports are tested but never invoked by production code.

## Chosen mechanism

Add non-selftest JSON CLI modes to `composite-build.ts`: `--plan-json` (wraps the existing,
already-exported `planPhaseExecution`) and `--map-evidence-json` (wraps the existing,
already-exported `mapEvidenceToTasks`).

Planning gives each manifest phase a unique `build-phase-<id>` owner and chunks dependency-ready
levels into batches capped at `maxParallelAgents` simultaneous dispatches — the cap bounds
concurrent calls within a batch, never phase ownership or the `build-phase-*` label count.

A labeled `build-plan` helper agent invokes the plan CLI; batches then run serially, and within each
proven dependency-ready, proven-disjoint batch the workflow calls `parallel()` with exactly one
labeled `build-phase-<id>` agent per phase in that batch, each prompt scoped only to that phase's
task IDs, predecessors, invariant, allowed Touches, and evidence schema — phase workers never stage
or commit.

A final serial `build-integrate` helper validates the changed-file set is in-scope, integrates in
deterministic topological order, runs integration tests, creates the ONE candidate-generation
commit, and invokes `--map-evidence-json`.

Because this repo runs milestones directly in a shared working tree with no per-phase worktree
isolation on the default path (CLAUDE.md's own corrected note on `execute-milestone.js`'s Build
phase), phase batches that could theoretically run independent git-writing agents must instead
serialize at the one integration-commit step — a cap on `maxParallelAgents` bounds simultaneous
*inspection/build* work, never simultaneous *commits*. Unknown dependencies, cycles,
duplicate/missing evidence, out-of-scope files, unexpected commits mid-Build, or a generation
mismatch fail closed before mutation.

Legacy width-1 (`_taskIds.length === 1`, whether via legacy `{taskId,...}` or a composite-shaped
singleton) never touches this new dispatcher — the existing single-agent Build path is completely
untouched, additive not rewritten.

### Key design decisions

- **Overlap fuses into one phase owner; uncertainty fuses, never parallelizes.** Consumed from
  DIR-119-D1's synthesis output — a valid candidate with precise disjoint Touches must produce more
  than one phase for THIS child's real proof run, or the multi-phase AC item is unproven.

- **No concurrent commits in the shared working tree.** `maxParallelAgents` only bounds simultaneous
  inspection/build work, never simultaneous commits — `build-integrate` is the sole, serial
  commit-creating step.

- **Legacy path is a hard boundary, not a fallthrough.** Width 1 stays completely untouched, the
  compatibility oracle for DIR-119-D5's golden-replay test.

### Risks and mitigations

- **Control-plane regression on the one script every future milestone runs through** — mitigated by
  keeping the repo-root halt sentinel present for the duration of Build, never running this child
  concurrently with any other dispatch, keeping the width-1 golden replay as a hard regression gate,
  and running the full canonical test suite as part of this child's own Gate/DoD evidence.

- **False confidence from prompt text** — the exact failure mode this task exists to fix. Mitigation:
  require literal non-selftest CLI invocations and raw import-graph plus journal-count evidence, not
  AC-citation prose.

### Non-goals

No Audit/Reconcile/Land wiring (DIR-119-D3/D4/D5's own scope). No worktree-per-phase as the primary
isolation mechanism — this repo does not currently isolate `execute-milestone.js`'s Build phase in a
worktree, and introducing that here would be a much larger, orthogonal runtime change. No
product-package or Provider ABI changes.

1. Add `--plan-json`/`--map-evidence-json` non-selftest CLI modes to `composite-build.ts` (+
   `plugin/scripts/` mirror).
2. Change `execute-milestone.js`'s (both mirrors) composite Build path to dispatch `build-plan`,
   then per-batch `parallel()` of `build-phase-<id>` agents respecting `requires`, then
   `build-integrate`.

   real synthesized manifest) and confirm from the real `journal.jsonl`: `build-plan` dispatched

   creating exactly one commit.
4. Legacy single-task dispatch must remain behavior-identical: width-1 calls still dispatch exactly
   one Build agent, unchanged prompt shape.
