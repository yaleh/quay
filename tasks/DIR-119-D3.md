## Proposal

Make `execute-milestone.js`'s Audit phase literally dispatch one agent per manifest audit shard,
each mechanically checked read-only via a workflow-side (not agent-self-reported, not in-process
`deepFreeze`) `git status` diff, instead of the current single agent that both audits and writes
state. Third child of DIR-119-D's split. Depends on DIR-119-D1's manifest shape and DIR-119-D2's
Build phase (Audit only starts from a clean, integrated Build state). **The composite per-shard
mechanism has NO worktree-isolation handling in the current code** — the composite dispatch gate is
`_isComposite && $a.compositeManifestFile` (`.claude/workflows/execute-milestone.js` L739-740, both
mirrors byte-identical) with no `!_useWorktree` check, so a composite manifest dispatch that ALSO
requests `isolationMode:'worktree'` is NOT refused: it would audit the primary checkout where the
worktree build does not exist (wrong REFUTATION) and run the mechanical git-status write-violation
diff blind to writes made inside the worktree. Closing that gap with a fail-closed Audit gate is
required work for this milestone (see Chosen mechanism); it is NOT yet implemented.

### Problem framing (re-verified against current tree, 2026-07-29)

Audit currently dispatches exactly one `agent()` call regardless of composite width, and that
prompt instructs checklist write-back, absorb-disposition append, and deviation-log write-back —
mutations the target architecture assigns to Reconcile (DIR-119-D4's own scope). `composite-audit.ts`
is referenced from exactly one production file, `composite-reconcile.ts` — and that reference is
**type-only** (`import type { BundleAuditResult }`), erased at compile/strip time, so there is zero
runtime JS connection. `composite-audit.ts`'s existing `deepFreeze`/`structuredClone`-based
`runReadOnlyAuditShard()` binds only in-process JS object mutation and cannot constrain a dispatched
agent's real filesystem writes — proven insufficient by this task's own Finding, independently
reproduced this session.

## Chosen mechanism

Remove every composite checklist/absorb/deviation/dashboard/lifecycle/status write instruction from
the Audit agent prompt (composite mode only — legacy width-1 Audit is unchanged); that mutation
moves entirely to Reconcile (DIR-119-D4).

Add non-selftest snapshot/guard and `--combine-json` CLI modes to `composite-audit.ts` (the guard
mode wraps `git status --porcelain=v1 --untracked-files=all`; `--combine-json` wraps the existing,
already-exported `combineShardVerdicts`).

The workflow dispatches exactly one `audit-shard-<id>` agent per `manifest.auditShards[]` entry,
each scoped only to that shard's declared task IDs/AC indexes/invariant/integrated generation. Each
shard worker takes exact before/after snapshots around its own inspection window and returns the raw
snapshots plus a typed verdict — it does not self-certify cleanliness.

**Composite × worktree cross-product is currently UNGUARDED (open defect, DIR-123) — the fail-closed
guard is REQUIRED WORK, not implemented.** The per-shard dispatcher does NOT require the
non-isolated path today: the composite dispatch gate is still `_isComposite && $a.compositeManifestFile`
(no `!_useWorktree`), the string `composite-x-worktree-unsupported` appears NOWHERE in code
(proposal-only), and no fixture/GREEN test asserts the guard (composite-audit.test.mjs has no
worktree assertion). This milestone MUST add the fail-closed gate — `_isComposite &&
$a.compositeManifestFile && !_useWorktree` → `composite-x-worktree-unsupported` → needs-human BEFORE
any `audit-shard-<id>` dispatch — and assert it with a fixture/GREEN test. Rationale for the guard:
the mechanical enforcement surface cannot span the worktree boundary — `composite-audit.ts`'s
`takeGitSnapshot()` runs `git status` in `process.cwd()` (the primary checkout), while the build
being audited lives in the per-milestone worktree (unmerged until Land). Auditing the primary
checkout would therefore see none of the build (wrong REFUTATION), and the workflow-side git-status
diff would be blind to writes made inside the worktree. The shard prompt's lack of the legacy
`_auditIsolationNote` worktree note is an IMPLEMENTATION GAP (that note is interpolated only into the
legacy single-agent Audit prompt, L742), not the result of a guard making it dead text — it must be
added together with the guard, or the guard alone suffices to keep the cross-product unreachable.
Full composite×worktree support (worktree-relative snapshots `git -C <worktreeRel> status` /
`takeGitSnapshot(cwd)`, a shard-prompt worktree note, worktree-aware write-violation diffing) is
deferred and must be added as ONE unit before that guard is ever relaxed.

**The workflow itself — not the agent's self-report, and not `composite-audit.ts`'s existing
`deepFreeze`/`structuredClone`-based `runReadOnlyAuditShard()` — diffs the two snapshots**; any
non-empty delta, tracked or untracked, hard-fails that shard as `audit-shard-write-violation:<id>`
regardless of what the agent claims.

A distinct `audit-combine` helper agent invokes the real `combineShardVerdicts()` (not a
workflow-side reimplementation) to produce the generation-bound `BundleAuditResult`.

Snapshot transport remains within the platform's existing agent/tool trust boundary: this is
mechanical adjudication of returned command output, not cryptographic proof an agent process cannot
forge its own output, and that limitation is stated plainly rather than oversold.

### Key design decisions

- **Read-only enforcement is mechanical, not agent self-report or in-process isolation.** The
  workflow's own before/after `git status` diff is the only enforcement point that sees the agent's
  real filesystem effect.

- **State-owner ambiguity** if Build/Audit prompts retain any residual write-instruction language —
  mitigated by explicitly stripping composite write instructions from the Audit prompt and verified
  via a structural static grep (not merely a single run's clean tree), since a stale instruction
  merely unexercised by one proof dispatch would otherwise pass silently.

- **Composite and worktree isolation must be mutually exclusive (fail-closed), never half-supported.
  NOT YET TRUE IN CODE — REQUIRED.** The load-bearing read-only enforcement point — the workflow's
  before/after `git status` diff — is defined against the primary checkout (`process.cwd()`), while
  a DIR-123 worktree build lives in the per-milestone worktree. The composite×worktree cross-product
  is NOT currently refused at the dispatch gate (no `!_useWorktree` guard, no
  `composite-x-worktree-unsupported` anywhere in code); adding that guard so the cross-product fails
  closed rather than mis-auditing the wrong checkout or running a write-violation check blind to the
  worktree is required work.

### Risks and mitigations

- **False confidence from prompt text or in-process clone/freeze** — the exact failure mode this
  task exists to fix. RED/GREEN fixtures required for the hostile-write catch, GREEN-only evidence
  does not discharge this risk.

- **Snapshot forgery / concurrent unrelated writers** — mitigated by retaining full raw `git status`
  command output in the audit artifact and enforcing single-driver discipline; stated plainly as
  mechanical adjudication within the existing agent/tool trust boundary, not a cryptographic
  attestation.

- **Composite×worktree mis-audit (auditing the wrong checkout)** — a composite dispatch under
  `isolationMode:'worktree'` audits the primary checkout where the build does not exist (wrong
  REFUTATION) and the mechanical git-status write-violation check is blind to writes made inside the
  worktree. NOT MITIGATED TODAY — this is an open defect. Mitigation REQUIRED: a fail-closed dispatch
  gate (`_isComposite && $a.compositeManifestFile && !_useWorktree` →
  `composite-x-worktree-unsupported` needs-human) asserted by a fixture/GREEN test (currently absent
  from composite-audit.test.mjs), not merely documented.

### Non-goals

No Reconcile/Land wiring (DIR-119-D4/D5's own scope). No Gate-failure attribution fix (DIR-119-D4's
own scope — Gate identity feeds Reconcile, not Audit). No composite×worktree support in this
milestone: worktree-relative snapshots (`git -C <worktreeRel> status` / `takeGitSnapshot(cwd)`), a
shard-prompt worktree note, and worktree-aware write-violation diffing are deferred. The fail-closed
guard (`_isComposite && $a.compositeManifestFile && !_useWorktree` →
`composite-x-worktree-unsupported` → needs-human) is REQUIRED, not optional: the cross-product must
never half-run — the guard must be implemented and fixture/GREEN-asserted before any composite×
worktree dispatch is possible.
