**type:** execution

## Proposal

Make `execute-milestone.js`'s Land phase literally invoke `composite-land.ts`'s
`buildLandTransaction()` via a new `--land-json` CLI mode as a mechanical transaction validator --
and, because this is the final child in DIR-119-D's ordered split, run the single real end-to-end
composite dispatch exercising the full five-mechanism pipeline (synthesis to Land) and obtain the
fresh independent wiring audit tracing all five composite-*.ts modules together. Fifth and final
child of DIR-119-D's split.

### Problem framing (verified against current tree, 2026-08-01)

**Confirmed by direct source read, not by trusting the existing task-body prose:**

`composite-land.ts`'s `buildLandTransaction()` and `legacySingletonLandShape()` are real, tested,
exported functions with **zero non-test production importers anywhere in the tree**. A grep across
all `.js`, `.ts`, and `.mjs` files (excluding `node_modules`, `.git/`, and `test/`) returns only:
(a) the single prose reference at `execute-milestone.js` line 872 (`"composite-land.ts's
atomic-Land invariant"` -- a comment string, not a real invocation), and (b) the definitions in
`composite-land.ts` and its `plugin/scripts/` mirror (byte-identical per `cmp`). The `--land-json`
CLI mode does not exist; the file's CLI entry only handles `--selftest` (line 141).

The Land phase in `execute-milestone.js` (both mirrors, byte-identical) dispatches one monolithic
agent per path (serial, concurrent-legacy, concurrent-worktree). The Reconcile phase
(DIR-119-D4 / M212) is already wired at lines 856-905: it dispatches the `reconcile-apply` agent,
captures `reconcileApply.result` (`{ok, reason?, mutations, bundleDisposition?}`) in memory from the
agent's structured return value (schema lines 893-896), and blocks Land on
`!reconcileApply?.applied || !reconcileApply?.result?.ok` (line 899). However, the composite Land
steps 3/4/7 still only say "VALIDATE ... do NOT re-write" via `_compositeLandNote` (lines
930-932) -- that validation is agent-judgment prose, not a mechanical `buildLandTransaction()`
invocation. There is no independent transaction-shape validation: a Land phase that succeeds despite
a reconcile-state anomaly (wrong counter delta, wrong task-completion count) would not be caught by
any mechanical check.

The `CompositeManifest.landPolicy` field (typed literal `"atomic"`) is already synthesized by
DIR-119-D1's `composite-manifest-synthesis.ts` (line 70, line 262: `landPolicy: "atomic"`) and
already validated by `checkCompositeContract()` in `composite-contracts.ts` (line 144: `if
(manifest.landPolicy !== "atomic")` produces a violation). But `buildLandTransaction()` does NOT
currently inspect `landPolicy` -- its signature is `(taskIds, reconcileResult)` and it only checks
`reconcileResult.ok` and set-equal membership completeness. A manifest with a non-`"atomic"`
`landPolicy` would pass through `buildLandTransaction()` silently. The `landPolicy` invariant is
enforced at synthesis and contract-check time, but not at Land-commit time -- a gap between the two
phases that this child closes.

The legacy single-task (width-1) path has no golden-replay oracle comparing against
`legacySingletonLandShape()`'s asserted `{counterDelta: 1, dashboardEntryCount: 1,
taskCompletionCount: 1}` shape.

**Dependency state:** DIR-119-D1 (manifest-synthesis) is `done`. DIR-119-D2 (phase-DAG Build),
DIR-119-D3 (per-shard read-only Audit), and DIR-119-D4 (Reconcile + Gate attribution) are `todo`
with committed builds and green tests; their real-dispatch AC items are unproven (by construction --
no end-to-end composite dispatch has run yet). This child is the integration point that runs that
first end-to-end dispatch and proves the full five-mechanism pipeline.

### Chosen mechanism

**New `--land-json` CLI mode on `composite-land.ts` (both mirrors, byte-identical).** The mechanism
has three layers:

**Layer 1 -- New exported function `validateLandPreconditions(taskIds, reconcileResult, manifest):`**
A thin wrapper that performs TWO pre-validation checks before delegating to the existing,
**unchanged** `buildLandTransaction()`:

a. **`landPolicy` enforcement (new, falsifiable -- [CLAIM-1]):** If `manifest.landPolicy !==
   "atomic"`, return `{ok: false, reason: "land-policy-not-atomic: <value>", counterDelta: 0,
   dashboardEntryCount: 0, taskCompletionCount: 0, taskMarks: []}` -- BEFORE any
   `buildLandTransaction()` call. This is the mechanical enforcement checkpoint that closes the
   synthesis-to-Land gap: `landPolicy` was checked at synthesis and contract-check time, but Land now
   independently re-verifies it at the commit boundary. **[CLAIM-1 maps to AC #5.]**

b. **Input shape validation [CLAIM-2]:** If `taskIds` is not a non-empty array or `reconcileResult`
   is not an object with `ok: boolean`, fail closed with a descriptive `reason` and all-zero counts.
   **[CLAIM-2 maps to AC #4 (fail-closed part).]**

After both checks pass, delegates to `buildLandTransaction(taskIds, reconcileResult)` and returns
its result unchanged. **[CLAIM-3: `validateLandPreconditions` delegates to `buildLandTransaction()`
unchanged -- its signature, internal logic, and return type receive ZERO edits. This is the real
production callsite that AC #1 demands.]**

`validateLandPreconditions()` does NOT access `bundleAudit`, `taskGates`, `milestoneGates`, or any
audit/gate result fields -- it is strictly a precondition check + delegation to the existing
`buildLandTransaction()`, which only checks `reconcileResult.ok` and membership completeness. Land
is a transaction-commit validator only, never a second policy engine.

**Layer 2 -- Non-selftest `--land-json` argv branch [CLAIM-4]:**
Added after the existing `--selftest` block (line 141). Accepts three flags:

- `--task-ids <json|file>`: inline JSON array (starts with `[`) parsed directly; otherwise a file
  path read via `fs.readFileSync`
- `--reconcile <json|file>`: inline JSON object (starts with `{`) parsed directly; otherwise a file
  path read via `fs.readFileSync`
- `--manifest <json|file>`: inline JSON object parsed directly; otherwise a file path read via
  `fs.readFileSync`. Additionally unwraps the `{manifest, context}` envelope that
  `composite-manifest-synthesis.ts` line 524 produces, extracting `.manifest` -- the same shape
  `composite-build.ts --plan-json` consumes

Prints the `LandTransaction` JSON (`{ok, reason?, counterDelta, dashboardEntryCount,
taskCompletionCount, taskMarks}`) to stdout. Exit code 0 on `ok:true`, exit code 1 on `ok:false`.
Fail-closed on JSON parse failure (stderr message + exit 1). **[CLAIM-4 maps to AC #1
(the production callsite).]**

**`buildLandTransaction()` / `legacySingletonLandShape()` / `selftest()` receive ZERO edits.** Land
is a transaction-commit validator only, never a second policy engine -- exactly one module
(Reconcile) decides "did this land," and Land rechecks/commits that one already-decided transaction.
The pure function stays pure; the `landPolicy` check lives in the wrapper where the manifest is
available. **Mechanism-claim [CLAIM-3a]: `buildLandTransaction()`'s signature `(taskIds,
reconcileResult)` is unchanged -- the `landPolicy` parameter never enters the pure function's
parameter list.**

**Layer 3 -- Production wiring in `execute-milestone.js` (both mirrors):**

For composite dispatches ONLY (`_isComposite && $a.compositeManifestFile` is present -- the same
guard the Reconcile phase already uses at lines 856-905), the serial Land path inserts a
`--land-json` pre-mutation validation step as the FIRST instruction in the Land agent's prompt,
BEFORE any Land-phase mutation (merge, CAPTURE, provenance writeback -- Reconcile's
counter/dashboard/status success-path writes already happened upstream in composite serial):

a. **Label [CLAIM-5]:** the serial Land agent dispatch gains the label
   `{ phase: 'Land', label: 'land-transaction' }` -- following the `split-or-commit-${tid}` /
   `reconcile-apply` label precedent, so it appears in `workflows/wf_*.json`'s `workflowProgress[]`
   as the terminal pipeline element. **[CLAIM-5 maps to AC #2 (pipeline ordering visible in
   `workflowProgress[]`).]**

b. **Validate-before-mutate instruction (composite) [CLAIM-6]:** the Land prompt instructs running
   the literal command `node --experimental-strip-types <path>/composite-land.ts --land-json
   --task-ids '<member JSON>' --reconcile '<serialized reconcileApply.result>' --manifest
   '<$a.compositeManifestFile>'` BEFORE any Land-phase mutation (merge, CAPTURE, provenance

   `reconcileApply.result` is serialized from in-memory -- the exact object the `reconcile-apply`

   never re-derives verdicts from disk state. **[CLAIM-6 maps to AC #1 (production callsite), AC

c. **On exit 0 with `ok:true` (composite serial -- write-ownership decision; resolves the

### Key design decisions

1. **Land is a transaction-commit validator only, never a second policy engine.** There is exactly
   one module (Reconcile) that decides "did this land." Land's `--land-json` check is a mechanical
   gate that either passes (the reconcile result is well-formed, membership-complete, and
   `landPolicy` is `"atomic"`) or fails closed with zero writes. It never re-derives verdicts, never
   runs audit logic, never decides a different outcome than Reconcile. `validateLandPreconditions()`
   takes `landPolicy` from the manifest but does NOT access `bundleAudit`, `taskGates`,
   `milestoneGates`, or any audit/gate result fields.

   **Write-ownership (composite serial):** `reconcile-apply` remains the SOLE success-path writer of
   EXACTLY ONE `milestone_counter` increment and EXACTLY ONE dashboard `## Log` absorb entry in
   composite serial (execute-milestone.js lines 925/942; the composite serial Land steps 3/4 already
   say "VALIDATE ... do NOT write again / do NOT increment again"). This Proposal does NOT alter
   Reconcile's serial-mode write scope. Land's `--land-json` gate ASSERTS (never re-applies)
   `counterDelta === 1` / `dashboardEntryCount === 1` / `taskCompletionCount === taskIds.length` and
   applies only its own Land-owned writes (merge/NO-OP, CAPTURE, provenance writeback). Width-1
   dispatches skip Reconcile and keep the legacy Land-owned `milestone_counter`++/dashboard writes.

2. **`landPolicy` is checked in `validateLandPreconditions()`, not in `buildLandTransaction()`.**
   The pure function `buildLandTransaction(taskIds, reconcileResult)` takes no manifest argument and
   stays focused on the reconcile-result-to-transaction mapping. The `landPolicy` check is a
   manifest-dependent precondition best located in the wrapper, where the manifest is available.
   This keeps the pure function testable without manifest fixtures (12+ existing test cases across
   `selftest()` and `composite-land.test.mjs`) and makes the precondition check's failure mode (exit
   nonzero, empty transaction on stdout) explicit at the production boundary.

3. **Reconcile result consumed from in-memory agent return, not re-read from disk.** The
   `--reconcile` flag receives the serialized `reconcileApply.result` -- the exact object the
   `reconcile-apply` agent returned. This avoids re-deriving the Reconcile result from disk state,
   which would re-open the "two deciders" anti-pattern. Land is strictly downstream of Reconcile's
   decision with zero filesystem intermediary. The only gap (agent return value falsified relative
   to actual disk writes) is the same trust-model limitation documented in DIR-119-D3's AC #5
   (`deepFreeze` blind to real filesystem writes) and is stated plainly rather than oversold.

4. **`--manifest` flag reads `landPolicy` from the synthesized manifest file (defense-in-depth).**
   The same `compositeManifestFile` already available as `$a.compositeManifestFile` from
   DIR-119-D1's synthesis step. The flag unwraps the `{manifest, context}` envelope that
   `composite-manifest-synthesis.ts` line 524 produces, extracting `.manifest` and reading
   `.landPolicy`. For the width-1 path, an inline golden manifest JSON `{"landPolicy":"atomic"}` is
   passed instead of a file path -- the same flag handles both paths via `--land-json`'s two-shape
   normalization. This is defense-in-depth: if a future code change silently drops the `"atomic"`
   literal from manifest synthesis, Land fails closed rather than defaulting to a non-atomic mode.

5. **Legacy path proven equivalent, not asserted.** Width-1 dispatches run through the SAME
   `--land-json` validate-before-mutate gate with inline golden singleton values -- the validated
   transaction is deep-equal to `legacySingletonLandShape()` on shared fields. The overhead is
   negligible (a single `node` process spawning `validateLandPreconditions` →
   `buildLandTransaction` with pre-computed inputs) and the proven equivalence is load-bearing
   evidence (AC #3). The three existing `plugin/test/execute-milestone-*.test.mjs` golden-replay
   files must pass unchanged.

6. **Fail-closed on every error path.** JSON parse failure, missing flags, `landPolicy` not
   `"atomic"`, `buildLandTransaction()` returning `ok:false`, exit code mismatch, callsite assertion
   failure -- every error path produces `needs-human` with zero counter/dashboard/status writes.
   There is no fallthrough to a default Land, no silent skip of the validation, and no partial
   application.

7. **`--land-json` is a pre-mutation gate, not a post-mutation audit.** It runs as the FIRST
   instruction in the Land agent's prompt, BEFORE any shared-checkout mutation (merge, CAPTURE,
   counter increment, dashboard write). This means a failed transaction validation leaves the tree
   exactly as Reconcile left it, with no cleanup needed and no need to roll back merge commits. The
   post-mutation split-or-commit check (`postLandSplitOrCommitCheck()`) runs only after a
   successful Land, not after a rejection.

8. **Concurrent Land paths stay untouched.** Both worktree-mode concurrent Land (which defers merge
   to the fan-in) and legacy concurrent Land defer counter/dashboard to the serial fan-in
   (`OUTER-LOOP.md` step g) and perform zero mutation themselves -- wiring `--land-json` there is
   wasted work and introduces a second callsite to maintain without adding protection. The serial
   Land path is the path composite dispatches actually use under single-driver discipline.

### Defaults and failure behavior

- **`--land-json` exit 1 or `ok:false`:** ZERO counter/dashboard/status writes; Land early-returns
  `{outcome:'needs-human', reason:'land-transaction-rejected:<reason>', phase:'Land'}` before any
  post-mutation split-or-commit check (a rejected Land performed zero mutations -- there is no new
  state to scan).
- **Missing/bad flags to `--land-json`:** stderr message, exit 1 -- fail-closed. The agent observes
  exit 1 and follows the `needs-human` path with zero writes.
- **JSON parse failure for any flag:** stderr message, exit 1 -- fail-closed, same as above.
- **Manifest `landPolicy` not `"atomic"`:** `validateLandPreconditions` returns `{ok: false,
  reason: "land-policy-not-atomic: <value>", counterDelta: 0, dashboardEntryCount: 0,
  taskCompletionCount: 0, taskMarks: []}` -- fail-closed, no mutation. This is the ONLY code path
  that enforces `landPolicy === "atomic"` at Land time -- `buildLandTransaction()` does not have
  this check, and the synthesis-time/contract-check-time validations are the earlier gates. A
  deliberately non-atomic manifest fixture must produce `needs-human` with zero writes (AC #5).
- **Reconcile `ok:false`:** The existing `buildLandTransaction` returns `{ok: false,
  reason: "reconcile-not-ok", ...}` with all-zero counts -- no mutation, same fail-closed path.
- **Reconcile mutation-set mismatch:** The existing `buildLandTransaction`'s lines 49-53
  defense-in-depth membership re-verification catches a reconcile with `ok:true` but incomplete
  mutations -- same all-zero failure path.
- **Callsite assertion failure:** `txn.counterDelta !== 1` or `txn.dashboardEntryCount !== 1` or
  `txn.taskCompletionCount !== taskIds.length` -- return `needs-human` with zero writes, even though
  `buildLandTransaction()` guarantees these values. This is defense-in-depth at the production
  boundary.
- **Legacy width-1 with inline golden singleton:** if the golden singleton itself fails validation
  (structurally impossible given the hardcoded `ok:true` / `landPolicy:"atomic"` values, but
  fail-closed regardless), same all-zero failure path.
- **Manifest file unreadable/missing:** `fs.readFileSync` throws → process exits nonzero, fail-closed
  -- same `needs-human` path.

### Compatibility

- **Legacy single-task path:** byte-for-behavior unchanged. The Land prompt's steps 1-8 retain their
  existing mutation instructions; the new `--land-json` step is prepended as a validate-before-mutate
  gate, and with the inline golden singleton it produces the exact `legacySingletonLandShape()`
  output -- the proven equivalence, not a prose claim. The three existing
  `plugin/test/execute-milestone-*.test.mjs` golden-replay files must pass.
- **Composite dispatch path:** previously had prose-only validation via `_compositeLandNote`
  ("VALIDATE the post-image"); now has mechanical `--land-json` validation before any Land-phase
  mutation (Reconcile's success-path writes -- counter, dashboard, status -- already happened; Land's
  own writes follow the validated gate and do NOT duplicate them). This is strictly additive -- a
  dispatch that would have passed before still passes, and a dispatch with a latent
  reconcile/membership mismatch that would have slipped through prose-only validation now fails
  closed at the mechanical gate.
- **Concurrent Land paths (worktree-isolated + legacy concurrent):** untouched -- defer to fan-in,
  outside the touch set.
- **No Provider ABI or product-package changes.** This touches only the workflow script,

- **`--selftest` mode:** unchanged -- the existing `--selftest` argv branch (line 141) fires BEFORE
  the new `--land-json` branch, so `--selftest` behavior is byte-identical. The two modes are

  validation and exits.
- **`buildLandTransaction()` pure function signature:** unchanged -- zero behavioral delta for
  existing test callers.

### Risks and mitigations

- **Control-plane regression on the one script every future milestone runs through.** The
  `--land-json` step is an ADDITIVE pre-mutation gate on the serial Land path only -- it adds one
  `node` invocation before the existing Land agent dispatch, does not alter the agent's own
  non-validation steps, and does not change the concurrent paths. Mitigation: the repo-root `.halt`
  sentinel stays present; this child never runs concurrently with any other dispatch; the full
  canonical test suite (`scripts/test.sh`) runs as part of this child's own Gate/DoD evidence; the
  legacy path's byte-identity golden replay is a hard regression gate.

- **Integration risk from DIR-119-D1 through D4 defects surfacing at Land time.** This child is the
  first time all five mechanisms run together. If any prior child has a latent defect not caught by
  its own child-scoped audit, it surfaces here as an end-to-end failure. Mitigation: this child's
  own real dispatch is the integration proof, not a replacement for each prior child's own audit; if
  the end-to-end run surfaces a defect traceable to an earlier child, file it as a new gap task
  against that child rather than silently patching it here (per the non-goal below). The fresh
  independent audit is explicitly scoped to trace the FULL chain, not just this child's
  Land-specific addition.

- **Reconcile-result drift between `reconcile-apply`'s execution and `--land-json`'s consumption.**
  The `reconcileApply.result` object is captured from the Reconcile agent's structured return value
  (the schema-enforced `.result` field, lines 893-896), not re-read from a file the agent might have
  modified. Since `reconcile-apply` returns `{applied, result}` and the workflow stores
  `reconcileApply.result` in memory, `--land-json` consumes the exact same object that Reconcile
  produced -- no file-system race. The only gap is if the agent's return value is falsified relative
  to what it actually wrote to disk; this is the same trust-model limitation documented in
  DIR-119-D3's AC #5 (`deepFreeze` blind to real filesystem writes) and is stated plainly rather
  than oversold.

- **Journaled `.result` field stripping by agent-schema validation.** If `landTransaction` /
  `taskIds` are not declared in the serial Land agent's schema, agent-schema validation may strip
  them from the journaled `.result`, making Stage 5's AC reads structurally unsatisfiable.
  Mitigation: the Return-line/schema extension (design decision #4 / CLAIM-9) explicitly declares
  every field Stage 5 reads -- this is a mechanical precondition, not an optional nice-to-have.

- **Manifest file read failure at Land time.** If `$a.compositeManifestFile` is missing or
  unparseable at Land time, the `--land-json` invocation fails with exit 1 -- fail-closed, zero
  writes. Mitigation: the manifest file is already validated by `composite-preflight.ts` at Verify
  time and read by `composite-build.ts --plan-json` at Build time; a missing manifest at Land time
  would indicate a catastrophic earlier-phase failure that should NOT be silently worked around.

- **Mirror drift between the two `execute-milestone.js` copies.** The `.claude/workflows/` and
  `plugin/workflows/` mirrors must stay byte-identical. Mitigation: after every edit, `cmp` both
  mirrors; the final Gate's `it0-mirror-identity-check.sh` enforces this mechanically.

### Non-goals

No re-litigating DIR-119-D1 through D4's own already-audited scope -- this child assumes their
independent audits already passed; if the end-to-end run surfaces a defect traceable to an earlier
child, file it as a new gap task against that child rather than silently patching it here. No repeat
of the width-7 canary -- 2-3 real tasks is sufficient for the integration proof. No product-package
or Provider ABI changes. No partial Land under any circumstance (rejected by the existing
`landPolicy: "atomic"` invariant). No change to `buildLandTransaction()`'s pure-function signature
-- the `landPolicy` check is in `validateLandPreconditions()`, not in the function. No wiring of
`--land-json` into the concurrent Land paths (deferred to fan-in, zero mutation at that point). No
re-derivation of audit or gate verdicts in Land -- Land is strictly downstream of Reconcile.

### Alternatives considered and rejected

**A: Add `landPolicy` parameter to `buildLandTransaction()` instead of the wrapper.** Rejected
because `buildLandTransaction()`'s current signature `(taskIds, reconcileResult)` is clean, tested,
and has a well-defined contract -- the `landPolicy` check is a deployment-context precondition (what
manifest was this dispatch given?), not a function-level invariant. Adding it to the pure function
would require every test fixture (12+ across `selftest()` and `composite-land.test.mjs`) to thread a
manifest through, and it would couple the pure function to the manifest schema.
`validateLandPreconditions()` is the natural boundary for manifest-dependent checks.

**B: Invoke `--land-json` AFTER the Land agent dispatch as a post-mutation audit.** Rejected
because a post-mutation audit that discovers a transaction violation has already mutated the shared
checkout (merge, CAPTURE, counter increment) -- rolling back is complex, error-prone, and
potentially impossible for merge commits already on `master`. A pre-mutation gate catches the
violation BEFORE any mutation, so the tree stays clean on failure.

**C: Have the Land agent itself invoke `--land-json` rather than the workflow DSL embedding it in
the prompt.** Rejected because (a) it delegates the fail-closed decision to the same agent that
would otherwise proceed with Land, creating a self-review conflict of interest, and (b) the workflow
DSL's immediate `needs-human` return on `ok:false` is a hard control-flow boundary the agent cannot
override. The workflow owns the decision; the agent only executes steps after the workflow has
already decided to proceed.

**D: Skip `--land-json` and keep Land as prose-only validation.** Rejected: this is the exact gap
DIR-119-D exists to close. The `_compositeLandNote` prose instruction ("VALIDATE the post-image") is
the same class of non-mechanical guidance that failed across DIR-119-C's audit. A mechanical
`buildLandTransaction()` call with a real exit code is the minimum bar.

**E: Have `validateLandPreconditions` re-derive audit/gate verdicts.** Rejected: violates the
single-policy-engine principle (Reconcile is the sole decider). Land rechecks the one
already-decided transaction; it does not re-run audit logic or gate checks.
`validateLandPreconditions` is a thin wrapper -- `landPolicy` check then delegate to the existing
`buildLandTransaction`, which already enforces membership completeness and reconcile-not-ok.

**F: Have `--land-json` re-derive the Reconcile result from disk state instead of consuming the
in-memory `reconcileApply.result`.** Rejected because re-deriving from disk state would re-open the
exact "two deciders" anti-pattern this design exists to prevent -- Land would be a second policy
engine re-interpreting post-Reconcile state, not a mechanical validator of a single already-decided
transaction. Consuming the in-memory result keeps Land strictly downstream of Reconcile's decision.

**G: Wire the concurrent Land paths too.** Rejected: concurrent Land (worktree-isolated and
legacy-concurrent) defers counter/dashboard to the serial fan-in, which is the SOLE merge owner.
Wiring `--land-json` there would produce a transaction validation at a point where no mutation
occurs -- wasted work, and it introduces a second callsite to maintain without adding protection.
The serial Land path is the path composite dispatches actually use (single-driver discipline).

**H: Require >= 2 build phases for the real composite dispatch.** Rejected by the grounded fact:
`composite-manifest-synthesis.ts` fuses overlapping-touch tasks into a single `phase-<A+B>`
component via union-find, so a 2-3 task composite whose tasks share a touch legally yields exactly
one `build-phase-*` label. Requiring >= 2 would exit non-zero on a healthy fully-wired run. The
`build-phase-*` floor is >= 1, and the `build-plan`/`build-integrate` slot presence plus the `. ==
sort` ordering clause already prove the phase-DAG path.

**I: Skip `--land-json` entirely for the width-1 case.** Rejected: running the legacy singleton
through the SAME validate-before-mutate gate proves byte-for-shape equivalence mechanically (AC #3)
rather than asserting it in prose. The overhead is negligible (a single `node` process spawning
`buildLandTransaction` with pre-computed inputs) and the proven equivalence is load-bearing
evidence.
