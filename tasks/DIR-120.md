### Problem framing (re-verified against current source, 2026-07-28)

Reading `packages/quay/src/gate/config/loader.ts`'s `readGatesConfig()` and
`packages/quay/src/loop-params.ts`'s `readLoopParams()` directly (not from memory) shows both
functions collapse **two structurally different scenarios into one `if (parsed === undefined)`
branch**:

- **(A) a governing `.quay/config.yml` exists at `workspaceRoot` but has no `gates:`/`loop:`
  key** — this is DIR-050's half-finished migration crutch. Root `.quay/config.yml` has always
  carried both sections (confirmed by reading it), so branch (A) is unreachable for the root
  workspace *today* — but the code path is live, and the two files' own `it0` gate script paths
  have **already silently diverged once** (DIR-120's own Finding #3): deleting the files without
  deleting this branch reproduces exactly the `[[gap-halt-sentinel-path-mismatch]]` failure shape
  ("looks authoritative, isn't wired, backed by stale docs") this whole directive exists to kill.
- **(B) no `.quay/config.yml` exists at `workspaceRoot` at all** — confirmed live and real:
  `ls experiments/quay-perpetual-stream/.quay/` shows **only** `loop.yml`, no `config.yml`. This
  is not a hypothetical; it is exp5's actual, current, day-to-day configuration shape, and it is
  the *only* branch a from-scratch config.yml-less directory can hit.

Cross-referencing real test fixtures resolves which branch each existing test actually depends
on (verified by reading the files, not assumed):
- `packages/quay/test/dod-gate-set.test.mjs`'s `tmpWorkspace()` writes **only** `.quay/gates.yml`,
  no `config.yml` — pure branch (B).
- `packages/quay/test/gate-ergonomics.test.mjs`'s `makeWorkspace()` writes a `.quay/config.yml`
  with a `providers:` section but **no `gates:` key**, then separately writes a sibling
  `.quay/gates.yml` for its per-test fixtures — pure branch (A).
- `packages/quay/test/loop-params.test.mjs` has explicit GREEN cases for both: `"...legacy
  loop.yml fallback when config.yml has no loop: section"` (branch A) and `"...legacy loop.yml
  fallback when no config.yml at all"` (branch B).

This means the two branches are independently real, independently tested, and independently
consumed — deleting them requires two different decisions, not one.

Three further hazards, cross-checked directly against the tree:

1. **`drivable-workspace-check.ts`'s `DEFAULT_REGISTRY_PATH` is a second, independently-discovered
   dangling reference of the exact `it0-set`/`vitest` shape** DIR-120's own Finding #1 already
   caught once. `export const DEFAULT_REGISTRY_PATH = path.join(__dirname, "..",
   "drivable-workspaces.yml")` resolves, from the script's real location (`plugin/scripts/`), to
   `plugin/drivable-workspaces.yml` — confirmed **not to exist** (`ls` errors ENOENT). The real,
   human-authorized registry lives at `experiments/quay-perpetual-stream/drivable-workspaces.yml`
   (confirmed present, 2657 bytes). Cross-referencing `milestones/M137/iterations/iteration-0.md`
   (which copied this script from `experiments/.../scripts/` into `plugin/scripts/` under
   DIR-070-B) against the unchanged `__dirname`-relative arithmetic shows the offset was correct
   when the script lived one directory shallower and went stale silently the moment it was copied
   one level deeper — the textbook "offset-coupled path breaks on relocation" bug. It has never
   caused a false pass: no task in this repo's history sets `drivableWorkspaceArgs` (`grep -rn
   drivableWorkspaceArgs tasks/` is empty), so the `it0` gate factory short-circuits on "no
   drivable-workspace arguments defined" before `loadRegistry(DEFAULT_REGISTRY_PATH)` is ever
   called — confirmed independently against `.quay/gate-events.jsonl`'s real firings, all of which
   fail on that exact message, never reaching registry load.
2. **`drivable-workspace-check.ts` (and its `.sh` wrapper) is a real, byte-identical, hand-
   maintained duplicate** between `plugin/scripts/` and `experiments/quay-perpetual-stream/

   `DEFAULT_REGISTRY_PATH`), so this is live, load-bearing duplication, not dead weight — the
   exact "two copies, one drifts" shape Finding #3 already found once for the gates-config

3. **The M192 charter's own `## Touches` list keeps `experiments/quay-perpetual-stream/
   drivable-workspaces.yml` at its current path** (not a new root-level path) — this is direct,

### Chosen mechanism

**Phase 2 — delete root legacy files + the branch-(A) fallback only, not branch (B):**

- Delete `.quay/gates.yml` and `.quay/loop.yml` at repo root.
- In `readGatesConfig()`: when a governing `.quay/config.yml` exists at `workspaceRoot` (whether
  or not it parses, whether or not it has a `gates:` key), **never** fall through to a sibling
  `.quay/gates.yml` — return the existing fail-quiet empty `GatesConfig` shape immediately. The
  branch-(B) "no config.yml at all → read `.quay/gates.yml` if present" path is **unchanged**.
- In `readLoopParams()`: when a governing `.quay/config.yml` exists at `workspaceRoot` but has no
  `loop:` key (or fails to parse), throw `FAIL-CLOSED: <path> has a config.yml but no loop:
  section — legacy sibling .quay/loop.yml is no longer consulted (DIR-120)` instead of falling
  through to a sibling `.quay/loop.yml`. This is strictly *more* fail-closed than today (today a
  config.yml-adjacent legacy file silently rescues; after this change it does not). The
  branch-(B) "no config.yml at all → read `.quay/loop.yml` if present" path is **preserved**,
  hardened by Phase 3a below — it is the one real mechanism exp5's config.yml-less `.quay/`
  directory needs to keep working, not legacy back-compat cruft to sweep away.
- Migrate `packages/quay/test/gate-ergonomics.test.mjs`'s `makeWorkspace()` fixtures: move each
  test's per-test gate definitions from a standalone sibling `.quay/gates.yml` write into that
  same test's `config.yml`'s own `gates:` section (real content move — diff old vs. new fixture
  field-for-field, including `cwd`/`timeoutMs`, so no coverage is silently thinned). Flip
  `loop-params.test.mjs`'s `"...legacy loop.yml fallback when config.yml has no loop: section"`
  GREEN case to a RED/FAIL-CLOSED assertion. Leave `dod-gate-set.test.mjs`'s branch-(B) fixtures
  and `loop-params.test.mjs`'s `"...legacy loop.yml fallback when no config.yml at all"` GREEN
  case **unmodified** — verify this asymmetry empirically (run both files) rather than assume it.
- Post-deletion proof (charter's explicit Done-when #2): (a) a real `quay gate` invocation against
  a real task in this repo, showing a real `GateEvent` resolves purely from `.quay/config.yml`;
  (b) a real, direct `readLoopParams(repoRoot)` call (or the equivalent already-real
  `config-wiring-check.ts --driver both`, which calls it internally against `REPO_ROOT`) showing
  valid params are still produced purely from `.quay/config.yml`.
- Verification of "no remaining read path," scoped precisely: `grep -n
  "existsSync(legacyGatesPath)\|existsSync(legacyLoopPath)"
  packages/quay/src/gate/config/loader.ts packages/quay/src/loop-params.ts` must show each
  check now reachable **only** inside the "no config.yml at all" branch, never when a config.yml
  exists — a targeted structural assertion, not a blind substring-absence grep. **Flagged
  explicitly as an interpretation the Plan/reviewer must sign off on** (see Risks): a literal,
  context-free reading of the AC's Chinese wording ("代码里不再存在读取这两个路径的分支") could be
  read as requiring branch (B)'s deletion too. That larger reading is evaluated and rejected below
  under Alternatives, but is surfaced here rather than silently resolved, per DIR-120's own
  "prose gets paraphrased away, prefer hard checks" principle — the hard check to run before
  landing is: does the Plan/reviewer accept the branch-A/branch-B split as satisfying the AC's
  intent (no config.yml-governed workspace can ever silently drift to a stale sibling file), or
  does it require the stricter, larger reading?

**Phase 3a — exp5 profile-fragment schema, mechanically enforced, via the existing reader:**

- Harden branch (B) of `readLoopParams()` in place — do **not** add a new, separately-named
  reader function. A profile fragment is read by exactly the same code path that already reads a
  config.yml-less directory's `.quay/loop.yml`, so hardening that path in place is the reading of
  DIR-120's own Phase-3 text ("exp5 保留自己的 loop 配置文件... 由 reader 机械强制") most directly
  supported by the current code shape, and avoids maintaining two parallel field-validation rule
  sets for what both authors' own drafts recognize is one contract shape (a fragment and a
  unified `loop:` section validate identically field-by-field; only the top-level key-set
  differs).
- Add, inside branch (B) only: if the parsed YAML object carries a `providers:` key at all, throw
  `FAIL-CLOSED: <path> is a loop-only profile fragment — providers: is not allowed here; it may
  only live in a workspace's own .quay/config.yml`. `providers:` has no legitimate meaning in a
  loop-only fragment (a second provider map is precisely the drift DIR-050/Finding #6 exists to
  prevent), so this is an unconditional key-presence ban, not a type check.
- The `gates:`-as-full-gate-definitions-object case (an object with `it0`/`adr`/`fixed`/`testPass`
  keys smuggled in under `gates:`, instead of the required string/array of gate *names*) is
  **already** rejected by `readLoopParams`'s existing Step-5 type check (confirmed by reading the
  source: `gates` must be `Array.isArray` or a non-empty string, else `FAIL-CLOSED: ... field
  'gates' must be a string or non-empty array`) — no new code needed, just a new, explicit test
  asserting this specific claim, since the check was never previously framed as "the `gates:`
  object-shape prohibition." (The directive's "禁止出现 providers:/gates:" text, read literally,
  would ban the *required* `gates` field outright, which is incoherent — a fragment without
  `gates:` can't declare which gate set to run. The RED-fixture example the charter/task actually
  specifies names only `providers:`, supporting this narrower, coherent reading.)
- RED/GREEN demonstration reuses the existing, already-real CLI surface rather than inventing a
  new flag or script: `plugin/scripts/config-wiring-check.ts` already accepts `--workspace <path>`
  and already calls `readLoopParams(workspaceRoot)` internally, printing `ERROR: cannot read loop
  params for <path>: <message>` and exiting 2 on throw. Since exp5's directory has no
  `config.yml`, `config-wiring-check.ts --workspace experiments/quay-perpetual-stream` already
  exercises branch (B) against the real file with zero new code.
  - RED fixture: a temp directory containing only a `.quay/loop.yml` with a `providers:` key
    added → `--workspace <tmp>` exits 2 with the named FAIL-CLOSED reason.
  - GREEN fixture: **exp5's own real, unmodified `.quay/loop.yml`** → `--workspace
    experiments/quay-perpetual-stream` succeeds (exit 0 from the loop-params read step; whatever
    the per-field driver-consumption report says afterward is orthogonal to this claim). Using the
    real file is both cheaper and stronger evidence than a synthetic GREEN: it proves the new
    restriction requires zero changes to exp5's actual configuration.
  - A small `experiments/quay-perpetual-stream/scripts/loop-profile-fragment-selfcheck.sh`
    wrapping both invocations (mirroring this repo's existing `<name>-selfcheck.sh` convention)
    gives a single, repeatable, named artifact for this evidence rather than ad hoc commands.

**Phase 3b — `drivable-workspaces.yml` layering fix, file stays where it is:**

- **Do not move the file.** Per the charter's own Touches list (which names the file at its
  current experiments-relative path, not a new root path) and DIR-120's own item-6 reasoning, the
  registry stays an independent file at `experiments/quay-perpetual-stream/drivable-
  workspaces.yml` — a methodology-layer artifact governing the *autonomous loop's* cross-workspace
  privilege, not a generic product concept.
- Remove `DEFAULT_REGISTRY_PATH`'s wrong, silently-present guess entirely rather than repointing
  it at another hardcoded guess (which would only relocate the same layering violation to a new
  constant). `--registry <path>` becomes **required**; a missing `--registry` is a usage error
  (exit 2), the same failure class as today's already-passing "no drivable-workspace arguments
  defined" gate outcome, not a new failure mode. This workspace's convention (documented in the
  script's own header) becomes: any `it0` gate entry wiring this script must supply `--registry
  ./experiments/quay-perpetual-stream/drivable-workspaces.yml` via its `argsKey`.
- Update the script's own `--selftest`, which currently does a conditional `if
  (fs.existsSync(DEFAULT_REGISTRY_PATH))` self-check, to instead point at the real registry path
  directly now that the constant is gone.
- **Convert `experiments/quay-perpetual-stream/scripts/drivable-workspace-check.ts` (and its
  `.sh` wrapper) into a real symlink to the `plugin/scripts/` original**, matching the precedent
  Phase 0 already established for `config-wiring-check.ts`. The two copies are today a real,
  live, hand-maintained duplication (imported by two other real TS files as a library), so
  re-copying after this fix merely delays the next drift; a symlink is the only durable fix.
  **This specific action is not on the M192 charter's own `## Touches` list today** (which names
  only the `.yml` file, not the check-script pair) — flagged explicitly in Risks for the Plan
  phase to either add it or explain why the duplication is being knowingly deferred.

### Concrete control/data flow (post-change)

```
readGatesConfig(workspaceRoot):
  if config.yml exists at workspaceRoot:
      gates := config.yml's own `gates:` key, or {} if absent   [branch A — no fallback, ever]
  else:
      gates := gates.yml at workspaceRoot, or {} if absent      [branch B — unchanged]

readLoopParams(workspaceRoot):
  if config.yml exists at workspaceRoot:
      if config.yml has `loop:` → validate+return it            [branch A-success]
      else → throw FAIL-CLOSED (no more sibling-file rescue)     [branch A-fail — NEW]
  else:
      if loop.yml exists at workspaceRoot:
          parsed := loop.yml
          if "providers" in parsed → throw FAIL-CLOSED           [Phase 3a — NEW]
          validate+return parsed (gates: object-shape already throws via existing Step 5)
      else → throw FAIL-CLOSED (unchanged: no config anywhere)
```

- `quay gate <task>` → `loadWorkspaceGates(workspaceRoot)` → `readGatesConfig(workspaceRoot)` →
  root workspace always has a config.yml, so this always hits branch A → reads `.quay/config.yml`
  `gates:` only, never touches `.quay/gates.yml` again for this repo.
- Any caller of `readLoopParams(repoRoot)` (product CLI, `plugin/skills/loop-driver/SKILL.md`,
  `config-wiring-check.ts --driver both`) → root always has config.yml → branch A → reads
  `.quay/config.yml` `loop:` only, never `.quay/loop.yml` again for this repo.
- exp5's own routines evaluation (`plugin/skills/routines/SKILL.md` / `run-routines.js`) →
  `experiments/quay-perpetual-stream/` has no `config.yml` → branch B, unchanged except for the
  new `providers:` ban — exp5's real file has no `providers:` key today, so this is a no-op for
  live behavior.
- `config-wiring-check.ts --workspace experiments/quay-perpetual-stream` → the same branch-B path
  as above, now doubling as the Phase-3a RED/GREEN demonstration surface with zero new code.
- `quay gate --gate drivable-workspace` (when a task ever supplies `drivableWorkspaceArgs`
  including `--registry`) → `drivable-workspace-check.sh` → `.ts` → `loadRegistry(<explicit
  --registry path>)` → resolves to the real, unmoved `experiments/quay-perpetual-stream/
  drivable-workspaces.yml`, identically whether invoked via the `plugin/scripts/` original or the
  (now-symlinked) experiments-side copy.

### Key design decisions

1. **Split the fallback-deletion scope into branch (A) and branch (B), delete only (A).** A
   config.yml that has adopted the unified format is held to being complete (no silent sibling
   rescue); a config.yml-less directory keeps the one mechanism it has always had, now hardened
   rather than removed. This is chosen over blanket deletion because branch (B) is independently,
   currently, verifiably exercised by exp5's real `.quay/` directory and by `dod-gate-set.test.mjs`
   / half of `loop-params.test.mjs`'s GREEN suite — deleting it is a materially larger, ~15-test
   -touching, currently-out-of-Touches-list change for no functional gain the AC actually asks
   for (see Alternatives).
2. **Harden the existing branch-(B) reader in place rather than introducing a new, separately-
   named `readLoopProfileFragment` function.** A fragment and a unified config's `loop:` section
   validate identically field-by-field; the only difference is the top-level key-set, which a
   3-line key-presence check inside the existing branch handles without duplicating the
   `board`/`gates`/`stop`/`policy`/`execution`/`audit`/`concurrency`/`routines` validation logic
   in a second place.
3. **`readGatesConfig` and `readLoopParams` are treated symmetrically** (same branch-A/branch-B
   split) even though their failure philosophies differ (`readGatesConfig` is fail-*quiet* by
   original design; `readLoopParams` is fail-*closed*) — this keeps the mental model, and the
   code review, to one shape instead of two bespoke ones.
4. **`drivable-workspaces.yml` stays put; the reader stops guessing instead of guessing
   differently.** A hardcoded `<script-dir>/../drivable-workspaces.yml` default is inherently
   layering-inverted for a generic `plugin/scripts/` script reused by an experiments-layer
   caller; the only default that is not itself another latent landmine is no default at all,
   forcing every caller to say explicitly where its registry lives. Relocating the file (the
   alternative both drafts considered) would only move the landmine, not defuse it, and
   contradicts the charter's own already-committed Touches path for the file.
5. **Symlink, don't re-copy, `drivable-workspace-check.ts`/`.sh`.** The two copies are real, live,
   hand-maintained duplication (two other TS files import the experiments-side copy as a
   library); Phase 0 already proved the symlink pattern works for exactly this situation
   (`config-wiring-check.ts`).

### Defaults and failure behavior

- `readGatesConfig`: config.yml present (with or without a `gates:` key) → that section or `{}`,
  never an error, never a fallback read. Config.yml absent → unchanged branch-B behavior
  (`.quay/gates.yml` or `{}`).
- `readLoopParams`: config.yml present but missing `loop:` → `FAIL-CLOSED`, no substitution (was:
  silent fallback). Config.yml absent → unchanged branch-B behavior, now additionally FAIL-CLOSED
  if the parsed fragment carries a `providers:` key.
- `drivable-workspace-check.ts`'s registry resolution: no `--registry` supplied → usage error,
  exit 2 — same fail-closed class as today's "no drivable-workspace arguments defined," never a
  silent pass.
- No new fail-open branch is introduced anywhere, per DIR-120's own item-7 invariant.

### Compatibility

- Root workspace: zero behavior change for any currently-passing path (config.yml already carries
  both sections; branch A's success path is untouched).
- Exp5: `experiments/quay-perpetual-stream/.quay/loop.yml` keeps validating exactly as today
  (branch B unchanged) unless it is edited to add a `providers:` key, which it does not have
  today — the real file is expected to pass the new GREEN fixture check unmodified.
- Test suite: `loop-params.test.mjs` needs exactly the one branch-A GREEN case flipped to RED,
  plus new RED/GREEN cases for the `providers:` ban and an explicit assertion of the pre-existing
  `gates:`-object-shape claim. `gate-ergonomics.test.mjs` needs its per-test gate fixtures
  migrated from a standalone `gates.yml` write into the same test's `config.yml`'s own `gates:`
  section (real content move, field-for-field, not a coverage deletion). `dod-gate-set.test.mjs`
  is unaffected (pure branch B) — verify this empirically, not by assumption.
- `config-wiring-check.ts`'s `checkGeneralReader` (scans `readLoopParams`'s `return {...}` shape)
  is unaffected — the returned field set does not change.
- Two real sibling workspaces already on the unified format (`meta-cc`, `archguard`, both
  verified in DIR-120's own Finding #1) are unaffected — neither relies on a bare legacy file
  with no accompanying `.quay/config.yml`'s matching section... and if either ever did, that is
  exactly branch A, which this Proposal explicitly closes; no other real external consumer of
  branch A is known to exist.
- `provider.yml` / `plugin/.claude-plugin/plugin.json`: untouched, per DIR-120's own explicit
  out-of-scope carve-out. `select-preflight.ts`'s `checkHalt()` fail-closed fix: already landed
  in Phase 1 (M186); out of scope here.

### Risks

- **Touches-list gap (flag for Plan-check).** The M192 charter's `## Touches` list does not name
  `packages/quay/test/loop-params.test.mjs`, `packages/quay/test/gate-ergonomics.test.mjs`, nor
  `plugin/scripts/drivable-workspace-check.ts`/`.sh` and its experiments-side mirror — all of
  which this mechanism requires editing. Recommend the Plan phase either amend the charter's
  Touches list explicitly or obtain an explicit ruling that test/companion-script edits colocated
  with an already-Touched source module don't require separate enumeration.
- **Branch-A/branch-B scoping is an interpretive choice, not a mechanically-forced one** (Key
  design decision #1). If the Plan author or a reviewer reads the AC's grep-based wording more
  literally and wants branch (B) deleted too, that is a materially larger (~15-test-touching)
  milestone and should be surfaced as an explicit scope question before implementation starts,
  not silently absorbed either way.
- **Undiscovered third consumer of branch (A).** Mitigate with a repo-wide grep for
  `readLoopParams(`/`readGatesConfig(`/`loadWorkspaceGates(` call sites, plus a grep for
  `gates.yml`/`loop.yml` string references in docs/skills (stale prose pointing at a soon-to-be
  narrower contract is a lower-severity instance of the same failure mode), before landing.
- **`gate-ergonomics.test.mjs` migration could silently thin coverage** if the migrated `gates:`
  section doesn't reproduce every field (`cwd`, `timeoutMs`) the original sibling-file fixtures
  exercised — mitigate by diffing old vs. new fixture content field-for-field, not just
  re-running green.
- **The `drivable-workspace` gate fix cannot be proven "working in production" by this milestone**
  — no task in this repo currently supplies `drivableWorkspaceArgs`, so the gate is not exercised
  end-to-end via a real `quay gate` call with real target paths today (confirmed against
  `.quay/gate-events.jsonl`'s real firing history), and this milestone does not change that. Must
  not be overclaimed as "now live" in the DoD evidence.
- **`plugin/test/plugin-packaging.test.mjs`'s `sync-vendor.sh --check` dynamic scan** (currently
  asserting a fixed count of identical-by-symlink entries) does not currently manage
  `drivable-workspace-check.ts`/`.sh` at all; converting them to a symlink should be transparent
  (a real symlink needs no separate sync check) but must be verified empirically against that
  test's exact assertion during implementation, not assumed.
