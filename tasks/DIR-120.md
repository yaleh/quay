## Proposal

directly against the current tree — `packages/quay/src/gate/config/loader.ts`,
`packages/quay/src/loop-params.ts`, root `.quay/{gates,loop,config}.yml`,

This document covers Phase 2/3 of DIR-120 (the M192 charter's scope) — Phase 0/1 already landed at
M186/commit `949f3c7`.

**One factual conflict between the two drafts was adjudicated by re-reading the live file

### Problem framing (verified directly against source)

`readGatesConfig()` (`loader.ts:67-101`) and `readLoopParams()` (`loop-params.ts:46-84`) each
collapse two structurally different situations into a single "no unified value found" fallback
that silently reads a sibling legacy file:

- **Branch A** — a governing `.quay/config.yml` exists at `workspaceRoot` (parses or not, has the
  relevant top-level key or not) but the reader still falls through to `.quay/gates.yml` /
  `.quay/loop.yml` beside it. For the repo root this is unreachable *today* only by accident:
  `.quay/config.yml` (6748 bytes) happens to always carry both `gates:` and `loop:` and always
  parses, but the sibling legacy files are still on disk (`.quay/gates.yml` 8410 bytes,
  `.quay/loop.yml` 295 bytes) and have already silently drifted from the canonical section — root
  `loop.yml` says `gates: [vitest]`, canonical `config.yml` says `gates: [acceptance]`. `vitest`
  matches no gate factory in `packages/quay/src/gate/registry.ts` and no dependency of this repo;
  it is a copy-paste leftover from `archguard`'s own `.quay/config.yml` (which genuinely runs
  `vitest`), never adapted for this project.
- **Branch B** — no `.quay/config.yml` exists at `workspaceRoot` at all. Not hypothetical:
  `experiments/quay-perpetual-stream/.quay/` contains only `loop.yml`, no `config.yml` — exp5's
  real, live shape, and exp5 is not an independent workspace (it shares root `tasks/` and the root
  provider map — no separate provider config lives under
  `experiments/quay-perpetual-stream/`), so it structurally cannot simply "graduate" to its own
  `config.yml`; it depends on this branch staying alive and correct.

A parse-failure asymmetry between the two readers already exists, independent of this milestone:
`readGatesConfig` swallows a malformed `config.yml` in `try/catch` and falls through to branch
A/B; `readLoopParams` throws `FAIL-CLOSED` immediately on the same input and never reaches its
fallback for a parse failure — only for a well-formed `config.yml` missing `loop:`. So for
`readLoopParams`, "exists but malformed" is *already* fail-closed and needs no change; the new
behavior this milestone adds is narrower — "exists, parses, but has no `loop:` key." The two
readers therefore need closing on a different number of sub-conditions (`readGatesConfig` on two:
missing key AND malformed YAML; `readLoopParams` on one: missing key only) — a distinction any
deletion plan must preserve, not paper over with a single uniform rule.

Reading (not pattern-matching) every test that exercises these paths:
- `dod-gate-set.test.mjs`'s `tmpWorkspace()` writes only `.quay/gates.yml` — pure branch B.
- `gate-ergonomics.test.mjs`'s `makeWorkspace()` builds a `config.yml` with only `providers:`
  (branch-A shaped), but it is used only by the file's three `--cwd`-flag tests, which never touch
  `gates.yml`. The three `gates.yml`-writing tests each build their **own** bare
  `fs.mkdtempSync` workspace and never write `config.yml` — confirmed by reading each test's own
  setup, not by trusting the helper's name. **No existing test constructs "`config.yml` with no
  `gates:` key + sibling `gates.yml`"** (confirmed via `grep -rl readGatesConfig
  packages/quay/test/`, zero hits — no test imports the function directly) — closing branch A in
  `readGatesConfig` needs exactly one new, purpose-built test, not a migration of these three.
- `loop-params.test.mjs` has one real branch-A GREEN case (`"...fallback when config.yml has no
  loop: section"`, a real `config.yml`-with-only-`providers:` + sibling `loop.yml` fixture) that
  must flip to RED, and one real branch-B GREEN case (`"...fallback when no config.yml at all"`)
  that must stay GREEN.

Two further hazards, confirmed by direct inspection, sharpen the mechanism beyond a naive "delete
the fallback" reading:

1. **`drivable-workspace-check.ts`'s `DEFAULT_REGISTRY_PATH`** (`path.join(__dirname, "..",
   "drivable-workspaces.yml")`, line 34) resolves, from `plugin/scripts/`, to
   `plugin/drivable-workspaces.yml` — confirmed ENOENT. The real registry is
   `experiments/quay-perpetual-stream/drivable-workspaces.yml` (confirmed present). `.quay/config.yml`'s
   own `gates.it0` list already registers a real `name: drivable-workspace` entry (`argsKey:
   drivableWorkspaceArgs`, lines 45-47) — a wired gate whose failure mode this fix changes, not
   dead configuration. No task currently sets `drivableWorkspaceArgs` (`grep -rn
   drivableWorkspaceArgs tasks/` matches only prose in `tasks/DIR-120.md` itself), so the gate
   factory's own per-task short-circuit is what currently prevents `loadRegistry(DEFAULT_REGISTRY_PATH)`
   from ever firing — not absent wiring. A future task that sets the field without an explicit
   `--registry` would fail closed for the *wrong* reason.
2. **`drivable-workspace-check.ts`/`.sh` is a real, byte-identical, hand-maintained duplicate**
   between `plugin/scripts/` and `experiments/quay-perpetual-stream/scripts/` (confirmed via
   `diff` — empty output on both files) — unlike `config-wiring-check.ts`, which Phase 0/M186
   already converted to a real symlink
   (`experiments/.../scripts/config-wiring-check.ts -> ../../../plugin/scripts/config-wiring-check.ts`,
   reconfirmed present). This duplication is load-bearing, not inert: `select-preflight.ts` and
   `human-steered-classify.ts` both
   `import { loadRegistry, DEFAULT_REGISTRY_PATH } from "./drivable-workspace-check.ts"` — the
   experiments-side copy, as a library.

**A concrete regression this milestone must account for, independently confirmed here (not named
in the other draft):** `experiments/quay-perpetual-stream/test/drivable-workspace-check.test.mjs`
— 26 tests, all currently green (`node --test` run directly: `26 pass / 0 fail`) — is **not
covered by `scripts/test.sh`'s glob** (`packages/*/test/*.test.mjs plugin/test/*.test.mjs` does
not match `experiments/quay-perpetual-stream/test/`, confirmed by reading `scripts/test.sh` line
37). This file both imports `DEFAULT_REGISTRY_PATH` directly (`"loadRegistry: real checked-in
registry parses with the real authorized_root"` calls `loadRegistry(DEFAULT_REGISTRY_PATH)`) and
runs 5 CLI subprocess tests with **no `--registry` flag at all** (`--selftest`, the two
coverage/uncovered path checks, the multi-path check, the no-args usage-error check), relying on
`DEFAULT_REGISTRY_PATH` resolving correctly. It resolves correctly **today only because this
specific copy's own `__dirname` sits one directory below the real registry file**
(`experiments/quay-perpetual-stream/scripts/` → `../drivable-workspaces.yml`) — the layering
inversion in miniature: the "default" is only ever right for the experiments-side copy, never for
the product-level one. Node resolves `import.meta.url` through a symlink to the **real file's**
location (confirmed by the existing code comment in `config-wiring-check.ts` lines 46-48,
independently corroborating this behavior). So once this file becomes a symlink to
`plugin/scripts/drivable-workspace-check.ts`, its own `__dirname` becomes `plugin/scripts/` and
`DEFAULT_REGISTRY_PATH` breaks for **every** caller, including this test file, independent of
whether the default is also explicitly removed. This means: **the symlink conversion and the
`DEFAULT_REGISTRY_PATH` removal are not independently optional — they must land together, and this
out-of-glob test file must be updated in the same change**, or a `scripts/test.sh` run reports
green while this file is provably broken if invoked directly (exactly the "looks handled, isn't"
failure shape this directive exists to close).

### Chosen mechanism

**Phase 2 — delete root legacy files + the branch-A fallback only, never branch B:**
- Delete `.quay/gates.yml` and `.quay/loop.yml` at repo root. `execution: dispatched` /
  `audit: adversarial` are already present in `.quay/config.yml`'s own `loop:` section (Phase
  1/M186, confirmed at lines 99-100 today) — no separate migration step is needed before this
  deletion; that was verified directly against the live file during adjudication of this
  proposal.
- `readGatesConfig()`: once `.quay/config.yml` exists at `workspaceRoot` — parses or not, has
  `gates:` or not — return the config-derived value or the empty `GatesConfig` shape immediately;
  never fall through to `.quay/gates.yml`. Branch B is unchanged.
- `readLoopParams()`: once `.quay/config.yml` exists but has no `loop:` key, throw `FAIL-CLOSED:
  <path> has a config.yml but no loop: section — legacy sibling .quay/loop.yml is no longer
  consulted (DIR-120)` instead of falling through. The malformed-YAML case is already fail-closed
  and needs no code change. Branch B is preserved, hardened by Phase 3a.
- Add exactly one new branch-A test for `readGatesConfig` (the one input shape — `config.yml` with
  no `gates:` + sibling `gates.yml` — no existing test constructs); flip `loop-params.test.mjs`'s
  branch-A GREEN case to RED. Leave `dod-gate-set.test.mjs` and `gate-ergonomics.test.mjs`'s three
  `gates.yml` tests unmodified — verified by re-running them, not by classification alone.
- Post-deletion proof (charter Done-when #2): a real `quay gate` call against a real task
  producing a real `GateEvent`, plus a real `readLoopParams(repoRoot)` call (directly, or via
  `config-wiring-check.ts --driver both`), both resolving purely from `.quay/config.yml`.
- Structural grep proof that `existsSync(legacyGatesPath)`/`existsSync(legacyLoopPath)` are
  reachable **only** inside the "no `config.yml`" branch — a check on where the guard sits, not a
  substring-absence grep (both strings will still exist in source, correctly, since branch B still
  needs them).
- Flagged for explicit sign-off, not silently resolved: branch-A-only deletion is a materially
  narrower reading of "delete the fallback branches" than deleting both A and B. See Risks /
  Alternatives.

**Phase 3a — exp5 profile-fragment schema, enforced inside the existing branch-B reader:**
- Harden branch B of `readLoopParams` in place rather than adding a second, separately-named
  reader — a fragment and a unified `loop:` section validate identically field-by-field; only the
  top-level key set differs.
- Inside branch B only: if the parsed object carries a `providers:` key at all, throw
  `FAIL-CLOSED: <path> is a loop-only profile fragment — providers: is not allowed here; it may
  only live in a workspace's own .quay/config.yml`. exp5 sharing root `tasks/`/the root provider
  map means a second `providers:` section for it is precisely the drift DIR-050 exists to prevent.
- The "`gates:` as a smuggled full gate-definitions object" shape is **already** rejected by the
  existing `gates` type check (`must be Array.isArray or a non-empty string`) — no new code, but a
  new explicit test naming this specific invariant (today true only incidentally).
- RED/GREEN reuses `config-wiring-check.ts --workspace <path>` (confirmed to accept the flag and
  call `readLoopParams(workspaceRoot)` internally, printing the thrown message and exiting
  non-zero) rather than a new flag: RED = a temp dir with a `providers:`-carrying `loop.yml` fails
  with the named reason; GREEN = exp5's own real, unmodified `.quay/loop.yml` (confirmed no
  `providers:` key today) succeeds against `--workspace experiments/quay-perpetual-stream` — a
  stronger proof than a synthetic GREEN since it needs zero config changes.

**Phase 3b — `drivable-workspaces.yml` layering fix, file stays where it is:**
- Do not move the file — the charter's own Touches list names its current path, matching
  DIR-120's own reasoning for an independent, separately-audited registry file (the
  `/etc/sudoers` analogy already in the task body).
- Remove `DEFAULT_REGISTRY_PATH`'s wrong default entirely (not repoint it — that only relocates
  the same layering violation and reproduces the exact offset-coupling fragility that caused the
  original bug; a future relocation would silently break it again). `--registry <path>` becomes
  required; a missing `--registry` is a usage error (exit 2) — the same failure class as today's
  already-passing "no drivable-workspace arguments defined" short-circuit. Update `--selftest`'s
  own `fs.existsSync(DEFAULT_REGISTRY_PATH)` check to point at the real path directly, so the
  "real registry" self-test cases run unconditionally instead of silently skipping.
- Convert `experiments/quay-perpetual-stream/scripts/drivable-workspace-check.ts` (and `.sh`) into
  real symlinks to the `plugin/scripts/` originals, matching Phase 0's `config-wiring-check.ts`
  precedent. Not on the charter's own `## Touches` list (which names only the `.yml` file) —
  flagged in Risks for explicit sign-off, since skipping it would leave the exact
  hand-maintained-duplicate drift risk this milestone is otherwise closing.
- **Load-bearing requirement surfaced by this proposal's own independent verification pass**:
  update `experiments/quay-perpetual-stream/test/drivable-workspace-check.test.mjs` in the *same*
  change — replace its `loadRegistry(DEFAULT_REGISTRY_PATH)` unit test and its five no-`--registry`
  CLI subprocess tests with versions that pass an explicit `--registry <real-path>` (or a
  fixture), and re-run this file directly (`node --test
  experiments/quay-perpetual-stream/test/drivable-workspace-check.test.mjs`) with pasted real
  output, since `scripts/test.sh` will not catch a regression here. The symlink conversion and the
  `DEFAULT_REGISTRY_PATH` removal must land atomically with this test update — landing either
  change alone breaks this file via a different mechanism (stale relative default vs.
  symlink-resolved `__dirname`).

### Concrete control/data flow (post-change)

```
readGatesConfig(workspaceRoot):
  if config.yml exists at workspaceRoot:
      gates := config.yml's `gates:` key (parses & has key), or {} otherwise   [branch A — no
                                                                                 fallback, ever,
                                                                                 incl. malformed YAML]
  else:
      gates := gates.yml at workspaceRoot, or {} if absent                    [branch B — unchanged]

readLoopParams(workspaceRoot):
  if config.yml exists at workspaceRoot:
      if malformed YAML → throw FAIL-CLOSED                    [branch A — pre-existing, unchanged]
      if has `loop:` → validate+return it                      [branch A success]
      else → throw FAIL-CLOSED                                 [branch A fail — NEW, was: fall through]
  else:
      if loop.yml exists at workspaceRoot:
          parsed := loop.yml
          if "providers" in parsed → throw FAIL-CLOSED          [Phase 3a — NEW]
          validate+return parsed  (gates:-object-shape already throws)
      else → throw FAIL-CLOSED                                 [unchanged]

drivable-workspace-check.ts (post Phase 3b):
  --registry omitted → usage error, exit 2                      [NEW — was: silent DEFAULT_REGISTRY_PATH guess]
  --registry <path> supplied → loadRegistry(<path>) → isCovered/checkPaths as today
  __dirname now always resolves through the symlink to plugin/scripts/ (Node resolves
  import.meta.url via realpath) — independently verified, matching config-wiring-check.ts's own
  existing comment (lines 46-48) about this exact behavior.
```

4. `config-wiring-check.ts --workspace experiments/quay-perpetual-stream` doubles as the Phase-3a

5. `quay gate --gate drivable-workspace` (only exercised if a task sets `drivableWorkspaceArgs`,

   Touches/AC list names it.

### Key design decisions

1. **Split fallback deletion into branch A (delete) and branch B (harden, keep).** Branch B is
   currently exercised by exp5's real `.quay/` directory and ~20+ tests across
   `dod-gate-set.test.mjs` and `loop-params.test.mjs`; deleting it is a substantially larger,
   not-currently-scoped change for no gain the charter's Done-when items ask for.
2. **Harden the existing branch-B reader in place, not a parallel `readLoopProfileFragment()`.**
   One validation rule set plus a 3-line key-presence check, versus duplicating the whole rule
   set.
3. **Both readers keep the same branch-A/B structural split despite differing failure
   philosophies** (`readGatesConfig` fails quiet by design — an absent gate config is a valid "no
   gates" state; `readLoopParams` fails closed — no valid loop config means the workspace cannot
   run) and differing pre-existing parse-error handling — the structural shape is unified, the
   philosophies and existing behaviors inside it are not silently changed into one uniform rule.
4. **`drivable-workspaces.yml` stays put; the reader stops guessing instead of guessing
   differently.** A hardcoded `<script-dir>/../` default is inherently layering-inverted for a
   `plugin/scripts/`-housed script with an experiments-layer caller at a different relative depth;
   requiring an explicit `--registry` removes the guess.
5. **Symlink, not re-copy, `drivable-workspace-check.ts`/`.sh`**, following the Phase-0
   `config-wiring-check.ts` precedent — the two files are today real, hand-maintained,
   byte-identical duplicates imported as a library by two other real files.
6. **The symlink conversion and the `DEFAULT_REGISTRY_PATH` removal must land in the same change,
   with the out-of-glob experiments-side test file updated in lockstep.** Landing either alone
   breaks the other's assumptions (see Problem framing's independently-verified symlink-resolution
   finding). This ordering constraint is this proposal's own addition beyond a generic "convert to
   symlink" description, and is not optional.
7. **No separate config.yml migration step for `execution`/`audit` before Phase 2.** Verified
   directly against the live file: Phase 1/M186 already landed both fields into
   `.quay/config.yml`'s `loop:` section. Treating this as an outstanding prerequisite (as one
   input draft did) would have added an unnecessary, already-completed step to the plan.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present (parses or not, `gates:` or not) → that section or `{}`,
  never an error, never a fallback read. `config.yml` absent → unchanged branch-B behavior.
- `readLoopParams`: `config.yml` present, parses, missing `loop:` → `FAIL-CLOSED` (the one
  genuinely new failure mode). `config.yml` present but malformed → `FAIL-CLOSED`, pre-existing,
  unchanged. `config.yml` absent → unchanged branch-B behavior, now additionally `FAIL-CLOSED` on
  a `providers:` key.
- `drivable-workspace-check.ts` registry resolution: no `--registry` → usage error, exit 2, same
  failure class as today's "no drivable-workspace arguments defined" short-circuit — never a
  silent pass.
- No new fail-open branch anywhere; every new failure mode is fail-closed.

### Compatibility

- Root workspace: zero behavior change for any currently-passing path — `config.yml` already
  carries both sections and always parses, and already carries `execution`/`audit` (Phase
  1/M186, confirmed at lines 99-100), so no additional migration precedes the deletion. The
  deleted files are, by construction, never read for this workspace today.
- exp5: its real `.quay/loop.yml` (no `providers:` key today) keeps validating exactly as today
  unless later edited to add one.
- `gate-ergonomics.test.mjs` / `dod-gate-set.test.mjs`: no changes — pure branch B, confirmed by
  reading each test's own setup — verified by running them, not assumed.
- `select-preflight.ts` / `human-steered-classify.ts` and their existing tests: must stay green
  through the symlink indirection.
- `experiments/quay-perpetual-stream/test/drivable-workspace-check.test.mjs`: **not** compatible
  as-is — must be edited in this milestone (see Key design decision #6) and re-run directly since
  `scripts/test.sh` does not cover it.
- `packages/*/provider.yml` and `plugin/.claude-plugin/plugin.json`: untouched, per DIR-120's
  explicit carve-out.
- `config-wiring-check.ts`'s `checkGeneralReader` (scans `readLoopParams`'s return shape):
  unaffected — the returned field set does not change.

### Risks

- **Touches-list gap.** The M192 charter's own `## Touches` list (confirmed by direct read) names
  neither `packages/quay/test/loop-params.test.mjs`, the new `readGatesConfig` test,
  `plugin/scripts/drivable-workspace-check.ts`/`.sh` and its experiments mirror, **nor**
  `experiments/quay-perpetual-stream/test/drivable-workspace-check.test.mjs` — all of which this
  mechanism edits. Needs explicit sign-off (amend Touches, or confirm test/companion-script edits
  colocated with an already-Touched module don't require separate enumeration).
- **Branch-A/branch-B scoping is interpretive, not mechanically forced** — a literal reading of
  "delete the fallback branch" could require branch B's deletion too, a materially larger change.
  Must be surfaced before implementation, not silently resolved.
- **Undiscovered third consumer of branch A** — mitigate with a repo-wide grep for
  `readLoopParams(`/`readGatesConfig(`/`loadWorkspaceGates(` call sites and for
  `gates.yml`/`loop.yml` string references in docs/skills before landing.
- **Symlink/default-removal ordering hazard (this proposal's own independently-verified
  finding).** Landing the symlink conversion without updating
  `experiments/.../test/drivable-workspace-check.test.mjs` breaks 6 currently-green tests silently
  with respect to `scripts/test.sh` (which never runs that file); landing the
  `DEFAULT_REGISTRY_PATH` removal without the symlink conversion breaks the same tests via a
  different code path. Both changes and the test-file update must land together, and the file must
  be run directly as evidence.
- **The `drivable-workspace` it0 gate is real, registered infrastructure** (`gates.it0` names it,
  `argsKey: drivableWorkspaceArgs`) — this milestone changes the failure mode of a wired gate, not
  a hypothetical. Since no task sets `drivableWorkspaceArgs` (confirmed by grep), AC coverage here
  is necessarily the usage-error proof plus a manual explicit-`--registry` invocation, not an
  end-to-end real-task-triggered proof — must not be overclaimed as "now live in a real gate
  firing"; needs either a real invocation against a task configured with this gate, or an explicit
  sign-off that this registered-but-never-fed entry stays unexercised end-to-end.
- **`plugin/test/plugin-packaging.test.mjs`'s exp5-label-leak test** names
  `plugin/scripts/drivable-workspace-check.ts`/`.sh` as shipped files that must not leak the
  `experiments/quay-perpetual-stream` path — the symlink conversion only touches the
  experiments-side copy, leaving the plugin-side file (and this test) unaffected, but must be
  verified empirically post-change, not assumed.
