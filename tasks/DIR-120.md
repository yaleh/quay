### Problem framing (re-verified directly against source, 2026-07-28)

Reading `packages/quay/src/gate/config/loader.ts`'s `readGatesConfig()` (lines 67-101) and
`packages/quay/src/loop-params.ts`'s `readLoopParams()` (lines 46-84) directly shows both
functions collapse **two structurally different scenarios into one `parsed === undefined`
fallback branch**:

- **Branch A** — a governing `.quay/config.yml` exists at `workspaceRoot`, but either it fails to
  parse, or it parses but has no `gates:`/`loop:` key. Both readers then silently read a sibling
  legacy file (`.quay/gates.yml` / `.quay/loop.yml`) instead. Root `.quay/config.yml` (confirmed:
  6748 bytes, `ls .quay/`) has always carried both sections, so branch A is unreachable for the
  root workspace *today* — but the code path is live, not dead: root `.quay/gates.yml` (confirmed
  8410 bytes) and root `.quay/loop.yml` (confirmed 295 bytes) both still exist on disk, and the
  gates file's own top-of-file comment already documents itself as dead-for-this-workspace
  back-compat weight (`gap-orphaned-check-scripts-not-wired`, M-DIR119-C-CANARY). Comparing the
  legacy root `.quay/loop.yml` against `.quay/config.yml`'s own `loop:` section shows they have
  already, silently, diverged: `gates: [vitest]` in the legacy file vs. `gates: [acceptance]` in
  the canonical section (`vitest` is not this project's dependency and appears nowhere in
  `packages/quay/src/gate/registry.ts` — dead, copy-pasted-from-elsewhere content, harmless only
  because branch A never fires here). This is the exact `[[gap-halt-sentinel-path-mismatch]]`
  failure shape ("looks authoritative, isn't wired, backed by stale docs") this directive exists
  to close.
- **Branch B** — no `.quay/config.yml` exists at `workspaceRoot` at all. Not hypothetical:
  `ls experiments/quay-perpetual-stream/.quay/` shows only `loop.yml`, no `config.yml` — exp5's
  real, current, day-to-day shape, and the only branch a from-scratch config.yml-less directory
  can hit.

**A parse-failure asymmetry between the two readers already exists today, independent of this
change** (verified by reading both functions): `readGatesConfig` swallows a malformed
`config.yml` in a `try/catch` and falls through to branch A/B (loader.ts:77-81); `readLoopParams`
throws immediately, `FAIL-CLOSED: .quay/config.yml is malformed YAML — ...`, on the same input
(loop-params.ts:55-61) — it never reaches the fallback branch for a parse failure at all, only for
a well-formed `config.yml` that lacks a `loop:` key. This matters for scoping the mechanism
precisely: for `readLoopParams`, "config.yml exists but fails to parse" is **already** fail-closed
and needs no code change; the new behavior is narrower than a first reading suggests — it applies
only to "config.yml exists, parses, but has no `loop:` key." For `readGatesConfig`, by contrast,
"config.yml exists but fails to parse" **currently** falls through to the sibling file and *does*
need to stop doing so — this is a genuine, if narrow, additional piece of branch-A closure beyond
the "no `gates:` key" case.

### Chosen mechanism

**Phase 2 — delete root legacy files + the branch-A fallback only, never branch B:**

- Delete `.quay/gates.yml` and `.quay/loop.yml` at repo root.
- In `readGatesConfig()`: once a `.quay/config.yml` exists at `workspaceRoot` — whether or not it
  parses, whether or not it has a `gates:` key — return the config-derived value, or the existing
  empty `GatesConfig` shape (`{it0:[],adr:[],fixed:[],testPass:[],coverageFloor:[],redGreen:[]}`),
  immediately; **never** fall through to a sibling `.quay/gates.yml`. This closes both the
  "no `gates:` key" case and the "malformed `config.yml`" case (the latter previously fell
  through silently; see the parse-asymmetry note above). Branch B ("no `config.yml` at all → read
  `.quay/gates.yml` if present") is unchanged.
- In `readLoopParams()`: once a `.quay/config.yml` exists at `workspaceRoot` but has no `loop:`
  key, throw `FAIL-CLOSED: <path> has a config.yml but no loop: section — legacy sibling
  .quay/loop.yml is no longer consulted (DIR-120)` instead of falling through to a sibling
  `.quay/loop.yml`. (The "malformed `config.yml`" case is **already** fail-closed today and needs
  no change — see parse-asymmetry note; do not re-claim it as new behavior.) Branch B ("no
  `config.yml` at all → read `.quay/loop.yml` if present") is preserved, hardened further by
  Phase 3a below.
- Add exactly **one** new, purpose-built test for `readGatesConfig`'s branch-A closure: a temp
  workspace with a `config.yml` (no `gates:` key) plus a sibling `.quay/gates.yml` must now yield
  the empty gate set, ignoring the sibling — this is the one input shape no existing test
  constructs (see Problem framing). Flip `loop-params.test.mjs`'s `"...legacy loop.yml fallback
  when config.yml has no loop: section"` GREEN case (line 197) to a RED/FAIL-CLOSED assertion.
  Leave `dod-gate-set.test.mjs`, all three of `gate-ergonomics.test.mjs`'s `gates.yml`-writing
  tests, and `loop-params.test.mjs`'s `"...legacy loop.yml fallback when no config.yml at all"`
  GREEN case (line 208) **unmodified** — verify this empirically by re-running all three files,
  not by assuming the branch classification holds.
- Post-deletion proof (charter Done-when #2): (a) a real `quay gate` invocation against a real
  task, producing a real `GateEvent` resolved purely from `.quay/config.yml`; (b) a real
  `readLoopParams(repoRoot)` call (directly, or via the already-real `config-wiring-check.ts
  --driver both`, which calls it internally against `REPO_ROOT`) producing valid params purely
  from `.quay/config.yml`.
- Verification that no read path remains, scoped precisely: `grep -n
  "existsSync(legacyGatesPath)\|existsSync(legacyLoopPath)" packages/quay/src/gate/config/loader.ts
  packages/quay/src/loop-params.ts` must show each check reachable **only** inside the "no
  `config.yml` at all" branch, never when a `config.yml` exists — a structural check on where the
  guard sits, not a blind substring-absence grep (both strings will still exist in the source;
  that is expected and correct).
- **Flagged as an interpretive choice requiring explicit sign-off, not silently resolved**: the
  branch-A/branch-B split (delete only A) is a materially narrower reading of "delete the fallback
  branches" than a literal reading of the AC's wording that would require branch B's deletion too.
  See Risks and Alternative #2.

**Phase 3a — exp5 profile-fragment schema, enforced inside the existing branch-B reader:**

- Harden branch B of `readLoopParams` in place rather than adding a new, separately-named reader
  (e.g. `readLoopProfileFragment`). A fragment and a unified `loop:` section validate identically
  field-by-field; only the top-level key-set differs, so a fragment-specific key-presence check
  belongs inside the one reader, not duplicated in a second one — this avoids maintaining two
  parallel `board`/`gates`/`stop`/`policy`/`execution`/`audit`/`concurrency`/`routines` validation
  rule sets for one contract shape.
- Inside branch B only: if the parsed object carries a `providers:` key at all, throw
  `FAIL-CLOSED: <path> is a loop-only profile fragment — providers: is not allowed here; it may
  only live in a workspace's own .quay/config.yml`. Unconditional key-presence ban — `providers:`
  has no legitimate meaning in a loop-only fragment (a second provider map for exp5, which is not
  an independent workspace and shares root `tasks/`/the root provider map, is precisely the drift
  DIR-050 exists to prevent).
- The "`gates:` as a smuggled full gate-definitions object" shape (an object with
  `it0`/`adr`/`fixed`/`testPass` keys under `gates:`, instead of a gate-name string/array) is
  **already** rejected today by `readLoopParams`'s existing type check (confirmed by reading the
  source: `gates` must be `Array.isArray` or a non-empty string, else `FAIL-CLOSED: ... field
  'gates' must be a string or non-empty array`) — no new code is needed for this case, only a new,
  explicit test naming this specific invariant, since today it is true only incidentally, never
  asserted as *this* claim. (Reading the directive's "禁止出现 providers:/gates:" text literally
  would ban the *required* `gates` field outright, which is incoherent — a fragment without
  `gates:` can't declare which gate set to run. The RED-fixture example the charter/task actually
  specifies names only `providers:`, supporting this narrower, coherent reading.)
- RED/GREEN evidence reuses the existing CLI surface (`plugin/scripts/config-wiring-check.ts
  --workspace <path>`, confirmed to accept that flag and to call `readLoopParams(workspaceRoot)`
  internally, printing a clear error and exiting 2 on throw) rather than inventing a new flag:
  since exp5's directory has no `config.yml`, `--workspace experiments/quay-perpetual-stream`
  already exercises branch B against the real file with zero new code.
  - RED: a temp directory with only a `.quay/loop.yml` carrying an added `providers:` key →
    `--workspace <tmp>` fails with the named FAIL-CLOSED reason.
  - GREEN: exp5's own real, unmodified `.quay/loop.yml` (confirmed to have no `providers:` key
    today by direct read) → `--workspace experiments/quay-perpetual-stream` succeeds. Using the
    real file is stronger evidence than a synthetic GREEN — it proves the new restriction requires
    zero changes to exp5's actual configuration.

**Phase 3b — `drivable-workspaces.yml` layering fix, file stays where it is:**

- **Do not move the file.** The charter's own `## Touches` list names it at its current path
  (`experiments/quay-perpetual-stream/drivable-workspaces.yml`), consistent with DIR-120's own
  reasoning for keeping a human-authorized-registry file independent of `.quay/config.yml`
  (independent review surface/blast radius, the `/etc/sudoers` analogy already in the task body).
- Remove `DEFAULT_REGISTRY_PATH`'s wrong default entirely (not repoint it at another hardcoded
  guess, which would only relocate the same layering violation). `--registry <path>` becomes
  **required**; a missing `--registry` is a usage error (exit 2) — the same failure class as
  today's already-passing "no drivable-workspace arguments defined" short-circuit, not a new
  failure mode. Update `--selftest`'s existing `fs.existsSync(DEFAULT_REGISTRY_PATH)` conditional
  check to point at the real registry path directly.
- **Convert `experiments/quay-perpetual-stream/scripts/drivable-workspace-check.ts` (and its `.sh`
  wrapper) into real symlinks to the `plugin/scripts/` originals**, matching the precedent Phase 0
  already established for `config-wiring-check.ts`. This is not on the charter's own `## Touches`
  list today (which names only the `.yml` file) — flagged in Risks for explicit sign-off, since
  removing this duplication is what makes the fix durable rather than re-creating the same drift
  risk on the next edit.

### Concrete control/data flow (post-change)

```
readGatesConfig(workspaceRoot):
  if config.yml exists at workspaceRoot:
      gates := config.yml's own `gates:` key (parses & has key), or {} otherwise   [branch A —
                                                                                     no fallback,
                                                                                     ever — incl.
                                                                                     malformed YAML]
  else:
      gates := gates.yml at workspaceRoot, or {} if absent                        [branch B —
                                                                                     unchanged]

readLoopParams(workspaceRoot):
  if config.yml exists at workspaceRoot:
      if malformed YAML → throw FAIL-CLOSED                     [branch A — pre-existing, UNCHANGED]
      if has `loop:` → validate+return it                       [branch A success]
      else → throw FAIL-CLOSED                                  [branch A fail — NEW, was: fall through]
  else:
      if loop.yml exists at workspaceRoot:
          parsed := loop.yml
          if "providers" in parsed → throw FAIL-CLOSED           [Phase 3a — NEW]
          validate+return parsed  (gates:-object-shape already throws via existing check)
      else → throw FAIL-CLOSED (unchanged)
```

**Claimed call/dispatch relationships (flagged per DIR-117 wiring-coverage requirement — each
needs a matching AC item, not just prose assertion):**

   (workspaceRoot)`. For the root workspace (which always has a `config.yml`), this hits branch A
   and, after this change, never touches `.quay/gates.yml` again.
2. Any caller of `readLoopParams(repoRoot)` — this includes `config-wiring-check.ts --driver
   both`, which calls it internally against `REPO_ROOT` — hits branch A for the root workspace
   and, after this change, never touches `.quay/loop.yml` again for a config.yml-governed root.
3. `experiments/quay-perpetual-stream/scripts/select-preflight.ts` and `human-steered-classify.ts`
   both `import { loadRegistry, DEFAULT_REGISTRY_PATH } from "./drivable-workspace-check.ts"` (the
   experiments-side copy) — after the symlink conversion, this import resolves through the
   symlink to the identical `plugin/scripts/` module; both files' own existing tests must stay
   green through that indirection.
4. `config-wiring-check.ts --workspace experiments/quay-perpetual-stream` exercises the same
   branch-B path as exp5's real routines evaluation, doubling as the Phase-3a RED/GREEN
   demonstration surface with zero new code — this reuse claim needs the AC item to actually
   invoke this exact command, not merely describe it.
5. `quay gate --gate drivable-workspace` (only exercised when a task supplies
   `drivableWorkspaceArgs`, which none currently does) → `drivable-workspace-check.sh` → `.ts` →

   coverage is necessarily the *usage-error* path (`--registry` omitted → exit 2) plus a manual
   invocation with an explicit `--registry` pointing at the real file — not an end-to-end proof
   via a real task-triggered gate firing, which does not exist to test against.

### Key design decisions

1. **Split fallback deletion into branch A (delete) and branch B (harden, keep).** A `config.yml`
   that has adopted the unified format is held to being complete (no silent sibling rescue); a
   `config.yml`-less directory keeps the one mechanism it has always had, now hardened. Chosen
   over blanket deletion of both branches because branch B is currently, verifiably exercised by
   exp5's real `.quay/` directory and by 20 tests in `dod-gate-set.test.mjs` plus half of
   `loop-params.test.mjs`'s branch-B GREEN suite — deleting it is a substantially larger,
   not-currently-scoped change for no functional gain the charter's own Done-when items ask for.
2. **Harden the existing branch-B reader in place rather than adding a parallel
   `readLoopProfileFragment` function.** One validation rule set plus a 3-line key-presence check,
   versus duplicating that whole rule set in a second function for marginal clarity gain.
3. **`readGatesConfig` and `readLoopParams` are treated with the same branch-A/branch-B split**,
   even though their failure philosophies differ today (`readGatesConfig` fails quiet by original
   design — an absent gate config is a valid "no gates" state; `readLoopParams` fails closed — a
   workspace with no valid loop config cannot run) and their parse-error handling already differs
   (see Problem framing). Keeping the same branch structure for both, while preserving each
   reader's own philosophy and pre-existing parse-error behavior inside that structure, keeps the
   change's mental model to one shape without silently over-claiming new behavior where none is
   introduced.
4. **`drivable-workspaces.yml` stays put; the reader stops guessing instead of guessing
   differently.** A hardcoded `<script-dir>/../` default is inherently layering-inverted for a
   `plugin/scripts/`-housed script used by an experiments-layer caller with a different relative
   depth; requiring an explicit `--registry` removes the guess rather than adjusting its offset
   (which would only reproduce the exact "offset breaks on relocation" bug class already found
   once for this same script).
5. **Symlink, not re-copy, `drivable-workspace-check.ts`/`.sh`.** The two files are today real,
   live, hand-maintained duplicates, imported as a library by two other real TS files;
   re-copying after this fix only delays the next drift. Phase 0 already validated the symlink
   pattern for `config-wiring-check.ts`.
6. **`gate-ergonomics.test.mjs` requires no fixture migration.** Its three `gates.yml`-writing
   tests are, confirmed by direct reading of each test's setup, pure branch B (each builds its own
   bare `fs.mkdtempSync` workspace, never writing a `config.yml`) — not branch A, as a surface
   reading of the file's unrelated `makeWorkspace()` helper might suggest. Only one brand-new
   branch-A test is needed for `readGatesConfig`, not a fixture migration; this is a materially
   smaller test-file footprint than a first pass over the file's helper shape would suggest.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present (parses or not, with or without `gates:`) → that section
  or `{}`, never an error, never a fallback read (this closes both the missing-key case and the
  previously-silent malformed-YAML case). `config.yml` absent → unchanged branch-B behavior.
- `readLoopParams`: `config.yml` present, parses, but missing `loop:` → `FAIL-CLOSED`, no
  substitution — this is the one genuinely new failure mode (was: silent fallback). `config.yml`
  present but malformed → `FAIL-CLOSED` — pre-existing, unchanged by this milestone. `config.yml`
  absent → unchanged branch-B behavior, now additionally `FAIL-CLOSED` if the parsed fragment
  carries `providers:`.
- `drivable-workspace-check.ts`'s registry resolution: no `--registry` → usage error, exit 2 —
  same failure class as today's "no drivable-workspace arguments defined" short-circuit, never a
  silent pass.
- No new fail-open branch is introduced anywhere; every new failure mode is fail-closed.

### Compatibility

- Root workspace: zero behavior change for any currently-passing path — `config.yml` already
  carries both sections and always parses; branch A's success path is untouched. The dead-weight
  files being deleted are, by construction, never read for this workspace today.
- exp5: `experiments/quay-perpetual-stream/.quay/loop.yml` (confirmed to have no `providers:` key)
  keeps validating exactly as today unless later edited to add one.
- Tests: `loop-params.test.mjs` needs one branch-A GREEN case flipped to RED, plus new RED/GREEN
  cases for the `providers:` ban and an explicit test for the pre-existing `gates:`-object-shape
  rejection. `readGatesConfig` needs exactly one new, purpose-built branch-A test (exact host file
  TBD at Plan time) — **not** a migration of any existing fixture, since none currently exercises

   - **`execution: dispatched` / `audit: adversarial`**：已核对 meta-cc、archguard 两个真实项目
     均显式设置且真实生效（`SKILL.md` 内真实分支消费，非声明未接线）——**结论：保留并接线**，
     不删除。落地时需要把这两个字段显式补进本项目 canonical 的 `config.yml` 的 `loop:` 段
     （目前只在即将删除的根 `loop.yml` 里有，`config.yml` 里缺失——这是 Phase 2 删除 legacy 文件
     前必须先做的迁移，否则删除会导致这两个已确认要保留的字段连同文件一起丢失）。

### Phase 2 — 删除备选项（这才是真正的"结晶"）

4. 删除根 `.quay/gates.yml` 与根 `.quay/loop.yml`，**同时删除 reader 里对应的 fallback 代码路径**
   （`packages/quay/src/gate/config/loader.ts`、`loop-params.ts`）。只要 fallback 还在，就永远是
   两个真相源——删文件而不删 fallback 等于没做。

### Phase 3 — exp5 的 profile fragment 化

5. exp5 保留自己的 loop 配置文件，但其 schema **显式降级为 profile fragment**：只允许携带 loop
   参数，**禁止**出现 `providers:`/`gates:`（那些只能来自根 `config.yml`），由 reader 机械强制
   （出现即 FAIL，不是警告）。这样既保住 `experiments/` 相对 `packages/` 的可分离性，又结构上杜绝
   provider map 漂移。
6. 修正层次倒置：`drivable-workspaces.yml` 要么挪到根（若它是产品级概念），要么让读它的 check 也
   降为 exp5 级。**建议这个文件本身保持独立、不并入 `config.yml`**——它是安全白名单（哪些外部
   工作区允许被驱动），独立文件带来独立的评审注意力、独立的爆炸半径、可单独审计，跟一般配置混在
   一起是负收益（同 `/etc/sudoers` 不并入通用配置的理由）。

### 贯穿全程的不变量

7. 明确写死一条：**配置读取失败 = fail closed，无例外**。据此修正 `select-preflight.ts`
   `checkHalt()` 的 `catch { halt: false }` 为 fail-closed（读不到 → 当作已暂停）。

  [[gap-orphaned-check-scripts-not-wired]]。
- `.halt` 路径本身的修正 —— 已归档在 [[gap-halt-sentinel-path-mismatch]]；本 directive 只接手它
  引出的 fail-open 语义问题（第 7 条）。
