### Chosen mechanism

**Phase 2 — branch-A-only deletion (already signed off, 2026-07-28, human decision recorded
above): branch A is deleted, branch B stays.** Split each reader's single `if (parsed ===
undefined) { fall back }` guard into two named, non-overlapping, terminal cases:

- **Branch A (`unifiedConfigPath` exists) — collapse to a single terminal outcome, no
  fallthrough.** `readGatesConfig` keeps its existing `try { unified = YAML.parse(...) } catch
  {}` (no philosophy change — still fail-quiet on unparsable `config.yml`), but once
  `config.yml` exists it returns *before* ever constructing `legacyGatesPath`: the config-derived
  `gates:` value if present, else the empty `{it0:[],adr:[],fixed:[],testPass:[],
  coverageFloor:[],redGreen:[]}` shape — never falls through to `.quay/gates.yml` again.
  `readLoopParams` keeps its existing "malformed `config.yml` → immediate `FAIL-CLOSED`" line
  and adds one new terminal case: `config.yml` parses but has no `loop:` key → `FAIL-CLOSED`
  immediately (the one genuinely new failure mode this task introduces — previously reachable for
  no live workspace, since root's `config.yml` always has `loop:`).
- **Branch B (`unifiedConfigPath` does not exist) — untouched code, unchanged behavior.** The
  `legacyGatesPath`/`legacyLoopPath` `existsSync` checks and their read logic stay exactly as-is,
  but move entirely inside this branch — after the change, a structural grep must show every
  surviving `existsSync(legacy*)` guard is reachable only when no `config.yml` exists, never as a
  fallthrough from a config.yml-bearing traversal.
- Physically delete root `.quay/gates.yml` and `.quay/loop.yml`. Safe specifically because
  deleting the branch-A code first (or atomically with the files) turns "unreachable" into "does
  not exist" — closing the same "authoritative-looking-but-dead" shape
  `gap-halt-sentinel-path-mismatch` already found once for `.halt`.
- **In scope, not cosmetic:** update the stale doc-comment pointers found in point 7 above —
  `.quay/config.yml`'s own `gates:`/`loop:` header comments, and `packages/quay/bin/quay.ts`'s
  `--help`/inline-comment references to "`.quay/gates.yml`'s own doc comment" / "a `gates.yml`
  per-gate field" — reworded to point at `.quay/config.yml`'s own sections instead of a file that
  no longer exists. Leaving these unedited after this milestone would land a small, avoidable
  instance of the exact drift class DIR-120 exists to close, inside DIR-120 itself.

**Phase 3a — exp5 profile-fragment restriction, enforced inside branch B of `readLoopParams`
only.** Immediately after branch B successfully parses YAML: if the parsed object carries a
`providers:` key (any value, including `null`/empty), `throw FAIL-CLOSED` naming the file and
reason ("a loop-only profile fragment may not declare `providers:` — that belongs exclusively in
a unified `.quay/config.yml`"). This lives inside branch B specifically, not as a global check,
because branch-A workspaces (which *have* a full `config.yml`) are legitimately allowed
`providers:` at that file's own top level — the restriction is "a loop-only *fragment* must not
smuggle in a second provider map," which only makes sense where no `config.yml` exists. The
sibling half — an object-shaped `gates:` value — needs **no new production code**:
`readLoopParams`'s existing type check (`loop-params.ts:104-113`, `Array.isArray(p.gates)` /
`typeof p.gates === "string"`, else throw) already rejects it. This task's obligation for that
half is a new, explicitly-named test in `loop-params.test.mjs` asserting this pre-existing but
never-directly-named invariant, not a code change.

**Cross-check mechanism (round-7 finding) — a concrete `--verify-readers` mode, not a manual
side-by-side paste.** Add `--verify-readers` to `plugin/scripts/config-wiring-check.ts` (point 6
above establishes the experiments path is a real symlink, so this one edit covers both invocation
surfaces automatically) that:
1. Imports and calls `readGatesConfig(workspaceRoot)` and `readLoopParams(workspaceRoot)`
   directly (both already real, in-repo functions — no reimplementation), printing their exact
   returned shapes.
2. Imports and calls `listGates(workspaceRoot)` (the same function `checkGatesValueResolvable`
   already uses) and asserts, **in code**, that every gate name referenced across
   `readGatesConfig`'s `it0`/`fixed`/`testPass`/`coverageFloor`/`redGreen` entries plus
   lower-cased `adr` entries is present in `listGates`'s output set — proving programmatically,
   not by inspection, that `checkGatesValueResolvable`'s "known gates" trace back to
   `readGatesConfig`'s real return value for *this* workspace.
3. Runs the existing `checkField("gates", loopParams.gates, drivers, workspaceRoot)` /
   `checkField("loop", ...)` paths and prints their verdicts directly beside the raw
   `readGatesConfig`/`readLoopParams` output, so both a human and a `node --test` assertion can
   see, for the real post-deletion repo state, whether the checker's opinion and the readers'
   actual behavior agree — not two separately-run, separately-pasted "it worked" claims.
4. Exits 0 if the set-containment assertion holds and `checkField`'s verdict matches the readers'
   real return/throw; exits 1 if the assertion fails; exits 2 on usage/environment error (the
   existing convention `main()` already uses for "workspace has neither config source").

This is the more concrete of the two drafts' cross-check proposals and is adopted over a purely
manual "run both, paste stdout, compare by eye" approach (see Alternatives #5) precisely because
the round-7 finding's complaint was that *no* code today asserts the two implementations agree —
a `--verify-readers` mode that asserts set-containment in code closes that gap durably, not just
for one review cycle.

### Key design decisions

1. The branch-A/branch-B split lives inside the generic reader functions themselves, keyed on
   `fs.existsSync(unifiedConfigPath)` — never as an exp5-specific hardcoded workspace-path
   carve-out. A path-based special case would reintroduce exactly the kind of drift DIR-050
   exists to eliminate.
2. `readGatesConfig`'s fail-quiet contract and `readLoopParams`'s fail-closed contract are **not**
   unified into one shared philosophy by this change, even though both readers get the identical
   structural branch-A/branch-B split. `readGatesConfig` continues to return the empty gates
   shape (never throw) when `config.yml` exists without a `gates:` key; `readLoopParams` newly
   throws in the equivalent case. Deliberate and pre-existing (gates absence = "no workspace
   gates," a valid default; loop absence = "this workspace declared itself but forgot how to
   run," a real misconfiguration) — this milestone must not accidentally converge the two
   contracts while restructuring both readers' branch logic.
3. No new parallel `readLoopProfileFragment()` validator, and no standalone second CLI tool for
   the cross-check — one reader keeps owning all loop-field validation, hardened in place; the
   cross-check is built by calling the *real* reader functions from a new mode on the *existing*
   `config-wiring-check.ts`.
4. The profile-fragment check rejects `providers:` (plus the already-covered object-shaped
   `gates:`) by key presence/type — a deny-list, not an allow-list enumerating every legitimate
   `loop:` key. An allow-list would need updating every time `loop-params.ts` gains a new
   optional field (already happened once for `routines`, DIR-056), silently breaking exp5's real
   file on every future field addition unless someone remembers the second list.
5. Doc-comment cleanup (`config.yml`'s own header, `quay.ts`'s `--help` text) is treated as
   in-scope, not cosmetic — a stale "see `gates.yml`'s own doc comment" pointer to a deleted file
   is the same failure shape `gap-halt-sentinel-path-mismatch` already found once; landing this
   milestone without fixing it would recreate a small instance of the very problem DIR-120 exists
   to close.
6. Root's `.quay/gates.yml`/`.quay/loop.yml` are the **only** files physically deleted. exp5's
   `.quay/loop.yml` survives, now validated under a strictly narrower schema; no third file is
   touched.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present → its `gates:` value, or the empty gates shape if the
  key is absent — never an error, never a fallback file read (unchanged fail-quiet contract,
  narrowed reach). `config.yml` absent → branch B, unchanged (existing `legacyGatesPath` logic,
  including its own malformed-YAML → empty-shape fallback).
- `readLoopParams`: `config.yml` present, parses, has `loop:` → normal return, unchanged.
  `config.yml` present, parses, missing `loop:` → **new** `FAIL-CLOSED` (previously silently fell
  through to any co-located `.quay/loop.yml`). `config.yml` malformed → `FAIL-CLOSED`,
  pre-existing, unchanged. `config.yml` absent → branch B unchanged, **plus** the new
  `providers:`-key `FAIL-CLOSED` check and the newly-named-but-pre-existing object-shaped-`gates:`
  rejection.
- `config-wiring-check.ts --verify-readers`: exits 0 if the set-containment assertion holds and
  `checkField`'s verdict matches the readers' real behavior; exits 1 if the cross-check assertion
  fails; exits 2 on usage/environment error (matching `main()`'s existing convention).
- No new silent-default or fail-open path is introduced anywhere in this milestone's scope — every
  new failure mode fails closed, matching `readLoopParams`'s existing overall contract.

### Alternatives considered and rejected

1. **Delete only the files, leave the reader fallback branches in place.** Rejected — exactly the
   half-measure this directive exists to close; the files would be gone but the
   "authoritative-looking-but-unreachable" branch-A code would still exist, ready to silently
   reactivate if either legacy file were ever recreated by accident (e.g. a stray `cp` during a
   merge).
2. **Delete branch B too, or give exp5 its own full `config.yml`.** Rejected — recreates the
   drifting second-provider-map problem DIR-050 exists to eliminate; exp5 shares the root task
   store and provider map by design.
3. **Unify both readers behind one new `readUnifiedConfig(section)` helper.** Rejected as the
   primary mechanism — `readGatesConfig`'s fail-quiet contract and `readLoopParams`'s fail-closed
   contract genuinely differ; forcing them through one helper would either erase that intentional
   divergence or require a per-caller failure-mode flag, adding indirection without functional
   gain, and would re-touch ~20 currently-green tests across both files for no behavior change.
4. **Allow-list of legitimate `loop:` keys instead of a deny-list of forbidden keys (`providers:`,
   object-shaped `gates:`).** Rejected — churns every time `loop-params.ts` gains a new optional
   field (already happened once for `routines`); a deny-list of the two keys that structurally
   cannot belong in a profile fragment is stable against that churn.
5. **Leave the `config-wiring-check.ts`/reader agreement as an informal "run both, paste stdout,
   compare by eye" step instead of a code-level assertion.** Rejected — this is precisely what the
   round-7 finding flagged as insufficient (point 5 above: the two implementations are connected
   only implicitly, several layers deep, and nothing today asserts they agree); a
   `--verify-readers` mode that asserts set-containment and verdict agreement in code is only
   marginally more work and closes the gap durably, not just for one review cycle.
6. **Skip the explicit branch-A/branch-B sign-off and implement "the obviously correct" reading at
   build time.** Rejected — the ambiguity between "delete branch A only" and "delete both
   branches" is real (exp5's structural dependency on branch B is not obvious from the directive's
   wording alone) and needed a recorded decision, not an implementer's private judgment call made
   silently mid-edit (now recorded, see the opening sign-off line).
7. **Build a full parallel `GATE_FIELDS`/`NO_READER`-etc. classification for the top-level
   `gates:` section inside `config-wiring-check.ts`.** Rejected for this charter — real scope, but
   a distinct unit of work from "delete the legacy fallbacks and prove no divergence for what
   changed"; the narrower `--verify-readers` mechanism satisfies this milestone's actual DoD item
   without that expansion.
8. **Treat this milestone as needing a pre-deletion migration/backfill step for some other
   workspace.** Rejected after directly checking both real sibling workspaces (archguard, meta-cc)
   this session — neither has a legacy `gates.yml`/`loop.yml`; there is no live migration debt to
   backfill before Phase 2's deletion is safe.
9. **Skip the doc-comment cleanup in `quay.ts`/`config.yml` as "just comments, not functional."**
   Rejected — comments asserting a false fact about the codebase ("`gates.yml` remains as a
   fallback," pointing users to a deleted file's "own doc comment") are exactly the molten-prose
   drift this repo's crystallization strategy targets; leaving them stale after this milestone
   would be a small, avoidable regression in the same direction DIR-120 is fixing.
