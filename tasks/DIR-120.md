### Chosen mechanism

**Phase 2 — branch-A-only termination (human-signed-off): delete branch A's fallthrough, keep
branch B.** Restructure each reader's single fallthrough guard into two named, non-overlapping,
terminal cases:

- **Branch A** (`fs.existsSync(unifiedConfigPath)` true) becomes terminal: it computes its outcome
  (the config-derived value, the empty shape, or a thrown FAIL-CLOSED) and returns/throws
  **before ever constructing `legacyGatesPath`/`legacyLoopPath`**. `readGatesConfig` keeps its
  existing `try { unified = YAML.parse(...) } catch {}` (no philosophy change — still fail-quiet on
  unparsable `config.yml`), but once `config.yml` exists it returns the config-derived `gates:`
  value or the empty six-key shape and never falls through to `.quay/gates.yml` again.
  `readLoopParams` keeps its existing "malformed `config.yml` → immediate FAIL-CLOSED" branch and
  adds one new terminal case: `config.yml` parses but has no `loop:` key → FAIL-CLOSED immediately
  (the one genuinely new *loop-side* failure mode this milestone introduces — unreachable for any
  workspace checked today, since all three real `.quay/config.yml`s have `loop:`).
- **Branch B** (`unifiedConfigPath` absent) is untouched code, physically relocated so every
  surviving `existsSync(legacy*)` guard is reachable only inside it — a structural grep must show
  zero fallthrough-from-branch-A call sites remaining.
- Physically delete root `.quay/gates.yml` and `.quay/loop.yml`. This is safe *specifically
  because* branch A's fallthrough is deleted in the same change — "unreachable" becomes "does not
  exist," removing the risk of silent reactivation if either legacy file were ever recreated by
  accident (a stray `cp` during a merge, for example).
- **Add the missing test named in point 11**: assert that "`config.yml` exists, no `gates:` key,
  real content in sibling `.quay/gates.yml`" now returns the empty six-key shape from
  `readGatesConfig`, not the legacy file's content. This is a first-class, separately-named test —
  not folded silently into the loop-side FAIL-CLOSED evidence, because the two behavior changes are
  asymmetric in severity (loud failure vs. silent data loss).
- **In scope, not cosmetic:** repoint the 9 stale `gates.yml` references in `packages/quay/bin/
  quay.ts` (lines 198, 205, 220, 383/384/386/388, 1110, 1141) and reword `.quay/config.yml`'s own
  `gates:`/`loop:` header comments so neither describes a deleted file as a live fallback. Leaving
  these unedited would land a small, avoidable instance of exactly the failure class this
  milestone exists to close, inside the milestone itself.

**Phase 3a — exp5 profile-fragment restriction, inside branch B only.** Immediately after branch B
parses YAML in `readLoopParams`, add two checks scoped to branch B only:
1. If the parsed object carries a `providers:` key (any value, including `null`), throw
   FAIL-CLOSED naming the file and reason ("a loop-only profile fragment may not declare
   `providers:` — that belongs exclusively in a unified `.quay/config.yml`"). This lives
   specifically inside branch B, not globally, because branch-A workspaces legitimately have
   `providers:` at `config.yml`'s own top level — the restriction is "a loop-only *fragment* may
   not smuggle in a second provider map," which is only a meaningful statement where no
   `config.yml` exists.
2. The object-shaped-`gates:` half needs **no new production code** — `loop-params.ts` lines
   104-113 (confirmed by direct read) already reject anything that is neither an array nor a
   non-empty string for `gates`; this milestone's obligation there is a new, explicitly-named test
   asserting that pre-existing but never-directly-named invariant — a test-coverage gap, not a
   code gap.

**Cross-check mechanism — a `--verify-readers` mode on the existing `config-wiring-check.ts`, not
a manual side-by-side paste.** Because the symlink means one file covers both invocation surfaces,
add one new CLI mode that:
1. Imports and directly calls `readGatesConfig(workspaceRoot)`/`readLoopParams(workspaceRoot)`
   (both real, already-in-repo functions — no reimplementation), printing their exact returned
   shapes.
2. Calls `listGates(workspaceRoot)` (the same function `checkGatesValueResolvable` already uses)
   and asserts in code that every gate name referenced in `readGatesConfig`'s
   `it0`/`fixed`/`testPass`/`coverageFloor`/`redGreen` entries (plus lower-cased `adr` entries) is
   present in `listGates`'s output — proving programmatically, not by inspection, that
   `checkGatesValueResolvable`'s notion of "known gates" really traces back to `readGatesConfig`'s
   real return for this workspace.
3. Runs the existing `checkField("gates", …)`/`checkField("loop", …)` paths and prints their
   verdicts beside the raw reader output, so a `node --test` assertion can check agreement instead
   of a human eyeballing two separately pasted transcripts.
4. Exits 0 if the set-containment assertion holds and `checkField`'s verdict matches the readers'
   real behavior; 1 if the cross-check assertion fails; 2 on usage/environment error, matching
   `main()`'s existing exit-code convention.

This is chosen over an informal "run both, paste stdout, compare by eye" step precisely because
the underlying finding this addresses is that *no code today* asserts the two implementations
agree — asserting set-containment and verdict agreement in code closes the gap durably, not just
for one review cycle.

### Key design decisions

1. The branch-A/branch-B split stays keyed on `fs.existsSync(unifiedConfigPath)` inside the
   generic reader functions — never an exp5-specific hardcoded path carve-out, which would
   reintroduce the drift class DIR-050 exists to close.
2. `readGatesConfig`'s fail-quiet contract and `readLoopParams`'s fail-closed contract are
   deliberately **not** unified, even though both readers get the same structural split.
   `readGatesConfig` still returns the empty gates shape when `config.yml` has no `gates:` key;
   `readLoopParams` newly throws in the equivalent case for `loop:` — gates-absence is a valid "no
   workspace gates" default, loop-absence is a real misconfiguration. This split must not be
   accidentally converged while restructuring both readers.
3. No new parallel `readLoopProfileFragment()` validator and no second CLI tool for the
   cross-check — one reader keeps owning all loop-field validation; the cross-check is a new mode
   on the *existing* `config-wiring-check.ts`, calling the real reader functions directly.
4. The profile-fragment check is a deny-list (reject `providers:` and object-shaped `gates:`), not
   an allow-list of legitimate `loop:` keys — an allow-list would need updating every time
   `loop-params.ts` gains a new optional field (already happened once for `routines`, DIR-056),
   silently breaking exp5's real file on the next field addition unless someone remembers the
   second list.
5. Doc-comment cleanup (`quay.ts`, `config.yml`) is in-scope, not cosmetic — leaving stale
   pointers after deleting the files they describe would land a small instance of the exact
   failure shape (`gap-halt-sentinel-path-mismatch`) this milestone's own reasoning invokes.
6. Root's two legacy files are the only files physically deleted; exp5's `.quay/loop.yml`
   survives under a strictly narrower schema; no third file is touched.
7. The `gates:`-side silent-data-loss test (problem-framing point 11) is a first-class,
   separately-named AC item, not folded silently into the `loop:`-side FAIL-CLOSED evidence — the
   two behavior changes are not symmetric in severity and must not be reported as one.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present → its `gates:` value or the empty shape — never an
  error (unchanged fail-quiet contract, narrowed reach). `config.yml` present, no `gates:` key,
  legacy `gates.yml` present with real content → **new, silent** empty-shape return
  (data-loss-shaped, not error-shaped — see control/data-flow item 6), instead of the legacy
  file's real content as today. `config.yml` absent → branch B unchanged (existing
  `legacyGatesPath` logic, including its own malformed-YAML → empty-shape fallback).
- `readLoopParams`: `config.yml` present + has `loop:` → normal return, unchanged. `config.yml`
  present + missing `loop:` → **new** FAIL-CLOSED (previously silently fell through to a
  co-located `.quay/loop.yml`). `config.yml` malformed → FAIL-CLOSED, pre-existing, unchanged.
  `config.yml` absent → branch B unchanged, plus the new `providers:`-key FAIL-CLOSED and the
  newly-named (pre-existing) object-shaped-`gates:` rejection.
- `config-wiring-check.ts --verify-readers`: 0 = agreement holds; 1 = cross-check assertion
  fails; 2 = usage/environment error (matches `main()`'s existing convention).
- Two real behavior changes ship in this milestone, not one, and they are asymmetric: the
  `loop`-side change fails **loud** (a new, actionable FAIL-CLOSED); the `gates`-side change fails
  **quiet** (a new silent empty-shape return, its pre-existing fail-quiet contract narrowed in
  reach but not converted to an error). Both must be named and tested as first-class items; neither
  is cosmetic, and neither should be described as "the only real behavior change" — that framing,
  present in an earlier revision of this task, undercounted the risk and has been corrected here.

### Risks

- **Branch A/B boundary misjudged** — mitigated by the explicit human sign-off recorded above, a
  structural grep proof (not substring-absence) that every surviving `existsSync(legacy*)` guard
  lives only inside the no-`config.yml` branch, and real post-deletion `quay gate`/
  `readLoopParams(repoRoot)` calls.
- **Checker/reader drift persists post-change** (the actual driver behind the cross-check
  requirement) — mitigated by `--verify-readers` asserting set-containment and verdict agreement
