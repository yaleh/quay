### Problem framing (re-verified directly against the live tree, 2026-07-28)

`readGatesConfig()` (`packages/quay/src/gate/config/loader.ts`) and `readLoopParams()`
(`packages/quay/src/loop-params.ts`) each collapse a real branch structure into a single fallback:

1. **Branch A** — a governing `.quay/config.yml` exists at `workspaceRoot`, but the reader still
   falls through to the sibling `.quay/gates.yml`/`.quay/loop.yml` beside it. `readGatesConfig` is
   fail-quiet here: a `config.yml` that parses but lacks a `gates:` key, **or** one that fails to
   parse at all (swallowed by `try/catch`), both fall through today — two distinct sub-conditions
   collapsed into one guard. `readLoopParams` is already fail-closed on malformed YAML (throws
   immediately, never reaching the fallback for that case); its only live branch-A leak is
   narrower — a well-formed `config.yml` simply missing `loop:` still falls through silently. Root
   `.quay/config.yml` (confirmed: always parses, always carries both `gates:` and `loop:`) makes
   branch A the only path root ever takes for either reader — provably dead today, not
   hypothetical. Root's own `.quay/gates.yml`/`.quay/loop.yml` have already drifted from
   `config.yml` while sitting there looking authoritative (`gates: [vitest]`, a copy-paste leftover
   from `archguard` where `vitest` is genuinely real but is dangling here — confirmed via grep
   against this repo's real dependencies/gate-events).
2. **Branch B** — no `.quay/config.yml` exists at `workspaceRoot` at all — is NOT uniformly dead:
   it is exp5's own real, live, structurally necessary path (`experiments/quay-perpetual-stream/
   .quay/` contains only `loop.yml`, confirmed via `ls`). exp5 shares the root `tasks/` store and
   root provider map; it cannot "graduate" to its own `config.yml` without recreating the exact
   drifting second-provider-map problem DIR-050 exists to eliminate. Branch B must survive.
   "Delete the fallback branch(es)" is therefore genuinely ambiguous as charter wording — deleting
   branch A only, vs. both, is a real scope decision requiring explicit sign-off (see Chosen
   mechanism).
3. **exp5's own `.quay/loop.yml` carries no `providers:`/object-shaped-`gates:` key today, but
   nothing in `readLoopParams` would reject one if added.** Because exp5 shares the root provider
   map, a `providers:` key smuggled into this loop-only fragment would silently create a second,
   unreconciled provider map — the same DIR-050-era drift this directive exists to close, one layer
   down. This is the concrete justification for Phase 3a's new structural check.
4. **`config-wiring-check.ts` does not call `readGatesConfig`/`readLoopParams` internally** — it
   independently re-implements grep-based evidence per its own doc comment. Post-deletion, its
   reported verdict for the `gates`/`loop` fields and the readers' actual runtime behavior must be
   shown to agree — this must be proven, not assumed true because one calls the other (it doesn't).

### Chosen mechanism

**Phase 2 — branch-A-only deletion (SIGN-OFF, 2026-07-28, human decision):** branch A is deleted;
branch B stays. Split the current single `if (parsed === undefined) { fall back }` guard in both
`readGatesConfig` and `readLoopParams` into two named cases: **Branch A — DELETE** (once
`config.yml` exists — parses or not, has the relevant key or not — return the config-derived value
or throw `FAIL-CLOSED` immediately; never fall through again). **Branch B — KEEP, unchanged**
(exp5's real, live, currently-necessary path; the generic back-compat path for any future
config.yml-less workspace). Root's `.quay/gates.yml`/`.quay/loop.yml` are then physically deleted —
safe because root's `config.yml` already makes branch A provably unreachable for root today;
deleting the branch code turns "unreachable" into "does not exist," closing the exact
"authoritative-looking but dead" shape `gap-halt-sentinel-path-mismatch` already found once.
Branch B's deletion (or giving exp5 its own full `config.yml`) is explicitly out of scope — exp5
structurally depends on branch B.

**Phase 3a — exp5 profile-fragment restriction, enforced inside `readLoopParams` itself:** inside
branch B only, if the parsed object carries a `providers:` key, throw `FAIL-CLOSED` naming the file
and reason. The sibling invariant — an object-shaped `gates:` value is rejected — needs no new
code (the existing field-type check already throws for this); this task's AC item for that half is
a new, explicitly-named test asserting the pre-existing-but-never-directly-named behavior. RED/GREEN
proof reuses `config-wiring-check.ts --workspace <path>` (already accepts the flag, calls
`readLoopParams` internally) rather than inventing a new flag.

**Post-deletion cross-check (2026-07-28, round-7 `prepare-milestone.js` finding, wf_e2e72ee1-a69):**
`config-wiring-check.ts`'s grep-derived verdict for the `gates`/`loop` fields and
`readGatesConfig(repoRoot)`/`readLoopParams(repoRoot)`'s actual real behavior must be shown to
agree post-deletion, side by side — not two independently-run "it worked" claims that could
silently diverge since neither implementation calls the other.

### Key design decisions

1. Branch A/B split lives in the generic reader, not as an exp5-special-case — a hardcoded
   workspace-path carve-out would reintroduce exactly the kind of drift DIR-050 exists to
   eliminate.
2. Harden the existing branch-B reader in place, not a parallel `readLoopProfileFragment()` /
   second validator — a fragment and the unified `loop:` section validate identically
   field-by-field; one reader keeps owning all loop-field validation.
3. The profile-fragment check rejects `providers:` (and the already-covered object-shaped `gates:`)
   by key presence/type, not a stricter allow-list of every legitimate loop key — an allow-list
   would churn every time `loop-params.ts` gains an optional field (already happened once,
   `routines`/DIR-056).
4. Both readers keep the same branch-A/B structural split despite differing failure philosophies —
   `readGatesConfig` fails quiet by design, `readLoopParams` fails closed by design; deleting
   branch A must not accidentally converge these two contracts into one.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present → that section's value, or the empty gates shape — never
  an error, never a fallback read. `config.yml` absent → unchanged branch-B behavior.
- `readLoopParams`: `config.yml` present, parses, missing `loop:` → `FAIL-CLOSED` (the one
  genuinely new failure mode this task introduces). Malformed `config.yml` → `FAIL-CLOSED`,
  pre-existing, unchanged. `config.yml` absent → unchanged branch-B behavior, now additionally
  `FAIL-CLOSED` on a `providers:` key or object-shaped `gates:`.
- No new silent-default or fail-open path is introduced anywhere in this task's scope.

### Compatibility

- **Root workspace**: zero observable behavior change for any currently-passing path — the two
  deleted files were already unreachable by construction.
- **exp5**: zero observable behavior change for its real, unmodified `.quay/loop.yml` (no
  `providers:`/object-`gates:` key present today) — branch B is untouched code, plus one new check
  its real file already passes.
- **Sibling workspaces** (`archguard`, `meta-cc`, checked directly): each has only `config.yml` —
  no legacy `gates.yml`/`loop.yml` in either — branch-A deletion breaks neither.
- **`gate-ergonomics.test.mjs`/`dod-gate-set.test.mjs`**: no code changes needed (both pure
  branch-B tests per their own setup) but both must be re-run unmodified, green, as explicit
  evidence, since both exercise the gate-loading path this task edits.
- **A hypothetical mid-migration third-party workspace** (has `config.yml` but forgot `loop:`/
  `gates:`, still has a legacy sibling file): the one real, named behavior change — what used to
  silently work via the fallback now fails closed with a specific, actionable error. Judged worth
  taking; zero known live victims today.

### Risks

- **Branch A/B boundary misjudged** — the single biggest risk; mitigated by the explicit,
  human-signed-off design decision above plus a structural grep proof (not substring-absence) that
  surviving `existsSync(legacy*)` guards are reachable only inside the no-`config.yml` branch.
- **`config-wiring-check.ts`'s verdict and the readers' actual behavior drift apart post-change**
  (round-7 finding) — mitigated by requiring the side-by-side agreement proof above, not two
  independent "it ran" evidence lines.
- **`gate-ergonomics.test.mjs`/`dod-gate-set.test.mjs` regressions** — mitigated by requiring both
  re-run green with pasted real output, unmodified.
- **Test-churn shortcut risk**: `loop-params.test.mjs`'s branch-A GREEN case must be *flipped to
  RED*, not deleted — deleting it would silently shrink RED coverage.
- **Touches-list gap**: needs an explicit sign-off (amend Touches, or confirm colocated
  test-file edits don't require separate enumeration), not a silent omission.

### Non-goals

- Any change to `packages/*/provider.yml` or `plugin/.claude-plugin/plugin.json`.
- A new top-level "profile fragment" CLI mode or standalone validator — the restriction is a branch
  inside the existing `readLoopParams` reader.

### Alternatives considered and rejected

1. **Delete only the files, leave the reader fallback branches in place.** Rejected — exactly the
   half-measure this directive exists to close.
2. **Delete branch B too / give exp5 its own full `config.yml`.** Rejected — recreates the
   drifting second-provider-map problem DIR-050 exists to eliminate.
3. **Unify both readers behind one new `readUnifiedConfig(section)` helper.** Rejected as the
   primary mechanism — the two readers' field sets, defaults, and fail-quiet-vs-fail-closed
   contracts genuinely differ; re-touches ~20 currently-green tests for no functional gain.
4. **Allow-list of legitimate loop keys instead of a deny-list of forbidden keys.** Rejected —
   churns every time `loop-params.ts` gains a new optional field.
5. **Skip the explicit branch-A/branch-B sign-off, implement "the obviously correct" reading at
   build time.** Rejected — this is precisely the ambiguity that needs a recorded decision, not an
   implementer's private judgment call.
6. **Treat Phase 0/1 (M186) as needing a pre-deletion migration step.** Rejected — re-verified
   directly against the live `.quay/config.yml`: all four Phase-1 values are already landed; no
   further migration is outstanding before Phase 2's deletion is safe.
