### Chosen mechanism

**Phase 2 — branch-A-only deletion (human-signed-off): delete branch A, keep branch B.**
Restructure each reader's single fallthrough guard into two named, non-overlapping, terminal
cases:

- **Branch A** (`fs.existsSync(unifiedConfigPath)` true) collapses to one terminal outcome, with
  no fallthrough to the legacy file at all. `readGatesConfig` keeps its existing `try { unified =
  YAML.parse(...) } catch {}` (no philosophy change — still fail-quiet on unparsable
  `config.yml`), but once `config.yml` exists it returns the config-derived `gates:` value or the
  empty six-key shape *before* ever constructing `legacyGatesPath` — never falls through to
  `.quay/gates.yml` again. `readLoopParams` keeps its existing "malformed `config.yml` →
  immediate FAIL-CLOSED" branch and adds one new terminal case: `config.yml` parses but has no
  `loop:` key → FAIL-CLOSED immediately (the one genuinely new failure mode this milestone
  introduces — unreachable for any workspace checked today, since all three real
  `.quay/config.yml`s have `loop:`).
- **Branch B** (`unifiedConfigPath` absent) is untouched code, physically relocated so every
  surviving `existsSync(legacy*)` guard is reachable only inside it — a structural grep must show
  zero fallthrough-from-branch-A call sites remaining.
- Physically delete root `.quay/gates.yml` and `.quay/loop.yml`. This is safe *specifically
  because* the branch-A code path is deleted in the same change — "unreachable" becomes "does not
  exist," instead of leaving an authoritative-looking dead branch that could silently reactivate
  if either legacy file were ever recreated by accident (e.g. a stray `cp` during a merge).
- **In scope, not cosmetic:** update the stale pointers found at points 6/7 above —
  `packages/quay/bin/quay.ts`'s `--help`/inline comments and `.quay/config.yml`'s own header
  comments, reworded to stop describing a deleted file as a live fallback. Leaving these unedited
  would land a small, avoidable instance of the exact "stale-but-authoritative-looking pointer"
  failure class this milestone exists to close, inside the milestone itself.

**Phase 3a — exp5 profile-fragment restriction, inside branch B only.** Immediately after branch B
parses YAML in `readLoopParams`: if the parsed object carries a `providers:` key (any value,
including `null`), throw `FAIL-CLOSED` naming the file and reason ("a loop-only profile fragment
may not declare `providers:` — that belongs exclusively in a unified `.quay/config.yml`"). This
check lives specifically inside branch B, not globally, because branch-A workspaces legitimately
have `providers:` at `config.yml`'s own top level — the restriction is "a loop-only *fragment* may
not smuggle in a second provider map," which is only a meaningful statement where no `config.yml`
exists. The sibling half (object-shaped `gates:`) needs **no new production code** —
`loop-params.ts` lines 104-113 already reject anything that is neither an array nor a non-empty
string for `gates`; this milestone's obligation there is a new, explicitly-named test asserting
that pre-existing but never-directly-named invariant — a test-coverage gap, not a code gap.

**Cross-check mechanism (round-7 finding) — a `--verify-readers` CLI mode on the existing
`config-wiring-check.ts`, not a manual side-by-side paste.** Because the symlink means one file
covers both invocation surfaces, add one new mode that:
1. Imports and calls `readGatesConfig(workspaceRoot)`/`readLoopParams(workspaceRoot)` directly
   (both already real, in-repo functions — no reimplementation), printing their exact returned
   shapes.
2. Imports and calls `listGates(workspaceRoot)` (the same function `checkGatesValueResolvable`
   already uses) and asserts *in code* that every gate name referenced in `readGatesConfig`'s
   `it0`/`fixed`/`testPass`/`coverageFloor`/`redGreen` entries (plus lower-cased `adr` entries) is
   present in `listGates`'s output — proving programmatically, not by inspection, that
   `checkGatesValueResolvable`'s notion of "known gates" traces back to `readGatesConfig`'s real
   return for *this* workspace.
3. Runs the existing `checkField("gates", …)`/`checkField("loop", …)` paths and prints their
   verdicts beside the raw reader output, so a `node --test` assertion (not eyeballing) can see
   whether the checker's opinion and the readers' real return/throw behavior agree for the real,
   post-deletion repo state.
4. Exits 0 if the set-containment assertion holds and `checkField`'s verdict matches the readers'
   real behavior; 1 if the cross-check assertion fails; 2 on usage/environment error (matching
   `main()`'s existing convention).

This is adopted over an informal "run both, paste stdout, compare by eye" step (Alternatives #5)
precisely because the round-7 finding's complaint was that *no* code today asserts the two
implementations agree — asserting set-containment and verdict agreement in code closes the gap
durably, not just for one review cycle.

### Key design decisions

1. The branch-A/branch-B split stays keyed on `fs.existsSync(unifiedConfigPath)` inside the
   generic reader functions — never an exp5-specific hardcoded path carve-out, which would
   reintroduce the drift class DIR-050 exists to close.
2. `readGatesConfig`'s fail-quiet contract and `readLoopParams`'s fail-closed contract are
   deliberately **not** unified even though both readers get the same structural split.
   `readGatesConfig` still returns the empty gates shape when `config.yml` has no `gates:` key;
   `readLoopParams` newly throws in the equivalent case — gates-absence is a valid "no workspace
   gates" default, loop-absence is a real misconfiguration. This milestone must not accidentally
   converge the two contracts while restructuring both readers.
3. No new parallel `readLoopProfileFragment()` validator and no second CLI tool for the
   cross-check — one reader keeps owning all loop-field validation; the cross-check is a new mode
   on the *existing* `config-wiring-check.ts`, calling the real reader functions.
4. The profile-fragment check is a deny-list (reject `providers:` and object-shaped `gates:`), not
   an allow-list of legitimate `loop:` keys — an allow-list would need updating every time
   `loop-params.ts` gains a new optional field (already happened once for `routines`, DIR-056),
   silently breaking exp5's real file on the next field addition unless someone remembers the
   second list.
5. Doc-comment cleanup (`quay.ts`, `config.yml`) is in-scope, not cosmetic — leaving stale
   pointers after deleting the files they describe would land a small instance of the exact
   failure shape (`gap-halt-sentinel-path-mismatch`) this milestone's own reasoning invokes.
6. Root's two legacy files are the only files physically deleted; exp5's `.quay/loop.yml` survives
   under a strictly narrower schema; no third file is touched.

### Defaults and failure behavior

- `readGatesConfig`: `config.yml` present → its `gates:` value or the empty shape — never an error
  (unchanged fail-quiet contract, narrowed reach). `config.yml` absent → branch B unchanged
  (existing `legacyGatesPath` logic, including its own malformed-YAML → empty-shape fallback).
- `readLoopParams`: `config.yml` present + has `loop:` → normal return, unchanged. `config.yml`
  present + missing `loop:` → **new** FAIL-CLOSED (previously silently fell through to a
  co-located `.quay/loop.yml`). `config.yml` malformed → FAIL-CLOSED, pre-existing, unchanged.
  `config.yml` absent → branch B unchanged, plus the new `providers:`-key FAIL-CLOSED and the
  newly-named (pre-existing) object-shaped-`gates:` rejection.
- `config-wiring-check.ts --verify-readers`: 0 = agreement holds; 1 = cross-check assertion
  fails; 2 = usage/environment error (matches `main()`'s existing convention).
- No new silent-default or fail-open path is introduced anywhere in this milestone's scope — every
  new failure mode fails closed, matching `readLoopParams`'s existing overall contract.

### Alternatives considered and rejected

1. **Delete only the files, leave the reader fallback branches in place.** Rejected — the exact
   half-measure this directive exists to close; the "authoritative-looking-but-unreachable" branch
   would remain, ready to silently reactivate if either legacy file were ever recreated by
   accident (e.g. a stray `cp` during a merge).
2. **Delete branch B too, or give exp5 its own full `config.yml`.** Rejected — recreates the
   drifting second-provider-map problem DIR-050 exists to eliminate.
3. **Unify both readers behind one new `readUnifiedConfig(section)` helper.** Rejected as the
   primary mechanism — the fail-quiet vs. fail-closed contracts genuinely differ; forcing them
   through one helper would either erase that intentional divergence or need a per-caller
   failure-mode flag, adding indirection without functional gain, and would re-touch ~20
   currently-green tests for no behavior change.
4. **Allow-list of legitimate `loop:` keys instead of a deny-list.** Rejected — churns every time
   `loop-params.ts` gains a new optional field (already happened once for `routines`); a deny-list
   of the two keys that structurally cannot belong in a profile fragment is stable against that
   churn.
5. **Leave the checker/reader agreement as an informal "run both, paste stdout, compare by eye"
