## Proposal

把配置面做一次真正的结晶（`docs/proposals/exp5-crystallization-strategy.md` 的"molten prose →
executable single-source"方向），但**结晶的对象不是"文件数量"，而是一条可机械检查的不变量**：

> 每个被声明的配置字段，有且只有一个具名的、可机械验证的 reader。

顺序上先立这条不变量（Phase 0），再解决现存的矛盾声明（Phase 1），最后才删除 legacy 文件、完成
DIR-050 已经开了头但没做完的统一（Phase 2-3）。

**为什么顺序不能反**：合并文件并不能解决 inert 字段问题，反而会让它更难被发现。如果 exp5 的
`concurrency: 2` 搬进统一的 `config.yml` 而 `OUTER-LOOP.md` 依然不读它，这个字段会显得**更**权威
（它在规范文件里！）却依然是死的。[[gap-halt-sentinel-path-mismatch]] 就是这个失效模式的活样本：
一个看起来权威、实际不在执行路径上的东西，配上一份过时的文档，酿成了一次安全相关的真实疏漏。

## Finding

（全部直接读文件核对，不是推测；2026-07-27）

1. **三份互相矛盾的 loop 声明**，不是冗余而是未解决的分叉：

   | 字段 | `.quay/config.yml` 的 `loop:` 段 | 根 `.quay/loop.yml` | exp5 `.quay/loop.yml` |
   |---|---|---|---|
   | `gates` | `[it0-set]` | **`[vitest]`** | `[it0-set]` |
   | `concurrency` | 无 | **4** | **2** |
   | routines 触发 | `every(5)`/`every(10)` | `every(3)`/`every(5)`/`every(10)` | **`on(checkpoint)`** |
   | `execution`/`audit` | 无 | `dispatched`/`adversarial` | 无 |

   "loop 到底跑哪套 gate"目前有两个不同答案（`it0-set` vs `vitest`），哪个生效取决于 reader 实现
   里 fallback 的先后顺序——**没有任何一处文档写明谁赢**。

2. **DIR-050 的统一做了一半**：`.quay/config.yml` 自己的 header 已经声明 `providers:`/`gates:`/
   `loop:` 三段是"the SINGLE SOURCE OF TRUTH for this workspace"，但 legacy 文件没删、reader 的
   fallback 路径还在。结果比两个极端都糟：既有规范文件，又有会赢过它的备选项。

3. **`.quay/gates.yml`（仓库根）是死代码**：`config.yml` 的 `gates:` 段永远存在，所以 fallback
   永远不会被触发。而且两者同名 gate 的脚本路径**已经悄悄分叉**（一个指 `plugin/scripts/`，一个指
   `experiments/.../scripts/`），目前无害仅仅因为这个文件没人读——一旦 loader 的 fallback 逻辑变
   动，同名 gate 会静默指向不同脚本。

4. **层次倒置**：`drivable-workspaces.yml` 实际位于 `experiments/quay-perpetual-stream/` 下，但读
   它的 `drivable-workspace-check.sh` 是 `plugin/scripts/` 里的**产品级** gate（由 `config.yml` 的
   `gates.it0` 段注册）。产品读实验目录的配置，方向反了。

5. **fail 语义不一致**：`readLoopParams` 是 FAIL-CLOSED 的，但 `select-preflight.ts` 的
   `checkHalt()` 用 `catch { return { halt: false } }` —— 读取失败默认"没暂停、放行"，是
   fail-**OPEN**。同一个仓库对"配置读不到怎么办"没有统一约定，而这正是 halt bug 之所以危险的直接
   原因。

6. **exp5 不是独立 workspace**：它的任务存在根 `tasks/`、用根的 provider map。所以给它一份完整的
   `config.yml` 会造出第二份会漂移的 provider 映射——正是要消灭的东西。

## Requested action

### Phase 0（前置，最便宜，可独立落地）— 立不变量

1. 新增 `config-wiring-check`（`plugin/scripts/` + `experiments/*/scripts/` 镜像，遵循本目录既有
   的 `<name>-selfcheck.sh` 约定）：对配置 schema 里的**每个字段**断言存在一个具名 reader（可
   grep 到的真实消费点），否则 FAIL。接进 CI 或 `.quay/config.yml` 的 gate 集。
2. 这个检查跑起来后，应当立刻把 `concurrency`/`execution`/`audit` 这几个当前无人读取的字段暴露
   为 FAIL——**这是预期的 RED 状态，必须贴出来**，不是先改字段再跑绿。

### Phase 1（人的决策，不是实现）— 先解决矛盾再谈合并

3. 两个互相矛盾的文件没法"合并"，只能静默选赢家。以下每一条都需要人明确拍板，并把决定写回本
   directive 或其里程碑 charter：
   - loop 的 `gates` 到底是 `it0-set` 还是 `vitest`？
   - `concurrency` 到底是 4 还是 2（还是分 profile 各自取值）？
   - routines 触发频率取哪一套（`every(N)` vs `on(checkpoint)`）？
   - `execution: dispatched` / `audit: adversarial` 这两个只存在于根 `loop.yml` 的字段，是保留并
     接线，还是删除？

### Phase 2 — 删除备选项（这才是真正的"结晶"）

4. 删除根 `.quay/gates.yml` 与根 `.quay/loop.yml`，**同时删除 reader 里对应的 fallback 代码路径**
   （`packages/quay/src/gate/config/loader.ts`、`loop-params.ts`）。只要 fallback 还在，就永远是
   两个真相源——删文件而不删 fallback 等于没做。

### Phase 3 — exp5 的 profile fragment 化

5. exp5 保留自己的 loop 配置文件，但其 schema **显式降级为 profile fragment**：只允许携带 loop
   参数，**禁止**出现 `providers:`/`gates:`（那些只能来自根 `config.yml`），由 reader 机械强制
   （出现即 FAIL，不是警告）。这样既保住 `experiments/` 相对 `packages/` 的可分离性，又结构上杜绝
   provider map 漂移。
6. 修正层次倒置：`drivable-workspaces.yml` 要么挪到根（若它是产品级概念），要么让读它的 check 也
   降为 exp5 级。**建议这个文件本身保持独立、不并入 `config.yml`**——它是安全白名单（哪些外部
   工作区允许被驱动），独立文件带来独立的评审注意力、独立的爆炸半径、可单独审计，跟一般配置混在
   一起是负收益（同 `/etc/sudoers` 不并入通用配置的理由）。

### 贯穿全程的不变量

7. 明确写死一条：**配置读取失败 = fail closed，无例外**。据此修正 `select-preflight.ts`
   `checkHalt()` 的 `catch { halt: false }` 为 fail-closed（读不到 → 当作已暂停）。

**Out of scope（明确不做，避免与已归档任务重复）**：
- `packages/*/provider.yml`、`plugin/.claude-plugin/plugin.json` —— **绝对不动**。前者随 Provider
  包发布、是第三方能自己写 provider 的 ABI 契约；后者 schema 由 Claude Code 拥有。跨这一层的合并
  是破坏，不是精简。
- `delivery-manifest.json` 及其孤儿 checker —— 它是对构建产物的**断言**（更接近 test fixture），
  不是"系统该怎么做"的配置，不该并入 `config.yml`；其接线问题已归档在
  [[gap-orphaned-check-scripts-not-wired]]。
- `.halt` 路径本身的修正 —— 已归档在 [[gap-halt-sentinel-path-mismatch]]；本 directive 只接手它
  引出的 fail-open 语义问题（第 7 条）。
