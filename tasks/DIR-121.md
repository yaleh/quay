## Proposal

Implement Stage 1 of the Codex adoption design as a bounded, human-authorized interactive Quay
operator. A fresh Codex session in this trusted repository must load concise repository guidance,
discover two repository Skills, connect to the existing provider-neutral Quay MCP server, and
safely perform explicitly authorized task administration with a separately proven CLI fallback.

Keep the four Codex surfaces separate and minimal:

1. root `AGENTS.md` carries durable repository authority, verification, and safety rules;
2. repository Skills carry the repeatable `quay-task-operator` and `quay-directive` workflows;
3. project `.codex/config.toml` registers only the Quay MCP server needed by this stage; and
4. Quay task/Git artifacts retain the authoritative result and real-landing evidence.

Use `plugin/skills/` as the runtime-neutral canonical Skill source. Codex repository Skills under
`.agents/skills/` must resolve to that source rather than copy lifecycle policy. The existing
Claude-facing `quay-directive` surface must also resolve to the same canonical task-canonical
contract, with host-specific invocation/path handling kept in a thin adapter only. Add a mechanical
drift check so `.claude` and `.agents` cannot silently disagree about task authority, write/readback,
schema validation, lifecycle, or completion boundaries.

This stage grants no autonomous lifecycle authority. Codex may list, get, check, create, and edit
tasks only after explicit human authorization in the active conversation. It may not independently
tick AC/DoD, close tasks, SELECT or execute milestones, launch workers, merge, ABSORB, schedule
continuations, or treat transcript/session evidence as authoritative state.

Conflict protection is deliberately bounded to mechanisms that exist now. Lifecycle writes use
`expectedStatus` CAS and must demonstrate a rejected stale-status write. Body writes use
read-before-write, a human-visible semantic diff, an immediate freshness re-read, write, readback,
schema check, and scoped Git diff/commit. This stage must not claim that those steps provide atomic
same-status body conflict protection. If live use proves an `expectedUpdatedAt`/content-hash ABI is
required, file a separate provider-neutral product task instead of expanding this directive
silently.

The final proof must use a fresh Codex session and real, useful tasks. A synthetic fixture or
self-congratulatory `CODEX-PROBE-*` task is useful for negative tests but cannot satisfy real
landing. If no legitimate task needs creation during the implementing milestone, the real-create
criterion remains open or `needs-human`; it is not replaced with a fake task.

## Finding

The repository has completed a detailed Codex portability design, but no Codex adaptation task or
implementation currently exists. Specifically:

- there is no root `AGENTS.md`, `.agents/skills/`, or project `.codex/config.toml`;
- `.mcp.json` registers Quay for the existing Claude environment, but `codex mcp list` does not list
  a project Quay server;
- the reusable methodology and directive Skills are Claude/plugin-oriented and are not discovered
  by Codex as repository Skills;
- the current global Codex environment happens to expose meta-cc, but that is an external
  prerequisite and not a Quay project adaptation;
- the Codex port proposal's Stage 1 and all implementing acceptance criteria remain unchecked.

The design identifies Stage 1 as independently useful: replace the human-facing Claude terminal
role for bounded Quay task administration before attempting session-evidence integration,
milestone execution, a Host Adapter, or restart-safe continuous operation.

## Requested action

1. Add a concise root `AGENTS.md` that names the task store/Provider ABI authority, supported
   commands, MCP-first and CLI-fallback paths, explicit-human-authorization rule, write/readback/
   schema/scoped-commit discipline, concurrent-work protection, and prohibited autonomous actions.
2. Add a runtime-neutral canonical `quay-task-operator` Skill and adapt the canonical
   `quay-directive` Skill so Codex can explicitly invoke them without copying task lifecycle policy.
   Expose them under `.agents/skills/`; use symlinks or equivalently mechanical single-source
   packaging, and enforce semantic identity with the Claude-facing surface.
3. Add the smallest trusted-project `.codex/config.toml` that registers the existing Quay stdio MCP
   server. Do not set repository model, reasoning, sandbox, approval, hook, automation, or telemetry
   defaults in this stage. Verify the exact configuration against the implementing Codex version
   with strict-config behavior rather than copying proposal syntax blindly.
4. Specify and test the operator transaction: task read and capability check; explicit human
   authorization; before snapshot and semantic diff; `expectedStatus` where applicable; immediate
   freshness re-read; MCP write; MCP readback; task schema check; CLI readback; scoped Git diff and
   commit. A conflict or unrelated dirty-file overlap fails closed.
5. Add static discovery/config/drift tests and negative tests for missing/untrusted project config,
   unavailable Quay MCP with working CLI fallback, stale `expectedStatus`, schema failure, unrelated
   dirty changes, and attempts to exercise prohibited lifecycle authority.
6. Run a new Codex session that loads the checked-in surfaces and, under explicit human direction,
   performs one meaningful edit to a real task and creates one genuinely useful task/directive.
   Retain provider-qualified task ids, before/after hashes or semantic diffs, MCP and CLI readbacks,
   schema results, the refused CAS probe, and scoped commit SHAs in a machine-checkable milestone
   evidence record.
7. Obtain a fresh-context adversarial audit of authority boundaries, single-source packaging,
   configuration scope, conflict honesty, real-task value, and the evidence record before closure.

## Definition of Done

Standard `experiments/quay-perpetual-stream/inherited-core.md` clauses apply. Files, symlinks,
configuration, Skills, scripts, fixtures, and green unit tests are necessary but insufficient.
This directive is done only when all of the following are true:

- [ ] A new trusted-repository Codex session—not the implementing session merely inspecting its own
  files—loads `AGENTS.md`, discovers and invokes the two repository Skills, and operates the real
  Quay MCP plus the independently tested CLI fallback.
- [ ] One genuinely useful real task is created and one existing real task is semantically edited
  under explicit human authorization, with durable MCP/readback/schema/CLI/scoped-commit evidence;
  no demo, fixture, or self-congratulatory probe substitutes for either real object.
- [ ] The rejected stale-CAS path, unavailable-MCP fallback, single-source Skill packaging, and
  prohibited-authority boundaries are independently audited with zero unresolved findings.
- [ ] The real evidence shows Codex did not tick AC/DoD, complete a task, SELECT/execute a milestone,
  launch a worker, merge, ABSORB, schedule itself, or use session evidence without explicit scope.
- [ ] `extra.dirStatus` remains `pending` until that real landing and audit exist. If the scope cannot
  complete as one milestone, DIR-026 SPLIT-OR-COMMIT creates completable child tasks; missing Stage 1
  behavior is not deferred in prose and the parent is not marked done early.

## Human verification when this workspace marks this done

1. Start Codex in a fresh trusted checkout and ask it to identify its loaded project instruction
   and Skill sources. Are root `AGENTS.md`, `$quay-task-operator`, and `$quay-directive` present and

2. Inspect `codex mcp list`: is Quay project-scoped and enabled without unrelated repository-wide
   model, permission, hook, telemetry, automation, or meta-cc settings?
3. Inspect the two real tasks and their commits. Were they valuable independently of this proof,
   explicitly authorized, read back through MCP and CLI, schema-valid, and isolated from unrelated
   work?
4. Replay the stale `expectedStatus` test and disable Quay MCP. Does CAS refuse the write, and does
   ordinary CLI task operation continue without granting broader authority?
5. Look for any claim that read/re-read provides atomic body CAS, or that Stage 1 proves session
   evidence, milestone execution, Host Adapter, hooks, scheduled tasks, or continuous operation.
   Any such claim means this directive is not done.

  transcript access;
- Codex outer/iteration workers, custom agents, worktree execution, structured worker results,
  Host Adapter/control-plane operations, leases, recovery, or perpetual supervision;
- hooks, OTel, scheduled tasks, unattended mutation, plugin-marketplace publication, or automatic
  tool discovery/installation;
- a new Quay transcript parser or widening Quay Core/Provider ABI into an observation tool bus;
- full atomic same-status body-write CAS or an `expectedUpdatedAt` protocol change unless separately
  proposed and selected.
