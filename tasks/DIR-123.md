**type:** execution

## Proposal

Give `execute-milestone.js`'s Build phase a real, per-milestone `git worktree` — created before
Build starts, real edits/tests/commits happen there, and Land does a real merge-back plus cleanup
— so that two `execute-milestone` dispatches for file-disjoint tasks can run genuinely
concurrently, with Land (not the whole pipeline) as the sole serialization point against the
shared checkout.

Introduce this the same way DIR-117 introduced its `Prepared` phase: **opt-in first, prove it on
real dispatches, then consider it default.** Add a new arg (e.g. `$a.isolationMode: 'worktree'`)
that, when present, routes Build/Audit/Gate through a created worktree
(`milestones/M<NN>/worktrees/iteration-0`, real `git worktree add`) and Land through a real
`git worktree merge`-equivalent (fetch the worktree branch's commits into the primary checkout,
then `git worktree remove` + branch cleanup). Omitted param = current direct-on-shared-tree
behavior, unchanged (back-compat, matches every dispatch through M191). This directive does not
force a permanent default switch — that is a later, separately-earned decision once real
concurrent dispatches have proven the mechanism.

Audit must operate against the SAME worktree Build used (not the primary checkout) — the worktree
path is threaded through Build → Audit → Gate, and only Land touches the shared tree. This is a
real architectural change to the control plane, not a point-fix: the same weight class as
DIR-119-B's arbitrary-width execution work.

## Finding

Promoted from `gap-execute-milestone-no-worktree-isolation` (filed and then closed-by-promotion the
same day, 2026-07-28) — real evidence, unchanged from that task's own Finding:

Real code read of `.claude/workflows/execute-milestone.js`'s Build-phase prompt: it instructs the
dispatched agent to "Edit/create files as needed... Run tests... COMMIT all changes" directly, with
zero `git worktree add` step — confirmed this is the actual, current behavior for M187 through
M191 (each explicitly noted in its own Execution record as "direct-to-master build, no separate
worktree"). The Land-phase prompt still contains "MERGE the iteration worktree into master" text,
which is vestigial for the now-default no-worktree path (it would only apply if a Build agent
independently chose to create its own worktree, which none of M187-M191 did).

This directly contradicted `CLAUDE.md`'s own prior documentation ("Per-milestone work happens in
`milestones/M<NN>/worktrees/iteration-{0,1}` worktrees merged into `master` at ABSORB") — already
corrected in place (`adb0f26`). Practical consequence: pairwise task-level `## Touches`
orthogonality (`touches-orthogonality-check.ts`) proves task-content safety but says nothing about
working-tree safety — two `execute-milestone` dispatches, even for fully disjoint tasks, cannot run
concurrently today without a real risk of one's uncommitted Build-phase state colliding with the
other's, because both operate directly on the same shared working tree with no isolation boundary.

**Why this matters now, concretely**: the real backlog already contains multiple mutually-disjoint,
ready-to-dispatch candidates (`DIR-120` Phase 2/3, `DIR-121` Codex Stage 1,
`gap-touches-orthogonality-symlink-isdirect-mismatch`, `gap-drain-dispose-body-corruption`) that
today must be strictly serialized purely because of this gap, at real wall-clock cost (each
milestone this session has taken 30-90 minutes).

Related but narrower: DIR-119-D's own design (composite phase-DAG Build) already plans
`isolation:'worktree'` for phases whose Touches overlap WITHIN a single composite dispatch — a
different, narrower mechanism (intra-composite phase isolation) that does not address whether two
SEPARATE, top-level `execute-milestone` milestones can run concurrently. This directive is the
broader mechanism; DIR-119-D's usage, once both land, should reduce to a special case of it rather
than remaining a second, parallel worktree-management implementation.

## Requested action

1. Add an opt-in `$a.isolationMode: 'worktree'` argument. When present: Build phase creates a real
   worktree (`git worktree add milestones/M<NM>/worktrees/iteration-0 -b <branch>`), threads its
   absolute path through to Audit and Gate (which run their checks against that path, not the
   primary checkout), and does all real editing/testing/committing there.
2. Land phase, under `isolationMode:'worktree'`: fetches/merges the worktree branch's commits into
   the primary checkout for real (not asserted), runs the same mechanical gates it already runs
   today, then `git worktree remove` + deletes the now-merged branch. Land remains the sole point
   that touches the shared checkout under this mode.
3. When `isolationMode` is omitted: byte-for-behavior-identical to current M191 behavior (direct
   on the shared tree) — golden-replay proof required, not asserted.
4. Fix Land's stale "MERGE the iteration worktree into master" prompt text to accurately describe
   BOTH paths (worktree-mode real merge vs. no-isolation-mode no-op), rather than describing an
   action that was never real for the current default path.
5. Real concurrent-dispatch proof: dispatch two real, file-disjoint milestones (candidates already
   named in Finding above) with `isolationMode:'worktree'`, launched close enough in time that
   their Build phases genuinely overlap — confirmed via real journal timestamps, not assumed from
   sequential dispatch. Both must Land correctly with zero shared-tree corruption.
6. Add fixtures/negative controls: a fixture where two worktree-isolated Builds touch the SAME file
   (deliberately, to test conflict handling — should this be rejected pre-dispatch by the
   orthogonality check, or handled as a real merge conflict at Land? — decide and implement
   explicitly, do not leave undefined) and a fixture proving Audit genuinely reads from the
   worktree path, not the primary checkout (e.g., a file that differs between the two).
7. Reuse `touches-orthogonality-check.ts` for the pre-dispatch safety decision (which candidates
   are eligible for concurrent worktree dispatch) rather than inventing a second eligibility
   checker — this directive is about EXECUTION isolation, not re-deciding WHICH tasks may batch,
   which `concurrent-batch-scheduler.ts`/DIR-057/DIR-116 already own.
