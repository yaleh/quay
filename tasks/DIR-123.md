**type:** execution

## Proposal

Give `execute-milestone.js`'s Build phase a real, per-milestone `git worktree` — created before
Build starts, real edits/tests/commits happen there, and Land does a real merge-back plus cleanup
on the serial path — so that two concurrent `execute-milestone` runs for file-disjoint tasks can
proceed genuinely in parallel. On the serial path, Land stays the sole phase that mutates the
shared checkout; on the existing `mode:'concurrent'` path, the already-present fan-in machinery
(not this directive) stays the sole merge owner, and worktree mode must compose with it rather than
introduce a second, parallel merge path (detailed below).

Introduce this the same way DIR-117 introduced its `Prepared` phase: **opt-in first, prove it on
real dispatches, then consider it default.** Add a new arg (e.g. `$a.isolationMode: 'worktree'`)
that, when present, threads Build/Audit/Gate through a created worktree
(`milestones/M<NN>/worktrees/iteration-0`, real `git worktree add`) and Land through a real
`git worktree merge`-equivalent (fetch the worktree branch's commits into the primary checkout,
then `git worktree remove` + branch cleanup). Omitted param = current direct-on-shared-tree
behavior, unchanged (back-compat, matches every dispatch through M191). This directive does not
force a permanent default switch — that is a later, separately-earned decision once real
concurrent dispatches have proven the mechanism.

Audit must operate against the SAME worktree Build used (not the primary checkout) — the worktree
path is threaded through Build → Audit → Gate, and only Land touches the shared tree. This is a
real architectural change to the control plane, not a point-fix: the same weight class as
DIR-119-B's arbitrary-width execution work.

Worktree mode is an isolation wrapper around the existing stages, not a replacement for the loop's
concurrent control plane, and its Land step must compose with the production fan-in exactly as the
current code already divides responsibility. In `mode:'concurrent'` today, the per-workflow Land
defers `milestone_counter` and `dashboard.md` writes to the serial fan-in (`serial-fanin-absorb.ts`),
and `OUTER-LOOP.md`'s `concurrent_execute` step g is documented as the SOLE merge owner (workflows
produce committed branches; the fan-in, not any single workflow, performs every merge). Under
worktree mode in concurrent batches, the workflow must therefore leave its created worktree branch
committed and un-merged for the fan-in to merge in `serial-fanin-absorb.ts` plan order — the
per-workflow Land must NOT itself merge the shared tree in concurrent mode, or two serial Lands
racing on merge / `milestone_counter++` / `it0-backlog-regen.ts` would lose a counter increment.
The one place the current text contradicts this — the concurrent Land prompt's stale "MERGE the
iteration worktree into master" line — is the same vestigial text item 4 already fixes, and under
this directive it must be corrected to describe the concurrent split (the workflow commits the
branch; the fan-in merges) rather than a per-workflow merge the surrounding machinery forbids.
Which exact phase is the merge owner under each mode (serial Land vs. concurrent fan-in) is a
falsifiable behavior this directive's evidence must pin, not an open question left to implementation.

Cleanup on the failure paths must be a decided, specified behavior, not an accident of where an
early return happens to exit. Today `execute-milestone.js` has three `needs-human` early returns —
Build-fail, Gate-fail, and Audit-REFUTED — and each exits before any worktree or branch cleanup, so
under worktree mode every aborted run would leave its created worktree and branch registered. That
omission has two branch-naming-dependent failure modes the spec must close explicitly: a branch
matching `worktree-branch-hygiene-check.sh`'s `^m[0-9]+-.*iteration-[01]$` pattern and holding a
milestone `.md` absent from `master` (Build commits the iteration report; Audit stages the audit
file into the branch) HARD-BLOCKS every subsequent Gate, while a non-matching name silently
accumulates as an orphan (the repo already carries six aged `wf_*` worktrees never pruned). A
retried aborted milestone would also collide on `git worktree add -b <existing-branch>`. This
directive therefore requires an explicit, implemented failure-path policy — remove-or-retain the
worktree and branch on each `needs-human` exit, and make a retried milestone idempotent against a
leftover branch — decided and documented the same way item 6 demands an explicit decision for the
same-file-conflict case, never left undefined.

Finally, the new argument is not real until the loop's actual production surface for concurrent
execution uses it. The only checked-in production surface for concurrent execution — `OUTER-LOOP.md`'s
`concurrent_execute` step a, the `Workflow({ ..., mode: 'concurrent' })` template the MAIN session
executes — must be updated to pass `isolationMode: 'worktree'` for the concurrent batch, because
that template (not the scheduler's eligibility logic) is what today produces non-isolated runs.
Reusing the scheduler's pre-existing touches-orthogonality import is necessary but not sufficient:
after a green run of this directive's other criteria, the loop must actually go through the isolated
path on a real concurrent cycle, with pasted evidence that a production cycle took the worktree
branch — not merely that the argument exists and the scheduler already imported the eligibility
check. `OUTER-LOOP.md` is therefore a required touched file for this directive, and its
concurrent-execution template is the reachability evidence.

## Finding

Promoted from `gap-execute-milestone-no-worktree-isolation` (filed and then closed-by-promotion the
same day, 2026-07-28) — real evidence, unchanged from that task's own Finding:

Real code read of `.claude/workflows/execute-milestone.js`'s Build-phase prompt: it instructs the
dispatched agent to "Edit/create files as needed... Run tests... COMMIT all changes" directly, with
zero `git worktree add` step — confirmed this is the actual, current behavior for M187 through
M191 (each explicitly noted in its own Execution record as "direct-to-master build, no separate
worktree"). The Land-phase prompt still contains "MERGE the iteration worktree into master" text,
which is vestigial for the now-default no-worktree path (it would only apply if a Build agent
independently chose to create its own worktree, which none of M187-M191 did).

This directly contradicted `CLAUDE.md`'s own prior documentation ("Per-milestone work happens in
`milestones/M<NN>/worktrees/iteration-{0,1}` worktrees merged into `master` at ABSORB") — already
corrected in place (`adb0f26`). Practical consequence: pairwise task-level `## Touches`
orthogonality (`touches-orthogonality-check.ts`) proves task-content safety but says nothing about
working-tree safety — two `execute-milestone` dispatches, even for fully disjoint tasks, cannot run
concurrently today without a real risk of one's uncommitted Build-phase state colliding with the
other's, because both operate directly on the same shared working tree with no isolation boundary.

**Why this matters now, concretely**: the real backlog already contains multiple mutually-disjoint,
ready-to-dispatch candidates (`DIR-119-D2` + `DIR-119-D3` Build phases are genuinely file-disjoint
— `composite-build.ts` vs `composite-audit.ts` — and could overlap if worktree isolation existed;
`DIR-120` Phase 2/3; `DIR-121` Codex Stage 1; `gap-touches-orthogonality-symlink-isdirect-mismatch`;
`gap-drain-dispose-body-corruption`) that today must be strictly serialized purely because of this
gap, at real wall-clock cost (each milestone this session has taken 30-90 minutes).

Related but narrower: DIR-119-D's own design (composite phase-DAG Build) already plans
`isolation:'worktree'` for phases whose Touches overlap WITHIN a single composite dispatch — a
different, narrower mechanism (intra-composite phase isolation) that does not address whether two
SEPARATE, top-level `execute-milestone` milestones can run concurrently. This directive is the
broader mechanism; DIR-119-D's usage, once both land, should reduce to a special case of it rather
than remaining a second, parallel worktree-management implementation.

**Code-level dependency check (2026-07-31):** DIR-123 has zero code dependencies on DIR-122,

## Requested action

1. Add an opt-in `$a.isolationMode: 'worktree'` argument. When present: Build phase creates a real
   worktree (`git worktree add milestones/M<NM>/worktrees/iteration-0 -b <branch>`), threads its
   absolute path through to Audit and Gate (which run their checks against that path, not the
   primary checkout), and does all real editing/testing/committing there.
2. Land phase, under `isolationMode:'worktree'`: fetches/merges the worktree branch's commits into
   the primary checkout for real (not asserted), runs the same mechanical gates it already runs
   today, then `git worktree remove` + deletes the now-merged branch. Land remains the sole point
   that touches the shared checkout under this mode.
3. When `isolationMode` is omitted: byte-for-behavior-identical to current M191 behavior (direct
   on the shared tree) — golden-replay proof required, not asserted.
4. Fix Land's stale "MERGE the iteration worktree into master" prompt text to accurately describe
   BOTH paths (worktree-mode real merge vs. no-isolation-mode no-op), rather than describing an
   action that was never real for the current default path.
5. Real concurrent-dispatch proof: dispatch two real, file-disjoint milestones with
   `isolationMode:'worktree'`, launched close enough in time that their Build phases genuinely
   overlap — confirmed via real journal timestamps, not assumed from sequential dispatch. Both must
   Land correctly with zero shared-tree corruption. Natural candidates: DIR-119-D2 + DIR-119-D3
   (genuinely file-disjoint — `composite-build.ts` vs `composite-audit.ts` — and on the critical
   path, so the concurrency gain is immediately realized).
6. Add fixtures/negative controls: a fixture where two worktree-isolated Builds touch the SAME file
   (deliberately, to test conflict handling — should this be rejected pre-dispatch by the
   orthogonality check, or handled as a real merge conflict at Land? — decide and implement
   explicitly, do not leave undefined) and a fixture proving Audit genuinely reads from the
   worktree path, not the primary checkout (e.g. a file that differs between the two).
7. Reuse `touches-orthogonality-check.ts` for the pre-dispatch safety decision (which candidates
   are eligible for concurrent worktree dispatch) rather than inventing a second eligibility
   checker — this directive is about EXECUTION isolation, not re-deciding WHICH tasks may batch,
   which `concurrent-batch-scheduler.ts`/DIR-057/DIR-116 already own.
8. Implement and prove the failure-path cleanup policy: for each of the three `needs-human` early
   returns (Build-fail, Gate-fail, Audit-REFUTED), an aborted `isolationMode:'worktree'` milestone
   must leave its created worktree and branch in the explicit remove-or-retain state the Proposal's
   failure-path paragraph requires (decided and documented, never undefined), and a re-dispatch of
   the same milestone must be idempotent against the leftover branch — no `git worktree add -b
   <existing-branch>` collision, no Gate hard-block from a branch matching
   `worktree-branch-hygiene-check.sh`'s `^m[0-9]+-.*iteration-[01]$` holding a milestone `.md`
   absent from `master`, and no silent orphan accumulation alongside the aged `wf_*` worktrees.
