**type:** execution

## Proposal

Give `execute-milestone.js`'s Build phase a real, per-milestone `git worktree` — created before
Build starts, real edits/tests/commits happen there, and Land does a real merge-back plus cleanup
— so that two `execute-milestone` dispatches for file-disjoint tasks can run genuinely
concurrently, with Land (not the whole pipeline) as the sole serialization point against the
shared checkout.

Introduce this the same way DIR-117 introduced its `Prepared` phase: **opt-in first, prove it on
real dispatches, then consider it default.** Add a new arg (e.g. `$a.isolationMode: 'worktree'`)
that, when present, routes Build/Audit/Gate through a created worktree
(`milestones/M<NN>/worktrees/iteration-0`, real `git worktree add`) and Land through a real
`git worktree merge`-equivalent (fetch the worktree branch's commits into the primary checkout,
then `git worktree remove` + branch cleanup). Omitted param = current direct-on-shared-tree
behavior, unchanged (back-compat, matches every dispatch through M191). This directive does not
force a permanent default switch — that is a later, separately-earned decision once real
concurrent dispatches have proven the mechanism.

Audit must operate against the SAME worktree Build used (not the primary checkout) — the worktree
path is threaded through Build → Audit → Gate, and only Land touches the shared tree. This is a
real architectural change to the control plane, not a point-fix: the same weight class as
DIR-119-B's arbitrary-width execution work.

## Implementation note (DIR-123 implementing subagent, 2026-07-31)

**Argument plumbing + worktree lifecycle (what was built).** `execute-milestone.js` (both mirrors)
computes `_isolationPlan` from `$a.isolationMode` right after `_milestone` is derived — an inline mirror
of `milestone-worktree.ts`'s pure `computeIsolationPlan`/`milestoneRootRel` (the workflow DSL has no
`import`; same documented mirror pattern as `composite-args.ts`), pinned against the `.ts` single-source
and against `gate-script-lib.sh`'s `gate_resolve_milestone_root` by tests so it cannot drift.
`isolationMode:'worktree'` + a numeric milestone → `_useWorktree=true`; anything else → legacy. A
requested-but-unusable isolation (unknown non-empty mode, or no numeric milestone) **fails closed at
Verify** (never a silent fall-back to the shared tree). Under `_useWorktree`: a `worktree-create` agent
runs the REAL `milestone-worktree.ts --add` (real `git worktree add <root>/worktrees/iteration-0 -b
milestone/M<NN>/iteration-0`, fail-closed on a pre-existing path/branch) BEFORE Build; the worktree's
repo-relative path is threaded into the Build, Audit, and every Gate prompt; Land (sole shared-checkout
mutator) acquires the single-flight **Land lock**, runs the REAL `--merge` (`git merge --no-ff`),
`--remove` (`git worktree remove` + `git branch -d`), and releases the lock. `milestone-worktree.ts`
performs all real git ops via `execFileSync`; the workflow emits the commands, the dispatched agents run
them. Omitted `isolationMode` → byte-for-behavior legacy (golden-replay-proven; only Land's step-1 text
differs, the AC #6 fix).

**Same-file-conflict decision (explicit).** REJECT PRE-DISPATCH via `touches-orthogonality-check.ts`'s
`checkTouchesPair` (the PRODUCTION disjointness verdict, reused through `concurrent-batch-scheduler.ts`'s
existing `assembleBatch`; no second checker. `worktreeDispatchEligibility`, added here, is a thin
TEST-FACING wrapper over `assembleBatch` that tags same-file conflicts — no separate production callers).
Overlapping `## Touches` → the later candidate
is deferred to a serial round, tagged `sameFileConflict:true`. Land's real-merge-conflict path
(`mergeWorktree` → `outcome:"conflict"` → auto-`git merge --abort`, primary left clean, branch kept,
needs-human) is the DEFINED backstop for an undeclared touch, never the primary mechanism, never a
blanket --ours/--theirs.

**Concurrency-obstacle analysis (reviewer brief).**
- *(a) Concurrent Land serialization* — HANDLED: Land acquires a GLOBAL single-flight Land lock
  (`.quay/land-locks/shared-checkout.lock`, the same atomic-`wx` + stale-reclaim + owner-fenced-release +
  audit-trail primitive as `prepare-admission-check.ts`) before any shared-checkout git mutation and
  releases it after; two Lands cannot merge/remove concurrently. Tested (acquire/contention/fenced-
  release/stale-reclaim/missing-session-id fail-closed).
- *(b) Worktree path collisions* — HANDLED by construction: the path/branch are derived deterministically
  from the milestone NUMBER (`milestones/M<NN>/worktrees/iteration-0` / `milestone/M<NN>/iteration-0`),
  so two DIFFERENT milestones can never share a path/branch; a same-milestone double-dispatch is a logic
  error the `--add` step fails closed on (`worktree-path-exists`/`branch-exists`), never a silent reuse.
- *(c) Admission lease (`.quay/prepare-leases/`) + epoch/lock under concurrent dispatch* — OUT OF SCOPE,
  genuinely: those belong to `prepare-milestone.js` (upstream of execute). The prepare lease is already
  PER-TASK (keyed on `taskId`, atomic `wx`), so two concurrent dispatches for DIFFERENT tasks hold
  disjoint leases by construction; execute-milestone does not read or write them. No change needed here.
- *(d) Shared mutable task-store/dashboard state under concurrent Builds* — HANDLED by existing
  composition: file-disjoint tasks write disjoint `tasks/*.md`; the dashboard/counter/v-meta-ledger are
  exactly `concurrent-batch-scheduler.ts`'s `SHARED_STATE_PATHS`, and the existing `$a.mode==='concurrent'`
  Land path already defers those writes to the serial fan-in. Worktree isolation composes with (does not
  bypass) that path — a concurrent+worktree Land still defers dashboard/counter and still runs the
  post-Land whole-store split-or-commit scan.

**Remaining deliberate out-of-scope concurrency obstacles (for reviewer confirmation).**
1. The real two-concurrent-milestone-journal proof (AC #1 / DoD #2) — needs real future dispatches on
   `master`; not producible in an isolated subagent worktree, not fabricated.
2. **ACCEPTED TRADEOFF (review C4 — deliberately NOT fixed, matches the reviewed sibling exactly):** the
   `rmSync` + retry-`wx` stale reclaim in `acquireLandLock` carries the SAME two residual, negligible
   microsecond windows as `proposal-convergence.ts`'s hardened `_acquireEpochLock` (the precedent it
   mirrors): (a) a loser's `rmSync` could, in a sub-millisecond interleaving, delete the winner's
   just-created fresh lock before the winner's `wx` returns — both then retry and the bounded loop
   re-converges to a single holder (never two simultaneous holders past the loop, never an unlocked
   proceed); and (b) a Land phase exceeding the 30-minute staleness window could be reclaimed mid-flight
   (no mid-Land heartbeat/renew; a crashed Land is still recoverable, never a permanent lockout). Both
   are identical to the sibling's accepted design and negligible operational risk for an opt-in,
   single-host, human-supervised loop. Diverging here would needlessly depart from the established,
   independently-reviewed pattern; a fencing-token / renew-at-phase-boundary heartbeat is the later
   hardening if real Lands ever approach these bounds. (Also documented in a comment at the reclaim site
   in `milestone-worktree.ts`.)
3. The Land lock is a LOCAL single-host mutex (matches CLAUDE.md's DIR-027 single-shared-working-tree-on-
   `master` assumption and `prepare-admission-check.ts`'s own stated non-distributed posture), not a
   distributed lock.

- **OBSTACLE 2 (concurrent+worktree contradicted the fan-in's SOLE-merge-owner invariant) — FIXED.**
  DECISION: **the fan-in is the single owner of merges for `mode:'concurrent'` + worktree** (the cleaner
  option, consistent with DIR-075/M142's "defer shared-state writes to the fan-in"). The per-workflow
  concurrent Land now merges NOTHING, removes nothing, takes no lock, and does no CAPTURE-commit on the
  primary — it leaves the worktree branch committed and returns `buildBranch` + `worktreeRel` (+ the
  read-only `touchedFiles` and the deferred `dashboardEntry`). `OUTER-LOOP.md` step g is updated so the
  fan-in, for each survivor UNDER the Land lock, runs `--merge` (`git merge --no-ff buildBranch`) →
  CAPTURE (git add evidence + commit on the primary) → `--remove` (worktree remove + branch -d) →
  `--land-lock-release`. This moves CAPTURE's shared-checkout commit UNDER the lock (fixing the
  concurrent-CAPTURE index race) and keeps step g the literal SOLE merge owner. Step a now passes
  `isolationMode:'worktree'` for every concurrent dispatch. Test: "OBSTACLE 2" asserts the
  concurrent+worktree Land runs no merge/remove/lock, returns `buildBranch`, leaves the primary
  untouched, and leaves the worktree+branch in place for the fan-in.
- **OBSTACLE 3 (crashed dispatch stranded the worktree forever) — FIXED.** Added an idempotent
  `milestone-worktree.ts --clean-stale`: it removes a stranded same-milestone worktree+branch ONLY when
  that branch has ZERO commits ahead of master (unambiguously a crashed attempt that built nothing real —
  safe because the path/branch are milestone-scoped); a branch WITH commits ahead → `has-commits` (fail
  closed, real work never discarded). The worktree-create step now runs `--add`; on a
  `worktree-path-exists`/`branch-exists` collision it runs `--clean-stale`; if `cleaned` it retries
  `--add`; if `has-commits` it fails closed to needs-human. Tests: module `cleanStaleWorktree` test
  (cleans 0-ahead, refuses real work) + workflow "OBSTACLE 3" recovery (0-ahead auto-recovers) and
  fail-closed (real commits → needs-human, work preserved).
- **OBSTACLE 4 (non-atomic lock reclaim TOCTOU + scheduling-luck test) — FIXED.** (a) `acquireLandLock`'s
  reclaim now mirrors the just-hardened sibling `proposal-convergence.ts`'s `_acquireEpochLock`: the
  grant is ALWAYS the atomic `wx`-create; a stale lock is reclaimed via `fs.rmSync` + RETRY the atomic
  `wx` in a bounded loop (two racing reclaimers resolve to exactly one winner), with the file's own
  mtime as a corruption-proof staleness clock — never a plain read-then-overwrite. (b) Added
  `QUAY_LAND_LOCK_TEST_HOLD_MS` (env-gated hold-delay after acquiring, mirroring the sibling's
  `QUAY_EPOCH_LOCK_TEST_HOLD_MS`) and a deterministic two-process test: a holder subprocess holds the
  lock across a widened critical section and a concurrent acquirer is DETERMINISTICALLY refused — real
  mutual exclusion, not the scheduling luck the sibling learned is unreliable (~57% on a real machine).
- **OBSTACLE 5 (default vs worktree dispatches not mutually serialized) — documented hard precondition +
  mechanical backstops.** A truly mechanical in-flight-legacy-detector is NOT feasible without modifying
  the legacy Build path (which would break the golden-replay legacy contract). So: (1) `OUTER-LOOP.md`
  step a now ALWAYS passes `isolationMode:'worktree'` for concurrent batches — a concurrent batch is
  worktree-isolated BY CONSTRUCTION, so a no-isolation dispatch can never be admitted into one; (2)
  the production eligibility mechanism (`assembleBatch` → `checkTouchesPair`, surfaced for this concern
  via the test-facing `worktreeDispatchEligibility` wrapper) only admits touches-disjoint candidates;
  (3) the Land lock serializes all worktree Lands. HARD PRECONDITION
  (documented here + CLAUDE.md): the default (no-isolation) path takes NO Land lock and commits directly
  to master in Build, so a no-isolation dispatch must NEVER overlap a concurrent batch against the same
  checkout — enforced by the driver only ever using worktree mode for concurrent batches (plus DIR-027
  one-driver discipline).
