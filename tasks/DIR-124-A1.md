## Proposal (original, preserved for context)

Define one canonical, minimal, append-only stage-event schema and observational emission at the 8
workflow boundaries between `prepare-milestone.js` and `execute-milestone.js` -- without changing
dispatch order, concurrency, lifecycle results, or write authority.

First child of the DIR-124-A split (mechanism M1, `split-multi-mechanism` finding). No dependencies.
**This proposal is now implemented across two children: [DIR-124-A1a](DIR-124-A1a.md) (M248, schema
module) and [DIR-124-A1b](DIR-124-A1b.md) (M249, emission instrumentation).**

### Problem framing (grounded in current repository state, 2026-08-01)

The two milestone-workflow files (`execute-milestone.js` at 1257 lines, `prepare-milestone.js` at
1558 lines) drive the full milestone lifecycle from SELECT through Land. Between them they touch 16
phase boundaries (8 in `execute-milestone.js` at lines 66/234/389/719/817/919/961; 8 in
`prepare-milestone.js` at lines 164/628/660/662/666/704/746/1305/1354/1385/1440), each demarcated
by a DSL `phase('Name')` call. Byte-identical mirrors exist at `plugin/workflows/` (confirmed by
`diff` exit 0 at HEAD).

Yet neither file emits any structured event record at these boundaries. The workflow DSL's
`meta.phases[]` metadata block is declaration-only -- it describes phases to the runtime harness
but produces no runtime event trail. The runner's own `log()` calls are unstructured diagnostic
strings. Confirmed by grep: zero hits for `workflow-event-schema`, `recordStageEvent`, or
`stage-event` outside DIR-124 task bodies. The `.workflow-events/` directory does not exist.

Existing telemetry is partial and purpose-specific:
- **M207 `_phaseTimings`** in `prepare-milestone.js` accumulates per-boundary timing spans, but
  it is prepare-workflow-only, agent-mediated (clock values from lease-renewal CLI responses, not
  JS-emitted `Date.now()`), tied to the single-flight lease renewal mechanism, and carries only a
  partial field set (phase name, round, startedAtMs, endedAtMs). It does not cover
  `execute-milestone.js` at all.
- **`proposal-convergence.ts`** writes committed telemetry to `milestones/prepare-telemetry/`
  (git-committed JSON). Its schema serves cross-generation resume decisions, not stage lifecycle
  observability.
- **Gate events** at `.quay/gate-events.jsonl` (gitignored) serve the gate engine's immutable
  append-only log -- a different purpose, different schema, different storage path.

Without a canonical stage-event schema and per-boundary emission, every downstream consumer (A2's
golden replay corpus, A5's baseline metrics, DIR-124-B's stage scheduler, DIR-124-C's pipeline
reorder, DIR-124-E's resource-aware scheduling) must invent its own format, parse unstructured
`log()` output, or reconstruct timelines from prose. What the workflow actually did, when, in what
order, against what state, and with what result is observable only through agent self-reported
structured-output fields and human-eye-inspected `log()` strings.

The specific difficulty that makes this urgent is the **Prepare admission boundary** (E1):
`prepare-milestone.js` runs `prepare-admission-check.ts --acquire` to obtain an atomic filesystem
lease via `writeFileSync 'wx'` BEFORE any content agent is dispatched. This means: (a) the
admission boundary HAS no agent to emit through, so an agent-emitted design would miss it;
(b) the admission boundary is the natural place to record the fencing token and the
`queuedAtMs -> startedAtMs` timing before any LLM-turn cost is spent.

### Chosen mechanism

A single canonical `workflow-event-schema.mjs` module (byte-identical mirror at
`plugin/scripts/workflow-event-schema.mjs`) as the **first-class home** of the v1 stage-event
schema, exporting a `recordStageEvent({...})` helper invoked by the workflow JS itself at all 8
boundaries, following the established `node --experimental-strip-types <script> --emit-event
'<json>'` CLI dispatch pattern already used by `composite-preflight.ts`, `composite-reconcile.ts`,
`milestone-worktree.ts`, and `prepare-admission-check.ts` invocations throughout both workflow
files. This is a NEW observability layer, not a replacement for or extension of existing
`_phaseTimings` / `proposal-convergence.ts` / `gate-events.jsonl` -- those serve different
purposes with different schemas, storage paths, and commit policies. No unification, no migration,
no dual-write.

**WIRING-CLAIM (A1-SCHEMA-HOME):** `experiments/quay-perpetual-stream/scripts/workflow-event-schema.mjs`
is the single canonical home of the stage-event schema v1 -- the schema is never embedded in an
emission script or duplicated in workflow files.

**WIRING-CLAIM (A1-MIRROR):** Both mirror pairs are byte-identically instrumented:
- `workflow-event-schema.mjs` at `experiments/` and `plugin/` are byte-identical.
- `execute-milestone.js` at `.claude/workflows/` and `plugin/workflows/` (already byte-identical
  at HEAD) gain identical `_emitStageEvent` helper and `--emit-event` dispatch snippets.
- `prepare-milestone.js` at `.claude/workflows/` and `plugin/workflows/` (already byte-identical
  at HEAD) gain identical snippets.
- The existing inline-mirror test pattern (which pins `_normalizeExecuteArgsInline` and
  `_isolationPlan` against their `.ts` single-sources) is extended to cover the `_emitStageEvent`
  dispatch wrapper and call-site parity. Mirror-parity `diff` checks pass at Land.

#### Schema shape (v1)

Each event object carries:

| Field | Type | Description |
|---|---|---|
| `schemaVersion` | `"1"` | Explicit version marker for DIR-124-B `migrateDir124AEvent(event)` adapter |
| `runId` | string | Run identifier: `M<NN>` for execute stages, `prepare-M<NN>` for prepare Admission; timestamp fallback if extraction fails |
| `candidateId` | string | The `M${_milestone}-${_primaryTaskId}` candidate identifier |
| `taskId` | string | The primary task id (for single-task; the lead for composite) |
| `stage` | string | One of the 8 boundary names (see below) |
| `stageIndex` | number | 0-based ordinal within this run's sequence |
| `eventKind` | `"start"` \| `"end"` | Whether this is the entry or exit of the stage |
| `attempt` | number | Attempt ordinal (0-based; incremented on retry) |
| `timing` | object | `{queuedAtMs, startedAtMs, endedAtMs}` -- wall-clock timestamps (`endedAtMs` null on start events) |
| `agentLabel` | string | The `label` field of the agent dispatch for this stage (or `"workflow-runner"` for the admission pre-agent boundary) |
| `executionCwd` | string | Working directory at stage entry |
| `worktreePath` | string\|null | Populated from `_isolationPlan.worktreeRel` under `isolationMode:'worktree'`; null otherwise |
| `commandIdentity` | string\|null | The `node --experimental-strip-types <script> <flags>` command invoked, or agent prompt label |
| `baseCommit` | string\|null | Git commit SHA at stage entry |
| `candidateCommit` | string\|null | Git commit SHA at stage exit (populated by Build/Land) |
| `outcome` | `"done"` \| `"needs-human"` \| `"skipped"` \| `"error"` \| null | null for `start` events; populated for `end` events |
| `waitReason` | string\|null | Why the stage waited before starting: `admission-contention` \| `cache-hit` \| `prepared-blocked` \| null |
| `resourceClaim` | string\|null | Lease fencing token (populated at E1 admission; null elsewhere) |
| `observedWrites` | string[] | File paths written during this stage (from `git diff --name-only` post-stage vs pre-stage) |
| `isolationMode` | `"worktree"` \| null | Whether worktree isolation was active (from `_isolationPlan`) |
| `dispatchMode` | `"serial"` \| `"concurrent"` \| null | Dispatch mode for execute stages; null for prepare stages |
| `observedDurationMs` | number\|null | Wall-clock stage duration (end event only; `endedAtMs - startedAtMs`) |
| `errorDetail` | string\|null | Error message on outcome `"error"`; null otherwise |

The schema module exports `SCHEMA_VERSION = "1"`, the `StageEvent` type (JSDoc-annotated), a
`validateEvent(event)` structural validator (fail-soft -- logs to stderr, never throws), a
`recordStageEvent(event)` function that serializes + validates + appends one JSON line to the
per-run event log, and a `--emit-event '<json>'` CLI mode (via `process.argv` parsing) invoked
by workflow agent calls.

#### Emission mechanism

**WIRING-CLAIM (A1-DISPATCH-PATTERN):** The workflow DSL has no `import` capability (documented
constraint at `execute-milestone.js` lines 23-25). The schema module is invoked via
`node --experimental-strip-types` CLI calls dispatched through the workflow's existing `agent()`
primitive, following the SAME pattern used by `composite-preflight.ts` (line ~503),
`milestone-worktree.ts` (line ~398), `composite-reconcile.ts` (line ~886),
`prepare-admission-check.ts` (line ~171), and `proposal-convergence.ts`
(`_convergenceAgentCall`). This is the established, tested, documented mechanism for
workflow-to-TypeScript invocation.

Each workflow file gains a single inline helper function (following the `_normalizeExecuteArgsInline`
pattern at `execute-milestone.js` lines 29-46 and the `_isolationPlan` inline mirror at lines
96-100):

```js
async function _emitStageEvent(eventObj) {
  const json = JSON.stringify(eventObj);
  // Fire-and-forget -- result is never parsed or branched on.
  // Follows the exact _convergenceAgentCall shape (M203/DIR-126-D).
  await agent(
    `Run exactly this shell command and report its stdout verbatim:\\nnode --no-warnings --experimental-strip-types experiments/quay-perpetual-stream/scripts/workflow-event-schema.mjs --emit-event '${json.replace(/'/g, "'\\\\''")}'\\nDo not paraphrase or reformat the command's stdout. Return {raw: <the exact stdout text, or null if the command produced no output at all>}.`,
    { label: `emit-event-${eventObj.stage}-${eventObj.eventKind}`, phase: eventObj.stage,
      schema: { type: 'object', properties: { raw: { type: ['string', 'null'] } } } }
  );
  // No return-value inspection. No branching. No coupling to dispatch outcome.
}
```

The label prefix `emit-event-<stage>-<kind>` is a naming convention that is never referenced by
any scheduling, routing, or gating logic -- it exists only for diagnostic visibility in the
workflow journal.

**WIRING-CLAIM (A1-FIRE-AND-FORGET):** The per-event agent dispatch is fire-and-forget -- its
result is never parsed, branched on, or fed into any scheduling or gating decision. This is the
SAME pattern `_convergenceAgentCall` already uses for `--record-attempt` (M203/DIR-126-D):
"telemetry is additive, its own result is never inspected/branched on, and the caller's existing
return value/shape is byte-identical either way."

The `--emit-event` CLI mode on `workflow-event-schema.mjs`:
1. Parses the event JSON from the CLI argument.
2. Validates it structurally against the v1 schema (required fields present, types correct,
   `stage` is one of the 8 known names, `outcome` is one of the 4 known values when present).
3. Resolves the repository root via `QUAY_WORKSPACE_ROOT` env var or CWD walking (finding
   `.quay/` or `.git/`).
4. Creates `experiments/quay-perpetual-stream/.workflow-events/` if it does not exist.
5. Appends one JSON line to `<repoRoot>/experiments/quay-perpetual-stream/.workflow-events/<runId>.jsonl`.
6. On any failure (bad JSON, schema validation fail, missing directory, disk full, permissions):
   writes to `process.stderr` and **never throws** -- the event log is a best-effort
   observability channel, not a gate. Returns exit code 0 always.

#### Event log storage

Per-run event log at `experiments/quay-perpetual-stream/.workflow-events/<runId>.jsonl` (gitignored,

Each boundary's `start` event fires immediately after `phase('Name')` via `_emitStageEvent`. Each
boundary's `end` event fires at the phase's terminal return/continuation site -- the point where
the phase's outcome is determined and the workflow either returns to the caller or advances to the
next phase.

### Key design decisions

**DD1: Workflow-JS-emitted, not agent-emitted.** The workflow DSL's `phase()` call sites and
dispatch helpers are the only places where every boundary is guaranteed to fire. Agent
structured-output emission couples content agents to the observability contract and cannot
guarantee emission: agents crash, return unparseable output, or skip the field entirely. The E1
(Prepare admission) boundary fires BEFORE any content agent is dispatched -- by construction, the
workflow JS is the only emitter that can reach it. This is the split review's blocking
architectural finding. The M207 `_phaseTimings` mechanism already established a limited form of
this approach in prepare-milestone.js.

**DD2: Single canonical schema module, not embedded.** The schema lives in
`workflow-event-schema.mjs` as a first-class module with an explicit `SCHEMA_VERSION = "1"`
export. The split review's `no-schema-home` finding explicitly forbids embedding the schema in
an emission script. DIR-124-B (M236) already references consuming A1's schema as an importable
migration source via `migrateDir124AEvent(event)`. Embedding it in an emission-only file would
force DIR-124-B to copy-paste the schema, reproducing the exact fragmentation this child prevents.

**DD3: Fire-and-forget, never a gate.** `recordStageEvent` is observational-only with zero
return-value coupling to stage dispatch, scheduling, or outcome. A failed emission (agent crash,
JSON parse error, schema validation fail, disk full) is silently dropped. The event log is a
best-effort observability channel, not a gate. The workflow's existing `_convergenceAgentCall`
`--record-attempt` dispatch (M203) is the precedent: telemetry is additive, its return value is
never parsed or branched on. A crashed agent that never reaches phase exit leaves the start event
unmatched -- exactly the observability signal a crash produces.

**DD4: Start+end events per boundary.** Each boundary emits two events: a `start` event (with
`eventKind: 'start'`, `timing.queuedAtMs` and `startedAtMs`) at phase entry, and an `end` event
(with `eventKind: 'end'`, `endedAtMs`, `outcome`, `observedWrites`, `candidateCommit` where
available) at phase exit. The start/end pair captures `queuedAtMs -> startedAtMs` timing (the
admission-contention or Land-lock wait time) as a separate metric from the phase's actual
execution time. A single exit-only event would fold these together, losing the queue delay signal
that DIR-124-E's resource-aware scheduling needs.

**DD5: Versioned schema, forward-migratable.** `SCHEMA_VERSION = "1"` is explicit. DIR-124-B's
plan (M236) references consuming A1's v1 event shape with a `migrateDir124AEvent(event)` adapter
that maps v1 fields into canonical `StageEvent` envelopes. The v1 version marker makes this
migration explicit and testable. No second journal format is introduced.

**DD6: Byte-identical dual mirrors.** Both `experiments/scripts/` and `plugin/scripts/` copies of
the schema module are byte-identical. Both `.claude/workflows/` and `plugin/workflows/` copies of
the workflow files receive identical `_emitStageEvent` instrumentation. The existing mirror-diff
check enforces this at Land. Neither workflow file changes behavior -- both gain only additive
`agent()` calls at the exact same positions.

**DD7: Pre-instrumentation baseline.** A real baseline run's phase sequence, agent count, and
outcome is captured BEFORE the workflow files are edited. Golden replay proves instrumentation
changes no stage order, agent count, outcome, shared-state mutation, or scheduling decision. This
is the same "capture before editing" pattern used in `proposal-convergence.ts`'s M207 checkpoint
mechanism.

**WIRING-CLAIM (A1-PRE-BASELINE):** A pre-instrumentation baseline run is captured BEFORE workflow
edits; golden replay proves instrumentation changes no stage order, agent count, outcome,
shared-state mutation, or scheduling decision.

**DD8: No interaction with existing telemetry.** The A1 event stream does not replace, extend, or
couple with `_phaseTimings` / `proposal-convergence.ts` / `gate-events.jsonl`. Each system serves
a different purpose, writes to a different path, and has a different schema. `recordStageEvent` is
called at workflow-DSL level; `_recordPhaseBoundary` / `--record-generation` are called at
prepare-specific lease-renewal/terminal level. No unification, no migration, no dual-write.

**DD9: Thin dispatch wrapper, not a full import.** The workflow DSL cannot `import` the schema
module -- the `agent()`-dispatched `node --experimental-strip-types` CLI call is the established,
tested, documented mechanism for workflow-to-script invocation, already used for 5+ other modules
in the installed workflow. Introducing an import mechanism would be a larger scope change than
the observability boundary itself.

**DD10: Event log is local observability, not committed artifact.** The `.workflow-events/`
directory is gitignored, following `.quay/gate-events.jsonl`'s pattern. Workflow events are
session-specific diagnostic data, not committed provenance. The git-committed
`milestones/prepare-telemetry/` tree serves committed provenance; these two storage paths are
intentionally separate.

### Defaults and failure behavior

**Normal path:** Each `phase()` call site in both workflow files fires a `start` event, and each
terminal return/continuation site fires an `end` event, producing a complete event pair per phase
per run.

**Emission failures:** `recordStageEvent` is fail-soft. JSON serialization failure, schema
validation failure, missing `.workflow-events/` directory, disk full, permissions error -- all
produce `console.error` to stderr but never throw, never block the phase, never change dispatch
outcome. The per-event `agent()` call is fire-and-forget: a crashed `agent()` call is silently
consumed. The event log is a best-effort observability channel.

**Missing `runId`:** If `_milestone` cannot be extracted from `$a.charterFile` (regex returns no
match), `runId` is derived from `${_milestone}-${_primaryTaskId}-${Date.now()}`. The log filename
is predictable and unique.

**Conditional Reconcile (E7):** When `_isComposite` is false or `$a.compositeManifestFile` is
missing, Reconcile emits start+end with `outcome: "skipped"`. The event stream honestly reflects
that no Reconcile work was performed while preserving event-log completeness (all 8 boundaries
represented).

**Build-Evidence sub-phase (execute-milestone.js line 501):** This is NOT instrumented as a
separate boundary. It fires inside the Build phase, after `phase('Build')` at line 389 and before
the Build end event. It is an internal sub-step of Build, not a cross-workflow boundary.

**Schema version mismatch:** If a future caller passes a v2 event shape to the v1 `--emit-event`
CLI, the `validateEvent` pass fails and the event is dropped (stderr warning). This is safe:
DIR-124-B will introduce v2 as an additive version in the same module.

**Worktree path:** `worktreePath` is populated from `_isolationPlan.worktreeRel` (line ~97) when
`_useWorktree` is true; null otherwise. `isolationMode` is `worktree` or null. No new derivation
-- the existing `_isolationPlan` inline mirror already computes these values.

**Agent dispatch failure:** The `agent()` call throws, caught by the workflow's existing `try/catch`
or the DSL runtime's own error handling. Since the event dispatch is NOT the phase's primary agent
call (it is a separate, additional `agent()` call before/after the phase's real work), a failed
event dispatch never blocks the phase -- the phase's real agent call (Build, Audit, Gate, Land) is
a separate dispatch. The worst case is a missing event pair in the log.

**WIRING-CLAIM (A1-NO-COUPLING):** No phase scheduling decision, lifecycle transition, gate
pass/fail verdict, or dispatch routing reads or branches on any event-emission agent's return
value or the event log's content.

### Compatibility

A1 is **strictly behavior-preserving** with respect to the installed workflow at HEAD (`059b5b16`):

- **Phase order:** unchanged. Every `phase()` call and `return` site remains at the exact same
  line and the exact same control flow. Event-emission `agent()` dispatches are inserted
  IMMEDIATELY AFTER each `phase()` call and BEFORE any phase-specific logic.
- **Agent count:** the event-emission agents are ADDITIONAL dispatches (not replacements), so the
  raw agent count increases by exactly 2 per instrumented boundary (one start, one end). The
  pre-instrumentation baseline captures the before-state count; golden replay proves the delta is
  exactly the event-emission agents and nothing else.
- **Outcome:** unchanged. Every `return {outcome:...}` site produces the same value. No phase's
  outcome decision reads or branches on event-emission results.
- **Shared-state mutations:** unchanged. `recordStageEvent` writes only to the gitignored
  `.workflow-events/` directory -- it does not touch `tasks/`, `dashboard.md`, `milestone_counter`,
  `.quay/`, or the working tree. `git diff` before vs after an instrumented run shows zero delta.
- **Scheduling decisions:** unchanged. No cache-fingerprint, verify-cache, prepared-receipt,
  build-plan, composite-manifest, or gate-vector decision reads event-emission output.
- **Concurrency:** unchanged. The event-emission agents follow the same dispatch model as the
  existing `_convergenceAgentCall` telemetry dispatches -- additive, never awaited-for-decision.
  The Land lock boundary is not affected.
- **Legacy single-task path:** byte-for-behavior unchanged. The `_emitStageEvent` helper is called
  unconditionally at each boundary, same as in the composite path.
- **Mirror parity:** preserved. Both `.claude/workflows/` and `plugin/workflows/` mirrors receive
  identical instrumentation; mirror-diff `diff` exits 0 at Land.

### Risks

**R1: Instrumentation perturbs behavior.** Adding 16 agent-dispatched CLI calls at phase boundaries
could change timing or throughput. Mitigation: the pre-instrumentation baseline + golden replay
proves zero delta in stage order, agent count, outcome, shared-state mutation, or scheduling.
Each dispatch is fire-and-forget with an `emit-event-<boundary>` label that no routing or
scheduling logic references.

**R2: Mirror drift.** A future edit to one workflow mirror that adds/modifies a `--emit-event`
dispatch without updating the other would produce incomplete event streams. Mitigation: the
existing inline-mirror test pattern is extended to cover `_emitStageEvent` dispatch sites; the
mirror-diff gate check already in the Gate phase's parallel array catches byte-level divergence
at Land.

**R3: Schema becomes a second journal format.** The crystallization document warns against adding
a second representation (section 3.5). Mitigation: explicit v1 versioning; DIR-124-B extends via
`migrateDir124AEvent` adapter rather than forking; A5's metrics consume the same stream; no
second journal format is introduced. The A1 event stream and `gate-events.jsonl` have distinct
purposes (workflow observability vs. gate verdicts) and distinct consumers -- this is two
different kinds of data, not two formats for the same data.

**R4: Event log disk growth.** Per-run JSONL files accumulate under `.workflow-events/`.
Mitigation: gitignored (never committed); a single run is small (~16 events x ~600 bytes = ~10KB).
The `cleanup_temp_files` MCP tool handles stale files.

**R5: `runId` collision.** Two concurrent runs of the same milestone could produce the same
derived `runId`. Mitigation: the `M<NN>`/`prepare-M<NN>` pattern per-works them; the outer loop's
dispatch framework provides a unique `runId`; the derived fallback includes `Date.now()` with
millisecond precision. Concurrent dispatches are already serialized at the Land lock boundary.

**R6: Pre-instrumentation baseline capture is missed or incomplete.** If the workflow files are
edited before the baseline run is captured, the zero-delta claim becomes unprovable. Mitigation:
the baseline capture is an explicit, ordered step in the implementation sequence (step 3 in the
task's Requested action) -- it must be completed BEFORE any workflow file edit, and its output is
checked into the milestone directory as deliverable evidence.

### Alternatives considered and rejected

**Alt1: Agent structured-output emission.** Would require content agents to include a `stageEvent`
field in their structured-output schema. Rejected for three reasons: (a) the Prepare admission
boundary (E1) fires before any content agent exists -- no agent to emit through, so E1 would be
unrepresentable; (b) agents can crash, return unparseable JSON, or skip the field entirely --
emission-by-construction is impossible to guarantee; (c) it couples all content agents to the
observability contract, requiring every agent prompt template across both workflows to be
updated and maintained. The split review's blocking finding explicitly identifies this as
architecturally wrong.

**Alt2: Embedding the schema inside an emission script (no separate module).** The schema would
live as a local constant inside the script that does the emitting. Rejected per the split review's
`no-schema-home` finding: DIR-124-B must extend the same schema without copy-pasting from an
emission-only file. A first-class module at `workflow-event-schema.mjs` with explicit
`SCHEMA_VERSION` export is the single canonical home. DIR-124-B's plan (M236) already treats A1's
schema as an importable migration source -- embedding it would force M236 to copy-paste,
reproducing the exact fragmentation this child prevents.

**Alt3: Instrumenting all prepare-milestone.js phases (not just Admission).** The other prepare
phases (Preflight, ProposalAuthors, Adjudicate, ProposalReview, PlanAuthor, PlanCheck, Receipt)
involve multi-round content-agent dispatch with N independent agents, delta continuation, and
cross-generation resume. Their internal timing is already partially covered by M207's
`_phaseTimings`. Instrumenting them at A1's granularity would be scope creep -- A1's charter is
the execution boundary. Rejected: scope is the 8 cross-workflow boundaries.

**Alt4: Wrapping only dispatch helpers (not explicit per-boundary calls).** Emit events only from
the `agent()` dispatch wrapper, not from bare `phase()` calls. Rejected because: (a) the Prepare
admission boundary (`phase('Admission')` + `--acquire` success) has no agent dispatch until the
lease is acquired -- the admission timing/wait/fencing-token data is lost if we only wrap agent
calls; (b) the Verify, Prepared, and Reconcile phases have significant workflow-runner logic
(argument normalization, cache-fingerprint comparison, receipt validation, reconcile-apply
invocation) that happens OUTSIDE any single agent dispatch -- wrapping only agents would miss
these entire phases; (c) uniform per-`phase()` instrumentation is simpler, more auditable, and
covers every boundary by construction rather than by convention.

**Alt5: Importing the schema module into the workflow DSL (adding `import` support).** Would allow
the workflow to `import { recordStageEvent } from './workflow-event-schema.mjs'` and call it
synchronously. Rejected: the workflow DSL's `import`-less constraint is a documented, load-bearing
architectural boundary (lines 23-25). Introducing a novel import mechanism is a larger scope
change than this entire observability child. The existing `node --experimental-strip-types` CLI
dispatch pattern is the established, tested, documented mechanism -- it works, it is already used
across dozens of call sites in both workflow files, and it requires zero DSL-runtime changes.

**Alt6: Using the event stream as a gating mechanism.** Making a missing or malformed event block
the phase or change dispatch outcome. Rejected: the event stream is observational-only. The gate
engine (`quay gate`) already has its own immutable GateEvent append mechanism at
`.quay/gate-events.jsonl`. Introducing a competing gate journal is explicitly the parent AC9
non-goal. Fire-and-forget is the correct semantics for an observability layer.

**Alt7: Unifying the event stream with existing prepare-telemetry or gate-events.** Merging
`recordStageEvent` output into `proposal-convergence.ts`'s telemetry path or
`.quay/gate-events.jsonl`. Rejected: these systems serve different purposes (cross-generation
resume vs lifecycle transition vs phase observability), have different schemas, different storage
paths, different commit policies (git-committed vs gitignored), and different consumers. Forcing
unification would constrain each system by the requirements of the others. DIR-124-B's migration
path already defines how the event stream feeds into a later unified journal -- unification can
happen there, when the full picture is visible.

**Alt8: Merging A1 and A5 into one child (schema + metrics in a single deliverable).** Rejected
per the split review's core finding: A1 and A5 are independently landable mechanisms. A5 consumes
A1's event stream as a downstream consumer; coupling them would break independent landability and
make each harder to audit. The parent DIR-124-A's ordered-child split form encodes this boundary
explicitly.

**Alt9: Single-boundary event (no start/end pair).** Emit only one event per phase at exit.
Rejected: the start/end pair captures `queuedAtMs -> startedAtMs` timing (the
admission-contention or Land-lock wait time) as a separate metric from the phase's actual
execution time. A single exit-only event folds these together, losing the queue delay signal that
DIR-124-E's resource-aware scheduling needs.

**Alt10: Schema as TypeScript (.ts) rather than .mjs.** Using `.ts` with `--experimental-strip-types`
for the schema module. Rejected: the schema module is simple enough (data definitions, validation
function, CLI arg parsing, file I/O) that `.mjs` with JSDoc type annotations suffices. Using
`.mjs` avoids the `--experimental-strip-types` overhead on the emission path itself (the WORKFLOW
still uses `--experimental-strip-types` to invoke other `.ts` modules, but the event schema module
loads directly). The task's own `## Touches` specifies `.mjs`, confirming this decision.

**Alt11: Writing events to git-committed storage.** Committing `.workflow-events/` would pollute
the commit history with transient diagnostic data. Rejected: gitignored, following
`.quay/gate-events.jsonl`'s pattern. Committed provenance belongs in
`milestones/prepare-telemetry/` (a separate system).
