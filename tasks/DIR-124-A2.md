### Problem framing (grounded in current code, 2026-08-01)

### Chosen mechanism

A **classified event-stream replay runner** (`scripts/workflow-replay.ts`, both mirrors) that replays each fixture's recorded A1 v1 event stream through a deterministic phase-transition state machine and checks per-assertion predicates against the observed state vector. The runner is a pure function — no agent dispatch, no network, no filesystem mutation beyond reading fixture files and the A1 schema module.

Three layers:

**Layer 1 — Fixture format.** Each fixture directory under `fixtures/workflow-replay/<case-name>/` contains:
- `events.jsonl` — A trimmed A1 v1 event stream (conforming to `workflow-event-schema.mjs`'s `StageEvent` type). Validated on load against the canonical schema module; schema version mismatch is a hard error.
- `expectations.json` — Assertion manifest: an array of `{id, description, classification: "normative"|"compatibility-only"|"known-defect", internalCategory: "normative"|"compatibility-only"|"observed-but-undesired"|"explicitly-open-defect", mappingNote?, check: {predicate, args}, expected}` objects. The `classification` field uses the parent AC3's 3-label public set. The `internalCategory` field preserves the 4-category taxonomy from the split review; `observed-but-undesired` and `explicitly-open-defect` both map to public label `known-defect`, and every such mapping is documented in `mappingNote`.
- `README.md` — Required for constructed (synthetic) fixtures; optional for real-run-derived fixtures. Documents provenance, construction methodology, and the git commit at fixture-creation time.

**Mechanism-claim (A2-CONSUME-A1):** The replay runner reads A1 v1 event streams from `fixtures/workflow-replay/<case>/events.jsonl` and validates each line against `workflow-event-schema.mjs`'s v1 schema. This is the sole A2-on-A1 dependency — the runner imports the schema module for structural validation and field-name reference.

**Layer 2 — Replay runner** (`scripts/workflow-replay.ts`). Exports `runWorkflowReplay(casePath: string): ReplayResult` and `runAllWorkflowReplays(fixturesDir: string): ReplayResult[]` for direct test import, with a CLI `main()` for manual invocation. Follows the exact established pattern of `golden-replay-dir044.ts` (DIR-044's terminal proof): pure-function TypeScript module, deterministic output, `isDirect` detection for CLI vs. import modes.

Replay flow per fixture:
1. Load `events.jsonl`, parse as JSONL, validate each line against `workflow-event-schema.mjs`'s v1 `validateEvent()`.
2. Load `expectations.json`, verify internal consistency: every `classification: "known-defect"` must carry a valid `internalCategory` of `"observed-but-undesired"` or `"explicitly-open-defect"`; every `classification: "normative"` must carry `internalCategory: "normative"`; every `classification: "compatibility-only"` must carry `internalCategory` of `"compatibility-only"` or `"explicitly-open-defect"`; no assertion classified `normative` may reference a predicate that depends on known-defect behavior.
3. Build the observed state vector by walking `events[]` in temporal order. Extracts: `phaseSequence: string[]` (from `event.stage` values), `agentCounts: Map<stage, number>` (distinct `event.agentLabel` values per stage), `outcome: {outcome, reason?, phase?}` (terminal event's outcome), `sharedStateMutations: string[]` (union of all `event.observedWrites`), `schedulingDecisions: string[]` (agent dispatch labels + dispatch metadata). Only A1 schema fields are consumed — `stage`, `agentLabel`, `outcome`, `observedWrites`, `timing.queuedAtMs`/`startedAtMs`/`endedAtMs` from the v1 `StageEvent` type.
4. Evaluate each assertion's `check` predicate against the observed state vector. Predicates are composable helpers over the event array: `stageOrderedBefore(events, A, B)`, `agentCountForStage(events, stage, expectedCount)`, `fieldEquals(events, stage, field, expectedValue)`, `outcomeMatches(events, expectedOutcome)`, `hasStage(events, stage)`, `stageSkipped(events, stage)`, `worktreeFieldsPopulated(events, stage)`. Predicate names and args are referenced declaratively in `expectations.json`; the runner resolves them by name.
5. Classify each assertion result by its `classification` policy (see Defaults and failure behavior below). Aggregate into per-fixture and overall verdict.

**Mechanism-claim (A2-RUNNER-PURE):** The replay runner is a pure function of its fixture input — it never dispatches agents (`agent()`), never touches the filesystem beyond reading fixtures and the A1 schema module (`fs.readFileSync` on known fixture paths only), never shells out to `quay` CLI or any subprocess, never writes to disk, and never mutates shared module state. Two calls with the same fixture arguments return structurally identical results, verified by `assert.deepEqual` in the test suite. Verified by `grep` for `agent(`, `execFile`, `writeFileSync`, `appendFileSync` returning zero hits on the runner body.

**Layer 3 — Test harness** (`test/workflow-replay.test.mjs`, both mirrors). Node test-runner tests that import `runWorkflowReplay()` directly (no subprocess, no agent dispatch) and exercise all 10 fixtures plus the RED/GREEN negative controls. Standard `node:test` with `node:assert/strict`. The `plugin/test/` mirror is discovered by `scripts/test.sh`'s default glob (`plugin/test/*.test.mjs`, line 68); the `experiments/quay-perpetual-stream/test/` mirror is a symlink to the plugin copy or a byte-identical mirror checked by the extended mirror-diff mechanism at Land.

**Mechanism-claim (A2-TEST-GLOB):** The `plugin/test/workflow-replay.test.mjs` mirror is picked up by `scripts/test.sh`'s default glob (`plugin/test/*.test.mjs`, line 68). The `experiments/quay-perpetual-stream/test/` mirror is a symlink (`../../../plugin/test/workflow-replay.test.mjs`) or byte-identical copy verified by the mirror parity check. No opt-in flag or separate invocation is required.

### Key design decisions

**D1 — Replay the event stream, not re-execute agents.** The workflow agents (Build, Audit, Gate, Land) are LLM-driven and non-deterministic — the same prompt produces different outputs across runs. Replaying the recorded A1 event stream gives deterministic, repeatable results. The event stream IS the ground truth of what the workflow did; replaying it checks whether the OBSERVED behavior matches the EXPECTED contract. This is the same pattern as `golden-replay-dir044.ts` (DIR-044), which replays recorded touches through the scheduler pipeline, never re-runs actual agent builds.

**D2 — Per-assertion classification, not per-fixture.** A single fixture contains multiple assertions, each with its own classification. For the legacy-singleton-success fixture: "phase sequence IS Verify→Prepared→Build→Audit→Gate→Land" is `normative`; "exactly 6 Verify agents were dispatched" is `compatibility-only` (DIR-124-B may parallelize them). Without per-assertion granularity, a deliberate refactoring that parallelizes Verify would fail the entire fixture on one detail. Classification lives on each assertion individually. This is the mechanism that prevents known-defect shapes from being normalized into invariants.

**D3 — 3-label public classification, 4-category internal taxonomy stored together.** Each assertion carries both `classification` (public: `normative` / `compatibility-only` / `known-defect`) and `internalCategory` (normative / compatibility-only / observed-but-undesired / explicitly-open-defect). The public label drives the replay verdict. The internal category preserves the split review's finer distinction so that when a defect is later fixed (as M192 was at M208), the fixture metadata retains the audit trail that this was once an observed-but-undesired behavior, not a compatibility quirk. The mapping is: `normative` → `normative`; `compatibility-only` → `compatibility-only`; `observed-but-undesired` → `known-defect`; `explicitly-open-defect` → `known-defect`.

**Mechanism-claim (A2-FINER-TAXONOMY):** The `internalCategory` field is present and validated on every assertion in both defect fixtures. The runner's expectation validator rejects any assertion with `classification: "known-defect"` that lacks a valid `internalCategory` value (must be `observed-but-undesired` or `explicitly-open-defect`). The validator also rejects `classification: "normative"` assertions with a non-`normative` `internalCategory`, and `classification: "compatibility-only"` assertions with an `internalCategory` other than `"compatibility-only"` or `"explicitly-open-defect"`.

**D4 — RED/GREEN negative controls are committed fixtures with dedicated test assertions.** RED controls prove the runner correctly reproduces known defects. GREEN controls prove the runner is not a tautology: a tampered normative assertion MUST fail, and a defect misclassified as normative MUST be rejected. Both are committed fixture directories so that CI runs them automatically. Test suite includes dedicated `node:test` blocks asserting correct exit outcomes for each control.

**D5 — Pre-instrumentation baseline comparison via mechanical state-vector diff.** The baseline (`meta.baseline` field in the legacy-singleton-success fixture) is mechanically compared against the observed state vector built from the fixture's event stream. `JSON.stringify` equality across all 5 dimensions: stage order, agent count, outcome, shared-state mutations, and scheduling decisions. ### Defaults and failure behavior

**Runner CLI defaults:**
- `--all` (default): replays every fixture directory under `fixtures/workflow-replay/`, excluding negative-control subdirectories (which have dedicated test blocks).
- `--case <name>`: replays a single named fixture.
- `--negative-controls`: replays only the RED/GREEN negative control fixtures.
- `--strict`: treats compatibility-only assertion failures as hard failures (exit 1), not just stderr warnings. Useful for pre-refactoring baselines where every observable change must be accounted for.

**Classification-level failure behavior:**
- `normative` assertion fails: exit 1, message to stdout: `FAIL [normative] <case>:<assertion-id>: <description>. Expected: <expected>, Actual: <actual>.`
- `compatibility-only` assertion fails (non-strict mode): exit 2, message to stderr: `WARN [compatibility-only] <case>:<assertion-id>: <description>.`
- `known-defect` assertion passes (defect no longer reproduces — e.g. post-M208 run against M192 fixture): informational stdout: `INFO [known-defect] <case>:<assertion-id>: defect resolved -- behavior no longer matches recorded defect shape.` Exit 0. This is not a failure; the defect was fixed.
- `known-defect` assertion reproduces correctly: informational stdout: `INFO [known-defect] <case>:<assertion-id>: defect reproduced as expected.`
- `known-defect` assertion changes unexpectedly (defect shape itself drifts from what was recorded): exit 1: `FAIL [known-defect] <case>:<assertion-id>: defect shape changed. Recorded: <expected>, Observed: <actual>.`

**Edge cases (all fail-closed):**
- Empty fixtures directory: exit 0, message "no fixtures found."
- Missing fixture directory (referenced but not on disk): `{ok: false, error: 'fixture-not-found'}`, never silently skipped.
- Malformed `events.jsonl` (invalid JSONL syntax, or lines failing A1 v1 schema validation): exit 1, hard error at load time with the offending line number.
- Malformed `expectations.json` (missing required fields, unknown predicate name, classification/`internalCategory` mismatch): exit 1.
- Assertion references a stage that does not appear in the event stream: exit 1.
- Fixture directory missing either `events.jsonl` or `expectations.json`: exit 1.
- Unknown `classification` label: hard error at validation time, exit 1 — an unknown label is a schema error caught before any assertion is evaluated; the valid 3-label set is `normative` / `compatibility-only` / `known-defect` and any other value is rejected.
- Schema version mismatch (`schemaVersion` is not `"1"`): exit 1 with explicit message.

### Compatibility

**With A1:** A2 consumes A1's v1 schema via `import { validateEvent, SCHEMA_VERSION } from './workflow-event-schema.mjs'`. Schema version mismatch is explicitly detected and rejected at load time. If DIR-124-B extends the schema (as permitted by A1's forward-migratability AC), A2's validator accepts extended fields (additional properties are allowed, never rejected) and only consumes the fields it needs — unknown fields are ignored. A schema-breaking change (v2 with removed v1 fields) requires fixture recapture.

**With the installed workflow:** A2 modifies no workflow file — it adds only fixtures, a runner script, and a test file. The fixtures capture the workflow's behavior as of the temporal anchor; post-anchor changes are detected as behavioral drift, which is the entire purpose.

**With DIR-124-B/C/D/E:** Each child deliberately changes the workflow's behavior. When they do, the A2 runner run against the post-change workflow's event stream reports assertion failures. The child's own Plan must classify each failure as intentional or accidental. A2 provides the measurement baseline, not a gate.

**With existing golden replay (`golden-replay-dir044.ts`):** `golden-replay-dir044.ts` covers the concurrent scheduler's orthogonality check, batch assembly, fan-in, and anti-drift — the scheduling pipeline. A2 covers the full workflow lifecycle — the execution pipeline. The two corpora serve different scopes with independent fixture data, different assertion vocabularies, and different consumers. No overlap, no duplication.

**With mirror parity:** Enforced by the existing `sync-vendor.sh --check` pattern, extended to cover `fixtures/workflow-replay/`, `scripts/workflow-replay.ts`, and `test/workflow-replay.test.mjs`.

**With `scripts/test.sh`:** The `plugin/test/workflow-replay.test.mjs` mirror is discovered by the default glob (`plugin/test/*.test.mjs`, line 68). No opt-in flag, no separate invocation. The replay tests are purely mechanical (no agent dispatch, no network, no GitHub token), so they always run and always complete in under 1 second.

**Node version:** Node >= 20 (ESM, `--experimental-strip-types` for the runner's `.ts` source, `node:test`, `node:assert/strict` — same floor as the rest of the repo).

### Risks

**R1 — A1 not yet landed, so no real event streams exist to build fixtures from.** Mitigation: the runner and fixture format are designed against the published A1 schema (which exports `SCHEMA_VERSION = "1"`, `StageEvent` type, and `validateEvent` as a pure data module). Fixtures are committed as schema-conformant JSONL. Once A1 lands, a "real-stream" validation pass confirms constructed fixtures match real event shapes (the AC3 condition). The runner's schema-validator ensures fixtures never silently diverge from the canonical schema.

**R2 — Constructed fixtures may misrepresent actual behavior.** Mitigation: each fixture's `README.md` documents provenance (real run vs. constructed, which commit/run it was based on, trimming methodology). Only the two defect fixtures (M192, M195) are necessarily constructed; the 8 named cases are derivable from known workflow phase structure and the pre-instrumentation baseline. The runner's determinism property (D6) ensures that once a fixture's assertions are verified against a real event stream, they stay verified.

**R3 — Fixture staleness as the workflow evolves.** This is by design — the corpus is a before-state snapshot, not a living specification. Post-DIR-124-E, the entire corpus may need recapture. The fixtures serve their purpose if they correctly detect every behavior change introduced by DIR-124-B/C/D/E and force each change to be classified. Mitigation: each fixture's `meta` block carries `generatedAt` and `workflowCommit`; the test harness prints a diagnostic warning when the current HEAD differs from the recorded commit.

**R4 — M192 fixture encodes behavior already fixed at M208 (commit `de5c79a2`).** The M192 fixture encodes pre-M208 null-passthrough behavior that the current workflow no longer exhibits. A post-M208 run against this fixture reports "defect resolved" — the desired outcome. Mitigation: the fixture's `meta.synthetic: true` flag and documented synthesis methodology make the constructed provenance explicit. The `observed-but-undesired` internal category preserves the audit trail even after the defect is resolved.

**R5 — Concurrent partial survivor fixture complexity.** This case depends on DIR-123's worktree isolation being landed AND the workflow supporting `mode: 'concurrent'`. If the concurrent path is not yet operationally proven, the fixture may need updating. Mitigation: scheduling-decision assertions are classified `compatibility-only` (exact parallel agent count may change); only structural invariants (single-flight Land lock held, milestone_counter advanced by survivor count) are `normative`.

**R6 — Schema version mismatch between A1 v1 and future changes.** Mitigation: the runner validates `schemaVersion` on each event line and rejects non-`"1"` versions with an explicit message. If A1's schema changes, fixtures are recaptured. Schema migration is out of A2's scope.

**R7 — Per-assertion check predicates become complex for multi-stage ordering invariants.** Mitigation: predicates are composable pure functions over the event array; the vocabulary is defined in the runner module and referenced by name in `expectations.json`, keeping fixtures declarative and the runner independently testable. No predicate may close over mutable state or perform I/O.

**R8 — Mirror parity drift.** Mitigation: the existing `sync-vendor.sh` mirror-diff pattern is extended to cover the replay fixtures directory, runner module, and test file.

### Alternatives considered and rejected

1. **Naive golden snapshot (full state capture without classification).** Would freeze M192's null-passthrough and M195's Verify-before-Prepared ordering as normative invariants. Any later refactoring that fixed either behavior would appear as a regression. Rejected: per-assertion classification with RED/GREEN negative controls is required to distinguish defect from invariant.

2. **Prose replay descriptions (markdown document).** A human reading "the Build phase should produce a mergeCommit" cannot mechanically verify it against an event stream. Prose gets paraphrased away (ADR-004 principle). Rejected: the corpus must produce deterministic machine-readable pass/fail verdicts.

3. **Re-execute workflow agents against recorded state.** Set up a git worktree at the pre-Build commit, dispatch the same agent prompts, compare outputs. LLM agents are non-deterministic — same prompt produces different outputs. Rejected: replaying the recorded event stream is the only deterministic approach.

4. **Embed the replay runner in the workflow's Gate phase.** Would couple the Gate phase to fixture maintenance, add latency to every Land, and prevent workflow evolution (every DIR-124 child would fail the gate on a before-state corpus). Rejected: the runner is a development-time safety net, not a runtime gate.

5. **Single per-fixture classification label.** Would force an entire fixture to be "known-defect" even if only one assertion in it concerns the defect. Rejected: classification lives on each assertion individually.

6. **Separate the 4-category internal taxonomy from the fixture.** Would invite drift between the fixture and its classification metadata — exactly the single-source-of-truth violation DIR-028 prohibits. Rejected: the finer category travels WITH the fixture so a standalone replay carries the full classification context.

7. **Reuse `golden-replay-dir044.ts` by extending it to cover workflow lifecycle.** DIR-044 covers the concurrent scheduler; A2 covers the full lifecycle. Extending a single script to cover both would couple independent concerns. Rejected: separate runner owns its own assertion vocabulary, fixture format, and failure policy.

8. **Schema-free fixtures (raw JSON without A1 schema validation).** Would allow fixtures to silently drift from the canonical event shape. Rejected: runner validates every fixture line against `workflow-event-schema.mjs`'s v1 `validateEvent()` on load.

9. **Wiring into `it0-dod-check.ts` as a new clause.** Would give the replay runner gate-authority over milestone completion, preventing any workflow evolution. Rejected: runner is a standalone measurement tool.

10. **Live replay against the running workflow.** Would require a live quay workspace, real task files, real GitHub provider, and agent API access — making replay non-deterministic, expensive, and credential-dependent. Rejected: pure-function replay over committed fixture data is deterministic, fast, and CI-runnable without credentials.

11. **Merging A2 and A5 (baseline metrics) into a single child.** Both consume the A1 event stream but produce different outputs (classified replay verdicts vs. crystallization metrics) with different failure policies and different consumers. Rejected: split review's core finding is that each mechanism is independently landable.

12. **Constructing only the 8 success/failure fixtures, omitting known-defect shapes.** Would silently normalize the two known defects by omission. Every later refactoring child would measure against a baseline that pretends the defects don't exist. Rejected: the known-defect shapes must be explicitly encoded and classified.

13. **Encoding the M192 defect as a real captured run rather than a constructed fixture.** A real pre-M208 run would demonstrate the null-passthrough, but such a run does not exist in A1 event-stream format (A1 did not exist before M208). A constructed fixture with documented provenance (`meta.synthetic: true`, `README.md`) is more reliable than a prose-reconstructed "real" run. Rejected: constructed fixture preferred for both defect cases.
