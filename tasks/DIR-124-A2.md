**type:** execution

## Proposal

Build the golden replay corpus that separates intentional compatibility from known defects in the
installed milestone workflow. Replay fixtures cover legacy singleton success, Verify failure,
Prepared failure, Audit REFUTED, Gate failure, composite success, concurrent partial survivor, and
cache/resume behavior (8 named cases), plus the two measured known-defect shapes — M192's null
Build result advancing to Audit/Land (`observed-but-undesired`) and the stale M195 Prepared control
paying Verify cost before receipt rejection (a compatibility baseline for DIR-124-C's later
behavior-preserving reorder). Each assertion is labeled with its behavior classification.

Second child of the DIR-124-A split (mechanism M2). Depends on A1's schema/stream defining the
captured shape.

**Classification taxonomy (reconciling the split review finding):** the Finding's 4-category
taxonomy (normative / compatibility-only / observed-but-undesired / explicitly open defect) is the
internal classification; each assertion's PUBLIC label uses the 3-label set from the parent AC3
(normative / compatibility-only / known-defect observation). `observed-but-undesired` and
`explicitly open defect` both map to `known-defect observation` at the assertion label level, and
the finer internal category is retained in the fixture metadata so a defect is never silently
normalized into a normative invariant.

## Chosen mechanism

M2 from the split-review inventory. `fixtures/workflow-replay/*` holds the case fixtures; a replay
runner under `scripts/*workflow*replay*` replays each case against the A1 event stream and asserts
per-case verdicts. The two known-defect shapes are RED/GREEN negative controls: they must reproduce
exactly and be labeled `known-defect`, never asserted as normative.

## Finding

Without a before-state replay boundary, DIR-123 and kernel extraction cannot distinguish a
deliberate behavior change from an accidental capability regression. Naive golden snapshots are
dangerous: the current workflow contains known defects (M192 null-Build continuation; stale M195
Prepared) that a naive snapshot would freeze as desired behavior.

## Requested action

1. Capture 8 replay fixtures for the named cases; each assertion carries a 3-label classification
   plus the internal 4-category detail in fixture metadata.
2. Add the two known-defect shapes as RED/GREEN negative controls, explicitly labeled
   `known-defect`, never normalized into a normative invariant.
3. Run each case through the replay runner; store per-case verdicts mechanically.
4. Classify a captured behavior change as deliberate only when the replay diff is
   compatibility-only; a change in a normative assertion fails the run.
5. Cover the AC2 instrumentation-invariance claim: A2's replay of a baseline run shows zero
   delta in stage order/agent count/outcome/shared-state mutation/scheduling.

## Acceptance Criteria

- [ ] Replay fixtures cover all eight named success/failure/composite/concurrent/cache cases and
  label each assertion normative, compatibility-only, or known-defect observation.
- [ ] Golden replay includes the M192 null-Build continuation and stale-Prepared-after-Verify
  shapes, classifies both explicitly (`known-defect`), and does not make either defect a normative
  invariant.
- [ ] The replay diff of a pre-instrumentation baseline shows instrumentation changed no stage
  order, agent count, outcome, shared-state mutation, or scheduling decision (AC2).
- [ ] RED/GREEN negative controls exist for both known-defect shapes and for a
  deliberately-tampered normative assertion (fails replay).
- [ ] The two known-defect shapes are recorded in fixture metadata with the finer
  observed-but-undesired / explicitly-open-defect category, preserving the review taxonomy.
- [ ] No post-Land Wiring Audit, lifecycle-promotion policy, worktree redesign, stage scheduler, or
  resource lease is introduced by this child (parent AC9 non-goal).
