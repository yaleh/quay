## Proposal

### Problem framing (grounded in current code, 2026-08-01)

**What exists today.** The installed milestone-workflow pair (`prepare-milestone.js`, 1558 lines; `execute-milestone.js`, 1257 lines) has been repaired incrementally across M185-M189 regressions, M192's null-Build continuation, and M195's stale-Prepared ordering without a mechanically-replayable behavioral baseline. DIR-123's worktree isolation (commit `059b5b16`) is live, and DIR-124-B/C/D/E are queued to touch the control plane — stage scheduling, pipeline reorder, kernel extraction, and resource-aware scheduling. Each of those refactoring children must distinguish a deliberate behavior change from an accidental capability regression. Prose histories and manually reconstructed Claude Code timelines are insufficient for this (the M192 defect was discovered only when an independent audit's human reviewer noticed "Build outcome: null" was wrong, not because any mechanical check flagged the unexpected passthrough).

The A1 child (DIR-124-A1, mechanism M1) defines the canonical stage-event schema v1 in `scripts/workflow-event-schema.mjs` and instruments all 8 workflow boundaries (Prepare admission + Verify/Prepared/Build/Audit/Gate/Reconcile/Land in `execute-milestone.js` at lines 66/234/389/719/817/919/961) to emit structured events to `.workflow-events/<runId>.jsonl`. A1 also captures a pre-instrumentation baseline (phase sequence, agent counts, outcome) before the workflow edits land. A2 consumes that event stream to build a classified golden replay corpus — the fixed before-state snapshot against which every later control-plane change is measured.

**What A2 must deliver.** A classified golden-replay corpus that, against an A1-instrumented workflow's event stream, mechanically proves which phase-transition behaviors are normative invariants, which are compatibility-only observations, and which are known defects — so that DIR-124-B/C/D/E's refactorings have a machine-checkable contract. The corpus must replay the event stream, not re-execute the workflow agents (which are non-deterministic), and must classify every assertion so that a normative-invariant failure is a hard gate while a compatibility-only change is informational.

Naive golden snapshots (full state capture without classification) would freeze known workflow defects as normative invariants. The workflow contained two measured, real defects at the temporal anchor:

1. **M192 null-Build continuation** (`observed-but-undesired`): `execute-milestone.js`'s Build-phase result gate at line 490 originally checked only `buildResult?.outcome === 'needs-human'`, so a terminally-errored `agent()` call resolving to `null` silently passed through — `null?.outcome` is `undefined`, which is NOT `'needs-human'`, so the condition evaluated to `false` and the null result proceeded to Audit/Gate/Land. This was the real behavior from M192 through M207; fixed at M208 (commit `de5c79a2`, positive-outcome Build-phase gate that rejects anything other than `outcome === 'done'`). The defect was discovered only because a human auditor noticed the anomaly — exactly the class of defect a mechanical replay baseline must encode.

2. **M195 stale-Prepared-after-Verify** (`compatibility-only` baseline): Before DIR-117-B/M195's enforced-default Prepared-phase fail-closed flip, the Verify phase's 6 it0 systematic-explore checks ran to completion before the Prepared phase could reject a stale or missing `preparationReceiptFile`. The Verify cost (~6 agent calls) is paid before the fail-closed receipt gate fires. This ordering is correct (Prepared is a pre-Build gate, not a pre-Verify gate), making this a `compatibility-only` baseline, not a defect — the behavior is correct-by-design, but the cost of running Verify before the Prepared check is measurable, and DIR-124-C's later behavior-preserving reorder may choose to swap them. The fixture encodes the current pre-reorder shape so DIR-124-C can prove its reorder changes nothing about the eventual rejection, only about WHEN the cost is paid.

A per-assertion classification taxonomy is required: normative assertions (must pass), compatibility-only assertions (diagnostic warnings only), and known-defect observations (must reproduce exactly, never normalized into normative invariants). An internal 4-category taxonomy (normative / compatibility-only / observed-but-undesired / explicitly open defect) is retained in fixture metadata so the finer category is never lost when a defect shape is later fixed.

### Chosen mechanism

A **classified event-stream replay runner** that replays each of the 10 fixtures (8 named cases + 2 known-defect shapes) against the A1 event stream, asserting per-case verdicts mechanically. Each fixture is a directory under `fixtures/workflow-replay/<case-name>/` containing the recorded event stream plus an expectation manifest; the replay runner loads the fixture, replays the event stream through a deterministic phase-transition model, and checks each assertion's pass/fail against its classification.

The mechanism has three layers:

**Layer 1 — Fixture format** (`fixtures/workflow-replay/<case-name>/`). Each fixture is a directory containing:
- `events.jsonl` — the trimmed A1 event stream covering the case's relevant stages (a real or constructed trace conforming to the A1 v1 schema: `schemaVersion`, `runId`, `candidateId`, `taskId`, `stage`, `attempt`, `timing: {queuedAtMs, startedAtMs, endedAtMs}`, `agentLabel`, `executionCwd`, `worktreePath`, `commandIdentity`, `baseCommit`, `candidateCommit`, `outcome`, `waitReason`, `resourceClaim`, `observedWrites`, `isolationMode`, `dispatchMode`). Each event line is valid against `workflow-event-schema.mjs`'s v1 shape; the runner validates this on load.
- `expectations.json` — the assertion manifest: an array of `{id, description, classification: "normative"|"compatibility-only"|"known-defect", internalCategory: "normative"|"compatibility-only"|"observed-but-undesired"|"explicitly-open-defect", check: <per-assertion predicate>, expected: <expected outcome>}` objects. The `classification` field is the public 3-label set from the parent's AC3. The `internalCategory` field retains the finer 4-category taxonomy; `observed-but-undesired` and `explicitly-open-defect` both map to public label `known-defect`. A `mappingNote` field is required on every `known-defect` assertion explaining the mapping (e.g. "observed-but-undesired → known-defect observation").
- `README.md` (optional) — prose description of the case, its real-world provenance, and any fixture construction notes. Required for constructed fixtures (M192, M195) to document the synthesis methodology.

**Mechanism-claim (A2-CONSUME-A1):** The replay runner reads A1 v1 event streams from `fixtures/workflow-replay/<case>/events.jsonl` and validates each line against `workflow-event-schema.mjs`'s v1 schema. This is the A2-on-A1 dependency contract.

**Layer 2 — Replay runner** (`scripts/workflow-replay.ts`, both mirrors). The runner exports `runWorkflowReplay(casePath: string): ReplayResult` and `runAllWorkflowReplays(fixturesDir: string): ReplayResult[]` for testability, with a CLI `main()` for manual invocation. It follows the exact same established pattern as `golden-replay-dir044.ts` (DIR-044's terminal proof): a pure-function TypeScript module, deterministic output (no LLM agents, no API calls, no filesystem mutation beyond reading fixtures), exit 0 on all normative + defect assertions passing.

For each fixture:
1. Load and validate `events.jsonl` against the A1 v1 schema module (`workflow-event-schema.mjs`). Schema version mismatch → hard error.
2. Load and validate `expectations.json` for internal consistency: every `classification: "known-defect"` assertion must have `internalCategory` of `observed-but-undesired` or `explicitly-open-defect`; every `classification: "normative"` must have `internalCategory: "normative"`.
3. Replay the event stream: walk the `events` array in temporal order, building an observed state vector (`phaseSequence: string[]`, `agentCounts: Map<phase, number>`, `outcome: {outcome, reason?, phase?}`, `sharedStateMutations: string[]` from `event.observedWrites`, `schedulingDecisions: string[]` from agent-call labels + dispatch metadata). The state vector is built from A1's `stageName`, `agentCallLabel`, `outcome`, `observedWrites`, `queuedAtMs`/`startedAtMs`/`endedAtMs` fields — these exact field names, no other event fields consumed (MC-4).
4. For each assertion in the fixture, evaluate its `check` predicate against the observed state vector. Check predicates are pure functions over the event array — `(events: StageEvent[]) => boolean`. Complex predicates (ordering, count, field equality) are implemented as composable helpers: `stageOrderedBefore(events, 'Audit', 'Gate')`, `agentCountForStage(events, 'Verify', 6)`, `fieldEquals(events, 'Land', 'outcome', 'done')`. The predicate vocabulary is defined in the runner module and referenced by name in `expectations.json`, keeping fixtures declarative and the implementation testable independent of any specific fixture.
5. Classify the assertion result by its `classification` policy (see Defaults and failure behavior).

**Mechanism-claim (A2-RUNNER-PURE):** The replay runner is a pure function of its fixture input — it NEVER dispatches agents, never touches the filesystem beyond reading the fixture and the A1 schema module, never shells out to `quay` CLI, and never mutates shared state. It is deterministic: two calls with the same fixture return identical results (MC-2).

**Layer 3 — Test harness** (`test/workflow-replay.test.mjs`, both mirrors). Node test-runner tests that import `runWorkflowReplay()` directly (no subprocess, no agent dispatch) and call it for each of the 10 fixtures (MC-3). Standard `node:test` with `node:assert/strict`. `scripts/test.sh` picks up `test/workflow-replay.test.mjs` via its default glob — no opt-in flag needed. The replay tests are purely mechanical (no agent dispatch, no network, no GitHub token), so they always run.

### RED/GREEN negative controls

**RED negative controls** (must pass replay — proving the defect is recognized):
- **M192 shape reproduces correctly**: The M192 fixture replays and all `known-defect` assertions pass — the defect shape matches the recorded behavior. Runner reports "defect reproduced: M192 null-Build continuation."
- **M195 shape reproduces correctly**: The M195 fixture replays and all `known-defect` assertions pass — the stale-Prepared ordering matches the recorded behavior.

**GREEN negative controls** (must fail replay — proving the runner actually enforces):
- **Tampered normative assertion** (`legacy-singleton-success-tampered/`): A copy of the legacy-singleton-success fixture where one normative assertion is deliberately altered (e.g., asserting Build dispatched 2 agents when the recorded stream shows 1). The runner detects the mismatch and exits non-zero with "normative invariant violated." This proves the mechanism is not a tautology.
- **Defect normalized as normative** (`m192-defect-as-normative/`): A copy of the M192 fixture where the `classification` on the null-passthrough assertion is changed from `known-defect` to `normative`. The runner rejects this at validation time (classification inconsistency: "assertion classified as normative but references known-defect shape") OR the normative assertion on the null-passthrough fails because the observed behavior (null passthrough) contradicts the normative expectation (Build must produce a valid result). Either way, runner exits non-zero, proving defect shapes are never silently normalized.
- Each GREEN control is a committed fixture directory; the test suite includes dedicated test blocks asserting the runner exits non-zero with the expected failure message. **WIRING-CLAIM (A2-NEG-CTRL):** All RED/GREEN controls are committed fixture directories with dedicated test assertions; the test suite proves both RED controls pass and both GREEN controls fail.

### Key design decisions

**D1 — Replay the event stream, not re-execute agents.** The workflow agents (Build, Audit, Gate, Land) are LLM-driven and non-deterministic. Replaying the recorded event stream — which A1 captures observationally — gives deterministic, repeatable results. The event stream IS the ground truth of what the workflow did; replaying it checks whether the OBSERVED behavior matches the EXPECTED contract. This is the same pattern as DIR-044's golden replay (which replays recorded touches through the scheduler pipeline, never re-runs the actual agent builds).

**D2 — Per-assertion classification, not per-fixture.** A single fixture (e.g., legacy-singleton-success) contains multiple assertions, each with its own classification. The phase sequence "Verify→Prepared→Build→Audit→Gate→Land" might be `normative` (it MUST be exactly this order), while the exact number of Audit agent dispatches might be `compatibility-only` (it may change if DIR-124-B parallelizes audit shards). This granularity prevents false positives where a deliberate refactoring fails an entire fixture because one compatibility-only detail changed. Classification lives on each assertion, not on the fixture as a whole. This allows the defect-shape fixtures to encode the defect's real behavior (normative for the defect shape, known-defect for the passthrough/ordering anomaly) without normalizing the anomaly.

**D3 — The 3-label public classification and 4-category internal taxonomy are both stored.** Each assertion carries both `classification` (public: `normative` / `compatibility-only` / `known-defect`) and `internalCategory` (normative / compatibility-only / observed-but-undesired / explicitly-open-defect). The public label drives the replay verdict. The internal category is stored in fixture metadata so that a post-refactoring review can distinguish "this compatibility behavior was known-undesired but tolerated" from "this was pure compatibility, neither desired nor undesired." No defect is ever silently normalized into a normative invariant. The mapping is: `normative` → `normative`; `compatibility-only` → `compatibility-only`; `observed-but-undesired` → `known-defect`; `explicitly-open-defect` → `known-defect`. When a defect is later fixed (as M192 was at M208), its internal category stays `observed-but-undesired` in the fixture metadata, preserving the audit trail.

**D4 — RED/GREEN negative controls are honest, committed fixtures.** RED controls (defect shapes reproduce) prove the mechanism recognizes known defects. GREEN controls (tampered normative fails, defect-normalized fails) prove the mechanism is not a tautology — it actually detects regressions and rejects normalization of defects. Both are committed fixture directories with dedicated test assertions. The test suite proves both RED controls pass and both GREEN controls fail. This matches `golden-replay-dir044.test.mjs`'s three-test pattern (end-to-end, counter monotonicity, deterministic ordering).

**D5 — The pre-instrumentation baseline comparison is a mechanical `JSON.stringify` diff.** The baseline (`meta.baseline` in the legacy-singleton-success fixture) is mechanically compared against the observed state vector built from the fixture's event stream. The comparison checks all 5 dimensions: stage order, agent count, outcome, shared-state mutation, and scheduling decisions. `JSON.stringify` equality is used; structural comparison handles field ordering. This is the mechanical proof that A1's instrumentation is behavior-preserving (AC2/AC3).

**D6 — Pure-function TypeScript runner, following established precedent.** The runner is a `node:test`-importable module exporting `runWorkflowReplay(casePath)` and `runAllWorkflowReplays(fixturesDir)`, with a CLI `main()` wired behind `isDirect` detection (matching `golden-replay-dir044.ts` line 102-106). No LLM agents, no API calls, no filesystem mutation beyond reading fixtures. Deterministic output for CI integration: a failing normative assertion produces a non-zero exit code carrying structured failure messages to stdout.

**D7 — Fixtures are A1-event-stream fragments, not workflow journal replays.** Each fixture's `events.jsonl` contains only the subset of events relevant to its case — a trimmed run or a deliberately-constructed trace. This keeps fixtures small, auditable, and focused on the specific behavior being asserted. A full milestone journal would contain irrelevant detail and be harder to review for correctness. Trimming is documented in each fixture's `README.md`.

**D8 — Corpus is explicitly a before-state snapshot.** The fixtures are pinned against the installed workflow as of the temporal anchor (DIR-123 at commit `059b5b16` + A1's behavior-preserving instrumentation). DIR-124-B/C/D/E will deliberately change behavior; when they do, the A2 fixtures serve as the comparison baseline. A behavior change that alters a normative assertion is a regression. A behavior change that alters a compatibility-only assertion is a logged diagnostic. A behavior change that resolves a known-defect observation is detected positively: the defect no longer reproduces.

**D9 — Both mirrors, byte-identical.** The `plugin/scripts/workflow-replay.ts` mirror is byte-identical to `experiments/quay-perpetual-stream/scripts/workflow-replay.ts`. Both `fixtures/workflow-replay/` directories and both `test/workflow-replay.test.mjs` files are byte-identical. The existing `sync-vendor.sh --check` mirror parity test enforces this at Land. **WIRING-CLAIM (A2-MIRROR):** Both mirror copies are byte-identical; mirror-diff passes at Land.

**D10 — Dependency on A1 is schema-level, not runtime-level.** A2's fixtures reference A1's v1 schema fields by name. The runner imports `workflow-event-schema.mjs` to validate fixture format against the canonical schema. This is a soft dependency: A2's tests can run against the schema module even before A1's emission instrumentation is live in the workflow, because the schema module itself is a pure data definition. Full mechanical replay against a real dispatch's `.workflow-events/` output requires A1 to have landed — that is the AC3 condition.

### Defaults and failure behavior

**Runner defaults:**
- `--all`: replays all fixture cases and reports pass/fail per case.
- `--case <name>`: replays a single named fixture.
- `--negative-controls`: replays only the RED/GREEN negative control fixtures.
- `--strict`: treats compatibility-only failures as hard failures (exit 1) in addition to normative violations — useful for pre-refactoring baselines.

**Classification-level failure behavior:**
- `normative` assertion fails → exit 1, message to stdout: `FAIL [normative] <case>:<assertion-id>: <description>. Expected: <expected>, Actual: <actual>.`
- `compatibility-only` assertion fails → exit 2, message to stderr: `WARN [compatibility-only] <case>:<assertion-id>: <description>.`
- `known-defect` assertion passes (defect no longer reproduces) → informational to stdout: `INFO [known-defect] <case>:<assertion-id>: defect resolved -- behavior no longer matches recorded defect shape.` Exit 0 — this is not a failure; the defect was fixed intentionally or incidentally.
- `known-defect` assertion reproduces correctly → informational to stdout: `INFO [known-defect] <case>:<assertion-id>: defect reproduced as expected.`
- `known-defect` assertion changes unexpectedly (defect shape itself drifts) → exit 1, message: `FAIL [known-defect] <case>:<assertion-id>: defect shape changed. Expected defect behavior: <expected>, Actual: <actual>. This is a regression signal.`

**Edge cases:**
- Empty fixtures directory → exit 0, message "no fixtures found."
- Missing fixture directory → `{ok: false, error: 'fixture-not-found'}` — never silently skipped.
- Malformed `events.jsonl` (not valid JSONL, or lines not conforming to A1 v1 schema) → exit 1, hard error at load time.
- Malformed `expectations.json` (missing required fields, classification/`internalCategory` mismatch) → exit 1.
- Assertion predicate references a stage that does not exist in the event stream → exit 1.
- Fixture directory missing `events.jsonl` or `expectations.json` → exit 1.
- Unknown `classification` label → treated as `normative` (fail-safe: an unknown label could be a typo; defaulting to the strictest classification prevents accidental normalization of a defect).
- Schema validation failure → hard error at load time (exit non-zero), not a per-assertion result.

**Negative-control failure behavior:**
- GREEN control (tampered normative assertion): runner must exit non-zero. Test harness asserts exit code != 0 with expected failure message.
- GREEN control (defect normalized as normative): runner must exit non-zero either at validation time or at assertion time.
- RED control (defect shape reproduces): runner must exit 0 with "defect reproduced" message.

### Compatibility

A2 is strictly a consumer of the A1 event stream and a writer of committed fixture files — it changes no workflow behavior, introduces no new lifecycle policy, and modifies no existing code paths.

- **With A1:** A2's runner validates fixture events against A1's v1 schema. If A1's schema changes (v2), A2 fixtures reference v1 and the runner reports a schema version mismatch — the fixture must be recaptured. The v1 version marker in the schema makes this explicitly detectable. The runner imports the A1 schema module dynamically; if DIR-124-B extends the schema (as permitted by A1's forward-migratability AC), the runner's validation will accept extended fields (additional properties are allowed, never rejected). The runner only consumes the fields it needs — unknown fields are ignored.
- **With the installed workflow:** A2 does not modify `execute-milestone.js`, `prepare-milestone.js`, `OUTER-LOOP.md`, or any composite module. The fixtures capture the workflow's behavior as of the temporal anchor; post-anchor changes are detected as behavioral drift — which is the entire purpose.
- **With DIR-124-B/C/D/E:** Each child will change the workflow's control plane. When they do, the A2 runner run against the post-change workflow's event stream will report assertion failures on normative invariants that changed. The child's own Plan must classify each such failure as intentional or accidental. A2 does not gate the later children — it provides the measurement baseline.
- **With existing golden replay:** `golden-replay-dir044.ts` covers the concurrent scheduler's orthogonality check and fan-in. A2 covers the full workflow lifecycle. The two corpora serve different scopes and do not overlap; A2 does not duplicate DIR-044's fixture data or assertions.
- **With mirror parity:** Enforced by the existing `sync-vendor.sh --check` mirror parity test at Land, extended to cover `fixtures/workflow-replay/`, `scripts/workflow-replay.ts`, and `test/workflow-replay.test.mjs`.
- **Node version:** Node >= 20 (ESM, `--experimental-strip-types`, `node:test`, `node:assert/strict` — same floor as the rest of the repo).

### Risks

**R1 — A1 not yet landed, so no real event streams exist to build fixtures from.** The A2 fixtures must be constructed from the A1 schema spec and the known workflow phase structure, not from captured real events. Mitigation: the runner and fixture format are designed against the published A1 schema; the fixtures are committed as schema-conformant JSONL. Once A1 lands and a real dispatch produces events, a "real-stream" validation pass confirms the constructed fixtures match real event shapes (the AC3 condition). The runner's schema-validator ensures fixtures never silently diverge from the canonical schema.

**R2 — Constructed fixtures may misrepresent actual behavior.** A fixture hand-crafted from reading the workflow source may encode an assertion that does not match real observed behavior. Mitigation: each fixture's `README.md` documents provenance (real run vs. constructed, which commit/run it was based on). The pre-instrumentation baseline (AC2/AC3) runs the runner against a real post-A1 dispatch and flags any constructed-vs-real mismatch. Fixtures derived from real runs (the 8 named cases) are preferred; only the two known-defect fixtures (M192, M195) are necessarily constructed.

**R3 — Fixture staleness as the workflow evolves.** This is by design — the corpus is a before-state snapshot. Post-DIR-124-E, the entire corpus may need recapture. The fixtures serve their purpose if they correctly detect every behavior change introduced by DIR-124-B/C/D/E and force each change to be classified as intentional or accidental. Mitigation: each fixture's `meta` block carries a `generatedAt` timestamp and the git commit hash of the workflow files at fixture-creation time. The test harness prints a warning if the current workflow commit differs from the fixture's recorded commit — a diagnostic, not a gate.

**R4 — M192 fixture encodes behavior already fixed.** The M192 fixture encodes pre-M208 null-passthrough behavior that the current workflow no longer exhibits. This is intentional: the fixture is documentary, proving the defect was recognized and classified. The runner's "defect resolved" message is the desired outcome for a post-M208 run. Mitigation: the fixture's `meta.synthetic` flag is `true`, and the synthesis methodology is documented in its `README.md`. A post-Land audit explicitly checks whether the synthesized stream accurately reflects the pre-fix behavior.

**R5 — Concurrent partial survivor fixture complexity.** This case requires a real concurrent dispatch with worktree isolation, which depends on DIR-123 being landed AND the workflow supporting `mode: 'concurrent'` + `isolationMode: 'worktree'`. If the concurrent path is not yet operationally proven, the fixture may need updating when the first real concurrent dispatch occurs. Mitigation: the fixture is tagged `compatibility-only` for scheduling-decision assertions (exact agent count per phase under concurrency) and `normative` only for structural invariants (the single-flight Land lock was held, the milestone_counter advanced by exactly the survivor count).

**R6 — Schema version mismatch between A1 v1 and future A1 changes.** If A1 is amended (v1.1, v2) to add or remove fields, A2 fixtures referencing v1 fields may fail structural validation. Mitigation: the runner validates `schemaVersion` on each event line and fails with an explicit message if the version is not `"1"`. A schema migration path is out of A2's scope; if A1's schema changes, the fixtures are recaptured.

**R7 — Per-assertion check predicates become complex for multi-stage invariants.** Assertions like "Reconcile phase follows Gate phase which follows Audit phase" require multi-event correlation. Mitigation: check predicates are pure functions over the event array; complex predicates are implemented as composable helpers. The predicate vocabulary is defined in the runner module and referenced by name in `expectations.json`, keeping fixtures declarative.

**R8 — Mirror parity drift.** If one mirror is edited without updating the other, the parity check catches it. Mitigation: the existing `sync-vendor.sh` mirror-diff pattern is extended to cover the replay fixtures directory, runner module, and test file.

### Non-goals

Explicitly excluded from A2's scope, per parent AC9 non-goal:

1. **No live workflow monitoring or real-time replay.** A2 replays committed fixture data, not live event streams. The runner is a batch tool, not a daemon.
2. **No full milestone journal archival.** A2 fixtures contain trimmed event subsets, not complete run journals. The complete journal is the A1 event stream itself (`.workflow-events/<runId>.jsonl`).
3. **No automatic fixture generation from live runs.** The runner replays pre-built fixtures; it does not capture new fixtures from live dispatches. Fixture creation is a manual authoring step.
4. **No post-Land Wiring Audit, lifecycle-promotion policy, worktree redesign, stage scheduler, or resource lease** (parent AC9 non-goal enforced per-child).
5. **No replacement or extension of DIR-044's golden replay.** `golden-replay-dir044.ts` covers the concurrent scheduler; A2 covers the workflow lifecycle. Independent corpora, different scopes.
6. **No schema migration or A1 schema extension.** A2 consumes A1 v1 as-is.
7. **No Gate integration or DoD-clause wiring.** The replay runner is a standalone tool, not wired into `it0-dod-check.ts` or the Gate-phase `parallel([])` checks. The runner is invoked manually or in CI; it does not gate milestone completion.
8. **No second journal format.** A2 consumes the A1 event stream; it does not create a parallel event format or a new storage location.
9. **No performance benchmarking or timing assertion precision.** The replay runner checks structural/ordering/outcome invariants, not wall-clock timing. Timing fields are present in the event stream for A5's metric consumption; A2's assertions do not assert specific timing values.
10. **No cross-milestone behavioral comparison.** A2 compares a single case's fixture against its expected behavior, not across different milestones or workflow versions.
11. **No per-case agent dispatch.** The replay runner is a pure function of its fixture input. Zero agents are dispatched. Zero network calls are made.

### Alternatives considered and rejected

1. **Naive golden snapshot (full state capture).** Would freeze M192's null-passthrough and M195's Verify-before-Prepared ordering as desired behavior. Any later refactoring that changed either behavior would appear as a regression, even if the change was the intended fix. Rejected: per-assertion classification with RED/GREEN negative controls is required.

2. **Prose replay descriptions (markdown document).** A human reading "the Build phase should produce a mergeCommit" cannot mechanically verify it against a real run's event stream. Prose gets paraphrased away (ADR-004). Rejected: the corpus must be machine-readable and produce deterministic pass/fail verdicts.

3. **Re-execute the workflow agents against a recorded state.** Set up a git worktree at the pre-Build commit, dispatch the same agent prompts, and compare outputs. LLM agents are non-deterministic — the same prompt produces different outputs across runs. Rejected: replaying the recorded event stream is the only deterministic approach.

4. **Embed the replay runner in the workflow's Gate phase.** Would couple the Gate phase to fixture maintenance, add latency to every Land, and prevent workflow evolution (every DIR-124-B/C/D/E child would fail the gate on a before-state corpus). Rejected: the runner is a development-time safety net, not a runtime gate.

5. **Single per-fixture classification label.** Would force an entire fixture to be "known-defect" even if most assertions in it are normative (e.g., the M192 fixture: only the null-passthrough is the defect; everything else about that run was normal). Rejected: classification lives on each assertion individually.

6. **Separate the 4-category internal taxonomy from the fixture and store it in a review document.** Would invite drift between the fixture and its classification metadata. Rejected: the finer category must travel WITH the fixture so a standalone replay run carries the full classification context.

7. **Reuse `golden-replay-dir044.ts` directly (extend to cover workflow lifecycle).** DIR-044's replay covers the concurrent scheduler's orthogonality check, batch assembly, fan-in, and anti-drift — a different pipeline segment from the workflow lifecycle A2 covers. Extending a single script to cover both scopes would couple two independent concerns. Rejected: a separate runner at `scripts/workflow-replay.ts` is the correct granularity, following the same proven pattern but owning its own assertion vocabulary and fixture format.

8. **Schema-free fixtures (raw JSON without A1 schema validation).** Would allow fixtures to silently drift from the canonical event shape. If A1 adds a field, a schema-free fixture would not detect that its captured fields are now a subset of the canonical shape. Rejected: the runner validates every fixture line against the A1 v1 schema module on load.

9. **Wired into `it0-dod-check.ts` as a new clause.** Would give the replay runner gate-authority over milestone completion. Gating a milestone on a fixture corpus that is explicitly a before-state snapshot would prevent any workflow evolution. Rejected: the runner is a standalone measurement tool, not a DoD gate.

10. **Live replay against the running workflow.** Would require a live quay workspace, real task files, a real GitHub provider, and agent API access — making the replay non-deterministic, expensive, and dependent on external state. Rejected: pure-function replay over recorded fixture data is deterministic, fast, and runnable in CI without credentials.

11. **Merging A2 and A5 (baseline metrics) into a single child.** A5 emits the 10 crystallization-document metrics from the A1 event stream; A2 replays specific case behaviors with per-assertion classification. These are different consumers of the same data with different output formats, different failure policies, and different consumers. Rejected: the split-review's core finding is that each mechanism is independently landable.

12. **Constructing only the 8 success/failure fixtures, omitting the known-defect shapes.** Would produce a clean, normative-only corpus that silently normalizes the two known defects by omission. Every later refactoring child would measure against a baseline that pretends the defects don't exist. Rejected: the known-defect shapes must be explicitly encoded and classified.

13. **Encoding the M192 defect as a real captured run rather than a constructed fixture.** A real pre-M208 run captured the null-passthrough behavior, but such a run does not exist in A1-event-stream format (A1 didn't exist before M208). A constructed fixture with documented provenance is more reliable than a prose-reconstructed "real" run. Rejected: constructed fixture preferred, with `meta.synthetic: true`.
