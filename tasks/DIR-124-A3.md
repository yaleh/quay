## Proposal

### Problem framing

The installed milestone workflow is a distributed system spread across four layers with no inventory of which component owns which invariant:

1. **Workflow DSL scripts** (`.claude/workflows/`): `execute-milestone.js` (~1258 lines) drives the full pipeline (Verify/Prepared/Build/Build-Evidence/Audit/Gate/Reconcile/Land). `prepare-milestone.js`, `select-preflight.js`, `drain-directives.js`, `diagnose-verify-failure.js`, `run-routines.js` handle specific lifecycle stages. The workflow DSL has no `import` capability, so critical logic is duplicated inline.

2. **Experiment scripts** (`experiments/quay-perpetual-stream/scripts/`, ~80 files, ~25K lines): TypeScript/Bash modules implementing mechanical checks, composite-phase dispatch, DoD enforcement, gate checks, scheduling, and lifecycle automation.

3. **Plugin distribution** (`plugin/scripts/`, ~40 files): a vendored copy of many experiment scripts, distributed via the `dist-plugin` orphan branch as part of the quay plugin for use in other workspaces. Many files are byte-identical copies; some have minor comment-header differences; a few have diverged substantively (confirmed: `task-schema.ts` diverges at line 1 between the two copies).

4. **Driver documents**: `OUTER-LOOP.md` (the autonomous loop specification, with 16 formal invariants I₁-I₁₆ and 9 contracts C₁-C₉) and `inherited-core.md` (~532 lines of pinned methodology, DoD clause definitions, standing invariants).

The finding from the task body is accurate: small changes have repeatedly deformed unrelated behavior because no inventory exists of which invariant each piece owns and which other copies are duplicates to remove. Concrete examples observed in the current codebase:

- **Inline mirrors in `execute-milestone.js`**: `_normalizeExecuteArgsInline` (lines 29-53) duplicates `composite-args.ts`; `_isolationPlan` computation (lines 96-104) duplicates `milestone-worktree.ts`'s `computeIsolationPlan`; `_diffAuditSnapshotLines` (lines 592-605) duplicates `composite-audit.ts`'s `diffGitSnapshots`. Each is documented as a DSL-necessity mirror, but there is no mechanical check that they stay in sync with their authoritative source.

- **Plugin/experiment mirror pairs**: `task-schema.ts` exists in both directories with only comment-header differences; `it0-enforcement-with-design-check.ts` diverges in section-heading text ("Definition of DoD" vs "Definition of Done"); `gate-script-lib.sh` is byte-identical in both. There is no mechanical rule for which copy is authoritative when they inevitably drift.

- **Single-source violations**: `gate_resolve_milestone_root` in `gate-script-lib.sh` documents that "grep for '130' outside this function is a single-source violation", yet `execute-milestone.js` (lines 96-104) contains its own inline replication of the >=130 path-prefix rule, as does the `_milestoneRootCmd` construction. The OUTER-LOOP.md select step describes concurrency limits (`.quay/config.yml loop:.concurrency`) that are also asserted in CLAUDE.md.

- **Phase-specific invariants with no ownership record**: the "SOLE commit-creator" invariant for composite Builds (composite-build.ts AC8), the "SOLE success-path writer" invariant for composite Reconcile (DIR-119-D4), the "SOLE merge owner" invariant for concurrent Land fan-in (OUTER-LOOP.md step g), and the "Land lock held for entire Land phase" invariant (DIR-123) are each asserted in multiple places (workflow prompt text, composite contract docs, CLAUDE.md, OUTER-LOOP.md) with no canonical owner.

- **OUTER-LOOP.md invariants (I₁ through I₁₆)**: 16 formal invariants, each with a listed enforcement mechanism (discipline vs. script), but no assignment of which file/script is the single authoritative executable owner enforcing each invariant.

- **inherited-core.md DoD prose vs it0-dod-check.ts clauses**: `inherited-core.md` defines the DoD clauses in prose; `it0-dod-check.ts` (~919 lines, 13 clauses) is their mechanical enforcer. The prose definitions and the executable implementation are two copies of the same normative structure.

### Chosen mechanism

A two-file mechanism: an **invariant-ownership manifest** (single source of truth for invariant-to-owner assignment) plus a **mechanical enforcement script** (validates internal consistency of the manifest), wired into the DoD gate as a new clause.

1. **Invariant-ownership manifest** (`experiments/quay-perpetual-stream/invariant-ownership.md`) — a structured markdown file enumerating every load-bearing invariant of the milestone workflow. For each invariant, it records exactly one `[authoritative]` executable owner (a file path), and classifies every other occurrence as one of:
   - `[generated-view]` — a file derived from the authoritative source (e.g., `backlog.md` generated by `it0-backlog-regen.ts`)
   - `[compatibility-adapter]` — a copy maintained for distribution/portability that must stay in sync with the authoritative source (e.g., `plugin/scripts/composite-args.ts` mirroring `experiments/quay-perpetual-stream/scripts/composite-args.ts`)
   - `[duplicate-to-remove]` — a redundant occurrence scheduled for deletion by downstream crystallization milestones (DIR-124-B/C/D)
   - `[dsl-necessity-mirror]` — an inline copy in a workflow DSL script that cannot `import`; the mirror's identity is recorded so anti-drift checks can compare it against the authoritative source

   The manifest is mirrored into `plugin/` as a `[compatibility-adapter]` so the quay plugin distribution carries the ownership map. The experiment-side copy is authoritative.

2. **Enforcement script** (`experiments/quay-perpetual-stream/scripts/workflow-invariant-ownership.mjs`) — a Node.js ESM script (compatible with Node's built-in test runner, `--experimental-strip-types` compatible) that parses the manifest and mechanically validates two core rules:
   - **Single-authoritative-owner rule**: No invariant has two or more occurrences marked `[authoritative]`. Violation is a hard failure (exit 1).
   - **Owner-exists rule**: Every `[authoritative]` owner path resolves to an existing file. Violation is a hard failure (exit 1).

   Optional extended checks (enabled by flags, deferred to DIR-124-B):
   - **DSL-mirror anti-drift** (`--check-dsl-mirrors`): For each `[dsl-necessity-mirror]` occurrence, assert the mirror text in the workflow file matches the authoritative source (structural fingerprint comparison).
   - **Compatibility-adapter staleness** (`--check-adapters`): For each `[compatibility-adapter]` occurrence, assert the adapter file's structural fingerprint matches the authoritative source's.

### Manifest format: structured markdown, not YAML/JSON/table

The manifest uses heading-delimited blocks with key-value lines -- not free-form prose -- so the enforcement script can parse it reliably:

```
## Invariant: <short-name>
- **Rule:** <one-sentence statement of the invariant>
- **Authoritative owner:** `<repo-root-relative-path>` `[authoritative]`
- **Other occurrences:**
  - `<repo-root-relative-path>` `[classification]` `<rationale>
```

**Format rationale.** Markdown is human-readable, renders in the task board web UI, and is already the format of every other source-of-truth document in the repo (tasks, charters, inherited-core, ADRs). The enforcement script parses it structurally (heading-delimited sections with key-value lines via `extractSection` from `task-schema.ts`), not with a markdown parser. This avoids introducing a new file format while remaining mechanically parseable. A GFM table format was considered but rejected: the manifest is estimated at ~150 rows; heading-delimited blocks are self-contained, easier to diff, and align with the repo's existing `##`-section conventions.

### Enforcement design (control and data flow)

The enforcement script:

1. Reads `invariant-ownership.md` and extracts all `## Invariant:` blocks via section parsing (reusing `extractSection` from `task-schema.ts`).
2. For each block, extracts the `Authoritative owner:` line (fails if missing, fails if more than one).
3. Validates that the owner path exists on disk.
4. Collects all owner paths into a set; any duplicate owner path across different invariants is a warning (not a hard failure -- one file can own multiple invariants, but two invariants claiming the same rule via different owners is caught by rule 1).
5. Counts `[duplicate-to-remove]` entries and emits the deletion list as structured output (JSON with a `deletionList` field) for downstream consumption by DIR-124-B/C/D.

**Exit codes.** 0 = clean (no violations). 1 = invariant-ownership violation (two authoritative owners, or missing authoritative owner file). 2 = usage/environment error (missing Node, unparseable manifest, manifest file absent when `--require-manifest` flag is set).

**Anti-drift of DSL mirrors and compatibility adapters is out-of-scope for this child.** The `--check-dsl-mirrors` and `--check-adapters` flags are defined in the enforcement script's CLI contract but their implementation is deferred to DIR-124-B (the crystallization child that consumes this child's deletion list). This child only implements the single-authoritative-owner check and the owner-exists check. The DSL-mirror entries are recorded in the manifest metadata so DIR-124-B can consume them, but are not mechanically compared here.

### Defaults and failure behavior

- **Missing manifest (soft-launch):** If `invariant-ownership.md` is absent when the enforcement script runs, the enforcement script exits 0 with a warning ("no manifest found -- invariant ownership unchecked") rather than failing closed. This is deliberate: the manifest does not yet exist at this milestone's start, and failing closed would deadlock the very milestone that creates it. Once the manifest lands, it is self-hosting (the manifest's own entry records its owner, and the enforcement script validates that entry on subsequent runs). The `--require-manifest` flag (for use in CI or strict-audit contexts) changes this to exit 2 when the manifest is absent.
- **Duplicate authoritative owners:** Exit 1 with a diagnostic naming both entries. The DoD gate fails.
- **Missing owner file:** Exit 1 with a diagnostic naming the missing path. The DoD gate fails.
- **Parse failure:** Malformed manifest (unparseable structure, missing required fields on an invariant block) produces exit 2. The DoD gate treats exit 2 as `DodCheckEnvError` and the milestone fails.
- **Clause 13 runs unconditionally** in the DoD gate, mirroring clauses 10/11/12. A FAIL from the enforcement script is a DoD failure and blocks Land.
- The enforcement script's exit code is the only output that matters for the DoD gate. Human-readable detail goes to stdout; structured JSON (deletion list, violation details) goes to stdout in a format the DoD check can capture.

### Compatibility

This is a net-new file and script. No existing behavior is modified. The new DoD clause is additive (clause 13); existing clauses 0-12 are untouched. The manifest is the single source of truth for invariant ownership, but no existing file is forced to reference it -- that is the job of downstream crystallization milestones (DIR-124-B/C/D) which consume the deletion list. The enforcement script does not modify any existing file.

The manifest is forward-only. Milestones that predate this mechanism are not retroactively checked -- the soft-launch missing-manifest behavior (exit 0 with warning) means pre-existing milestones that lack the manifest do not fail the DoD gate.

The manifest exists at both `experiments/` and `plugin/` paths. The enforcement script reads from the workspace root, resolving whichever path the workspace uses.

### Risks

1. **Manifest staleness.** The manifest is hand-maintained. A future milestone that adds a new invariant but forgets to update the manifest will not be caught by the enforcement script (it only validates internal consistency, not completeness). Mitigation: the completeness problem is deferred to DIR-124-C (anti-drift), which can add a scan that cross-references the manifest against actual code patterns. For now, the manifest's value is in making ownership explicit for the invariants it does record, not in guaranteeing exhaustive coverage.

2. **DSL-mirror drift.** The inline mirrors in `execute-milestone.js` are documented as `[dsl-necessity-mirror]` entries but not mechanically compared to their authoritative sources in this child. A future edit to `composite-args.ts` that forgets to update the inline mirror will not be caught. Mitigation: DIR-124-B's scope includes anti-drift checks for these mirrors, consuming the mirror list from this manifest.

3. **Plugin-mirror drift.** Files in `plugin/scripts/` that are byte-identical today may diverge as the experiment copies evolve. Mitigation: same as above -- DIR-124-B adds the `--check-adapters` enforcement.

4. **Classification disagreements.** Two authors may disagree on whether an occurrence is a `[compatibility-adapter]` vs a `[duplicate-to-remove]`. The manifest records the classification; the enforcement script only verifies structural validity (one authoritative owner, no orphans), not semantic correctness of the classification. Classification correctness is an audit concern.

5. **Large manifest.** The initial manifest is estimated at ~150 rows (16 OUTER-LOOP invariants + 13 DoD clauses + ~8 phase-sequence invariants + 40+ script duplicates + ~5-10 inline mirrors + ~10 contracts + ~10 workflow invocation points). Maintenance burden is low because invariants change infrequently.

### Alternatives considered and rejected

1. **Prose-only manifest with no enforcement.** Rejected per ADR-004: prose gets paraphrased away. The value of the manifest is in the mechanical check that prevents two owners from silently diverging. Without enforcement, the manifest becomes documentation that rots at the same rate as the undocumented status quo.

2. **YAML/JSON manifest format.** Rejected because every other source-of-truth document in this repo is markdown (tasks, charters, inherited-core, ADRs). Introducing a new format for one file adds cognitive overhead with no benefit -- the manifest's structure is simple enough (heading-delimited sections with key-value lines) that a markdown parser is unnecessary.

3. **GFM table manifest format.** Rejected at ~150 rows. Heading-delimited blocks are self-contained, easier to diff and review individually, and align with the repo's existing `##`-section conventions. A table would require maintaining column alignment across 150+ rows.

4. **Embedding ownership metadata in each invariant's source file** (e.g., a comment at the top of `composite-args.ts` declaring "I own the args-normalization invariant"). Rejected because the manifest is the single source of truth -- embedding ownership in the source scatters the inventory across dozens of files, making it impossible to answer "who owns what?" with a single read. It also makes the duplicate-authoritative-owner check infeasible (it would require parsing 40+ files to find conflicts). A single manifest file makes the check a single-file parse.

5. **Auto-generating the manifest from code analysis.** Rejected because many invariants are semantic, not syntactic (e.g., "SOLE commit-creator" is a design constraint enforced by prompt text and agent discipline, not a function signature). An auto-generator would produce a large list of function-exports but miss the architectural invariants that are the actual load-bearing rules. The manifest is hand-authored for precision, then mechanically enforced for consistency.

6. **Failing closed when the manifest file is absent.** Rejected because this milestone creates the manifest -- it cannot exist before this milestone lands. A fail-closed approach would deadlock. The soft-launch (exit 0 with warning) allows the manifest to be created and landed, after which it becomes self-hosting (the manifest's own entry records itself, and the enforcement script validates that entry on subsequent runs).

7. **Integrating the enforcement into an existing DoD clause rather than a new clause.** Rejected because the invariant-ownership check is a distinct concern with its own failure modes and its own fixture. Adding it to an existing clause would conflate unrelated failure reasons, making diagnosis harder. A new clause (Clause 13) keeps the check independent and its failure self-describing.

8. **Using the `quay gate` engine (QENG) instead of a direct `execFileSync` shell-out.** Rejected because the invariant-ownership check is a workspace-level structural validator, not a per-task gate. The quay gate engine is task-scoped (it evaluates `quay gate <task-id>`). Running the enforcement as a gate would require a dummy task, which is a category error. The direct `execFileSync` pattern used by clauses 10/11/12 is the established mechanism for workspace-level mechanical checks and is the right fit here.

9. **Making the enforcement a standalone gate rather than a DoD clause.** Rejected. Wiring into `it0-dod-check.ts` means the check runs on every milestone Land with zero additional wiring -- the DoD enforcer already exists, already runs unconditionally, and already has the clause-adding pattern (clauses 10/11/12 were added using the exact same mechanism). A standalone gate would require additional OUTER-LOOP.md and `execute-milestone.js` wiring.

10. **Retroactive application to pre-existing milestones.** Rejected. Pre-existing milestones lack the manifest; requiring them to backfill it would be a retroactive scope expansion explicitly excluded by the charter. The soft-launch behavior handles the transition.
