**type:** execution

## Proposal

Record an invariant-ownership manifest for the milestone workflow: every load-bearing invariant
names one intended executable owner and classifies every other occurrence as generated view,
compatibility adapter, or duplicate to remove. Add mechanical enforcement that rejects two
authoritative executable owners for the same rule.

Third child of the DIR-124-A split (mechanism M3). No dependencies.

**File home (split review finding):** the manifest is a first-class checked file at
`experiments/quay-perpetual-stream/invariant-ownership.md` (mirrored at
`plugin/invariant-ownership.md`), and the enforcement script is
`experiments/quay-perpetual-stream/scripts/workflow-invariant-ownership.mjs` — both named in
Touches, not left homeless.

## Chosen mechanism

M3 from the split-review inventory. `scripts/workflow-invariant-ownership.mjs` parses the manifest
and the workflow/OUTER-LOOP/composite files, and fails if any invariant has two entries marked
`authoritative`. The manifest itself is the single source of truth for invariant → owner
assignment; `it0-dod-check.ts` (or a sibling) invokes the enforcement script as part of the DoD
gate.

## Finding

The live workflow is ~490 lines / 38 KB and owns argument compatibility, task policy, Verify
caching, preparation gating, Build method, Audit judgment and writes, Gate dispatch, Git/worktree
semantics, lifecycle mutation, dashboard/backlog updates, and serial/concurrent Land variants.
Small changes have repeatedly deformed unrelated behavior; there is no inventory of which invariant
each piece owns and which other copies are duplicates to remove.

## Requested action

1. Enumerate every load-bearing invariant of the installed milestone workflow and assign each ONE
   intended executable owner.
2. Classify every other occurrence as generated view, compatibility adapter, or duplicate to
   remove.
3. Add mechanical enforcement: two `authoritative` owners for the same invariant fails the check.
4. Wire the enforcement into the DoD gate (`it0-dod-check.ts`), not a standalone document.
5. Produce the duplicate/deletion list that downstream crystallization (DIR-124-B/C/D) consumes.

## Acceptance Criteria

- [ ] The invariant-ownership manifest is a checked file (`invariant-ownership.md`, both mirrors)
  with one authoritative owner per invariant.
- [ ] Enforcement (`workflow-invariant-ownership.mjs`) rejects two authoritative executable owners
  for the same rule (falsifiable: a two-owner fixture fails).
- [ ] Every known workflow/OUTER-LOOP/composite duplicate is identified in the manifest's
  deletion list.
- [ ] The enforcement script is wired into the DoD gate and runs as part of `it0-dod-check`.
- [ ] No post-Land Wiring Audit, lifecycle-promotion policy, worktree redesign, stage scheduler, or
  resource lease is introduced by this child (parent AC9 non-goal).

## Alternatives considered

- **Prose manifest only** — rejected: prose gets paraphrased away (ADR-004); enforcement must be
  mechanical.
- **Embedding ownership in task bodies** — rejected: the manifest is the single source of truth;
  task bodies reference it, not duplicate it.
