## Proposal

**Problem framing (grounded in current code, verified 2026-08-01 at commit 923f563e)**

The two installed workflow files -- `.claude/workflows/execute-milestone.js` (1257 lines) and `.claude/workflows/prepare-milestone.js` (~1550 lines) -- each carry a structured `export const meta` surface declaring `name`, `description`, and `phases[{title, detail}]`. This metadata is the advertised contract: what phases the workflow has, what outcomes it returns, what mechanisms it uses. The executable driver contract is the same file's body: `phase()` call sites, `agent()` dispatch sites, return-outcome literals, `node --experimental-strip-types` invocations, worktree/isolation code paths, cache/resume logic, and gate dispatch arrays. Nothing mechanically compares the metadata surface against the executable body.

Three classes of drift are confirmed present:

1. **Phase-set misalignment (execute-milestone.js):** `meta.phases` declares 7 entries (Verify, Prepared, Build, Audit, Gate, Reconcile, Land). The body contains 8 distinct `phase()` call sites -- the 8th, `phase('Build-Evidence')` at line 501, was added by M238 (`gap-build-evidence-manifest-missing`) without a corresponding metadata entry. A grep of `phase(` in the body returns: Verify (line 66), Prepared (234), Build (389), Build-Evidence (501), Audit (719), Gate (817), Reconcile (919), Land (961). The metadata's phases array has no Build-Evidence entry.

2. **Return-outcome claim stale (execute-milestone.js):** `meta.description` claims the workflow "Returns {outcome: 'done'|'needs-human'|'building'} -- 'building' means a background task was dispatched; the caller polls and resumes." A grep of all `{ outcome:` / `outcome:` return-value literals across the 1257-line body yields zero occurrences of the literal `'building'`. The actual return-outcome values found are: `'done'` (lines 385, final serial return, final concurrent return ~line 1010), `'needs-human'` (lines 49, 114, 219, 287, 315, 355, 382, 422, 492, 537, 627, 655, plus Land failures), and `'revision-needed'` (lines 237, 261, introduced by DIR-117-B/M195's Prepared phase). The `'building'` claim describes a background-dispatch pattern no longer used -- all agent dispatches are awaited inline, never unawaited. Additionally, `'revision-needed'` is an actual return outcome absent from the metadata's claimed union.

3. **Phase re-entry multiplicity not reflected (prepare-milestone.js):** `meta.phases` declares 8 entries with the unique label set {Admission, Preflight, ProposalAuthors, Adjudicate, ProposalReview, PlanAuthor, PlanCheck, Receipt}. The body contains 11 `phase()` call sites across these same 8 unique labels. The mismatch is re-entrant multiplicity, not label-set divergence: `phase('Preflight')` is called at two logically distinct insertion points -- line 628 (content preflight, gating ProposalAuthors) and line 1354 (plan-shape preflight, gating PlanCheck round 1). `phase('ProposalAuthors')` is called at lines 660 and 666 (resume-skip path and cold path). `phase('Adjudicate')` is called at lines 662 and 704 (same resume/cold branching). `phase('ProposalReview')` appears exactly once, at line 746. The convergence loop (the `while(true)` block spanning lines 746-1305) dispatches `agent()` calls with phase metadata fields and invokes `_recordPhaseBoundary()`, neither of which is a `phase()` call -- zero additional `phase()` invocations exist inside the convergence loop. The metadata's single `{title: 'Preflight', ...}` entry cannot distinguish the content-vs-plan-shape insertion points, and no annotation convention exists for re-entrant phase sites.

Additional drift classes that are currently clean but have no mechanical guard:

4. **Worktree/isolation logic absent from metadata:** execute-milestone.js contains 40+ references to `_useWorktree`, `_isolationPlan`, `isolationMode`, or `worktree` (DIR-123). Neither `meta.description` nor any `meta.phases[]` entry addresses worktree isolation -- a substantial mechanism with zero metadata mention. prepare-milestone.js contains zero worktree references (confirmed by grep). The metadata surface says nothing about which workflow supports worktree isolation.

5. **Node invocation convention divergence:** execute-milestone.js uses `node --experimental-strip-types` at all 18 call sites (never `--no-warnings`). prepare-milestone.js uses `node --no-warnings --experimental-strip-types` at all 8 call sites (always `--no-warnings`). The two files have contradictory conventions with no documented rationale -- an agent prompt embedding a literal node command is wrong for one of the two files.

6. **Gate-count imprecision:** `meta.phases`' Gate entry detail says "all absorb-phase mechanical gate checks" -- the actual gate dispatch array dispatches: vmeta-lag, dash-budget, tree, worktree, N instances of split-or-commit (one per member task), and build-evidence -- 5 named types plus variable split-or-commit, not a fixed count.

7. **Cache/resume description claims not reflected in prepare-milestone.js metadata:** The `meta.description` describes "real, resumable lifecycle stage" and "resumeFromAdjudicatedProposal / --decide-resume" -- the body has extensive resume/cache logic (lines 490-570 for `--decide-resume`, convergence checkpoint write at line 988), but `meta.phases` entries do not flag which phases are resumable. Conversely, execute-milestone.js has substantial cache-fingerprint/resume logic in the Verify phase (lines 77-212) with zero metadata mention.

8. **Mirror-byte-identity drift potential:** Both mirror pairs are currently byte-identical (confirmed: `diff` returns zero for both `execute-milestone.js` and `prepare-milestone.js` across `.claude/workflows/` and `plugin/workflows/`). Nothing mechanically verifies this on every milestone Land. A one-line edit to one mirror without the other would go undetected.

The cost of this drift is not hypothetical -- the DIR-124-A split review itself found multiple stale claims during a manual audit; a mechanical check would have caught them at Land time, before they could mislead a subsequent agent or human operator reading the metadata as a contract.

**Chosen mechanism**

A single checked Node.js script, `experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs`, with a byte-identical mirror at `plugin/scripts/workflow-metadata-conformance.mjs`. The script is a deterministic, import-free Node ESM module (runs under `node --experimental-strip-types`) that is a pure function (importable for testing) with a thin CLI wrapper for DoD-gate shell-out, following the established pattern of `it0-dod-check.ts` (importable `runDodCheck` + `main(argv)` wrapper) and `it0-split-or-commit-check.ts` (importable pure functions + CLI path).

**WIRING-CLAIM C1 (extraction method):** The checker uses targeted regex/grep extraction against the DSL's well-known structural conventions, NOT AST parsing. This matches the established pattern of `it0-dod-check.ts` which uses regex-based extraction for all its checks (clause 0 AC/DoD section parsing via `extractSection`, clause 5 exemption-language scanning, clause 6 escrow-language detection, clause 7 coverage-percentage regex). The workflow files reference DSL globals (`agent`, `phase`, `parallel`, `log`, `args`) that are not importable -- regex extraction avoids the DSL-global-reference problem entirely. A JS parser dependency (acorn, babel, etc.) would add supply-chain risk disproportionate to the benefit. The checker imports only Node.js built-ins (`fs`, `path`, `child_process`); extraction functions are pure regex/string operations on source text. The test suite verifies extraction correctness against known fixtures (the real workflow files plus fabricated-stale fixtures).

**WIRING-CLAIM C2 (pure-text extraction, never eval):** The checker reads workflow source files as text strings via `fs.readFileSync`. It never `eval()`s, never `import()`s, and never executes the workflow source. This avoids the DSL-global-reference problem entirely and makes the checker safe to run in any Node.js context.

**WIRING-CLAIM C3 (FAIL/WARN severity taxonomy):** Following the DIR-100-C diagnostic severity taxonomy: a metadata claim that is positively false (phase listed but never called, outcome claimed but never returned) is a FAIL (exit-impacting, RED). An executable mechanism with no metadata mention is a WARN (AMBER -- omission, not a lie; metadata is a summary, not an exhaustive catalog). The return object distinguishes `failures[]` from `warnings[]`; only `failures.length > 0` drives exit code 1. `--json` output includes both arrays.

**WIRING-CLAIM C4 (fixture isolation):** RED/GREEN fixture files live under `experiments/quay-perpetual-stream/test/fixtures/`, never in `.claude/workflows/`. The `--files` flag accepts arbitrary paths; the test passes fixture paths; the production invocation passes the real workflow paths. The test asserts zero references to the fixture filename in `.claude/workflows/`.

**WIRING-CLAIM C5 (dual-mirror byte-identity for the checker itself):** Both `experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs` and `plugin/scripts/workflow-metadata-conformance.mjs` are byte-identical. The test reads both files and asserts `file1Content === file2Content`. The existing `anti-drift-touches-check.sh` pattern (which already verifies mirror identity for other scripts) prevents future divergence.

**WIRING-CLAIM C6 (DoD integration):** A new clause (next available number -- currently clause 13, following the 0-12 range) in `it0-dod-check.ts` shells out to `workflow-metadata-conformance.mjs` via `execFileSync`, exactly matching the established pattern of clauses 3, 4, 10, 11, and 12: resolve `scriptPath` relative to `__dirname`, fail on missing script with `DodCheckEnvError`, run `execFileSync(scriptPath, ['--json'], {encoding: 'utf8'})`, parse the JSON, push PASS/FAIL lines, call `dispositionedClauses.add('workflow-metadata-conformance')`. The clause is mechanically unconditional (always runs, same as clauses 3/4/10/11/12), so it is added to `MECHANICALLY_UNCONDITIONAL_CLAUSES`.

**WIRING-CLAIM C7 (enforcement grep-ability):** The integration point in `it0-dod-check.ts` must be mechanically verifiable -- `grep -r 'workflow-metadata-conformance' experiments/quay-perpetual-stream/scripts/it0-dod-check.ts` returns the integration line. A RED finding blocks the DoD gate (the milestone cannot complete). The existing `dod-fixture-selfcheck.sh` exercises the clause through a fixture (a milestone's charter must be accompanied by an ABSORB entry that will exercise the clause).

**WIRING-CLAIM C8 (node-convention divergence as documented WARN):** The checker compares `--no-warnings` presence between the two files. If one file uses `--no-warnings` at every call site and the other uses it at zero call sites, and no explicit comment in either file documents this as intentional divergence, the checker reports WARN -- the divergence could be intentional but without a documented rationale it is indistinguishable from accidental drift.

The checker operates on 4 files: `.claude/workflows/execute-milestone.js`, `plugin/workflows/execute-milestone.js`, `.claude/workflows/prepare-milestone.js`, and `plugin/workflows/prepare-milestone.js`. It reads each as text, extracts the surface it needs, and reports.

**Concrete checks performed (per workflow file):**

**Check 1 -- Phase-list claim vs. actual phases (FAIL-level):** Parse `meta.phases[].title` and compare against `phase('<label>')` invocations in the body. Any phase label in the body but not in metadata is FAIL (stale metadata -- a phase was added to the body without updating the metadata). Any phase label in metadata but not in the body is FAIL (phantom phase -- metadata claims a phase the body never enters). Re-entrant labels (same label at multiple call sites, e.g., `Preflight` at lines 628 and 1354) are counted as one logical phase for set-comparison purposes; call-count multiplicity is reported separately as WARN when > 1 and not documented in the metadata.

**Check 2 -- Return-outcome claim vs. actual return sites (FAIL-level):** Parse the outcome-value literals claimed in `meta.description` (e.g., `'done'|'needs-human'|'building'`) and compare against all `outcome:` literal values at `return` sites in the body. Any outcome value claimed in metadata but absent from actual returns is FAIL (stale claim -- promises an outcome that cannot occur). Any outcome value present in actual returns but absent from metadata is FAIL (incomplete claim -- a real outcome shape has no metadata documentation). The checker extracts outcome literals from patterns matching `outcome:\s*'([^']+)'` and `outcome:\s*"([^"]+)"` in the body, and from `{outcome:\s*"[^"]+\|[^"]+\|..."`-shaped claims in the description.

**Check 3 -- Agent-count alignment, if claimed (FAIL-level if claimed, informational otherwise):** If `meta.description` includes a numeric claim about agent dispatches (e.g., "N=2 independent agents"), compare against the body's `await agent(` call count. Mismatch is FAIL. If no numeric claim exists, the count is reported as informational only (no FAIL/WARN). Currently neither workflow's description makes a numeric agent-count claim, so this check is informational in the initial deployment.

**Check 4 -- Node invocation convention consistency (WARN-level):** Count `node --experimental-strip-types` invocations per file, distinguishing `--no-warnings` presence. If the two files (execute-milestone.js and prepare-milestone.js) have contradictory conventions (one uses `--no-warnings` at every call site, the other at zero call sites) AND no explicit comment in either file documents the intentional divergence, report WARN. If `meta.description` or any phase detail mentions a specific node-invocation pattern that diverges from the body's actual invocations, report FAIL.

**Check 5 -- Worktree/isolation mechanism mention (WARN-level):** If the body contains substantial worktree/isolation logic (heuristic: >5 references to `_useWorktree`, `_isolationPlan`, `isolationMode`, `worktree`, `milestone-worktree.ts`) but neither `meta.description` nor any phase detail mentions "worktree" or "isolation", report WARN (metadata omission, not a false claim). Conversely, if the metadata claims worktree support but the body has zero references, report FAIL (false claim).

**Check 6 -- Cache/resume mechanism mention (FAIL-level if claimed, WARN-level if unclaimed mechanism present):** If `meta.description` mentions "cache", "resume", or "resumable", the checker verifies that corresponding mechanism patterns exist in the body: for execute-milestone, `cacheFingerprints` / `_cached(` / `verifyCacheUpdates`; for prepare-milestone, `resumeFromAdjudicatedProposal` / `--decide-resume`. A stale claim with no matching mechanism is FAIL. Conversely, if the body has substantial resume/cache logic but metadata never mentions resumability, report WARN.

**Check 7 -- Gate-count precision (WARN-level):** If `meta.phases[]` Gate entry or `meta.description` implies a specific or fixed set of gates, compare against the body's `const gates = await parallel([...])` array entries. Mismatch in gate-type count is WARN. If no specific number is claimed (currently the description says "all absorb-phase mechanical gate checks" -- a non-specific claim), this is informational.

**Check 8 -- Mirror byte-identity (FAIL-level):** `.claude/workflows/<name>.js` and `plugin/workflows/<name>.js` MUST be byte-identical for each workflow name. Non-identical is FAIL.

**Check 9 -- Re-entrant phase documentation (WARN-level):** When the same phase label appears at multiple call sites in the body (e.g., `Preflight` at 2 sites, `ProposalAuthors` at 2 sites, `Adjudicate` at 2 sites in prepare-milestone.js), and the metadata `phases[]` has only a single entry for that label, report the multiplicity as WARN with the call-site line numbers. Branch-duplicated phases (resume-skip vs. cold path) are semantically different from structurally distinct re-entries (content preflight vs. plan-shape preflight), and the metadata consumer cannot distinguish them without annotation.

**RED/GREEN negative control:** The checker ships with a deliberately-stale fixture workflow file under `experiments/quay-perpetual-stream/test/fixtures/` (never committed to `.claude/workflows/` -- it is a test-only file) that fabricates a stale claim: a `meta.phases` entry for a phase (`DeadPhase`) with no corresponding `phase()` call in the body. The checker MUST FAIL this fixture (RED). A corrected variant (same fixture minus the phantom phase entry) MUST PASS (GREEN). Additionally, the checker run against the real source files should produce findings for the 8 known discrepancies listed above -- these serve as the initial RED baseline that the implementation metadata fix will turn GREEN. This proves the checker is not vacuously green. The test also includes a "real-sourcefiles-were-parseable" regression test that fails if the regex no longer matches the real source files.

**Key design decisions**

1. **Regex/grep extraction, not AST parsing:** The workflow DSL is a constrained surface with well-known, regex-friendly structural conventions (`phase('...')`, `meta.phases = [...]`, `outcome:` literals). Full AST parsing would add a dependency chain (acorn, babel) and fragility (minified output, non-standard syntax, non-importable DSL globals) for no gain. The existing `it0-dod-check.ts` itself uses regex extraction for all its checks, establishing the pattern. The workflow files reference DSL globals (`agent`, `phase`, `parallel`, `log`, `args`) that are not importable -- regex extraction avoids the DSL-global-reference problem entirely.

2. **FAIL on false claims, WARN on omissions:** A metadata claim with no corresponding executable mechanism is an assertion that is factually false -- it must block the DoD gate. An executable mechanism with no metadata mention is an omission -- metadata is a summary, not an exhaustive catalog, and the omission may be intentional. This distinction matches the DIR-100-C diagnostic severity taxonomy: RED = claim is positively false, AMBER = suspicious but not provably false, GREEN = claim verified.

3. **Separate test fixture, not a self-modifying test:** The RED negative control fixture file lives under `test/fixtures/` and is never committed to `.claude/workflows/`. The checker reads the real workflow files at runtime; the test passes a fixture path as an override via `--files`. This avoids the circularity of deliberately breaking a production workflow file to prove the checker works.

4. **Single script with two byte-identical mirrors:** Following the established pattern (e.g., `anti-drift-touches-check.sh`, `tree-hygiene-check.sh` all have dual-mirror copies), the conformance script has two byte-identical copies. The test verifies both mirrors are byte-identical via a simple `file1Content === file2Content` assertion. The `anti-drift-touches-check.sh` pattern prevents future divergence.

5. **DoD gate integration via shell-out, not inline clause logic:** The new DoD clause shells out to `workflow-metadata-conformance.mjs` as a subprocess, exactly as clauses 3, 4, 10, 11, and 12 do for their checks. This keeps the conformance logic independently runnable, testable, and debuggable without modifying `it0-dod-check.ts`.

6. **Pure-text extraction, never evaluation:** The checker never `eval()`s or `import()`s the workflow source files. All extraction is from the text representation. This avoids the DSL-global-reference problem and makes the checker safe to run in any context.

7. **Re-entrant phase handling via label deduplication:** The same `phase('Preflight')` label appears at two distinct logical points in prepare-milestone.js. The checker deduplicates labels for set-comparison purposes and reports call-count multiplicity separately as WARN, rather than counting each call site as a separate logical phase. Branch-duplicated phases (resume-skip vs. cold path for ProposalAuthors and Adjudicate) are also deduplicated, with their line-number pairs reported for human review.

8. **No separate gate registration:** The checker is wired into the DoD enforcer's existing clause infrastructure, not registered as a new `.quay/gates.yml` gate. The DoD enforcer already has the charter-fixture/ABSORB-entry/clause-disposition infrastructure -- adding a new clause is a ~25-line delta (following clauses 10-12's exact pattern), while a new gate would require engine registration, gate-events.jsonl appends, and a Gate-phase invocation addition.

**Defaults and failure behavior**

- **Default (no args):** Runs against the 4 hardcoded workflow file paths resolved from the repository root. Exit 0 if all hard-checks pass (failures array is empty); exit 1 if any FAIL-level check fires; WARN-only findings do not affect the exit code.
- **`--files <path...>`:** Override the default file list (for testing with fixtures). Accepts one or more `.js` workflow files; each is independently checked, and the aggregate exit code is 0 only if ALL files pass all hard-checks.
- **`--json`:** Output the full check-result as a single JSON line to stdout (for machine consumption by the DoD gate clause). Default (without `--json`) produces human-readable output to stdout with failures and warnings enumerated.
- **Missing file:** Exit 2 (environment error, matching the `DodCheckEnvError` convention in `it0-dod-check.ts`). Never silently passes on a missing workflow file.
- **Unparseable metadata:** If a workflow file has no `meta` object or the `meta` literal cannot be regex-extracted, that is a FAIL with detail `metadata-unparseable`, not a silent skip. A missing `meta` export is itself a conformance failure -- the metadata surface is a required contract.
- **WARN findings:** Reported to stdout (or in the JSON `warnings[]` array) but do not cause a non-zero exit. They surface drift that needs human attention but does not block the milestone pipeline.
- **Default invocation frequency:** The clause runs on every DoD gate invocation (every milestone that reaches the Gate phase in execute-milestone.js). There is no opt-out -- the metadata surface should always be accurate. The clause is listed in `MECHANICALLY_UNCONDITIONAL_CLAUSES`.

**Compatibility**

- **Backward compatible with existing workflows:** The checker is purely additive -- it reads files, never writes them. Existing workflow behavior is unchanged.
- **No change to workflow DSL format:** The `meta` object shape is already the established convention in both workflow files. This checker enforces its accuracy, it does not change the convention.
- **Existing DoD clauses unchanged:** The new clause is additive (next available clause number: 13). Existing clauses 0-12 are byte-identical.
- **Existing fixtures unchanged:** All existing `fixtures/dod/*.md` test fixtures continue to pass because the new clause is a shell-out -- a missing conformance script at test time (for fixture milestones) is a `DodCheckEnvError` (exit 2, not a FAIL), and the existing `dod-fixture-selfcheck.sh` infrastructure can provide a stub.
- **No new dependencies:** The script uses only Node.js built-ins (`fs`, `path`, `child_process`) -- same as every existing script in `experiments/quay-perpetual-stream/scripts/`.
- **Mirror coverage:** Both `.claude/workflows/` and `plugin/workflows/` mirrors are checked. The existing mirror-byte-identity assertion in the test suite establishes this dual-mirror verification pattern.
- **No new file format or schema:** The `meta` export is already the established convention. The checker verifies what is already claimed.

**Risks**

1. **Regex fragility:** If the workflow DSL evolves new syntax (e.g., `phase()` calls generated dynamically via a helper, template literals for phase labels, or metadata declared via `Object.assign` rather than an object literal), the regex extraction may produce false negatives. Mitigation: the checker is a single script with a well-defined extraction surface; when the DSL evolves, updating the regex patterns is a targeted change. The RED/GREEN test fixture catches regressions, and the checker's test suite includes a test that fails if the regex no longer matches the real source files (the "real-sourcefiles-were-parseable" regression test).

2. **False positives on coincidental string matches:** A comment or agent prompt containing the literal text `phase('Verify')` as an example could be counted as an invocation. Mitigation: the regex for phase extraction matches only `phase('<name>')` that is not inside a `//` comment on the same line, using a negative-lookbehind pattern. Agent prompt strings (inside template literals or concatenated strings) are a harder case -- they legitimately contain `phase(` as instructional text. Mitigation: the extraction skips lines inside template-literal contexts (backtick-delimited regions of >1 line) and inside obvious agent-prompt string arguments (heuristic: lines containing `${` interpolation adjacent to `phase(` are skipped for phase-extraction purposes, counted only for instructional-reference reporting).

3. **Metadata description natural-language parsing:** Claims embedded in `meta.description` prose (e.g., "Returns {outcome: 'done'|'needs-human'|'building'}") require regex extraction that may miss a claim phrased differently from the expected pattern. Mitigation: the checker extracts claims using explicit regex patterns keyed on known structural markers (`outcome:`, specific outcome literal strings, "cache"/"resume" keywords); if a claim format cannot be extracted, it is reported as WARN `unparseable-description-claim` rather than silently ignored.

4. **The checker itself can drift:** The checker's own extraction logic could become stale if the workflow DSL changes. Mitigation: the RED/GREEN fixture test is run by `scripts/test.sh`, so a workflow DSL change that breaks the checker's extraction would be caught by the test suite before the checker could falsely PASS. Additionally, the "real-sourcefiles-were-parseable" regression test directly checks parseability against the real files.

5. **Static, not dynamic:** The checker is a static analysis tool. It cannot verify runtime behavior (e.g., whether the `'building'` outcome path was ever actually reachable, or whether a `phase()` call inside an unreachable `if (false)` branch should count). This is by design -- the checker detects stale *claims*, not stale *runtime behavior*. The RED/GREEN negative control proves the checker catches fabricated stale claims; it does not prove the workflow actually behaves as its metadata claims.

6. **Concurrent modification hazard:** If the checker reads a workflow file while it is being edited (e.g., a concurrent build agent is modifying it), the read may capture a partially-written state. Mitigation: negligible risk -- the DoD gate runs at Gate phase, after Build completes, and workflow files are only changed by human commits or during milestone execution, not concurrently during gate evaluation.

**Non-goals (explicitly excluded)**

- Full AST validation of the workflow DSL surface (explicitly rejected -- regex extraction handles the targeted claim surface).
- Runtime verification of workflow execution (this is a static metadata-vs-contract check, not a dynamic execution tracer).
- Checking prose comments outside the `meta` object for accuracy (only the structured metadata surface is checked).
- Checking workflow files other than the four named targets and their mirrors (the scope is `execute-milestone.js` + `prepare-milestone.js` only, per the task's Touches list).
- Introducing a new lifecycle-promotion policy, worktree redesign, stage scheduler, or resource lease (per the task's AC4 non-goal).
- Post-Land Wiring Audit (per the task's AC4 non-goal).
- A workflow linter or style checker -- agent prompt text quality, label naming conventions, and schema shape consistency are out of scope.

**Explicit alternatives considered and rejected**

1. **Manual prose review of workflow metadata claims:** Rejected -- no mechanical failure when a claim drifts. A stale `meta.phases` entry or a wrong outcome shape claim is invisible to human review unless someone specifically greps for it. The checker is the executable invariant -- it fails the DoD gate on any detected drift, forcing correction before a milestone can land.

2. **Full AST validation of the workflow DSL:** Rejected -- over-scoped. The workflow DSL is a moving target with evolving globals. A full AST parser would need to track those globals' semantics, which is a much larger effort. This task targets the narrow and stable metadata-vs-driver claim surface, which regex extraction handles adequately. Additionally, a JS parser dependency (acorn, babel) would add supply-chain risk disproportionate to the benefit.

3. **Inline assertion comments (e.g., `// @assert phase-count=8`):** A comment-based assertion embedded in the workflow file itself that a linter verifies. Rejected: requires modifying the workflow files (changing the surface under test), and a comment can drift just as easily as the metadata it annotates. The independent conformance script reads the metadata surface as-is and compares it to the driver -- it does not require the metadata to be annotated.

4. **Runtime trace comparison:** Run the workflow in a sandbox, capture the actual phase transitions, and diff against metadata. Rejected: requires a live Dispatch agent + a full milestone environment for what is structurally a static check. The static approach gives the same signal at zero runtime cost and zero flakiness. Runtime coverage is also path-dependent -- a phase that is never reached in a given run is not provably absent from the code.

5. **TypeScript-based schema validation of the meta export:** Adding a `.d.ts` or converting the files to `.ts`. Rejected: the workflow files are plain `.js` files without TypeScript annotations. Adding type annotations would be a structural change to the DSL convention, not a conformance check. The regex approach reads the existing convention as-is.

6. **Making the checker a quay gate (engine-registered, like `split-or-commit`):** Rejected: the checker is a per-milestone mechanical verification, not a per-task lifecycle gate. Wiring it into the existing DoD enforcer (which already has the charter-fixture / ABSORB-entry / clause-disposition infrastructure) is the simpler, lower-risk path. A quay gate would require gate-engine registration, a gate-events.jsonl append, and a Gate phase invocation -- all heavier than a single `execFileSync` in an existing clause.

7. **Making the checker a workflow phase:** Rejected: the checker should fire on every milestone, not only on milestones that opt into it. Wiring it into the DoD gate (which already fires unconditionally) ensures coverage without adding a new phase to either workflow.
