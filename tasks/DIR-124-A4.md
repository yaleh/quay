**type:** execution

## Proposal

**Problem framing (grounded in current code)**

The installed milestone-workflow pair (`.claude/workflows/execute-milestone.js` and `prepare-milestone.js`) carries a structured metadata surface -- `export const meta` with `name`, `description`, and `phases[]` -- that documents the contract each workflow promises. The executable driver contract lives in the same file's body: `phase()` calls, `agent()` dispatch sites, `node` invocation patterns, return-statement shapes, worktree-isolation code paths, and per-phase agent/dispatch counts. Nothing mechanically compares the metadata surface against the executable driver contract.

Three classes of drift are already present in the current repository state (2026-08-01, commit 923f563e):

1. **Phase-set misalignment** (execute-milestone.js): `meta.phases` declares 7 phases (Verify, Prepared, Build, Audit, Gate, Reconcile, Land), but the body contains 8 distinct `phase()` call sites -- the `Build-Evidence` phase (added by M238/gap-build-evidence-manifest-missing) was added to the body without a corresponding metadata entry.

2. **Return-shape claim stale** (execute-milestone.js): `meta.description` claims the workflow "Returns {outcome: 'done'|'needs-human'|'building'} -- 'building' means a background task was dispatched; the caller polls and resumes." A grep of all return statements in the body reveals zero occurrences of `{outcome: 'building'}`. The actual return shapes are `'done'`, `'needs-human'`, and `'revision-needed'` (the Prepared-phase contract introduced by DIR-117-B/M195). The `building` claim describes a dispatch pattern this workflow no longer uses; all agent dispatches are awaited inline, never backgrounded.

3. **Phase re-entry multiplicity not reflected** (prepare-milestone.js): `meta.phases` declares 8 phases with the unique label set {Admission, Preflight, ProposalAuthors, Adjudicate, ProposalReview, PlanAuthor, PlanCheck, Receipt}. The body contains 11 `phase()` call sites across the same 8 unique labels -- the unique-label sets match exactly (both 8). The issue is re-entrant multiplicity, not count mismatch: Preflight is called twice at two logically distinct insertion points (content checks and plan-shape checks, both under label `'Preflight'`), and ProposalAuthors and Adjudicate are each called twice in alternate if/else branches (resume-skip and cold paths). The metadata's single `{title: 'Preflight', ...}` entry cannot distinguish its two logically distinct insertion points, and no annotation convention exists for re-entrant or branch-duplicated phase call sites.

Further drift classes that are currently clean but have no mechanical guard against regressing include: worktree/isolationMode logic (97 lines in execute-milestone.js, DIR-123, but `meta.description` and phase details make no mention of worktree isolation); `node --experimental-strip-types` invocation count (18 call-sites in execute-milestone.js, 8 in prepare-milestone.js -- any future refactor switching to a bundled entrypoint would silently invalidate agent prompts that embed literal `node --experimental-strip-types` commands); description claims about gate counts (the description says "all absorb-phase mechanical gate checks" but the Gate phase now runs vmeta-lag/dash-budget/tree/worktree/split-or-commit-per-task/build-evidence -- six gate types, not a fixed count); and node invocation convention divergence (prepare-milestone.js uses `node --no-warnings --experimental-strip-types` at all 8 call sites; execute-milestone.js uses `node --experimental-strip-types` at all 18 call sites -- no `--no-warnings` -- and the two files' convention should be intentionally aligned or intentionally divergent, not accidentally divergent).

The cost of this drift is not hypothetical -- the DIR-124-A split review itself found multiple stale claims in the metadata surface during a manual audit; a mechanical check would have caught them at Land time.

**Chosen mechanism**

A single checked Node.js script, `experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs`, with a byte-identical mirror at `plugin/scripts/workflow-metadata-conformance.mjs`. The script is a deterministic, import-free Node ESM module (runs under `node --experimental-strip-types`) that is a pure function (importable for testing) with a thin CLI wrapper for DoD-gate shell-out, following the established pattern of `it0-dod-check.ts` (importable `runDodCheck` + `main(argv)` wrapper).

The checker does NOT parse the full AST of either file (rejected alternative -- see below). Instead it uses targeted regex/grep extraction against the DSL's well-known structural conventions, matching the established pattern of `it0-dod-check.ts` which itself uses regex extraction for all its checks (clause 0 AC/DoD section parsing, clause 5 exemption-language scanning, clause 6 escrow-language detection).

**WIRING-CLAIM C1 (extraction method):** Conformance check uses regex extraction, not AST parsing. The checker's implementation imports no parser library; extraction functions are pure regex/string operations.

The checker operates on 4 files: `.claude/workflows/execute-milestone.js`, `plugin/workflows/execute-milestone.js`, `.claude/workflows/prepare-milestone.js`, and `plugin/workflows/prepare-milestone.js`. It reads each as text (never `eval()`s or `import()`s -- avoids the DSL-global-reference problem), extracts the surface it needs, and reports.

The checker performs the following comparisons for each workflow file:

1. **Phase-list claim vs. actual phases**: Parse `meta.phases[]` entries and compare against `phase('...')` invocations in the executable body. Any phase in the body not in metadata is a FAIL (stale metadata); any phase in metadata not in the body is a FAIL (phantom phase). Distinguishes "unique labels" from "call count" to handle re-entrant phases (e.g., `phase('Preflight')` called twice in prepare-milestone.js) -- a re-entrant label is counted as one logical phase for set-comparison purposes when the metadata explicitly documents the re-entry.

2. **Return-outcome claim vs. actual return sites**: Parse the `outcome:` literal strings in the metadata description (e.g., `"done"|"needs-human"|"building"`) and compare against all `{ outcome:` / `"needs-human"` / `"revision-needed"` / `"done"` / `"building"` literal outcome-value return sites in the executable body. Any outcome value that appears in actual returns but NOT in the metadata description is a FAIL (stale claim).

3. **`node --experimental-strip-types` invocation count**: The metadata description or phase details may reference "node --experimental-strip-types" -- the checker counts the actual call-sites and compares.

4. **Worktree/isolation mention claim**: If metadata or any phase detail mentions "worktree" / "isolation", the checker verifies that `$a.isolationMode` or worktree-related logic exists in the executable body. Conversely, if the body has substantial worktree logic (e.g., >50 lines mentioning `_useWorktree` / `_isolationPlan`) but metadata never mentions it, that is a WARN (not a hard FAIL -- metadata omission is less dangerous than a false claim, but it is still drift).

5. **Cache/resume claim**: If the metadata description mentions "caching" / "cache" / "resume" / "resumable", the checker verifies that `cacheFingerprints` / `_cached(` / `verifyCacheUpdates` (for execute-milestone) or `resumeFromAdjudicatedProposal` / `--decide-resume` (for prepare-milestone) patterns exist in the executable body. A stale cache/resume claim with no corresponding mechanism is a FAIL.

6. **Gate-count claim**: If the metadata description or any phase detail mentions a specific gate count or names a specific gate, the checker verifies the gate dispatch array (`const gates = await parallel([...])`) contains matching labels.

7. **Agent-count alignment** (if claimed): If `meta.description` includes a numeric claim about agent dispatches, it MUST match the body's `agent(` / `await agent(` count.

8. **Node-invocation consistency**: The two workflow files MUST use the same node invocation convention (`--no-warnings` presence) OR an explicit comment must document the intentional divergence.

9. **Mirror byte-identity**: `.claude/workflows/<name>.js` and `plugin/workflows/<name>.js` MUST be byte-identical for each workflow name.

**WIRING-CLAIM C2 (severity split):** FAIL/WARN severity split: false metadata claim = FAIL (exit-impacting), missing metadata mention = WARN (non-exit-impacting). The checker's return object distinguishes `failures[]` from `warnings[]`; `--json` output includes both; only `failures.length > 0` drives exit code 1. Follows the DIR-100-C diagnostic severity taxonomy: RED = claim is positively false (e.g., phase listed but never called, outcome claimed but never returned); AMBER = suspicious but not provably false (e.g., phase called but not listed -- could be intentional, needs a metadata update); GREEN = claim verified.

**RED/GREEN negative control**: The checker ships with a deliberately-stale fixture workflow file under `test/fixtures/` (never committed to `.claude/workflows/` -- it is a test-only file) that fabricates a stale claim: a `meta.phases` array listing a phase (`DeadPhase`) that has no corresponding `phase()` call in the body. The checker must FAIL this fixture. A corrected version of the same fixture (with the phantom phase removed) must PASS. Additionally, the checker run against the real source files should produce findings for the 3 known discrepancies listed above -- these serve as the initial RED baseline that the implementation fix (updating the metadata) will turn GREEN. This proves the checker is not vacuously green.

**WIRING-CLAIM C3 (fixture isolation):** RED/GREEN fixture files live under `test/fixtures/`, never in `.claude/workflows/`. The `--files` flag accepts arbitrary paths; the test passes fixture paths; the production invocation (DoD clause) passes the real workflow paths.

**Concrete control/data flow**

```
DoD gate (it0-dod-check.ts, new clause)
  └─ shell out: node --experimental-strip-types experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs
       └─ parse 4 input files:
            ├─ .claude/workflows/execute-milestone.js
            ├─ plugin/workflows/execute-milestone.js
            ├─ .claude/workflows/prepare-milestone.js
            └─ plugin/workflows/prepare-milestone.js
       └─ Phase 1: Extract metadata surface from each file
       │    ├─ Parse `export const meta = { ... }` literal
       │    └─ Yield { name, description, phases: [{title, detail}, ...] }
       └─ Phase 2: Extract executable driver contract from each file body
       │    ├─ phase(): all `phase('Label')` call sites → {labels, uniqueCount, callCount}
       │    ├─ agent(): all `await agent(` and `agent(` call sites → {callCount, labels}
       │    ├─ node invocations → {countWithWarnings, countWithoutWarnings}
       │    ├─ return outcomes → {outcomes: Set<string>}
       │    └─ worktree code paths → {present: bool, refCount: number}
       └─ Phase 3: Assertions (per claim class above)
       │    ├─ Phase-label alignment, phase-count alignment
       │    ├─ Return-outcome alignment, no-stale-outcome claim
       │    ├─ Node-invocation count, node-invocation consistency
       │    ├─ Worktree mention, cache/resume claim, gate-count claim
       │    ├─ Agent-count alignment (if claimed)
       │    └─ Mirror byte-identity
       └─ return { ok: <all hard-checks passed>, failures: [...], warnings: [...] }
       └─ exit 0 if ok, exit 1 if failures non-empty
```

**WIRING-CLAIM C4 (dual-mirror byte-identity):** Both `experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs` and `plugin/scripts/workflow-metadata-conformance.mjs` are byte-identical. The test reads both files and asserts `file1Content === file2Content`; the existing `anti-drift-touches-check.sh` pattern prevents divergence.

**WIRING-CLAIM C5 (DoD integration):** The new DoD clause shells out to `workflow-metadata-conformance.mjs` as a subprocess, exactly as clauses 3/4/10/11/12 do for their checks. This keeps the conformance logic independently runnable and testable, and keeps `it0-dod-check.ts`'s clause surface thin. Failure maps to a `FAIL: clause<N>-workflow-metadata-conformance:` line; the existing `dod-fixture-selfcheck.sh` exercises the clause through a fixture.

**WIRING-CLAIM C6 (enforcement):** The integration point in `it0-dod-check.ts` must be mechanically verifiable -- grep for the conformance script name in the DoD enforcer source. A RED finding blocks the DoD gate (the milestone cannot complete).
The DoD gate wiring (new clause in `it0-dod-check.ts`) shells out to the conformance script exactly as clause 3 shells out to `it0-ceiling-line-budget-check.sh` -- reused, not re-implemented. The clause is mechanically unconditional (always runs, same as clauses 3/4/10/11/12), so it is listed in `MECHANICALLY_UNCONDITIONAL_CLAUSES` for the self-exemption meta-clause.

**Key design decisions**

1. **Regex/grep extraction, not AST parsing**: The workflow DSL is a constrained surface with well-known, regex-friendly structural conventions (`phase('...')`, `meta.phases = [...]`, `"outcome"` literals). Full AST parsing (via acorn, babel, etc.) would add a dependency chain and fragility (minified/transpiled output, non-standard syntax extensions) for no gain. The existing `it0-dod-check.ts` itself uses regex extraction for all its checks, establishing the pattern. The workflow files reference DSL globals (`agent`, `phase`, `parallel`, `log`, `args`) that are not importable -- regex extraction avoids the DSL-global-reference problem entirely.

2. **Hard-FAIL on stale claims, WARN on omissions**: A metadata claim with no corresponding executable mechanism is a hard FAIL -- it is an assertion that is factually false. An executable mechanism with no metadata mention is a WARN -- it is an omission, not a lie, and the metadata may legitimately omit implementation details. This distinction matches the task's RED/GREEN framing: RED = false claim, GREEN = matched claim, WARN = missing documentation.

3. **Separate test fixture, not a self-modifying test**: The RED negative control fixture file lives under `test/fixtures/` and is never committed to `.claude/workflows/`. The checker reads the real workflow files at runtime; the test passes a fixture path as an override via `--files`. This avoids the circularity of deliberately breaking a production workflow file to prove the checker works.

4. **Single script with two mirrors, not two separate scripts**: Following the established pattern (e.g., `anti-drift-touches-check.sh` exists at both `experiments/quay-perpetual-stream/scripts/` and `plugin/scripts/`), the conformance script has two byte-identical copies. The test verifies both mirrors are byte-identical.

5. **DoD gate integration via shell-out, not inline clause logic**: The new DoD clause shells out to `workflow-metadata-conformance.mjs` as a subprocess, exactly as clauses 3/4/10/11/12 do for their checks. This keeps the conformance logic independently runnable and testable.

6. **Pure-text extraction, no evaluation**: The checker never `eval()`s or `import()`s the workflow source files. All extraction is from the text representation. This avoids the DSL-global-reference problem and makes the checker safe to run in any context.

7. **Re-entrant phase handling**: The same `phase('Preflight')` label appears at two distinct logical points in prepare-milestone.js (content preflight and plan-shape preflight). The checker distinguishes "unique labels" from "call count" and treats re-entrant labels as a single logical phase when the metadata explicitly documents the re-entry -- a naive phase-set comparison would miscount. This is handled in the assertion logic, not by special-casing Preflight.

**Defaults and failure behavior**

- **Default (no args):** Runs against the 4 hardcoded workflow file paths (`.claude/workflows/execute-milestone.js`, `plugin/workflows/execute-milestone.js`, `.claude/workflows/prepare-milestone.js`, `plugin/workflows/prepare-milestone.js`) resolved from the repository root. Exit 0 if all hard-checks pass; exit 1 if any hard-check fails.
- **`--files <path...>`:** Override the default file list (for testing with fixtures). Accepts one or more `.js` workflow files; each is independently checked, and the aggregate exit code is 0 only if ALL files pass.
- **`--json`:** Output the full check-result as a single JSON line to stdout (for machine consumption by the DoD gate clause). Default (without `--json`) produces human-readable output.
- **Missing file:** Exit 2 (environment error, same convention as `it0-dod-check.ts`). Never silently passes on a missing workflow file.
- **Unparseable metadata:** If a workflow file has no `meta` object or the `meta` cannot be extracted, that is a FAIL with detail `metadata-unparseable`, not a silent skip. A missing `meta` is itself a conformance failure (the metadata surface is a required contract).
- **AMBER/WARN findings:** Logged to stderr but do not cause a non-zero exit. They surface drift that needs human attention but does not block the pipeline.
- **Default invocation:** The checker runs on every DoD gate invocation (every milestone that reaches the Gate phase). There is no opt-out -- the metadata surface should always be accurate.

**Compatibility**

- **Backward compatible with existing workflows**: The checker is purely additive -- it reads files, never writes them. Existing workflow behavior is unchanged.
- **No change to workflow DSL format**: The `meta` object shape is already the established convention. This checker enforces it, it does not change it.
- **Existing DoD clauses unchanged**: The new clause is additive (next available clause number). Existing clauses 0-12 are byte-identical.
- **Existing fixtures unchanged**: All existing `fixtures/dod/*.md` test fixtures continue to pass because the new clause is a shell-out -- a missing conformance script at test time is a `DodCheckEnvError` (exit 2, not a FAIL), and the test harness can provide a stub.
- **No new dependencies**: The script uses only Node.js built-ins (`fs`, `path`, `child_process`) -- same as every existing script in `experiments/quay-perpetual-stream/scripts/`.
- **Mirror coverage**: Both `.claude/workflows/` and `plugin/workflows/` mirrors are checked. The existing `execute-milestone-disposition-conformance.test.mjs` already establishes this dual-mirror pattern.
- **No new file format or schema**: The `meta` export is already the established convention. The checker simply verifies what is already claimed.

**Risks**

1. **Regex fragility**: If the workflow DSL evolves new syntax (e.g., `phase()` calls generated dynamically, template literals for phase labels, or metadata declared via a helper function rather than an object literal), the regex extraction may produce false negatives. Mitigation: the checker is a single script with a well-defined surface; when the DSL evolves, updating the regex patterns is a targeted change, not a rewrite. The RED/GREEN test fixture catches regressions, and the checker's test suite includes a regression test that fails if the regex no longer matches the real source files.

2. **False positives on coincidental string matches**: A comment containing the literal text `phase('Verify')` as an example could be counted as an invocation. Mitigation: the regex for phase extraction matches only `phase('<name>')` anchored at the start of the expression context (not inside a comment), using negative lookbehind for `//` on the same line. Same accuracy as the existing `it0-dod-check.ts` patterns.

3. **Metadata description natural-language parsing**: Claims embedded in `meta.description` prose (e.g., "Returns {outcome: ...}") require regex extraction that may miss a claim phrased differently. Mitigation: the checker extracts claims using explicit regex patterns; if a claim cannot be extracted, it is skipped with a WARN "unparseable claim" finding, not silently ignored.

4. **The checker itself can drift**: The checker's own extraction logic could become stale if the workflow DSL changes. Mitigation: the RED/GREEN fixture test is itself part of the test suite run by `scripts/test.sh`, so a workflow DSL change that breaks the checker's extraction would be caught by the test suite before the checker could falsely PASS.

5. **Test-suite-only coverage, not workflow-runtime**: The checker is a static analysis tool. It cannot verify runtime behavior (e.g., whether the `building` outcome path was ever actually reachable). This is by design -- the checker detects stale *claims*, not stale *behavior*. The RED/GREEN negative control proves the checker catches fabricated stale claims; it does not prove the workflow actually behaves as its metadata claims.

**Non-goals**

- Full AST validation of the workflow DSL surface (explicitly rejected -- see Alternatives).
- Runtime verification of workflow execution (this is a static metadata-vs-contract check, not a dynamic execution tracer).
- Checking prose comments outside the `meta` object for accuracy (only the structured metadata surface is checked).
- Checking workflow files other than the two named targets and their mirrors (the scope is `execute-milestone.js` + `prepare-milestone.js` only, per the task's own Touches list and AC1's "named in Touches" constraint).
- Introducing a new lifecycle-promotion policy, worktree redesign, stage scheduler, or resource lease (per the task's AC4 non-goal).
- Post-Land Wiring Audit (per the task's AC4 non-goal).
- A workflow linter or style checker -- agent prompt text quality, label naming conventions, and schema shape consistency are out of scope.
- A general-purpose JavaScript conformance framework -- the checker is specific to the two workflow files and their `meta` export convention.
- Modifying the workflow source files to fix drift -- the checker reports findings; fixing them is a human or Build-agent task.
- Making the checker a workflow phase rather than a DoD clause -- the checker should fire on every milestone, not only on milestones that opt into it.
- A separate gate registered in `.quay/gates.yml` -- adds a new gate registration and invocation path when the DoD enforcer already has a well-established clause-extension pattern.

**Explicit alternatives considered and rejected**

1. **Manual prose review of workflow comments** (task's listed alternative): Rejected -- no mechanical failure when a claim drifts. A stale `meta.phases` entry or a wrong outcome shape claim is invisible to human review unless someone specifically greps for it. The checker is the executable invariant -- it fails the DoD gate on any detected drift, forcing correction before a milestone can land.

2. **Full AST validation of the workflow DSL** (task's listed alternative): Rejected -- over-scoped for this child. The workflow DSL is a moving target with evolving globals (`agent`, `phase`, `parallel`, `log`). A full AST parser would need to track those globals' semantics, which is a much larger effort. This child targets the narrow and stable metadata-vs-driver claim surface, which regex extraction handles adequately. Additionally, a JS parser dependency (acorn, babel, etc.) would add supply-chain risk that is disproportionate to the benefit.

3. **Inline assertion comments (e.g., `// @assert phase-count=8`)** -- a comment-based assertion embedded in the workflow file itself that a linter verifies. Rejected: requires modifying the workflow files (changing the surface under test), and a comment can drift just as easily as the metadata it annotates. The independent conformance script reads the metadata surface as-is and compares it to the driver -- it does not require the metadata to be annotated.

4. **Runtime trace comparison** -- run the workflow in a sandbox, capture the actual phase transitions, and diff against metadata. Rejected: requires a live Dispatch agent + a full milestone environment for what is structurally a static check; the same comparison can be made by parsing the source text. The static approach gives the same signal at zero runtime cost and zero flakiness. Additionally, runtime coverage is path-dependent -- a phase that is never reached in a given run is not provably absent from the code.

5. **TypeScript-based schema validation of the meta export** -- adding a `.d.ts` or converting the files to `.ts`. Rejected: the workflow files are plain `.js` files without TypeScript annotations. Adding type annotations would be a structural change to the DSL convention, not a conformance check. The regex approach reads the existing convention as-is.

6. **Making the checker a quay gate (engine-registered, like split-or-commit)** rather than a DoD clause. Rejected: the checker is a per-milestone mechanical verification, not a per-task lifecycle gate. Wiring it into the existing DoD enforcer (which already has the charter-fixture / ABSORB-entry / clause-disposition infrastructure) is the simpler, lower-risk path. A quay gate would require gate-engine registration, a gate-events.jsonl append, and a Gate phase invocation -- all heavier than a single `execFileSync` in an existing clause.

7. **Making the checker a workflow phase rather than a DoD clause.** Rejected: the checker should fire on every milestone, not only on milestones that opt into it. Wiring it into the DoD gate (which already fires unconditionally) ensures coverage without adding a new phase to either workflow.

## Finding

Recent workflow repairs have relied on prose histories and manually reconstructed Claude Code timelines; stale claims in workflow metadata (e.g. a `building` phase description naming a retired dispatch path, or a comment citing a worktree invocation line that moved) go unnoticed because nothing compares metadata to the executable driver contract.

## Requested action

1. Build a conformance checker that extracts the workflow DSL's phase/comment/claim surface.
2. Compare each claim against the executable driver contract (phase list, worktree invocation, gate-count, cache/resume, node invocation pattern).
3. Add RED/GREEN controls: a deliberately-stale claim fails; the corrected claim passes.
4. Wire the checker into the DoD gate so a stale metadata/driver mismatch fails the milestone.

## Acceptance Criteria

- [ ] The conformance check exists as a checked script (both mirrors) named in Touches.
- [ ] A deliberately stale workflow metadata/driver claim fails the conformance check; the corrected claim passes (RED/GREEN negative control).
- [ ] The checker runs as part of the DoD gate (`it0-dod-check.ts` or sibling).
- [ ] No post-Land Wiring Audit, lifecycle-promotion policy, worktree redesign, stage scheduler, or resource lease is introduced by this child (parent AC9 non-goal).
- [ ] The checker extracts `phase()` call sites from the body via regex and compares the unique label set against `meta.phases[]`; re-entrant labels (same label at multiple call sites) are counted as one logical phase for set comparison, with call-count multiplicity reported separately; any phase in body not in meta is FAIL, any phase in meta not in body is FAIL.
- [ ] The checker extracts return-outcome values from `meta.description` (e.g. `{outcome: 'done'|'needs-human'|'building'}`) and compares against actual return-site outcome literals in the body; any outcome claimed in meta but absent from body is FAIL.
- [ ] The checker extracts `agent(` / `await agent(` call sites; if `meta.description` includes a numeric agent-count claim, the checker verifies it matches the actual body call count.
- [ ] The checker counts `node --experimental-strip-types` invocations in each workflow file, verifies `--no-warnings` consistency between the two files, and reports unintentional divergence as WARN (intentional divergence requires an explicit comment documenting it).
- [ ] The RED/GREEN negative control uses a deliberately-stale fixture file under `test/fixtures/` (fabricated `meta.phases` entry `DeadPhase` with no matching `phase()` call) that the checker FAILs; the corrected variant (same fixture minus `DeadPhase`) PASSes; the fixture file is never committed to `.claude/workflows/`.
- [ ] The checker's DoD gate integration shells out to `workflow-metadata-conformance.mjs` following the established clause 3/4/10/11/12 pattern; the integration point is mechanically grep-able in `it0-dod-check.ts`.
- [ ] The checker distinguishes FAIL (false claim -> exit code 1) from WARN (missing documentation -> non-exit-impacting); the return object separates `failures[]` from `warnings[]`.
- [ ] Both mirrors (`experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs` and `plugin/scripts/workflow-metadata-conformance.mjs`) are byte-identical; a unit test asserts `file1Content === file2Content`.
