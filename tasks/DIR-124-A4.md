**type:** execution

## Proposal

Add a conformance check comparing workflow metadata (the DSL phase/description/comment surface in
`.claude/workflows/execute-milestone.js` and `prepare-milestone.js`) against the executable driver
contract, so stale `building`, worktree, gate-count, cache/resume, or phase claims become visible
failures instead of silently drifting prose.

Fourth child of the DIR-124-A split (mechanism M4). No dependencies.

**File home (split review finding):** the conformance check is
`experiments/quay-perpetual-stream/scripts/workflow-metadata-conformance.mjs` (mirrored at
`plugin/scripts/workflow-metadata-conformance.mjs`) — named in Touches, not left homeless.

## Chosen mechanism

M4 from the split-review inventory. The script parses the workflow DSL's metadata surface and
compares each claim against the executable driver contract (the actual phase list, worktree
invocation lines, gate-count wiring, cache/resume flags, and `node --experimental-strip-types`
callsites in `execute-milestone.js`/`prepare-milestone.js`). A deliberately-stale RED fixture
(fabricated claim not present in the driver) fails; the corrected claim passes.

## Finding

Recent workflow repairs have relied on prose histories and manually reconstructed Claude Code
timelines; stale claims in workflow metadata (e.g. a `building` phase description naming a retired
dispatch path, or a comment citing a worktree invocation line that moved) go unnoticed because
nothing compares metadata to the executable driver contract.

## Requested action

1. Build a conformance checker that extracts the workflow DSL's phase/comment/claim surface.
2. Compare each claim against the executable driver contract (phase list, worktree invocation,
   gate-count, cache/resume, node invocation pattern).
3. Add RED/GREEN controls: a deliberately-stale claim fails; the corrected claim passes.
4. Wire the checker into the DoD gate so a stale metadata/driver mismatch fails the milestone.

## Acceptance Criteria

- [ ] The conformance check exists as a checked script (both mirrors) named in Touches.
- [ ] A deliberately stale workflow metadata/driver claim fails the conformance check; the
  corrected claim passes (RED/GREEN negative control).
- [ ] The checker runs as part of the DoD gate (`it0-dod-check.ts` or sibling).
- [ ] No post-Land Wiring Audit, lifecycle-promotion policy, worktree redesign, stage scheduler, or
  resource lease is introduced by this child (parent AC9 non-goal).

## Definition of Done

Standard inherited-core DoD clauses apply.

- [ ] Landed on `master` under human-steered discipline.
- [ ] Real checker + RED/GREEN tests land together.

## Alternatives considered

- **Manual prose review of workflow comments** — rejected: no mechanical failure when a claim
  drifts; the checker is the executable invariant.
- **Full AST validation of the DSL** — rejected: over-scoped for this child; metadata-vs-driver
  claim comparison is the targeted surface.

## Human verification

1. Does a deliberately stale `building`/worktree/gate-count/cache claim fail the check?
2. Is the checker wired into the DoD gate, not a standalone document?
