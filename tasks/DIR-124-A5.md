## Proposal

### Problem framing (grounded in current repository state, 2026-08-01)

The crystallization document (`docs/proposals/quay-milestone-workflow-git-crystallization.md`, 568 lines, `status: proposed`) defines 10 baseline metrics at section 8 (lines 483-497): change-propagation radius, context working set, shared-writer count, duplicate-rule count, prompt-to-code ratio, receipt reuse rate, replay variance, failure-attribution precision, full-suite executions per candidate commit, and Land-fence hold/queue time. Today, **zero** of these metrics are measured mechanically. They are reconstructed from prose reports and Claude Code session timelines -- a manual, non-reproducible process. No classification separates mechanical-runner work (script dispatches, gate checks, merge operations) from content-agent work (proposal authoring, audit reasoning, plan checking). Missing data is silently approximated rather than reported as explicit unknowns.

DIR-124-A1 (currently `todo`, the ordered-first child of DIR-124-A) will land the canonical stage-event schema v1 and emission instrumentation at 8 workflow boundaries (Prepare admission, Verify, Prepared, Build, Audit, Gate, Reconcile, Land), writing per-run event logs to `experiments/quay-perpetual-stream/.workflow-events/<runId>.jsonl` (gitignored). Each event carries `timing: {queuedAtMs, startedAtMs, endedAtMs}`, `agentLabel`, `commandIdentity`, `observedWrites`, `outcome`, `waitReason`, `resourceClaim`, `isolationMode`, `dispatchMode`, and commit identity -- a structured surface from which the 10 crystallization metrics can be mechanically derived.

DIR-124-A5 is the **consumer of that stream**: it computes and emits the RA5/RA9 mechanical before-state baseline. Without it, DIR-124-E's resource-aware scheduling has no comparison surface -- it cannot distinguish a scheduling improvement from a measurement artifact.

**What exists today (directly observed on disk, 2026-08-01):**

- **Prepare-only telemetry, not execution-wide.** `prepare-milestone.js` (1558 lines mirror at `.claude/workflows/`, ~1547 lines at `experiments/`) carries a `_phaseTimings` array that accumulates `{phase, round, startedAtMs, endedAtMs}` spans from lease-renewal CLI subprocess JSON output. `_recordPhaseBoundary()` pushes closed spans at 6 boundaries (Adjudicate, ProposalReview, ProposalReview-delta-round-N, PlanAuthor, PlanCheck-round-N), and `_phaseTimingsForTerminal()` flushes them to `proposal-convergence.ts --record-generation` at terminal phases with `--phaseTimings` payload. This writes committed telemetry to `milestones/prepare-telemetry/<taskId>/<recordId>.json` (schema v2, git-committed, 135 records across ~20 task directories). This covers **Admission through Receipt only** -- zero execute stages (Verify, Prepared, Build, Audit, Gate, Reconcile, Land). The timing values are agent-mediated (clock values read from `--acquire`/`--renew` CLI subprocess output via `v.nowMs`, not JS-emitted `Date.now()` readings). It carries findingCode recurrence but no agent-call counts, no token usage, no command identities, no observed writes, no worktree paths, no Land-fence timing, and no isolation/dispatch mode context.

- **Gate events log** at `.quay/gate-events.jsonl` (gitignored, append-only, workspace-wide) records gate verdicts (`{ok, reason, event}`) but carries no stage timing, no agent-call metadata, no command identity, no observed writes, no worktree info, and no prepare-stage data. It is a lifecycle-verdict stream, not a workflow-stage event stream.

- **No workflow-level event log exists.** Confirmed: `find` for `.workflow-events` returns zero results; `find` for `*workflow-event-schema*` returns zero results; no `recordStageEvent`, `emit-event`, or `stage-event` references exist in any workflow file or experiments script outside DIR-124 task bodies. The A1 schema has not landed.

- **No invariant-ownership manifest** exists at `experiments/quay-perpetual-stream/invariant-ownership.md` -- A3 has not landed.

- **No replay fixture directory** exists at `experiments/quay-perpetual-stream/fixtures/workflow-replay/` -- A2 has not landed.

- **No baseline metrics script or metric classification code exists.** Confirmed: `grep` for `metricClass`, `mechanical-runner`, `content-agent`, or `workflow-baseline` returns zero hits outside DIR-124 task bodies. No code distinguishes mechanical-runner work from content-agent work.

- **The crystallization document** (568 lines) defines the 10 metrics in prose. It is not executable -- no code consumes its metric definitions.

- **`execute-milestone.js`** (1257 lines mirror) has no event emission instrumentation at any of its phases (Verify, Prepared, Build, Audit, Gate, Reconcile, Land). The phases exist as `phase('Name')` call sites, orchestrating agent dispatches and mechanical checks, but emit no structured timing, command-identity, or observed-writes records.

- **Existing script patterns** in `experiments/quay-perpetual-stream/scripts/` establish a consistent convention: `chart-headroom.ts` (5805 bytes), `rolling-slope-check.ts`, and `chart2-s3-external-validation.ts` all follow a uniform pattern -- `#!/usr/bin/env node --experimental-strip-types` shebang, exported pure functions with typed interfaces, `main()` with CLI flags via hand-written `for`-loop over `process.argv`, `--selftest` mode with embedded RED/GREEN fixtures using `mkdtempSync`/`writeFileSync`/`rmSync` for temp directories, exit codes 0/1/2, and zero npm dependencies beyond Node.js built-ins (`fs`, `path`).

**The gap:** no single data source spans Prepare admission through Execute Land; no source mechanically distinguishes mechanical-runner work from content-agent work; no source reports missing fields as explicit unknowns rather than zeros or guesses; no source captures all 10 crystallization metrics for a real run end-to-end.

**Why this matters for DIR-124-E.** Resource-aware scheduling needs a before-state baseline to compare against. Without it, any scheduling change is indistinguishable from a measurement artifact -- you cannot tell whether Land-fence time decreased because the scheduler improved or because the instrumentation changed. The baseline must be mechanical (derived from structured event fields, not prose), honest about unknowns, and classified by work type so the scheduler knows where optimization effort yields the most return.

### Chosen mechanism

A new standalone TypeScript script `experiments/quay-perpetual-stream/scripts/workflow-baseline-metrics.ts` (mirrored byte-identically at `plugin/scripts/workflow-baseline-metrics.ts`) that:

1. **Consumes the A1 event stream** from `experiments/quay-perpetual-stream/.workflow-events/*.jsonl` -- the primary structured data source for all 10 crystallization metrics. Each `.jsonl` file is one run's event log, containing stage-start and stage-end events with `timing`, `agentLabel`, `commandIdentity`, `observedWrites`, `outcome`, `waitReason`, `resourceClaim`, `stage`, `candidateId`, `runId`, `isolationMode`, `dispatchMode`, and `schemaVersion` fields.

2. **Consumes A3's invariant-ownership manifest** from `experiments/quay-perpetual-stream/invariant-ownership.md` for metric 4 (duplicate-rule count), if the manifest exists on disk. Parses the manifest for `## Invariant:` blocks with "Other occurrences" sections containing `[duplicate-to-remove]` entries.

3. **Consumes A2's replay fixtures** from `experiments/quay-perpetual-stream/fixtures/workflow-replay/` for metric 7 (replay variance), if the fixtures exist on disk. Reads expected `{outcome, stage, observedWrites}` assertions and compares against actual event-stream outcomes.

4. **Computes all 10 crystallization-document metrics mechanically** from structured event fields via deterministic functions -- no prose parsing, no Claude Code timeline reconstruction, no agent structured-output interpretation.

5. **Classifies every metric and diagnostic with a `metricClass` tag** of `"mechanical-runner"`, `"content-agent"`, or `"unknown"`, by rule-based matching of `agentLabel` prefix patterns and `commandIdentity` script-path patterns. Classification is deterministic and auditable -- never LLM-judged.

6. **Reports missing data as the JSON string `"unknown"`** (or `null` where appropriate) -- never as `0` or an implicit guess. Every metric carries `evidenceStatus: "measured"` or `evidenceStatus: "unknown"`.

7. **Records the before-state only** -- no delivered-value inference, no pass/fail policy, no recommendations, no gate consumption. Purely a measurement instrument.

8. **Is strictly read-only** -- never writes to the event log, never mutates workflow state, never changes lifecycle status. Opens event logs and sibling outputs as a reader, computes metrics in memory, writes only to stdout.

**Metric computation map (all 10, mechanically sourced):**

| # | Metric | metricClass | Primary data source | Computation |
|---|---|---|---|---|
| 1 | change-propagation radius | mechanical-runner | `observedWrites` (string arrays on stage end-events) | Group events by `candidateId`. Count unique file paths and unique parent directories across all events for each candidate. Report `{uniqueFiles, uniqueDirectories, paths}` per candidate plus aggregate min/median/max. |
| 2 | context working set | content-agent | `commandIdentity` (script invocations: parse `--<file>` flag paths) + `agentLabel` (cross-reference task/charter files from task store) + `observedWrites` (lower-bound fallback: writes imply reads) | Enumerate files each stage's agent or script read. Script invocations: parse `commandIdentity` for `<script-path>` and `--<flag> <path>` arguments. Agent invocations: use `agentLabel` to look up the corresponding task `.md` file and charter file. `observedWrites` provides a lower-bound estimate. Stages with no `commandIdentity` and no `observedWrites` report `"unknown"`. |
| 3 | shared-writer count | mechanical-runner | `observedWrites` across events, grouped by `candidateId` | For each candidate, compute the pairwise intersection of `observedWrites` across all stages. Count stage pairs with non-empty intersection. Key shared-state paths: `backlog.md`, `dashboard.md`, `tasks/*.md`, `milestones/M<NN>/*`, `milestone_counter`. Report `{sharedWriterPairs, pairs: [{stageA, stageB, commonPaths}]}`. |
| 4 | duplicate-rule count | mechanical-runner | A3's `invariant-ownership.md` manifest (read from disk) | Parse the manifest for invariant blocks. Count rules where the "Other occurrences" section contains at least one `[duplicate-to-remove]` entry. If A3 has not landed (manifest file absent), report `"unknown"` with note `"A3 invariant-ownership manifest not yet available"`. Never re-implements A3's own duplicate detection. |
| 5 | prompt-to-code ratio | mechanical-runner | `commandIdentity` across all events, grouped by `candidateId` | Classify each `commandIdentity`: a mechanical-script invocation matches `node --experimental-strip-types experiments/quay-perpetual-stream/scripts/` or `scripts/test.sh` or `scripts/*.sh`. An agent-only NL instruction has `commandIdentity` matching an agent label pattern without a shell-out script match. Ratio = mechanical-count / (mechanical-count + content-agent-count). Events with null `commandIdentity` are excluded from the denominator (conservative: don't guess). |
| 6 | receipt reuse rate | mechanical-runner | Prepared-phase end-events | Count end-events where `outcome === "skipped"` and `waitReason` matches `"cache-hit"` or `"prepared-blocked"`, divided by total Prepared end-events with non-null `outcome`. Candidates with no Prepared stage contribute a null entry. |
| 7 | replay variance | mechanical-runner | A2 replay fixture expected verdicts vs. actual event-stream outcomes | Read A2 fixtures from disk (if they exist). For each fixture, extract expected `{outcome, stage, observedWrites}` assertions and compare against actual events for matching `candidateId` + `stage`. Deterministic field comparison. Mismatches counted. If A2 fixtures do not exist, report `"unknown"`. Never re-implements A2's own replay logic. |
| 8 | failure-attribution precision | mechanical-runner | End-events where `outcome === "needs-human"` | Count events where `stage`, `waitReason`, AND `commandIdentity` are all non-null (all three attribution dimensions present). Divide by total `needs-human` end-events. Report `{preciselyAttributed, totalNeedsHuman, precision}`. |
| 9 | full-suite executions per candidate | mechanical-runner | `commandIdentity` entries matching `scripts/test.sh` (the canonical test entrypoint per ADR-019/DIR-109) | Count per `candidateId`, broken down by `stage`. Exact string containment: `commandIdentity` includes `scripts/test.sh`. |
| 10 | Land-fence hold/queue time | mechanical-runner | Land-stage end-events: `timing.queuedAtMs` to `timing.startedAtMs` delta | `landQueueMs = startedAtMs - queuedAtMs` (measures lock-contention wait under `.quay/land-locks/shared-checkout.lock`). `landDurationMs = endedAtMs - startedAtMs`. `totalLandMs = landQueueMs + landDurationMs`. Per-candidate and aggregate min/median/max. |

**Mechanical/content-agent split.** Every metric and diagnostic carries a `metricClass` tag. Classification is rule-based -- never LLM-judged:

- **`"mechanical-runner"`**: Metrics sourced from mechanical phase boundaries (Verify script dispatches, Gate agent dispatches, Reconcile CLI, Land merge/commit), from `timing` wall-clock readings, or from CLI-invocation-pattern counts. Identified by `commandIdentity` matching `node --experimental-strip-types experiments/quay-perpetual-stream/scripts/` (a known script path), and agent calls with labels matching established mechanical-check patterns: `ceiling-check`, `gate-hash`, `line-budget`, `dogfood-evidence`, `composite-preflight`, `worktree-create`, `worktree-merge`, `worktree-remove`, `build-evidence-collector`, `emit-event-*`. Metrics 1, 3, 4, 5, 6, 7, 8, 9, 10 are tagged `mechanical-runner`.

- **`"content-agent"`**: Metrics requiring agent-level data beyond the mechanical event stream. Includes: ProposalAuthors, Adjudicate, ProposalReview, PlanAuthor, PlanCheck, Build implementation, Audit adversarial reasoning, Gate policy agents (`domain-misfit`, `prepare-receipt` check). Identified by `agentLabel` matching content-agent prefix patterns (`ProposalAuthors`, `Adjudicate`, `ProposalReview`, `PlanAuthor`, `PlanCheck`, `Build`, `Audit`, `domain-misfit`, `prepare-receipt`) and by the absence of a shell-script `commandIdentity`. Metric 2 is tagged `content-agent` (accurate file-read enumeration requires more than `commandIdentity` string matching).

- **`"unknown"`**: If classification is ambiguous (unrecognized label, missing `commandIdentity`, no script path match), it is tagged `"unknown"` rather than guessed. The split is honest about edge cases.

Classification priority when both `commandIdentity` (matching a script) and `agentLabel` (matching a content prefix) are present: `commandIdentity` wins -- the script invocation is the observable mechanical behavior. This split is itself a deliverable: it provides DIR-124-E with a quantified picture of how much workflow cost is mechanical overhead versus content generation. [WIRING-CLAIM: A5-SPLIT]

**Agent-level diagnostics.** Reported alongside the 10 metrics:

- **Agent-minutes:** Sum of `timing.endedAtMs - timing.startedAtMs` across all content-agent events, converted to minutes. Broken down by `stage` and by `agentLabel`. Mechanical-runner events excluded. Reported as `{totalMinutes, perStage: {...}, perAgentLabel: {...}}`.

- **Tokens:** Not present in A1 v1 event schema. Reported as `"unknown"` with note `"token usage is not in A1 v1 event schema -- available when DIR-124-B extends the schema"`. The baseline does not guess.

- **Finding novelty/recurrence:** Extracted from `outcome` + `waitReason` combinations across candidates. A finding is "novel" if the specific `{outcome, waitReason, stage}` tuple appears for the first time in the observed set (ordered by event timestamp); "recurrent" if the same tuple appears across multiple candidates. Reported as `{novelFindings, recurrentFindings, recurrenceKeys: [...]}`.

- **Artifact-class output:** From `observedWrites`, categorized by file extension and directory prefix: `code` (paths under `experiments/` or `packages/`), `docs` (paths under `docs/`), `tasks` (paths under `tasks/`), `milestones` (paths under `milestones/`), `other` (everything else). Byte counts are `"unknown"` -- `observedWrites` records paths only, not byte deltas; reading current file sizes would measure post-Land state, not emission-time state.

**CLI surface.** The script follows the established pattern of `chart-headroom.ts` / `rolling-slope-check.ts` / `chart2-s3-external-validation.ts`:

- `#!/usr/bin/env node --experimental-strip-types` shebang (Node >=20 native TS execution)
- Exported pure functions: `computeBaselineMetrics`, `classifyMetric`, `classifyEvent`, `parseEventStream`, `parseInvariantManifest`, `computeAgentMinutes`, `computeFindingRecurrence`, `computeArtifactClassOutput`, `computePromptToCodeRatio`, `computeChangePropagationRadius`, `computeSharedWriterCount`, `computeReceiptReuseRate`, `computeFailureAttributionPrecision`, `computeFullSuiteExecutions`, `computeLandFenceTime`, `computeDuplicateRuleCount`, `computeReplayVariance`, `computeContextWorkingSet`
- `main()` with hand-written `process.argv` for-loop, reading:
  - `--event-dir <path>` (default: `experiments/quay-perpetual-stream/.workflow-events`)
  - `--manifest <path>` (default: `experiments/quay-perpetual-stream/invariant-ownership.md`)
  - `--replay-fixtures <path>` (default: `experiments/quay-perpetual-stream/fixtures/workflow-replay`)
  - `--json` -- emits the structured JSON report to stdout
  - `--selftest` -- runs embedded RED/GREEN fixtures
- Exit codes: 0 (valid report, even if all-unknown -- an honest empty baseline is valid output), 1 (selftest failure), 2 (usage/environment error: unreadable event dir, zero JSONL files, unreadable manifest)
- Zero npm dependencies beyond Node.js built-ins (`fs`, `path`)
- Single file, inline argument parsing (matching `chart-headroom.ts`'s `for`-loop over `process.argv`)

[WIRING-CLAIM: A5-CLI-MODE]

**Emission format.** Single JSON object to stdout with `schemaVersion: "1"`, `scriptVersion: "1.0.0"`, `generatedAt` (ISO8601), `samples` (count), `sampleRunIds`, `sampleRange`, `parseWarnings`, `metrics` (all 10 metrics with per-candidate and aggregate views), `diagnostics` (agent-minutes, tokens, finding novelty/recurrence, artifact-class output), and `status` (`"ok"`, `"no-data"`, or `"error"`). Every metric value is either a computed object with `evidenceStatus: "measured"` or the JSON string `"unknown"` with `evidenceStatus: "unknown"` and a `reason` field. The string `"unknown"` is semantically distinct from the number `0`. [WIRING-CLAIM: A5-UNKNOWNS]

### Key design decisions

**DD1: Mechanical computation from A1 event stream, not prose estimation.** The split review's baseline-ordering finding requires a mechanical before-state for DIR-124-E's comparison surface. The A1 event stream carries `timing`, `commandIdentity`, `observedWrites`, `outcome`, `agentLabel`, and `waitReason` -- all fields needed to compute the 10 crystallization metrics mechanically. Every metric is derived from structured event fields via deterministic functions -- never from agent structured-output summary reports, Claude Code timeline inspection, or prose reconstruction. This is the single most important design decision: it makes the baseline a comparison surface rather than another opinion. [WIRING-CLAIM: A5-CONSUME, A5-METRIC-MAP]

**DD2: First-class mechanical/content-agent split.** The crystallization document (section 3.5) describes the "shadow architecture" -- a typed contract layer beside the prompt monolith that is not the execution mechanism. The `metricClass` tag quantifies this split: how much of the workflow's cost is mechanical overhead versus content generation. Classification is rule-based (agent label prefix pattern, script path pattern, `commandIdentity` presence) -- never LLM-judged. An ambiguous entry gets `metricClass: "unknown"` rather than a guessed classification. When both `commandIdentity` (matching a script) and `agentLabel` (matching a content prefix) are present, `commandIdentity` wins -- the script invocation is the observable mechanical behavior. [WIRING-CLAIM: A5-SPLIT]

**DD3: Explicit unknowns, never zeros or guesses.** A metric with insufficient evidence is reported as the JSON string `"unknown"`, not `0`. This is critical for DIR-124-E: a resource-aware scheduler must distinguish "we have zero data on Land-fence queue time" from "Land-fence queue time is 0ms" -- the latter would silently disable queue-time-aware scheduling. Every metric's `evidenceStatus` is `"measured"` or `"unknown"`, never implicit. A zero is a meaningful measurement (e.g., zero full-suite runs means `test.sh` was never invoked); an unknown means "we don't know." [WIRING-CLAIM: A5-UNKNOWNS]

**DD4: Before-state only -- no inference of delivered value.** The baseline records what the event stream contains, not what it means. It does not compute a "milestone quality" score, does not tag metrics as "good" or "bad," and does not emit recommendations. This is a measurement instrument, not an evaluation instrument. DIR-124-E owns the scheduling decisions that consume this data. [WIRING-CLAIM: A5-NO-INFERENCE]

**DD5: Cross-child dependencies are additive, not mandatory.** A5 declares dependencies on A1 (event stream), A2 (replay fixtures), and A3 (invariant-ownership manifest). But only A1 is hard: without event log files, status is `"no-data"`. Without A2 or A3, the corresponding metrics are `"unknown"` with explanatory notes -- A5 produces a valid (thinner) baseline. This preserves independent landability per the parent's split-multi-mechanism finding. [WIRING-CLAIM: A5-CROSS-CHILD]

**DD6: Follows established repo script patterns exactly.** The script follows the established `chart-headroom.ts` / `rolling-slope-check.ts` / `chart2-s3-external-validation.ts` pattern: shebang, exported pure functions, `main()` with CLI flags, embedded RED/GREEN selftest fixtures using `mkdtempSync`/`writeFileSync`/`rmSync` for temp directories, exit code 0/1/2 convention, inline argument parsing via `for`-loop over `process.argv`. No new pattern is invented. [WIRING-CLAIM: A5-CLI-MODE]

**DD7: Both mirror paths, byte-identical at Land.** The script lives at both `experiments/quay-perpetual-stream/scripts/workflow-baseline-metrics.ts` and `plugin/scripts/workflow-baseline-metrics.ts`, byte-identical. The existing mirror-diff test pattern (which `diff`s both directories for files in the Touches list) covers this script. Test fixtures at `experiments/quay-perpetual-stream/test/workflow-baseline-metrics.test.mjs` (mirrored at `plugin/test/workflow-baseline-metrics.test.mjs`) verify: (a) mirrors are byte-identical, (b) each metric computation produces expected output from known synthetic event fixtures, (c) missing-field paths produce `"unknown"`, and (d) classification is rule-based and deterministic. [WIRING-CLAIM: A5-MIRROR]

**DD8: Honest zero-sample behavior is valid output.** When zero real event samples exist (A1 landed but no real milestone run has executed yet), the script reports `{samples: 0, status: "no-data"}` and exits zero. All 10 metrics are `"unknown"` with reason `"no-event-samples"`. This is not a failure -- it is a true statement about the before-state. DIR-124-E's design must handle a thin baseline; fabricating richness would be worse. [WIRING-CLAIM: A5-ZERO-SAMPLES]

**DD9: Single-file module, zero npm deps, inline CLI parsing.** The script is a single `.ts` file using only Node.js built-ins (`fs`, `path`). The shebang `#!/usr/bin/env node --experimental-strip-types` enables direct TypeScript execution on Node >=20. Plain functions, no class hierarchy. Matches the existing script pattern where `chart-headroom.ts`, `rolling-slope-check.ts`, and `chart2-s3-external-validation.ts` all implement their own `for`-loop `process.argv` parsing rather than importing a shared argument parser.

**DD10: Read-only, fire-and-forget consumer. Parse warnings, not parse failures.** The script opens event logs and sibling outputs as a reader, computes metrics, and writes only to stdout. Verified mechanically: `grep` for `writeFileSync`, `appendFileSync`, `mkdirSync`, `rmSync`, `cpSync` returns zero hits on the script body (excluding the selftest section which creates temp fixtures and cleans them up). No file creation, modification, or deletion in the production path. A malformed JSON line in an event log is skipped with a warning entry in `parseWarnings`. A single corrupted line does not invalidate the entire event stream. If ALL events in ALL logs are corrupt, status is `"no-data"`. [WIRING-CLAIM: A5-NO-INFERENCE, A5-READ-ONLY]

### Defaults and failure behavior

**Default paths:**
- Event directory: `experiments/quay-perpetual-stream/.workflow-events` (overridable via `--event-dir`)
- Manifest: `experiments/quay-perpetual-stream/invariant-ownership.md` (overridable via `--manifest`)
- Replay fixtures: `experiments/quay-perpetual-stream/fixtures/workflow-replay` (overridable via `--replay-fixtures`)

**Zero event samples:** Reports `{samples: 0, status: "no-data"}` to stdout, exits 0. All 10 metrics are `"unknown"` with reason `"no-event-samples"`. Not an error -- an honest empty baseline. [WIRING-CLAIM: A5-ZERO-SAMPLES]

**Partial event log (fewer than all 8 stages instrumented):** The baseline includes partial data for stages present. Missing stages contribute `"unknown"` for stage-specific metrics. Exit zero.

**Unreadable event directory:** Exit code 2 (usage/environment error), message to stderr. Never silently returns an empty report when the directory should exist but is unreadable.

**Event JSON parse error (corrupted JSONL line):** The corrupted line is skipped, counted in `parseWarnings` as `{type: "malformed-line", file, line, error}`. Exit 0 unless all events in all logs are corrupt (then `"no-data"`).

**Missing event field (null in an otherwise valid event):** Reported as `null` in the metric output. If the field is required for a metric and is null across all relevant events for that metric, the metric is `"unknown"` with reason `"insufficient-field-data"`.

**Unrecognized `stage` value (future workflow phase):** Event is still counted in aggregate metrics; the per-stage breakdown labels it as `"unknown-stage:<value>"`. Forward-compatible.

**Missing `commandIdentity` in an event:** The event is classified as `metricClass: "content-agent"` (conservative default: assume agent work when script identity is unknown).

**A1 schema version mismatch:** Events with `schemaVersion` other than `"1"` produce a stderr warning and are processed with v1 field expectations. New v2 fields silently ignored; removed fields produce `"unknown"`. Forward-compatible read.

**No `observedWrites` in any event:** change-propagation radius, shared-writer count, and artifact-class output are all `"unknown"`. The baseline is honest about its data gap.

**Cross-child artifact missing (A2 fixtures, A3 manifest):** The affected metric is `"unknown"` with reason `"cross-child-artifact-not-yet-landed"`. Never a crash -- each child lands independently. Exit 0. [WIRING-CLAIM: A5-CROSS-CHILD]

**Unparseable invariant-ownership manifest:** Metric 4 is `"unknown"` with reason `"manifest-parse-failure"`. Other metrics unaffected. Exit 0.

**Disk I/O error (stdout write failure, permission denied on event dir):** Script exits non-zero. `{status: "error", reason: "<err.message>"}` to stdout if `--json` is set.

**Selftest failure:** Exit code 1. The embedded RED/GREEN fixtures verify: (a) GREEN -- synthetic JSONL stream produces correct values for all 10 metrics; (b) GREEN -- zero samples produces `{samples: 0, status: "no-data"}`; (c) RED -- null metric field produces `"unknown"`, not `0`; (d) RED -- malformed JSONL line is skipped with `parseWarning`; (e) RED -- event with no `observedWrites` contributes zero to change-propagation radius; (f) RED -- unreadable directory exits non-zero; (g) GREEN -- classification table produces correct tags for known agent labels.

**With A2:** The script reads A2 replay fixtures from the default path. If A2 is not yet landed (fixture directory absent), metric 7 is `"unknown"`. The fixture reading expects A2's assertion format (`{outcome, stage, observedWrites}`). **With DIR-124-E:** The baseline report's JSON schema (v1, `schemaVersion: "1"`) is a stable contract. DIR-124-E consumes this exact shape. If the metric set is expanded later, a new report schema version (v2) is introduced -- DIR-124-E's consumer checks `schemaVersion` and adapts.

**With the installed workflow:** A5 is a pure consumer -- it reads files, computes, writes to stdout. It does not modify: the A1 event stream, any workflow file (`.claude/workflows/*`, `plugin/workflows/*`), any workflow state (no lifecycle mutation, no status write), any gate configuration, or any pass/fail policy. **No behavioral coupling to the 10-metric list.** The script's per-metric-function architecture allows adding a new metric by adding a function + output key without touching existing computations.

### Risks

**R1: A1 event stream does not yet exist (ordering dependency).** A5 cannot produce real evidence until A1 lands and at least one milestone run populates the event stream. Mitigation: A1 is the ordered-first child; A5's ordering position follows from this dependency. A5's test fixtures use hand-crafted JSONL event files matching the A1 v1 schema shape -- these are sufficient for RED/GREEN testing before A1 lands. Real-evidence proof requires A1 to have landed and at least one milestone to have executed.

**R2: Thin baseline at Land time.** Only a handful of real milestone runs may populate the event stream by the time A5 lands (the event stream is new). Mitigation: explicit unknowns -- the baseline does not estimate or fabricate. The `samples: N` field is an honest count. DIR-124-E's design must handle a thin baseline; fabricating data would produce a misleading comparison surface.

**R3: Schema drift between A1 event schema and metric computation map.** If DIR-124-B's v2 schema renames or removes a field that A5's metric computation depends on, the affected metrics silently become `"unknown"`. Mitigation: `schemaVersion` check with explicit warnings. When a v2 event with removed required fields appears, the parse warning records it and the metric computation defaults to `"unknown"`. A5's computation map is pinned to the v1 field set. When v2 lands, A5's implementation must be revisited.

**R4: Cross-child artifact format drift (A2, A3).** A3's `invariant-ownership.md` format or A2's fixture format may evolve after A5 lands. Mitigation: each cross-child consumer is fail-soft -- an unparseable artifact produces `"unknown"` with a diagnostic note. No crash, no cascade failure. The `parseWarnings` array records the failure reason.

**R5: Mirror drift.** The `experiments/` and `plugin/` copies of the script and test file may diverge if a future edit updates one but not the other. Mitigation: the existing mirror-diff test pattern catches divergence mechanically at Land.

**R6: Large event log accumulation.** Accumulated `.jsonl` files under `.workflow-events/` could grow to hundreds of runs. Mitigation: the script processes files sequentially (streaming parse, never loads all events into memory at once); the directory is gitignored; each run's event log is approximately 16 lines at ~600 bytes each = ~10KB. If performance becomes an issue with >1000 runs, a `--max-samples N` flag can be added in a future iteration -- not in scope for v1.

**R7: Mechanical/content classification ambiguity.** Some events straddle the boundary (e.g., an agent with label `Build` that invokes `composite-build.ts` mechanically but also does LLM-driven implementation work). The classification priority rule is: `commandIdentity` matching a script pattern wins over `agentLabel`. An event with only an `agentLabel` (no script `commandIdentity`) is `content-agent`. An event matching neither is `unknown`. This rule is documented in the script and auditable.

**R8: Context working set (metric 2) is inherently imprecise from event-stream data alone.** The event stream records `commandIdentity` (which script was invoked) and `agentLabel` (which agent role), but not which files the agent actually read during reasoning. The metric's computation is a lower bound: script invocations enumerate flag-referenced files; agent invocations enumerate the task and charter files. The actual context working set may be larger. This is why metric 2 is the only metric tagged `content-agent` -- accurate measurement requires agent-level data beyond the event stream.

**R9: Multi-run-dependent metrics thin with few samples.** Finding recurrence (needs multiple candidates), replay variance (needs A2 fixtures), and duplicate-rule count (needs A3 manifest) may all be `"unknown"` at A5's own Land time. Mitigation: explicitly tagged `"unknown"` with explanatory notes. DIR-124-E's design must handle unknown metrics gracefully.

### Alternatives considered and rejected

**Alt1: Prose estimation from reports (current state).** Reconstructing metrics from Claude Code timelines and agent prose summaries is exactly the broken state this child fixes. Rejected: the split review's baseline-ordering finding (`repairable: false`) requires a mechanical before-state for DIR-124-E's comparison surface. Prose estimation cannot produce reproducible, verifiable metrics because each run's prose format differs, each human reconstructs differently, and no two measurements of the same run produce the same numbers.

**Alt2: Extending A1 to also emit metrics inline.** Adding metric computation to `recordStageEvent` would couple emission to analysis. A1's contract is fire-and-forget event emission -- `recordStageEvent` is called at phase boundaries and never inspects its own output. Adding metric computation to the emission path would: (a) make A1's agent-dispatched CLI calls more expensive (10+ additional metric computations per run, each scanning all prior events); (b) violate A1's "observational-only, never a gate" design decision; (c) force metrics logic to live in a workflow-agent-dispatched call path (the schema module is called from the workflow DSL, not a standalone context). Rejected: A5 is a distinct deliverable consuming the A1 stream; separating emission from analysis preserves independent landability -- the split review's core finding.

**Alt3: Merging A5 into A1 (schema + metrics in one child).** The split review's `split-multi-mechanism` finding (`repairable: false`) explicitly identified A1 and A5 as independently landable mechanisms. Merging them would reproduce the exact condition that triggered the split. Rejected per the split review's finding.

**Alt4: Merging A5 with A2 (replay corpus + metrics in one child).** Both consume the A1 event stream and could share the event-reading layer. Rejected: A2's scope is replay correctness (classification taxonomy, negative controls, known-defect labeling); A5's scope is metric computation (10 formulas, mechanical/content split, explicit unknowns). **Alt5: Reconstructing pre-A1 runs from prose for richer baseline.** Would estimate from Claude Code timelines, agent prose summaries, and git history -- the non-mechanical approach being replaced. Would produce a mixed baseline (mechanical + estimated) that DIR-124-E cannot trust as a comparison surface. Rejected: only post-A1 runs are covered; an honest thin baseline is better than a thick estimated one.

**Alt6: Wired enforcement -- making baseline report a gate check.** Would gate milestone promotion on baseline report validity, creating circularity (baseline measures Land, but Land requires baseline). Rejected: baseline is purely observational -- DIR-124-E's scheduling policy may consume it, but that is DIR-124-E's decision.

**Alt7: Embedding the metric computation in workflow files.** The workflow DSL has no `import` capability (documented constraint at `execute-milestone.js` lines 23-25) and its `agent()` primitive is for agent dispatch, not data processing. The established pattern in this repo is standalone TypeScript scripts with exported pure functions and a `main()` CLI. Rejected: a first-class script is the correct mechanism.

**Alt8: Aggregate report only, no per-candidate breakdown.** Would lose the per-candidate granularity that DIR-124-E needs (e.g., "development-class milestones consistently have 3x the Land-fence wait time of mechanical-class milestones"). Rejected: report includes both per-candidate and aggregate (min/median/max) views.

**Alt9: Streaming/incremental metrics (append to report as events arrive).** Would require a persistent metrics database, a write mechanism, and a concurrency model -- far beyond the scope of a baseline measurement tool. Rejected: batch processing of completed event logs is sufficient for v1. Incremental metrics belong in DIR-124-E or later.

**Alt10: Unifying with `gate-events.jsonl` or `prepare-telemetry`.** Gate events (lifecycle verdicts), prepare-telemetry records (convergence tracking), and stage events (workflow timing/effects) have different schemas, purposes, and storage paths. Unifying them would create a single format serving none well. Rejected: separate systems, separate consumers -- no unification in this child's scope.

**Alt11: Consuming prepare-telemetry data alongside A1 events.** The existing 135 prepare-telemetry records under `milestones/prepare-telemetry/` contain phaseTimings and findingCodes for the prepare lifecycle. **Alt12: LLM-based classification for the mechanical/content split.** An agent reading each event and classifying it introduces non-determinism and makes the baseline unreproducible. **Alt13: Reading current files to populate artifact-class byte counts.** `stat`-ing files that `observedWrites` references would measure post-Land state (after subsequent stages, Land itself, or later milestones modified them), not emission-time state. Rejected: byte counts are `"unknown"` -- a future event schema recording per-file byte deltas at emission time would fix this correctly.

**Alt14: Reporting `0` for metrics with insufficient data.** Using `0` as default would produce a misleading zero-rich baseline that DIR-124-E might misinterpret as "everything is fine, the system is cheap." Rejected: `"unknown"` is semantically distinct from `0` -- a consumer can distinguish "this metric was never measured" from "this metric was measured and found to be zero."

**Alt15: Requiring A2 and A3 to be landed before A5 produces any output.** Would couple A5 to sibling completion, contradicting the parent's independent-landability design. Rejected: A5 produces a valid (possibly thinner) baseline with any subset of available sibling data. Cross-child consumption is additive, not mandatory.

**Alt16: Using a `.mjs` module instead of `.ts` for the metric script.** The schema module (`workflow-event-schema.mjs`) uses `.mjs` because it must load without `--experimental-strip-types` on the emission path (the workflow's agent-dispatched CLI invocations call it directly). Using `.ts` with `--experimental-strip-types` enables TypeScript type annotations in the metric computation functions, making the 10-metric map more readable and the pure-function signatures self-documenting. The three existing convention scripts (`chart-headroom.ts`, `rolling-slope-check.ts`, `chart2-s3-external-validation.ts`) all use `.ts`. Rejected: `.mjs` was considered for consistency with the A1 schema module but `.ts` is the correct choice for a standalone metric-script with complex typed function signatures.
