## Proposal

### Problem framing (grounded in current repository state, 2026-08-01)

The crystallization document (`docs/proposals/quay-milestone-workflow-git-crystallization.md`, section 8, lines 483-497) defines 10 baseline metrics: change-propagation radius, context working set, shared-writer count, duplicate-rule count, prompt-to-code ratio, receipt reuse rate, replay variance, failure-attribution precision, full-suite executions per candidate commit, and Land-fence hold/queue time. These are today **reconstructed from prose reports and Claude Code timelines**, not measured mechanically. No classification separates mechanical-runner work from content-agent work. Missing data is silently approximated rather than reported as explicit unknowns.

DIR-124-A1 (currently `todo`) will land the canonical stage-event schema and emission instrumentation at all 8 workflow boundaries (Prepare admission, Verify, Prepared, Build, Audit, Gate, Reconcile, Land). This event stream records per-stage `timing: {queuedAtMs, startedAtMs, endedAtMs}`, `agentLabel`, `commandIdentity`, `observedWrites`, `outcome`, `waitReason`, `resourceClaim`, `isolationMode`, `dispatchMode`, and commit identity — a rich mechanical surface.

DIR-124-A5 is the **consumer** of that stream: emit the RA5/RA9 mechanical before-state baseline. Without it, DIR-124-E's resource-aware scheduling has no comparison surface — it cannot distinguish a scheduling improvement from a measurement artifact.

The existing telemetry infrastructure is **prepare-only, not execution-wide.** `prepare-milestone.js` carries `_phaseTimings` (an array of `{phase, round, startedAtMs, endedAtMs}` spans accumulated from lease-renewal agent-dispatched CLI calls, flushed to `proposal-convergence.ts --record-generation` at each terminal). `proposal-convergence.ts` writes committed telemetry to `milestones/prepare-telemetry/<taskId>/<recordId>.json` (125 records across ~20 tasks as of today, git-committed, schema version 2). This covers ONLY the prepare lifecycle: Admission through Receipt. It covers ZERO execute stages (Verify, Prepared, Build, Build-Evidence, Audit, Gate, Reconcile, Land). The timing values are agent-mediated (clock values read from `--acquire`/`--renew` CLI subprocess JSON output, not JS-emitted `Date.now()` readings). It carries findingCode recurrence tracking but no agent-call counts, no token usage, no command identities, no observed writes, no worktree paths, no Land-fence timing, and no isolation/dispatch mode context.

The `.quay/gate-events.jsonl` file (gitignored, append-only, workspace-wide) records gate outcomes but carries no stage timing, no agent-call metadata, no command identity, no observed writes, no worktree info, and no prepare-stage data.

**The gap:** no single data source spans Prepare admission through Execute Land; no source mechanically distinguishes mechanical-runner from content-agent work; no source reports missing fields as explicit unknowns rather than zeros or guesses; no source captures all 10 crystallization metrics for a real run end-to-end.

No existing workflow-level metrics script exists anywhere in the repository (confirmed by `find` for `*metric*` and `*baseline*` — zero results outside the DIR-124 tasks themselves). This is greenfield consumption of A1's event stream.

### Chosen mechanism

A new script `experiments/quay-perpetual-stream/scripts/workflow-baseline-metrics.ts` (mirrored byte-identically at `plugin/scripts/workflow-baseline-metrics.ts`) consumes the A1 event stream from `experiments/quay-perpetual-stream/.workflow-events/*.jsonl` and emits the 10 crystallization-document metrics mechanically. Each metric is tagged with a first-class `metricClass: "mechanical-runner" | "content-agent"`. Missing fields are explicit `"unknown"` string values (or `null` where JSON null is appropriate), never zeros or guesses. The baseline records the before-state only — no delivered-value inference, no pass/fail policy change.

**Metric computation map (mechanical, from A1 event fields):**

| # | Metric | metricClass | Computation from A1 event stream |
|---|---|---|---|
| 1 | change-propagation radius | mechanical-runner | Count of unique `observedWrites` file paths across all events for a candidate (grouped by `candidateId`). An event with no `observedWrites` contributes zero. Reported as `{uniqueFiles: N, uniqueDirectories: M, paths: [...]}`. |
| 2 | context working set | content-agent | Files read by content agents per stage. Reverse-computed from `commandIdentity` (for script invocations: the script's own source file + any `--<file>` flag arguments referencing repo paths) and `agentLabel` (for agent invocations: the task file, charter file, and any files referenced in the agent's prompt body — extracted from `observedWrites`). If a stage has no `commandIdentity` and no `observedWrites`, reported as `"unknown"`. Requires agent-level file-read enumeration beyond `commandIdentity` string matching — hence classified `content-agent`. |
| 3 | shared-writer count | mechanical-runner | Stages whose `observedWrites` intersection is non-empty. The key shared-state files are: `backlog.md`, `dashboard.md`, `tasks/*.md`, `milestones/M<NN>/*`, `milestone_counter`. A stage pair shares a writer relationship if both events' `observedWrites` contain at least one common path. Counted as unique stage pairs. Computed purely from event-stream `observedWrites` fields — no agent reasoning data required. |
| 4 | duplicate-rule count | mechanical-runner | From A3's invariant-ownership manifest (read directly from `experiments/quay-perpetual-stream/invariant-ownership.md`, not from the event stream): count rules with `>1` occurrence (authoritative + duplicate entries). This is the only metric not sourced from A1 events. If A3 has not yet landed, reported as `"unknown"` with `note: "A3 invariant-ownership manifest not yet available"`. Never re-implements A3's own duplicate detection. |
| 5 | prompt-to-code ratio | mechanical-runner | For each candidate: `commandIdentity` entries that are CLI invocations of real scripts (match `node --experimental-strip-types scripts/...` or `scripts/test.sh` or `scripts/*.sh`) divided by total `commandIdentity` entries across all stages. Agent-only NL instruction entries (no shell-out match) form the denominator complement. A run with 12 mechanical-script dispatches and 18 agent-only NL calls has ratio 12/30 = 0.40. |
| 6 | receipt reuse rate | mechanical-runner | Count of Prepared-phase events where `outcome === "skipped"` divided by total Prepared-phase events, across all candidates. A `skipped` Prepared outcome from a `waitReason: "cache-hit"` or `waitReason: "prepared-blocked"` (receipt reuse) counts. Events with no Prepared stage at all contribute a null entry, not zero. |
| 7 | replay variance | mechanical-runner | Difference between A2's expected replay outcomes and actual event-stream outcomes. Computed by comparing A2 fixture expected verdicts against the actual `outcome` + `stage` + `observedWrites` for matching events. The comparison is deterministic (expected vs. actual field matching), hence classified `mechanical-runner`. If A2 fixtures do not exist yet (`experiments/quay-perpetual-stream/fixtures/workflow-replay/`), the metric is `"unknown"` with `note: "A2 replay fixtures not yet available"`. Never re-implements A2's own replay logic. |
| 8 | failure-attribution precision | mechanical-runner | Fraction of `outcome === "needs-human"` events where `stage`, `waitReason`, AND `commandIdentity` are all non-null (all three attribution dimensions present) versus total `needs-human` events. Reported as `{preciselyAttributed: N, totalNeedsHuman: M, precision: N/M}`. |
| 9 | full-suite executions per candidate | mechanical-runner | Count of `commandIdentity` entries matching `scripts/test.sh` (the canonical test entrypoint per ADR-019) per `candidateId`. Per-stage breakdown: which stage ran the full suite (Build for development-class, Verify for mechanical, Audit for re-runs). |
| 10 | Land-fence hold/queue time | mechanical-runner | For Land-stage events: `timing.queuedAtMs` to `timing.startedAtMs` delta in milliseconds (measures Land-lock wait time under the `.quay/land-locks/shared-checkout.lock`). Under worktree isolation with concurrent dispatch, this is the serialization penalty. Under serial dispatch, this is typically near-zero. Aggregated as per-candidate and cross-candidate min/median/max. Reported as `{landQueueMs: N, landDurationMs: M, totalLandMs: N+M}`. |

**Mechanical/content-agent split.** Every metric and diagnostic carries a `metricClass` tag. Classification is rule-based (agent label prefix patterns, script path patterns, `commandIdentity` presence) — never LLM-judged:

- **`mechanical-runner`**: metrics sourced from mechanical phase boundaries (Verify script dispatches, Gate agent dispatches, Reconcile CLI, Land merge/commit), from `timing` wall-clock readings, or from CLI-invocation-pattern counts. Identified by `commandIdentity` entries matching `node --experimental-strip-types experiments/quay-perpetual-stream/scripts/` (a known script, not an agent prompt) and agent calls with labels matching established mechanical-check prefix patterns (`ceiling-check`, `gate-hash`, `line-budget`, `dogfood-evidence`, `composite-preflight`, `worktree-create`, `worktree-merge`, `worktree-remove`, `build-evidence-collector`, `emit-event-*`). Metrics 1, 3, 4, 5, 6, 7, 8, 9, 10 are tagged `mechanical-runner`.

- **`content-agent`**: metrics requiring agent-level data beyond the mechanical event stream. LLM-driven agent invocations that generate, reason about, review, or implement task content. Includes: ProposalAuthors, Adjudicate, ProposalReview, PlanAuthor, PlanCheck, Build implementation, Audit adversarial reasoning, Gate policy agents (the `domain-misfit` agent, the `prepare-receipt` check agent). Identified by `agentLabel` entries with labels matching established content-agent prefix patterns (`ProposalAuthors`, `Adjudicate`, `ProposalReview`, `PlanAuthor`, `PlanCheck`, `Build`, `Audit`, `domain-misfit`) and by the absence of a shell-script `commandIdentity`. Metric 2 is tagged `content-agent` because accurate context-working-set enumeration requires agent reasoning data beyond `commandIdentity` string matching.

- **`unknown`**: If an agent call cannot be unambiguously classified (ambiguous label, no `commandIdentity`, no script path match), it is tagged `metricClass: "unknown"` — the split is honest about classification edge cases rather than guessing.

The classification is **structural**: a metric's `metricClass` is determined by whether its data source is purely the mechanical event stream or also requires agent reasoning content. This split is itself a deliverable — it provides DIR-124-E with a quantified picture of how much of the workflow's cost is mechanical overhead versus content generation.

**Agent-level diagnostics.** These are explanatory diagnostics reported alongside the 10 metrics:

- **Agent-minutes:** sum of `timing.endedAtMs - timing.startedAtMs` across all content-agent events, converted to minutes. Broken down by stage and by `agentLabel`.
- **Tokens:** not directly present in A1 v1 events (the event schema is a stage-boundary record, not a per-agent-call cost log). Reported as `"unknown"` with `note: "token use not in A1 v1 event schema — available when DIR-124-B extends the schema or when the workflow runtime exposes per-agent-call token reporting"`. The baseline does not guess.
- **Finding novelty/recurrence:** extracted from `outcome` and `waitReason` patterns across candidates. A finding is "novel" if it appears for the first time in the observed set; "recurrent" if the same outcome/reason/`waitReason` combination appears across multiple candidates. Reported as `{novelFindings: N, recurrentFindings: M, recurrenceKeys: [...]}`.
- **Artifact-class output:** from `observedWrites`, categorized by file extension/project location: `{code: N (paths under experiments/ or packages/), docs: M (paths under docs/), tasks: K (paths under tasks/), milestones: L (paths under milestones/), other: P}`. Bytes are reported as `"unknown"` (byte counts are not in A1 v1 events — `observedWrites` records paths, not byte deltas; reading current file sizes would measure post-Land state, not the state at event-emission time).

**CLI surface.** The script follows the established pattern (`chart-headroom.ts`, `rolling-slope-check.ts`, `chart2-s3-external-validation.ts`): `#!/usr/bin/env node --experimental-strip-types` shebang (enabling direct TypeScript execution with Node's `--experimental-strip-types`), exported pure functions (`computeBaselineMetrics`, `classifyMetric`, `parseEventStream`, `parseInvariantManifest`), and a `main()` that reads `argv` for:

- `--event-dir <path>` (default: `experiments/quay-perpetual-stream/.workflow-events`)
- `--manifest <path>` (default: `experiments/quay-perpetual-stream/invariant-ownership.md`)
- `--json` — emits a structured JSON report to stdout; without it, a human-readable summary goes to stdout
- `--selftest` — runs embedded RED/GREEN fixtures (verifying: synthetic events produce correct metric values, zero samples produces `no-data`, null fields produce `"unknown"`, malformed lines are skipped with warnings, events with no `observedWrites` contribute zero to change-propagation radius)

Exit codes: 0 on valid report (even if all metrics are unknown — an honest empty baseline is valid output), 1 on selftest failure, 2 on usage/environment error (event dir unreadable, zero JSONL files found, manifest unreadable).

**Emission format.** The script emits a single JSON object to stdout:

```json
{
  "schemaVersion": "1",
  "scriptVersion": "1.0.0",
  "generatedAt": "<ISO8601>",
  "samples": N,
  "sampleRunIds": ["runId1", ...],
  "sampleRange": { "earliestEventAt": "<ISO8601>", "latestEventAt": "<ISO8601>" },
  "parseWarnings": [],
  "metrics": {
    "changePropagationRadius": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "perCandidate": { "<candidateId>": { "uniqueFiles": N, "uniqueDirectories": M, "paths": [...] } }, "aggregate": { "min": N, "median": N, "max": N } },
    "contextWorkingSet": { "metricClass": "content-agent", "evidenceStatus": "measured", "perCandidate": { "<candidateId>": { "filesRead": N, "files": [...] } } },
    "sharedWriterCount": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "sharedWriterPairs": N, "pairs": [{"stageA": "...", "stageB": "...", "commonPaths": [...]}] } },
    "duplicateRuleCount": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "totalRules": N, "duplicateRules": M, "ruleIds": [...] } },
    "promptToCodeRatio": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "mechanicalCalls": N, "contentAgentCalls": M, "ratio": N/(N+M) } },
    "receiptReuseRate": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "reusedCount": N, "totalPrepared": M, "rate": N/M } },
    "replayVariance": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "mismatches": N, "totalAssertions": M, "varianceRate": N/M } },
    "failureAttributionPrecision": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "preciselyAttributed": N, "totalNeedsHuman": M, "precision": N/M } },
    "fullSuiteExecutions": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "value": { "count": N, "perStage": {"Build": N, "Verify": N, "Audit": N} } },
    "landFenceTime": { "metricClass": "mechanical-runner", "evidenceStatus": "measured", "perCandidate": { "<candidateId>": { "landQueueMs": N, "landDurationMs": M, "totalLandMs": N+M } }, "aggregate": { "min": N, "median": N, "max": N } }

  "diagnostics": {
    "agentMinutes": { "metricClass": "content-agent", "value": { "totalMinutes": N, "perStage": {...}, "perAgentLabel": {...} } },
```

Every metric value is either a computed object or the string `"unknown"` (never `0` or `null` as a placeholder for missing data). The `status` field is `"ok"` for a successfully computed baseline (even a thin one) and `"no-data"` when zero event log files exist.

```
                                     │

              experiments/quay-perpetual-stream/.workflow-events/<runId>.jsonl
              (gitignored, per-run append-only .jsonl, one JSON line per event)

              workflow-baseline-metrics.ts
```

The A1 event stream is the single data source. A5 reads it from the gitignored `.workflow-events/` directory under `experiments/quay-perpetual-stream/`. The A3 invariant-ownership manifest (for duplicate-rule count, metric 4) is consumed from `experiments/quay-perpetual-stream/invariant-ownership.md` if it exists; if not, the metric is `"unknown"`. A2's replay fixtures (for replay variance, metric 7) are consumed from `experiments/quay-perpetual-stream/fixtures/workflow-replay/` if they exist; if not, the metric is `"unknown"`. These cross-child dependencies are additive, not mandatory — A5 produces a valid baseline with any subset of available sibling data.

The script is purely a reader — it never writes to the event log, never mutates any workflow state, never changes any lifecycle status. It is runnable at any time after A1 events exist, either ad-hoc by a human or mechanically as part of a metrics collection pipeline.

### Key design decisions

**DD1: Mechanical computation from A1 event stream, not prose estimation.** The split review's baseline-ordering finding requires a mechanical before-state. The A1 event stream carries `timing`, `commandIdentity`, `observedWrites`, `outcome`, `agentLabel`, and `waitReason` — all fields needed to compute the 10 crystallization metrics mechanically. Every metric is derived from structured event fields via deterministic functions — never from agent structured-output summary reports, Claude Code timeline inspection, or prose reconstruction. This is the single most important design decision — it is what makes the baseline a comparison surface rather than another opinion.

**DD2: First-class mechanical/content-agent split on every metric.** The crystallization document (section 3.5) describes the "shadow architecture" — a typed contract layer that exists beside the prompt monolith but is not the execution mechanism. The `metricClass` tag quantifies this split: how much of the workflow's cost is mechanical overhead (script dispatches, gate checks, merge operations) versus content generation (proposal authoring, audit reasoning, plan checking). Classification is rule-based (agent label prefix pattern, script path pattern, `commandIdentity` presence) — never LLM-judged. An ambiguous entry gets `metricClass: "unknown"` rather than a guessed classification. DIR-124-E's resource-aware scheduling needs this split to decide where optimization effort is best spent.

**DD3: Explicit unknowns, never zeros or guesses.** A metric with insufficient evidence is `"unknown"`, not `0`. This is critical for DIR-124-E: a resource-aware scheduler must distinguish "we have zero data on Land-fence queue time" from "Land-fence queue time is 0ms" — the latter would silently disable queue-time-aware scheduling. Every metric's `evidenceStatus` field is `"measured"` or `"unknown"`, never implicit. A zero is a meaningful measurement (e.g., zero full-suite runs means `test.sh` was never invoked); an unknown means "we don't know."

**DD4: Before-state only — no inference of delivered value.** The baseline records what the event stream contains, not what it means. It does not compute a "milestone quality" score, does not tag metrics as "good" or "bad," and does not emit recommendations. This is a measurement instrument, not an evaluation instrument. DIR-124-E owns the scheduling decisions that consume this data.

**DD5: Cross-child dependencies are additive, not mandatory.** A5 declares dependencies on A1 (event stream), A2 (replay fixtures), and A3 (invariant-ownership manifest). But only the A1 dependency is hard: without event log files, the status is `"no-data"`. Without A2 or A3, the corresponding metrics are `"unknown"` with an explanatory note — A5 produces a valid (thinner) baseline. This preserves independent landability per the parent's split-multi-mechanism finding: each child is independently useful even if its siblings are still in flight.

**DD6: Follows established script patterns exactly.** The script follows the `chart-headroom.ts`/`rolling-slope-check.ts`/`chart2-s3-external-validation.ts` pattern: shebang, exported pure functions, `main()` with CLI flags (`--event-dir`, `--manifest`, `--json`, `--selftest`), embedded RED/GREEN selftest fixtures, exit code 0/1/2 convention. No new pattern is introduced — this is the repo's established metric-script convention.

**DD7: Both mirror paths, byte-identical at Land.** The script lives at both `experiments/quay-perpetual-stream/scripts/workflow-baseline-metrics.ts` and `plugin/scripts/workflow-baseline-metrics.ts`, byte-identical. The existing mirror-diff test pattern (which `diff`s both directories for files in the Touches list) covers this script. A test fixture at `experiments/quay-perpetual-stream/test/workflow-baseline-metrics.test.mjs` (mirrored at `plugin/test/workflow-baseline-metrics.test.mjs`) verifies: (a) the two mirrors are byte-identical, (b) each metric computation produces expected output from a known event fixture, (c) missing-field paths produce `"unknown"` rather than zeros, and (d) the mechanical/content classification is rule-based and deterministic.

**DD8: Single-file module, zero npm dependencies.** The script is a single `.ts` file with zero npm dependencies beyond Node.js built-ins (`fs`, `path`). It implements its own inline CLI argument parsing (matching the established `chart-headroom.ts`/`rolling-slope-check.ts`/`chart2-s3-external-validation.ts` pattern — all three implement their own for-loop `process.argv` parsing; none imports `isDirectEntry()` or `parseArgs()` from `gate-script-base.ts`). The shebang `#!/usr/bin/env node --experimental-strip-types` enables direct TypeScript execution on Node >=20. Plain functions, no class hierarchy.

**DD9: Honest zero-sample handling is valid output.** When zero real event samples exist (A1 landed but no real milestone run has executed yet), the script reports `{samples: 0, status: "no-data"}` and exits zero. All 10 metrics are `"unknown"` with reason `"no-event-samples"`. This is not a failure — it is a true statement about the before-state. DIR-124-E can then design its scheduling policy knowing which metrics have data and which do not.

### Defaults and failure behavior

**Default event directory:** `experiments/quay-perpetual-stream/.workflow-events` (the A1 per-run event log directory). Overridable via `--event-dir <path>`.

**Default manifest path:** `experiments/quay-perpetual-stream/invariant-ownership.md` (A3's manifest). Overridable via `--manifest <path>`.

**Zero event samples:** The script reports `{samples: 0, status: "no-data"}` and exits 0. All 10 metrics are `"unknown"` with reason `"no-event-samples"`. This is valid output — an honest empty baseline.

**A single event log found with fewer than 8 stages:** The baseline includes partial data for the stages that are present. Missing stages contribute `"unknown"` for stage-specific metrics. Exit zero.

**Unreadable event directory:** Exit code 2 (usage/environment error), message to stderr. Never silently returns an empty report when the directory should exist but is unreadable.

**Event JSON parse error (corrupted line in an event log):** The corrupted event is skipped with a count in the report's `parseWarnings` array (e.g., `{type: "malformed-line", file: "<path>", line: N}`). A single malformed line does not invalidate the entire event stream — it is a warning, not a failure. If all events in all logs are corrupt, status is `"no-data"`.

**Missing event field (null in source):** Reported as `null` in the metric output. If the field is required for a metric computation and is null across all events for that metric, the metric is `"unknown"` with reason `"insufficient-field-data"`.

**Unrecognized `stage` value (future workflow phase added after A5 landed):** The event's metrics are still counted (the unknown stage is included in counts) but the per-stage breakdown labels it as `"unknown-stage:<value>"`. Forward-compatible behavior.

**Missing `commandIdentity` in an event:** The event is classified as `metricClass: "content-agent"` (conservative: assume agent work when script identity is unknown). If the missing field makes a metric uncomputable, that metric is `"unknown"`.

**A1 schema version mismatch:** If an event carries `schemaVersion` other than `"1"`, a warning is emitted to stderr and the event is processed with v1 field expectations (missing fields become `"unknown"`). A future v2 event with new fields has those new fields silently ignored. A future v2 event with removed fields produces `"unknown"` for the removed field.

**No `observedWrites` in any event:** change-propagation-radius, shared-writer-count, and artifact-class-output are all `"unknown"`. The baseline is honest about its data gap.

**Cross-child artifact missing (A2 fixtures, A3 manifest):** The affected metric is `"unknown"` with reason `"cross-child-artifact-not-yet-landed"`. Never a crash — each child lands independently.

**Invalid manifest format (unparseable invariant-ownership.md):** If the manifest is requested (metric 4) but unparseable, that specific metric is `"unknown"` with reason `"manifest-parse-failure"`. Other metrics are unaffected.

**Disk I/O error (write failure on stdout, permission denied on event directory):** The script exits non-zero. An event directory that becomes unreadable mid-run exits with `{status: "error", reason: "<err.message>"}`.

**Selftest failure:** Exit code 1. The script's `--selftest` mode runs embedded RED/GREEN fixtures that verify: (a) GREEN — a synthetic 3-event JSONL stream produces correct metric values for all 10 metrics; (b) GREEN — zero samples produces `{samples: 0, status: "no-data"}`; (c) RED — a metric field that is null in the event produces `"unknown"`, not `0`; (d) RED — a malformed JSONL line is skipped with a `parseWarning`, not a crash; (e) RED — an event with no `observedWrites` contributes zero to change-propagation radius.

### Compatibility

This child is **behavior-preserving** with respect to the installed workflow. It is a pure consumer of the A1 event stream — it reads files, computes metrics, and writes to stdout. It does not:
- Modify the A1 event stream (read-only)
- Modify any workflow file (`.claude/workflows/*`, `plugin/workflows/*`)
- Modify any workflow state (no lifecycle mutation, no status write)
- Introduce a new journal format (consumes A1's v1 schema; does not create a parallel format)
- Change any gate behavior (not wired into `it0-dod-check.ts`; purely observational)
- Change pass/fail policy for any milestone

**Backward compatibility with A1:** The script depends on A1's v1 schema fields. If A1's schema is extended (v2 by DIR-124-B), the script's `parseEventStream` function must handle the new fields gracefully: unknown fields are ignored (forward-compatible read), and any metric that requires a v2-only field is `"unknown"` until the script is updated. The `schemaVersion` marker in each event makes this explicit.

**Forward compatibility for DIR-124-E:** The baseline report's JSON schema (v1) is a stable contract. DIR-124-E consumes this exact shape. If the metric set is expanded later, a new report schema version (v2) is introduced — DIR-124-E's consumer can check `schemaVersion` and adapt.

**Cross-child ordering:** A5 depends on A1 (event stream must exist). A5 cross-references A2 (replay variance) and A3 (duplicate-rule count) but does not depend on them — those metrics gracefully degrade to `"unknown"` if the cross-child artifact is not yet landed. This preserves independent landability: A5 can land and produce a valid report even if A2 and A3 are still in flight.

**No behavioral coupling to the 10-metric list.** The crystallization document's metric set is the initial target, but the script's architecture (per-metric function, tagged output) allows adding a new metric by adding a function + output key without touching existing computations. DIR-124-E may request additional metrics without A5 becoming a bottleneck.

### Risks

**R1: A1 event stream does not yet exist.** A5 cannot be implemented or tested with real data until A1 lands. Mitigation: A1 is the ordered-first child; A5 depends on it. The implementation order is enforced by the parent's ordering (A1 → A5). A5's test fixtures use hand-crafted JSONL event files matching the A1 v1 schema shape — these fixtures are sufficient for RED/GREEN testing before A1 lands, but real-evidence proof requires A1 to be landed first.

**R2: Thin baseline at Land time.** Only a handful of real milestone runs may exist when A5 lands (the event stream is new, populated only by post-A1 Land activity). Mitigation: explicit unknowns — the baseline does not estimate. The report's `samples: N` field is honest. DIR-124-E's design must handle a thin baseline; fabricating richness would be worse.

**R3: Drift between event stream schema and metric computation.** If A1's v2 schema adds/renames fields, the metric computation map may produce incorrect or `"unknown"` results. Mitigation: the script checks `schemaVersion` on each event and skips events with unrecognized versions (logged in `parseWarnings`). When DIR-124-B extends the schema, A5's computation map must be revisited — this is a deliberate coupling point, not an accident.

**R4: Cross-child artifact format drift.** A3's invariant-ownership manifest format may change after A5 lands, breaking metric 4 (duplicate-rule count). A2's replay fixture format may change, breaking metric 7 (replay variance). Mitigation: each cross-child consumer is fail-soft — an unparseable artifact produces `"unknown"`, not a crash. The `parseWarnings` array records the failure reason.

**R5: Mirror drift.** The `experiments/` and `plugin/` copies of `workflow-baseline-metrics.ts` may diverge if a future edit updates one but not the other. Mitigation: the existing mirror-parity test pattern (which `diff`s both directories for files in the Touches list) covers this script. A divergence is caught at Land.

**R6: Large event logs.** Accumulated `.jsonl` files under `.workflow-events/` could grow to hundreds of runs. The script reads all matching files; on a very large directory (>1000 runs), the read-and-parse step could be slow. Mitigation: the script processes files sequentially (streaming parse, not loading all into memory); the default event directory is gitignored; the `cleanup_temp_files` MCP tool already cleans stale files. If performance becomes an issue, a `--max-samples N` flag can be added later — not in scope for v1.

**R7: Mechanical/content classification ambiguity.** Some metrics straddle the boundary — e.g., context working set (metric 2) could be partially computed from `commandIdentity` string matching (mechanical-runner) but fully accurate enumeration requires agent reasoning data (content-agent). Mitigation: each metric's classification is documented and auditable. The classification is structural, not narrative — "this metric is `content-agent` because it requires data beyond the event stream." If a classification is wrong, it is auditable and correctable.

**R8: Metrics that require cross-run context are thin with few samples.** Finding recurrence (needs multiple runs to establish), replay variance (needs A2 fixtures), and duplicate-rule count (needs A3 manifest) may all be `"unknown"` at A5's own Land time. Mitigation: these are explicitly tagged `"unknown"` — the baseline is not pretending to have data it doesn't. DIR-124-E's design must handle unknown metrics gracefully.

### Non-goals

Explicitly excluded from this child's scope:

1. **Inferring delivered value from baseline metrics.** The baseline records what happened, not whether it was good. No "milestone quality" score, no pass/fail threshold, no recommendation engine.
2. **Changing pass/fail policy.** No gate check consumes the baseline report. No milestone promotion decision references it. Purely observational.
3. **Resource-aware scheduling.** DIR-124-E consumes this baseline; A5 only produces it.
4. **Real-time metrics dashboard or streaming.** The script is a batch processor — it reads completed event logs and emits a point-in-time report. No WebSocket, no live dashboard, no incremental update.
5. **Post-Land Wiring Audit.** The baseline report is not checked by any gate. No `it0-dod-check.ts` clause verifies it. It is a deliverable artifact, not an enforcement mechanism.
6. **Worktree redesign, stage scheduler, resource lease, lifecycle-promotion policy.** Per parent AC9 non-goal — none of these are introduced.
7. **Unifying with `gate-events.jsonl` or `prepare-telemetry`.** These are separate systems with different schemas, storage paths, commit policies, and purposes. A5 consumes only the A1 event stream. Cross-referencing prepare-telemetry data is a future task (DIR-124-B's migration adapter scope, not A5's).
8. **Estimating metrics for runs that predate A1.** The baseline only covers runs with A1 events. Pre-A1 runs are not reconstructed from prose — that would defeat the mechanical-before-state purpose.
9. **Second journal format.** A5 emits to stdout only (parent non-goal 3). It never creates a parallel event log, never writes to `.quay/gate-events.jsonl`, never writes to `milestones/prepare-telemetry/`.
10. **Token-use measurement.** A1 v1 events carry no token counts. Adding token reporting is DIR-124-B's scope. A5 reports tokens as `"unknown"` with an explanatory note.
11. **Byte-level artifact size measurement.** `observedWrites` records paths, not byte deltas. Reading current file sizes would measure post-Land state, not the state at event-emission time. Byte counts are `"unknown"` — a future event schema version that records per-file byte deltas at emission time would fix this correctly.

### Alternatives considered and rejected

**Alt1: Prose estimation from reports (the current state).** Reconstructing metrics from Claude Code timelines and agent prose summaries is exactly the broken state this child fixes. Rejected: the split review's baseline-ordering finding requires a mechanical before-state for DIR-124-E's comparison surface. Prose estimation cannot produce reproducible, verifiable metrics because each run's prose format differs.

**Alt2: Extending A1 to also emit metrics inline.** A1's `recordStageEvent` is observational-only by design — it records raw events, not derived metrics. Adding metric computation to A1 would: (a) couple emission to analysis, violating A1's fire-and-forget contract; (b) require metrics logic to live in a workflow file (the DSL has no `import` capability, so non-trivial computation must be in an agent-invoked script); (c) force A5's deliverable to be produced as a side effect of event emission rather than as an independent artifact. Rejected: A5 is a distinct deliverable consuming the A1 stream; keeping them separate preserves independent landability — the split review's core finding.

**Alt3: Merging A5 into A1 (schema + metrics in one child).** The split review's `split-multi-mechanism` finding explicitly identified A1 and A5 as independently landable mechanisms. The `repairable: false` verdict means this is a structural split, not a fixable defect. Rejected: A1 and A5 remain separate children per the split review's finding.

**Alt4: Merging A5 with A2 (replay corpus + metrics in one child).** Both consume the A1 event stream. Combined, they could share the event-reading layer. Rejected: A2's scope is replay correctness (classification taxonomy, negative controls, known-defect labeling); A5's scope is metric computation (10 formulas, mechanical/content split, explicit unknowns). They have different test fixtures, different output formats, and different consumers (A2 feeds DIR-124-B's stage scheduler validation; A5 feeds DIR-124-E's resource-aware scheduling). Independent landability wins.

**Alt5: Reconstructing pre-A1 runs from prose for a richer baseline.** Would estimate from Claude Code timelines, agent prose summaries, and git history — exactly the non-mechanical approach this child replaces. Would also produce a baseline that DIR-124-E cannot trust as a comparison surface because it mixes mechanical (post-A1) and estimated (pre-A1) data. Rejected: the baseline covers only runs with real A1 events. An honest thin baseline is better than a thick estimated one.

**Alt6: Wired enforcement — making the baseline report a gate check.** Would gate milestone promotion on baseline report validity, creating a circular dependency (the baseline measures Land, but Land requires the baseline). Would also block Land when there are zero historical event logs (a new installation) or when A2/A3 have not yet landed (cross-child circular dependency). Rejected: the baseline is purely observational. DIR-124-E's scheduling policy may consume it, but that is DIR-124-E's decision, not A5's.

**Alt7: Embedding the metric computation map in the workflow files.** The workflow DSL has no `import` capability and its `agent()` primitive is designed for agent dispatch, not data processing. The established pattern in this repo is to write a standalone TypeScript/JavaScript script with exported pure functions and a `main()` CLI — this is what `chart-headroom.ts`, `rolling-slope-check.ts`, `chart2-s3-external-validation.ts`, and dozens of other scripts do. Rejected: a first-class script following the established pattern is the correct mechanism.

**Alt8: A single aggregate report rather than per-candidate breakdown.** Would lose the per-candidate granularity that DIR-124-E needs for scheduling decisions (e.g., "this class of milestone consistently has 3x the Land-fence wait time"). Rejected: the report includes both per-candidate and aggregate (min/median/max) views.

**Alt9: Streaming/incremental metrics (append to report as events arrive).** Would require a persistent metrics database, a write mechanism, and a concurrency model — far beyond the scope of a baseline measurement tool. Rejected: batch processing of completed event logs is sufficient for v1. Incremental metrics belong in DIR-124-E or later.

**Alt10: Unifying with `gate-events.jsonl` or `prepare-telemetry` for a single observability surface.** Gate events, prepare-telemetry records, and workflow stage events have different schemas, purposes, storage paths, and consumers. Gate events record lifecycle transition verdicts (the meter); prepare-telemetry tracks convergence (prepare lifecycle); stage events record workflow execution timing and effects (the measurement). Unifying them would create a single format that serves none well. Rejected: separate systems, separate consumers — no unification in this child's scope.

**Alt11: Consuming prepare-telemetry data alongside A1 events.** The existing 125 prepare-telemetry records under `milestones/prepare-telemetry/` contain phaseTimings and findingCodes for the prepare lifecycle. They could fill gaps where A1 events are not yet available. Rejected: the prepare-telemetry schema (v2) is a different shape, different storage path (git-committed), and different purpose (convergence-generation tracking). Consuming it would couple A5 to a schema that DIR-126-D owns and may evolve independently. DIR-124-B's migration adapter is the designated bridge between prepare-telemetry and the canonical journal — A5 should consume the canonical event stream, not the pre-canonical telemetry format.

**Alt12: Using LLM classification for the mechanical/content split.** An agent could read each event's `agentLabel` and `commandIdentity` and classify it as mechanical or content. Rejected: the split must be deterministic (same event produces same classification every run) and verifiable (a reviewer can trace the rule that produced a given classification). An LLM classifier introduces non-determinism and makes the baseline unreproducible — defeating the purpose of a before-state measurement boundary.

**Alt13: Reading actual files to populate artifact-class byte counts.** The `observedWrites` field lists paths — the script could `stat` each file to get byte sizes. Rejected: `observedWrites` captures the files a stage touched at the time it ran. By the time A5 runs (post-Land), those files may have been further modified by subsequent stages, Land itself, or later milestones. Reading current file sizes would measure the wrong state. Byte counts are `"unknown"` in this baseline — a future event schema version that records per-file byte deltas at emission time would fix this correctly.

**Alt14: Reporting "0" for metrics with insufficient data.** Using `0` as the default when a metric cannot be computed would produce a misleading zero-rich baseline that DIR-124-E might misinterpret as "everything is fine, the system is cheap." Rejected: `"unknown"` is semantically distinct from `0` — a reader can distinguish "this metric was never measured" from "this metric was measured and found to be zero."

**Alt15: Requiring A2 and A3 to be landed before A5 can produce any output.** This would couple A5 to sibling completion, contradicting the parent's independent-landability design. Rejected: A5 produces a valid (possibly thinner) baseline with any subset of available sibling data. Cross-child consumption is additive, not mandatory.

**Alt16: Inferring token usage from agent metadata when the event stream does not carry it.** A1's v1 schema does not include token usage as a first-class field (it is not in the RA1 field set). Token usage is agent-level metadata, not a stage-boundary event field. The baseline can report it as a diagnostic where available (from agent output metadata), but it is tagged `"unknown"` when not. Rejected: fabricating token counts from event fields would violate the mechanical-before-state contract.
