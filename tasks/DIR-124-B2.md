### Chosen mechanism

Two zero-dependency TS script families (both mirrors, byte-identical), each an ESM module with an
embedded CLI invoked via the established `node --experimental-strip-types <abs path>/<script>.ts
<mode>` pattern — no new DSL import mechanism (relative TS imports work under that flag, proven by
`milestone-worktree.ts` consumers).

**`stage-receipt.ts` — the versioned contract module.** ONE authoritative schema family —
`FindingEnvelope`, `StageEvent`, `StageReceiptEnvelope`, `ReceiptValidationResult` — guarded by a
single `CONTRACT_SCHEMA_VERSION` const; a schema change is a new envelope version, never silent field
drift:

1. `StageEvent` — the durable journal event: a field-for-field **superset of the LANDED A1a 20-field
   schema** (all 20 fields preserved), **imported** from the sibling `workflow-event-schema.mjs`
   (`SCHEMA_VERSION`/`REQUIRED_FIELDS`/`validateEvent`/`emitEvent` — A1 stays the single source of the
   20-field shape), plus the binding/provenance fields the envelope needs: `eventId`,
   `workflowSourcePath`, `workflowSourceHash`, `workflowSourceCommit`, `runtimeGeneration`,
   `materialInputHashes`, `receiptRef` (path, null on non-green), and provenance
   `migratedFrom`/`sourceRecordId`/`sourceHashes`. Stage/outcome/wait/isolation/dispatch **VALUES**
   are imported from A1's shared constants — one stage vocabulary, no second stage-name authority.
2. `FindingEnvelope` — occurrence identity (`findingId`), stable `recurrenceKey` (the
   `sha256(taskId::code).slice(0,12)` precedent), observer/earliest-detectable stage, subsystem/claim
   reference, severity/blocking/everBlocking, evidence references (bounded `{path, sha256}`),
   material input hashes, first/last generation, disposition/resolution, and the
   `task-specific|profile|global` generalization. Generalization is **descriptive metadata, never a
   reuse predicate**: reuse is decided solely by recurrence key + material input hashes, so a
   same-`recurrenceKey`-different-hash fixture must fail (AC1/AC2 negative control).
3. `buildReceiptEnvelope`/`bindReceipt` — mechanically bind base/candidate commits, workflow source
   path/hash/commit (`git log -1 --format=%H -- <path>` + `sha256sum <path>`), runtime generation, and
   every material input hash; a receipt with empty `materialInputHashes` is not reusable.
4. `validateReceipt` — fail-closed, returning `ReceiptValidationResult {ok, code, detail}` with ONE
   distinct `code` per AC6 hazard: `wrong-base`, `wrong-candidate`, `modified-plan`,
   `stale-workflow-materialization`, `wrong-runtime-generation`, `missing-artifact`,
   `moved-candidate-commit`, `tampered-receipt` — as fixed RED/GREEN tests.
5. `validateEvidenceManifestRef({path, sha256})` — hash-validates a bounded Build evidence-manifest
   reference (`manifestRefForReceipt`'s `{hash, path, candidateCommit}` shape) against the file it
   names WITHOUT copying authoritative content; `rejectDuplicateAuthority` is the permanent negative
   control rejecting a receipt embedding copied task/Proposal/charter/Plan text, extending
   `validateManifestShape`'s existing `no-second-authority` code.
6. `migratePrepareLedger(entry)` — the one-way `proposal-ledger.json` entry → `FindingEnvelope`
   adapter, preserving `id`/`subsystem`/`claimRef`/`severity`/`blocking`/`everBlocking`/
   `disposition`/`rootCauseKey`/`firstSeenRound`/`lastSeenRound` and carrying source hashes.
7. CLI: `--validate-receipt`, `--evidence-manifest-ref`, `--migrate-prepare-ledger`, plus embedded
   `--selftest`/`--json` per the A1 precedent.

**`workflow-journal.ts` — the `StageJournalStore`.** Append-only durable journal at
`milestones/M<NN>/stage-journal.jsonl` plus `receipts/*.json` under the canonical milestone root
resolved by importing `parseMilestoneNum`/`milestoneRootRel` from `milestone-worktree.ts` (the
existing test-pinned TS twin of `gate_resolve_milestone_root`) — never a second path convention; the
`>= 130` boundary literal stays out of B2's TS (a grep selfcheck fails otherwise). The store exposes:

1. `appendStage(event)` — validates against the schema family, line-safe framed append (each record
   is one single-line JSON object, `emitEvent`-serialized so no embedded newline), atomic
   (write-temp-then-rename on the journal file), torn-write rejection (a partial trailing record is
   surfaced as `{ok:false, code:'torn-trailing-record'}` on read, never silently parsed).
2. `writeReceipt(envelope)` — temp-then-rename into `receipts/*.json` (one file per run-stage), never
   overwrites in place.
3. `persistVerifyCache(updates)` / `loadValidatedVerifyCache(runIdentity)` — the store's cache
   methods. `load` validates exact check input + base/candidate state + workflow source hash + runtime
   generation **before** any reuse and fails closed (no valid receipt → fresh dispatch). Persistence
   is atomic and a failed write leaves the store unchanged. B2 ships these methods + their RED/GREEN
   contract tests; the execute-milestone callsites are B3/B4's, not B2's.
4. `migrateDir124AEvent(event)` — field-for-field map of the **pinned A1 20-field schema** (importing
   A1's own `validateEvent`/`emitEvent`) into a `StageEvent`, appended to the **same** journal, so
   after migration no dual authoritative event format remains.
5. `migrateDir126DTelemetry(record)` — one-way map of a prepare-telemetry record into a `StageEvent`,
   preserving `recordId`/`generationId` and `hashes`; no reverse writer.
6. DIR-118 extension fields declared but inert; `landed-awaiting-wiring` is grep-forbidden in both
   mirrors; no post-Land Wiring Audit dispatch, no `done`-promotion enforcement.
7. CLI: `--append-stage`, `--migrate-dir124a`, `--migrate-dir126d`, `--persist-verify-cache`,
   `--load-validated-verify-cache`, plus embedded `--selftest`/`--json`.

The Verify-cache persistence (`persistVerifyCache`/`loadValidatedVerifyCache`) lives in this same
store module and is exercised by DIR-124-B3; the store's cache-load methods are the contract B3
consumes.

**WIRING-CLAIM (B2-DURABLE-STORE):** `execute-milestone.js` appends a `StageEvent` via
`workflow-journal.ts --append-stage` at each of the **eight** phase boundaries (Verify, Prepared,
Build, Build-Evidence, Audit, Gate, Reconcile, Land) and writes a hash-bound `StageReceiptEnvelope`
on green boundaries; the store resolves its root via `milestoneRootRel` (the TS twin of
`gate_resolve_milestone_root`) and rejects torn/partial writes. → AC4, CLAIM-B2/B3/B10/B11. NOTE:
these execute-milestone.js callsites are wired by sibling DIR-124-B4 (M256); B2's Touches
deliberately exclude `execute-milestone.js`. B2 therefore proves the real-object half through a real
dispatch against the store's own CLI at the canonical `milestones/M254` root (see DoD), and the
wiring half is a forward contract B4 must AC-prove.

### Key design decisions

- **DD1 — Root resolution is REUSE, not re-derivation.** The store imports `parseMilestoneNum`/
  `milestoneRootRel` from `milestone-worktree.ts` — the existing, test-pinned TS twin of
  `gate_resolve_milestone_root` (pinned against the shell function by
  `execute-milestone-worktree.test.mjs`). A third hand-copied `>= 130` rule — or a per-append
  `execSync` into bash — is the exact path-convention drift/fragility class this milestone must not
  reintroduce. B2's TS contains no `>= 130` literal (a grep selfcheck fails otherwise); the boundary
  lives only in gate-script-lib.sh + the pre-existing pinned twin. Store fixtures assert
  `milestoneRootRel("M254") === "milestones/M254"` and round-trip through the shell resolver.
- **DD2 — Durable committed store under the canonical milestone root.** The gitignored
  `.workflow-events/` stream is A1's transient observability; B2's journal/receipts must survive
  process/session restart and be post-Land auditable, so they are committed pipeline-generated
  milestone artifacts under `milestones/M<NN>/` (same commit policy as `preparation.json`/
  `build-evidence-manifest.json` — no new path convention, no source-glob edits). The store creates
  `milestones/M254` if absent.
- **DD3 — One authoritative schema family, versioned by explicit bump.** All four envelope types live
  in `stage-receipt.ts`, guarded by `CONTRACT_SCHEMA_VERSION`; a schema change is a new envelope
  version, never silent field drift. A1's 20-field shape is imported (never re-declared), so A1 stays
  the single source of the A1 fields and the adapter is a real, testable boundary.
- **DD4 — Receipts bind everything mechanically.** `bindReceipt` records base/candidate commits,
  workflow source path/hash/commit, runtime generation, and every material input hash. This is what
  defeats the M176 stale-named-workflow defect: a stale materialized workflow body is literally
  different file content, so `workflowSourceHash` differs and the receipt fails closed — no reliance
  on prompt/label identity.
- **DD5 — Runtime generation derived from installed workflow source hash.** Defined as the installed
  workflow source hash at dispatch (a monotonic journal counter bumping on hash change is optional);
  the fixed derivation is pinned by fixtures so the definition cannot drift, and
  `wrong-runtime-generation` is a distinct fail-closed code.
- **DD6 — Atomic write + torn-write rejection.** Journal uses line-safe framed append (single-line
  records via A1's `emitEvent`, so no embedded newline can split a record) with temp-then-rename;
  receipts use temp-then-rename. A partial trailing record is surfaced on read, never silently parsed;
  no partial-success state is observable.
- **DD7 — One-way migration adapters only.** `migrateDir124AEvent`, `migrateDir126DTelemetry`, and
  `migratePrepareLedger` are schema mappers + hash/provenance preservers, never schema authors and
  never reverse writers. After migration there is exactly one authoritative journal format. An absent
  migration input (e.g. no A1 event stream yet because A1b/A1c emission is `todo`) is a
  recorded-provenance no-op, never a guessed shape.
- **DD8 — Receipts never copy authoritative content.** Hashes + a bounded evidence-manifest reference
  only; `manifestRefForReceipt`'s `{hash, path, candidateCommit}` is consumed, not duplicated;
  `rejectDuplicateAuthority` is the permanent negative control, extending `validateManifestShape`'s
  existing `no-second-authority` code.
- **DD9 — Verify-cache persistence lives in the store, callsites elsewhere.**
  `persistVerifyCache`/`loadValidatedVerifyCache` are store methods with fail-closed load (no valid
  receipt → fresh dispatch) and atomic, failure-safe persistence. B2 ships the methods + contract
  tests; B3 exercises them; B4 wires them. A store write failure can never yield a stale reuse
  (fail-safe direction).
- **DD10 — DIR-118 extension fields declared but inert.** Forward-compatible optional fields exist on
  the envelopes; no wiring reads or acts on them. `landed-awaiting-wiring` is grep-forbidden in both
  mirrors; no post-Land Wiring Audit dispatch, no `done`-promotion enforcement.
- **DD11 — Zero production callers at land.** B2 is substrate-only and fully rollbackable pre-wiring;
  the only production-path touch is B2's own two-process real-object exercise on `milestones/M254/`.
  B4 owns the execute-milestone.js callsites.
- **DD12 — `bindReceipt` accepts identity as a structural input, not an import.** B1's
  `run-identity.ts` may land before or after B2; `stage-receipt.ts` therefore consumes a
  `RunIdentity`-shaped object (documented structural contract) and B2's tests use a fixture-shaped
  identity. No import dependency on B1's module keeps the two substrate families independently
  landable.
- **DD13 — Mirror parity as an enforcement surface.** Both script pairs byte-identical (`cmp` exit 0)
  and both test files byte-identical; the mirror `diff` must stay clean. `scripts/test.sh`'s default
  glob picks up the new `plugin/test/*.test.mjs` by location alone.

### Defaults and failure behavior

- **Cold start (no journal):** valid input, never a crash; the first append creates the journal.
- **Empty `materialInputHashes`:** the receipt is not reusable (`validateReceipt` fails with
  `empty-material-inputs`).
- **Torn/partial write:** surfaced as `torn-trailing-record` on read, never silently parsed; atomic
  write means no partial-success state is observable.
- **Tampered receipt / each AC6 hazard:** sha256/HMAC mismatch → `tampered-receipt`; each of the
  eight hazard classes (wrong base, wrong candidate, modified Plan, stale named-workflow
  materialization, wrong runtime generation, missing artifact, moved candidate commit, tampered
  receipt) returns its **own** distinct `ReceiptValidationResult` code.
- **Evidence-manifest ref to a missing/mismatched file:** hash validation fails closed with a distinct
  code.
- **Duplicate authority:** a receipt embedding copied authoritative content is rejected by
  `rejectDuplicateAuthority`.
- **Cache load failure:** treated as "no valid receipt" → fresh dispatch for that check; a store bug
  cannot cause silent stale reuse. **Cache persist failure:** store unchanged; Verify falls back to
  fresh dispatch.
- **Reverse migration attempt:** errors; adapters never edit `.workflow-events/`, `prepare-telemetry/`,
  or `proposal-ledger.json`.
- **Absent migration input:** recorded-provenance no-op (a provenance note appended to the journal),
  never a guessed shape.
- **Lifecycle (DoD 2-3):** B2's real-object proof is a REAL dispatch through the store's own CLI
  against `milestones/M254` — write the journal + at least one receipt in one node process, read them
  back in a separate node process, and have the independent audit check bytes/hashes and real caller
  persistence. The end-to-end execute-milestone wiring proof is B4's; the pre-Land iteration-0 Audit
  refutes-by-construction any claim of that wiring within B2 — B2 lands human-steered with a declared
  external needs-human reason, and `done` is reached only via the post-Land real proof + re-promote.

### Compatibility

- **Reads, never edits, the pinned inputs:** `workflow-event-schema.mjs`, `proposal-convergence.ts`,
  `milestone-preparation-check.ts`, `build-evidence-manifest.ts`, `milestone-worktree.ts`,
  `gate-script-lib.sh`, `prepare-milestone.js`, `prepare-admission-check.ts`, `composite-*.ts`, and
  the four golden-replay `plugin/test/execute-milestone-*.test.mjs` files are all read-only inputs;
  editing any of them is a Plan violation.
- **Reuses, never forks, the single-sourced root resolver** (`milestoneRootRel`) and the shared A1a
  stage vocabulary.
- **Prepare artifacts stay the Prepare authority:** `preparation.json`/`proposal-ledger.json`/
  `prepare-telemetry/` remain authoritative in their own layer; B2 reads them one-way with source
  hashes preserved (no dual-write, no reverse dependency).
- **A1's `.workflow-events/` stream and B2's journal coexist during the transition;** B2's journal is
  the sole receipt authority after migration. Each stays its own system (no unification with
  `.quay/gate-events.jsonl`).
- **Dependency surface:** B1's `RunIdentity` is consumed as a structural input (DD12); B3 consumes
  the store's cache-load methods as its contract; B4 wires the callsites. B2 does not call B3/B4 code.
- **Worktree isolation is bound, not assumed:** receipts record whatever isolation was used; a
  receipt's binding fields are validated at load, so a resume under a different candidate state
  revalidates before reuse. Legacy (no-isolation) and worktree-isolated dispatch consume the same
  substrate.
- **Behavior-preserving:** no existing script, gate, or workflow is modified; the real-object proof
  adds files under `milestones/M254/` only.

### Risks

- **R1 — Verify hot path once wired (B3/B4).** A store-load bug could force unnecessary re-runs or
  stale reuse. Mitigation: fail-closed load (no valid receipt → fresh dispatch), atomic failure-safe
  persistence, and the AC6 hazard matrix as fixed RED/GREEN so a silent-reuse regression is a test
  failure.
- **R2 — Dual authoritative event formats if migration is partial.** Mitigation: single-journal guard
  — all stage events/receipts flow only through `StageJournalStore`; adapters are one-way;
  reverse-write attempts error; AC6's "no dual authoritative event format remains" is an explicit
  post-migration assertion.
- **R3 — Runtime-generation definition drift.** Mitigation: fixed derivation (installed workflow
  source hash) pinned by fixtures (DD5); "wrong runtime generation" is a named hazard with its own
  code.
- **R4 — A1 emission gap for the real AC8 exercise.** A1b/A1c emission is `todo`, so a real
  `.workflow-events/` stream may not exist. Mitigation: the adapter is written against the **landed**
  20-field schema (a real current contract, imported, not re-declared); the real migration exercise is
  gated on the stream existing; absent stream = recorded-provenance no-op, never an invented shape.
- **R5 — `milestoneRootRel` drifting from the shell rule.** Mitigation: the existing
  `execute-milestone-worktree.test.mjs` pin already covers it; B2 adds a store-level resolution fixture
  asserting `milestoneRootRel("M254") === "milestones/M254"` and round-trips through the shell resolver.
- **R6 — Committed journal bloat.** Mitigation: receipts store hashes + bounded manifest refs only
  (DD8); journal is per-milestone and small (~8 events + receipts per run).
- **R7 — Unenumerated hazard class.** The eight-code AC6 matrix is exhaustive-by-fiat; an
  unclassified mismatch is a test failure, not a review comment.
- **R8 — Real-proof timing / lifecycle.** DoD 2/3 require a real milestone to write and re-validate
  across a process boundary; the full end-to-end execute-milestone wiring proof is B4's. Mitigation:
  B2 self-hosts on M254's own directory via the store CLI (two separate node processes: Build-phase
  write, Audit-phase re-read/validate) — mechanical, no dependency on B4 wiring; B2 lands
  human-steered with a declared external needs-human reason and reaches `done` only via the post-Land
  real proof + re-promote.
- **R9 — Base drift.** The parent plan was authored against older bases; live HEAD is `a31c9552`.
  Mitigation: re-verify every grounded fact against the live tree before dispatch (line anchors are
  advisory), and test the store's write path against the actual live `gate_resolve_milestone_root` /
  `milestoneRootRel`.

### Alternatives considered and rejected

- **Alt1 — Reimplement the milestone-root rule in TS (a pure-TS resolver hand-copied by B2).**
  Rejected: gate-script-lib.sh's own comment declares a "grep for '130' outside this function" a
  single-source violation — the exact bug class the resolver was created to kill. B2 reuses the
  existing test-pinned `milestoneRootRel`/`parseMilestoneNum` twin instead (DD1).
- **Alt2 — The store shells out to bash `gate_resolve_milestone_root` per resolution (`execSync`).**
  Rejected: the TS twin already exists precisely for this consumer (documented: "for the workflow DSL
  which cannot source a .sh"), and a subprocess per append is slow and fragile (bash availability,
  path resolution). The twin is pinned against the shell function by `execute-milestone-worktree.test.mjs`.
- **Alt3 — Extend A1's `.workflow-events/` stream into the durable journal.** Rejected: A1's stream is
  gitignored, per-run, best-effort, and fire-and-forget by design; receipts must survive restart and
  be post-Land-auditable, requiring committed durable state. Keeping A1 transient and B2 committed
  also keeps the one-way migration a real, testable boundary instead of a rename.
- **Alt4 — A single monolithic `stage-substrate.ts`** holding contracts + store + cache + adapters.
  Rejected: the task's `## Touches` globs define two files with distinct responsibilities
  (`*stage-receipt*`, `*workflow-journal*`); per-file isolation keeps each independently testable and
  landable, mirroring the repo's script-family granularity.
- **Alt5 — Bump A1's schema in place (modify `workflow-event-schema.mjs`).** Rejected: A1's v1 is
  pinned by A2's replay corpus and A5's metrics; the one-way adapter preserves A1's schema while
  making B's `StageEvent` the sole cross-workflow receipt contract (AC8).
- **Alt6 — B2 defines its own stage vocabulary (a second `VALID_STAGES` copy).** Rejected: a second
  stage-name authority recreates the dual-authority problem at the vocabulary level. Import the shared
  constants from `workflow-event-schema.mjs`; B2 owns only the field-set superset.
- **Alt7 — `stage-receipt.ts` imports `run-identity.ts` for the identity type.** Rejected: tight
  coupling breaks B1/B2 independent landability; `bindReceipt` accepts a `RunIdentity`-shaped
  structural input with a fixture stand-in in tests (DD12).
- **Alt8 — Own the cache methods in B3, not the store.** Rejected: the parent's split explicitly
  places `persistVerifyCache`/`loadValidatedVerifyCache` in the store module; the store owning the
  loop is the point (the caller's exit sites keep their return contract).
- **Alt9 — Copy authoritative content / full JSON payloads into receipts instead of hashes + bounded
  refs.** Rejected: duplicate-authority negative control + journal bloat;
  `validateManifestShape`'s `no-second-authority` precedent shows the repo treats copied requirement
  text as an error.
- **Alt10 — A server/native component or standalone JSON-schema files.** Rejected: the repo has no
  build step and prefers zero-dependency single-source TS modules with embedded validation (A1,
  build-evidence-manifest precedent); a server would add an availability failure mode the journal
  cannot tolerate.
- **Alt11 — Unversioned silent field drift on the envelope family.** Rejected: DD3 makes a schema
  change a new envelope version; the A1 forward-compat rule (unknown extra fields pass through)
  applies to observability, not to changing the receipt contract's semantics.
- **Alt12 — Reverse migration (journal → prepare-telemetry / proposal-ledger) to "round-trip" data.**
  Rejected: one-way only; reverse-write attempts error, keeping Prepare artifacts authoritative in
  their layer with no dual-write dependency.
