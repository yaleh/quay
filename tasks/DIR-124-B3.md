## Proposal

Split from DIR-124-B (M236) — mechanism 3, the **store-driven Verify cache + explicit resume computation**. This child owns `workflow-resume.ts` (both mirrors): the resume computation that consumes the stage journal + validated receipts (DIR-124-B2's `StageJournalStore`) and the RunIdentity shape (DIR-124-B1), and closes the Verify cache loop. ### Problem framing (grounded in current code)

**The Verify cache loop is OPEN at the only stage that has a cache today — and it is inert, because no caller persists or supplies it.** In both `execute-milestone.js` mirrors (`.claude/workflows/execute-milestone.js` and `plugin/workflows/execute-milestone.js`, `cmp`-verified byte-identical, 1257 lines each): `cacheFingerprints = $a.cacheFingerprints || {}` and `priorVerifyCache = $a.priorVerifyCache || {}` are read at L77-78; the per-check lookup `_cached(label)` at L121-128 reuses `priorVerifyCache[label].result` on fingerprint equality alone (`if (!prior || prior.fingerprint !== fp) return null` → `return prior.result`); `verifyCacheUpdates[r.check] = { fingerprint: fp, result: r }` is built at L208-211 and threaded through **16 return sites** (`grep -n verifyCacheUpdates`: L219, L237, L261, L422, L492, L537, L802, L905, L954, L973, L1139, L1144, L1195, L1201, L1252, L1257). A repo-wide `grep` for `verifyCacheUpdates`/`priorVerifyCache`/`cacheFingerprints` matches ONLY `execute-milestone.js` itself — OUTER-LOOP.md and the concurrent fan-in have ZERO references. So the loop is structurally open: a cached PASS is returned on fingerprint equality with no binding to base commit, candidate commit, workflow source, or runtime generation, and no caller ever persists the updates or supplies a prior cache in the live path.

The six mechanical checks that flow through this cache are `ceiling-check`, `gate-hash`, `line-budget`, `dogfood-evidence`, `domain-misfit` (informational), and `composite-preflight` (composite-only), each dispatched as a separate `agent()` with `MECH_SCHEMA {check, ok, detail, source}`. Because `_cached` compares only the caller-precomputed fingerprint, a cached PASS produced by a stale materialized workflow body — the documented CLAUDE.md M176 `Workflow({name})` stale-script-cache defect, where a name-dispatch materializes an OLD checked-in script even after the file was edited — is indistinguishable from a valid reuse. A wrong base commit, a moved candidate commit, a different workflow generation, or changed material inputs all look "cached-identical" as long as the fingerprint string matches. This violates crystallization safety invariant 3 ("no receipt is valid outside its bound base, candidate, inputs, workflow source, and runtime generation") at exactly the one stage that has a cache today.

**Resume is folklore, not a durable transition.** The execute side has no persisted stage history and no explicit earliest-invalid-stage computation; nothing records which installed workflow generation produced a stage result, so the M176 hazard cannot be rejected by any later stage either. The prepare side has a documented resume idiom (`$a.resumeFromAdjudicatedProposal`, `prepare-milestone.js` L199-206/L594-643), but execute-side dispatch has no equivalent — a `Workflow({name})` stale-materialization defect cannot be rejected because nothing records which checked-in workflow generation produced a stage's result.

**Useful crystal nuclei exist and are consumable.** DIR-124-A1a (M248, landed) supplies `workflow-event-schema.mjs` v1 (20 required fields incl. `runId`, `candidateCommit`, `baseCommit`, and `VALID_STAGES`, the canonical phase set) — transient observability only, gitignored `.workflow-events/<runId>.jsonl`, deliberately not a durable cross-workflow contract. `build-evidence-manifest.ts` (M238) exports `manifestRefForReceipt()` (L240) whose doc comment names DIR-124-B receipt binding, yet nothing consumes it. The preparation receipt `milestones/M<NN>/preparation.json` (M191/DIR-117) already hash-binds proposal/charter/Plan/sources — Prepare-only. Session identity is already mechanically available via `echo $CLAUDE_CODE_SESSION_ID` (5 uses in the live workflow: L516, L568, L682, L787, L1014). None of these close the Verify cache loop.

**The workflow DSL has no ESM `import` capability** (execute-milestone.js L28); every new production callsite must be a literal bash `node --experimental-strip-types <abs path>/<script>.ts <mode>` invocation dispatched via `agent()` (precedent: `milestone-preparation-check.ts`, `composite-audit.ts --combine-json`).

**Base drift is real.** The task body's phase-boundary anchors (Verify L66, Prepared L234, Build L389, Audit L673, Gate L769, Reconcile L866, Land L908) match the live tree ONLY through Build; Audit/Gate/Reconcile/Land have drifted to L719/L817/L919/L961 (~45-53 lines) since the task was authored. Line anchors are advisory; the Plan must re-verify them at edit time (they are B4's concern, but B3's fixtures must use the live phase set from `workflow-event-schema.mjs` `VALID_STAGES`).

### Chosen mechanism

A new `workflow-resume.ts` (both mirrors, byte-identical) that (a) CLOSES the Verify cache loop by orchestrating the store-driven cache methods and (b) computes the explicit resume plan. It is the child's ONE new script family, under the task's own `## Touches` globs (`*workflow-resume*`, plus test-side `*workflow-journal*` globs for the cache-behavior fixtures). It consumes the two sibling contracts per the declared B1→B2→B3 dependency order, via the established `.ts`-to-`.ts` ESM import pattern (`composite-args.ts` → `./candidate-contracts.ts` precedent) — it does NOT re-implement them:

1. **Store-driven Verify cache orchestration** — `loadValidatedVerifyCache(runIdentity)` and `persistVerifyCache(updates)` are implemented in DIR-124-B2's `workflow-journal.ts` `StageJournalStore`; `workflow-resume.ts` is the consumer that (i) drives `--load-validated-verify-cache` semantics so a check is reused ONLY when the fingerprint matches AND base/candidate/workflow-source/runtime-generation equality is validated by the store at load time, and (ii) drives `--persist-verify-cache` so `verifyCacheUpdates` land in the store. Reuse granularity is per-check: an unchanged run reuses all valid receipts; changing ONE check's material input reruns ONLY that check. The store owns the loop; the workflow's exit sites keep their return contract (parent DD5).

2. **`resumePlan({journal, receipts, candidateState})` → `{earliestInvalidStage, plan}`** — the pure decision function. It walks the journal's stage events in canonical order, validates each stage's green-boundary receipt against current candidate state (via B2's `validateReceipt`/`ReceiptValidationResult`), identifies the earliest stage whose receipt is missing or invalid (`earliestInvalidStage`), and emits a per-stage reason list: `reused-valid` for every stage before it whose receipt validates, `invalidated-by-<code>` for the invalid/missing stage and everything after. It increments the attempt identity to prior-max + 1, keyed on the run lineage (candidateState family + runId base) so interleaved runs on the same milestone journal are not confused. It NEVER reuses on prompt/label string equality alone (AC5). Its inputs (`journal`, `receipts`, `candidateState`) are passed as JSON; the decision is a pure function of validated state.

3. **CLI surface** — `--resume-plan <json>` is the workflow callsite, dispatched via the established `node --experimental-strip-types <abs path>/workflow-resume.ts <mode>` agent-dispatch pattern (milestone-preparation-check.ts precedent; the DSL has no import capability, execute-milestone.js L28). Embedded `--selftest` for fixture-pinned self-check.

The actual `execute-milestone.js` callsite wiring (replacing the `_cached` LOOKUP, persisting `verifyCacheUpdates`, invoking `--resume-plan` on journal-present dispatch) is DIR-124-B4's scope and is NOT built here; B3 owns the computation, the store-method semantics, and the fixtures proving reuse validity.

**WIRING-CLAIM (B3-CACHE-CLOSED):** the Verify cache LOOKUP (L121-128) is replaced by a `--load-validated-verify-cache` callsite and `verifyCacheUpdates` are persisted via `--persist-verify-cache` — the caller no longer owns the loop (AC1, AC2, AC3). The wiring lives in DIR-124-B4; this child owns the computation + fixtures proving reuse validity.

**WIRING-CLAIM (B3-RESUME-PLAN):** `workflow-resume.ts --resume-plan` is invoked on dispatch when a journal exists and returns `{earliestInvalidStage, plan}`; the workflow starts at the earliest invalid stage (AC4; B4 wires the invocation).

   ├─ fresh agents → allVerifyResults (L208) → verifyCacheUpdates (L208-211)

The B3 data surface: reads = journal stage events + `receipts/*.json` + candidate state (base/candidate commits, workflow source hash); writes = none directly (persist goes through B2's `persistVerifyCache`); decision output = `{earliestInvalidStage, plan}` to the caller.

### Key design decisions

**DD1 — The store owns the Verify cache loop; B3 is the orchestration, B4 is the wiring.** `loadValidatedVerifyCache`/`persistVerifyCache` live in B2's `workflow-journal.ts` (store module) — a single owner of persistence + validation. B3's `workflow-resume.ts` consumes them and carries the reuse-validity fixtures. B4 replaces the `_cached` callsite. This three-way split keeps each child independently landable/testable and gives the review phase a clean proof surface: B2 AC proves the store methods exist and bind; B3 AC proves their reuse semantics (per-check granularity, fail-safe persist, load-failure → fresh); B4 AC proves the callers invoke them.

**DD2 — Reuse is receipt-validated, never prompt/label-validated (parent DD6).** `resumePlan` revalidates every prior receipt against current candidate state through B2's `validateReceipt` before deciding reuse. A receipt whose prompt/label strings match but whose material inputs differ is NEVER reused — that is a RED/GREEN fixture, not a prose promise (AC5). The M176 stale-materialization hazard is defeated mechanically: a stale materialized workflow body is literally different file content, so `workflowSourceHash` recorded in the receipt differs from the installed source's current hash and `validateReceipt` fails closed with a distinct code. `resumePlan` needs no notion of "did the prompt look the same" — that predicate is structurally absent.

**DD3 — Attempt identity is journal-derived, never caller-forged.** `resumePlan` computes `attempt = prior max + 1` from the journal's recorded attempts for the SAME run lineage (candidateState family + runId base, so interleaved runs on a shared milestone journal are not confused); the plan feeds that attempt back to identity minting at Verify entry (B1/B4 wiring). On a cold journal (no prior), attempt = 1. This is the durable counterpart to B1's `runId` nonce: a resumed run is provably a new attempt, and the M176 stale-cache PASS cannot masquerade as the current attempt's result.

**DD4 — `invalidated-by-<code>` reuses B2's distinct hazard codes verbatim.** Wrong base, wrong candidate, modified Plan, stale named-workflow materialization, wrong runtime generation, missing artifact, moved candidate commit, tampered receipt, non-vacuous failure — each maps to its own code; `resumePlan` never invents a coarse "invalid" bucket that would hide which hazard class fired. An unclassified mismatch is a test failure, not a review comment. (The exact code set is B2's AC6-enumerated closed set; B3 inherits it.)

**DD5 — Fail-safe is the DEFAULT direction on every failure edge.** Cache miss, any binding mismatch, cache-load failure, and persist failure ALL resolve to fresh agent dispatch — never a reuse of possibly-stale state. A cache write failure leaves the store unchanged. A malformed `--resume-plan` JSON envelope fails closed with a distinct needs-human reason, never a guess.

**DD6 — Zero-dependency single-source module, embedded validation.** `workflow-resume.ts` imports only node built-ins + B1/B2 contracts via `.ts` imports; no new DSL import mechanism, no build step, no server. Matches the `workflow-event-schema.mjs`/`build-evidence-manifest.ts` precedent. All interaction from the workflow is the `node --experimental-strip-types <abs path>/workflow-resume.ts --resume-plan '<json>'` agent-dispatch invocation.

**DD7 — Canonical root, one path convention.** The journal/receipts root is resolved ONLY via `gate_resolve_milestone_root` (gate-script-lib.sh L152; rule: ≥130 → `milestones/M<NN>`, <130 → `experiments/quay-perpetual-stream/milestones/M<NN>`). A second hand-derived path is the bug class this milestone must not reintroduce.

**DD8 — Cross-child touches are coordinated, not overlapping.** B3's `*workflow-journal*` touch globs are the test/exercise side of B2's store cache methods (B2 owns the implementation; the task body states B2's store cache-load methods "are the contract B3 consumes"). B3 lands serial AFTER B2 (B1→B2→B3), so no concurrency collision; the Plan must pin exactly which workflow-journal test files B3 adds vs. B2. B3 does NOT touch `execute-milestone.js` (B4's Touches).

### Defaults and failure behavior

- **Cold dispatch (no journal):** normal full dispatch; `resumePlan` returns `{earliestInvalidStage: 'Verify', plan: []}` — the workflow falls through to its normal full dispatch path; no special-casing of "no prior" is required by callers. An empty journal is valid input, never a crash. First green boundaries seed the journal.
- **Cache miss** (no prior, no fingerprint, or ANY binding mismatch) → fresh agent dispatch, never a reuse.
- **Per-check granularity:** unchanged run reuses all valid receipts; ONE changed check reruns only that check.
- **`persistVerifyCache` failure:** store unchanged; Verify falls back to fresh agent dispatch — a cache write failure NEVER yields a stale reuse.
- **Cache load failure:** treated as "no valid receipt" → full fresh dispatch for that check; a store bug cannot cause silent stale reuse.
- **Tampered/mismatched receipt:** `validateReceipt` returns its distinct code; `resumePlan` maps it to `invalidated-by-<code>` and re-runs from that stage. An unclassified mismatch is a test failure, not a silent reuse.
- **Missing receipt (stage event present, no green receipt):** stage is incomplete → earliest-invalid; never assumed green.
- **Non-vacuous receipts:** a receipt with empty `materialInputHashes` is not reusable; `resumePlan` treats it as invalid.
- **Attempt increment:** prior max + 1, journal-derived, keyed on run lineage.
- **No prompt/label reuse:** a same-strings-different-inputs fixture is RED (AC5).
- **Malformed `--resume-plan` JSON envelope:** fail-closed error to the workflow (surfaced at Verify as a needs-human with a distinct reason), never a guess.

- **R3 — Base drift in the task's line anchors.** Audit/Gate/Reconcile/Land anchors drifted ~45-53 lines since authoring. ### Alternatives considered and rejected

- **Alt1 — Close the loop at the CALLER (OUTER-LOOP.md / fan-in persists `verifyCacheUpdates`).** Rejected: that is the current structural hole — grep confirms the callers have zero references; caller-owned persistence keeps cache semantics in folklore, couples every future caller to the cache contract, and still lacks base/candidate/workflow-source/runtime-generation binding. Store-driven + receipt-validated is closed by construction.
- **Alt2 — Trust the existing `_cached` fingerprint-equality predicate and only add persistence.** Rejected: fingerprint equality is precisely the AC5 hazard (prompt/label-equal, inputs-differ); persistence without validation would just make stale reuse durable.
- **Alt3 — Reuse the `Workflow` engine cache (`resumeFromRunId`) for resume.** Rejected: the M144/M176 defects are precisely the engine cache keying on (prompt, opts) only and being blind to external-state changes; resume must live at the domain layer where hashes and commits are visible.
- **Alt4 — Put `resumePlan` and the cache orchestration inside B2's `workflow-journal.ts` (one monolith).** Rejected: B2 is the store/receipt authority; resume is a distinct consumption-time computation with its own CLI and its own test surface (`*workflow-resume*` glob), and splitting it keeps B2's store footprint small and its atomic-write guarantees untangled from decision logic.
- **Alt5 — Resume by checkpoint/snapshot restore.** Rejected: snapshot restore re-establishes state without PROVING it; `resumePlan` revalidates receipts against current candidate state and records per-stage reasons, which a snapshot cannot explain.
- **Alt6 — Trust prompt/label identity for cache reuse (or infer the restart stage from task/prompt/label text).** Rejected: exactly the M176 stale-materialization hazard; every reuse must be receipt-validated against current workflow source hash and material input hashes (AC5).
- **Alt7 — B3 implements its own copy of the cache methods (a local stub store).** Rejected: would create a second authoritative cache implementation and a dual-write hazard; the declared B1→B2→B3 dependency order makes B2 the sole implementer and B3 the consumer (DD1). A stub would test a fiction.
- **Alt8 — A native/server component for the cache/resume service.** Rejected: the repo has no build step and prefers zero-dependency single-source TS modules; a server adds an availability failure mode the journal cannot tolerate.
- **Alt9 — Resume by re-running ALL prior stages on any journal presence.** Rejected: loses the per-check/per-stage reuse granularity that is the whole point of AC2/AC5; `resumePlan` reuses validated receipts and reruns only from the earliest invalid stage.
- **Alt10 — Disable the Verify cache entirely (always fresh dispatch).** Rejected: that abandons the per-check incremental value (AC2) without fixing the hazard; the task is safe reuse, not no reuse.

## Acceptance Criteria

- [ ] `loadValidatedVerifyCache(runIdentity)` validates the exact check input, base/candidate state,
  workflow source, and runtime generation BEFORE reuse; a cache miss on ANY binding mismatch → fresh
  agent dispatch, never a reuse. The wired `--load-validated-verify-cache` and `--persist-verify-cache`
  callsite semantics are proven against the REAL store: `verifyCacheUpdates` are persisted only via the
  validated path, never a stale reuse.
- [ ] A second unchanged run reuses valid Verify receipts from the store; changing only one check's
  material input reruns only that check.
- [ ] `persistVerifyCache` failure leaves the store unchanged and Verify falls back to fresh agent
  dispatch — a cache write failure never yields a stale reuse (fail-safe direction).
- [ ] `workflow-resume.ts --resume-plan` returns `{earliestInvalidStage, plan}` from VALIDATED
  receipts, increments attempt identity to prior max + 1, and records a per-stage reason
  (`reused-valid` | `invalidated-by-<code>`); the start-at-earliest-invalid dispatch behavior is
  verified against a resumed-journal fixture.
- [ ] A fixture whose receipt prompt/label strings match but whose inputs differ is NEVER silently
  reused (AC5, RED/GREEN).
- [ ] A cache load failure is treated as "no valid receipt" → full fresh dispatch for that check; a
  store bug cannot cause silent stale reuse.
- [ ] Both mirrors byte-identical (`diff` exit 0); tests RED/GREEN per `scripts/test.sh`.
- [ ] B3's fixtures import and exercise the REAL landed B2 `workflow-journal.ts`/`stage-receipt.ts`

- [ ] The `execute-milestone.js` callsite wiring — replacing the `_cached` LOOKUP, persisting

  computation the wired callsite consumes.
