## Proposal

Split from DIR-124-B (M236) — mechanism 3, the **store-driven Verify cache + explicit resume
computation**. This child owns `workflow-resume.ts` (both mirrors): the resume computation that
consumes the stage journal + validated receipts and closes the Verify cache loop. Per the parent's
DD5/DD6 + CLAIM-B4/B5 (→ AC5, AC7).

### Chosen mechanism

The Verify cache loop today is OPEN: `cacheFingerprints = $a.cacheFingerprints` and
`priorVerifyCache = $a.priorVerifyCache` (execute-milestone.js L77-78); the per-check lookup `_cached(label)`
(L121-128) reuses `priorVerifyCache[label].result` on fingerprint equality alone; `verifyCacheUpdates`
is built (L208-211) and returned but the callers (OUTER-LOOP.md + concurrent fan-in) have ZERO
`verifyCacheUpdates`/`priorVerifyCache` references. A cached PASS from a stale materialized workflow
body (the M176 `Workflow({name})` stale-script-cache defect) or a wrong base is indistinguishable from
a valid reuse.

`workflow-resume.ts` implements the store-driven cache + resume computation:

1. **`persistVerifyCache(updates)` / `loadValidatedVerifyCache(runIdentity)`** — implemented in the
   journal store (DIR-124-B2) and consumed here. Cache lookup validates the exact check input,
   base/candidate state, workflow source, and runtime generation BEFORE reuse (Requested-action items
   3-4, AC5). Reuse requires fingerprint match AND base/candidate/workflow-source/runtime-generation
   equality, validated by the store at load time. An unchanged run reuses all valid receipts; changing
   ONE check's material input reruns ONLY that check. The store owns the loop; the workflow's exit
   sites keep their return contract (DD5).
2. **`resumePlan({journal, receipts, candidateState})` → `{earliestInvalidStage, plan}`** — determines
   the earliest invalid/incomplete stage from VALIDATED receipts, reuses only validated prior receipts,
   increments the attempt identity (new attempt = prior max + 1), and records a per-stage reason for
   reuse or invalidation (`reused-valid` | `invalidated-by-<code>`). A receipt whose prompt/label
   strings match but whose inputs differ is NEVER silently reused (AC7, DD6).
3. **CLI surface:** `--resume-plan <json>` is the workflow callsite (via the established
   `node --experimental-strip-types <abs path>/workflow-resume.ts <mode>` agent-dispatch pattern).
4. **Failure behavior:** cache miss (no prior, no fingerprint, or ANY binding mismatch) → fresh agent
   dispatch, never a reuse; a failed `--persist-verify-cache` leaves the store unchanged and Verify
   falls back to fresh agent dispatch (fail-safe direction — a cache write failure NEVER yields a stale
   reuse); a cache load failure is treated as "no valid receipt" → full fresh dispatch for that check.

**WIRING-CLAIM (B3-CACHE-CLOSED):** the Verify cache LOOKUP (L121-128) is replaced by a
`--load-validated-verify-cache` callsite and `verifyCacheUpdates` are persisted via
`--persist-verify-cache` — the caller no longer owns the loop (AC5, CLAIM-B4). The wiring lives in
DIR-124-B4; this child owns the computation + fixtures proving reuse validity.

**WIRING-CLAIM (B3-RESUME-PLAN):** `workflow-resume.ts --resume-plan` is invoked on dispatch when a
journal exists and returns `{earliestInvalidStage, plan}`; the workflow starts at the earliest invalid
stage (AC7, CLAIM-B5).

## Acceptance Criteria

- [ ] `loadValidatedVerifyCache(runIdentity)` validates the exact check input, base/candidate state,
  workflow source, and runtime generation BEFORE reuse; a cache miss on ANY binding mismatch → fresh
  agent dispatch, never a reuse.
- [ ] A second unchanged run reuses valid Verify receipts from the store; changing only one check's
  material input reruns only that check (AC5).
- [ ] `persistVerifyCache` failure leaves the store unchanged and Verify falls back to fresh agent
  dispatch — a cache write failure never yields a stale reuse (fail-safe direction).
- [ ] `resumePlan` returns `{earliestInvalidStage, plan}` from VALIDATED receipts, increments attempt
  identity to prior max + 1, and records a per-stage reason (`reused-valid` | `invalidated-by-<code>`).
- [ ] A fixture whose receipt prompt/label strings match but whose inputs differ is NEVER silently
  reused (AC7, RED/GREEN).
- [ ] A cache load failure is treated as "no valid receipt" → full fresh dispatch for that check; a
  store bug cannot cause silent stale reuse.
- [ ] Both mirrors byte-identical (`diff` exit 0); tests RED/GREEN per `scripts/test.sh`.
