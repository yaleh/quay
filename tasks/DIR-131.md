## Proposal

**Context**：人 2026-09-07 就 goal 机制与 task 机制的分工做出边界裁定。本 directive 把该裁定记成
task-canonical 正本，并**给它造一个产物**——因为这条边界目前只活在 `plugin/scripts/goal-driver.ts`
的头注释散文里，「守」与「不守」在记录上无法区分（硬规则 9）。

**裁定逐字**：

> 创建 task 后到 task 落地的过程应当由 task 相关机制（如 promotion-driver 和 worker-driver）驱动。
> goal 机制应当负责 task 以外的 goal 相关生命周期。

**做法**：① 把边界的**正向半边**写成正本（既有记录只说了 goal 机制不许做什么，没说它负责什么）；
② 新增一个按位置判定的静态检查，机械断言 `goal-driver.ts` 无 task 写路径，并接进 `scripts/test.sh`
的静态层；③ 该检查必须带负控制（插入真实写调用 ⇒ 报红；同内容写成注释 ⇒ 仍绿），否则它是一个
结构上不可能报红的检查（硬规则 3b + 硬规则 4）。

N/A —— 单叶执行任务即可闭合，无需分阶段计划。实现落点为一个新的 `plugin/scripts/*` 检查脚本 +

## Finding

**现状已合规（2026-09-07 实测，按位置查而非按关键词）**：`goal-driver.ts` 对 `tasks/*.md`
**只有读路径**——`:233 readTaskFacts`（读 `tasks/*.md` → `{id, status, goalAc}`）、`:642` 算缺口、
以及 `stalled` 第四态所依赖的 `ready-pool-check` 只读判定面。**无任何 task 状态写路径**：
无 `task_write` / `lifecycle_promote` / `lifecycle_retreat` / 直接写 `tasks/*.md` 的调用点。
头注释（`:14-24`）已载人 2026-09-06 裁定 3+5 的**禁止半边**：「⛔ 不直接改 task 状态（撞
lifecycle/promotion-driver 的 expectedStatus CAS）」「⛔ 不机械写 `tasks/*.md`（全仓四个 driver
零先例）」。

**本裁定补的是正向半边**——goal 机制**负责**的是 task 以外的 goal 生命周期：跑 AC criterion、
写 evidence、I2 推导 flip（AC/GOAL active→achieved）、I3 陈旧三态、I4 分歧、缺口读数、
以及缺口非空时经 ABI（`quay-file-task`）立案。**立案是 goal 侧的最后一个动作**；此后从 `todo`
到 `done` 的全过程（晋升门、派发、worktree、fan-in、落地）归 `promotion-driver` / `worker-driver`。

**本轮实际发生的归因错误（写进正本作为反例）**：管理者在 2026-09-07 的汇报里把
「fan-in 落地速率低（当日仅 +2 achieved，而环立了 3 条案）」表述为「goal 机制持续驱动 GOAL 落地的
限制」。**按本裁定这是错误归因**——落地速率是 task 机制的指标，不是 goal 机制的缺陷。同族的三个
不得混淆项：**fan-in 落地率 / ready 池积压 / `needs-human` 恢复**，全部归 task 机制侧。特别是
`needs-human`：其恢复**按设计就是人**（`plugin/scripts/worker-driver.ts:881` 逐字「人把
needs-human 翻回 ready 后，内存集合据此清除、下一轮重新可派」；退回通道见 DIR-102
「Allow lifecycle_retreat from needs-human to todo」）——goal 侧对它唯一该做的是**如实报
`stalled` 并停止为它空派 gap-filing agent**（落点 `tasks/gap-goal-gap-needs-human-invisible-burns-spawn-slot`），
而不是去替 task 机制恢复它。

**为什么需要产物**：上述边界至今只有散文载体。一个未来的实现者在 `goal-driver.ts` 里加一行
`task_write` 不会触发任何红——与「没有违规」在记录上完全同形。
