## Finding

- `plugin/scripts/full-suite-runner.ts:993` `DEFAULT_SYSTEMD_RUN_LIMITS.memoryMax = "16G"` 是人 2026-09-24 在 128 核大宿主上实测调的字面量，不是通用默认——在 2-8GB 内存的小宿主上，这个值会超过宿主总内存，cgroup 层面形同不设限，真正的 OOM 保护会退化成内核直接杀进程而非受控的 cgroup oom_kill。
- `gap-driver-anchor-runs-without-host-derived-memory-envelope`（done）已经证明了一个可复用的"宿主推导包络"公式（`floor(os.totalmem()×0.25)`，页对齐，真 cgroup 负控制验证过 oom_kill 行为），但该公式读 `os.totalmem()`（host `/proc/meminfo`），**不读** cgroup `memory.max`——如果 quay/ClaudeCodeUI 自己被装在一个内存受限容器里，这个公式会算出远大于真实可用量的包络，同样的缺口。
- CPU 侧：`resource-gate.sh`/`process-budget.sh` 的 `nproc`/`nproc --all` 是 affinity/host-wide 读数，专为"host-wide loadavg 该跟多大核数比"设计（`gap-systemd-run-cpuquota-scope-distorts-nproc` 的既有注释已写明），不读 `/sys/fs/cgroup/cpu.max` 的 CFS bandwidth quota。`runner-concurrency.ts` 的并发推导用 `os.availableParallelism()`，按 Node 文档可能已经对容器 CPU quota 敏感，但本仓库目前没有任何测试/记录验证过这一点——不能当已确认的结论用。
- 跨项目协调现状（2026-10-09 与 ClaudeCodeUI 两次协同对话实测确认）：ClaudeCodeUI 跑的就是 quay 自己的 `worker-driver.js`/`resource-gate.sh`（同一份脚本同一套判据），不是独立实现；但 `suiteLockBase()` 锚在各自仓库自己的 `.git`，两边的 single-flight 槛互不相通，`resource-gate.sh` 本身只是一次性只读快照，不是预留/互斥机制——即使两边用同一套判据，也不能防止"几乎同时双触发"的竞态。ClaudeCodeUI 独立确认了 CPU/memory cgroup 探测这个缺口的存在，并提出了自己的实现方向（`effective-capacity.sh`），双方已对齐输出形状（key=value+--json，env override 测试缝风格），各自独立实现、不互相阻塞。
