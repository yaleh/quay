## Proposal

Two methodology gaps currently exist in the Skill files that are documented
in iteration reports but not yet reflected in the canonical Skill definitions:

**Gap 1 — Three-tier manda reliability not annotated**: The manda reliability
annotation in both `quay:author` and `quay:execute` SKILL.md files currently
records only "1 successful call (PONG trial)" from iteration 4 (trivial tier,
90s timeout). Iterations 5 and 6 established medium and complex tiers
respectively:
- Medium (single file read + structured JSON): SUCCESS 1/1 at 150s (iteration 5)
- Complex (multi-file read + adversarial analysis + structured verdict): SUCCESS
  1/1 at 150s (iteration 6)

The annotation should reflect the full three-tier reliability envelope now
confirmed, as a genuine documentation accuracy improvement. If the Skill files
are read by a future executor, they will understate the reliability track
record.

**Gap 2 — Timing-recording methodology gap**: The effectiveness V_meta factor
requires a scope-matched task (single source file, logic change, no network I/O)
with recorded wall-clock timing for a native Skill-driven execution. Iteration 6
confirmed the baseline exists (QN-006: author ~51s, execute ~2m59s in
timing/iteration-0.log). But iteration reports for QC-* tasks do not record
wall-clock timing for Skill-driven execution phases — a gap the Skill files
should note so future executors know to record timing when a scope-matched task
arises.

**Approach**: Update both Skill files' iteration-4 manda annotation to extend
through iterations 5 and 6 (three-tier confirmed). Add a brief note in the
Skill files about timing recording for effectiveness measurement. Both changes
are documentation-only — no source file modification, no test file modification.
