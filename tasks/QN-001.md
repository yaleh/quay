## Proposal

`quay-native`'s data-write path (`store.write()`) already accepts a full
patch (`title, status, labels, parent, children, extra, body`) and both the
MCP `task_write` tool and the CLI's `task edit` subcommand call the same
underlying function (design §6 CLI/MCP symmetry, verified directly in
iteration 1's `test/abi-symmetry.mjs` for the fields both surfaces *do*
expose). However, a concrete asymmetry exists **today**, found by reading
the actual argv-parsing code (not assumed):

- MCP's `task_write` inputSchema accepts `body` and `children` as
  first-class patch fields (`src/mcp-server.js`).
- The CLI's `task edit` subcommand (`bin/quay-native.js`) only wires
  `--title`, `--status`, `--labels`, `--parent`, and `--append-notes` into
  the patch object — **`--body` and `--children` are silently unavailable**
  on `edit` (only `create` accepts `--body`, and nothing accepts
  `--children` or `--extra` at all, on either subcommand path for `edit`).

This is exactly the kind of "symmetry of interface must not become
asymmetry of data integrity" gap design §6 warns about — here it's a
capability asymmetry rather than a corruption risk, but it means a human/CLI
operator cannot do everything an MCP client (e.g. a future `quay:author`/
`quay:execute` Skill acting through the ABI, or the `quay` Core CLI acting as
an MCP client) can do. Since design §6 requires the CLI to be "the golden
test harness" for the whole ABI, this gap has to close: today the CLI simply
cannot exercise full `task_write` semantics.

**Approach:** extend `task edit`'s flag parsing to accept `--body <text>`,
`--children <id1,id2,...>`, and `--extra <json>` (mirroring how `--labels`
already parses a comma list), passed straight through to the existing
`store.write()` patch object — no new store logic needed, since
`store.write()` already accepts all these fields. This is a CLI-surface-only
change (no `store.js` change), keeping the fix scoped to exactly the gap
found.

## Plan

- Phase 1: add `--body`, `--children`, `--extra` flag parsing to the `edit`
  subcommand in `bin/quay-native.js`, following the existing pattern (each
  flag maps to one `patch` key; `--children` comma-split like `--labels`;
  `--extra` parsed as a JSON string, matching how frontmatter's `extra` is
  already an object).
- Phase 2: write a CLI-vs-MCP symmetry test extending
  `test/abi-symmetry.mjs`'s `task_write` case to also patch `body` and
  `children` via CLI `--body`/`--children` and independently via MCP
  `task_write`, then diff the resulting `store.get()` view-models field by
  field (not just key sets — actual values), for both surfaces.
- Phase 3: re-run the full `test/abi-symmetry.mjs` suite plus the existing
  `test/lock.test.mjs` concurrency suite to confirm no regression from the
  new flags (the underlying locked `write()` path is unchanged).
