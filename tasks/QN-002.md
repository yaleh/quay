## Proposal

Protocol §4.1's bootstrap ladder names stage "2..k" as the point where
`quay-native` starts driving the build of the **GitHub Provider** — the
project's sole V_meta reusability transfer target (protocol resolved
decision 4; README §5's "held-out declaration"; roadmap proposal §14 v1:
"do not declare the ABI stable until native + GitHub both run"). Two
consecutive iterations (1: authoring self-hosts; 2: execution self-hosts,
first σ>0) have produced real, evidenced native-side progress with no
outstanding blocking defect after QN-007's fix — this is the judgment call
this iteration makes to open stage 2 on the **authoring side only** (per
this iteration's explicit scope: author, do not execute/implement).

**Why a GitHub Provider, and why now:** the proposal's central risk (§16)
is "contract designed in the abstract" — mitigated by "extract, don't
design: bootstrap the ABI from the native reference, then validate against
GitHub before generalizing." Native's ABI (`task_list`/`task_get`/
`task_write`/`task_check`/`provider://manifest`) is now reasonably
exercised (all four MCP tools implemented, CLI/MCP value-level symmetry
proven for `body`/`children`/`extra`, `\Z` gate bug fixed, `\extra`
MCP-drop bug fixed) — a plausible point to start proving the contract
against a real, heterogeneous second backend, per proposal §14's explicit
sequencing ("Second real Provider: GitHub issues... do not write a third
Provider before native + GitHub both run").

**Why v1 must be minimal (walking-skeleton discipline, G5, applies to the
GitHub Provider itself, not just to native):** proposal §16 and this
protocol's G5 warn against gold-plating; the natural failure mode here is
designing a fully-featured GitHub Provider (labels sync, milestones,
projects-v2 boards, webhooks) before proving the ABI at all. This task's
scope is therefore **read-only, minimal**: prove `data.read` +
`manifest` map onto GitHub Issues correctly; defer `data.write`/`gate` to a
follow-up task once the read path is proven (mirroring how native itself
staged `data.read` before `data.write`/`gate`, per iteration 0's v0 loop).

**What this task is NOT:** it is not the implementation. Per this
iteration's explicit guardrails, no `gh` command, no real GitHub API call,
and no code for the GitHub Provider itself may be written this iteration.
This task's Plan is deliberately a **design-only deliverable** — phases,
mapping rules, and an AC/DoD that a *future* iteration's `quay:execute`
dispatch can pick up and implement for real, once `gh` auth + the
stage-2 preconditions (README §9, ITERATION-PROMPTS.md "§Stage 2+") are
confirmed satisfied by whichever iteration actually executes this task.

## Plan

**Phase 0 — precondition gate (execution-time only, not authoring-time).**
Before any future iteration executes this task: confirm `gh auth status`
shows an authenticated user with `repo`+`workflow` scopes (protocol §10.1;
README §9), and confirm this repository is published to GitHub with real
issues to target. This phase is listed here for the *executing* iteration's
benefit; it performs no action itself during authoring.

**Phase 1 — provider bundle skeleton.** Create
`packages/quay-github/` as a sibling package to `quay-native`
(glossary: "Provider" = one bundle registering into Provider registry +
Claude Code skills + MCP). Minimal layout mirroring `quay-native`'s own
(design §1's "native as conformance reference" — the GitHub Provider should
structurally resemble the reference, not invent a new shape):
```
packages/quay-github/
├─ package.json
├─ provider.yml        # capabilities: data.read + manifest ONLY for v1
├─ src/
│  ├─ mcp-server.js     # task_list / task_get + provider://manifest only
│  └─ github-client.js  # thin wrapper over `gh api` or octokit-equivalent
└─ bin/
   └─ quay-github.js     # `mcp` subcommand only for v1 (no `task` CLI
                          # subcommands required yet — GitHub is the
                          # heterogeneous backend; a raw local CLI mirroring
                          # quay-native's convenience commands is not
                          # required by the ABI, only the MCP surface is)
```

**Phase 2 — view-model mapping rules (the actual contract-proving work).**
Define, in the Provider's own design note
(`packages/quay-github/DESIGN.md`), the mapping from a GitHub Issue to the
canonical view-model (design §7.1 / glossary's task schema):
```
id       ← "gh-issues/<owner>/<repo>#<number>"   (or a shorter scheme TBD by
                                                    the executing iteration —
                                                    named as an open question,
                                                    not resolved here, since
                                                    resolving it IS part of
                                                    the execution work)
title    ← issue.title
body     ← issue.body                            (verbatim; no reformatting
                                                    imposed by the Provider —
                                                    proposal §6.3's "no
                                                    backend branch in Core"
                                                    principle mirrored here:
                                                    no Provider-side content
                                                    rewriting either)
status   ← derived from issue.state + labels     (open, no `status:*` label
                                                    → todo; a `status:ready`
                                                    label → ready; issue
                                                    closed → done; a
                                                    `needs-human` label →
                                                    needs-human) — this is
                                                    the LCD problem the
                                                    proposal (§2.2, §16)
                                                    warns about in miniature;
                                                    resolving the exact label
                                                    convention is execution-
                                                    phase work, named here
                                                    only as the shape of the
                                                    mapping, not the final
                                                    answer.
lane     ← a label convention (`lane:authoring` / `lane:execution`), TBD
labels   ← issue.labels minus the reserved status/lane labels above
parent   ← a `Sub-issues`/task-list reference if GitHub's native sub-issue
           feature is available, else unset (v1 may leave this unresolved —
           explicitly out of scope for the MINIMAL read-only capability;
           name it as a known gap, not a silent omission)
children ← same caveat as parent
extra    ← issue.number, issue.html_url, issue.user.login — anything
           GitHub-specific that doesn't fit the canonical fields (design
           §7.1's stated purpose for `extra`)
```
This phase's deliverable is the mapping rules document, not code — writing
the actual `github-client.js`/`mcp-server.js` logic is Phase 3, deferred to
execution.

**Phase 3 — implement `data.read` + `manifest` only (deferred to
execution).** `task_list`/`task_get` backed by `gh api` (or an
equivalent library) reading real issues from this repository; static
`provider.yml` declaring `capabilities: { data.read: true, manifest: true }`
ONLY — `data.write`/`gate`/`skill` explicitly `false`/absent for v1 (a
read-only Provider is valid per design §6.2's capability table: "no write →
grey out edit... a read-only Provider is valid"). This phase performs no
work during authoring; it is the target for whichever iteration executes
this task.

**Phase 4 — prove the minimal capability end-to-end (deferred to
execution).** `quay task list` (the Core CLI, provider-agnostic) against
the GitHub Provider returns real issues from this repository, with the
Core rendering them with zero `if provider === 'github'` branches (proposal
§6.3's invariant) — this is the concrete "at minimum a read-only capability
works end-to-end" bar this task's AC sets.
