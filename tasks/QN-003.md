## Proposal

`quay:author` (`packages/quay-native/skills/author/SKILL.md`) was written in
iteration 0 as an honest v0 port of epicd's `authoring-convergence` pattern,
but its own "Gaps" section names a real, load-bearing shortfall: **no Layer-1
operation Skills (`write-proposal`, `review-proposal`, `write-plan`,
`review-plan`) exist as separate dispatchable Skill files.** Instead, the
orchestration Skill inlines all four steps in one context — which violates
design §5's explicit contract ("Orchestration explicitly dispatches operation
Skills as subagents... fresh context per operation is required (isolation +
review independence)").

Iteration 1 exercised `quay:author` against QN-001 and QN-005 for real
(experiments/quay-native-bootstrap/provenance.md, experiments/quay-native-bootstrap/iterations/iteration-1.md) and hit this
gap concretely, not hypothetically: **this session's tool-calling environment
has no subagent-dispatch primitive** (no `Task`/`Agent`-equivalent tool was
available — confirmed by an explicit `ToolSearch` check during iteration 1,
not assumed). So "review-proposal" and "review-plan" could only be performed
as a same-session re-read pass (checking heading presence + AC-checkbox
presence + Plan-phase/AC alignment), not a genuinely independent, fresh-
context review. This is the same self-verification gap iteration 0's
`adjudicate` audit already flagged for the execution side (G3) — it now
demonstrably also applies to the authoring side's internal review steps, not
just the external audit.

**Approach:** do not try to solve "no subagent tool exists in this
environment" (out of this task's control — that is an environment/harness
capability, not something quay-native's own code can create). Instead, make
the gap **honest and structural** in the Skill itself, per design §5's own
escape hatch: *"A Skill declares the environment capability it needs and
defines a degraded fallback for environments without it."* Concretely:

1. Split `write-proposal` / `review-proposal` / `write-plan` / `review-plan`
   out of `quay:author`'s inlined "Method" section into their own
   documented steps with **explicit dispatch-capability requirements** and a
   **named degraded-mode fallback** (same-session sequential execution with
   an explicit self-review checklist), so that an environment *with* a
   subagent-dispatch primitive can wire real isolation later without
   `quay:author`'s contract changing, and an environment *without* one (like
   this one, today) still gets a documented, honest, checklist-based
   approximation instead of a silent inline shortcut.
2. Keep `quay:author` itself as the one Layer-2 orchestration Skill (do
   **not** fork it into 5 separate always-standalone files this iteration —
   that would be premature given no dispatch primitive exists yet to
   actually invoke them independently; G5 applies here too: don't build
   subagent-dispatch machinery this experiment cannot yet exercise for
   real). This resolves design §8 open decision 5 ("is `decompose` its own
   Skill or folded into `review-plan`? recommended: folded") in the same
   spirit — keep Layer-1 *logically* distinct (named steps, own review
   checklist) without *physically* forking into files whose isolation
   contract can't be honored in this environment yet.

**Non-goal:** implementing an actual subagent-spawning mechanism — that is
an environment/harness capability, out of scope for a quay-native task.

## Plan

- Phase 1: rewrite `quay:author`'s "Method" section into four explicitly
  named steps (`write-proposal`, `review-proposal`, `write-plan`,
  `review-plan`), each with: (a) its dispatch-capable-environment target
  behavior (own subagent, fresh context), (b) its degraded-mode fallback
  (same-session, with a concrete self-review checklist: heading presence +
  minimum content + AC-checkbox presence + Plan-phase/AC alignment — the
  exact checks iteration 1 actually performed for QN-001/QN-005), and (c) an
  explicit statement of which mode this environment is currently in and why
  (no dispatch tool found).
- Phase 2: update the "Honesty note" and "Gaps" sections to reflect
  iteration 1's actual dispatch evidence (σ movement, which tasks were
  authored, the concrete environment-capability finding) rather than
  iteration 0's forward-looking placeholder language.
- Phase 3: no `store.js`/CLI/MCP change — this is a Skill-definition-only
  task (SKILL.md content), verified by re-reading the file and confirming
  the four steps + degraded-mode fallback are present and match what
  iteration 1's real dispatches actually did.
