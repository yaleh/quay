## Proposal

`quay-native task check`'s current gates (design §3, `store.js#check`) are
deliberately thin (iteration 0's own honest admission, iteration-0.md §7):

- **`author->ready`** is **presence-only** — it checks that `## Proposal`,
  `## Plan`, `## AC`, `## DoD` headings exist in the body, with **zero**
  check of content quality (a heading followed by a single word would pass).
- **`ready->done`** is a **checkbox-count heuristic** — it checks that all
  `- [ ]` boxes under `## AC` are ticked, with **zero** verification that a
  ticked box corresponds to an actually-satisfied criterion (a task could
  check all its own boxes falsely and the gate would not catch it).

This gap matters concretely for this very experiment: `quay:author`
(iteration 1's subject) is *exactly* the kind of self-certifying actor the
gate is supposed to guard against — it authors artifacts and then asks its
own gate whether the artifacts are good enough. A gate that only checks
"is there a heading" cannot catch a shallow Proposal/Plan, and a gate that
only counts checkboxes cannot catch a false completion claim. Per the design
(§3: "Convergence is therefore a *fact* asserted by `quay-native task check`,
not a feeling") and G3 (the gate is "both contestant and judge"), the gate
needs to do more real work before self-hosting proceeds much further.

**Approach (v1, still deliberately restrained per G5 — do not gold-plate):**

1. **`author->ready` gate — minimum-content check, not just presence.**
   Require each of the four sections to contain a *minimum* amount of
   substantive content (a non-trivial line count / non-placeholder text),
   not merely the heading. This catches the "heading with one word" failure
   mode without attempting deep semantic understanding (out of scope for a
   mechanical gate — semantic quality is what independent review/audit is
   for, not the gate).
2. **`author->ready` gate — AC must be machine-checkable.** Require the `##
   AC` section to contain at least one checkbox line (`- [ ]`). A Proposal/
   Plan/DoD with prose-only "AC" that never becomes checkboxes cannot
   mechanically gate `ready->done` later — catch this at the `todo->ready`
   boundary instead of discovering it's uncheckable at `ready->done`.
3. **`ready->done` gate — do not change the checkbox-count heuristic's
   mechanism in this task** (that would require the gate to independently
   re-derive AC truth, which is exactly what the out-of-band `adjudicate`
   audit is for, per G3/G4 — the mechanical gate and the independent audit
   are deliberately two different, non-substitutable checks). Scope for
   *this* task is the `author->ready` side only, where a cheap, real
   improvement is available without duplicating audit's job.

**Non-goals for this task:** implementing NLP-based semantic quality scoring,
building an automated `adjudicate` dispatcher (tracked separately — this
experiment's G3 audit is a manual/session-level process for now), or
changing the checkbox-count mechanism of the `ready->done` gate.

## Plan

- Phase 1: add a `MIN_SECTION_CHARS` threshold (small, e.g. 40 non-whitespace
  chars) to `artifactSections()` in `store.js`; a section only counts as
  "present" if its heading exists **and** its body content (up to the next
  `##` heading) meets the threshold.
- Phase 2: extend the `author->ready` gate in `check()` to also require the
  `## AC` section to contain at least one `- [ ]`/`- [x]` checkbox line —
  add this as a distinct failure reason (`"AC section has no checkboxes"`)
  so the gate's `reason` field stays specific and actionable, matching the
  existing pattern of naming exactly which artifact is missing.
- Phase 3: write unit tests (no MCP server needed — `store.js`'s `check()` is
  directly importable) covering: (a) a heading-only-no-content task correctly
  fails the gate with the new reason, (b) a task with substantive content in
  all four sections but no AC checkboxes correctly fails with the new
  checkbox reason, (c) a task meeting both new bars passes, (d) the existing
  QN-006 fixture-equivalent (already-done task) still gates correctly
  post-change — no regression on the `ready->done` path, which is untouched.
