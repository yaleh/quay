## Proposal

`quay-native`'s CLI (`bin/quay-native.js`) and MCP server (`src/mcp-server.js`)
both call into the same `store.js` core (design §6 CLI/MCP symmetry), but
`store.write()` currently has no concurrency guard: two writers racing on the
same task file (e.g. a human editing via CLI while an agent session calls
`task_write` over MCP) can interleave and corrupt the YAML frontmatter block.
Add a simple file lock so "symmetry of interface" (CLI vs MCP) does not
silently become "asymmetry of data integrity" (design §6, explicit warning).

Approach: use an advisory lockfile per task id (`<id>.md.lock`), acquired
before read-modify-write in `store.write()` and `store.appendNote()`,
released after. This is the simplest correct mechanism for a single-machine,
single-process-family file store — no external lock service, no database.

## Plan

- Phase 1: add `acquireLock(id)` / `releaseLock(id)` helpers to `store.js`
  using `fs.openSync(..., 'wx')` (exclusive create) with a short retry/backoff
  loop and a stale-lock timeout (drop locks older than 5s — crash recovery).
- Phase 2: wrap `write()` and `appendNote()`'s read-modify-write sections with
  acquire/release (try/finally to guarantee release on error).
- Phase 3: add a concurrency test — two near-simultaneous `write()` calls on
  the same id from two separate Node processes (spawned via `child_process`)
  must not corrupt the resulting frontmatter (both patches land, in some
  order, and the file remains parseable).

## AC

- [x] `store.write()` and `store.appendNote()` acquire an exclusive lock
      before reading current file state and release it after writing.
- [x] Two concurrent writers (separate processes) racing on the same task id
      never corrupt the file: after both complete, `store.get(id)` parses
      successfully and reflects one of the two patches (last-writer-wins is
      acceptable; corruption is not).
- [x] A stale lock (holder crashed) does not permanently deadlock future
      writers — the stale-lock timeout reclaims it.
- [x] `quay-native task edit` (CLI) and `task_write` (MCP) both go through the
      same locked path (no separate unlocked write function exists).

## DoD

- [x] AC above all checked.
- [x] Concurrency test in Phase 3 exists and passes, run for real (not just

- [x] No regression: existing single-writer CLI smoke tests (`task create`,

- [x] Code change is scoped to `store.js` only — no CLI/MCP surface API change.
