## Proposal

The iteration-2 independent audit (`experiment/audits/iteration-2-independent-adjudicate.md`)
found a real, live ABI-symmetry defect: `quay-native mcp`'s `task_write` tool
declares its `inputSchema` (`packages/quay-native/src/mcp-server.js`) with
`id, title, status, labels, parent, children, body` — **`extra` is missing**.
Verified live during this iteration (not re-asserted from the audit's prose):
patching a task via MCP `task_write` with `{ id, extra: { foo: "bar" } }`
returns the task with `"extra": {}` — the value is silently dropped by the
MCP SDK's schema validation before it ever reaches `store.write()` (confirmed
`store.js#write` itself handles `extra` correctly: `if (extra !== undefined)
frontmatter.extra = extra;`, called from the CLI's `edit --extra` path
without issue — the bug is purely in the MCP tool's declared schema, not in
the shared store core).

This is the **mirror image** of QN-001's own finding (CLI `edit` was missing
`--body`/`--children`/`--extra` wiring; fixed in iteration 2). QN-001 fixed
the CLI-side gap; this bug is the same asymmetry class on the **MCP side**,
for the `extra` field specifically. It went undetected by
`test/abi-symmetry.mjs`'s `task_write_value_equivalence` block because that
block only diffs `body`, `children`, and re-derived `role` — it never
constructs or diffs an `extra` value at all, on either surface.

**Why this matters for self-hosting (not just a point bug):** design §7.1
names `extra` explicitly as "the escape hatch for backend-specific fields" —
it is a first-class part of the canonical view-model, not an afterthought.
An ABI whose CLI can set `extra` but whose MCP surface silently discards it
is not symmetric in exactly the sense design §6/glossary's "CLI/MCP
symmetry" promises. Left unfixed, any Provider or agent driving `quay-native`
purely through MCP (the formal ABI transport, per design §5.1 and glossary's
"provider ABI over MCP") can never durably set `extra` — a silent, systemic
data-loss bug for the one field name-checked in the spec as the
generalization escape hatch.

**Approach (v1, restrained — G5):**
1. Add `extra: z.record(z.any()).optional()` (or equivalent) to
   `task_write`'s `inputSchema` in `mcp-server.js`, mirroring the CLI's
   `--extra` semantics (a JSON object, merged/replaced the same way
   `store.write()` already handles it for the CLI path — no new store.js
   logic needed, since the store core already accepts `extra` correctly;
   only the MCP tool's schema needs to stop discarding it).
2. Strengthen `test/abi-symmetry.mjs`'s `task_write_value_equivalence` block
   to explicitly construct and diff `extra` **values** (not just its
   presence as a key) between the CLI-patched and MCP-patched sibling tasks
   — so this specific class of "field present in schema key-set but its
   *value* silently dropped" bug cannot silently regress again. Per the
   independent audit's own framing: this bug is a *value*-level asymmetry,
   which key-set-only symmetry checks (like iteration 1's original 4-surface
   test) structurally cannot catch — this is exactly why iteration 2 added a
   value-level check for `body`/`children`/`role`, and exactly why it must
   now be extended to also cover `extra`.
3. Do not gold-plate: no schema validation beyond "accept any JSON object,"
   matching the CLI's own `JSON.parse(flags.extra)` looseness. No new CLI
   changes needed (the CLI side already works).

## Plan

**Phase 1 — fix the MCP schema.** In `packages/quay-native/src/mcp-server.js`,
add `extra: z.record(z.any()).optional()` to `task_write`'s `inputSchema`
object (alongside the existing `body` key). No change needed to the tool's
handler body (`async ({ id, ...patch }) => { const task = store.write(id,
patch); ... }`) since `patch.extra` will now actually be present in the
destructured object once the schema stops stripping it.

**Phase 2 — strengthen the ABI symmetry test.** Extend
`test/abi-symmetry.mjs`'s existing `task_write_value_equivalence` block (or
add a clearly-labeled sibling block, `task_write_extra_value_equivalence`)
that:
- Patches one sibling task via CLI `task edit --extra '{"k":"v"}'`.
- Patches a second sibling task via MCP `task_write` with
  `{ id, extra: { k: "v" } }`.
- Diffs the two tasks' resulting `extra` **values** field-by-field (not just
  checking both have an `extra` key) — asserting `JSON.stringify(cli.extra)
  === JSON.stringify(mcpTask.extra)` and that the MCP-patched task's `extra`
  is NOT `{}` (the specific regression this bug produced) unless explicitly
  patched to be empty.
- Reports `match: true/false` in the same results object as the existing
  blocks, so a single `node test/abi-symmetry.mjs` run continues to be the
  one command asserting all ABI-surface symmetry, per design §6.

**Phase 3 — regression-proof and verify.** Re-run
`test/abi-symmetry.mjs`, `test/gate-correctness.test.mjs`, `test/lock.test.mjs`
after the fix — all must still pass, exit 0. Re-run this iteration's own
live repro script (the exact MCP `task_write` call with `extra:{"foo":"bar"}`
that produced `{}` before the fix) and confirm it now returns
`{"foo":"bar"}` unchanged.
