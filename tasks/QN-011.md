## Proposal

Child task of QN-008 (epic decomposition, design §4). Scopes exactly one of
the 3 independently mergeable fixes from QN-008's Plan: fix 3, the
undocumented last-write-wins behavior when an issue carries more than one
`status:*` label (iteration-4 independent audit, bug #4 in that audit's
"Bugs / concerns" section — the original code took whichever `status:*`
label `issue.labels` happened to iterate last, an accident of GitHub's
unspecified label ordering, with no documented rule and no test).

This is a self-contained change to the label-parsing loop inside
`issueToViewModel` only — independent of fix 1 (relations mapping, a
different code path entirely) and fix 2 (pagination, in `createGithubClient`
not `issueToViewModel`).

## Plan

1. Collect *all* `status:*` labels found on an issue (not just the last
   one), into `statusLabelsFound`.
2. Define an explicit precedence order: `done > needs-human > ready > todo`
   (most-advanced lifecycle stage wins) — rationale: a human who leaves a
   stale earlier-stage label while adding a newer one almost always means
   the newer, more-advanced one to take effect. Unrecognized label values
   are lowest precedence.
3. If exactly one `status:*` label is present, use it directly (no
   regression vs. current single-label behavior). If more than one is
   present, resolve via the precedence order, not iteration order.
4. `issue.state == "closed"` still unconditionally forces `status = "done"`
   regardless of any label — this existing rule is unchanged, and must be
   proven to still hold even with multiple conflicting labels present on a
   closed issue.
5. Add test cases to `packages/quay-github/test/view-model.test.mjs`
   covering: two labels in each possible order (proving it is precedence-
   based, not last-write-wins); a 3-way case; the closed-wins interaction
   with multiple labels; and a no-regression check for the single-label and
   no-label cases.
6. Document the rule in `packages/quay-github/DESIGN.md` §3.1.

## AC

- [x] A documented precedence order (`done > needs-human > ready > todo`)

- [x] `issue.state == "closed"` still unconditionally forces `"done"` even
      when multiple conflicting `status:*` labels are present on a closed

- [x] Single-label and no-label cases are unaffected (no regression).

      rationale.
