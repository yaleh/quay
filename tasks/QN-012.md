## Proposal

Iteration 5's own independent audit
(`experiments/quay-native-bootstrap/audits/iteration-5-independent-adjudicate.md`, Claim 5) found a
real, honestly-pre-declared gap: `packages/quay-native/src/store.js`'s
`check(id)` has **no role-aware (compound vs. primitive) branch at all**. For
any task whose `status === "done"`, `check()` unconditionally returns
`{ gate: "none", ok: true, reason: "terminal" }` — regardless of whether the
task is a compound (epic) task and regardless of whether its children are
actually still `done`. Concretely: if a child of a `done` epic were later
reverted to `todo` (accidentally, or by a bug elsewhere), `task check
<epic-id>` would still report `ok: true, reason: terminal` with **zero
cross-check** against the children's live state. `skill/execute/SKILL.md`'s
own Gaps section already names this indirectly ("the epic branch...
untested code-as-documentation") but the gate mechanism itself has never
been fixed to actually enforce the invariant `quay:execute`'s `executeEpic`
pseudocode assumes (design §4: "integrationAccept... Pass -> done").

This is a real, load-bearing correctness gap in the gate that is also this
experiment's own convergence oracle (protocol G3: "the gate is both
contestant and judge") — leaving it unfixed means `task check` on a
compound task is not actually asserting anything about the epic's structural
integrity, only about its own artifact/AC-checkbox presence, which is a
weaker claim than the mechanical gate appears to make.

The fix must stay v0-honest (G5): a compound-aware `check()` should verify
that a `done` epic's children are themselves all `status: done` (the
concrete, cheap, cross-checkable invariant `executeEpic`'s pseudocode
implies), and should also extend the `ready` (execute->done) gate check for
a compound task to require the same children-done invariant in addition to
the existing AC-checkbox check — since a compound task's own AC/DoD do not
mechanically encode "and all children finished," today's checkbox-only gate
would happily flip a compound task to `done` even if a child were still
`todo`. This does not attempt to re-run integration tests (that remains a
Skill-level, not gate-level, responsibility — re-running arbitrary test
suites is out of scope for a generic file-based gate) — it only asserts the
one invariant that is cheap, structural, and directly checkable from the
task store itself: children existence + children status.

## Plan

1. Add a `childrenStatus(t)` helper to `store.js` that, given a task view-
   model, looks up each id in `t.children` via `get()` and returns an array
   of `{ id, status }` (status `"missing"` if the child id does not resolve
   to an existing task file — a distinct, real failure mode, not silently
   treated as `done`).
2. In `check(id)`, for a task whose `role === "compound"` (derived, per
   design §2: `children.length > 0`):
   - `status === "done"`: instead of the unconditional
     `{ gate: "none", ok: true, reason: "terminal" }`, compute
     `childrenStatus` and return `ok: true` only if every child's status is
     `"done"`; otherwise return `ok: false` with a `reason` naming exactly
     which child(ren) are not done (or missing), and a `childrenStatus` field
     in the result for machine consumption. This makes a `done` epic's gate
     check a genuine, cheap re-verification, not a rubber stamp.
   - `status === "ready"` (execute->done gate): in addition to the existing
     AC-checkbox check, also require `childrenStatus` to show all children
     `done` before `ok: true` — a compound task cannot mechanically pass its
     own execute->done gate while any child remains unfinished, closing the
     gap `executeEpic`'s pseudocode assumed but the gate never enforced.
   - `status === "todo"` (author->ready gate): unchanged — a compound task's
     authoring gate is about artifact presence, not children completion
     (children may legitimately not exist yet at authoring time, per
     `executeEpic`'s own `ensureChildrenExist` step, which runs at *execute*
     time, not author time).
3. Primitive tasks (`role === "primitive"`, `children.length === 0`):
   completely unchanged — `childrenStatus` is trivially `[]` and the new
   branch's condition (`every child done`) is vacuously true, so no
   primitive-task behavior changes. This is verified explicitly by a
   regression test, not assumed.
4. Add `packages/quay-native/test/compound-gate.test.mjs`: a new test file
   (following the existing test files' style — plain Node assertions, no
   test framework dependency) covering:
   - A `done` compound task whose children are all `done` → `check()`
     returns `ok: true`.
   - A `done` compound task with one child still `todo` → `check()` returns
     `ok: false`, naming the offending child in `reason`.
   - A `done` compound task with a child id that does not resolve to any
     task file → `check()` returns `ok: false`, `reason` names it as
     missing, distinct from "not done".
   - A `ready` compound task whose AC is fully checked but a child is still
     `todo` → `check()` returns `ok: false` (execute->done gate correctly
     blocked on children, not just AC checkboxes).
   - A `ready` compound task whose AC is fully checked and all children are
     `done` → `check()` returns `ok: true` (positive case, proves the new
     branch does not over-block).
   - A primitive (leaf) task, `done` and `ready` cases — unchanged behavior,
     proving no regression (this is the adversarial check that most matters:
     confirm the new compound branch does not accidentally affect the
     ~11 existing primitive tasks' own gate checks).
5. Re-run the full existing regression suite (`abi-symmetry.mjs`,
   `gate-correctness.test.mjs`, `lock.test.mjs`) plus a live
   `quay-native task check` against QN-008 (the one real compound task in
   this repo, currently `done` with all 3 children `done`) to confirm it
   still reports `ok: true` — the positive real-world case, not just
   synthetic tests.
6. Update `packages/quay-native/skills/execute/SKILL.md`'s Gaps section:
   remove the now-fixed "no compound-aware re-verification" framing (it is
   currently only implied, not stated as a named gap in that file — this
   task both fixes the gate code and makes the SKILL.md's Gaps section
   accurately reflect the new state, since `skills/execute/SKILL.md`'s Spec
   section's `executeEpic` pseudocode's guarantee is now actually backed by
   the gate rather than merely by process discipline).

## AC

- [x] `check()` for a `done` compound task with all children `done` returns
      `ok: true` (positive case, no regression).
- [x] `check()` for a `done` compound task with ≥1 non-`done` or missing
      child returns `ok: false`, naming the specific offending child(ren) in
      `reason`.
- [x] `check()` for a `ready` compound task requires both AC-checkbox
      completion AND all-children-done before returning `ok: true` for the
      execute->done gate.

      regression test cases for `done` and `ready` primitive tasks).

      assertions covering all of the above, passes with exit 0.
