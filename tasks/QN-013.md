## Proposal

Two independently mergeable, real deliverables, bundled as an epic per the
decompose test (design §4):

1. **QN-014** — construct a real, large/paginated GitHub-issue-count fixture
   to genuinely exercise the untested `DEFAULT_MAX_ISSUES` overflow throw
   path in `packages/quay-github/src/github-client.js` (iteration 5's
   Problem 5, deferred at the time; the real `yaleh/quay` repo only has 4
   issues, so `fetchAllIssues()`'s overflow branch has never actually thrown
   in this experiment — it is tested today only by code inspection, per
   `view-model.test.mjs`'s own header comment admitting this).

2. **QN-015** — this iteration's mandate (per protocol §7 discipline of
   testing the adversarial epic case) explicitly requires exercising a
   child that **genuinely fails its own gate mid-epic**, to prove
   `executeEpic`'s `needs-human` fallback path actually works — this path
   has never been exercised in 6 iterations (every prior epic child, QN-009/
   010/011, happened to already have correct underlying implementation
   before its own AC/DoD were written, per iteration 5's own honest
   scoring caveat). QN-015 is deliberately scoped to a case genuinely hard
   enough that a first honest implementation attempt is expected to fall
   short of its own AC on the first pass: harden `quay-native`'s
   `appendNote()` (`packages/quay-native/src/store.js`) against a real,
   previously-undocumented TOCTOU (time-of-check-to-time-of-use) window —
   `appendNote`'s own internal `readRaw()` happens inside `withLock`, but a
   concurrent CLI process invoking `task edit` on a DIFFERENT field between
   two racing `appendNote` calls from separate processes can still interleave
   incorrectly if the *external* status-check-then-decide logic in a Skill
   (not `store.js` itself) reads a task's status, decides an action, and only
   then calls `appendNote`/`write()` — the check and the use are not atomic
   across that boundary, which `store.js`'s own file lock cannot fix, because
   the race is at a layer *above* `store.js`'s API, not inside it. Fully
   solving this in general (e.g. a compare-and-swap `write` variant keyed on
   an expected prior status) is a real, non-trivial API design question, not
   a small bug fix — genuinely likely to require more than one pass, more
   design discussion, or a `needs-human` escalation if the first attempt's
   scope turns out to be bigger than a v0 gate can mechanically verify.

**Decompose-test application (design §4, done live during authoring, before
either child existed):** QN-014 and QN-015 touch entirely different
packages (`quay-github` vs. `quay-native`), have no shared code path, and
are independently testable/mergeable/revertible — a reviewer could accept
QN-014 and reject QN-015 (or vice versa) with zero interaction between the
two. This qualifies as an epic under the same test iteration 5 already
established (≥2 independently mergeable deliverables with real margin over
a single-PR ceiling).

## Plan

1. Author QN-014 as a `todo` child, scoped exactly to the pagination
   overflow fixture (see QN-014's own file for its Proposal/Plan/AC/DoD).
2. Author QN-015 as a `todo` child, scoped exactly to the TOCTOU
   hardening investigation (see QN-015's own file). QN-015's AC is
   deliberately written to require a genuine compare-and-swap primitive
   AND a demonstrated concurrent-race regression test proving the race is
   closed — a substantially harder bar than QN-014's, by design, since
   this task's explicit purpose is to test whether `quay:execute`'s
   `needs-human` fallback triggers honestly when a first pass falls short.
3. Set QN-013's own `children` to `[QN-014, QN-015]` via
   `task edit --children` (proving `role` re-derives to `compound`, same
   mechanism already proven in iteration 5 for QN-008).
4. Drive QN-014 through its own full `todo -> ready -> done` lifecycle via
   `quay:author` + `quay:execute` — expected to succeed cleanly (it is a
   test-fixture-construction task with a clear, bounded scope).
5. Drive QN-015 through `quay:author` (author its Proposal/Plan/AC/DoD,
   defining a genuinely hard bar) then attempt `quay:execute`'s `executeLeaf`
   method against it, honestly, without pre-deciding the outcome. If the
   first implementation pass satisfies QN-015's own AC, that is a genuine,
   not-manufactured PASS and is recorded as such (the adversarial exercise
   is then honestly reported as "attempted, but did not turn out to be hard
   enough to trigger needs-human" rather than force-failing a task that
   actually passed, which would be dishonest per G1). If the first pass does
   NOT satisfy QN-015's own AC (a stated risk in this task's own Proposal),
   `quay:execute`'s `gate-check` step is followed literally: report the
   gate's `reason`, leave the task at `ready` (not force `done`), and route
   QN-015 to `needs-human` — then re-run `quay:execute`'s `executeEpic`
   `driveEach` step, honestly recording that one child returned
   `NeedsHuman`, and prove QN-013's own epic-level `integrationAccept`
   correctly reports `Fail` (not `Pass`) as a direct, mechanical consequence
   -- this is the actual thing this task exists to prove, per the executive
   mandate for this iteration.
6. Whatever the genuine outcome of step 5, record it honestly in
   `experiments/quay-native-bootstrap/provenance.md` and this iteration's report — do not force
   QN-013 to `done` if QN-015 is not actually `done`; a `needs-human`
   verdict for QN-013 itself (mirroring QN-015's own) is the CORRECT,
   expected epic-level outcome if step 5 lands on `NeedsHuman`, not a
   failure of this task.
