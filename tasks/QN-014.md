## Proposal

Child task of QN-013 (epic decomposition, design §4). Scopes exactly one of
the 2 independently mergeable deliverables: iteration 5's Problem 5
(deferred at the time) — `packages/quay-github/src/github-client.js`'s
`fetchAllIssues()` overflow branch (`issues.length >= maxIssues` throw) has
never actually been exercised against real overflow, because the real
`yaleh/quay` repo has only 4 issues and this experiment has no live access
to a repo with hundreds of real issues. `test/view-model.test.mjs`'s own
header comment already honestly admits this ("no live large-repo fixture is
available to test the throw path without network access").

The fix does not require a real GitHub repo with 500+ issues (impractical
and out of scope) — it requires exercising the actual overflow *logic* with
a low, controllable threshold via `QUAY_GITHUB_MAX_ISSUES`, and a fake `gh`
subprocess stand-in (since `ghApiJson` shells out to the real `gh` CLI,
which cannot be pointed at a fixture repo without creating one). The
cleanest, most honest way to do this without touching real GitHub state is
to extract `fetchAllIssues`'s core paging/overflow logic into a form that
accepts an injectable page-fetcher function, and test that function
directly with a synthetic fetcher returning a controlled number of
synthetic pages — proving the exact loop/throw logic that
`createGithubClient` wires up to the real `gh api` calls, without needing a
real 500-issue repository.

## Plan

1. Refactor `github-client.js`: extract the paging loop (currently inlined
   inside `createGithubClient`'s `fetchAllIssues`) into a standalone,
   exported, injectable function `pageIssues({ maxIssues, perPage, fetchPage
   })`, where `fetchPage(page, perPage)` is the thing that actually talks to
   `gh api` in production, but can be a synthetic stand-in in tests. This is
   a minimal, non-gold-plated refactor (G5) — no new capability, purely
   making the existing loop's core logic independently testable.
2. `createGithubClient`'s `fetchAllIssues` becomes a thin call to
   `pageIssues` with a real `fetchPage` that calls `ghApiJson` — behavior
   must be provably identical to before the refactor (a regression, not a
   feature).
3. Add `packages/quay-github/test/pagination.test.mjs`: a new test file
   exercising `pageIssues` directly with a synthetic `fetchPage`:
   - A small number of pages (natural end reached before the cap) → returns
     exactly the expected concatenated issues, no throw.
   - A `fetchPage` that would produce exactly `maxIssues` items with no
     natural short-page end within the cap → the overflow branch throws,
     with a message matching the existing descriptive error shape.
   - A `QUAY_GITHUB_MAX_ISSUES`-equivalent override (passed as an explicit
     `maxIssues` param, since `pageIssues` itself should not read
     `process.env` directly — that stays `createGithubClient`'s job) raises
     the cap and the same synthetic fetcher that overflowed at the default
     cap now completes without throwing.
4. Re-run `view-model.test.mjs` (unaffected — it does not touch pagination)
   and a live `quay task list --provider github --json` call against the
   real `yaleh/quay` repo (4 issues, nowhere near the cap) to confirm no
   regression in the real, unrefactored call path.
