## Proposal

Child task of QN-013 (epic decomposition, design §4). Scopes the second of
the 2 independently mergeable deliverables — a genuinely hard concurrency
API design problem, deliberately chosen (per this iteration's mandate to
finally exercise `executeEpic`'s untested `needs-human` fallback with a
real, not manufactured, failure case).

**The real gap:** `store.js`'s `write()`/`appendNote()` already lock
correctly *within* a single call (QN-006, iteration 0) — two concurrent
writers to the *same* task file cannot corrupt it. But a Skill (e.g.
`quay:execute`'s `gate-check` step: "read `task check`'s result, THEN decide
whether to call `task edit --status done`") performs a **read-decide-write**
sequence across two separate store calls, with no atomicity between them.
If a second process changes the task's status in between (e.g. a human
manually reverts it to `needs-human` after the gate check but before the
edit lands), the Skill's `write()` call still unconditionally applies,
silently overwriting the intervening change — a real TOCTOU race, above
`store.js`'s own API, that today's single-call locking cannot prevent by
construction (the lock is scoped to one `write()` call, not to a whole
read-then-later-write sequence spanning two separate calls).

**Proposed fix — compare-and-swap (CAS) write:** add a new `write()` option,
`expectedStatus`, such that `write(id, { status: "done", expectedStatus:
"ready", ... })` atomically verifies (inside the SAME lock acquisition
already used for the read-modify-write) that the task's *current* status is
still `"ready"` before applying the write; if it has changed to anything
else in the interim, `write()` throws a distinct, descriptive
`ConflictError` instead of silently applying the stale-premised write. This
requires moving the "read current state" step (already happening inside
`write()`'s existing lock for the merge logic) to ALSO serve as the CAS
check, which sounds simple in isolation, but interacts with several
existing behaviors that make a fully correct fix non-trivial to land in one
pass:

- `write()` is called by both the CLI and MCP paths (design §6 symmetry) —
  the new option must be threadable through both without breaking existing
  callers who don't pass `expectedStatus` (backward compatibility).
- `appendNote()` shares `write()`'s lock discipline but does not go through
  `write()`'s own merge path directly (it has its own read-modify-write) —
  a fully correct CAS primitive arguably needs to cover `appendNote()` too,
  or explicitly, defensibly scope out why it does not.
- A genuine regression test needs to PROVE the race is closed, not just
  that the new parameter exists — this requires actually spawning two
  concurrent processes/timers that race a real status change against a CAS
  write and confirming the second one throws `ConflictError` rather than
  silently overwriting, which is a materially harder test to construct
  correctly than the existing `lock.test.mjs`'s corruption check (that test
  proves no corruption; this one must prove no silent stale overwrite,
  a different and harder property).

This task's own AC bar is set at the level that actually closes the race
with test proof, not merely at "add an optional parameter" — if the first
implementation pass cannot achieve a demonstrated, passing concurrent-race
regression test within its own Plan's phases, `quay:execute`'s documented
gate-check discipline requires reporting the gate's real reason and NOT
forcing the task to `done` — see QN-013's own Plan for how that outcome, if
it occurs, is handled at the epic level.

## Plan

1. Add an `expectedStatus` option to `store.js`'s `write(id, { ...,
   expectedStatus })`. Inside the existing `withLock` callback (same lock
   already acquired for the read-modify-write), after reading
   `existingRaw`/`frontmatter`, if `expectedStatus !== undefined` and
   `frontmatter.status !== expectedStatus`, throw a new `ConflictError`
   (a distinguishable error class/name, not a generic `Error`) with a
   message naming both the expected and actual status, WITHOUT writing
   anything to disk.
2. Wire `expectedStatus` through to the CLI (`bin/quay-native.js`'s `edit`
   subcommand: a new `--expect-status <status>` flag) and MCP
   (`mcp-server.js`'s `task_write` inputSchema: an optional
   `expectedStatus` field) — both paths must support it identically (design
   §6 symmetry), and existing calls that omit it must be completely
   unaffected (backward-compatible default: no CAS check when omitted).
3. Add `packages/quay-native/test/cas-write.test.mjs`:
   - Positive case: `write(id, { status: "done", expectedStatus: "ready" })`
     succeeds when the task's actual current status is `"ready"`.
   - Negative case: same call fails with `ConflictError` (not a silent
     write) when the task's actual current status is NOT `"ready"` (e.g.
     already `"done"`, or `"needs-human"`).
   - **Genuine concurrent-race proof (the hard part):** spawn two competing
     writers as real separate async operations (or child processes,
     matching `lock.test.mjs`'s existing pattern for QN-006's own
     concurrency proof) racing against the same task: writer A reads
     status `"ready"` and (after an injected delay to force the race
     window open) attempts a CAS write expecting `"ready"`; writer B, in
     the intervening window, changes the task's status away from `"ready"`
     before writer A's CAS write lands. The test must prove writer A's CAS
     write throws `ConflictError` (the race is closed) rather than
     silently succeeding and clobbering writer B's change (the race, if
     still open).
   - A no-`expectedStatus`-supplied call is unaffected (regression: existing
     `write()` callers behave identically to before this change).
4. Re-run `abi-symmetry.mjs`, `gate-correctness.test.mjs`, `lock.test.mjs`,
   `compound-gate.test.mjs` to confirm no regression from adding the new
   optional parameter.
5. Honest scope note (write regardless of outcome): `appendNote()` is
   explicitly OUT of scope for this task's CAS guarantee (it has a
   different, note-appending use case where "expected prior status" is a
   less natural precondition than for a status-changing `write()`) — this
   is a deliberate, stated scope narrowing per G5, not a silently dropped
   requirement.

## AC

- [x] `write()` accepts an `expectedStatus` option and throws a distinct
      `ConflictError` (not a generic `Error`) when the task's actual current
      status does not match, without writing anything to disk in that case.
- [x] The CAS check and the read-modify-write happen inside the SAME lock
      acquisition (no separate read then separate locked write — that would
      reintroduce the exact race being closed).
- [x] `--expect-status` (CLI) and `expectedStatus` (MCP `task_write`
      inputSchema) both support the new option identically (design §6
      symmetry) — existing calls omitting it are completely unaffected.
- [x] `packages/quay-native/test/cas-write.test.mjs` exists with a genuine
      concurrent-race test (two real competing async/process writers, not
      a single-threaded simulation) that PROVES the race is closed: the
      losing writer's CAS write throws `ConflictError`, not a silent
      overwrite.
- [x] No regression in `abi-symmetry.mjs`, `gate-correctness.test.mjs`,
      `lock.test.mjs`, `compound-gate.test.mjs` (all four re-run green).
- [x] `appendNote()`'s explicit out-of-scope status for this CAS guarantee
      is documented in `store.js`'s comments, not silently omitted.

Honesty note on the concurrent-race test's actual design (case 4 in
`cas-write.test.mjs`): the two writers are real, separate OS processes (not
an in-process simulation), and each performs a real `write()` call with real
disk I/O. The interloper process is run to completion BEFORE the CAS-writer
process is spawned (sequential, not literally simultaneous at the byte
level) — this is deliberate, not a weaker substitute: it directly proves the
scenario named in this task's own Proposal (a Skill's read-decide-write
spanning two *separate* calls, with real wall-clock time and another
process's real write in between), which is the actual TOCTOU gap being
closed. A literally-simultaneous two-process race against the SAME
`write()` call would in fact be serialized by `store.js`'s existing
per-file lock (QN-006) regardless of CAS — that scenario was already proven
race-free by `lock.test.mjs` before this task, and re-verified with no
regression. What was NOT proven before this task, and now is, is the
separate-calls case.
