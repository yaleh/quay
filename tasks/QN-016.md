## Proposal

Iteration 6's genuinely independent, out-of-band audit
(`experiment/audits/iteration-6-independent-adjudicate.md`, Finding 1) found a
real, previously-undocumented limitation in QN-012's compound-aware gate fix:
`store.js`'s `childrenStatus(t)` helper only reads `child.status` — one level
deep. It does not recurse into a child's own `children` array. Concretely: if
a task `E` (epic) has child `C` (itself a compound task with child `G`), and
`G` is later reverted from `done` to `todo` while `C`'s own stored `status`
frontmatter field is stale at `"done"` (a real, plausible scenario — nothing
in the current write path re-derives or cascades a parent's stored `status`
when a grandchild changes), `task check E` would read `C.status === "done"`
directly from `C`'s frontmatter and report the whole subtree healthy, without
ever looking at `G`. This is exactly the compound-blindness gap QN-012 closed
for the single-level case, still open one level deeper — a genuine correctness
gap in the gate, not a hypothetical: `quay-native`'s own task model (design
§2) explicitly allows arbitrary-depth nesting (a compound task's children can
themselves be compound), and `quay:execute`'s `executeEpic` pseudocode
(`skills/execute/SKILL.md`) already documents `driveChildToDone` as
"recursive: todo->author->ready->execute->done" — the execution path already
assumes recursion is a normal, supported shape. The gate-check path currently
does not match that assumption.

This is a natural, non-gold-plated next step (G5): it closes a specific,
independently-found gap in existing shipped code, using the exact same
mechanism (`childrenStatus`) already proven correct at one level, rather than
inventing new gate machinery. It is scoped tightly to the one invariant named
by the audit (recursive re-verification of children's live status), not a
broader rewrite of the gate.

## Plan

1. Change `childrenStatus(t)` in `store.js` to recurse: for each declared
   child id, resolve the child via `get()` as today, but if the child itself
   is `role === "compound"` (has its own children), also recursively resolve
   *its* children's statuses, and roll up: a child is only reported `"done"`
   in the parent's `childrenStatus` result if the child's own stored
   `status === "done"` **AND** all of that child's own (recursively derived)
   children are `"done"`. A child whose stored status is `"done"` but whose
   own subtree is not fully done is reported with a distinct status value
   (`"stale-done"`) rather than silently passed through as `"done"` — this
   keeps the failure mode nameable and distinguishable from an honestly
   incomplete child (`"todo"`/`"ready"`) or a dangling reference (`"missing"`),
   matching the existing convention of naming failure modes explicitly rather
   than collapsing them.
2. Guard against cycles: track visited ids during the recursive walk; if a
   child id is revisited within the same `childrenStatus` call, treat it as
   `"missing"` for the purposes of this check (a cyclic parent/children graph
   is itself a data-integrity bug the gate should not crash on, and quay-
   native has no existing cycle-prevention at write time — this is the
   correct minimal defensive behavior, not a full cycle-detection feature,
   which is out of scope here per G5).
3. `check()`'s existing `"done"` and `"ready"` compound branches (QN-012) do
   not need their own logic changed — they already call `childrenStatus(t)`
   and check `.every(c => c.status === "done")`; making `childrenStatus`
   itself recursive and correctly reporting `"stale-done"` (not `"done"`) for
   an unhealthy subtree is sufficient to make the existing `.every(...)`
   check catch the grandchild case, with zero changes needed to `check()`'s
   own branch bodies.
4. Primitive (leaf) tasks and single-level compound tasks (no grandchildren):
   completely unchanged behavior — verified by a regression test, not
   assumed. A child with no children of its own has nothing to recurse into,
   so the new logic degrades to exactly QN-012's original one-level check.
5. Add `packages/quay-native/test/compound-gate-recursive.test.mjs` covering:
   - A 3-level task tree (epic -> compound child -> leaf grandchild), all
     `done` -> `check()` on the top epic returns `ok: true`.
   - The same tree with the grandchild reverted to `todo` (parent's own
     stored status frontmatter left stale at `"done"`) -> `check()` on the
     top epic returns `ok: false`, correctly identifying the *grandchild's*
     revert even though the immediate child's own stored status still says
     `"done"`.
   - The same case, but checking the *middle* task directly (not the top
     epic) -> also correctly returns `ok: false` (recursion is not only
     reachable from the very top).
   - A synthetic self-referential cycle (a task listing itself, directly or
     via a 2-hop cycle, as its own child) -> `check()` does not crash/infinite-
     loop, and reports the cyclic id as unresolvable rather than hanging.
   - Regression: the existing single-level compound cases from
     `compound-gate.test.mjs` (all of them) still pass unchanged, plus a
     leaf-task case proving zero behavior change for primitives.
6. Re-run the full existing regression suite (`compound-gate.test.mjs`,
   `abi-symmetry.mjs`, `gate-correctness.test.mjs`, `lock.test.mjs`,
   `cas-write.test.mjs`) plus a live `quay-native task check QN-008 --json`
   and `QN-013 --json` (the two real compound tasks in this repo, both
   single-level) to confirm no regression on real data.
7. Update `store.js`'s own QN-012 code comments and `skills/execute/
   SKILL.md`'s Gaps section to note the one-level limitation is now closed,
   citing this task and the independent audit finding that surfaced it.
