## Proposal

Iteration 7's QN-017 surfaced a real, first-hand gate-design gap (not
previously named as a concrete task, only as a carried-forward observation
in iteration 7's "Problems identified for next iteration" item 2):
`store.js`'s `check()` "todo" branch (`author->ready` gate) tests the AC
section only for checkbox **presence** —

```js
const acHasCheckbox = /- \[[ xX]\]/.test(acSection);
```

— not checked-**state**. A task can therefore reach `ready` with zero AC
boxes actually checked, so long as at least one checkbox line exists in the
AC section at all. This is inconsistent with the `execute->done` gate (the
"ready" branch), which correctly requires **all** AC checkboxes to be
checked:

```js
const acOk = checkboxes.length > 0 && checked.length === checkboxes.length;
```

This inconsistency is a real correctness gap in the gate that is also this
experiment's own convergence oracle (protocol G3: "the gate is both
contestant and judge") — an author could reach `ready` today by writing an
AC section with entirely unchecked boxes, and the mechanical gate would not
catch it. `quay:author`'s own documented degraded-fallback checklist (Gaps
section) is a process-level mitigation, not a gate-level one; the gate
itself should not be weaker than the process it is meant to check.

**Why this is a natural, non-gold-plated next step (G5), not scope
creep:** the fix reuses the exact same checkbox-parsing primitive already
proven correct at the `execute->done` gate (`checkboxes`/`checked` regex
match), applied to the same AC section already being read at the
`author->ready` gate. No new mechanism is introduced; an existing,
already-tested mechanism is extended to a second call site that was
inconsistently thinner. This does not gold-plate the gate with new
capability — it removes an asymmetry between the two existing gates.

**What this fix does NOT address (explicitly out of scope, per G5):** the
deeper "checkbox-count gameability" gap named in iterations 6/7 (an author
could check AC boxes without independent verification that the underlying
claim is true — the mechanical gate cannot detect a false-but-checked box).
This task closes the narrower, purely mechanical "checked vs. merely
present" asymmetry only. The broader self-certification gap (G3) remains
open and is not claimed to be resolved here.

## Plan

1. Change `check()`'s `"todo"` branch in `packages/quay-native/src/store.js`
   to require **all** AC checkboxes in the AC section to be checked, not
   merely that at least one checkbox exists — the same `checkboxes`/
   `checked` regex-count logic the `"ready"` branch already uses. Report a
   distinct, specific failure reason (`"N/M AC checkboxes checked"`,
   mirroring the `execute->done` gate's own reason string) when boxes exist
   but are not all checked, and keep the existing `"AC section has no
   checkboxes"` reason for the true zero-checkbox case.
2. Add regression tests to a new
   `packages/quay-native/test/gate-checked-state.test.mjs` covering: (a) AC
   section with zero checkboxes → `ok:false`, "no checkboxes" reason
   (unchanged from before); (b) AC section with checkboxes present but not
   all checked → `ok:false`, new "N/M checked" reason (the exact case
   QN-017 exposed); (c) AC section with all checkboxes checked → `ok:true`
   (unchanged); (d) regression — the existing `execute->done` (ready)
   branch and `done`-status branch are unaffected (both already require
   full-checked state and were not touched).
3. Verify via genuine `git stash`/`git stash pop` TDD discipline: pre-fix
   store.js must genuinely fail the new case (b) test; post-fix must pass
   all new tests plus the full existing regression suite
   (`compound-gate.test.mjs`, `compound-gate-recursive.test.mjs`,
   `abi-symmetry.mjs`, `gate-correctness.test.mjs`, `lock.test.mjs`,
   `cas-write.test.mjs`).
4. Re-check all 17 existing real task files in this repo's own `tasks/`
   directory against the new, stricter `author->ready` gate logic — since
   every one of them is already at `ready`/`done`/`needs-human` (past the
   `todo` gate), this is a live regression check that the tightened gate
   does not retroactively invalidate any already-passed real task. Note
   honestly whether any of the 17 would newly fail if re-run from `todo`
   under the tightened gate (informational only — their `status` fields are
   not touched by this task).
5. Update `skills/author/SKILL.md`'s Gaps section to document the fix,
   citing iteration 7's finding as the motivating evidence.
