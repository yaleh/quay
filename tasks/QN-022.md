## Proposal

Iterations 7 and 8 together resolved two of `executeEpic`'s `needs-human`
sub-cases, but a third, narrower one remains explicitly open, named in both
`quay:execute`'s own SKILL.md Gaps section and iteration 8's "Problems
identified for next iteration" (item 1): the pseudocode's `integrationAccept:
runEpicLevelACAndDoD(task)` branch failing *after* `driveEach` has
successfully driven **every** child to `done`. This is a structurally
distinct trigger from both prior cases:

- QN-017 (iteration 7): a plain leaf task's own `execute->done` gate fails
  (`executeLeaf`'s `needs-human` branch).
- QN-020/QN-021 (iteration 8): an epic's child **cannot be driven to
  `done`** at all, so `driveEach` itself never completes (`executeEpic`'s
  "child cannot complete" sub-case).
- **This task (QN-022/QN-023): every child DOES reach `done`, but the
  epic's own AC/DoD — the "integration acceptance" step, mapped concretely
  onto `store.js`'s `check()` for the epic's own `execute->done` gate
  (`acOk && childrenOk`, see `store.js` lines ~404-424) — is deliberately
  left with a genuinely unsatisfiable AC item, so `acOk` is honestly false
  even though `childrenOk` is honestly true.**

This third sub-case has a real, mechanical difference in `store.js`'s own
gate logic worth exercising directly: `acOk` and `childrenOk` are two
independent boolean terms ANDed together (`const ok = acOk && childrenOk`).
Every previously-tested compound case in this repo's real tasks (QN-008,
QN-013) had both terms true, and QN-020/QN-021 tested `childrenOk = false`
with `acOk` never actually reached (QN-021 never got far enough for QN-020's
own AC to even be the relevant blocker). No real task in this repo's history
has yet exercised `acOk = false ∧ childrenOk = true` for a compound task —
this task closes that specific, previously-undemonstrated combination.

**What this task is NOT:** it is not organic backlog work, exactly as
QN-017 and QN-020/QN-021 were not. It exists specifically to construct the
one remaining untested boolean combination in `store.js`'s own compound
`execute->done` gate logic.

## Decompose-test honesty note (read before treating this as a routine epic)

Same honest exception as QN-020: this epic has exactly one child, which
would normally fail design §4's "≥2 independently mergeable deliverables"
decompose test on editorial grounds. It is authored as compound (one child)
solely because `executeEpic`'s code path requires `role === "compound"`
(`children.length > 0`, design §2) — there is no way to exercise the
epic-level `integrationAccept` gate logic without at least one child.
Recorded explicitly, not silently passed off as an ordinary multi-deliverable
epic.

   QN-021, its own AC must be honestly completable, so that it actually

   adversarial — only the epic's own AC is adversarial here.

   genuinely reaches `done`.

   structurally false to check right now (same discipline as QN-017/QN-021:
   a real, re-confirmed-absent environmental precondition — the
   subagent-dispatch primitive — not a subjective "hard" claim), alongside
   other items that ARE genuinely satisfiable and will be checked true. This

   this iteration (do not assume from prior iterations).
5. Attempt `quay:execute`'s `executeEpic` method against QN-022:
   `ensureChildrenExist` (QN-023 exists), `driveEach` (QN-023 genuinely
   reaches `done` — this is the key structural difference from QN-020),

6. Per `quay:execute`'s own Method, since the blocker is genuine (not an

   `needs-human`, matching the same discipline QN-017/QN-020 used.
7. Update `quay:execute`'s SKILL.md Gaps section: mark this third, narrower
   sub-case as now resolved, citing this task, and note explicitly what (if
   anything) remains open in `executeEpic`'s branch space after all three
   sub-cases are covered.
8. Do not fabricate a dispatch primitive, do not force QN-022's checkbox, do
   not silently reinterpret its AC to make it pass artificially.
