## Proposal

`packages/quay-github/provider.yml` has declared `data.write: false` since
QN-002 (iteration 4), unchanged across 5 consecutive iterations (7, 8, 9 all
re-confirmed "no natural reason to act" per protocol resolved-decision 4:
read-only is sufficient for the v1 transfer-target *proof*, criterion 3).
That remains true for criterion 3. But `reusability` (V_meta component) has
independently been held flat at 0.55 for 6 consecutive iterations (4
through 9) for a *different*, honest reason stated each time: "no new
Provider or transfer target was built or touched this iteration" (G2 — hold
constant absent a genuine new transfer event, do not force one).

This task is that genuine, not-forced opportunity: the ABI (native
`task_write`'s CLI/MCP shape, `store.js`'s status-transition semantics) has
been stable across 9+ iterations with zero further changes required beyond
QN-007's `extra`-field fix (iteration 3) and QN-015's CAS option (iteration
6) — both native-side hardening, neither touching the read-only/write
boundary of a second Provider. Live evidence this is genuinely overdue, not
manufactured: two real, pre-existing GitHub issues (#3, #4, created in
iteration 4 as read targets) sit at stale `status:ready`/`status:todo`
labels on GitHub even though the underlying native tasks they mirror
(QN-001, an earlier config bug) have long since reached `done` natively —
a real, visible drift between the two Providers that a working `data.write`
capability would resolve, not a synthetic test fixture built to force a
number.

**Scope discipline (G5 — do not gold-plate a v1 Provider):** implement only
the minimal write surface needed to prove the transfer — a `task_write`
MCP tool + CLI `task edit` subcommand that patches an issue's `status:*`
label (open/close the issue for `done`, swap the `status:*` label
otherwise) via `gh api`. Do NOT implement `gate` or `skill` capabilities in
this task — those remain correctly out of scope (unchanged, still 0
natural reason this iteration for either). Do NOT implement title/body/
labels/parent/children writes — status-only is the minimal slice that
proves the write-path ABI symmetry claim (`quay task edit --provider github
--status X` produces the same shape of result as native's equivalent call),
without expanding scope beyond what's needed for the reusability proof.

## Plan

1. **Phase 1 — `github-client.js`: add a `setStatus(id, status)` function.**
   Maps the canonical `status` value back onto GitHub's representation:
   `done` → close the issue (`PATCH .../issues/<n> {state: "closed"}`,
   leaving whatever `status:*` label is present, since `state=="closed"`
   already unconditionally forces `status="done"` on read per DESIGN.md §3
   — no label change needed for this transition); any other status
   (`todo`/`ready`/`needs-human`) → ensure the issue is `state: "open"` (if
   currently closed, reopen it) and replace any existing `status:*` label
   with `status:<newStatus>` (remove old `status:*` labels first, to avoid
   the multi-label-precedence ambiguity DESIGN.md §3.1 already had to
   solve for read — do not reintroduce that ambiguity on the write side).
2. **Phase 2 — `mcp-server.js`: register `task_write`.** Mirrors
   quay-native's own `task_write` tool name/shape (design §6 symmetry),
   input schema `{ id: string, status: string.optional() }` only (no other
   fields, per this task's scope discipline) — calls `client.setStatus`.
   Update `provider.yml`: `data.write: true`.
3. **Phase 3 — `bin/quay-github.js`: add `task edit <id> --status <s>`
   CLI subcommand**, calling the same `github-client.js` function (CLI is
   the golden ABI-symmetry harness, same principle as native's own
   `abi-symmetry.mjs`).
4. **Phase 4 — test coverage**: a new
   `packages/quay-github/test/write.test.mjs` unit-tests `setStatus`'s
   label-replacement logic against a synthetic/injectable `gh api` stand-in
   (same pattern as QN-014's `pageIssues` injection — this repo's real
   issue count is too small to safely target with destructive live writes
   in an automated test). Additionally, run ONE real, live write against
   this repo's actual issue #4 (the stale `status:todo` mirror of the
   long-`done` QN-001) via the real CLI, to prove the live transfer end to
   end — then verify by a live `gh issue view 4 --json labels,state` read,
   not by trusting the write call's own reported success.
5. **Phase 5 — self-audit + gate.** Re-verify all AC items against live
   command output (not "should work"). Run `quay-native task check
   QN-024 --json`, and if `ok:true`, drive to `ready` then `done` via
   `quay:execute`.
