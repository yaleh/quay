## Proposal

`packages/quay-github/DESIGN.md` still states, in two places, that
quay-github is "v1 implemented (read-only: `data.read` + `manifest` only)"
(§Status line and §1) and, in its own §5 capabilities table, lists
`data.write: false  # deferred`. This has been stale since iteration 10
(QN-024), which genuinely shipped a real, live-tested status-only
`data.write` capability and correctly flipped `provider.yml`'s own
`data.write: true` at the time — but did not update `DESIGN.md` to match
(confirmed by direct `grep` this iteration: `provider.yml` says `true`,
`DESIGN.md` still says `false`). Iterations 11 was corrective and did not
touch this area; the drift has persisted for 2 iterations, undetected
until this iteration's routine re-read of `DESIGN.md` while evaluating
whether a natural reason exists to act on `gate`/`skill`.

This is a genuine, evidenced completeness gap (V_meta's `completeness`
factor requires the methodology/design documentation to be "fully
documented and self-contained," not "mostly") — not manufactured. A
reader trusting `DESIGN.md` alone (as the file's own header invites: "see
`tasks/QN-002.md` for the authored Proposal/Plan/AC/DoD this package
executes") would incorrectly believe no write path exists at all, when a
real one has been live and tested since iteration 10, including two
independently-audited live writes/reverts against this repo's actual
issue #4.

## Plan

1. Update `DESIGN.md`'s top status line and §1 to say "v1.1 implemented:
   read + minimal status-only write" (matching `provider.yml`'s own v1
   comment convention), citing QN-024.
2. Update `DESIGN.md` §5's capability table: `data.write: true  # QN-024
   (iteration 10) — status-only patch via \`quay-github task edit --status\`;
   title/body/labels/parent/children remain unimplemented`. Leave
   `gate`/`skill` as `false` (still accurate, still deferred, no natural
   reason found this iteration either — see this iteration's own report
   §Observe for the honest re-evaluation).
3. Add a short new §3.4 subsection ("status-write path, iteration 10")
   cross-referencing QN-024's own AC/DoD and the two independently-audited
   live writes against issue #4, so §3's field-by-field table and §4's
   "what transferred / what required normalization" table both stay
   internally consistent with the new §3.4 (status write required no new
   normalization beyond what §3's status-read mapping already established
   — the same label convention is reused for both directions).
4. No code change — this is a documentation-only sync; verify via `grep`
   that `provider.yml` and `DESIGN.md` agree afterward, and that no other
   `.md` file in the repo repeats the stale "read-only" claim.
