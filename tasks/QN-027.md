## Proposal

`quay task check` — Core's own CLI verb calling `task_check` via the
provider-agnostic MCP ABI — does not exist. Found this iteration while
investigating (per this iteration's mandate) whether DIR-004's now-confirmed
manda dispatch primitive changes the "no natural reason" verdict on
quay-github's `gate`/`skill` capabilities. Reading native's own `mcp-server.js`
alongside Core's `provider-client.js` and `quay.js` surfaced a concrete,
previously-unflagged asymmetry, confirmed by live command output rather than
code-reading alone:

```
$ node packages/quay-native/bin/quay-native.js task check QN-001 --json
{"id":"QN-001","gate":"none","ok":true,"reason":"terminal"}

$ node packages/quay/bin/quay.js task check QN-001 --json
usage: quay <task list|view|action list|run|serve> ...
(exit 1)
```

`quay-native`'s own CLI implements `check` by calling `store.check(id)`
directly (bypassing its own MCP layer) — not by round-tripping through
`task_check` at all. Core's `provider-client.js` has `taskList`/`taskGet`/
`taskWrite`/`manifest` passthroughs but no `taskCheck`, and `quay.js` never
calls it. This means `task_check` — a capability native's own
`provider.yml` declares (`gate: true`) and registers as an MCP tool
(`mcp-server.js`) — has never actually been exercised through Core's
provider-agnostic client, in 12+ iterations of scoring `abi_symmetry` at
0.90-0.92. This is a real gap in the CLI-JSON-equals-MCP-tool-output
symmetry claim (design §6), not a manufactured one: `abi_symmetry`'s own
evidence source (protocol §5.1) is specifically "quay-native task ...
--json emits the same schema as the corresponding MCP tool result" — and
that comparison has silently never included `check`.

This also bears on `quay-github`'s `gate` capability (protocol §10,
resolved decision 4; DESIGN.md §5): before quay-github's own `gate` could
ever be meaningfully exercised **through Core** (as opposed to a bespoke
per-Provider CLI), Core itself needs a `task check` verb to call through.
Fixing this is a genuine prerequisite, not itself an implementation of
quay-github's `gate` (which remains a separate, larger decision — see
this iteration's own Observe/Strategy sections for why `gate`/`skill`
for quay-github specifically still has no natural trigger this
iteration).

Scope, deliberately narrow (G5): add the passthrough only. Do not touch
`store.js`'s `check()` gate logic itself (unchanged, still correct per
prior iterations' work), and do not implement quay-github's own
`task_check` (out of scope — no natural trigger yet, per Observe).

## Plan

1. `packages/quay/src/provider-client.js`: add a `taskCheck(id)` function,
   mirroring the existing `taskWrite` passthrough pattern exactly — calls
   `client.callTool({ name: "task_check", arguments: { id } })`, returns
   `structuredContent` (or throws on `isError`, consistent with
   `taskWrite`'s existing error convention). Export it from the returned
   object.
2. `packages/quay/bin/quay.js`: add `if (cmd === "task" && sub === "check")`
   branch, mirroring `task view`'s structure — takes `id` positional,
   prints JSON if `--json`, else a human-readable one-line summary
   (`${id}: PASS/FAIL — ${reason}`), sets `process.exitCode` from `ok`
   (matching quay-native's own CLI convention for `check`).
3. No change to `store.js`, `mcp-server.js` (native or github), or any
   gate logic. This is purely a Core-side passthrough addition.
4. Verify live, not just via new unit tests: run
   `node packages/quay/bin/quay.js task check QN-001 --json` (a real,
   `done`, terminal task) and confirm its JSON output is schema-identical
   to `node packages/quay-native/bin/quay-native.js task check QN-001
   --json`'s own output (the actual abi_symmetry evidence this task
   exists to produce).
5. Add a regression test (`packages/quay/test/task-check.test.mjs` or
   equivalent) exercising the new passthrough against a fake/stub
   MCP client, following the existing test conventions in
   `packages/quay-native/test/`.
