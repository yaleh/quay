## Proposal

`quay-github`'s `gate` capability has been `false` since QN-002 (iteration
4), and every iteration from 4 through 16 (13 consecutive substantive
checks) re-confirmed "no natural reason to implement this iteration" — the
correct, honest call each time, since no usage event ever required it.
Iteration 16 explicitly surfaced a top-level-orchestrator judgment call:
either declare practical convergence at the current, far-below-threshold
V-levels, or deliberately author the next real increment rather than
continuing to wait for an organic trigger that this experiment's own
structure cannot produce. The orchestrator has now made that call for this
iteration: implement `gate` deliberately, as planned core scope (protocol
§10 resolved decision 4 established quay-github as the V_meta transfer
target specifically to prove methodology transfer to a second, structurally
different Provider) — not as manufactured busywork, but as the acknowledged
next scheduled increment now that organic discovery has genuinely
plateaued (iteration 16 §10).

**What "gate" means operationally, established by reading quay-native's own
`store.js#check()` before designing this task (not assumed from the design
doc alone):** for a `todo`-status task, the `author->ready` gate requires
all four artifact sections (Proposal/Plan/AC/DoD) present with real content
(≥ `MIN_SECTION_CHARS` non-whitespace chars each) AND the AC section to
contain at least one checkbox AND all AC checkboxes checked (`- [x]`), per
QN-019's iteration-8 tightening. For a `ready`-status task, the
`execute->done` gate requires the same full-checked-AC-checkbox condition
(compound-awareness — QN-012/QN-016's children-status recursion — is
explicitly OUT of scope for this task, see Scope below). `done`-status
tasks are a terminal, unconditional pass (`ok:true, reason:"terminal"`) for
primitives. This is the exact semantic quay-github must replicate against
its own primitive (GitHub Issues has no compound/epic concept in this
experiment's usage to date — no GitHub-backed task has ever had
`children`), using GitHub's own actual data model, not native's file-based
one.

**Design choice — issue body checkboxes, not labels (resolved, not left
open):** DESIGN.md §3 already establishes that `quay-github` derives
`children` from `- [ ] #N` / `- [x] #N` checkbox lines in an issue's *body*
(the task-list-checkbox convention), and that reading logic
(`extractChildRefs` in `github-client.js`) is already live, tested
infrastructure. The natural, minimal-normalization-cost mapping for the AC
gate is therefore the **same mechanism, reused**: quay-github issues follow
the identical four-heading Markdown convention (`## Proposal` / `## Plan`
/ `## AC` / `## DoD`) in their body that native tasks use in their file
body — this experiment's own GitHub issues (mirroring QN-001..QN-027) are
already written this way, confirmed by inspection of the live repo's issue
bodies via `gh issue view`. A GitHub-Issues-native alternative (e.g.
`status:*` labels, or a separate `gate:passed` label) was considered and
rejected: labels have no room for structured, machine-checkable per-item
content (a label is a boolean tag, not a checklist), whereas the issue body
already carries real Markdown checkboxes GitHub itself renders as
interactive checkboxes in its UI — this is the closest GitHub primitive to
native's own AC-checkbox gate semantic, and it costs zero new
normalization convention (the four-heading/checkbox parsing logic is
structurally identical to native's `extractSection`/checkbox-regex
approach, applied to `issue.body` instead of a task file's body).

**Scope discipline (G5 — walking-skeleton, do not gold-plate):**

- Implement ONLY `todo->ready` and `ready->done` gate semantics for
  **primitive** (non-compound) GitHub-backed tasks. quay-github has never
  had a compound/epic task in this experiment (`children` has always been
  empty for every real GitHub issue used so far) — extending
  `childrenStatus`-equivalent recursive compound-awareness (QN-012/QN-016's
  native-side work) to GitHub tasks with zero real compound-task evidence
  to test against would be exactly the kind of anticipatory gold-plating
  G5 forbids. If a compound GitHub task is later authored, that is a
  distinct, separate follow-up task, not this one.
- Do NOT implement `skill` (status→Skill map / action buttons) in this
  task. That is a structurally separate increment (routing/orchestration,
  not gate mechanics) and, per the dispatch's explicit instruction, is
  authored as its own distinct follow-up task if it later proves needed —
  not folded into this task's scope even if it turns out to be "nearly
  free," since gate and skill are different capabilities in `provider.yml`
  and conflating them would blur exactly the kind of provenance/scope
  clarity this experiment's methodology depends on.
- Do NOT change native's own `store.js#check()` gate logic. This task
  ports the *semantic*, it does not touch the reference implementation.
- Do NOT wire `quay task check --provider github` end-to-end against a
  real live GitHub issue as part of this task's AC unless time/scope
  allows within this iteration; if it does not fully complete, report
  honestly (author done, execute partial) rather than forcing a fake
  `done` status — per this iteration's explicit dispatch instruction.

## Plan

1. **Phase 1 — `github-client.js`: add `checkGate(issue)` (or equivalent
   pure function), mirroring `store.js#artifactSections`/`check()`'s
   logic exactly, adapted to operate on `issue.body` (a GitHub issue's
   raw body text) instead of a native task file's body.**
   - Reuse the same four-heading regex approach as native's
     `extractSection`/`artifactSections` (Proposal/Plan/AC/DoD headings,
     `MIN_SECTION_CHARS` content-length floor, `- [ ]`/`- [x]` checkbox
     counting in the AC section) — this is a direct, mechanical port, not
     a redesign; the two implementations should be structurally
     comparable side-by-side (same regex shapes, same constant), each
     living in its own package (no cross-package `import` — Providers do
     not share code beyond the ABI, per design's Provider-independence
     principle).
   - Given a view-model task (canonical shape, `status` already derived
     per DESIGN.md §3) and its raw `body`, compute the same
     `{gate, ok, reason, acTotal, acChecked}` shape native's `check()`
     returns for `todo` and `ready` statuses; `done` status returns the
     unconditional terminal pass (no children-recursion, per Scope).
2. **Phase 2 — `mcp-server.js`: register `task_check`.** Mirrors native's
   own `task_check` tool name/schema (`{id: string}` input,
   `structuredContent` output) exactly — same ABI shape, so Core's
   already-existing, provider-agnostic `taskCheck()` passthrough
   (`provider-client.js`, added QN-027) requires zero changes to talk to
   this Provider (the actual reusability proof this task exists to
   produce). Update `provider.yml`: `gate: true`.
3. **Phase 3 — `bin/quay-github.js`: add `task check <id>` CLI
   subcommand**, calling the same underlying function as the MCP tool
   (ABI symmetry, same convention as QN-024's `task edit`).
4. **Phase 4 — test coverage**: a new
   `packages/quay-github/test/gate.test.mjs`, following the exact
   conventions of `packages/quay-native/test/gate-correctness.test.mjs`
   (injectable fixtures, no live `gh api` calls in the automated test —
   same pattern QN-014's `pageIssues` and QN-024's `write.test.mjs`
   already established for this package) — cover: (a) all-four-sections
   present + all AC checked → `todo` gates `ok:true`; (b) AC checkboxes
   present but not all checked → `todo` gate fails with the correct
   reason string; (c) missing/short sections → fails with "missing
   artifacts" reason; (d) `ready` status with fully-checked AC → `ok:true`
   (`execute->done`); (e) `ready` status with partially-checked AC →
   `ok:false` with the correct N/M reason; (f) `done` status → terminal
   unconditional pass, matching native's own `check()` terminal branch.
5. **Phase 5 — live verification, if time allows within this iteration.**
   Run `node packages/quay-github/bin/quay-github.js task check <id>
   --json` against a real issue in `yaleh/quay` whose body already
   follows the four-heading convention, and independently confirm the
   JSON shape matches native's own `task check --json` output shape
   (same keys: `id`, `gate`, `ok`, `reason`, and `acTotal`/`acChecked`
   where applicable) — the actual abi_symmetry evidence this task
   produces for a second Provider. If this live step cannot be completed
   within this iteration's scope, defer it explicitly and report the task
   as partially executed (author done, execute in progress) rather than
   forcing completion.
6. **Phase 6 — self-audit + gate.** Re-verify every AC item against real
   command output before checking any box. Run `quay-native task check
   QN-028 --json`; if `ok:true`, drive `todo->ready` via `quay:author`'s
   method, then attempt `ready->done` via `quay:execute`'s method within
   this same iteration if time/scope allows.
