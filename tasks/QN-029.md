## Proposal

Iteration 17 (QN-028) implemented quay-github's `gate` capability and left
`skill` (status→Skill map / action buttons) as an explicitly separate,
deliberately-deferred follow-up. Iteration 18's own re-check of
`packages/quay-native/skills/author/SKILL.md` and `.../execute/SKILL.md`
(read in full before scoping this task, not assumed from the design doc)
found a concrete, real fact that must be named honestly before this task's
scope is set: **both Skills are hardcoded to `quay-native task ...` CLI
invocations** (`quay-native task get`, `quay-native task check`,
`quay-native task edit`) at every Method step — they do not currently accept
or honor a provider parameter. This means declaring
`status_skill_map`/`action_buttons` in `quay-github/provider.yml` alone
would be a **config-only, semantically-empty change**: the host
(`quay serve`/`quay action run`) would compose a payload naming
`quay:author`/`quay:execute`, but invoking either Skill against a
GitHub-backed task id would silently operate on `quay-native`'s own local
task store instead (or error, if the id doesn't exist there) — a real bug
class, not a reusability proof. Declaring `skill: true` without fixing this
would be dishonest inflation of the `reusability` V_meta component.

The correct, narrowly-scoped fix (this task's actual deliverable):
parameterize both Skills to take an optional `provider` argument (default
`native`, preserving all existing behavior and all prior provenance
records unchanged), and have every Method step invoke
`quay task <cmd> --provider <provider>` (Core's already-existing,
provider-agnostic CLI — see `packages/quay/bin/quay.js`'s `withProvider`
helper, live since QN-024/QN-027) instead of hardcoding `quay-native task
<cmd>` directly. This makes the Skills genuinely provider-transferable
using infrastructure that already exists and needs no new code in Core
itself — the same "zero Core-side branching" bar QN-024/QN-027/QN-028 each
met for their own ABI surfaces. Once this parameterization is real (not
just declared), `quay-github/provider.yml` can honestly flip `skill: true`
and declare its own `status_skill_map`/`action_buttons` (identical shape to
native's own, since the Skills are now the same two Skills, just told which
provider to target) — completing the "contract proven" gap protocol §7
criterion 3 names (native + GitHub Provider both running the *complete*
methodology, not just individual ABI surfaces).

**Precedent for this scope choice:** QN-028 explicitly declined to fold
`skill` into its own scope, precisely so this distinct capability's real
cost (a Skill-level fix, not a provider.yml-level one) would not be hidden
or downplayed. This task makes that real cost visible and pays it once,
generically, rather than writing a second, GitHub-specific pair of Skills
that would duplicate `quay:author`/`quay:execute`'s entire Method and
create a maintenance-divergence risk the parameterized-Skill approach
avoids.

## Plan

1. **Phase 1 — parameterize `quay:author`.** Edit
   `packages/quay-native/skills/author/SKILL.md`: add an optional
   `provider` argument to the Skill's invocation contract (documented in
   the Spec block, default `native`); replace every `quay-native task
   get/check/edit` invocation in the Method steps with
   `quay task <cmd> --provider {{provider}}` (Core's generic CLI). Add an
   honesty note explaining the change and citing this task.
2. **Phase 2 — parameterize `quay:execute`.** Same treatment for
   `packages/quay-native/skills/execute/SKILL.md`.
3. **Phase 3 — regression-check native-provider invocation is
   byte-for-byte unchanged.** `quay task get/check/edit <id> --provider
   native --json` must produce identical output to
   `quay-native task get/check/edit <id> --json` directly (this is Core's
   existing passthrough contract, already proven by QN-024/QN-027/QN-028
   for `data.write`/`gate` — this task extends the same proof to the
   Skill-invocation layer, not the ABI layer). No existing provenance
   record or prior iteration's `native`-mode evidence is invalidated by
   this change.
4. **Phase 4 — declare quay-github's `skill` capability.** Flip
   `packages/quay-github/provider.yml`'s `skill: false` → `true`. Add
   `status_skill_map` (identical `todo: "quay:author"`, `ready:
   "quay:execute"` mapping as native's own) and `action_buttons` (same
   `advance` button shape as native's own — Core's `composePayload`
   already reads these fields generically per-Provider, confirmed by
   reading `packages/quay/src/action.js` in full: zero Provider-specific
   branching exists there).
5. **Phase 5 — live verification.** Drive one real GitHub issue's gate
   check via the parameterized `quay:author` Method steps
   (`quay task check <id> --provider github`), confirming the Skill's
   own steps now correctly target quay-github when invoked with
   `provider: github` — this is the concrete reusability/transfer proof
   this task exists to produce, at the Skill-invocation layer (a level
   QN-028 explicitly did not reach).
6. **Phase 6 — test coverage.** No new automated test file is needed if
   Phase 3's regression check (byte-identical native-mode output) is
   itself captured as a script/verbatim run in the iteration report —
   Skill `.md` files are prompts, not code, so "testing" them means
   demonstrating the actual invocation sequence runs correctly against
   both providers, which Phase 3 (native) + Phase 5 (github) together
   cover. If a lightweight automated regression test is easy to add for
   the underlying `--provider` CLI flag itself (not the Skill prose), add
   it; do not force one if it would only duplicate QN-024/QN-027/QN-028's
   existing provider-flag tests.
7. **Phase 7 — self-audit + gate.** Re-verify every AC item against real
   command output. Drive `QN-029` itself through `quay:author`'s
   (newly-parameterized, `provider: native` default) Method to `ready`,
   then `quay:execute`'s Method to `done` within this same iteration if
   time/scope allows.

## Scope discipline (G5 — walking-skeleton, do not gold-plate)

- Do NOT write new, separate GitHub-specific Skills. Parameterize the
  existing two Skills — this is the minimal change that makes them
  genuinely provider-transferable, per this task's own Proposal reasoning
  about duplication risk.
- Do NOT extend this task to cover compound/epic GitHub tasks — no real
  compound GitHub-backed task has ever existed in this experiment (same
  scope boundary QN-028 already established for `gate`); `executeEpic`'s
  provider-parameterization, if ever needed, is a distinct future task.
- Do NOT change Core's `provider-client.js`/`bin/quay.js` — the generic
  `--provider` flag and `withProvider` passthrough already exist
  (QN-024/QN-027); this task only changes which CLI invocation the two
  Skill `.md` files' prose specifies, plus quay-github's own
  `provider.yml` declaration.
- Do NOT attempt to wire manda/action-button delivery end-to-end against
  a real Claude Code session picking up a GitHub-sourced trigger — that
  is the same environmental-limitation surface already documented (no
  subagent-dispatch primitive found, standing finding across 17
  iterations) and is out of scope for this task's own AC.
