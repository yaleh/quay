## Proposal

`store.js`'s `check()` gate (design §3) has, since iteration 2 (QN-005), an
explicit code comment stating a deliberate architectural boundary: the gate
mechanically verifies checkbox **presence** and **checked-state** only, "not
attempting semantic quality scoring (out of scope for a mechanical gate; that
is what independent review/audit is for, per design §3/G3)." This boundary —
referred to across 9+ iterations' reports as "the checkbox-count-gameability
gap" — has been named in prose repeatedly (iterations 9, 11, 12, 13, 16, 17,
18, 19) but has **never been demonstrated by a live, executable test**. It
has only ever been asserted, not proven.

This task closes that specific, narrow gap: not by "fixing" the gate (which
is impossible for a purely mechanical checkbox-parser — verifying that a
checked box's underlying claim is *true* requires either running the actual
work being claimed, which is task-specific and out of a generic gate's
reach, or an LLM-level semantic judgment, which is explicitly what G3's
independent audit exists to provide instead of the gate itself), but by
writing an adversarial regression test that mechanically demonstrates the
gate accepting a task whose AC checkbox is checked while the underlying
claim is provably false (e.g. an AC item claiming "the regression suite
passes" while, in the same fixture, a sibling assertion shows the suite
does not). This converts a 9-iteration-old prose assertion into a concrete,
reproducible, executable artifact — directly strengthening the evidence
basis for `gate_correctness`'s honest score without pretending to close an
unfixable gap.

**Why this is not gold-plating / busywork (G5):** this is not adding a new
mechanical check that would make the gate stricter (that would either (a) be
impossible in general, as argued above, or (b) require task-specific
semantic verification incompatible with a generic gate). It is closing a
documentation-to-executable-proof gap for a limitation that has been
repeatedly *asserted* but never *demonstrated live* — the same kind of
"convert a prose claim into a live, adversarial, reproducible check" pattern
QN-007's adversarial re-break-then-restore test and QN-015's genuinely-hard
CAS-primitive test both already established as valuable precedent in this
experiment's own history.

## Plan

1. Add a new test file `packages/quay-native/test/gate-gameability.test.mjs`
   demonstrating, live:
   - A task fixture at `ready` status whose AC section contains a checked
     box asserting a specific, checkable claim (e.g. "the regression suite
     passes with zero failures").
   - The claim is, in fact, false for this fixture (constructed so a real
     check of the claim — e.g. actually running a trivial assertion — would
     fail), yet `store.check()` still reports `ok: true` for the
     `execute->done` gate, because it only inspects checkbox syntax, never
     the claim's truth.
   - A second case showing the same for the `author->ready` gate (an AC
     item falsely claiming a precondition that is demonstrably not met in
     the same fixture).
2. Add a code comment cross-reference in `store.js`'s `check()` (near the
   existing `MIN_SECTION_CHARS`/artifactSections comment) pointing at the
   new test file, so a future reader finds the live proof, not just prose.
3. Update this task's own body with a `## Gaps` note (mirroring the pattern
   used by `quay:author`/`quay:execute`'s own SKILL.md Gaps sections)
   stating explicitly: this test proves the boundary exists; it does not
   and cannot close it; G3's independent, out-of-band audit remains the
   actual mechanism compensating for it, unchanged.
4. Re-run the full regression suite (all pre-existing test files across
   quay-native/quay-github/quay) to confirm zero regressions.

## Gaps (honestly declared, not hidden)

This task **proves** the checkbox-count-gameability boundary exists; it does
**not** and **cannot** close it. A generic mechanical gate (`store.js`'s
`check()`) can verify checkbox syntax (presence, checked-state) but not the
semantic truth of the claim behind a checked box — doing so in general would
require either running the specific work each claim describes (task-specific,
out of a generic gate's reach) or an LLM-level judgment call, which is
exactly what G3's independent, out-of-band audit exists to provide instead
of the gate itself (protocol §6: "the gate is both contestant and judge").

This is why the experiment's convergence criteria (protocol §7) require
**both** a green mechanical gate **and** a separate out-of-band audit for
every σ lift (criterion 4), and why G4 (Trusting Trust) insists fixpoint
reproduction alone never substitutes for correctness. `gate-gameability.test.mjs`
is a permanent regression fixture recording this boundary, not a step toward
removing it. Future work that wants a *stronger* gate should treat that as a
new, separately-justified architectural decision (e.g. "should `check()` gain
task-specific verification hooks, and does that reintroduce the
contestant-and-judge problem at a different layer?") — not a bug fix to this
test.
