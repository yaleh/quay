## Proposal

`packages/quay/src/serve.js` (`startServer`) and `packages/quay/src/action.js`
(`composePayload`/`deliverTrigger`/`mandaAvailable`) are the literal running
code behind the `skeleton` V_instance factor — the v0 loop's own definition
(protocol §5.1: "the v0 loop runs end-to-end (`config → mcp → serve → action
→ Skill → done`)"). `skeleton` has been scored 0.60 and held flat since
iteration 4 (16 consecutive iterations, confirmed by grepping every prior
iteration report's own `skeleton:` line). Despite this, **no automated
regression test file exists anywhere in the repo for `serve.js` or
`action.js`** — confirmed this iteration by grepping every `*.test.mjs`/
`*.mjs` test file across `packages/quay-native/test/`, `packages/quay/test/`,
and `packages/quay-github/test/` for any reference to `serve.js`,
`startServer`, `composePayload`, `deliverTrigger`, or `mandaAvailable`: zero
hits. The list/detail HTTP view and the action-button trigger-composition
logic have only ever been exercised by a **manual** curl/browser walkthrough,
once, in iteration 0 (`experiment/timing/iteration-0.log`'s "full v0 loop
re-verified end-to-end via quay serve Web UI" checkpoint) — and never
re-verified live by an automated, re-runnable check since.

This is the same class of gap QN-030 closed for `gate_correctness`
(iteration 20): a component whose behavior has been asserted/relied-upon
across many iterations' `skeleton: 0.60 (unchanged)` lines, but never
converted into a live, re-runnable, executable proof. Per iteration 20's own
"Problems identified for next iteration" item 2 (check whether `skeleton`/
`abi_symmetry`/`skill_convergence` have similarly-scoped "prose claim never
demonstrated live" gaps, using the same search pattern that found QN-030),
this iteration performed that exact search and found this gap on the
`skeleton` axis specifically (not `abi_symmetry`, which already has
`abi-symmetry.mjs`, and not `skill_convergence`, which is exercised by every
Skill-driven task's own dispatch).

**Why this is not gold-plating / busywork (G5):** this does not add new
runtime behavior to `serve.js`/`action.js` — it writes a regression test
proving the *existing* list → detail → action-button → trigger-delivery
chain actually works, mechanically, right now, so that a future change
cannot silently break the v0 loop without a red test catching it. This is
squarely `skeleton` evidence-quality work, the same kind of increment
QN-030 was for `gate_correctness`.

## Plan

1. Add a new test file `packages/quay/test/serve.test.mjs`:
   - Start a real `startServer()` instance (from `serve.js`) against a
     temporary, isolated tasks directory (mirroring the isolation pattern
     `task-check.test.mjs` already uses for `provider-client.js`), backed by
     a real `quay-native mcp` child process (not mocked) — spun up over
     stdio the same way `abi-symmetry.mjs`/`task-check.test.mjs` already do.
   - `GET /`: assert 200, assert the response body contains the seeded
     task's id/status/role/title (real HTML string match, not a snapshot).
   - `GET /task/<id>`: assert 200, assert the action button for the task's
     current status is rendered (per `provider.yml`'s `action_buttons`/
     `whenStatus` filter) — and, separately, seed a second task at a status
     with **no** matching action button and assert the button is correctly
     *absent* (a negative control, mirroring QN-030's own GAME-C
     discipline).
   - `GET /task/<nonexistent-id>`: assert 404.
   - `POST /task/<id>/action/<actionId>`: assert a 302 redirect back to the
     task's detail page, and assert `composePayload`'s output shape
     (`label`/`payload`/`skill`/`taskId`/`status`) is correct for a real
     task/manifest pair — using `action.js`'s real `composePayload` function
     directly (not stubbed), and stub only the actual manda subprocess call
     (`deliverTrigger`'s `execFileAsync`) since a live manda dispatch itself
     is out of scope for this test (this iteration is not re-testing manda
     delivery, only the HTTP/composition chain that feeds it).
2. Run the new test, live, and confirm it passes for real.
3. Adversarially confirm the test has teeth: temporarily break one assertion
   target (e.g. comment out the `action_buttons` filter in `serve.js`, or
   break the 404 branch) and confirm the test fails with a clear diagnostic,
   then restore and confirm it passes again — mirroring QN-007/QN-030's own
   break/restore discipline.
4. Re-run the full regression suite (all pre-existing test files across
   quay-native/quay-github/quay) to confirm zero regressions.

## Gaps (honestly declared, not hidden)

This test proves the HTTP list/detail/action-button chain (`serve.js`) and
`composePayload()` (`action.js`) work mechanically, live, against a real
quay-native MCP process. It does **not** verify:

- **Real manda dispatch.** `deliverTrigger()`'s `haveManda === true` branch
  (an actual `manda send` call reaching a real channel/subscriber) is not
  exercised — this test's isolated `workspaceRoot` has no `.manda` config,
  so `mandaAvailable()` genuinely (not by a stub) returns `false`, and the
  "degraded: print the command" branch is what actually runs and is
  verified. Exercising the real-manda branch would require this test to
  spin up or connect to a live manda daemon scoped to a throwaway
  workspace — out of scope for this task; each iteration's own G6
  precondition check already separately confirms manda is live for the
  real workspace.
- **Browser-level rendering.** Only raw HTTP response bodies are asserted
  (string containment on the returned HTML), not actual browser DOM
  rendering, CSS, or JS execution (there is none — `serve.js`'s own header
  comment states "no framework, no styling," consistent with G5's
  walking-skeleton discipline).
- **Concurrent requests / load.** This test issues requests sequentially;
  it does not test the HTTP server under concurrent load (out of scope for
  a v0 walking skeleton test; `lock.test.mjs`/`cas-write.test.mjs` already
  cover concurrency at the store layer, which is the actual risk surface).

None of these gaps were in this task's own AC/DoD scope; they are named
here so a future reader does not mistake this test for full end-to-end
coverage of the action-button-to-manda-to-Skill delivery chain — only the
HTTP-and-composition half of it, up to (but not including) the manda
subprocess call itself.
