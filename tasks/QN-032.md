## Proposal

`packages/quay/src/config.js` (`findConfig`, `loadConfig`, `activeProvider`)
is the literal first link in the `skeleton` V_instance factor's own chain
(protocol §5.1: "the v0 loop runs end-to-end (`config → mcp → serve → action
→ Skill → done`)") — `.quay/config.yml` **is** "config" in that chain. Despite
this, **no automated test anywhere in the repo directly exercises
`config.js`** — confirmed this iteration by grepping every `*.test.mjs` file
across `packages/quay-native/test/`, `packages/quay/test/`, and
`packages/quay-github/test/` for `findConfig`, `loadConfig`, or
`activeProvider`: the only hit is `packages/quay/test/serve.test.mjs`
(QN-031, iteration 21), and that hit is purely incidental — `serve.test.mjs`
writes one single, always-valid throwaway `.quay/config.yml` so that
`startServer()`'s internal call to `loadConfig()`/`activeProvider()`
succeeds; it does not call `config.js`'s exports directly, and it never
exercises any of the module's three error-throwing branches or its
directory-upward-search behavior.

Concretely, reading `config.js` fresh this iteration (not from memory) finds
**three untested error paths and one untested search behavior**:

1. `findConfig()` walks from `startDir` upward looking for `.quay/config.yml`,
   stopping at the filesystem root (`path.dirname(dir) === dir`) and
   returning `null` if none is found. The upward-search-across-multiple-
   directory-levels behavior itself (not just "cwd has one") has never been
   exercised.
2. `loadConfig()` throws `"no .quay/config.yml found (searched from ...
   upward)..."` when `findConfig()` returns `null`. Never triggered by any
   test.
3. `activeProvider(cfg, id)` throws `` `no such provider "${id}" in
   .quay/config.yml` `` when an explicit `id` is given but not present in
   the config's `providers` map. Never triggered by any test.
4. `activeProvider(cfg)` (no `id` argument) throws `"no enabled provider in
   .quay/config.yml"` when no provider in the map has `enabled: true`. Never
   triggered by any test.

This is the same class of gap QN-031 (iteration 21) and QN-030 (iteration
20) closed on the `skeleton`/`gate_correctness` axes respectively: real,
shipped logic — including three distinct user-facing error messages a real
operator could hit (a missing config file, a typo'd `--provider` id, or a
config with every provider disabled) — has zero automated regression
coverage and has only ever been exercised implicitly, as an accidental
side-effect of another task's happy-path fixture (QN-031's `serve.test.mjs`).
This is exactly the "asserted/relied-upon but never converted to a live,
re-runnable, executable proof" pattern named in iteration 21's own "Problems
identified for next iteration" item 2 (check whether skeleton's remaining
scope beyond serve.js/action.js — explicitly naming "`.quay/config.yml`'s
own parsing/validation" — has a similar gap).

**Why this is not gold-plating / busywork (G5):** this adds no new runtime
behavior to `config.js` — it writes a regression test directly targeting the
module's existing exported functions and their existing error paths, so a
future change (e.g. refactoring the upward-search loop, or changing an error
message) cannot silently break the v0 loop's config-loading link without a
red test catching it.

## Plan

1. Add a new test file `packages/quay/test/config.test.mjs`, unit-level
   (no HTTP server, no MCP child process needed — `config.js` has no such
   dependency), covering:
   - `findConfig()`: create a nested temp directory tree (e.g.
     `tmp/a/b/c`), write `.quay/config.yml` only at `tmp/a`, call
     `findConfig("tmp/a/b/c")` and assert it returns the path at `tmp/a`
     (proves the upward, multi-level search actually walks parents, not
     just checks `startDir` itself).
   - `findConfig()` negative case: call it against a directory tree with no
     `.quay/config.yml` anywhere in its ancestry (an isolated temp dir with
     no `.quay` at any level up to a safe stopping point) and assert it
     returns `null`.
   - `loadConfig()`: happy path — a valid `.quay/config.yml` — assert the
     returned `{ config, configPath, workspaceRoot }` shape is correct
     (`workspaceRoot` is two directories up from `configPath`, per the
     source: `path.dirname(path.dirname(configPath))`).
   - `loadConfig()` error path: call it against a directory with no
     `.quay/config.yml` in its ancestry and assert it throws, and that the
     thrown message contains `"no .quay/config.yml found"`.
   - `activeProvider(cfg, id)`: happy path with explicit `id` matching a
     provider in the map (including one that is `enabled: false`, per the
     source comment: "Explicit-id selection does not require the provider
     to be `enabled: true`") — assert the returned object has `id` plus the
     provider's own fields spread in.
   - `activeProvider(cfg, id)` error path: explicit `id` not present in the
     map — assert it throws with a message containing `no such provider`.
   - `activeProvider(cfg)` (no `id`): happy path — exactly one provider has
     `enabled: true` — assert that provider is returned.
   - `activeProvider(cfg)` error path: no provider has `enabled: true` (all
     `false`, or an empty `providers: {}` map) — assert it throws with a
     message containing `no enabled provider`.
2. Run the new test, live, and confirm it passes for real (all cases).
3. Adversarially confirm at least one case has real teeth: temporarily
   break `activeProvider`'s enabled-lookup (e.g. change `providers[pid].
   enabled` to `!providers[pid].enabled`) and confirm the "happy path, no
   id" assertion now fails with a clear diagnostic; restore and re-confirm
   it passes — mirroring QN-007/QN-030/QN-031's own break/restore
   discipline.
4. Re-run the full regression suite (all pre-existing test files) to
   confirm zero regressions.

## Gaps (honestly declared, not hidden)

This test proves `findConfig()`'s multi-level upward search (both
directions), `loadConfig()`'s happy path and its "no config found" error
path, and all four of `activeProvider()`'s paths (two happy, two error) work
mechanically, live, against the real, unmodified `config.js` module. It does
**not** verify:

- **Malformed YAML.** `loadConfig()` calls `YAML.parse(raw)` with no
  try/catch of its own — if `.quay/config.yml` contains syntactically
  invalid YAML, the `yaml` package's own parse error propagates unmodified.
  This test does not exercise that path; it was not in scope (the module
  itself does no validation or wrapping of this case — testing it would
  really be testing the `yaml` dependency's own error behavior, not
  `config.js`'s own logic).
- **Filesystem permission errors.** `fs.readFileSync(configPath, "utf8")`
  will throw a Node.js `EACCES`-style error if the file exists but is
  unreadable (e.g. wrong permissions). Not exercised — this is standard
  Node.js `fs` behavior, not `config.js`'s own logic, and simulating it
  portably (permission semantics differ across environments) was judged out
  of scope for this task's aim (closing the "zero coverage of this module's
  own branching logic" gap, not achieving exhaustive OS-level fault
  injection).
- **`config.yml` with a non-object `providers` value** (e.g. `providers:
  "oops"` — a string instead of a map). `activeProvider()`'s
  `cfg.config.providers ?? {}` would pass a string through unchanged into
  `Object.keys(...)`, which would iterate its numeric-index characters
  rather than throwing — a real, if obscure, malformed-input edge case not
  covered here. Named honestly as a possible future increment, not treated
  as in-scope for this task (it was not identified until after the eight
  planned cases were already written and passing; adding a ninth,
  differently-shaped case at this point would expand scope beyond what was
  authored, per G5 — better to name it than silently add or silently
  ignore it).

None of these gaps were in this task's own AC/DoD scope; they are named here
so a future reader does not mistake this test for exhaustive coverage of
every conceivable malformed-input or OS-fault path through `config.js` —
only its own three exported functions' documented, in-scope logic branches.
