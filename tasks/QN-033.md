## Proposal

`packages/quay/bin/quay.js` — the Core CLI binary (`quay task list/view/edit/
check`, `quay action list/run`, `quay serve`, plus `parseFlags()`,
`resolveProviderEnv()`, `withProvider()`, and the top-level `main().catch(...)`
error handler) — has **zero automated test coverage anywhere in the repo**,
confirmed this iteration by grepping every `*.test.mjs` file under
`packages/quay-native/test/`, `packages/quay/test/`, and
`packages/quay-github/test/` for any reference to `bin/quay.js` or a spawn of
it: zero hits. This is a genuine, non-manufactured gap of the same class
QN-030 (gate_correctness), QN-031 (skeleton/serve+action), and QN-032
(skeleton/config) each closed on other axes — found by following iteration
22's own explicit pointer to check "`bin/quay.js`'s own top-level dispatch/
error-handling `main().catch(...)` block" as a residual, unsearched part of
`skeleton`'s chain.

Contrast with its sibling: `packages/quay-native/bin/quay-native.js` (the
Provider-side CLI) is exercised extensively via `execFileSync`/`execFileAsync`
subprocess spawns across `abi-symmetry.mjs`, `create-validation.test.mjs`,
`serve.test.mjs`, and `task-check.test.mjs`. But every one of those tests
that touches Core's own logic (`serve.test.mjs`, `task-check.test.mjs`)
imports Core's `src/*.js` modules directly (`startServer`, `composePayload`,
`connectProvider`) — none of them spawns `bin/quay.js` itself as a child
process. So the CLI dispatch layer itself — argv parsing via `parseFlags()`,
the `cmd === "task" && sub === "..."` branch table, the `action list`/
`action run` branches, the `serve` branch's own argv-reparsing quirk
(`process.argv.slice(3)`, noted in the source as necessary because `serve`
has no subcommand token), `resolveProviderEnv()`'s relative-vs-passthrough
path resolution, `--json` flag handling per branch, the "no such task"/
"missing required --status" error paths, and `main()`'s own top-level
`usage:` fallback and `.catch()` stack-trace handler — is entirely untested,
relying silently on manual/incidental use across every iteration that has
ever run `quay task ...`/`quay action ...` from a shell.

This is not gold-plating (G5): no new runtime behavior is proposed, only
test coverage of already-shipped, already-working CLI dispatch code, via a
real subprocess spawn of the actual binary (the only way to test argv
parsing and the `main().catch` handler, which by construction cannot be
imported and called as a plain function the way `src/*.js` exports can).

## Plan

Add `packages/quay/test/cli.test.mjs`, following the exact isolation pattern
`task-check.test.mjs`/`serve.test.mjs` already established, adapted for the
fact that `bin/quay.js`'s `withProvider()` reads `.quay/config.yml` via
`loadConfig()`, which walks upward from CWD looking for `.quay/config.yml`.
So the test spawns `node bin/quay.js ...` with `cwd` set to a temporary
directory that has its own real `.quay/config.yml` (pointing at the real
native Provider's `mcp_entry`, with an isolated `tasks_dir` env value) —
mirroring the shape of the real repo's own `.quay/config.yml`, but isolated
per-test so it never touches the repo's own `tasks/` directory.

Cases to cover (each a real `execFileSync`/`execFileAsync` spawn of
`bin/quay.js`, not an import):
1. `quay task list --json` — lists tasks from the isolated store, confirms
   JSON array shape and non-JSON tab-separated fallback format.
2. `quay task view <id> --json` — happy path; and the "no such task" error
   path (unknown id) with correct stderr message + exit code 1.
3. `quay task edit <id> --status ready --json` — happy path status-only
   write; and the "missing required --status" error path (exit 1, no
   provider call attempted).
4. `quay task check <id> --json` — both ok:true and ok:false gate results,
   confirming exit code mirrors `result.ok` (0 vs 1) — this is `main()`'s own
   `process.exitCode = result.ok ? 0 : 1` line, distinct from what
   `task-check.test.mjs` already covers (that test calls `provider-client.js`
   directly, never through this CLI's own exit-code-setting branch).
5. `quay action list <id> --json` — confirms the manifest's `action_buttons`
   are correctly filtered by `whenStatus` against the task's live status.
6. `quay action run <id> advance --json` — confirms `composePayload()` is
   invoked with real manifest+task data and `deliverTrigger()`'s degraded
   (no-manda... or manda-present, whichever the test env yields) path is
   reached without throwing; assert the JSON output includes the expected
   `skill`/`channel`/`delivered` fields.
7. An unknown top-level command (e.g. `quay bogus`) — confirms the
   `usage: quay <task list|view|edit|check|action list|run|serve> ...`
   fallback + exit code 1.
8. `resolveProviderEnv()`'s relative-path resolution — confirmed indirectly:
   since `.quay/config.yml`'s `env.QUAY_NATIVE_TASKS_DIR` uses a `./`-relative
   path in the fixture config, a successful `task list` against a real
   isolated tasks dir is itself the proof this function correctly resolves
   the relative env value against `workspaceRoot` (if it resolved wrong, the
   spawned `quay-native mcp` subprocess would read from the wrong/empty dir
   and `task list` would return 0 unexpected tasks instead of the seeded
   ones).

An adversarial break/restore cycle will be performed live (mirroring
QN-007/QN-030/QN-031/QN-032 precedent): temporarily break one assertion's
target behavior (e.g. invert the `result.ok ? 0 : 1` exit code logic in
`bin/quay.js`), confirm the test correctly fails, then restore from a backup
copy and confirm a byte-identical diff and full green re-run.

## Gaps (named honestly, not hidden)

- `resolveProviderEnv()`'s absolute-path passthrough branch (values that do
  NOT start with `./` or `../`, e.g. `"owner/repo"` for the github Provider's
  `QUAY_GITHUB_REPO`) is not directly exercised by this task, since the
  native Provider fixture used here has no such env value — this remains a
  narrow, named residual gap for a possible future increment, not silently
  claimed as covered.
- `quay serve`'s own CLI entrypoint (the `cmd === "serve"` branch, including
  its `process.argv.slice(3)` re-parse quirk) is out of scope for this task;
  `serve.js`'s own HTTP behavior is already covered by QN-031's
  `serve.test.mjs`, but that test imports `startServer` directly and never
  spawns `bin/quay.js serve` itself — this remains a small, named residual
  gap, distinct from (and narrower than) this task's own AC scope, which
  focuses on `task`/`action` dispatch, not `serve`'s own CLI branch.
