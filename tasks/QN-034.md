## Proposal

`packages/quay-github/bin/quay-github.js` — the GitHub Provider's own CLI
dispatch layer (`resolveRepo()`, `parseFlags()`, the `cmd`/`sub` branch
table for `mcp`/`manifest`/`task list|get|edit|check`, and the top-level
`main().catch(...)` handler) — has **zero automated test coverage anywhere
in the repo**. Confirmed by grepping every `*.test.mjs` file in all three
packages for any reference to `quay-github.js` or a subprocess spawn of it:
zero hits. This is the sibling gap to QN-033 (iteration 23), which closed
the identical class of gap for `packages/quay/bin/quay.js`. Iteration 23's
own "Problems identified for next iteration" named this exact file as a
candidate.

**This is a materially different-shaped task than QN-030/031/032/033**, not
a repeat of the same template with a new filename swapped in:

- Every prior CLI-dispatch test (QN-031, QN-033) span up a **fully
  isolated, disposable local fixture** (a temp `.quay/config.yml` + temp
  tasks dir) with no external dependency. `quay-github.js`'s CLI has **no
  local fixture equivalent** — `createGithubClient()` shells out to the
  real `gh api` for every operation (`list`, `get`, `setStatus`, `check`);
  there is no dependency-injection seam in the CLI binary itself (unlike
  `github-client.js`'s already-tested pure functions, which the existing
  `write.test.mjs`/`pagination.test.mjs`/`gate.test.mjs`/`view-model.test.mjs`
  suite exercises with synthetic fixtures precisely to avoid live network
  calls).
- Therefore closing this gap at the CLI-subprocess level requires either
  (a) live calls against the real `yaleh/quay` GitHub repo, or (b) refactoring
  the CLI for injectability (out of scope — G5, no source change motivated
  by a test-only need). This task takes path (a), but with an explicit,
  load-bearing constraint the existing `write.test.mjs` header comment
  already established for this package: **"this repo's real issue count is
  too small/precious to safely target with destructive live writes in an
  automated, repeatable test file."** This task's scope is therefore
  deliberately restricted to CLI surfaces that are provably read-only or
  fail before any write call is reached — `task edit --status <s>` (the
  only write-capable CLI verb) is exercised **only** via its
  missing-required-flag error path (which returns before `client.setStatus`
  is ever called), never via a real status change to a live issue.

## Plan

1. Read `packages/quay-github/bin/quay-github.js` in full (already done
   this iteration) and confirm exactly which branches are reachable without
   a live write: `manifest`, `task list` (json + non-json), `task get`
   (happy + not-found), `task check` (both ok:true/ok:false against real
   issues #3/#4, whose current status is stable and known), `task edit`
   missing-`--status` error path, unknown `task` subcommand, unknown
   top-level command, and the `QUAY_GITHUB_REPO` malformed-value throw path
   in `resolveRepo()`.
2. Live-probe every one of these branches directly via manual `node
   bin/quay-github.js ...` invocations first (not assumed), to confirm
   exact exit codes / stdout / stderr shapes before encoding them as
   assertions.
3. Write `packages/quay-github/test/cli.test.mjs`, spawning the real
   `bin/quay-github.js` binary via `execFileSync` with `QUAY_GITHUB_REPO`
   pointed at the real `yaleh/quay` repo, asserting on the exact
   exit-code/stdout/stderr shapes confirmed in step 2. No `task edit
   --status <value>` call that would reach `client.setStatus` is ever made.
4. Adversarially break one exit-code line (`task check`'s
   `process.exitCode = result.ok ? 0 : 1` in `bin/quay-github.js`) and
   confirm the test produces live FAILs, then restore from a backup,
   confirm byte-identical restoration via `diff`, and re-run to confirm a
   full green run again.
5. Re-run the full regression suite (all packages) and confirm no
   regressions.
6. Name explicitly, in this task's own body, what remains untested: the
   real `task edit --status <value>` write path itself (`client.setStatus`,
   the label add/remove/close-vs-reopen branches) and the `mcp` subcommand
   (starting the MCP transport) — both out of scope for the reasons above
   (destructive-write risk / stdio-transport process lifecycle,
   respectively).
