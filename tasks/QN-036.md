## Proposal

`docs/proposal/quay-proposal.md` §5's architecture diagram declares three
sibling consumer-layer front-ends over the Provider ABI: Web UI, `quay` CLI,
and an **"MCP projection → Agent"** — with the Core (`quay`) acting as the
single MCP endpoint an Agent (Claude Code) connects to, internally fanning
out as an MCP client to each enabled Provider's own MCP server. A human
directive (`experiment/directives/pending/DIR-007-implement-core-mcp-server.md`,
present at the start of this iteration) found, via direct repo inspection,
that this consumer-facing MCP server does **not exist**: only `quay-native`
and `quay-github` have real MCP server implementations;
`packages/quay/src/provider-client.js` is confirmed to be Core's MCP
**client** side only, and `bin/quay.js` has no `mcp` subcommand at all.

This task implements `quay`'s own MCP server as a genuine, live-verified
capability: a new `mcp` subcommand on `bin/quay.js`, backed by a new
`src/mcp-server.js` that starts a real MCP server (`McpServer` +
`StdioServerTransport`) and internally connects, as an MCP client, to every
Provider currently `enabled: true` in `.quay/config.yml` (reusing
`provider-client.js#connectProvider()` unmodified), proxying/aggregating
`task_list`/`task_get`/`task_write`/`task_check`/`provider://manifest`
back out over the one Core-level MCP endpoint.

## Plan

1. Add `src/mcp-server.js#startMcpServer()`: an `McpServer` instance that,
   for each Provider id in `.quay/config.yml`'s `providers` map with
   `enabled: true`, lazily connects (on first tool call referencing it) via
   `connectProvider()`, caching each connection and closing all of them
   together when the Core server's own stdio transport closes.
2. Multi-Provider disambiguation (explicit decision, not a silent
   single-Provider assumption, per DIR-007 point 2): every proxied tool
   takes an **optional `provider` argument** (omitted → first
   `enabled: true` Provider, same default rule as `config.js#activeProvider()`
   already uses for the CLI's `--provider` flag). `provider://manifest` is
   exposed as a default-Provider alias, plus one real
   `provider://manifest/<id>` resource per enabled Provider (resources are
   uri-identified, not argument-selected, so this differs in mechanism from
   the tools).
3. Wire the `mcp` subcommand into `bin/quay.js` (`cmd === "mcp"` branch,
   paralleling the existing `serve`/`task`/`action` branches), mirroring
   `quay-native`/`quay-github`'s own `mcp` subcommand shape (no flags, no
   sub-token).
4. Live-verify end-to-end against **both real Providers already in this
   repo**: spawn `quay mcp` as a real subprocess, connect a real MCP
   client, and confirm `task_list`/`task_get`/`task_check`/
   `provider://manifest` results are byte-identical to calling each
   Provider's own `mcp` subcommand directly — for native, and for github
   against the real, live `yaleh/quay` repository (temporarily flipping
   `.quay/config.yml`'s `github.enabled` to `true` for the duration of the
   live check only, then restoring it).
5. Write a committed regression test
   (`packages/quay/test/mcp-server.test.mjs`) that reproduces the same
   aggregation/byte-identical proof using two fully local, isolated native
   task stores as two distinct enabled Providers — zero external-network
   dependency in the automated suite, consistent with this package's
   existing test-isolation conventions.
6. Create `packages/quay/DESIGN.md` (did not exist before this task) and
   update `docs/proposal/quay-proposal.md` §5 to reflect the
   now-implemented capability, with the live-verification transcript.
7. Move `DIR-007` to `archive/` with a `## Resolution` section; update
   `experiment/provenance.md` with this task's provenance record and σ
   recomputation.
