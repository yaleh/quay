## Proposal

Iterations 25 and 26 both named the same residual gap for convergence
criterion 3 ("contract proven"): `executeEpic`'s own compound-recursion
path (`quay:execute`'s SKILL.md, `Spec` section — `driveEach` over real
children, followed by `integrationAccept`) has never actually been run
end-to-end as a live `quay:execute` **Skill invocation** driving a real
multi-child epic from `todo` to `done` through the Skill orchestration
layer itself. Every prior compound/epic live-verification (native's
QN-012/QN-016, GitHub's QN-035/DIR-006) exercised only the **gate's own**
compound-recursion logic (`checkGate()`/`childrenStatus()`) via direct,
manual `task check`/`task edit` commands standing in for the Skill, never
`executeEpic`'s own recursive orchestration as an actual Skill-level
drive.

This task is the native-side tracker (this experiment's own backlog
convention: a native task records/tracks a GitHub-Provider-side proof,
mirroring how QN-002/QN-024/QN-028/QN-029/QN-035/QN-036 each had a native
counterpart or were themselves the native-side record for cross-Provider
work) for the actual live drive, which was performed against three real
GitHub issues in this repository: a fresh epic (issue #10, referencing two
fresh children, issues #8 and #9), created live this iteration
specifically because the pre-existing compound fixture (gh-7/gh-5/gh-6,
from iteration 25's QN-035) was already `done` before this iteration
began and therefore could not serve as a fresh `todo`-to-`done` drive.

## Plan

1. Create three fresh GitHub issues (#8, #9 as children; #10 as the
   epic referencing both) via `gh issue create`, all starting genuinely
   at `todo`.
2. Author the epic (gh-10) via `quay:author`'s own documented Method: the
   Proposal/Plan/AC/DoD are written directly in the issue body; the
   decompose test (design §4) is confirmed to genuinely apply (2
   independently mergeable deliverables — two separate DESIGN.md
   doc-comment sentences); AC is restructured, after an initial
   authoring mistake, to be genuinely checkable at authoring time
   (execution-outcome verification lives in DoD/the iteration report, not
   in AC items that cannot be true before execution — per this project's
   own QN-020 precedent); gate-check `todo -> ready`.
3. Drive the epic via `quay:execute`'s own `executeEpic` pseudocode:
   `driveEach` — for each child (gh-8, then gh-9, in genuine temporal
   order, one fully `done` before the next is even authored), invoke
   `quay:author` then `quay:execute`'s `executeLeaf` path
   (`implement-phase`: a real `packages/quay-github/DESIGN.md` doc-comment
   addition per child; `self-audit-ac`: full regression suite re-run;
   `gate-check`: `task check` -> `task edit --status ready` -> (after
   re-verification) `task edit --status done`).
4. After child A (gh-8) reaches `done` but before child B (gh-9) is
   authored, live-capture the epic's own intermediate gate state
   (expected `ok:false`, naming gh-9 as the blocking child) — the
   necessary intermediate proof that the compound gate genuinely tracks
   partial completion, not just the final state.
5. Once both children reach `done`, run `integrationAccept`: re-check the
   epic's own `execute->done` gate (expected `ok:true`, `childrenStatus`
   showing both children `done`), check the epic's own DoD boxes (having
   first updated `quay:execute`'s SKILL.md Gaps section, per the epic's
   own DoD requirement), then flip the epic to `done`.
6. Cross-check Core's passthrough (`quay task check gh-10 --provider
   github --json`) against `quay-github`'s own direct CLI output for
   byte-identical proof, and restore `.quay/config.yml`'s temporary
   `github.enabled: true` flip.
