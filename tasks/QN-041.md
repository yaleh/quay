## Proposal

`packages/quay/DESIGN.md` §2.5 ("Known gaps, named honestly") lists three
residual, never-closed test-coverage gaps left after QN-036 (iteration 26)
implemented Core's own MCP server. This task closes the third of those
three (the other two — the real-Claude-Code-session stdio transport
lifecycle, and CAS-through-Core specifically — remain out of scope for
this task; see "Explicit scope check" below):

> The `provider://manifest/<id>` per-Provider resource naming
> (`manifest-${id}` as the MCP resource *name*, distinct from its *uri*)
> has not been checked against any MCP client that enumerates resources
> by name rather than uri; every check performed this iteration used
> uri-based `readResource()` calls.

**Fresh verification performed this iteration, before writing this
Proposal (per the standing precedent-search discipline):** a standalone
probe script was written and run against the real, unmodified `quay mcp`
subprocess (a two-Provider fixture identical in shape to
`mcp-server.test.mjs`'s own). It confirmed two things, live:

1. `client.listResources()` returns each resource's `name` field
   (`"manifest"` for the default alias, `"manifest-native"` for the
   per-Provider one) alongside its `uri` — genuinely present, distinct
   fields, exactly as `mcp-server.js`'s own source comments claim
   (lines ~119-148).
2. Calling `client.readResource({ name: "manifest" })` (omitting `uri`)
   throws an MCP protocol-level error (`-32603`, zod validation:
   `params.uri` expected string, got undefined) — the MCP SDK's
   `resources/read` request is uri-keyed by protocol design; `name` is a
   listing/display-only field, never a lookup key, for ANY MCP resource
   in this SDK, not specific to `quay mcp`'s own implementation.

This is genuinely new evidence (a live probe against a real subprocess,
not reasoning from memory) that closes the named gap: the answer is now
demonstrated, not merely assumed. It should be captured as a committed,
repeatable regression assertion (not left as a throwaway probe script) so
a future refactor cannot silently regress the "name and uri are both
present and distinct" invariant `mcp-server.js`'s own resource
registration relies on.

**Explicit scope check (avoiding the credit-two-factors-for-one-fact
failure mode named at this iteration's start):** this is a **test-
coverage-closure** task, of the same shape as QN-039 (iteration 29):
adding a regression assertion for existing, unchanged, already-correct
behavior. It is NOT a new ABI surface, NOT a new schema, and NOT a new
gate-logic change. Per QN-039's own iteration-29 precedent (held
`skeleton`/`abi_symmetry`/`gate_correctness`/`skill_convergence` all
flat, reasoning "tested existing schema-conformant branches, it did not
add or change any schema"), this task is expected, honestly, to hold all
four V_instance factors flat too — this Proposal states that expectation
up front rather than deciding post-hoc which factor "feels right."
Per DIR-008's constraint 4(b) (Core-level three-way-symmetry-shaped work
maps to the same factors as Provider-level analogues), IF this had
instead added a genuinely new symmetry surface it would map to
`abi_symmetry` — but it does not, because the fact being proven
(uri-keyed, not name-keyed lookup) is a pre-existing, unchanged protocol
property of the MCP SDK itself, not a new quay-built surface.
