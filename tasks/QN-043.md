## Proposal

`packages/quay/DESIGN.md` §2.5 ("Known gaps") names two gaps honestly, not
silently claimed as covered, at the end of iteration 26 (DIR-007/QN-036):

1. The `provider://manifest/<id>` name-vs-uri resource gap — **already
   closed** in iteration 30 (QN-041).
2. `task_write`'s CAS (`expectedStatus`) option is forwarded by Core's MCP
   server (`mcp-server.js`'s `task_write` tool passes `expectedStatus`
   straight through to `client.taskWrite({ id, ...patch })`) but was **not
   specifically exercised through the Core MCP path** — "a thin, generic
   passthrough with no Core-specific CAS logic, so the risk surface is low,
   but it is named here rather than silently assumed covered by
   transitivity."

This task closes the second, remaining named gap, following the exact
precedent QN-041 set for closing the first one: a real, live-verified test
against the actual `quay mcp` subprocess (not a unit test of
`provider-client.js` in isolation), because DESIGN.md's own gap statement
is specifically about the *Core MCP path*, which no existing test exercises
for this option (confirmed by `grep -n "expectedStatus" packages/quay/test/*.test.mjs`
returning zero hits before this task's own test is written).

**Expected V-factor attribution, stated up front (per DIR-008 constraint
4(b), and directly following QN-041's own iteration-30 precedent for the
*first* §2.5 gap):** this is new *test coverage* of an *already-existing,
unchanged* capability (`expectedStatus` passthrough has existed in
`mcp-server.js` since QN-036/iteration 26, unmodified) — not new capability
construction. Per QN-041's own precedent (iteration 30, held `skeleton`
flat: "no new capability was constructed... zero change to `mcp-server.js`'s
own runtime behavior... the field it asserts on already existed"), and per
iteration 28's "new proof vs. new capability" distinction, this task is
expected to hold **all four `V_instance` factors flat** unless the live run
surfaces a genuine, previously-unknown defect requiring a real code fix (in
which case that fix, not the test itself, would be the `skeleton`/
`gate_correctness`-relevant event). This is stated honestly before
execution, not decided post-hoc.
