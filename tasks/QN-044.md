## Proposal

`experiments/quay-native-bootstrap/directives/pending/DIR-010-core-cli-mcp-webui-three-way-symmetry.md`
(human-asserted, 2026-07-15) finds, via direct repo inspection, that
`docs/proposal/quay-proposal.md` §5 (line 54, "Three sibling front-ends over
the same Provider ABI: Web UI, Core CLI, and an MCP projection for agents —
one capability set, three bindings") and §9 (line 235, "The Web UI is the
same capability set with a web binding") state a Core-level three-way
symmetry requirement that has never been operationalized into a checkable
test, unlike the analogous but distinct Provider-level P3 claim
(`packages/quay-native/DESIGN.md`, already enforced by
`packages/quay-native/test/abi-symmetry.mjs`).

A direct read of the three Core-level surfaces (performed in the directive
itself) found one concrete, checkable gap: §9's own listed capability set
(lines 226-230) is exactly `serve`, `task list`, `task view`, `action list`,
`action run` -- i.e. task-list rendering, task-detail rendering, and
action-button triggering. Core CLI (`bin/quay.js`) and the Web UI
(`src/serve.js`) both cover this set; Core MCP (`src/mcp-server.js`, shipped
by DIR-007/QN-036) registered only `task_list`/`task_get`/`task_write`/
`task_check` -- no `action_list` or `action_run` tool existed. An Agent
connected only via `quay mcp` could not list or trigger action buttons, even
though both are explicitly part of §9's own listed capability set.
`task edit` and `task check` are explicitly **not** part of this contract
(added to the CLI later, QN-024/QN-027, never proposed for the Web UI) and
must not be asserted as a symmetry gap.

**V-factor attribution, stated up front (per DIR-008 constraint 4(b), and
DIR-010 point 5's own instruction to cite precedent precisely rather than
default to flat):** this task is **not** structurally identical to QN-041/
QN-043 (the two DESIGN.md §2.5 gap-closures, both pure test-coverage of an
already-existing, unmodified capability, correctly held flat). This task
adds two genuinely new MCP tools (`action_list`, `action_run`) to
`src/mcp-server.js` that did not exist before -- new binding/capability
surface, the same shape as QN-036/DIR-007 itself (which stood up the whole
MCP server as new capability and was credited on `skeleton`), not the
QN-041/QN-043 "new proof of an existing thing" shape. Per DIR-009/QN-042's
own precedent (a new delivery *mode* added to `action.js`, credited on
`skeleton` per constraint 4(b)'s mapping "new Core capability code →
`skeleton`"), and per QN-036's own precedent (new MCP tool surface credited
on `skeleton`), this task's item-1 work (the new tools) is expected to move
**`skeleton`**, not `abi_symmetry` -- `abi_symmetry` (0.94) is scored
against `abi-symmetry.mjs`'s own Provider-level P3 contract, which this
task's new tools do not touch (confirmed: zero diff to
`packages/quay-native`/`packages/quay-github`, and `abi-symmetry.mjs` itself
re-runs unchanged). Item 2 (the new Core-level symmetry test) is itself the
*enforcement mechanism* for the Core-level three-way contract this task
documents in DESIGN.md §4 -- by the same reasoning `abi-symmetry.mjs` is not
treated as moving a factor merely by existing, but by what it enforces, this
new test's own existence is not double-counted as an additional movement
distinct from the `action_list`/`action_run` capability it verifies. This is
recorded here, before scoring, not decided post-hoc.

## Plan

1. Add `action_list` and `action_run` tools to `packages/quay/src/
   mcp-server.js`, mirroring the existing four tools' shape exactly
   (optional `provider` argument, same `isError:true`-on-failure
   convention). `action_run` accepts an optional `mockLogPath` argument
   selecting the DIR-009 deterministic mock/file-log delivery mode instead
   of live manda, reusing `action.js`'s `composePayload`/`deliverTrigger`
   unmodified.
2. Add `packages/quay/test/core-three-way-symmetry.test.mjs`: a fresh,
   isolated native Provider task store with one fixture task, three legs
   checked against the same fixture (CLI subprocess, Core MCP subprocess via
   a real MCP client, Web UI via real HTTP requests against `serve.js`) for
   each of task-list rendering, task-detail rendering, and action-button
   list/trigger -- explicitly not asserting anything about `task edit`/
   `task check`'s absence from the Web UI.
3. Add `packages/quay/DESIGN.md` §4 ("Core-level three-way symmetry"):
   state the contract, what closed the gap, the enforcement mechanism, and
   name (without fixing) any pre-existing asymmetry discovered along the
   way.
4. Do not touch `abi-symmetry.mjs` or any Provider-level file -- additive,
   Core-layer-only, confirmed via `git diff --stat -- packages/quay-native
   packages/quay-github`.
5. Run the new test standalone 3+ times for determinism, then the full
   regression suite (all pre-existing test-bearing files plus the new one)
   to confirm zero regressions.
6. Score V_instance/V_meta per the up-front attribution stated in the
   Proposal, citing the QN-036/QN-042 precedents by name and by re-reading
   their reasoning directly (not merely gesturing at them), per DIR-010
   point 5's explicit instruction.
