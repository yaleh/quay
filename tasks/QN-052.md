## Proposal

`packages/quay-native/provider.yml` declares both `capabilities.skill:
true` (line 20-21) AND a `skills_path: "./skills"` field (line 63)
pointing at the real, physical Skill files (`packages/quay-native/skills/
author/`, `.../execute/`). `packages/quay-github/provider.yml` also
declares `capabilities.skill: true` (line 35-43), with a comment crediting
this to "the provider-parameterized quay:author/quay:execute Skills" —
but it declares **no `skills_path` field at all**. Confirmed directly via
`grep -n "skills_path" packages/quay-github/provider.yml` (zero hits) vs.
`packages/quay-native/provider.yml` (one hit, line 63).

This is a genuine, previously-undiscovered manifest asymmetry between the
two Providers' self-declarations — the same class of defect QN-049
(`quay-github/provider.yml`/`DESIGN.md`), QN-050
(`quay-native-design.md` §8), and QN-051 (`quay-native/provider.yml`'s own
stale comments) each closed, applied to a field-presence gap rather than a
stale-comment gap. Confirmed via `grep -rn "skills_path"
packages/*/src/*.js` (zero hits, repo-wide) that `skills_path` is **never
read by any code path** in either Provider or Core — it is purely
declarative/documentary metadata (the physical Skill files are consumed
today only via the Core CLI's provider-agnostic `quay task <cmd>
--provider <id>` passthrough, per QN-029's own iteration-18 fix, not by
any code that reads `skills_path`). This task is therefore, like QN-049/
QN-050/QN-051, a documentation/manifest-accuracy fix with zero executable
behavior change — not a capability change.

`reusability` (protocol §5.2: "the methodology transfers to a second
Provider (GitHub) unmodified") was considered directly: the actual
transfer mechanism (provider-parameterized Skill invocation via `quay
task <cmd> --provider github`) already works and was already credited
(iteration 18, QN-029; iteration 25, QN-035) — this field is unconsumed
metadata, so adding it does not itself demonstrate any new transfer
capability, matching the established precedent (QN-049/QN-050/QN-051) for
identical-class fixes.

## Plan

1. Re-verify the asymmetry directly: `grep -n "skills_path"
   packages/quay-native/provider.yml packages/quay-github/provider.yml`
   and `grep -rn "skills_path" packages/*/src/*.js` (repo-wide, confirm
   zero consumers).
2. Add a `skills_path` field to `packages/quay-github/provider.yml`,
   consistent in shape with native's own (`skills_path: "./skills"`),
   even though `packages/quay-github/skills/` does not physically exist
   as a directory — with an explicit, honest comment explaining this:
   the field documents *which Skills* provide this Provider's
   orchestration (the same `quay:author`/`quay:execute` Skills, per the
   established provider-parameterization mechanism), not a separate,
   physically-duplicated copy of the Skill files. Do NOT create a
   duplicate `packages/quay-github/skills/` directory — that would be a
   real, unjustified duplication of Skill content across Providers with
   no demonstrated need (G5 gold-plating risk), when the actual, already-
   working, already-credited transfer mechanism is Core-level Skill
   invocation with an explicit `--provider` argument, not per-Provider
   physical Skill copies.
3. Re-run the full regression suite and confirm zero `.js` diff and that
   every other `provider.yml` field is byte-identical to before the edit.
