## Proposal

Iterations 54/55/56/57 systematically closed the cross-Provider (GitHub)
read-path test-coverage gap at the CLI layer (task view/action list/task
check --provider github), the Core MCP aggregation layer, and the Web-UI
layer, respectively. All four closed the identical shape of gap: does a
Core-level binding correctly render/return *ordinary application data* from
a live, correctly-configured GitHub Provider. Iteration 57's own reflection
explicitly named the next genuinely different angle: "negative/error-path
coverage specifically for the GitHub Provider (e.g. malformed issue bodies,
a repo/token misconfiguration, rate-limit or network-failure handling)."

This task closes one concrete instance of that angle: Provider-SUBPROCESS
STARTUP-FAILURE propagation. `packages/quay-github/bin/quay-github.js`'s
own `resolveRepo()` throws synchronously if `QUAY_GITHUB_REPO` is not
`owner/repo`-shaped -- but this failure mode had only ever been tested
directly against `quay-github.js`'s own CLI (QN-034, iteration 24). It had
never been tested through any Core-level binding, where the failure must
additionally survive an MCP stdio-transport connect attempt before
reaching the caller -- a materially different code path (Core's own
`connectProvider()`/`withProvider()` in `provider-client.js`/`bin/quay.js`,
and `mcp-server.js`'s lazy `getClient()`) than the one QN-034 exercised.

Manual, pre-test-code verification (this session) established the actual
behavior differs by layer: Core's CLI (`bin/quay.js`) and Web UI
(`serve.js`) connect to every enabled Provider EAGERLY, so a crashing
Provider fails fast with a verbose (name-bearing) stderr diagnostic and
exit code 1; Core's own MCP server (`mcp-server.js`) connects LAZILY (only
on first tool call naming the Provider), so `quay mcp` itself starts up
fine even with a broken Provider, and the first tool call against it
returns a gracefully-caught `isError:true` MCP result whose error text is
opaque ("MCP error -32000: Connection closed") -- it does NOT surface
`resolveRepo()`'s own actual diagnostic text at all. This asymmetry was
previously undocumented and untested.

## Plan

1. Add test 12 to `packages/quay/test/cli.test.mjs`: a Provider entry whose
   `mcp_entry` is `quay-github.js` with a deliberately malformed
   `QUAY_GITHUB_REPO`, invoked via `quay task list --provider
   broken-github`. Assert exit code 1, empty stdout, and a stderr
   diagnostic naming the failure. No live GitHub network access required
   (the failure is local/synchronous, before any `gh api` call would be
   attempted).
2. Add block 11 to `packages/quay/test/mcp-server.test.mjs`: the same
   broken-Provider fixture, connected via a real `quay mcp` subprocess.
   Assert `task_list` returns `isError:true` (not a hang, not an uncaught
   crash of the `quay mcp` process itself), and that a second, independent
   call also returns `isError:true` (proving the aggregator process
   survives the first failure rather than crashing).
3. Update both files' own header comments documenting the new angle and the
   documented CLI-vs-MCP error-shape asymmetry.
4. Re-run the full regression suite (`node --test packages/*/test/*.test.mjs`)
   and `abi-symmetry.mjs`; confirm zero `src/*.js` diff (test-file-only
   change) and zero live write to any real GitHub issue.
