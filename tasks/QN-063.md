## Proposal

`packages/quay-github/src/github-client.js`'s `checkGate()` and
`issueToViewModel()` both already defend against a GitHub issue whose
`body` field is `null` (the real, documented shape `gh api` returns for an
issue created with no description at all — distinct from an issue with an
explicitly empty-string body, which is what every existing fixture in
`view-model.test.mjs`/`gate.test.mjs` uses instead) — `issueToViewModel()`
line 140 defends via `issue.body ?? ""`, and `checkGate()`'s own
`gateArtifactSections()`/`extractGateSection()` both default via `body ||
""` before regex-matching. Manually confirmed this session (via a direct
`node -e` probe against the real, unmodified `checkGate()`) that a `null`
body does not crash: it correctly reports `ok:false` with a
"missing artifacts" reason at the `todo` gate, and correctly reports
`acTotal:0`/`acChecked:0` at the `ready` gate, for both `null` and
`undefined` body values.

However, zero test file in the repo exercises this specific case: `grep -n
"body: null\|body: undefined" packages/quay-github/test/*.mjs` returns no
hits. Every existing fixture (`view-model.test.mjs`'s `mkIssue()` default,
`gate.test.mjs`'s hand-written bodies) uses an empty *string* (`""`), never
the real, distinct `null`/`undefined` shape a genuinely bodyless GitHub
issue actually has. This is a genuinely new negative/error-path angle
(distinct from iteration 58's Provider-subprocess-startup-failure angle,
and from the now-fully-exhausted cross-Provider read-path sweep,
iterations 54-57): it targets a specific, previously-uncovered, realistic
malformed-input shape at the Provider's own view-model/gate layer, per
iteration 58's own reflection naming "malformed issue bodies" as a distinct
future instance of the negative/error-path category, not yet closed by any
prior iteration (confirmed via `grep -n "malformed issue" experiment/
provenance.md` — no prior task addresses this specific shape).

This task has **no live GitHub network dependency** (it is a pure-function
unit test, exactly matching `gate.test.mjs`'s and `view-model.test.mjs`'s
own existing no-live-API convention) — the same property iteration 58's
own task had, which iteration 58 explicitly declined to leverage into an
`effectiveness` credit because it lacked an actual timed comparison. This
task performs that timed comparison, scope-matched against the stage-0
seed baseline (QN-006, ~2m59s, `experiment/timing/iteration-0.log`) and
iteration 22's own scope-matched comparator (QN-032, ~3m07s,
`experiment/timing/iteration-22.log`), per iteration 22's own established
methodology (one already-existing, unmodified code unit; one new test
file/block; no source-code change expected; gate check; done) — not
manufactured solely to produce a score, but because this task genuinely
fits that same narrow scope shape and the comparison had not yet been
repeated since iteration 22.

## Plan

1. Add a new test block to `packages/quay-github/test/view-model.test.mjs`
   asserting `issueToViewModel()` correctly normalizes a `null`-body issue
   (and an `undefined`-body issue) to `body: ""`, `children: []`, with no
   crash — using the same `mkIssue()` fixture helper already in that file.
2. Add a new test case to `packages/quay-github/test/gate.test.mjs`
   asserting `checkGate()` correctly reports `ok:false` with a
   "missing artifacts" reason for a `null`-body `todo`-status task, and
   `acTotal:0`/`acChecked:0`/`ok:false` for a `null`-body `ready`-status
   task — using the same `assert()` helper already in that file.
3. Run both test files standalone, then the full regression suite, to
   confirm the new assertions pass against the real, unmodified source
   (no source-code change expected or made).
4. Record wall-clock timing checkpoints (`date -u`) at task creation,
   gate checks, and completion, to `experiment/timing/iteration-59.log`,
   for the scope-matched effectiveness comparison.
