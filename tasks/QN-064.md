## Proposal

Iterations 58 and 59 named "malformed issue bodies" and "rate-limit/network-
transient-failure handling, misconfiguration surfaced at other lifecycle
points" as distinct, not-yet-closed instances of the broader
negative/error-path category (`provenance.md`, iteration-58 and
iteration-59 reflections). Iteration 58 closed the Provider **subprocess
startup** failure angle (a malformed `QUAY_GITHUB_REPO` causing
`resolveRepo()` to throw synchronously, before any `gh api` call).
Iteration 59 closed the **null/undefined issue-body** input-shape angle.

Read `packages/quay-github/src/github-client.js` in full this session.
Found a third, genuinely distinct and previously untested angle: what
happens when `gh api` itself fails (network error, 404, auth failure,
rate-limit) **after** a successful Provider startup, **during** a live
`task_list` call (i.e. inside `fetchAllIssues()`)? This is a different
failure point from both prior angles — the Provider process is already
up and connected (unlike QN-062's pre-connect crash), and the failure
originates from the live `gh api` subprocess call inside `list()`
(`github-client.js` line 504, via `fetchAllIssues()` → `pageIssues()` →
`fetchPage` → `ghApiJson()`), not from a malformed input value in an
issue body (unlike QN-063).

Confirmed via a direct probe this session
(`QUAY_GITHUB_REPO=nonexistent-owner-xyz-123/nonexistent-repo-abc`)
that `list()` has **no try/catch** around `fetchAllIssues()` — unlike
`get(id)` (line 512-521), which already wraps its own `ghApiJson` call
in `try { ... } catch { return null; }`. A raw `execFileSync` failure
(the real `Error` Node throws when `gh api` exits non-zero, carrying `gh`'s
own stderr text, e.g. `gh: Not Found (HTTP 404)`) propagates unhandled out
of `list()`.

Confirmed this is genuinely untested: `grep -n "fetchAllIssues\|\.list("
packages/quay-github/test/*.mjs` shows `list()`/`fetchAllIssues` is only
ever exercised against the real, live, reachable `yaleh/quay` repo
(`mcp-server.test.mjs`) or via the fully-synthetic, injectable
`pageIssues` (`pagination.test.mjs`, which tests only the max-issues
overflow-cap throw, a different failure mode entirely — a *successful*
`gh api` call whose result set is too large, not a *failing* `gh api`
call). Also confirmed via `grep -n "malformed issue\|rate-limit"
experiments/quay-native-bootstrap/provenance.md` that this exact angle (a live `gh api` failure
during `task_list`, as opposed to at Provider startup) has never been
closed.

## Plan

1. Add a new test block to `packages/quay-github/test/mcp-server.test.mjs`
   spawning a real `quay-github mcp` subprocess with
   `QUAY_GITHUB_REPO=nonexistent-owner-xyz-123/nonexistent-repo-abc` (an
   unreachable, real-network-round-trip 404, not a malformed-format value —
   distinct from QN-062's synchronous, pre-network `resolveRepo()` throw).
   Assert `task_list` returns `isError:true` (not a hang, not an uncaught
   crash of the `quay-github mcp` process), with error text derived from
   `gh`'s own diagnostic, and that a second, independent `task_list` call
   also returns `isError:true` (proving the process survives the failure,
   the same aggregator-survival property QN-062 established for Core's own
   MCP server, now checked directly against quay-github's own MCP server
   for a *different* failure trigger).
2. Add a new test to `packages/quay-github/test/cli.test.mjs` for the
   direct CLI path: `quay-github task list --json` against the same
   unreachable owner/repo; assert non-zero exit code and that stderr
   carries `gh`'s own diagnostic text (contrasting with `task get`'s own
   already-caught not-found path, which prints a clean `no such task: ...`
   line instead of a raw stack — documenting a second CLI-internal
   asymmetry, this time between `list()`'s unhandled failure and `get()`'s
   already-caught one, both within quay-github's own CLI).
3. Update both files' own header comments documenting the new angle.
4. Re-run the full regression suite (`node --test packages/*/test/*.test.mjs`)
   and `abi-symmetry.mjs`; confirm zero `src/*.js` diff (test-file-only
   change) and zero live write to any real GitHub issue.
