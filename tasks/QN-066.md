## Proposal

Iterations 58/59/60 closed three distinct negative/error-path instances
(Provider-subprocess-startup failure, malformed/null issue-body input, and a
live `gh api` failure mid-session during `task_list`). Iteration 61 fed that
discipline back into `quay:execute`'s own Method (a documentation-only
change, whose scoring credit was later reverted post-hoc — see
`provenance.md`'s iteration-61 section).

This iteration searched for a fourth genuine, previously-untested
negative/error-path instance before considering V_meta movement. Two
candidate angles were investigated live:

1. **`quay-github`'s `setStatus` (the actual `gh api` PATCH/label-write
   path) failing mid-write**, distinct from the already-tested GET-404
   failure (`mcp-server.test.mjs` test 6 only exercises the GET call inside
   `setStatus`, never the PATCH/label calls that follow it). This was
   investigated directly against the real `yaleh/quay` repo. A probe
   (`gh api repos/yaleh/quay/issues/3/labels -X POST -f
   "labels[]=status:nonexistent-value-xyz"`) accidentally **created a real
   label on issue #3** — immediately reverted via a matching `DELETE` call,
   confirmed via a follow-up `GET` that issue #3's labels are back to
   exactly `status:ready`/`lane:execution`, its original state. A second,
   non-mutating probe (`PATCH .../issues/3 -f "state=bogus-invalid-state-value"`)
   showed GitHub's API silently ignores an invalid `state` value rather than
   erroring — no clean, safe, non-mutating way exists to trigger a
   PATCH-specific failure against a real, existing issue without either
   already knowing it will no-op (defeating the purpose) or risking a real
   mutation to this repo's small, precious issue set. **This angle is
   correctly left closed** — the existing `write.test.mjs`/`cli.test.mjs`/
   `mcp-server.test.mjs` header comments' standing scope constraint ("this
   repo's real issue count is too small/precious to safely target with
   destructive live writes") is reconfirmed as a genuine safety boundary,
   not a gap to close, by this iteration's own live probe.
2. **`bin/quay.js`'s own direct-CLI-subprocess dispatch for `action run`
   with an unknown `actionId`.** `composePayload()`'s `no such action
   button: <id>` throw is already tested at the MCP layer
   (`packages/quay/test/mcp-server.test.mjs`, `action_run` with an unknown
   `actionId` returns `isError:true`) and at the direct `src/action.js`
   unit level (`packages/quay/test/serve.test.mjs`, a bare function-throw
   assertion). A repo-wide grep for `"no such action button"` confirmed
   `bin/quay.js` itself — spawned as a real child process, so the failure
   must propagate through `withProvider()`'s async callback all the way to
   the top-level `main().catch(...)` handler and produce a real
   process-level exit code/stderr shape — had never been exercised this
   way. This is genuinely distinct from both existing tests: the MCP case
   is caught and returned as a structured tool result by the SDK; the
   `serve.test.mjs` case asserts directly against the thrown JS exception
   in-process; neither exercises the real CLI-subprocess exit-code/stderr
   contract. This requires no live GitHub/network access (the throw
   happens before `deliverTrigger()`, entirely local, against the existing
   `packages/quay/test/cli.test.mjs` fixture already used throughout that
   file).

Angle 2 was selected: genuine, safely closeable, previously-untested.

## Plan

1. Add a new test (6b) to `packages/quay/test/cli.test.mjs`, immediately
   after the existing test 6 (`action run <id> advance --json` happy path),
   spawning `quay action run CLI-1 bogus-action-id --json` against the
   file's existing local fixture (no live GitHub, no new fixture setup).
2. Assert: exit code 1 (not a hang, not silent success); stderr contains
   `no such action button`; stdout never contains `"delivered"` (proving
   `deliverTrigger()` is never reached — the throw happens strictly before
   it).
3. Adversarially verify the new test has real teeth: temporarily replace
   `composePayload`'s throw with a stub success return, confirm all three
   new assertions fail, then restore the original file and confirm they
   pass again (byte-identical `git diff --stat` on `src/action.js` before
   and after, zero net change).
4. Re-run the full regression suite (`node --test packages/*/test/*.test.mjs`)
   and `abi-symmetry.mjs`; confirm no regression and zero `src/*.js` diff
   (test-file-only change).
