## Proposal

`packages/quay-github/src/github-client.js`'s `issueToViewModel()` implements
a documented precedence rule (comment above `STATUS_PRECEDENCE`, iteration-4
independent-audit bug fix #3) for the "multiple `status:*` labels on one
issue" case: recognized labels are ranked by `STATUS_PRECEDENCE`
(`["done","needs-human","ready","todo"]`), and the comment explicitly states
"Unrecognized label values (not in STATUS_PRECEDENCE) are treated as lowest
precedence, in the order encountered, below all recognized ones." This
fallback branch of the sort comparator (`ai === -1 ? STATUS_PRECEDENCE.length
: ai`) has never been exercised by any test: `test/view-model.test.mjs`'s six
precedence cases (lines 40-81) only ever combine labels that are each
individually a member of `STATUS_PRECEDENCE` (`ready`/`todo`,
`ready`/`needs-human`, etc.) or a single recognized label. No test combines a
recognized `status:*` label with an *unrecognized* one (a label value with no
entry in `STATUS_PRECEDENCE` at all, e.g. `status:some-typo-value`), so the
documented "ranked below all recognized ones" fallback behavior has never
actually been proven correct at runtime — only asserted in a comment.

Confirmed via direct invocation this iteration:
```
$ node --input-type=module -e '
import { issueToViewModel } from "/home/yale/work/quay/packages/quay-github/src/github-client.js";
const vm = issueToViewModel({number:1,title:"t",body:"",state:"open",labels:[{name:"status:ready"},{name:"status:bogus-unrecognized-value"}],html_url:"x",user:{login:"a"}});
console.log(vm.status);
'
ready
```
This currently returns `"ready"` (the recognized label correctly beats the
unrecognized one), matching the comment's claim, but zero regression test
protects this behavior today.

This is a genuinely distinct instance from the standing negative/error-path
discipline (iterations 58-61's Method sub-check in `quay:execute`): this is
not a network/process-failure angle, but a data-*shape* anomaly inside an
otherwise-successful response (an unrecognized label value), closest in kind
to iteration 59's null/undefined-body work but for a different function
(`issueToViewModel`'s precedence sort, not `checkGate`).

## Plan

1. Add a new test case to `packages/quay-github/test/view-model.test.mjs`,
   immediately after the existing 6 precedence cases (after line 81),
   combining a recognized `status:*` label with an unrecognized one, in both
   label orders, asserting the recognized one wins both times.
2. Add a second case: two unrecognized `status:*` labels (neither in
   `STATUS_PRECEDENCE`) -- assert the first one encountered wins (the
   documented "in the order encountered" tie-break for the fully-unranked
   case), proving the stable-sort assumption holds for this input shape too.
3. Adversarially verify: temporarily change the comparator's `-1` fallback
   handling (e.g. make unrecognized values rank *above* recognized ones) and
   confirm the new tests fail; restore and confirm they pass again.
