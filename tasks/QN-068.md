## Proposal

Both `packages/quay-native/src/store.js#check()` and
`packages/quay-github/src/github-client.js#checkGate()` implement two
terminal-status branches that have never been exercised by any unit test on
either Provider:

1. **`status === "needs-human"`** — both implementations return
   `{ id, gate: "none", ok: false, reason: "soft stop; human action
   required" }` (native: `store.js` lines 472-474; GitHub: `github-client.js`
   lines 463-464). Confirmed via `grep -rn "soft stop" packages/*/test/*.mjs`
   this session: **zero hits** — no test file asserts this exact response
   shape for either Provider.
2. **The final `unrecognized status` fallthrough** — both implementations
   return `{ id, gate: "unknown", ok: false, reason: "unrecognized status
   <status>" }` for any `status` value outside the four valid ones (native:
   `store.js` line 475; GitHub: `github-client.js` line 467). Confirmed via
   `grep -rn "gate.*unknown\|gate: \"unknown\"" packages/*/test/*.mjs`:
   **zero hits** on either Provider.

This is distinct from, though related to, the standing negative/error-path
discipline (`quay:execute`'s Method step 1, added iteration 61): those three
categories concern connection/startup failure, malformed input, and live
mid-session failure — all *external*-boundary failure modes. This gap is
different in kind: it is the gate's own **terminal-branch logic**
(`store.js#check()`/`github-client.js#checkGate()`'s status-dispatch
`if`/`else if` chain) never being exercised for two of its five possible
branches (`todo`, `ready`, `done` are all covered; `needs-human` and the
"anything else" fallthrough are not), a pure internal-logic gap, not an
external-boundary one.

Notably, `needs-human` is **not** an untested *state* in this experiment —
provenance.md's iterations 7, 8, and 9 (QN-017; QN-020/021; QN-022/023) each
narrate a real, live `task check`/`task edit --status needs-human`
transition. But those are one-off narrated events in historical iteration
reports, not a repeatable regression test asserting the exact response
shape going forward — nothing today would catch a future refactor that
silently changed `needs-human`'s reason string or `gate`/`ok` values. This
mirrors the exact distinction iteration 63's own audit (independently)
endorsed for `skeleton` credit: a runtime-exercised, adversarially-verified
test is categorically different from prose/narration describing a fact.

Both Providers currently behave correctly (identical shapes, as required by
the ABI-symmetry design), but zero regression test protects either behavior
today on either side. `bogus-status-value` is not a value `store.js`'s own
`VALID_STATUSES` accepts for writes at the CLI/MCP layer (write-time
validation exists elsewhere), but `check()`/`checkGate()` themselves accept
any string in `status` with no upstream validation inside these specific
functions — so this fallthrough is a genuine defensive branch, not dead
code, and is exactly the kind of "what if the task file itself was hand-edited
or corrupted to hold an unexpected status string" defensive case a gate
mechanism (G3: "the gate is both contestant and judge") should have direct
proof for.

## Plan

1. **Native**: add two new cases to `packages/quay-native/test/
   gate-correctness.test.mjs` (after case (d)): a `needs-human` task
   asserting the exact `{gate:"none", ok:false, reason:"soft stop; human
   action required"}` shape, and a task with an unrecognized status string
   asserting `{gate:"unknown", ok:false, reason:"unrecognized status
   <value>"}`.
2. **GitHub**: add the equivalent two new cases to `packages/quay-github/
   test/gate.test.mjs` (after case (f)), calling `checkGate()` directly with
   `status: "needs-human"` and `status: "bogus-status-value"`, asserting the
   identical shapes (proving cross-Provider ABI parity for these two
   terminal branches, not just each Provider's own internal correctness).
3. Adversarially verify both new native cases: temporarily comment out
   `store.js`'s `needs-human` branch (falling through to the unrecognized-
   status branch) and confirm the `needs-human` case's assertions correctly
   fail; restore and confirm byte-identical diff and tests passing again.
   Do the same for the GitHub-side `needs-human` branch in
   `github-client.js`. No live `gh api` call required (pure function tests,
   matching the existing convention in both test files).
