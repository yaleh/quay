## Proposal

`packages/quay/src/provider-client.js#taskCheck()` is Core's own generic,
provider-agnostic passthrough for the `task_check` MCP tool (added QN-027,
iteration 13). It has exactly one direct regression test today,
`packages/quay/test/task-check.test.mjs`, and that test exercises exactly two
of the gate's five possible response shapes: the AC/DoD-complete `ok:true`
case and the AC/DoD-incomplete `ok:false` case (both against
`packages/quay-native`'s own `store.js#check()`).

QN-068 (iteration 64) added direct-Provider-level unit test coverage for the
other two terminal shapes — the `needs-human` soft-stop (`gate:"none"`) and
the final "unrecognized status" fallthrough (`gate:"unknown"`) — on **both**
`packages/quay-native/src/store.js#check()` and
`packages/quay-github/src/github-client.js#checkGate()` directly. But QN-068
was explicitly scoped to the two Providers' own gate functions in isolation
(`gate-correctness.test.mjs`, `gate.test.mjs`); it did not touch Core's own
`taskCheck()` passthrough at all — confirmed via `git show
--stat <QN-068-commit>` showing only `packages/quay-native/test/
gate-correctness.test.mjs` and `packages/quay-github/test/gate.test.mjs`
touched, zero files under `packages/quay/`.

This leaves a genuinely distinct gap, not a repeat of QN-068: does Core's own
`taskCheck()` function (`provider-client.js`) — the thing quay's CLI/MCP
server/Web UI actually call, not the Provider's gate function directly —
correctly forward the `needs-human` and unrecognized-status shapes unchanged,
end-to-end over a real stdio MCP connection to a real `quay-native mcp`
server? This is a Core-layer question (per `experiments/quay-native-bootstrap/ITERATION-PROMPTS.md`
§Core-scope work item 5 / DIR-013, which codifies that G3's independent-audit
discipline — and by direct extension per item 4(b)'s existing precedent,
`gate_correctness` V-factor attribution — applies to Core exactly as it does
to a Provider), and it was not answered by QN-068's Provider-direct tests, nor
by `task-check.test.mjs`'s existing ok:true/ok:false-only coverage, nor by
`mcp-server.test.mjs`'s one incidental use of the literal string
`"needs-human"` (line 288: used purely as an arbitrary status value to
trigger a CAS `expectedStatus` mismatch in a `task_write` test — that
assertion never calls `task_check`/`taskCheck()` on a `needs-human` task at
all, confirmed by reading the full surrounding test block).

Confirmed via direct invocation this session (before any test is written) —
Core's own `taskCheck()` passthrough, live over a real MCP connection to
`quay-native mcp`, for both previously-uncovered shapes:

```
$ node --input-type=module -e '

{"id":"NH-1","gate":"none","ok":false,"reason":"soft stop; human action required"}
```

Both shapes pass through Core's `taskCheck()` unchanged today, but zero
regression test protects this specific passthrough path — a future refactor
of `provider-client.js#taskCheck()` (e.g. accidentally special-casing
`ok:false` results, or dropping fields present only on non-AC/DoD gate
outcomes) would not be caught by any existing test.

## Plan

1. Add two new cases to `packages/quay/test/task-check.test.mjs`, after the
   existing PASS-1/FAIL-1 cases: a task whose on-disk frontmatter is
   hand-edited to `status: needs-human` (same disclosed
   read-then-write-frontmatter technique QN-068 used on the native side,
   applied here through Core's own passthrough instead of directly against
   `store.js`), asserting `client.taskCheck(id)` returns exactly
   `{id, gate:"none", ok:false, reason:"soft stop; human action required"}`;
   and a second task hand-edited to an unrecognized status string, asserting
   `client.taskCheck(id)` returns exactly `{id, gate:"unknown", ok:false,
   reason:"unrecognized status <value>"}`.
2. Adversarially verify: temporarily comment out `store.js`'s `needs-human`
   branch (same edit QN-068 already used and restored), confirm the new
   Core-level `needs-human` case fails with the expected shape mismatch
   (falls through to the `unrecognized status needs-human` shape instead),
   then restore and confirm `git diff --stat` is empty and the full
   regression suite passes again.
3. No change to `provider-client.js` itself is anticipated (the passthrough
   already forwards these shapes correctly, confirmed above) — this is a
   test-coverage-only addition, matching the established convention for this
   closure class (QN-062 through QN-068).
