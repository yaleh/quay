## Proposal

QN-068 (iteration 64) added direct-Provider-level unit test coverage for
the gate's `needs-human` soft-stop (`gate:"none"`) and "unrecognized
status" fallthrough (`gate:"unknown"`) shapes on **both**
`packages/quay-native/src/store.js#check()` and
`packages/quay-github/src/github-client.js#checkGate()` directly
(`gate-correctness.test.mjs`, `gate.test.mjs`). QN-069 (iteration 66) then
closed the distinct question of whether Core's own generic `taskCheck()`
passthrough (`provider-client.js`) forwards those same two shapes
unchanged over a **real stdio MCP connection** — but QN-069 only exercised
this against the **native** Provider
(`packages/quay/test/task-check.test.mjs`).

Confirmed by direct grep this iteration: `"needs-human"` and
`"unrecognized status"` appear nowhere in
`packages/quay/test/mcp-server.test.mjs`'s GitHub-provider block, which
only exercises `task_check` for the real, live, read-only-fixture issue
gh-3's actual `ready`-status ok:false shape (block 10, iteration 26/QN-060).
No test anywhere in the suite exercises Core's `taskCheck()` passthrough
against the **GitHub** Provider for the needs-human/unrecognized-status
shapes — a genuinely distinct gap from QN-069, not a repeat of it, and the
direct GitHub-side analog of the gap QN-069 closed on the native side.

**Constraint**: issues #3/#4 on `yaleh/quay` are a strictly READ-ONLY test
fixture (this project's standing discipline, repeated in
write.test.mjs/cli.test.mjs/mcp-server.test.mjs's own header comments) —
neither can be mutated, and neither currently carries a
`needs-human`/unrecognized-status label, so this cannot be tested against
the live fixture without either writing to it (forbidden) or depending on
an unrelated, unstable fact about its current label state. No
function-argument injection point exists in `github-client.js`'s own
`check()`/`get()` path (unlike `pageIssues()`'s existing injectable-fixture
convention), and `mcp-server.js#startMcpServer()` hardcodes
`createGithubClient({owner, repo})` directly (both confirmed by reading
the source this iteration) — so no existing test mechanism reaches this
path without a live `gh api` call.

## Plan

1. Add a new, narrowly-scoped test-infrastructure fixture,
   `packages/quay-github/test/fixtures/fake-gh.mjs`: a fake `gh` CLI
   understanding exactly one invocation shape (`gh api
   repos/<owner>/<repo>/issues/<n>`, the only call `github-client.js`'s
   own `get()`/`check()` path makes), returning a test-supplied canned
   issue JSON via the `FAKE_GH_ISSUE_JSON` env var. Anything else exits
   non-zero loudly.
2. Add `packages/quay-github/test/task-check-passthrough.test.mjs`:
   PATH-shadow a fresh temp dir containing a `gh` shim delegating to the
   fixture, spawn a REAL `quay-github mcp` subprocess (and, separately, a
   real `quay mcp` Core-aggregation subprocess) against it, and assert both
   layers surface the needs-human and unrecognized-status shapes unchanged
   for a synthetic fixture issue — zero live network calls, zero
   reads/writes against the real yaleh/quay repository.
3. Adversarially verify: temporarily remove github-client.js's
   `needs-human` branch, confirm the new needs-human case now fails with
   the expected shape mismatch (falls through to "unrecognized status
   needs-human"), then restore and confirm byte-identical source and a
   clean re-run — same disclosed technique QN-069's own Plan step 2 used.
4. No change to `provider-client.js`, `mcp-server.js`, or
   `github-client.js` themselves anticipated (all three already forward/
   compute these shapes correctly, confirmed by this task's own test
   passing on the first run) — test-coverage/test-infrastructure-only.
