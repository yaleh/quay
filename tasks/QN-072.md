## Proposal

Iteration 85's own Practical Convergence recommendation was independently
G3-audited (`experiments/quay-native-bootstrap/audits/iteration-85-independent-adjudicate.md`)
and returned PASS-WITH-CONCERNS: every factual claim checked out, but the
audit found one specific, checkable overreach — `skeleton` (unlike
`gate_correctness`, which has a genuine, argued, 65-iteration-old
architectural ceiling) has no comparable ceiling argument and moved as
recently as iteration 76 via a repeatable pattern: closing a genuinely
new, previously-uncovered Core-`taskCheck()`-passthrough-fidelity gap for
a gate shape that already exists directly on a Provider (QN-069/QN-071's
own pattern for the needs-human/unrecognized-status shapes).

This iteration re-read that exact pattern (iterations 66/69/76's full
work, not just their summaries) and searched for a real, currently-open
instance of it. Found one: `store.js#check()`
(`packages/quay-native/src/store.js`) and
`github-client.js#checkGate()` (`packages/quay-github/src/github-client.js`)
have both had a **compound (epic) `childrenStatus` rollup** branch since
QN-012 (iteration 6, native) / QN-035 (iteration 25, DIR-006, GitHub) —
a `done`/`ready` compound task's gate re-verifies every child is actually
`done`, reporting `stale-done`/`missing`-child detail via a
`childrenStatus` array. This logic has been thoroughly, repeatedly
exercised **directly** against both Providers' own gate functions
(`compound-gate.test.mjs`, `compound-gate-recursive.test.mjs` on native;
`compound-gate.test.mjs`, `gate-gameability.test.mjs`, `view-model.test.mjs`
on GitHub) — but confirmed by direct grep across every `*.test.mjs` in the
repo before writing this task: **no test anywhere calls Core's own
generic `taskCheck()` passthrough (`provider-client.js`, over a real
stdio MCP connection) for a compound task, on either Provider.** This is
the exact same class of gap QN-069/QN-071 closed for the needs-human/
unrecognized-status shapes, applied to the one remaining untested
`check()`/`checkGate()` branch: the epic rollup.

Both MCP servers already wire this through with zero extra code: native's
`task_check` tool calls `store.check(id)` directly (already
compound-aware); GitHub's `task_check` tool calls `client.check(id)`,
which internally supplies its own `get()` as the child-fetcher (also
already compound-aware) — despite the tool's own description text saying
"primitive tasks only, v1" (a stale doc comment, not an actual code
restriction; confirmed by reading `github-client.js#check()` directly).
This is a genuine, previously-undiscovered test-coverage gap, not a
manufactured one, and closing it directly answers the G3 audit's specific
objection: it demonstrates `skeleton`'s discovery pattern (a fresh,
previously-uncovered passthrough-fidelity angle over already-existing,
unchanged code) is still live, 10 iterations after its last use.

## Plan

1. Extend `packages/quay/test/task-check.test.mjs` (QN-027/QN-069's own
   file) with a new native-Provider compound-passthrough case: create a
   parent task with `--children` set to a mix of a genuinely-done child
   and a still-`todo` child, marked `status: done` itself, and assert
   Core's `taskCheck()` surfaces the `stale-done`-style
   `{gate:"none", ok:false, childrenStatus:[...]}` shape unchanged,
   including a positive "all children genuinely done" case.
2. Extend `packages/quay-github/test/task-check-passthrough.test.mjs`
   (QN-071's own file) with the GitHub-Provider analog: extend
   `fake-gh.mjs` to optionally serve a **multi**-issue fixture map
   (`FAKE_GH_ISSUES_JSON`, keyed by issue number), since a compound
   GitHub-backed task's gate check fetches each child by a separate
   single-issue GET — backward-compatible, existing `FAKE_GH_ISSUE_JSON`
   callers unaffected. Build a parent issue whose body contains a
   `- [ ] #<child>` checkbox reference (GitHub's own lightweight
   parent/child convention) and assert both `quay-github mcp`'s own
   `task_check` tool and Core's aggregated `quay mcp` `task_check` tool
   surface the compound rollup shape unchanged, for both a "child still
   todo" (ok:false) and "child genuinely done" (ok:true) case.
3. Adversarially verify both new cases have real teeth: (a) native —
   sever the parent/child link (`--children ""`) and confirm the
   passthrough falls back to the plain-leaf `terminal` shape with no
   `childrenStatus` field; (b) GitHub — temporarily force
   `github-client.js`'s `isCompound` guard to `false` in the `done`
   branch (the exact unconditional-rubber-stamp regression QN-012's own
   motivating bug was on the native side) and confirm the same fixture
   now WRONGLY reports `ok:true` with no `childrenStatus`, then restore
   and confirm byte-identical source.
4. No change to `provider-client.js`, `store.js`, `github-client.js`, or
   either `mcp-server.js` anticipated (all already correctly wire this
   through, confirmed by both new test blocks passing on first run) —
   test-coverage/test-infrastructure-only, same as QN-069/QN-071.
