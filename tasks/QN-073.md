## Proposal

Iteration 86 closed a genuine, previously-undiscovered gap in `skeleton`:
Core's `taskCheck()` passthrough had never been exercised, on either
Provider, for a compound (epic) task's `status: done` `childrenStatus`
rollup (QN-012/QN-035). Its independent G3 audit (PASS, with first-party
adversarial verification) left one question explicitly open: whether
iteration 86's find was an isolated pocket, or the edge of a larger
uncovered vein.

This iteration re-applied iteration 86's own methodology (enumerate every
branch of `store.js#check()` and `github-client.js#checkGate()`, and
cross-reference against every existing test file's actual call pattern,
not just filenames) to determine whether further headroom exists.

Systematic enumeration of `check()`/`checkGate()`'s branches on both
Providers: `todo` (author->ready, no compound-specific logic on either
Provider — confirmed by reading both files directly), `ready`
(execute->done — HAS a compound-specific `isCompound`/`childrenOk` guard
on both Providers), `done`-terminal (HAS a compound-specific guard on both
Providers — this is exactly what QN-072 closed), `needs-human` (soft-stop,
no compound logic, already covered by QN-068/QN-069/QN-071), and
`unrecognized status` (fallthrough, no compound logic, already covered).

This leaves exactly one remaining, genuinely distinct gap: the
`status: ready` branch's own compound rollup. This is **not** a duplicate
of QN-072's `done`-branch case — it is a separate `if` block in both
`store.js` and `github-client.js`, with its own `childrenOk` computation,
and critically **it plays a different structural role**: in the `ready`
branch, `childrenOk` is directly ANDed into the gate's own `ok` value
(`const ok = acOk && childrenOk`), so a bug here would silently permit or
block a real `ready -> done` status transition. In the `done` branch
(QN-072's case), the rollup is purely informational/corrective metadata
attached to an already-computed `ok` — the branch's own `ok` value is
`false` specifically *because* it detects the compound task already
claims `done` while a child regressed, which is a different (softer,
after-the-fact-detection) failure mode than the `ready` branch's
gate-blocking role.

Confirmed by direct grep across every `*.test.mjs` file in the repo before
writing any new code: no existing test (`task-check.test.mjs`,
`task-check-passthrough.test.mjs`, `compound-gate.test.mjs`,
`compound-gate-recursive.test.mjs`, `gate-gameability.test.mjs`,
`view-model.test.mjs`, or `mcp-server.test.mjs`) connects a
`status: ready` compound fixture to `connectProvider()`, a real
`quay-native mcp`/`quay-github mcp` subprocess, or `quay mcp`'s
aggregation layer. `compound-gate.test.mjs`'s own Cases 4/5 (which do
exercise the ready-compound branch) call `store.check()` directly,
in-process — never through the MCP transport. This is a genuine,
previously-undiscovered gap, not a manufactured one.

## Plan

1. Extend `packages/quay/test/task-check.test.mjs` (QN-027/QN-069/QN-072's
   own file) with new native-Provider `status: ready` compound-passthrough
   cases: a `ready` epic whose AC is fully checked but a child is still
   `todo` (assert `ok:false`, `gate:"execute->done"`, `childrenStatus`
   array naming the offending child), and a positive case (AC checked, all
   children genuinely `done`, `ok:true`).
2. Extend `packages/quay-github/test/task-check-passthrough.test.mjs`
   (QN-071/QN-072's own file) with the GitHub-Provider analog, reusing the
   existing `FAKE_GH_ISSUES_JSON` multi-issue fixture mode QN-072 already
   added: a `status:ready`-labeled parent issue referencing a still-`open`/
   `status:todo` child (negative case) and a genuinely-`closed` child
   (positive case), asserted through both `quay-github mcp`'s own
   `task_check` tool and Core's `quay mcp` aggregation layer.
3. Adversarially verify both new cases have real teeth: (a) native — sever
   the ready epic's children (`--children ""`) and confirm the passthrough
   now reports `ok:true` with no `childrenStatus` field (the epic's own AC
   is fully checked, so this proves the prior `ok:false` was genuinely
   gated on the children check, not AC state); (b) GitHub — temporarily
   force `github-client.js`'s `isCompound` guard to `false` specifically
   in the **`ready`** branch (distinct source location from QN-072's
   `done`-branch adversarial edit) and confirm the same fixture now
   WRONGLY reports `ok:true` with no `childrenStatus`, then restore and
   confirm byte-identical source.
4. No change to `provider-client.js`, `store.js`, `github-client.js`, or
   either `mcp-server.js` anticipated (all already correctly wire this
   through, confirmed by both new test blocks passing on first run) —
   test-coverage/test-infrastructure-only, same as QN-069/QN-071/QN-072.
