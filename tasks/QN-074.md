## Proposal

Iterations 86/87 closed the `skeleton` check()/checkGate()-branch
passthrough-fidelity vein and iteration 87's independent G3 audit
explicitly recommended the next genuinely useful step is a comparably
rigorous fresh search of `abi_symmetry` and `skill_convergence` — both
last genuinely moved a long time ago (`abi_symmetry`: iteration 35's
0.95->0.96 correction, 52+ iterations flat; `skill_convergence`: set at
iterations 0-7, never moved once in 87 iterations).

This task's search: re-derive "the four surfaces" from primary sources
(design §6's table: list/get/write/check, CLI vs MCP tool, one core two
thin bindings) and systematically check each for undiscovered
asymmetries beyond `abi-symmetry.mjs`'s existing 4 happy-path checks
(key-set equivalence for task_list/task_get/task_check, plus key-set AND
value equivalence for task_write).

Found: `task_write`'s CAS option (QN-015, iteration 6) — CLI's
`--expect-status` flag / MCP's `expectedStatus` param, both wired since
QN-015 into the identical `store.write()` CAS check and both throwing the
identical `ConflictError` — has **zero** test coverage anywhere in the
repo for its CLI-vs-MCP error-shape symmetry. Confirmed by an exhaustive
grep across every `*.test.mjs` file before writing any new code:
`cas-write.test.mjs` (QN-015's own test) exercises `store.write()`
directly, in-process, calling neither the CLI binary nor an MCP client —
it never asserts that the CLI's `printJson({error, message, id,
expectedStatus, actualStatus})` conflict shape and the MCP tool's
`{isError:true, structuredContent:{error, message, id, expectedStatus,
actualStatus}}` conflict shape are actually the same schema, which is
exactly design §6's stated requirement ("same schema... CLI is the golden
test harness") applied to an error path, not just the happy path.

This is a genuine, real, previously-undiscovered gap in test coverage of
an existing, already-shipped ABI contract — not a manufactured one:
`--expect-status` literally does not appear in any test file in the repo
before this task (`grep -rn "expect-status" packages/*/test/` returns
nothing pre-task).

## Plan

1. Extend `packages/quay-native/test/abi-symmetry.mjs` (the existing,
   canonical ABI-symmetry harness) with a 5th check block: seed two
   sibling `ready`-status tasks, force a CAS conflict on each surface
   (CLI: `task edit <id> --status done --expect-status todo`; MCP:
   `task_write` with `{status:"done", expectedStatus:"todo"}`), and
   assert the two resulting error shapes are schema-identical (same key
   set) and value-identical (`error`, `expectedStatus`, `actualStatus`
   all matching), plus that both surfaces signal the error condition
   correctly (CLI: non-zero exit + JSON error body; MCP: `isError:true`).
2. Reuse the existing `cliJson`/exec-then-catch-stdout pattern the
   script's own `task_check` block (block 4) already established for
   handling a CLI subcommand that exits non-zero while still emitting
   JSON on stdout.
3. Adversarially verify: temporarily disable the CLI's `--expect-status`
   wiring (`if (flags["expect-status"] !== undefined)` -> `if (false &&
   ...)`), confirm the new check fails loudly (the CLI silently succeeds
   instead of raising a CAS conflict, so the script's own "expected a
   conflict" assertion throws), then restore the file byte-identical.
4. No change to `store.js`, `mcp-server.js`, or any other production
   source anticipated — this is test-coverage-only, confirming an
   already-correct symmetric implementation, the same shape as QN-069/
   QN-071/QN-072/QN-073's own test-only DoD bar.
