## Proposal
The task detail page (GET /task/:id) renders the task body in a `<pre>` block as raw text. This is a gap from ui_read_capability's "Done when" clause: rendered markdown body is required. The fix is to add a minimal inline markdown-to-HTML renderer in serve.js (no external deps, G5 discipline) that handles the most common markdown constructs found in task bodies: headings (##, ###), bold/italic, unordered lists, ordered lists, horizontal rules, and paragraph breaks. Code blocks and inline code can use `<pre>` / `<code>` respectively. This replaces the bare `<pre>${escapeHtml(t.body)}</pre>` with `<div class="body">${renderMarkdown(t.body)}</div>`.

## Plan
Phase 1: Implement a `renderMarkdown(text)` function in serve.js using string processing (no external library). It should handle: fenced code blocks (``` ... ```), ATX headings (#, ##, ###), bold (**text**), inline code (`code`), unordered lists (- item), ordered lists (1. item), horizontal rules (---), and paragraph breaks. Use a line-by-line state machine approach.

Phase 2: Replace `<pre>${escapeHtml(t.body)}</pre>` in the detail page route with `<div class="body">${renderMarkdown(t.body)}</div>`.

Phase 3: Write browser-automation tests in web-ui-browser.test.mjs verifying: (a) task body is no longer in a bare `<pre>` block at the top level (or the body contains the rendered HTML elements), (b) heading markers like "## Proposal" appear as `<h2>` in the rendered output, (c) AC checkbox lines appear as list items.

Phase 4: Run the full test suite to confirm no regression.
