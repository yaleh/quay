## Proposal
The task list page (GET /) currently shows ALL tasks regardless of status. The "Done when" clause for ui_read_capability explicitly requires filter-by-status capability. This is the highest-priority remaining gap after iteration 1's rendered-markdown-body addition. The fix is to accept an optional `?status=<value>` query parameter in the GET / route handler in serve.js, filter the tasks array before rendering, and display an affordance (a simple set of status-filter links) in the task list page header so users can navigate between filtered and unfiltered views. This is a single-file change to packages/quay/src/serve.js. No external dependencies. The filter must correctly handle: (a) no `?status` param → show all tasks; (b) `?status=todo` → only todo tasks; (c) `?status=done` → only done tasks; (d) unknown status values → empty list (not an error). The implementation must not change any other route behavior.

## Plan
Phase 1: Add filter logic in the GET / route handler of serve.js. After `client.taskList({})` returns all tasks, read `url.searchParams.get('status')` and filter the tasks array. Render filter navigation links (`All`, `todo`, `done`, `ready`, `needs-human`) above the table so the user can switch between views. Highlight the active filter.

Phase 2: Add browser-automation assertions to web-ui-browser.test.mjs verifying: (a) GET / still returns all tasks when no `?status` param is present; (b) GET /?status=todo returns only todo tasks and excludes done tasks; (c) GET /?status=done returns only done tasks and excludes todo tasks; (d) the filter navigation links are present in the page.

Phase 3: Run the full test suite (node --test packages/*/test/*.test.mjs) to confirm no regression (current baseline: 30 pass, 0 fail).
