## Proposal

The task list page (GET /) currently shows tasks in the order returned by the provider (insertion order for native). Users need to be able to sort by id (alphabetical) or by status (grouping same-status tasks together) to improve scannability, especially as the task count grows. This is a high-priority ui_read_capability gap (experiment 3, iteration 3 plan item 1).

Approach: add a ?sort=<value> query parameter to GET /. Supported values: id (alphabetical by t.id) and status (alphabetical by t.status, then t.id as tiebreaker). No sort param (or an unknown value) → default insertion order. A sort navigation UI (similar to the existing filter nav) is rendered so users can switch sort without editing the URL.

Core stays dumb: no backend-specific logic. The sort is applied to the already-fetched allTasks array (after the status filter, if any). No new external dependency.

## Plan

Phase 1 - implement sort logic in GET / handler (serve.js): Read url.searchParams.get('sort') → sortKey (null | 'id' | 'status'). If sortKey === 'id': sort tasks array by t.id (lexicographic). If sortKey === 'status': sort by t.status then t.id (tiebreaker). Otherwise: no sort (insertion order preserved). Sort is applied AFTER the status filter (so /?status=todo&sort=id filters first, then sorts).

Phase 2 - render sort navigation (serve.js): Render a sortNav string similar to filterNav: Sort: Default id status. Active sort is shown as strong text, inactive as links. Sort nav must preserve the active status filter in its href (e.g. if ?status=todo is active, sort links emit /?status=todo&sort=id). Render sortNav in the list page HTML as p.meta.

Phase 3 - tests (web-ui-browser.test.mjs): Seed three tasks with distinct ids and statuses (SORT-A todo, SORT-B done, SORT-C ready). GET /?sort=id: verify SORT-A appears before SORT-B (alphabetical). GET /?sort=status: verify tasks grouped by status. GET /?status=todo&sort=id: verify only todo tasks in response. GET / (no sort): verify all three tasks present.
