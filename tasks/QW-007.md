## Proposal

QW-007 addresses the highest-priority remaining gap in ui_read_capability: the task list
shows all tasks on a single page regardless of count. With 85+ tasks in the real task
store, this is unusable for browsing. The 'Done when' clause for ui_read_capability=1.0
explicitly requires pagination with page-based navigation (?page=N) and a max page size of
20 tasks.

Scope: single-file serve.js modification to the GET / route — apply a page slice after
filtering and sorting, add ?page=N navigation links. No external dependency. Purely
GET-route rendering change (G5 preserved).

## Plan

Phase 1: Add pagination logic to GET / route in serve.js.
- Read ?page=N from searchParams (default: page=1).
- Calculate offset = (page-1) * PAGE_SIZE (PAGE_SIZE = 20).
- Slice tasks: pageTasks = tasks.slice(offset, offset + PAGE_SIZE).
- Compute totalPages = Math.ceil(tasks.length / PAGE_SIZE).
- Render pageTasks (not tasks) for the table rows.

Phase 2: Add page navigation UI to list page.
- Update buildHref() to accept page param (5th param or integrate page into existing helper).
- Render pageNav: Previous/Next links preserving active status/sort/label filters.
- Show pagination info: 'Page N of M (X tasks total)'.
- Previous link disabled (plain text) when page=1; Next link disabled when page=totalPages.

Phase 3: Add browser-automation tests for pagination.
- Seed 25 tasks (PAGE-01 through PAGE-25).
- Verify GET / shows PAGE-01..PAGE-20, not PAGE-21..PAGE-25.
- Verify GET /?page=2 shows PAGE-21..PAGE-25, not PAGE-01..PAGE-20.
- Verify page nav presence and correct href links.
- Verify combined ?page=2&status=todo filter: only filtered tasks paginated.
- Verify GET /?page=1 and GET / are equivalent (page=1 is default).
