## Proposal

Add a `?prefix=<string>` query parameter filter to the Web UI list page in `packages/quay/src/serve.js`. This closes CB-002.

The Web UI list page currently shows all tasks from all experiments in one flat list. The prefix filter follows the same approach as the CLI (QX-002) and MCP (QX-003) changes: a `?prefix=QX` URL parameter filters client-side after fetching, showing only tasks whose id starts with the given prefix.

The UI element: detect unique prefixes across all tasks (the part before the first `-`) and render them as clickable links, similar to the existing status/label nav bars. Active prefix is shown in bold; others are links. "All" link clears the prefix filter.

## Plan

Phase 1: Add prefix filter logic to serve.js list route.
- Parse `url.searchParams.get("prefix")` query parameter
- After fetching all tasks but before status/label filtering, apply prefix filter: keep only tasks where `t.id.toUpperCase().startsWith(prefixFilter.toUpperCase())`
- Apply prefix filter FIRST (before status and label filters, which then operate on the prefix-filtered subset)

Phase 2: Add prefix navigation UI.
- Detect unique prefixes from ALL tasks (before any filter): extract the part of each task id up to (but not including) the first `-` character, collect unique values, sort
- Render as a nav row `Prefix: All · QC · QN · QW · QX` (similar to the existing Filter/Sort/Label rows)
- `buildHref()` function updated to accept and pass through the prefix parameter
- Active prefix shown bold; "All" clears it (omits the prefix param from the URL)
- Show `Prefix:` row only when 2+ distinct prefixes exist (single-experiment workspaces need no clutter)

Phase 3: Add test to `packages/quay/test/serve.test.mjs`.
- Seed tasks with two different prefixes (PFXA-1, PFXB-1) in isolated workspace
- Assert GET `/?prefix=PFXA` returns 200 and includes PFXA-1 but NOT PFXB-1
- Assert GET `/` (no prefix) still returns both tasks (no regression)
- Assert GET `/` includes "Prefix:" nav row with 2+ distinct prefixes
