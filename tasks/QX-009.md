## Proposal

The Web UI list page shows task rows with id/status/role/title/labels but no action button. To advance a task the user must navigate to the detail page and click Advance there — a forced round-trip that 2/3 simulated-user personas flagged (CB-003). The Advance action already exists on the detail page; this task adds it as an inline button on each list-page row for tasks whose current status makes the "advance" action applicable.

Write-surface evaluation (§Core-scope constraints item 6): The Advance action itself already exists on the detail page (not a new action). The list page will POST to the same existing `/task/<id>/action/<actionId>` endpoint. No new backend-specific conditional rendering. Evidence: CB-003 in gap-list (2/3 personas). Core-stays-dumb maintained (same backend-agnostic action composition). G3 dispatched by orchestrator. Write surface: AUTHORIZED.

## Plan

Phase 1: In `serve.js` list route, after building `pageTasks`, fetch applicable actions for each task using `manifest.action_buttons` filtered by `whenStatus` (same logic as the detail page). Add an action column to the table.
Phase 2: For each task with an applicable action button, render a `<form method="post">` button inline in the table row.
Phase 3: On POST, after completing the action, redirect back to the list page with current filters preserved (prefix, status, label, sort, page params carried through the redirect Location header).
Phase 4: Add automated test asserting the button appears in the list page for an applicable-status task and that the POST redirects back to the list (not the detail page).

Note: the action button should only appear for tasks where at least one action button's `whenStatus` matches the task's current status. Tasks with no applicable actions show an empty cell.
