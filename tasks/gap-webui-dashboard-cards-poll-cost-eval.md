**type:** finding

## Finding

**实测（2026-09-17，`.quay/quay-access.log` 近 7 天 8324 条请求）**：`/dashboard/cards?hours=N` 单一端点 6471 次，占总请求量 78%；轮询间隔众数 30s（200 个样本里 98 个落在 30s，其余在 29–32s 区间抖动，符合浏览器 `setInterval(30000)` 的典型抖动）。同期 `/health` 探活 1172 次（14%），真正对应"有人手动点了一下"的导航请求只有约 679 次（8%）。

**⚠️ 先排除了"这是性能急症"的误判**：对生产实例 `100.78.206.100:4173` 直接 `curl` 三次 `/dashboard/cards?hours=3`，单次耗时 22–27ms、响应体 22502 字节——**这个端点本身很便宜**，不是 `gap-webui-dashboard-regressed-to-12-60s-past-two-done-tasks`（已 done，那条修的是 `/dashboard` 整页渲染 12.8–60.5s 的问题）的同类回归。当前**没有**证据表明这个端点在拖慢服务器或造成用户可感知的延迟。

**真正的问题是比例，不是急症**：一个开着的 Dashboard 标签页，仅靠自动刷新就以 30s 一次的频率产生请求，7 天里一个标签页贡献的量级是 78% 的总流量；每多开一个标签页/多一个人常驻观察，这个比例线性增长。22.5KB × 每 30s，单个常驻查看者一周下来是 ~145MB 的重复传输，其中大部分时刻内容很可能没变化（circular pulse 状态、driver 状态等在两次刷新之间经常不变）。这是否值得优化，取决于实际会有多少并发常驻查看者——**本任务是先把这个比例摆出来交给实现者判断，不是预设了"必须换成 SSE/WebSocket"的结论**。`/live` 页面看起来已经用了不同的更新模式，可以参考其实现决定是否复用。

## Decision

**维持现状：保留 30s 轮询，不改为 ETag/304，也不改为 SSE/WebSocket。** 依据是本任务列出的两个实测数字（先复核再引用），**外加五条对照读数**——不是"听起来合理"。

### 一、两个立案数字的复核（引用前先重测）

- **「78% 占比」→ 复核为 66–78%（取决于窗口）。** 滚动 7 天窗口下 `/dashboard/cards` 占全部请求的 66–78%；立案时的 78% 对应其中 09-09/09-10 有 2213/2654 次轮询的密集段。**关键是：这是一个「占比」，不是「负载」——它的分母极小**：同一个 7 天窗口（起点取 09-10T17:09，即最后一次日志条目往前推 7 天）内整台服务器一共只有 **6792 次请求**（≈0.011 req/s），其中本端点 **4482 次**（66.0%）。决定取舍的是绝对量：**~4482 次 / 7 天 = ~0.0074 req/s**（平均 2.25 分钟一次），且到达间隔直方图的众数是 **30s**（300 个样本里 184 个），说明**实际上就是一个常驻标签页**在轮询，不是"很多人在用"。
- **「22–27ms 单次耗时」→ 复核为 17–20ms。** 5 次连测 `time_total` 17.0/17.7/18.5/19.3/19.6ms，且 `time_starttransfer ≈ time_total`（connect 仅 0.3ms）⇒ **确实是服务端耗时，不是网络**。按观测速率计 ≈ **12 s CPU/天**。（立案时的 22–27ms 落在此区间上沿；我另有一次 1116ms 的离群值，是连接/重建抖动，不是稳态。）

### 二、补做的对照（每条都是"若结论为假则会给出不同结果"的读数）

1. **服务端代价不在这个端点上（决定性读数）。** 取生产实例一个 **120s 窗口，期间只到达 1 次** `/dashboard/cards`，服务器仍烧掉 **53.84s CPU = 44.9% 单核**（自 CPU 46.48s + 收割子进程 CPU 7.36s）。⇒ **这是后台周期工作，不是请求处理。**
   **可归因的一项**是 30s 一次的 snapshot 重建 tick（`startDashboardSnapshotRefresh`）：120s 内 4 次重建共消耗 **7.36s 子进程 CPU ≈ 1.84s/次**（两次机制 shell-out）。
   **⚠️ 诚实边界：其余自 CPU 未逐项归因**（develop-ref 后台刷新 / reconcile 定时器 / 各 reader 各占多少，本任务没测）。本决策**不需要**该分解——方向已由第 2 条反向对照定死。本条**只**主张"轮询不是这笔开销的来源"，**不**主张它的逐项构成。
   ⇒ **优化轮询会砍掉「请求数」，不会砍掉「服务端代价」。**
2. **反向对照：打得更多也测不出代价。** 人为打到 **~1.4 req/s（约观测速率的 190 倍）**持续 87s，self-CPU 速率 **0.347 s/s**，反而**略低于**同长度空闲窗口的 **0.387 s/s** ⇒ 该端点的边际 CPU **在噪声之下**。（诚实边界：该实验不足以分辨 19ms/次这个量级——它证明的是"190 倍速率下仍不动针"，不是"单次成本 = 0"。）
3. **ETag/304 在这里是【结构性不可用】，不是"尚未实现"。** 间隔 4s 的两次真实探测，响应体**不同**：`liveCard` 甘特条的 x/width 由挂钟 `now` 推出（亚像素级漂移）、`testsCard` 带 `55m ago → 56m ago`、`sysRaw.ts` 是实时采样戳。逐 key 比对：**8 个 key 中只有 5 个（17110 / 32665 字节 ≈ 52%）在连续两次轮询间逐字稳定**。⇒ 整体载荷校验子**永不命中**；**在这里加 ETag 会是一个"看起来在优化、实际恒不生效"的死机制**（正是硬规则 3b 说的那种更贵的形态）。另外 `Cache-Control: no-store` 是**刻意的**（陈旧卡片正是本端点要修的东西），而条件请求要求客户端存过该响应。按 key 的条件响应可行，但那是为 0.007 req/s 的负载新造一套请求/响应协议。
4. **SSE/WebSocket 收益未被测量到，且"复用 /live"这条前提不成立。** 它会把 0.007 req/s 换成"每个查看者常驻一个 socket"+ 心跳/重连/代理缓冲的机制面。**⚠️ 立案时写的"`/live` 页面看起来已经用了不同的更新模式，可以参考其实现"经查为假**：`serve-live.ts` 渲染的是普通页面，且**全 `packages/quay/src/` 里没有任何 `EventSource` / `text/event-stream` / `WebSocket`** —— `/live` 没有可复用的推送实现。
5. **新鲜度已经最优。** 客户端周期与服务器自己的 snapshot TTL（`DASHBOARD_SNAPSHOT_REFRESH_MS` = 30s）**对齐**，轮询更快拿不到更新的数据；且隐藏标签页**已经不轮询**（`visibilityState` 闸）。即"默认继续加频率"这个选项本来就被结构排除了。

### 三、可复用基线读数（供并发查看者数量变化时重新评估）

| 量 | 实测值（2026-09-17） | 读法 |
|---|---|---|
| 载荷大小 | **32.6 KB / 次**（立案时记的 22.5 KB 已随卡片增加而增长） | `curl -w '%{size_download}'` |
| 单次服务端耗时 | **17–20 ms**（TTFB≈total） | `curl -w '%{time_starttransfer}'` |
| 观测轮询速率 | **0.0074 req/s**（7 天 4482 次）；到达间隔众数 **30s** | `.quay/quay-access.log` 路径频次 + 到达间隔直方图 |
| 单查看者成本（8h/天开着的标签页） | **~960 次/天 ≈ 31 MB/天** | 上两行相乘 |
| 服务端固定开销（与轮询无关） | **~45% 单核**（逐项分解未测，见二.1） | 采样 `/proc/<pid>/stat` 的 `utime+stime+cutime+cstime` |

**⟳ 重新评估触发条件**：成本对查看者数 **V 线性**。当 `V × 31 MB/天` 不再可忽略时重评——例如 **V≈30 ⇒ ~1 GB/天**，届时"按 key 的条件响应"（那 ~52% 逐字稳定的字节）才开始值回它的复杂度。**这里不预设魔法阈值**：上表给的是单查看者常数，乘以实际 V 即可。
